## 问题

BuildMax 当前使用由运维人员创建的账户和一次性登录码。这是明确的 Alpha 引导机制，适合可信的私有使用场景，但不适合需要集中管理账户生命周期的组织。Space 角色已经构成资源边界，因此企业身份接入必须将经过验证的企业身份映射到这些现有边界，同时不能让本地 CLI 和直接模型调用依赖 Server。

## 目标

- 让运维人员能够将私有部署连接到企业身份系统。
- 定义身份、Space 与现有 `owner`、`admin`、`member` 角色之间的关系。
- 让登录、访问权移除和会话失效可观测、可测试。
- 保留当前引导流程，供运维人员建立首次身份连接。

## 非目标

- 面向公众的多租户 SaaS 注册。
- 由 BuildMax 自行维护的密码系统、邮件投递服务或身份目录。
- 在首个企业身份实现阶段加入自定义资源级 ACL。
- 取代 Space 成员关系这一授权边界。

## 待评估方案

| 方案 | 优势 | 主要顾虑 |
|---|---|---|
| 要求使用执行认证的反向代理 | 适合快速实现单个受控部署 | 身份声明和登出语义因代理而异；授权可能变成隐式行为 |
| 原生集成 OpenID Connect | 标准浏览器流程，显式处理身份声明 | 需要设计回调、会话、签发方和密钥轮换 |
| 仅集成 SAML | 在成熟企业中常见 | 实现更复杂，也不太适合作为现代自托管场景的首次集成 |
| 先做 OIDC，后续通过 SCIM 配置账户 | 将交互式登录与账户生命周期分开 | 过渡期内需要明确的入职和离职处理流程 |

可能的方向是先原生支持 OIDC，保留运维引导账户，并记录代理兼容性。这还不是决策；需要了解私有部署实际使用哪些身份提供商，并获取运维人员反馈。

## 待解决问题

- 哪些声明足够稳定，可用于标识用户：签发方加主体、已验证邮箱，还是两者兼用？
- 是否允许即时创建账户，创建时如何分配 Space？
- 如何应用账户停用、角色变化和用户组到 Space 的映射？
- 成员关系变化或用户离职时，哪些会话必须失效？
- 自动化至少需要怎样的服务账户或 API 令牌模型？

## 决策所需证据

- 涵盖签发方信任、声明变化、回调处理和账户关联的威胁模型。
- 对接符合标准的 OIDC 提供商开展端到端测试。
- 从登录码账户迁移到外部托管身份的方案。
- 明确记录运维人员被身份提供商锁在门外时的备用恢复方式。
