# Agent 探索性测试

> **翻译说明：** 本文是[英文原文](../../contribute/exploratory-testing.md)的简体中文派生翻译。若中英文存在语义冲突，以英文原文为准。
> **受众：** 贡献者与测试 Agent · **状态：** 当前有效

通过真实用户旅程，发现固定测试用例尚未描述的失败和使用障碍。留下足够的证据，让另一位贡献者能够复现每项发现，并决定需要做什么改变。

仓库已经具备脚本化验证，以及 Portal 和 Desktop 的交互驱动。本文提供探索方法：选择目标、操作产品、理解结果，再根据观察选择下一步。不增加运行器或自动门禁。探索可以跨越端到端边界；区别在于，探索分支会在使用过程中逐步形成。必需运行的套件仍由[测试指导](testing.md)规定。

## 选择一个旅程

当任务要求探索产品、变更后的流程需要实际操作评审，或尚不清楚应该编写什么回归断言时，使用这条路径。常规机械性修改不要求进行探索性测试。

从用户目标、它为何重要的证据，以及当前约束开始。阅读相关[用户手册](../../../manual/introduction.md)、[当前状态](../current-state.md)和[路线图](../ROADMAP.md)，区分可用行为与计划。已报告的障碍或变更影响的旅程都是合适的起点。用代码定位风险、解释结果，但不能让当前实现成为正确性的唯一定义。

操作产品前，写下简短的探索任务说明：

```text
旅程及其重要性：
用户角色、初始数据、可观察的成功结果：
使用界面与环境；被测源码/构建：
范围、允许的修改、模型模式/费用边界：
时间预算，包含准备、复现、报告和清理：
初始问题或怀疑的风险：
```

如果任务未限定常规选择，自行选择一个相关旅程和 30 分钟预算，说明假设后在已有授权内继续。为证据整理和清理预留最后一部分时间。仅在缺少访问条件，或无法推断的重大范围决策阻碍工作时询问；反复确认不是这套方法的一部分。

以下是起始任务示例，不是强制检查清单，也不代表已有覆盖：

| 旅程 | 可观察的结果 | 首次尝试后的可能分支 |
|---|---|---|
| Portal：提交工作，离开页面，再返回查看结果 | 能找到同一个 Task，理解其 TaskRun 状态，并访问可用结果 | 执行期间刷新；离开再返回；查看失败的运行；在界面提供操作时取消或重试 |
| Desktop：完成首次本地任务 | 用户能发现所需配置、提交工作，并找到对应 Session 和输出 | 未配置模型时启动；切换 Project；中断工作；重新打开 Session |
| CLI/TUI：中断工作，稍后继续 | 用户理解哪些工作已停止、哪些内容已保存，以及如何继续 | 等待时取消；退出后重新打开；检查历史和工作区变化 |

## 准备责任明确的环境

环境选择和生命周期遵循[测试指导](testing.md)。启动基础设施或安装前置依赖前，查看 `./make help` 及相关命令的帮助。使用能够支撑结论的最小环境；Portal/worker 部署方面的结论仍需要该指导规定的 kind 边界。

- 记录提交、工作区是否有未提交修改、实际目标 URL 或二进制，以及运行中的构建如何得到。使用变更后的镜像作为证据前，先重新加载。交互驱动不会代你执行脚本套件中的源码与部署一致性检查；如果无法确认身份，应明确说明。
- 确认环境是本次拥有还是借用。任务自有集群使用文档中的临时 kind 生命周期；常驻的 `buildmaxdev` 集群属于个人。不要为了得到干净起点而重置共享状态。为测试资源使用唯一名称，并记录其 ID。
- 本地旅程使用隔离的运行时目录和可丢弃工作区。开发命令使用持久的 `testing-sandbox`，不会每次创建全新目录。在宣称测试“首次使用”前检查已有状态；若状态属于其他任务或贡献者，不要删除。
- 记录模型响应是脚本回放还是真实推理。固定 E2E 场景适合验证边界，但未必支持任意探索提示词。不要把场景不匹配当成产品缺陷，也不要把脚本响应当成真实模型质量的证据。临时开发会话不会自动接入 E2E mock。当旅程依赖实际生成、工具选择、流式响应或模型错误恢复时，使用已配置的真实模型。探索性测试请求包含在任务范围和预算内使用可用真实模型的授权，包括付费推理，无需每次运行都单独确认。遵守明确的免费限制或费用上限。未指定费用上限时，以少量、围绕探索问题的尝试推进，不要启动批量评估。凭据不可用时，报告该阻碍并继续独立分支。
- 真实模型尝试应记录 provider/model、相关设置、已脱敏的提示词和输出或追踪引用、耗时，以及可获得的 token 用量和费用。无法获取的费用标为未知。根据可观察的状态和结果判断用户目标是否实现，调查失败来自产品、provider、模型行为还是它们的交互。模型存在波动，不意味着观察到的用户失败可以忽略；一次成功尝试也不能构成可靠性评分。
- 确认所选账号、Space 角色、服务和种子数据支持旅程起点。把创建预置数据和特权登录准备记录为环境准备，不能视为新用户能完成这些步骤的证明。

选择可用的交互方式，并保留其证据限制：

| 使用界面 | 入口 | 证据边界 |
|---|---|---|
| Portal | 对现有部署使用 [Portal 驱动](../../../.buildmax/skills/drive-portal/SKILL.md)，或可用的浏览器工具 | 驱动的 `login` 辅助命令通过 kind 签发登录码，不是 Compose 登录助手。`ss` 命令临时展开滚动容器，因此图片不能证明原始视口布局。检查裁切或遮挡时，用支持该能力的浏览器工具截取未修改的视口。 |
| Desktop | 对开发浏览器桥接使用 [Desktop 驱动](../../../.buildmax/skills/drive-desktop/SKILL.md)，或可用的原生 UI 工具 | 驱动使用 DOM `el.click()`，不会操作原生窗口。在宣称控件可用前，通过真实指针/键盘交互确认可见性与点击命中。没有原生证据时，将原生窗口行为标为未测试。 |
| CLI/TUI | 使用隔离目录和工作区的已构建 CLI；参见 [CLI 参考](../../../manual/cli.md)和 `./make help run` | 交互行为需要支持 PTY 的终端。仅有命令输出无法证明焦点、按键处理或屏幕布局正常。 |

具体命令使用链接中的准备指导，不要发明探索命令。缺少交互能力是一项需要报告的限制，不能据此悄悄用后端调用替代用户动作。

## 根据观察探索

1. **先通过用户界面尝试正常旅程。** 使用可见标签、无障碍名称或终端帮助发现操作。观察用户在每一步能知道什么：发生了什么、工作是否仍在继续、下一步能做什么。即使操作成功，也记录其中的阻力。
2. **观察后再选择下一步。** 每次有意义的状态变化后，检查可见状态与相关输出。必要时查看控制台错误或日志；页面外壳成功渲染，或驱动返回 `OK`，都不能证明用户目标实现。保留简短的“动作/观察/下一个问题”记录，让分支选择有据可循。
3. **追踪最值得回答的问题。** 进度提示含糊，可以尝试离开再返回；失败难以理解，可以探索恢复；意外重复，可以检查重复提交。依据证据选择分支，不要求执行下面的所有想法。
4. **先保留异常，再诊断。** 捕获原始状态、输入、资源 ID 和相关证据，再在预算内缩短步骤、从已知起点重试。重试成功也保留首次失败，明确报告间歇性行为。
5. **完成旅程收尾。** 检查结果与最终状态，包括可用历史或输出。如果任务包含修复，先保留修复前的发现，再标明新构建，在独立的一次尝试中验证修复。

选择分支时可以参考这些问题：

- **连续性：** 刷新、返回、离开再进入，或重新打开 Session 后会怎样？是否还能辨认同一项工作？
- **时序：** 状态变化期间重复执行、取消或重试界面提供的操作，会怎样？不同视图的最终状态是否一致？
- **输入与展示：** 用户能否理解空状态、无效输入、长内容、键盘焦点、滚动和窄布局？
- **失败与恢复：** 错误是否解释了后果和可用的下一步？重试是否保留有用工作？
- **归属：** 使用明确准备的测试账号和角色，切换 Space 或 Project 后，上下文与访问权限是否仍易于理解？

后端调用和代码阅读可以用于准备数据或诊断失败，但应与用户旅程分开记录。如果 UI 障碍迫使你绕过界面，记录该障碍，并将后续路径标为“借助额外操作完成”。注入网络或服务故障时，记录注入方式，结论仅限于实际覆盖的边界；浏览器响应覆盖不能证明后端恢复能力。破坏性故障注入仅限自有环境且在任务范围内进行。

## 依据证据判断发现

说明预期及其依据：当前产品承诺、明确的任务要求，或具体的一致性规则，例如“同一个 TaskRun 刷新后仍保留相同的终态结果”。文档与行为不符时，核实哪一方有误；旧设计记录不是验收契约。

在报告中区分以下情况：

| 发现类型 | 记录内容 |
|---|---|
| 已确认缺陷 | 被违反的预期、实际行为、受影响的用户目标和复现证据 |
| 使用障碍 | 观察到的含糊标签、隐藏操作、缺少反馈或额外工作；解释影响，不要把个人偏好当成契约被破坏 |
| 疑似缺陷或产品问题 | 观察、可能解释，以及缺少的证据或决策 |
| 环境或工具阻碍 | 失败的前置条件或交互能力，以及旅程中尚未测试的部分 |

按影响排序：工作丢失或错误访问、无法完成或恢复、可以避免的困惑，最后是外观问题。影响与置信程度、复现稳定性分开记录。看似合理的原因在核实前仍是假设。Agent 自报 PASS、控制台没有错误，或一次重试成功，都不是产品正常的独立证据。

## 报告、清理并沉淀发现

当主要问题已有证据、时间预算耗尽，或访问、费用、安全、工具边界阻止有效进展时结束。某个分支受阻不必阻止范围内其他独立分支。记录实际操作过什么、跳过什么、仍有哪些不确定性；不要把“本次未发现问题”转成产品全面通过或覆盖率百分比。

在已被 git 忽略的 `.artifacts/` 下，为每次探索使用独立目录，保存报告、截图、终端输出及相关日志或追踪。不要复用会被测试套件清空的 E2E 输出目录。清理前保留证据，分享前隐去凭据、登录码和无关隐私数据。

使用以下简短报告结构；不适用的字段可以省略，不要编造数据：

```text
探索任务：旅程、原因、角色、成功条件、范围、耗时
环境：日期、提交/未提交修改、构建身份、使用界面、目标、
      账号角色、初始数据、自有/借用资源
模型：脚本/真实、provider/model 与设置、提示词/输出或追踪、
      耗时、可获得的 token 用量与费用、适用预算
已探索：动作 -> 观察 -> 下一个问题；各分支结果
发现（每项一条）：
  标题、分类、用户影响、置信程度/复现稳定性
  前置条件和已知最短复现步骤
  预期及其依据；实际行为
  证据路径和相关 Task/TaskRun/Session ID
  已知绕行方式；剩余不确定性
未执行或受阻：范围和原因
清理：已删除资源、保留证据、残留资源及其所有者
后续：建议修复或待决策事项、适合的回归范围
```

仅停止自己启动的进程，仅删除本次拥有的资源。即使准备失败，也应遵循自有基础设施的清理指导；检查部分创建的资源，不要假设失败就没有残留。借用环境时，记录无法通过支持的操作删除的资源。不要删除共享数据或他人的集群。

交接时包含发现和证据位置。后续修复时，在能够证明该失败的最低层级增加有针对性的回归测试；依赖交互或展示的缺陷用浏览器回归，跨越部署边界的缺陷运行要求的部署验证。运行[测试指导](testing.md)规定的范围，并更新文档，使其匹配修正后的行为。通过修复或已获授权的工作项沉淀发现，确保评审者能够访问证据；只有本地文件路径不能构成持久的共享证据。工作项的 backlog/issue 归属遵循 [AGENTS.md](../../../AGENTS.md)，避免重复记录。探索发现不会自动授权发布 issue、扩大实现范围，或宣称已经达到 Beta 就绪标准。
