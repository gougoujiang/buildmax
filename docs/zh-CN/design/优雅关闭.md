## 问题

BuildMax 部署会因日常运维而停止：滚动升级会替换服务器 Pod，`docker compose down` 会重启 Compose 栈，节点排空会驱逐 Worker Pod。这些都不是故障，但目前总会被某个组件当成故障。

服务器现在只正确处理了 HTTP 这一部分。当前一次停止会依次造成：已连接的 Portal 流在事件中途断开；正在运行的本地 Worker 会一直阻止进程退出；被终止的 Worker 会让运行卡在 `RUNNING`，直到六小时后由过期运行清理器标记失败；原本应收到运行完成报告的 Conversation 也可能永远得不到通知。

这些问题成因各异，但都源于同一个缺失的决策：**没有任何规则定义进程各部分按什么顺序停止，也没有定义承载运行的进程即将退出时，该运行应得到什么结果。**

## 决策

两项决策需要配套实施。

**分阶段关闭顺序。** 停止过程是一段连续时间预算内的有序序列，不是一组互不相关的 `defer`。顺序遵循一条规则：*一个组件只能在所有依赖它的组件都停止之后再停止。* Worker 需要通过服务器自身的 HTTP API 报告结果，因此 HTTP listener 必须接近序列末尾关闭，而不是像当前代码那样最先关闭。

**第三种停止原因。** 运行时已经区分两种情况：被取消的运行标记为 `CANCELED`，并保留已经产生的内容；进程意外消失则意味着“没有结果可报告”（见 [`internal/agentapp/taskrun/runtime.go`](../../../internal/agentapp/taskrun/runtime.go)）。优雅关闭不属于任何一种：进程提前知道自己将要停止，因此应让运行报告实际发生的情况，而不是沉默数小时后才被判定为遗弃。

### 2.1 调度器停止没有上限

`LocalRunner.Run`（[`internal/server/scheduler/runner.go`](../../../internal/server/scheduler/runner.go)）调用 `cmd.Run`，会一直阻塞到 Worker 进程退出；调度器轮询循环又直接调用它。`Scheduler.Stop` 关闭 `stopCh` 并等待轮询循环，因此停止时正在运行的 Agent 可能让进程等待数小时。在 systemd 或 Compose 下，宽限期最终耗尽，进程被强制终止，后续关闭阶段也无法执行。

开发者对停止的预期形成的位置， 构建和本地开发做。 `K8sJobRunner.Run` [`internal/infra/k8s/job.go`](../../../internal/infra/k8s/job.go)

该循环使用 `context.Background()`，因此调度器即使决定放弃，也无法向子进程发送取消信号。

### 2.2 Worker 完全忽略信号

[`cmd/buildmax-worker/main.go`](../../../cmd/buildmax-worker/main.go) 在 `context.Background()` 上运行。SIGTERM 会触发 Go 默认行为，直接终止进程：运行产生的内容不会上传，没有状态报告，也没有轨迹流。运行会保持 `RUNNING`，直到 `StaleRunReaper`（[`internal/server/scheduler/stale_runs.go`](../../../internal/server/scheduler/stale_runs.go)）默认在六小时后将其标记失败。这个回收器适合处理 Worker *意外消失*，不适合处理 Worker *收到停止请求后正常退出*；后者应在几秒内报告 `worker.run_timeout` 或更准确的终态。

在生产中，这最重要：一个工人囊是一个工作囊，

### 2.3 流式连接占满整个预算

`http.Server.Shutdown` 会关闭 listener，并等待连接变为空闲；它不会取消正在执行的请求，而 Server-Sent Events 处理器通常不会自行返回。处理器等待 `r.Context().Done()`，但关闭过程不会触发它。因此，一个正在观看 Task 的 Portal 页面可能占满完整的 10 秒预算，随后进程退出、连接被删除。关闭必须为流式观察者设置明确的排空信号，不能让它独占整个预算（[`internal/server/handlers/work/stream.go`](../../../internal/server/handlers/work/stream.go)）。

### 2.4 没有明确的排空状态

`readyzHandler`（[`internal/server/health.go`](../../../internal/server/health.go)）检查依赖，但关闭期间仍返回 `ready`。Kubernetes 在 SIGTERM 后不会同步删除 Endpoint，因此传播窗口内 Service 仍会把新请求发送到已经停止监听的服务器，调用方得到连接拒绝，而不是可重试的 503。`terminationGracePeriodSeconds` 和 `preStop`（[`deployment/production/buildmax.yaml`](../../../deployment/production/buildmax.yaml)、[`deployment/buildmax-deploy.yaml`](../../../deployment/buildmax-deploy.yaml)）必须配合排空状态。

## 子代理 Scheduler Worker

### 6.1 两阶段的调度器停机

变为`Stop()`的`Stop(ctx context.Context) bool`，有两个阶段：

1. **停止认领。** 向轮询循环发送信号；它最多完成当前一次轮询，不再认领新任务。
2. **排空调度。** 取消调度 Context，然后在 `ctx` 限定的时间内等待已经进行中的调度，并报告它们是否全部完成。

两种方法仅仅是因为发送不再运行在民意调查循环上.它是这样的，这就是使旧的`Stop`无界的原因：循环是运行代理.它现在运行在自己的 goroutine，一个接一个，这是直线版本的同步.索赔和发送仍然发生在同一民意调查中，没有任何东西之间一个停留可以打断，所以没有索赔但没有发送状态释放。

对于`K8sJobRunner`，第二阶段是即时的：发送是一个`CreateJob`呼叫，工作寿命超过创建它的服务器，这是正确的 运行不需要其计划器继续运行。

对于`LocalRunner`相，第二阶段是跑步实际生活的地方，并且跑步者获得了两个`exec.Cmd`场，为此存在：

```go
cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) }
```

取消发送文本，然后要求工人停止第6.2条定义的方式，如果不这样做,`WaitDelay`会杀死它。 在Windows上,[`internal/infra/proc/kill_windows.go`](../../../internal/infra/proc/kill_windows.go)已经记录了没有礼貌信号，没有设置`Cancel`，默认杀死状态；本地Windows工人在飞行中失去了运行，因为第2.2条的倒退，并且模式部署不是本地参考过程。

发送者必须知道的还有一件事：因为这个过程停止了，所以停止的工人已经报告了自己的结果，并且`cmd.Run`无论如何都会返回一个错误.记录这作为发送失败将取代运行产生的信息，因此一个被取消的文本发送的发送器没有记录任何东西。

## 7. 部署

两个参考表现在服务器部署上获利：

```yaml
terminationGracePeriodSeconds: 45   # > shutdown_grace, with room for preStop
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

`preStop` 睡眠覆盖终点传播:Kubelet 发送SIGTERM并同时移除终点，因此没有它，在那个窗口中被录取的请求会遇到一个闭幕的听者。

工人工作规范每6.3节获得自己的`terminationGracePeriodSeconds`。
