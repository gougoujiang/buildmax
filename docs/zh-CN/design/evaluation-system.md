## 1. 摘要

BuildMax 需要一个衡量产品承诺的评估系统，而不是把当前的编码冒烟测试简单扩充成更大的版本。

该产品是一套共享的 Agent 运行时，通过本地工作台和私有 Space 平台提供。它的有效产出不只是助手回复，而是对工作区或 Space 状态进行有目的、受约束且可解释的变更，并让用户能够检查结果、让运维人员能够治理结果。因此，评估必须覆盖本地执行和 Worker 执行中的能力、可靠性、可信性以及端到端产品结果。

本设计决定 BuildMax 将：

1. 移除当前的 `eval/` 目录、`internal/agenteval` 和现有基准运行器，不保留其任务或结果格式；
2. 在主仓库中创建新的顶层 `evaluation/` 工作区；
3. 定义与提供商和框架无关的自有契约，用于描述任务、评估对象、试验包、评分结果和实验比较；
4. 通过黑盒执行适配器评估构建后的二进制文件和部署 Artifact，而不把内部 Go 函数作为基准接口；
5. 在外部框架各自擅长的领域使用它们——例如使用 Inspect 进行实验控制和统计，使用 Harbor 运行 Terminal-Bench 2.1 及其他容器基准，并将自托管可观测性平台作为可选查看器——但不让任何单一框架拥有 BuildMax 的评估语义；
6. 将公共基准保留为外部参照，而由产品自有测试套件决定 BuildMax 的发布与资格认证；
7. 首先面向维护人员和私有部署运维人员设计，同时明确保留在发布前评估 Space Agent 和 Workflow 的路径。

已接受的产品与治理决策，以及仍需由证据决定的技术选择，记录在[第 15 节](#15-决策)中。

## 2. 问题与当前背景

### 2.1 当前基准回答的问题过于狭窄

当前测试框架会向临时工作区发送一条很短的提示，然后执行一个 Shell grader。其目录包含小型、合成的 Go 任务。这对早期冒烟测试有用，但不能代表当前产品：

- 它主要测量短视野本地编码；
- 它运行一个试验，报告一个二进制通过/失败结果；
- 任务指令和 grader 逻辑共享 Agent 可见的 fixture 目录；
- 用户设置、Hook、Plugin、权限和沙箱配置都可能改变被测对象；
- 格式错误的任务和缺失的 fixture 不一定会使实验可靠失效；
- 它无法区分 Agent 故障、grader 故障和基础设施故障；
- 它不评估 Portal 编排、Worker 执行、Artifact、托管推理、治理或跨界面一致性；以及
- 虽然每次运行都已经生成持久化 trace，但结果格式没有利用 trace 进行评分或诊断。

本设计把现有实现及其格式视为可丢弃的。一些 fixture 思路可能会作为低价值冒烟用例重建，但不以兼容当前目录为目标。

### 2.2 产品已经超出“只评估模型”

BuildMax 的行为由远不止模型本身的因素共同产生：

- 共享 Agent 循环和 BuildMax 修订版本；
- 提供商、模型、推理配置、上下文窗口和输出限制；
- 系统指令、工作区指令、记忆、技能和 Agent 定义；
- 内置工具、MCP 服务器、Plugin 和子代理；
- Hook、权限、审批和沙箱解析结果；
- 本地、Worker 或 Conversation 执行界面；
- 操作系统、容器镜像、资源限制、网络可用性和模型传输；以及
- 运行开始前物化的状态。

因此，被评估的对象是 **Agent 系统配置**，而不是模型名称。无法识别该配置的结果不能支撑模型资格认证或回归决策。

### 2.3 产品正确性有多种证据

单元测试可以证明工具会拒绝无效路径，却不能证明真实 Agent 会稳定地选择正确工具。模型评分器可以评估报告是否有用，却不应决定是否发生了未授权写入。Portal 浏览器测试可以证明结果被显示，却不能证明 Worker 在五次独立试验中都产生了正确业务结果。

BuildMax 应当将确定性测试、行为评估、安全场景、公共基准和生产反馈分别对待。评估系统可以汇总这些证据，但不能把它们压缩成一个具有误导性的单一分数。

## 3. 产品问题

评估系统应回答：

> BuildMax 能否在产品界面与执行边界内，可靠且安全地把用户意图转化为有用、可检查的结果？

这个问题包含四个评估领域：

| 领域 | 问题 | 典型证据 |
|---|---|---|
| 能力 | Agent 能否完成有用的工作？ | 最终状态、测试、Artifact、量表维度 |
| 可靠性 | 它能否持续完成工作，并从常见故障中恢复？ | 重复试验、通过率、故障分类和方差 |
| 信任与控制 | 它是否遵守指令、授权和执行边界？ | 策略与 trace 断言、对抗场景和边界记录 |
| 产品结果 | 完整的本地或 Space 平台流程能否交付预期结果？ | Conversation、TaskRun、Artifact、状态、trace、账本和 UI 证据 |

这些领域分别设有评分卡和门槛。能力不能抵消信任违规，良好的用户体验也不能弥补错误的最终状态。

## 4. 评估使用者

### 4.1 BuildMax 维护者

维护者需要在修改 Agent 循环、指令、工具、适配器、模型默认值、策略或执行环境后，将候选版本与基线比较。系统必须指出逐用例回归、统计不确定性、故障类别、成本和复现路径。

### 4.2 私人部署运营商

运维人员需要用有代表性的私有工作来验证模型和部署配置：

- 已批准的模型是否足以适用于当地和工人使用；
- 预期可靠性，延迟，代币使用和基础设施错误率；
- 工人和车型运输是否遵守预期边界；以及
- 是否部署特定的依赖导致产品故障。

运维人员的数据集和 trace 必须留在部署内，除非运维人员明确导出它们。

### 4.3 Space Agent 与 Workflow 作者

未来的产品界面可能允许 Space 作者在发布 Agent 或 Workflow 前运行私有场景。本设计不承诺该 UI 或数据模型，但要求任务、被测对象、试验和 grader 契约不能假设评估只面向维护者。

## 5. 目标

- 定义独立于模型提供商和评估框架的、稳定且由 BuildMax 所有的评估契约。
- 评估用户和运维人员实际运行的 Artifact：构建二进制、Worker 镜像和已部署界面。
- 让本地与 Worker 执行之间的差异明确且可衡量。
- 优先评估最终状态和可观察结果，而不是自然语言风格。
- 使用持久运行 trace 作为结构化过程证据，但不把精确轨迹匹配作为默认要求。
- 支持重复试验、成对的基线比较、不确定性，以及单独报告的基础设施可靠性。
- 将隐藏 grader 和私有 holdout 与 Agent 隔离。
- 保留足够且有界的证据，以便复现和诊断失败。
- 允许外部基准与分析工具集成，但不要求 SaaS 依赖。
- 将评估工具依赖置于产品运行时和 Go Core 之外。

## 6. 非目标

- 保留当前任务 Markdown、内嵌 Shell grader、结果 JSONL 或基准 CLI 的行为。
- 建立公共排行榜或通用评估 SaaS。
- 把某个公共基准当作 BuildMax 的产品分数。
- 用真实模型试验替代确定性的单元、集成、架构或端到端测试。
- 默认将私有提示、trace、工作区或 grader 输出发送给 BuildMax 或第三方。
- 要求正常 CLI 和 Desktop 使用 Server、Python、Node、Docker 或评估平台。
- 在维护者和运维人员的工作流尚未可靠前，就将评估产品化为 Space 面向能力。
- 未经与人工或确定性标签校准，就宣称 LLM judge 是事实标准。

## 7. 设计原则

### 7.1 结果优先

对于会改变状态的 Agent，正确答案通常是最终环境状态。说“报告已上传”并不能证明 Artifact 存在；说“预订已完成”也不能证明数据库发生了变化。在可行时，确定性的状态检查和契约检查优先。

### 7.2 过程证据，而不是唯一的“正确路径”

Trace 应能回答 Agent 是否使用了禁止工具、越过边界、遗漏必需验证、陷入循环、执行压缩、进行了委派或遇到工具错误。只有当顺序本身属于产品或安全契约时，才应要求精确的工具调用顺序。在边界内得到有效结果的创造性路径应当被允许。

### 7.3 评估实际运行系统

测试辅助器对开发有用，但不是主要能力基准。权威执行适配器应使用构建产物作为被测对象。

### 7.4 区分能力故障与配套故障

Agent 故障、无效任务、基础设施故障、grader 故障、超时和取消代表不同结果。基础设施故障不能被默认为模型故障，也不能从报告中消失。

### 7.5 全局分数不能掩盖严重失败

报告可以提供套件摘要，但不能用加权平均把信任违规变成“通过”，也不能让其他地方的编码质量抵消它。

### 7.6 默认本地优先且保持私有

试验包默认留在生成它们的机器或部署中。导出必须是明确、可审计、受限的操作，并且可以与执行分开。可选的托管工具不应成为评估或正常产品运行的必需依赖。

## 8. 系统模型

拟议的流量是：

```text
dataset + experiment
        |
        v
subject resolver --------> immutable subject manifest
        |
        v
execution adapter --------> isolated trial environment
        |
        v
canonical trial bundle <-- trace + final state + artifacts + usage + errors
        |
        v
graders ------------------> per-dimension scores, labels, explanations
        |
        v
experiment comparison ---> qualification report and gates
```

### 8.1 Task

任务定义：

- 稳定ID，版本，套件，标签和目标评估域；
- 指示或多轮场景；
- 可见的初始状态；
- 执行表面和所需的能力；
- 墙时，转换，工具调用，代币和资源限制；
- 要求和可选的分级；
- 试验计数默认情况；
- 环境和依赖版本；以及
- 关于隐藏的验证和预言。

每个任务都必须通过飞行前：

1. 起始状态尚未满足所需的结果；
2. 他的口语完成了任务。
3. 所有要求的学生都接受预言。
4. 复制的口语运行对所述解释来说足够确定性；以及
5. 试验边界中,Agent不能通过隐藏的级别或预言材料访问。

### 8.2 专题

实体表将评估的配置结，包括：

- 子代理 BuildMax
- 双色图像或容器图像消化；
- 表面和执行适配器版本；
- 提供商的运输，目标模型或别名，推理和产量限制；
- 有效的系统提示和工具方案消化；
- 快速层，技能，插件,MCP，以及Agent定义来源；
- 权限，子和沙箱分辨率；
- 操作系统，架构,CPU，内存和网络配置文件；以及
- 数据集和合同版本。

秘密和完全私人指导机构不属于表格.它们的消化和安全来源识别主题，而不会使结果成为一个凭证或内容存储。 当提供商无法披露确切的模型修改时，表格记录了不确定性而不是发明了精确性。

### 8.3 审判

一项试验是一个主体在一个任务中独立尝试的。

| 状态 | 意思 |
|---|---|
| 通过 | 所有要求的成绩都通过了 |
| 失败 | 执行完成，但一个或多个要求的评级失败 |
| 代理_错误 | Agent运行时间失败，然后产生可测量的结果 |
| 基础设施_错误 | 环境或依赖性不论是Agent能力如何失败 |
| grader_error | 要求的分类不能完成 |
| 时间已过 | 共同任务壁时间预算已过期 |
| 取消 | 实验控制器阻止了试验 |
| 无效_任务 | 飞行前或任务完整性失败 |

### 8.4 尼基试验包

试验组是稳定交换界限。 它包含或安全引用：

- 任务，数据集，实验，主体和试验身份；
- 输入和初始状态消化；
- 终端状态和故障分类；
- 根据保留政策允许的最终回复和结构性结果；
- 持久的痕迹和儿童痕迹参考；
- 工作空间或数据库状态的最终证据；
- 产品身份，哈希和验证输出；
- 标准版本和每尺寸的结果；
- 采用"LLM"的呼叫，工具呼叫，代币，持续时间和资源观测；以及
- 限制繁殖描述。

合同是无BuildMax进程的版本和串行.跑步者和观众可以添加扩展，但资格门只读取BuildMax所有的字段。

## 9. 执行适配器

合同支持多个适配器，因为没有一个环境代表产品：

| 适配器 | 目的 |
|---|---|
| 核/本地核 Agent | 快速的行为工作与共享的本地运行时间相比 |
| 双色球： CLI | 验证运输的本地命令和工作空间行为 |
| 运行时间 Desktop | 检查 UI 呈现下面的本地工作桌平衡 |
| Worker/TaskRun | 检查物质化，非互动执行，Artifact，运输和边界 |
| Conversation | 验证前景答案，可选的Agent任务委托，结构化结果预测和多轮聊天结果 |
| 部署 | 检查复合或Kubernetes依赖性和操作员可见的故障行为 |
| Harbor | 子代理 Run Terminal-Bench |

确定性端到端套件仍然是不同的.它们可能与评估适配器共享环境和进程启动辅助器，但编写模型协议测试和概率实模型测试保留不同的名称，结果和释放解释。

## 10. 评分器

### 10.1 确定性结果评级器

尽可能多的偏好：

- 测试和静态分析；
- 文件，Artifact，方案和内容声明；
- 数据库或API状态验证；
- 授权和所有权检查；
- 部署和依赖性健康证据；以及
- 通过失败加上通过回归检查。

### 10.2 追踪和政策评级

它们检查结构化的事件，而不是散文：

- 禁止或缺失工具使用；
- 论证和范围有效性；
- 批准，和沙箱决定；
- 试验，循环，紧缩和早速停止行为；
- 完成之前需要进行验证；
- 基因和继承政策；以及
- 边界或编辑违规。

现在的可持续的痕迹还没有表达所有所需的事件。 缺失的执行，文件更改，每命令界限和重试证据应该仍然是明确的空白，而不是从自由文本中推断。

### 10.3 标准表

用于不能缩小到状态检查的尺寸，如有用性，深度，覆盖性，清晰性，或是否有必要的澄清.每个尺寸都有独立的结构化标签和`unknown`路径.模型评级器记录了自己的主题和成本。

在模型评级器成为硬门之前，必须根据一个冷的人类标签的集合进行评估，以确定同意，自相一致性，位置或风格偏见和对抗性强度。

### 10.4 人类评级

人类审查校准模型评级，判断任务或评级缺陷，并采样重要生产衍生案例.它不需要在每一次例行实验中，并且后期的人类决定与原始自动结果分开记录。

## 11. 测试套件策略

首个产品所有套房应该是：

| 套房 | 主要目的 |
|---|---|
| 核回归 Agent | 工具循环，恢复，紧缩，并行调用，排列输入，停止 |
| 地方工作台 | 编码，文件，结构化数据，研究，会议，本地Artifact |
| Worker TaskRun | 材料化、托管/直接交付、Artifact、取消、重试和超时 |
| Conversation / Workflow | 意图处理、澄清、委托、结果交付和多轮状态 |

### 18.7 什么改造和运行Harbor适配器

运行它增加了三点，这些是值得阅读的：没有一个是通过测试可达成的，其中两个将会使公布的数字错误而不是缺席。

** 代码需要自己的出口代码.** 代理循环的顶是固定在200，到达它时，可以通过`ExitModelError`出口，与一个无法达到的提供商相同的代码.这些问题是对方的：提供商故障是值得重新尝试的错误，而耗尽的预算是答案 再次尝试它支付了相同的顶，更糟糕的是，会丢弃验证者的判决.该顶现在可以通过`agent.max_iterations`和`--max-iterations`来配置，到达它时，它会出口相关标识符与相关标识符。 顶相关标识符 仍然存在，因此它可以通过测试代码来保护一个工作空间，从而使这个测试代码能够保持一个完整的测试代码。 `7` `iteration_cap` Harbor

**`Limits.Iterations`是装饰.**该合同自第一步以来一直携带了该领域，没有任何适配器将其传递到任何东西：一个任务表示代代数限制运行到二进制的自定义，试验报告了一个没有人应用的绑定.直到上述变化之前，没有旗可以传递到它。

**尝试指数被分配，而不是读取.** Harbor不编号尝试试题名为任务加上随机后音，因此进口商根据开始时间从稳定的排序中对每个任务进行编号.因此，指数是进口的属性而不是外部的身份，并且两个进口的同一工作必须一致，否则对比将每次运行不同的尝试。

** Artifact消化属于包含文件的代码.** 7.3 节将结果变成黑盒测量的消化,Harbor仅记录了命名二进制路径的kwarg.一个从调用者那里获取消化器将让调用者命名一个从未运行过的文件，没有下游任何东西能够检查它.适配器将上传的二进制 hash，并记录；版本和提交来自于容器内传达的二进制.一个错过了消化器的试验被拒绝，而不是没有进口。

**跨越语言界限的事实需要监护，因为故障是沉默的.**试用家庭的设置文件和主题图普都是用Python生成的，并用在Go中。 一边拼写不同的是一个键不是错误载机或地图查找只是错过它所以运行继续与未设置的字段，结果归因于一个从未这样配置的主题.三个测试将这些对对进行：设置键对 `evaluation/adapter`的自己的结构，元数据键对进口者的结构，和Python适配器版本对 相关标识符。 `pins.json`

**一个后台进程留下了Bash命令永远挂在代理中.** 这是一个产品错误，与评估无关，只有运行基准才发现它.Bash工具通过管道读出输出,Go的`Wait`只返回每次写结束关闭时，所以代理在任务中早些时候启动的服务器将管道打开，并在自己的最后期限内打死的命令从来没有返回.一个鱼试验在记录的120秒时间内两个小时坐在一个工具调用上.该工具现在限制了等待。

库已经知道这个故障:`evaluation/adapter/cli.go`记录了它，对于适配器启动的过程.它没有做的就是应用相同的推理，一个级别下，在工具中，它启动自己的命令.在一个地方记录的危险不是一个在所有地方固定的危险，这是值得记住下次一次写下。

**未能得到可用证据的尝试不能带来工作.**在中期中被杀的受试者留下空白的结果包，在二进制编写字节之前， shell 创建文件，并将其作为破产输出合同，输出五份好进口到一个被杀的容器.一个进口降低了试验和记录差距；它不会拒绝工作。

经过对实际输出与源头所建议的比较，有四项较小的发现：试验结果文件是`result.json`，而不是`results.json` Harbor的文件串名称两次；任务是`<org>/<name>`，该任务的任务ID不能容纳，任务过器需要；并且`task_checksum`是空，其中同一树的引用标签.每个任务都是从代码中读取的假设，而不是看到的，并且每个任务在第一次实际进口中都失败了。

**取消一项规律并不是停止一个容器.**Harbor将代理阶段与`asyncio.wait_for`相结合，这是正确的形状和每任务预算，它没有做任何事.取消一个正在等待`docker compose exec`的规律结束了等待；环境只会在客户的每执行时间内结束，适配器从未设置。 CLI

运行超过预算的运行并不略微精确；它根本无法比较，因为排名板上的每个代理都被保持在该预算.适配器现在在清理中收获了集装程序，取消已经运行，这就是使手套的自行时间表有意义.自行预算仍然是Harbor：一个定制代理无法读取它 Harbor将`agent_timeout_sec`传递给单独的预言代理，因此试图执行自己的适配器将重新执行一个每个任务的号码.它没有办法知道。

**成本不能通过带进行往返旅行.** Harbor重新编码代理报告的成本并以美元为浮动，而运行时间则以整数纳米单位为浮动.因此，进口商更喜欢BuildMax的印刷模式包裹，该适配器将其留在试验代理目录中，并且只会在没有包裹时重回Harbor的数字标记恢复成本不完整，因为通过浮动进行圆的总数不应该读为准确。

| 读取或利用Agents级别仪 | 单独的可见和隐藏材料，具有实际执行界限，并具有对抗性测试级别 |
| 评判奖励风格或可操纵 LLM | 适应冷标签，分别的尺寸，允许未知，并保持确定性门权威 |
| 提供商或基础设施噪音报告为回归 | 双运行，重复试验，明确的主题/资源表格以及独立的基础设施状态 |
| 公共任务变得污染或过度适合 | 专用/轮换停机，生产衍生案例，定期任务更新 |
| 试验集成成为敏感数据湖 | 地方/私人默认，边界，编辑，保留，无内容的表格，明确出口 |
| 外部框架发展突破评估 | 采用BuildMax所有版本的合同和适配器的合照测试 |
| 主存储工具负担正常贡献者 | 独立锁和重量命令；确定性存储器检查仍然轻量化 |
| 评分鼓励优化基准而不是产品 | 多个产品领域，质量故障审查，公众基准分离，没有全球分数 |

## 20. 实施所需证据

在选择框架之前，该产品方向被接受。

1. 实际BuildMax故障或手动检查场景的代表集合；
2. 随时的测量和测试结果和信任评级的可用和缺失的踪迹场的清单
由[第18节](#182-追踪证据审计)供应；
3. 黑盒适配器用于本地和工人执行，加上一个图表
构建的适配器和剩余的空隙是
已被[第183节](#183-黑盒适配器的草图)记录；
4. 试验内容，保留和出口的隐私审查；
5. 提供商初始成本和重复估计；
6. 检查/控制器尖和Harbor定制Agent适配器尖
子代理 Terminal-Bench
7. 预言和测量仪评估显示初始任务测量声称能力。

外部实践支持这一方向，但并没有决定BuildMax的产品合同：

- [克斯的Anthropic的Agent评估指导](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
区分任务，试验，评分，转录，结果以及Agent带；建议
复制试验和能力/回归分离；并将最终环境状态视为
与Agent所说的不同。
- [谷歌ADK评估](https://github.com/google/adk-docs/blob/main/docs/evaluate/index.md)
评估最终反应和工具轨迹，包括多轮标准和用户
模拟。
- 采用数据集，解决器，得分器， [检查人工智能](https://inspect.aisi.org.uk/tasks.html)
沙盒，限制和时代，而其[计量](https://inspect.aisi.org.uk/metrics.html)
包括不确定性和间级协议。
- 相关标识符 评估在容器中的任意相关标识符 Agents [Harbor](https://github.com/harbor-framework/harbor)
环境和是官方的带
[Terminal-Bench 2.1](https://www.tbench.ai/leaderboard/terminal-bench/2.1)。
据[2.1 释放](https://www.tbench.ai/news/terminal-bench-2-1)文件，
结果是不同的数据集而不是基线。
- 子代理 [代理基准检查清单](https://github.com/uiuc-kang-lab/agentic-benchmarks/blob/main/ABC.md)
强调任务和结果的有效性，隐藏的地面真理，预言解决器，污染控制，
报告不确定性。
