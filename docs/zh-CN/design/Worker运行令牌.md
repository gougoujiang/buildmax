## 问题

一次 TaskRun 归属于某个用户和某个 Space，但执行它的 Worker 却无法证明这两者中的任何一个。它此前用 `worker.token` 完成认证——一个按字符串比较的、部署级共享密钥，这只能证明调用者是*某个* Worker，无法证明它正在执行哪一次运行、代表谁、又归属于谁。

每条 `/api/worker/*` 路由都会在路径中指名一次运行，因此共享密钥意味着任何 Worker 都能冒充任何运行：读取任意 Space 下所有 Task 的提示文本，把另一个 Space 的运行 `PATCH` 成携带任意输出的 SUCCEEDED，或者向另一次运行的实时流中注入增量。

托管推理让这个问题从"仅仅是松散"变成了"不可持续"。当时网关的策略与配额输入是按 Space 划分作用域的，因此一个不携带任何 Space 信息的凭证，迫使服务器只能从调用者提供的运行 ID 反推出一个 Space。后来 [Client Modes](客户端模式.md) 取消了按 Space 划分的模型策略，让模型目录在整个部署范围内统一可用，但 Worker 仍然需要一个运行作用域的身份，用于路由授权、归因，以及 Space 与运行之间的隔离。

## 决策

服务器在派发一次运行时会签发一个**运行令牌**：一个短期有效的 JWT，其中标明用户、Space 和这次运行，除此之外不授予任何其他权限。每条 `/api/worker/*` 路由都要求携带该令牌，并要求令牌中所标明的运行必须与路径中的运行一致。

它是分三步落地的，而且是刻意为之。托管推理路由第一个采用它,原因是这条路由当时还没有调用方——没有需要设计的兼容期，也没有任何东西需要改两遍——而且它的失败模式不过是一次模型调用失败。只有在一次真实部署已经在它之上稳定运行之后,同一套凭证才接管了那些负责上报已完成工作的路由,因为在那里一旦出错,丢掉的就是工作成果本身;这些路由在一个发布周期内保留了共享的 `worker.token`,用于覆盖升级窗口——即服务器 Pod 尚未重启,却已经派发了一个预期收到运行令牌的新版 Worker 镜像的情形。第三步则把它彻底移除。如今一个 Worker 只持有一个凭证,一次在没有令牌的情况下被派发的运行会在启动时直接失败,而不会退回到一个不指名任何运行的旧密钥上。

### 为什么不复用用户的访问令牌

Worker 执行的是模型选择的 shell 命令。用户访问令牌是一种通用凭证:它能打开该用户所属的每一个 Space,以及 Issue、Conversation、文件和其他 Task。把它交给 Worker,等于把"这次运行可以消耗推理额度"放大成了"模型可以在任何地方冒充这个用户"——其影响范围严格大于它本应替代的那个共享密钥。目标是把结果归因到某个用户,而不是靠凭证冒充来实现这一点。

### 为什么用 JWT 而不是存一个令牌

刷新令牌是存放在 `user_refresh_token` 表中的不透明随机字符串,所以"用一个持久化存储的凭证"这种做法是有先例的。但运行令牌没有沿用这条路:

- 在这里新增一张表代价不小。`AutoMigrate` 没有回退路径,因此任何新增的表结构都要背负相应的回滚成本,而这个凭证不足以证明这份成本是划算的。
- 精确撤销的能力已经通过另一条路径具备了。处理函数本来就要加载这次运行以确认它正在执行中,而一次已经结束的运行会拒绝后续的一切调用。这就是撤销的边界所在,不需要再靠一张令牌表来实现。

## 令牌结构

| 声明 | 值 |
|---|---|
| `typ` | `run` |
| `sub` | 拥有该 Task 的用户 ID |
| `tid` | Space ID |
| `rid` | TaskRun ID |
| `kid` | Task ID |
| `exp` | 签发时间加上 `worker.run_token_ttl` |

使用部署现有的 `jwt_secret` 以 HS256 签名。Worker 从不接触这个密钥——`internal/config/env_spec.go` 中并未把 `BUILDMAX_JWT_SECRET` 标记为 `WorkerNeeds`——因此 Worker 只能出示分发给它的那一个令牌,无法自行签发另一个。

`typ` 使这两类凭证无法互相替代。`parseAccessToken` 已经会拒绝任何 `typ` 不是 `access` 的令牌,因此运行令牌不能被当作用户登录凭证使用;反过来的检查——拒绝把访问令牌当作运行令牌使用——则由运行令牌的解析器负责。

签名与解析的实现放在 `internal/server/` 下的一个小包里,由负责签发的调度器和负责校验的处理函数共用。`internal/core` 不参与其中:这属于传输层的授权问题,不是领域代码。

## 生命周期

1. **在派发时签发。** 调度器认领一个处于 `PENDING` 状态的运行,加载其所属 Task 以获取 Space 和所有者信息,签发一个令牌,并把它交给 `WorkerRunner`。
2. **通过环境变量传递。** `BUILDMAX_RUN_TOKEN` 会到达 Worker 进程:由 `LocalRunner` 追加到子进程环境变量中,由 `K8sJobRunner` 添加到 Pod 的环境变量中。它不会作为命令行参数传递——那样会让凭证出现在 `ps` 的输出里。
3. **在 Worker 的每次调用中使用。** Worker 在它自己发起的所有调用中都出示这个令牌:读取运行信息、上报状态与结果、流式传输输出,以及托管推理。
4. **对照服务器状态进行校验。** 中间件要求令牌所标明的运行必须与路径中的运行一致。推理路由还会额外向存储层确认这次运行确实处于执行中,并且其 Task 所属的 Space 与令牌中的 Space 一致。归因信息永远不会来自请求体。
5. **随运行结束而失效。** 一次已进入终态的运行会拒绝进一步的推理调用;令牌也会按自身的有效期到期,与运行状态无关;而一次始终无人关闭的运行,最终会被"过期运行回收器"判定为失败。

## 这不解决什么

无论这个特性被记录在哪里,都要说明以下这些局限;它们都不是这次设计要解决的问题。

- **到期前无法撤销。** 令牌是无状态的。结束一次运行之所以能停止对网关的调用,是因为路由会检查运行状态,而不是因为凭证本身失效了。一个从 Worker 泄漏出去的令牌,在 `exp` 到期之前始终是签名有效的。
- **有效期必须覆盖最长的运行时长。** `worker.run_token_ttl` 是一项部署级设置,并且没有续期机制。一次运行如果活得比这个时长还长,就再也无法上报任何信息,包括自己的最终结果——这正是需要 `worker.run_timeout` 来关闭这类运行、而不是任其无限期运行下去的原因。
- **Kubernetes 会把它暴露在 Job 规格中。** 这个令牌是一个明文的环境变量值,任何能够读取该命名空间下 Job 对象的人都能读到它。为每次运行创建一个带 owner reference 的独立 Secret 可以解决这个问题,但这次设计特意没有把它纳入第一个版本。
- **沙箱不会向模型隐藏它。** `ScrubEnvList` 本可以在沙箱化的子进程中剔除一个 `_TOKEN` 变量,但当沙箱关闭时,`Manager.ScrubEnv` 会原样返回环境变量——而沙箱关闭正是所有使用面(包括 Worker)当前的默认状态。因此 Worker 会在读取 `BUILDMAX_RUN_TOKEN` 之后,自行把它从自己的环境变量中清除,让这个值只存在于内存中。真正起保护作用的是这一步,而不是擦除列表。
- **它不会收窄对象存储的访问范围。** `internal/config/env_spec.go` 中把 `BUILDMAX_MINIO_ACCESS_KEY` 和 `BUILDMAX_MINIO_SECRET_KEY` 标记为 `WorkerNeeds`,因此一个 Job Pod 除了拿到运行作用域的令牌之外,仍然会拿到部署级的长期存储桶凭证。要去掉这一点,需要一个由服务器签发的、或基于工作负载身份的凭证,把权限收窄到这次运行自己的前缀下,同时又不能把任意文件访问能力搬到服务器里。这是"一次运行只持有它所需要的凭证"这一目标尚未完成的另一半,目前还没有设计方案。
- **它不会锁定模型。** 运行令牌授权的是一次运行,而不是某个模型别名。Worker 仍然可以调用其所属 Space 被授予访问权限的任何别名。把某个批准过的别名与这次运行绑定、并拒绝其他别名,是后续的一步。

## 淘汰共享 Worker 令牌

`worker.token` 是静态的:运维人员用 `deployment/buildmax-secret.example.yaml` 里的 `openssl rand -hex 24`,或者 `deployment/compose/generate-env.sh` 里生成的随机十六进制串生成它一次,此后服务器和每一个 Worker 都读取同一个字符串,直到有人手动轮换它为止。它没有有效期、没有作用域范围,也不携带任何与具体运行相关的信息。校验方式就是字符串比较。

运行令牌取代了它。由于每条 Worker 路由本身在路径中就已经限定了具体的运行,中间件只需要一条规则——令牌中的运行必须等于路径中的运行——而且没有任何一条 Worker 路由有正当理由需要越出它正在执行的那次运行:

```text
GET    /api/worker/task-runs/{task_run_id}
PATCH  /api/worker/task-runs/{task_run_id}
POST   /api/worker/task-runs/{task_run_id}/stream
POST   /api/worker/task-runs/{task_run_id}/artifacts
POST   /api/worker/task-runs/{task_run_id}/llm/completions
```

这一改动所堵住的口子,远不止推理这一项。持有共享密钥的人此前可以读取任意一次运行的输入,也就是每个 Space 下所有 Task 的提示文本;可以把任意一次运行 `PATCH` 成携带任意输出的 SUCCEEDED,相当于替一个自己并不属于的 Space 伪造结果;还可以向任意一次运行的实时流中注入增量。按运行划分作用域之后,这一切都被缩小到了单次运行以内,而且只在这次运行结束之前有效。

由于现在每一条路由都需要一个运行令牌,所以**每一次**被派发的运行都会得到一个令牌,而不只是托管推理的运行——因为即便是直连模式的运行,也需要靠它来上报自己完成的工作。

在此之前,有四个问题必须先解决,而它们现在都已经落实:

| 关注点 | 解决方案 |
|---|---|
| 一次运行如果活得比令牌还久,就会丢失最后一次 `PATCH`,而此前也没有机制去回收卡在 `RUNNING` 状态的运行 | `scheduler.StaleRunReaper` 会把停留在 `SCHEDULED` 或 `RUNNING`、超过 `worker.run_timeout` 的运行判定为失败 |
| 服务器 Pod 在升级过程中派发了一个更新版本的 Worker 镜像,而旧版服务器还没有能力签发令牌 | 中间件曾在一个发布周期内接受共享令牌并给出弃用警告;该发布周期已经过去,这条回退路径也已移除,因此升级顺序是先升级服务器,再升级 Worker 镜像 |
| 运维人员失去了手动驱动某条 Worker 路由的能力 | `buildmax-server run-token <task_run_id>` 可以签发一个令牌,与 `buildmax-server model` 并列 |
| 路由的状态检查此前是围绕一个不携带任何作用域信息的凭证写的 | 见下文 |

### 每条路由分别要求什么

凭证证明的是"哪次运行在调用",而运行状态是另一个独立的问题;每条路由都各自明确地回答这个问题,而不是被动地继承别处的判断。

| 路由 | 要求的运行状态 | 原因 |
|---|---|---|
| `GET` | 任意状态 | Worker 会在认领之前先读取这次运行,此时状态可能仍是 `SCHEDULED` |
| `PATCH` 为 `RUNNING` | `SCHEDULED` | 正是这个认领动作阻止了两个 Worker 同时执行同一次运行 |
| `PATCH` 为某个终态 | 任意状态 | 一次早早就失败的运行,无论走到哪个状态都必须能够上报这个结果 |
| `POST /stream` | 任意状态 | 增量输出只是诊断信息,拒绝它们对这次运行没有任何帮助 |
| `POST /llm/completions` | `RUNNING` | 推理会消耗某个 Space 的配额,因此这次运行一旦停止,推理调用也必须立刻停止 |

### 回退路径已被彻底移除

这是一次性完成的改动,因此不存在"共享密钥仍然打开着部分接口"这种半吊子状态:

- `runScopedWorkerMiddleware` 中的共享令牌分支,以及与之相关的 `Config.WorkerToken`——中间件现在统一委托给 `requireRunToken`,因此无论是需要读取声明内容的路由,还是只需要放行的路由,遵循的都是同一条规则;
- `internal/bootstrap/worker.go` 中的回退逻辑——现在如果一次运行在被派发时没有携带 `BUILDMAX_RUN_TOKEN`,会直接判定失败,而不会去找第二种凭证顶上;
- 配置中的 `worker.token` 和 `BUILDMAX_WORKER_TOKEN`,包括 `internal/config/env_spec.go` 中的 `WorkerNeeds` 标记——一个没有退路可走的 Worker,没有理由再持有它;
- 部署清单、`generate-env.sh`,以及 `tools/mk` 中 kind 引导流程里的这个密钥。

如果一份旧的 `server.yaml` 里还留着 `worker.token`,现在它就是一个不会被读取的失效键。升级顺序应当先升级服务器——正是它负责签发 Worker 出示的那个凭证。

## 验证

以下内容由测试覆盖:

- 运行令牌被当作用户访问令牌使用时会被拒绝,反过来访问令牌被当作运行令牌使用时也会被拒绝;
- 一次运行的令牌无法驱动针对另一次运行的调用;
- 已过期的令牌,以及由另一个部署签发的令牌,都会被拒绝;
- 针对一次已不再执行中的运行发起的调用会被拒绝;
- Space 与运行不一致的令牌会被拒绝;
- 调用台账会记录一次 Worker 调用所对应的用户、Space、Task 和运行;
- 托管模式的 Worker 环境中不含服务商凭证,而直连模式的 Worker 仍会收到它;
- 每一条 Worker 路由都会拒绝为另一次运行签发的令牌,也会拒绝静态的共享密钥、随意伪造的凭证、由另一个部署签名的令牌,以及完全不携带凭证的请求——该测试中的路由表覆盖了这个包注册的每一条路由,因此新增一条路由若忘记要求凭证,测试就会失败;
- 一次被遗弃的运行会被判定为失败,而不是永远停留在 `SCHEDULED` 或 `RUNNING` 状态。

`./make compose smoke managed` 与 `./make kind smoke managed` 提供端到端的覆盖:一个 Worker 针对一个确定性的模拟上游完成一次真实的 Task,并留下一条记录着用户、Space、运行以及运维人员批准的模型别名的调用台账。如果换成使用服务商密钥的 Worker,同样能完成这个 Task,却不会留下这样一条台账记录——正因如此,证据来自这条台账,而不是这次 Task 本身是否成功。

两者都是必需的,因为令牌到达 Worker 的路径有两条:`LocalRunner` 把它放进子进程的环境变量,`K8sJobRunner` 把它放进 Job 规格;一条投递路径能跑通,并不能说明另一条也能。
