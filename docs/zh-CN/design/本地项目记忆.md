>
> 原路线图优先级：P0.5 本地后续工作。CLI/TUI 和 Desktop 在范围内；Portal、worker task run 和 Space Memory 不在范围内。
>
> 有一处落地与 §9.1 不同：直接编辑导致某个 Memory 文件不可用时，会跳过并报告该文件，但写入工具仍保持注册。工具注册表按模型缓存，而文件随时可能变化，因此按文件的瞬时状态撤销工具，充其量只能靠运气生效；"replace 前必须先 read"规则本身就已经拒绝了未读取正文的运行执行替换，这正是撤销工具原本要保护的性质。只有当整个存储库整体无法读取，或本次运行禁用了 Memory 时，两个工具才会一起撤销。
>
> 还有两处较小的差异。其一，Desktop 仅按 Project 缓存运行时（§11.5），因为它总是在 Project 的默认 Workspace 打开，一个 Project 目前恰好只对应一个根目录；只有当 Desktop 具备进入工作树的能力后，才需要更宽的缓存键。其二，Desktop 界面有意保持只读：它列出 Memory 并逐条打开正文；编辑仍通过直接编辑 Markdown 完成，删除和清空使用 `buildmax project forget`，单次运行禁用使用 `--no-project-memory`。`buildmax info` 和 TUI 的 `/info` Memory 标签页在其他界面上展示的是同一份列表。

## 1. 决策

BuildMax 将为 CLI/TUI 和 Desktop 添加一个共享的本地 Project 模型，并让 Project 拥有第一个跨 Session 的 Memory 作用域。

本设计有意将三个概念区分开来：

| 概念 | 含义 | 权威性 | 示例 |
|---|---|---|---|
| Instructions（指令） | Agent 必须遵循的协议 | 规范性 | Runtime system prompt、全局 `AGENTS.md`、工作区 `AGENTS.md`、额外 system prompt |
| Memory（记忆） | Agent 整理的、可能有误但有助于未来工作的记忆 | 描述性 | Session notes、todos、Project 偏好、Project 决策 |
| Session history（会话历史） | 一次任务对话中所发生事情的有序证据 | 历史性 | 用户和 Assistant 消息、工具调用及结果、生命周期记录 |

压缩摘要不会仅仅因为有助于 Agent 记忆就被提升为 Memory。它是 Session History 的有损投影：日志始终保持权威，摘要仍然绑定在它所总结的那个 Session 和分支上。

本地层次结构将变为：

```text
Local Project (stable identity and shared memory)
  ├── Workspace A (one actual execution root)
  │     └── Sessions that ran there
  ├── Workspace B (a worktree of the same Git repository)
  │     └── Sessions that ran there
  └── Project Memory (shared by those sessions)
```

Session 仍然物理存放在 `<BUILDMAX_HOME>/sessions/` 下。Project 成员关系是通过 `project_id` 表达的逻辑关系，并不构成把 Session 捆绑迁移到 Project 目录下的理由。

对于 Git 仓库，一个 Project 覆盖主检出以及所有报告相同 Git common directory 的关联工作树。它不会自动合并互不相关的克隆或无关目录。对于非 Git 目录，一个规范化的根目录对应一个 Project。

Project Memory 存储为 Project 捆绑内的一组小型、用户可读的 Markdown 文件——每条 Memory 一个文件，并配有一个生成的 `MEMORY.md` 索引。每次模型调用只渲染索引，将其作为低权威的上下文块，而不是 system prompt 指令层。当索引行提示相关时，Agent 才会读取某条 Memory 的正文，并且一次只写入一条 Memory。用户可以查看、编辑、删除、清空或禁用它们。已完成的契约不包含任何自动提取流程。

## 2. 为什么必须区分这些概念

"Memory"这个词一直承载着几种互不兼容的含义。这会让存储上的决策看起来比实际更简单，并造成权威性方面的错误：摘要变成了指令，用户偏好变成了不可更改的规则，或者转录记录被当成了经过整理的事实库。

内容的语义类别由其契约决定，而不是由传递给模型时所使用的角色或字段决定。压缩摘要目前可能因实现原因被追加到 system 消息中，但它依然是派生历史。Project Memory 可能作为 user-role 上下文消息被追加，但它仍然不是用户请求。传输方式不能悄悄地提升内容的权威性。

### 2.1 指令

指令说明 Agent 必须做什么。它们由运行时或人编写或选定，而不是从普通的任务经验中推断出来。

现有的指令层保持不变：

1. Runtime prompt 及能力特定的运行时层。
2. `<BUILDMAX_HOME>/AGENTS.md`。
3. `<workspace>/AGENTS.md`。
4. 本次运行的额外 system prompt。

两个 `AGENTS.md` 文件已经提供了所需的全局层和仓库层。Project Memory 不会取代它们，Agent 也永远不会自主写入其中任何一个。当某个观察到的偏好应当升级为强制性策略时，Agent 可以建议修改 `AGENTS.md`，但由用户来决定并执行或授权这一升级。

### 2.2 Memory

Memory 是 Agent 从经验中选取的、认为可能对以后的工作有帮助的信息。它有用，但不具备权威性；它可能不完整、过时或错误，因此必须具备明确的作用域，并且可查看、可编辑、可遗忘。

在本设计之后，BuildMax 有两种 Memory 生命周期：

| 生命周期 | 状态 | 用途 |
|---|---|---|
| 工作 / Session Memory | 现有的 notes 和 todos | 在一个 Session 内的裁剪与压缩过程中，保留当前的决策、约束和工作状态 |
| Project Memory | 已实现的按 Project 存放的 Memory 文件 | 在 CLI/Desktop 的多个 Session 以及相关的 Git 工作树之间，传递稳定的项目知识 |

全局用户 Memory、Space Memory 和可复用的 Agent Memory 仍是独立且不在范围内的概念，本记录不规划这些作用域。全局的强制偏好已经可以作为 `<BUILDMAX_HOME>/AGENTS.md` 中的指令存在；这并不会使其变成用户 Memory。

区分二者的不是作用域，而是来源。用户**明确表述**的偏好具有规范性，属于指令层——由用户编写、用户可见。而 Agent **从重复的交互中推断出**的模式——比如"我提供的选项列表总是被截断到第一项，所以应该把推荐项放在最前面"——是用户从未说过、也可能不认同的东西。关于一个人的未经确认的断言不能写入规范性文件，这正是为什么这一类内容按其来源本质上就属于 Memory，而不是因为存放位置才归为 Memory。§9.2 界定了可以推断到什么程度。

### 2.3 Session History

Session History 是重建一次对话所需的有序记录：

- 用户和 Assistant 消息；
- Assistant 的工具调用及工具结果；
- 由 provider 拥有的消息状态和非文本部分；
- turn、恢复、回退和压缩记录；以及
- Session 范围内 notes 和 todos 的替换记录。

`history.jsonl` 仍然是权威来源。Project Memory 不会被复制进每个 Session 日志，因为那样做会造成过时的快照，并让共享文档看起来像是某个 Session 私有的。`MemoryWrite` 调用及其结果仍会记录在 Session 日志中，作为这次变更的溯源；`MemoryRead` 返回的正文在那里也只是一个普通的工具结果，而 Memory 本身则存放在 Project 捆绑中。

### 2.4 冲突规则

当这些信息源发生冲突时，BuildMax 使用以下语义规则：

1. 指令始终保持规范性，Memory 不能覆盖它们。
2. 用户当前的明确纠正会覆盖过时的 Memory。
3. Session notes 和 todos 描述的是当前任务，通常优先于关于该任务的、更旧的 Project 记忆。
4. Project Memory 只是辅助性上下文，绝不是某个事实仍然成立的证明；当工作区能够直接给出答案时，Agent 应对其进行核实。
5. 压缩摘要只是既往历史的一个有损视图；当用户或诊断界面要查看实际发生了什么时，原始日志记录优先。

这些是语义层面的规则，而不是新增了一层模型角色等级。提示词文本必须明确写出这些规则，因为 provider 的协议并不了解 BuildMax 的这套分类体系。

## 3. 本设计落地前的基线

### 3.1 当时已经具备的能力

本设计落地前，BuildMax 已经具备 Session 本地这一半：

- `NoteWrite` 和 `TodoWrite` 会替换并持久化保存在 Session 日志中的有界状态；
- 该状态在每次模型调用时都会重新渲染，并且能在压缩之后保留下来；
- 压缩前的检查点为模型提供最后一次更新它的机会；
- 压缩摘要会不断累积，并保持分支范围；以及
- 四层指令由 `agentapp` 组合而成。

持久化的 Session 结构已经足够可靠：

```text
<BUILDMAX_HOME>/sessions/
  index.json
  <session_id>/
    meta.json
    history.jsonl
    traces/<run_id>.jsonl
    writer.lock
```

### 3.2 当时缺失的能力

当时没有任何地方能让 Agent 在学到某个项目特定的事实之后、在那个 Session 结束时把它保留下来。用户可以把这样的事实写进 `AGENTS.md`，但这会把描述性的记忆变成强制性的指令，并且要求 Agent 去编写一份它本不该拥有的策略文件。

适合作为 Project Memory 的例子包括：

- 维护者更偏好在这个仓库中使用范围狭窄的表驱动测试；
- 某个被尝试过的库之所以被否决，是因为它无法保存 provider 状态；
- 生成的 fixture 出于某种在代码树中并不明显的原因，被放在了普通测试数据目录之外；或者
- 相同的用户纠正在多个 Session 中反复出现，并且在此处很有用，但又不至于成为每个 Agent 都必须遵守的协议。

不适合放在那里的例子包括：

- "永远不要推送到 main"——这是一条指令；
- 达成某个决定的完整对话过程——这是 Session History；
- "接下来运行失败的测试"——这是一条 todo；
- 一次压缩总结——这是派生出来的 Session History；
- 可以从当前源码中廉价且无歧义地获取到的事实；或者
- 凭证、访问令牌、私钥，或复制进来的机密载荷。

### 3.3 Project 身份与 Session 身份当时是分裂的

Desktop 当时拥有一个私有的 `Project` 记录，包含名称和一个文件夹，存储在 `<BUILDMAX_HOME>/projects/projects.json` 中。CLI 不会解析或记录该 Project。两个界面都把 Session 存放在同一个全局 Session 目录下，而 `session.Meta` 只记录了一个工作区路径，并没有 Project ID。

这造成了明显的不一致：

- CLI 的 `--continue` 选择的是全局最新的 Session，而不是当前仓库最新的 Session；
- TUI 和 Desktop 的 Session 列表都是全局的；
- Desktop 通过匹配工作区路径别名来清除某个项目的 Session；以及
- 一个主检出和它关联的工作树看起来像是不同的文件夹，尽管现有的 Worktree 能力把它们视为同一个仓库。

如果把 Memory 添加到当前的 Desktop Project 上，会让这种分裂固化下来：Desktop 和 CLI 可能针对同一个仓库运行，却读取着不同的 Memory，或者 CLI 完全不读取任何 Memory。因此，共享的 Project 身份必须先于共享的 Project Memory 落地。

## 4. 现有本地布局的经验

本节记录的是观察结果，而不是兼容性目标。这些本地布局是在 2026-08-29 检查的，它们可能独立于 BuildMax 发生变化。

### 4.1 Claude 风格的路径所有权

被检查的 Claude 布局将 Session JSONL 和一个 `memory/` 目录，一起分组存放在一个经过转义的绝对工作区路径之下。它的优点是简单、局部性明显：浏览一个目录即可看到属于一起的 Session 和 Memory。

在 `memory/` 内部，其组织方式是一个索引对应多个文件，每条 Memory 一个文件，而不是单一文档。被检查的实例中有十一条 Memory，正文总计 14.4 kB，而 `MEMORY.md` 索引仅 1.5 kB，其中每一行都是一个链接加一句钩子式说明。每个正文都带有 YAML frontmatter——一个 slug、一句话描述、一个 type、写入它的 Session，以及一个修改时间——然后是事实本身，接着是**为什么（Why）**相信它，以及**如何应用（How to apply）**它。正文之间通过 `[[slug]]` 相互链接，指向一条尚不存在的 Memory 的链接会被当作一个标记来容忍，而不是当作错误处理。有几条正文标明了自己所依据的事实来源，以及上一次针对该来源核实的日期，这正是一条总结昂贵信息的 Memory 能够保持有用、而不用假装自己是最新的方式。

BuildMax 从中汲取的是两个特性。**索引是始终会被加载的部分；正文是按需读取的。** 这正是存储库能够容纳十倍于常驻预算的内容、而常驻成本却不会随之增长的原因。以及**一条 Memory 就是一个文件**，因此两个 Session 记录不同的事实永远不会互相冲突，一次过时的写入最多损坏一条 Memory，而不是整个存储库。

路径同时也是身份标识，这就产生了这里所关心的弱点。同一个 BuildMax 仓库出现了两次：一次是主检出，另一次是每个工作树各自出现一次——二十二个工作树目录，每个都有自己的 Session JSONL。只有主检出的目录持有 `memory/`，而在某个工作树中运行的 Session 读取的正是那一份。也就是说，这种关联对 Memory 做了修复，却没有对 Session 做修复——这直接证明了本记录所提议的这种拆分是必要的,也印证了 §8.2 的论点：物理放置和逻辑所有权不必是同一套层级结构。移动一个检出、通过符号链接打开它，或者使用第二个相关的根目录，仍然会分裂修复层未覆盖到的部分。

BuildMax 采纳了这种可读的、按项目分组的 Memory 捆绑及其"索引加文件"的形态,但不采纳把转义后的路径当作身份标识这一点。

### 4.2 Codex 风格的逻辑项目

被检查的 Codex 布局把物理的 Session rollout 记录在一棵全局的按日期组织的树中，同时单独记录逻辑上的 Project 和根目录关联关系。这证明了一个有用的区分：Session 的存放位置和 Project 的所有权关系不必是同一套层级结构。官方 Codex 文档同样将 CLI 项目描述为由其起始目录界定，而 Desktop 项目可以挂载多个文件夹，本地 Memory 则是一个独立的存储库。参见 [Projects](https://learn.chatgpt.com/docs/projects) 与 [Memories](https://learn.chatgpt.com/docs/customization/memories)。

BuildMax 采纳了逻辑所有权加全局 Session 捆绑的做法。它在 v1 中不采纳任意的多根项目：只有能够证明属于同一个 Git 仓库的多个根目录才会被自动分到一组。

## 5. 目标与非目标

### 5.1 目标

- 为 CLI/TUI 和 Desktop 提供一个权威的本地 Project 身份。
- 让 `--continue`、Session 列表、Session 清除以及 Desktop 分组都基于 `project_id`，而不是依赖路径上的巧合。
- 在相关的 Session 和 Git 工作树之间共享一个有界的 Project Memory。
- 让实际的 Workspace 根目录对工具、沙箱、Hook、工作区配置、diff 以及 `AGENTS.md` 保持明确。
- 让 Memory 可见、可编辑、可清除、可禁用，并能追溯到最后一次修改它的 Session。
- 防止两个 Session 并发更新 Memory 时发生过时写入。
- 保持 CLI 是纯 Go 的单一二进制，并复用现有的 JSON/Markdown 本地存储方式。
- 记录一次运行加载了哪些指令和 Memory 来源，同时不把敏感内容复制进轨迹中。

### 5.2 非目标

- Portal、worker、Space、组织或共享 Server 上的 Project Memory。
- 全局用户 Memory，或跨机器的自动同步（§20）。
- 由无关目录任意组成 Project。
- 仅凭远程 URL 就把两个独立的克隆当作同一个 Project。
- 嵌入向量、向量数据库、语义搜索或检索排序。
- 在每次对话结束时或在后台自动提取 Memory。
- 未经用户明确授权就写入或重写 `AGENTS.md`。
- 把 Session 捆绑迁移到 Project 目录之下。
- 导入 Claude 或 Codex 的 Memory 格式。
- 从 Alpha 版 Desktop 的 `projects.json` 形态做兼容性迁移。

## 6. 领域模型与不变量

### 6.1 Local Project

一个 Local Project 是一个稳定的、不透明的 ID 加上元数据，用来在多个 Session 之间标识同一个本地工作单元。

```go
type Project struct {
    ID               string
    Name             string
    Kind             Kind // git or directory
    DefaultWorkspace string
    GitCommonDir     string // git only
    CreatedAt        time.Time
    UpdatedAt        time.Time
    LastUsedAt       time.Time
}
```

持久化的形态使用明确的 `snake_case` JSON tag，以及仓库现有的不透明公共 ID 生成器。具体的 Go 命名在实现过程中可能会变化，但以下这些不变量不会：

- Project ID 是稳定的，并且是关系键。
- Name 只是展示用的元数据，绝不是身份标识。
- 一个 Git Project 在本地是由其规范化的 Git common directory 标识的。
- 一个目录型 Project 是由一个规范化的绝对根目录标识的。
- `DefaultWorkspace` 是一次新的 Desktop 运行默认打开的位置，而不是该 Project 可能包含的目录集合。
- Project 成员关系永远不会扩大某个工具被允许访问的文件系统根目录。一次运行仍然一次只对应一个 Workspace。

### 6.2 Workspace

Workspace 仍然是一个 Session 当前实际执行所在的具体目录。它决定：

- 文件系统和 Bash 的限制范围；
- 沙箱可写绑定；
- 工作区级别的 Hook、MCP 配置、技能和子 Agent 定义；
- 工作区级别的 `AGENTS.md`；
- Git diff 与工作树操作；以及
- 记录在 `turn_started` 上的路径。

Project Memory 跟随 `project_id`；而上述这些能力跟随 Workspace。切换工作树会改变 Workspace 及由其派生的工作区配置，但 Project 及其 Memory 保持不变。

### 6.3 Session

`session.Meta` 新增 `project_id`：

```json
{
  "id": "<session uuid>",
  "project_id": "<local project id>",
  "workspace": "/repo/.buildmax/worktrees/memory-design"
}
```

对于普通的本地 CLI/Desktop Session，该字段在创建时是必需的，之后不会再改变。一个 Session 可以在属于同一个 Project 的多个 Workspace 根目录之间移动，但不会悄悄地转移到另一个 Project。fork 会继承 Project ID。本地子 Agent 会为了溯源而继承它，但不会继承 Memory 上下文，见 §9.4。

在序列化边界上，这个字段仍然是可选的，因为 task run 及其他非本地 Session 不会仅仅为了满足这个形态,就获得一个虚构的本地 Project。CLI/Desktop 的构造函数会强制执行更严格的本地不变量。

### 6.4 一个 Project 可以覆盖多个工作目录

这是有意为之的，但受到约束：

```text
/work/buildmax                         ─┐
/work/buildmax/.buildmax/worktrees/a  ─┼─ same git common dir ─ one Project
/work/buildmax/.buildmax/worktrees/b  ─┘
```

两个互不相关的目录永远不会被自动合并。两个共享同一个远程仓库的克隆同样不会被合并：远程仓库地址可能会变化，fork 可能共享同一种 URL 形态，而且凭证有时会出现在 URL 中。未来若要支持明确的多根功能，需要它自己的一套边界、UI 和删除规则。

## 7. Project 解析

Project 解析是 CLI 和 Desktop 共用的一个 `agentapp` 操作。它接收一个 Workspace 路径，返回一个 Project 以及规范化后的 Workspace 根目录。

### 7.1 规范化 Workspace

解析器执行以下步骤：

1. 将路径变为绝对路径并清理干净；
2. 在现有的工作区机制已经处理别名的地方，解析文件系统别名；
3. 验证该路径指向一个可访问的目录；以及
4. 询问 Git 该路径是否属于某个工作树。

别名解析意味着要对符号链接求值，而不仅仅是清理字符串。`filepath.Clean` 加 `filepath.Abs`——也就是今天 `workspaceAliases` 所做的事情——对定位器来说是不够的，因为 Git 返回的是它自己拼写的 common directory：在 macOS 上，通过 `/var` 访问到的工作区，和 Git 报告的位于 `/private/var` 下的 common directory 其实是同一个目录，二者绝不能产生两个不同的 Project key。在进行比较或存储之前，比较的双方都要先经过解析。

这种规范化是为查找服务的。Session 仍然会记录运行时选定的那个可用路径，而现有的工作区别名处理逻辑对于旧的或用户手动输入的拼写方式仍然适用。

### 7.2 Git Project 查找

对于一个 Git 工作区，需要同时解析出工作树的顶层目录，以及绝对的 Git common directory。common directory 由主检出和它关联的工作树共享，因此它正是这个功能所需要的本地仓库键。

查找顺序：

1. 查找是否已存在某个 Project，其规范化的 `git_common_dir` 与之匹配。
2. 如果找到，更新 `last_used_at` 并使用它。
3. 如果没有找到，就创建一个新的 Project：分配一个新的稳定 Project ID，名称从工作树的顶层目录派生而来，并把这个工作区设为 `default_workspace`。

common directory 这个路径是一个定位器，而不是一种公开身份。移动整个仓库可能会使它失效。V1 通过用户打开被移动的文件夹时进行的显式重新关联（relink）来处理这一点；它不会向 `.git` 写入未经请求的标记，不会从远程 URL 推断身份，也不会投机性地合并仓库。重新关联流程会展示那些定位器缺失的候选项，并要求用户做出选择；不会有任何启发式规则悄悄地合并 Memory 域。

顺序决定了这一流程是否真的会被触发。一个被移动过的仓库会在查找中落空，于是第 3 步会在用户来得及要求任何东西之前,就已经创建了第二个 Memory 为空的 Project。因此，创建操作必须在目录中存在定位器已无法解析的 Project 时主动声明：新的 Project 会被创建——一次运行永远不会因为命名决策而被阻塞——同时界面会说明创建了一个新 Project，并且有 N 个现有的 Project 定位器缺失，同时指出重新关联命令的名字。如果没有这一步，恢复路径虽然存在，却永远不会被发现，重复创建的结果看起来就像是这个功能本该如此。

### 7.3 非 Git Project 查找

对于非 Git 工作区，查找使用规范化的绝对目录。移动同样需要显式的重新关联。指向同一个既有根目录的符号链接别名不应产生重复的 Project。

### 7.4 解析与损坏

模糊匹配是一个错误，而不是任意选择其中之一。损坏的 Project 索引会从 Project 元数据重建。在重建过程中发现的重复定位器会被报告出来，并且在修复之前不会选中任何一个 Project。

自动创建是安全的，因为它只在 `BUILDMAX_HOME` 下创建元数据，不会编辑仓库本身。一次失败的 Project 写入会阻止创建新的本地 Session，而不是启动一个带着无法持久化的身份的 Session。

可能创建或重新关联 Project 的解析操作，会先获取目录写入锁，在获取锁之后重复一次查找，然后才执行写入。正是这第二次查找，防止了 CLI 和 Desktop 进程在同一个新仓库中同时启动时创建出两个不同的 Project ID。

## 8. 存储

本地布局将变为：

```text
<BUILDMAX_HOME>/
  projects/
    index.json
    writer.lock
    <project_id>/
      meta.json
      memory/
        MEMORY.md      # generated index
        <slug>.md      # one file per memory
        writer.lock

  sessions/
    index.json
    <session_id>/
      meta.json
      history.jsonl
      traces/
      writer.lock
```

### 8.1 Project 元数据与索引

`projects/<project_id>/meta.json` 是 Project 身份与元数据的权威来源。`projects/index.json` 是一个可重建的、用于选取和定位的投影，与 Session 索引平行存在。它包含足够的信息，能够在不打开每一个 Project 捆绑的情况下解析出一个 Workspace。

元数据文件使用私有权限和原子替换。当索引缺失、无效或不一致时，会通过扫描 Project 元数据来重建它。它绝不是 Project 身份的唯一副本。`projects/writer.lock` 是一个操作系统级的建议性锁，围绕创建、重新关联、重命名和硬删除操作；普通的查找操作只读取一份稳定的索引，不需要获取该锁。和 Session 锁一样，内核所有权决定了锁的存活性，一个被遗弃的锁文件不代表任何权威性。

### 8.2 为什么 Session 保持顶层存放

曾经考虑过把 Session 嵌套到 Project 之下，但被否决了。这样做会让目录浏览看起来更整洁，但会把物理所有权和易变的分类耦合在一起：

- 一次 Project 重新关联或修复,可能需要迁移每一个 Session 目录；
- 全局 Session ID、锁、追踪、隐藏的子 Agent 捆绑和索引修复，目前都能在没有 Project 路径的情况下正常工作；
- `--resume <id>` 天然就是一次全局查找；以及
- 未来无 Project 归属或由 Server 端发起的 Session，不需要一个人为构造出来的父目录。

逻辑上的 `project_id` 已经能提供筛选和所有权归属能力，而不必付出这些代价。

### 8.3 Memory 文件

一条 Memory 就是一个文件。`<slug>.md` 是该条 Memory 的权威来源，并且刻意保持人类可读：

```text
projects/<project_id>/memory/
  MEMORY.md            # generated index
  writer.lock
  merge-commit.md
  rejected-sse-transport.md
  fixture-layout.md
```

文件名就是 slug，slug 就是这条 Memory 的身份标识——不存在第二个可能与它不一致的标识符。每个文件由 frontmatter 加正文组成：

```markdown
---
name: rejected-sse-transport
description: SSE was rejected for the event stream; it cannot resume mid-turn
type: project
session_id: <session uuid that last wrote it>
updated_at: 2026-08-29T10:00:00Z
verified_at: 2026-08-29
---

The event stream uses WebSocket, not SSE.

**Why:** SSE was tried in the worker-stream spike and dropped because a
reconnect cannot resume a turn already in flight.

**How to apply:** do not re-propose SSE for streaming without addressing
resume. Related: [[worker-stream-contract]].
```

frontmatter 的字段使用 `snake_case`，与仓库既有的持久化 JSON 约定一致。`session_id` 和 `updated_at` 给每条 Memory 提供了各自的溯源信息，这也是为什么不需要一个附属的元数据文件：此前的单文档设计之所以需要一个附属文件，是因为一个孤立的 Markdown 文件没有地方记录是谁写的它，而按文件维护的 frontmatter 消除了这种需要，而不是把这种需要转移到了别处。

`verified_at` 是可选的，它使得一条 Memory 可以在不声称自己是最新信息的前提下，总结某个获取成本高昂的事实；§9.2 说明了何时应当使用它。

`MEMORY.md` 是一个**生成出来的投影**，而不是手工维护的文件：它在每次写入之后都会从各条 Memory 文件重建一次，与 `projects/index.json` 从 Project 元数据重建的方式完全相同,原因也相同——一个可能与其数据源不一致的索引是一种没有相应能力去弥补的缺陷面。用户编辑的是各条 Memory，而不是索引本身。手动删除的 Memory 文件只会在下一次重建时,悄悄地从索引中消失。

一条正文如果 frontmatter 缺失、无法解析，或者超出预算，会被报告并跳过，而不是被凭空猜测处理。跳过一条 Memory，代价要小于渲染出一行承诺了某个正文、而读取工具却无法返回它的索引行。

v1 中没有 Project Memory 的修订日志。发起写入的那个 Session 已经记录了工具调用及其结果；而把每一次替换都复制进另一个只追加的文件，会在出现留存需求之前,就先创建出一份无边界增长的第二份历史记录。

## 9. Project Memory 契约

### 9.1 内容形态与预算

一个 Project 最多持有 **20 条 Memory**。每条 Memory 的 `description` 最多 **100 个字符**，正文最多 **2,000 个字符**。所有限制都在写入时强制执行，而不是在渲染时被悄悄截断。

之所以设置两套预算，是因为这两部分的成本性质不同。

**索引是常驻成本。** 它在每次调用时都会渲染在消息列表之后，而末尾的这些块永远不会成为下一次调用请求的前缀，因此它们在这个 Project 下每个 Session 的每一次迭代中，都要以全新的 input token 支付一次——而不是每次写入才支付一次。对输入内容加以约束，就从结构上约束了这一成本：二十行,每行是一个 slug 加上一个 100 字符的描述,加起来接近 3,200 个字符，这正是 `RenderSessionState` 已经对 invariants、notes 和 todos 三者合计所施加的上限。渲染器本身也直接强制执行 3,200 这一上限，因此即便单条 Memory 的限制被绕过,手工编辑过的存储库也无法突破这个总上限。

与之相比较的应该是这个上限,而不是额外的 system prompt。额外 system prompt 的上限是 8,192,约束的是用户主动编写、愿意为之付费的规范性文本；而 Project Memory 是模型生成、可能出错的文本，在生成过程中的位置比 system prompt 更靠后，所以它应当遵循和另一个"每次都会渲染"的区块相同的标准。

**正文是检索成本，只有在被读取时才会产生。** 每条正文 2,000 个字符之所以显得慷慨，正是因为它不是常驻的：一条 Memory 完全可以承担把 Why 和 How 都写清楚所需的篇幅，而不必被压缩成一条只靠丢掉理由才能塞进预算的要点。二十条这样的 Memory 加起来在磁盘上是 40 kB，而不会有任何一次运行会把它们一次性全部加载进来。

正是这种拆分让整个方案得以成立。一份始终整体加载的单一文档，必须先删掉一条旧 Memory 才能容纳一条新的；而在这里，增长的代价只是一行索引，压力落在数量以及"写一句值得占用这一行的描述"上，而不是落在知识本身上。

20 是固定的 v1 上限。改变它需要一个具体的用户结果和新的设计决策；这份已完成的范围不会收集产品遥测来自动调优它。

如果直接对文件系统的编辑，导致某个文件不是有效的 UTF-8 或超出预算，那条 Memory 会被报告并跳过（§8.3）。如果整个存储库都无法读取——缺失的目录不算错误，但无法读取的目录算——运行时不会发送一份可能造成误导的部分索引：它会为本次运行禁用整个 Memory 功能，撤下两个工具，并通过诊断信息和运行开始时的界面提示，报告出具体需要修复的内容。一个来源在整个 Session 期间悄无声息地缺失，正是这种报告机制要防止的失败情形，因此 `doctor` 并不是唯一会显示它的地方。

### 9.2 Agent 可以记住什么

工具描述和运行时提示词采用一种以精确为先的策略：

- 记住稳定的项目偏好、决策及其理由、反复出现的纠正、不明显的约定，以及代价高昂的死胡同；
- 不要复制那些当前的文件或命令就能廉价回答的事实；
- 不要存储临时的任务状态、对话叙述，或原始的工具输出；
- 不要把观察结果变成强制性指令；
- 永远不要存储凭证或令人意外的敏感内容；以及
- 当当前证据或用户的说法与某条 Memory 相矛盾时，更新或删除它。

每条 Memory 都带有一个 `type`：

| 类型 | 承载内容 |
|---|---|
| `feedback` | 用户就如何在这个 Project 中工作所给出的指导——既包括纠正，也包括已确认可行的做法 |
| `project` | 持续进行中的工作、目标、决策和约束，这些内容无法从代码或其历史中推导出来 |
| `reference` | 指向外部资源的指针：仪表盘、工单、规格说明 |

在被检查的那个布局中还有第四种类型——用来记录用户是谁的 `user` 作用域——在这里被有意省去了：那属于全局用户 Memory，而 §5.2 已经把它排除在这个按 Project 划分作用域的存储库之外。

一条 `feedback` 或 `project` 正文应先陈述事实，然后说明**为什么（Why）**相信它——它来自何时、取代了什么——最后说明**如何应用（How to apply）**它。正是这种结构，把一条 Memory 和一段孤立的事实碎片区分开来：一个不认同其 Why 的读者，可以基于证据丢弃这条 Memory，而不必去猜测它的依据。

一条 `feedback` 类型的 Memory 记录的应当是用户**想要什么**，而绝不是用户**是什么样的人**。"以给出推荐意见为先，而不是先列出一堆选项"是一种偏好，用户可以纠正它，并且它在下一轮对话中也有用。而"不熟悉并发"则是对一个人的一种评判，它会以仓库层面的事实所不会犯的方式出错：没有任何东西可以用来验证它，它会被沿用好几个月，而用户永远不会被告知答案为什么变了。更糟的是，它还会自我印证——Agent 解释得更多，用户因此适应了这种方式，于是这个推断看起来就像被验证了一样。无论未来是否会引入用户级别的作用域，这条界限都成立，因为 `feedback` 这种类型今天就已经可以承载这样一种评判。

对用户做出的推断需要的是反复出现，而不是灵光一现。同样的纠正在多个 Session 中反复出现，才是证据；而一次让人困惑的交流不是证据，它只属于那一个 Session。正文必须写明它所依据的具体场合，这样用户读到之后才能判断这种模式只是巧合——一句关于某个人的、没有依据的断言无法被人基于证据反驳，而一句注明了依据的断言可以。

`feedback` 正是指令边界受到考验的地方，所以本记录直接把它定下来，而不是让 §2.1 和下面这条"明确说'记住这个'是一个强烈信号"的规则相互拉扯。一条 `feedback` 类型的 Memory 记录的是**用户偏好某种做法，以及原因**；它永远不会变成 Agent 用来援引自身权威性的规则，并且当它与当前的某条指令或用户当前的说法冲突时，它不能被当作证据。当某种偏好应当约束未来每一次运行、无论 Memory 是否启用时，它的正确归宿是 `AGENTS.md`，而应由 Agent 建议这一变更，而不是自行做出。抄近路的诱惑是真实存在的，也应当被预见到：Agent 能写 Memory，却不能写 `AGENTS.md`，所以除非工具描述明确说清楚"记录一条偏好并不等同于采纳一项策略"，否则偏好会不断在存储库中堆积。

判断是否可以录入的标准是：这个事实在任何分支上都成立。Project Memory 是由该 Project 的每一个 Workspace 共享的，所以一个只在得出它的那个分支内成立的结论，不属于这里——它属于 Session 状态，而 `NoteWrite` 已经把它保留在了它真正适用的地方。这是应当预见到的第一种失败模式，而不是一种纯理论上的担忧：一种"每个任务一个工作树"的工作流会持续不断地产生一些读起来像是持久性知识、实则只是阶段性结论的内容,而文档自己举的那个"某个库被否决"的例子，也只有在理由能够超越那条分支时才是持久的。工具描述会用这样的措辞来陈述这一判断标准。

"不要复制文件本身能回答的内容"这条规则需要一处补充，因为被检查的那个布局发现了一种介于"记住"和"重新计算"之间的情况。有些内容重建成本高昂、变化又很缓慢——比如一个多阶段计划目前进行到哪一步，哪些子系统还没建成——即便花足够长的时间去读仓库最终也能得到答案,这样的内容仍然值得写成一条 Memory。这样的一条 Memory 会指明它的事实来源，并把 `verified_at` 设为上一次对照该来源核实的日期，其正文会告诉读者在据此采取行动之前要先去核实。这样做对"这是一份缓存"这件事是诚实的；而一句断言相同事实、却不作说明的话则不是。廉价就能查到的内容仍然不应该变成 Memory。

一句明确的"帮我记住这个项目的这件事"是一个强烈的写入信号。而在不可信的网页或工具输出中偶然看到一次的某个事实则不是。反复出现是"这条信息有用"的证据，但不是"它为真"的证明。

正文可以用 `[[slug]]` 链接到其他 Memory。运行时不会解析、校验或跟随这些链接；它们只是一种阅读辅助，指向一条尚不存在的 Memory 的链接，标记的是"这里有值得写下来的东西"，而不是一个断裂的引用。这套设计的任何部分都不依赖于这个链接图是完整的。

### 9.3 工具接口

主 Agent（本地）会收到两个工具。它们是按操作命名的，而不是按作用域命名的，因为 `NoteWrite` 和 `TodoWrite` 是 Session 范围的工具，同样没有带作用域前缀；如果将来真的设计出第二个 Memory 作用域，在这些工具上加一个作用域参数，会比再造一对新工具更合理，所以不带前缀的命名方式才是更能经受住变化的选择。

`MemoryRead` 接收索引提示值得打开来看的那些 slug：

```json
{ "names": ["rejected-sse-transport", "fixture-layout"] }
```

它会返回这些正文，并把不存在的那些 slug 列出来，而不是直接让整个调用失败。这里需要一个读取工具，这一点和此前单一的、始终整体渲染的文档不同：索引只携带一句描述，不携带真正的知识。

`MemoryWrite` 用于创建或替换恰好一条 Memory：

```json
{
  "name": "rejected-sse-transport",
  "description": "SSE was rejected for the event stream; it cannot resume mid-turn",
  "type": "project",
  "content": "The event stream uses WebSocket, not SSE.\n\n**Why:** ..."
}
```

`content` 为空即表示删除这条 Memory。没有追加模式，也没有强制模式。

并发规则是**只能替换本次运行已经读取过的内容**，而用于比较的 token 永远不会离开运行时环境。创建一条 slug 尚不存在的 Memory 总是会被接受。替换一条已存在的 Memory，则要求本次运行渲染过或读取过磁盘上当前这个版本；运行时会记录它交给模型的每一份正文的摘要值,存放在运行上下文中、与 note 存储库并列，并在加锁的情况下进行比较。如果一个模型只看到过某条 Memory 的索引行,却想去修改它，会被告知先去读取它——这才是诚实的答案，因为它不可能合并一份自己从未见过的内容。

把一个版本 token 发给模型、再指望它原样传回来，等于是把一个决定正确性的 token，交给了整个环路中最不可靠的那个环节，还会多出一种"参数被省略"的情况，而这种情况唯一说得通的兜底方案就是无条件覆盖。

具体操作步骤：

1. 校验 slug、description、type 和正文的预算限制，并在持久化之前应用一个尽力而为的凭证检测器；
2. 获取 Project Memory 的写入锁；
3. 如果是替换操作，比较本次运行读取到的摘要值与磁盘上当前的摘要值；
4. 只有在摘要匹配、或者是创建新条目的情况下,才原子性地写入 `<slug>.md`；
5. 从各文件重新生成 `MEMORY.md`；以及
6. 在有用的工具输出中,返回发生了什么变化以及最终的 Memory 数量。

一旦出现冲突——比如某个并发 Session 的写入，或者用户自本次运行读取正文以来做过的直接编辑——就不会写入任何内容，工具会如实说明。Agent 可以读取当前版本，再自行决定如何合并。

按文件划分粒度是这套机制安全性的主要来源。两个记录不同事实的 Session 会各自触及不同的文件，完全不会产生冲突，因此只有当两次运行真正对同一条 Memory 存在分歧时，才会走到冲突处理这条路径，而一次过时写入的影响范围也只是一条 Memory，而不是整个存储库。写入锁仍然会把各次写入串行化，因为索引会随着每次写入一起重新生成。

### 9.4 读写权限

- 主 CLI/TUI 和 Desktop 的 Agent 会收到索引、读取工具和写入工具。
- 本地子 Agent 三者都不会收到。它们是一个 Session 中运行频率最高的部分，因此如果给它们索引，它们支付常驻成本的频率也会最高；而当父 Agent 需要子 Agent 知道某件事时，可以直接把它写进委派的任务描述里——这比直接交出一整份目录要精确得多。不给它们这些权限，也意味着更小的影响范围：Memory 只会触及用户能够看见并纠正的那些运行。父 Agent 仍然是面向模型的唯一读取者和维护者。
- 在当前这个阶段，无 Project 归属的运行、worker 运行、Portal 运行,以及 Tier 1 对话运行，三者都不会收到。
- 用户可以在 CLI/print 模式下用 `--no-project-memory`，以及在 Desktop 对应的运行控制项中，为某一次运行禁用 Memory。禁用会把索引和两个工具一并移除，这样一次运行就不可能去读取或修改一个它本不被允许查看的来源。

## 10. 模型上下文组成

Project Memory 不会加入可缓存的指令前缀。在每次模型调用时，运行时会在常规历史记录之后、既有的 Session 状态锚点之前，渲染索引——而不是正文：

```text
... conversation history ...

<project-memory project_id="...">
Fallible project recall, not instructions. Each line is a pointer; read a
memory with MemoryRead before relying on or changing it. Current user
messages and verified workspace state override stale entries.

- rejected-sse-transport — SSE was rejected for the event stream; it cannot
  resume mid-turn
- fixture-layout — generated fixtures sit outside testdata/ on purpose
</project-memory>

<session-state>
... notes and todos for this session ...
</session-state>
```

这个顺序是刻意为之的：Project Memory 更旧、更具共享性质；而 Session 状态与当前任务更贴近，因此保留在离生成位置最近的地方。一个空的或被禁用的存储库不会渲染出任何区块。

这个区块：

- 是一条 user-role 的上下文消息，使用的传输方式与既有的 Session 状态锚点相同；
- 会计入上下文窗口和 token 估算；
- 每次请求都会重新生成，因此另一个 Session 已提交的写入，在下一次迭代中就是可见的；
- 从不会被持久化进 Session 历史；以及
- 携带 Project 作用域信息，让模型和轨迹都能识别其来源，同时不会把它当作一条指令。

description 是一个指针，而不是一段模型可以直接据此行动的摘要。这个区块会明确说明这一点，因为这里存在的失败风险，是仅凭一句提示性的钩子就采取行动，却不打开真正携带 Why 的正文——也就是从一个标题就直接得出结论。轮次中读取到的正文是普通的工具结果，会像其他工具结果一样保留在历史记录中；只有索引才会被反复重新渲染。

存储库用于在写入时比较的那些摘要值，会在正文被读取的过程中记录到运行上下文里，并且从不会展示给模型；参见 §9.3。

渲染器会对 description 中字面出现的 `project-memory` 开始或结束定界符序列进行转义。这样做保护的是结构边界，并不会让 Memory 因此变得可信——这正是为什么低权威警告和冲突规则仍然适用于其中的每一行，也适用于读取工具返回的每一段正文。

Prompt 缓存的稳定性并不是把可变的 Memory 放进 system prompt 的理由，缓存成本也不是这个选择所依据的考量。渲染在消息列表之后的区块，本来就已经处于任何可复用前缀之外：历史记录会在下一次调用时不断地增长在它们前面，所以一个末尾区块无论内容是否发生变化，都要以全新的 input token 支付一次。因此，一次 Project 写入不会让任何额外的东西失效。真正的成本是每次调用都要携带这份索引所产生的恒定成本，这正是 §9.1 所约束的对象，而把 Memory 排除在指令层之外的理由，是它较低的权威性。

## 11. 运行时流程

### 11.1 新建 CLI Session

1. 解析出请求中或当前所在的 Workspace。
2. 解析或创建它对应的 Local Project。
3. 创建这个 Session，带上 `project_id` 和 Workspace。
4. 打开 Project Memory 存储库，并把索引投影注册到读取和写入工具上。
5. 从运行时、全局 `AGENTS.md`、当前 Workspace 的 `AGENTS.md`,以及额外提示词构建出各层指令。
6. 运行时分别渲染 Project Memory 和 Session 状态。

Project 解析发生在 `AgentApp` 组装之前，这样 CLI 和 Desktop 就不会各自构建出并行的存储库,或者对身份产生分歧。

### 11.2 恢复与继续

`--continue` 的含义是"继续**当前 Workspace 中**最新可见的那个 Session"。它不再选择全局范围内最新的本地 Session，也不会扩大到整个 Project 范围。

Project 是共享 Memory 的作用域。它有意不作为 resume 的作用域，因为这两者回答的是不同的问题：Memory 关心的是这个仓库当前有哪些事实是真的，而 resume 关心的是用户刚才在进行哪一段对话。这两者在单一检出的场景下是重合的，但恰恰在本设计引入工作树之后就会出现分歧。如果把 continue 的作用域放大到 Project 级别，就会让工作树 B 中的 `buildmax -c` 选中一个记录在工作树 A 中的 Session，并且按照下面的 resume 规则在那里执行——这会把用户的工作根目录在他们不知情的情况下换掉，而这恰恰发生在一种存在的全部意义就是分支隔离的工作流中。

当当前 Workspace 没有任何 Session、而该 Project 有的时候，`--continue` 不会悄悄地借用一个来用。它会报告这个 Project 在其他 Workspace 中总共持有多少个 Session，并指出用来扩大搜索范围的那个 flag（`--continue --project`），使用它之后会在记录下来的那个 Workspace 中恢复，并在第一轮对话之前打印出该根目录。根目录的切换永远不是隐式发生的。

`--resume <session_id>` 仍然是一次全局的、显式的查找。存储下来的 `project_id` 是权威依据：

- 如果记录下来的 Workspace 存在，并且属于那个 Project，就在那里恢复；
- 只有当一个显式指定的 Workspace 覆写项解析到同一个 Project 时，才会被接受；
- 如果解析到了另一个不同的 Project，会被拒绝，并给出一条同时点名这两个 Project 的提示信息；以及
- 一个缺失的 Project 捆绑或缺失的 Workspace，会产生一条可见的、用于恢复"游离 Session"的路径，而不会发生任何静默的重新归属。

TUI 的 Session 选择器默认只显示当前 Project，并提供一个显式的"全部 Project"视图。在全部 Project 视图中，搜索可以包含 Project 名称。由于一个 Project 可能跨越多个 Workspace，选择器会显示每个 Session 所在的 Workspace，并标出那些位于当前根目录之外的 Session；选择其中一个是一次显式的操作，并且会打印出它将要运行在哪个根目录下。选择器之所以可以跨 Workspace 显示，是因为用户正在主动查看这份列表；而 `--continue` 之所以不能，是因为用户此刻并没有在看。

### 11.3 切换工作树

现有的 Worktree 生命周期机制已经把切换操作限制在当前 Git 仓库范围之内。在 Project 解析落地之后，这项检查还会额外证明目标解析出的 `project_id` 是同一个。由 Workspace 派生出的 Hook、技能、MCP、`AGENTS.md`、沙箱、diff 和标题都会跟随目标切换。Project Memory 不会随之改变。

### 11.4 写入 Memory

一次普通的 Agent 轮次，只要识别出了值得持久保存的项目知识，就可以调用 `MemoryWrite`。每次调用只写入一条 Memory。这次写入会在工具返回之前完成提交。随后，这次工具调用及其结果会通过普通的工具边界，提交进 Session 日志，从而让这次变更拥有 Session 和运行层面的溯源信息，而这一点也会反映在该条 Memory 自己的 `session_id` frontmatter 字段中。

替换一条既有的 Memory 要求先读取过它（见 §9.3），所以一次普通的更新操作,通常的形态是"先读后写"，而不是盲目覆盖。这在改变持久性共享状态的路径上，多出了一次工具调用，而在新增一条 Memory 的路径上则不会多出这一次调用。

与 Session notes 不同，Project Memory 没有强制性的压缩前检查点。把某个 Session 中的细节推广到未来的每一个 Session，是一个比"仅仅保留在当前 Session 内部"风险更高的决定。错过一条 Memory 付出的代价只是便利性上的损失；而一条错误的或者敏感的持久性 Memory，却可能误导许多未来的运行。这份已完成的范围不计划加入提取检查点。

### 11.5 Desktop

Desktop 不再自行拥有一个独立的 Project 文件，而是把列出、创建/打开、重命名和解析这些操作，都委托给共享的 Project 管理器。当打开一个已经通过其 Git common directory 而被知晓的文件夹时，会打开已存在的那个 Project，而不是为这个工作树重复创建一个新的。

运行时缓存不能假设一个 Project 只对应一个文件夹。运行时实例以 Project 加实际 Workspace 作为键，或者绑定到某个已打开的 Session 上。按 Project 划分的"待处理消息"和"一次只运行一个"策略仍然可以按 Project 做键；共享身份或共享 Memory 并不要求改变这种并发策略。

Desktop 提供一份只读的 Memory 列表——slug、description、type、每条 Memory 最后一次写入的时间，以及一次打开一条正文。它把 Memory 标注为可能出错的记忆，并把 `AGENTS.md` 留在指令界面中，而不是把两者呈现成同一份列表；`feedback` 类型很容易模糊这个界限，而 §9.2 正是这个界面所遵循的依据。不计划提供 Desktop 专用编辑器、单条删除和启用开关：直接编辑 Markdown 保留了可读文件契约，`buildmax project forget` 负责删除和清空，`--no-project-memory` 负责单次运行禁用，从而不增加第二条控制路径。

## 12. 可见性、轨迹与诊断

每次运行的轨迹都会新增来源相关的元数据，但不包含原始的指令或 Memory 内容。这会在同一次切换中，取代目前的 `prompt_layers` 记录，而不是留下两套用不同方式描述提示词构成的来源：

```json
{
  "type": "context_sources",
  "project_id": "...",
  "workspace": "/repo/worktree",
  "instructions": [
    {"name": "runtime", "chars": 6200},
    {"name": "user_agents_md", "chars": 400},
    {"name": "workspace_agents_md", "chars": 900}
  ],
  "memory": [
    {"name": "project_index", "entries": 11, "chars": 1400}
  ],
  "history_projection": {"compaction_present": true, "chars": 1800}
}
```

这条记录每次运行只写入一次，描述的是这次运行是由哪些内容组装而成的。Session 的 notes 和 todos 被有意排除在外：它们每一轮都会变化，所以一个"每次运行"级别的计数，只会报告运行开始时的那个值，看起来却像是关于这次运行的一个事实。Memory 索引之所以出现在这里，是因为"这次运行是用什么组装出来的"本身就是这次运行的一个属性。而哪些正文被读取过、以及任何一次写入，都是工具调用——它们已经带着各自的时间戳存在于 Session 日志中了，不需要让轨迹再描述一遍。

这取代了目前那种把所有上下文来源都笼统称作"Memory"的倾向。原始内容之所以不进入这份有边界的轨迹，是因为 Session 存储库和 Project 存储库本身已经拥有这些内容，而轨迹的脱敏处理是 fail-open 的。

`buildmax doctor` 会在不包含具体内容的前提下报告：

- 解析出的 Project ID 及其类型；
- Workspace，以及对于 Git 而言,它的 common directory 定位器；
- 存在多少条 Memory、Memory 是否启用，以及索引是否符合预算；
- 因 frontmatter 无法解析或正文超出预算而被跳过的 Memory；
- 重复或缺失的 Project 定位器；以及
- 引用了一个已缺失的 Project 的游离 Session。

## 13. 隐私与信任边界

Project Memory 是私有的本地状态，但它仍然是模型可见的内容。

- Project 目录和文件在受支持的平台上使用 `0700`/`0600` 权限。
- 启用时，索引——也就是每条 Memory 的 slug 和 description——会在每次调用时都发送给所选的模型。只有当 Agent 读取某条 Memory 时，它的正文才会被发送，而对大多数 Memory 来说，大多数轮次都不会发生这种情况。UI 和用户指南必须把这两部分都讲清楚："只有索引会一直被发送"这句话本身就意味着离开本机的信息量有了实质性的减少，而如果夸大这一点，后果会比根本不去这样宣称还要糟糕。
- 写入工具会拒绝明显的机密信息，但没有任何检测器能证明内容绝对安全。Agent 的约定始终是"不要保存凭证或令人意外的敏感信息"。
- 外部文档、工具输出、仓库文件和网页,都不能指使 Agent 去把它们自己记下来。它们是不可信的证据；只有 Agent 才能对经过核实、对该 Project 有用的事实进行整理。
- Memory 内容不能授予工具权限、改变沙箱策略、启用某个插件，或者覆盖 Hook。这些控制项始终保留在模型生成的状态之外。
- 用户的直接编辑会被当作内容接受，但不会被悄悄地重新归类为系统指令。

用户可以在不删除 Session 的情况下清空 Memory，也可以在不删除 Memory 的情况下为某次运行禁用它。清除 Session 不会清空 Project Memory。

## 14. 所有权与架构

这是一次明确的所有权变更。Local Project 现在是 CLI 和 Desktop 共享的运行时概念，而不是 Desktop 本地 UI 状态。

| 职责 | 归属 |
|---|---|
| Local Project 身份、校验，以及 Project Memory 文档契约 | 新增的纯粹能力 `internal/core/localproject` |
| 原子化的 Project 捆绑、两份索引、Memory 锁、摘要值和权限 | 新增的 `internal/infra/localprojectstore` |
| Git 工作树 / common directory 的发现 | `internal/infra/git` |
| Workspace 到 Project 的解析,以及运行时的接线 | `internal/agentapp` |
| 供 Agent 循环使用的通用 Memory 渲染/写入接口 | `internal/core/agent` 中定义的接口，由 `agentapp` 在 Project 存储库之上实现 |
| `MemoryRead`/`MemoryWrite` 及其面向 LLM 的契约 | `internal/tool` |
| Project 范围的 continue/list 命令与 TUI 界面 | `internal/interface/cli` |
| 文件夹选择器,以及 Project/Memory 的展示 | `internal/interface/desktop` |
| Session 成员关系与索引投影 | `internal/core/session`，由 `internal/infra/sessionstore` 负责持久化 |

任何配置或文件系统相关的包都不会进入 `internal/core`。Project 存储接口与其核心模型放在一起，由 infra 层实现，遵循的是 Session 存储所采用的边界。`agentapp` 仍然是 CLI 和 Desktop 共用的唯一运行时组装者。

Desktop、CLI、Session、Agent Loop 以及仓库布局的架构文档随所有权转移一并更新。旧的 Desktop `Project` 及其读写实现已被直接删除，而不是作为兼容层保留。

## 15. 删除与生命周期

Project 的展示、Memory 和 Session 各自拥有独立的破坏性操作：

- 从 Desktop 的导航中移除一个 Project，不会删除它的 Session 或 Memory；这只是一个展示层面的选择，而不是领域模型层面的删除；
- 删除一条 Memory 会移除它的文件和索引中对应的那一行，这个操作与清空整个存储库是分开提供的；
- 清空 Project Memory 会移除所有 Memory 文件，留下一份空索引；
- 清除 Project 的 Session 是按 `project_id` 筛选的，会展示具体的 Session ID，并且不会动到 Memory；以及
- 只有在没有任何 Session 引用某个 Project 捆绑时，或者在一次明确的"分离/删除"决策已经指明了哪些内容将变得不可用之后，才会提供对该 Project 捆绑的硬删除。

这里不存在基于路径的级联删除。从 Git 中移除一个工作树，不会删除这个 Project 或它的 Memory，因为其他工作树和 Session 可能仍然依赖着它们。

全局的 Session 选择器仍然可以显示一个游离的 Session。恢复这样一个 Session 不会悄悄地重建或关联某个 Project；用户需要选择一个替代的 Workspace，并确认这次 Project 关联关系。

## 16. Alpha 切换

这项实现会让 CLI 和 Desktop 一起完成切换：

- 创建共享的 Project 存储库与解析器；
- 为 Session 元数据及其选择器索引新增 `project_id`；
- 把两个界面以及 Project 相关的 Session 操作,都切换到这个共享管理器；
- 新增 Project Memory 存储库、它的索引投影，以及两个工具；
- 移除 Desktop 私有的 Project 类型，以及 `projects.json` 的读写实现；以及
- 在同一个功能系列中,更新架构文档、用户文档、轨迹和测试。

不会有任何双读或迁移逻辑来保留当前 Alpha 版 Desktop 的 `projects/projects.json`。新的存储库可以直接忽略那个文件。没有 `project_id` 的本地 Session，同样被当作旧的 Alpha 数据，在正常启动过程中不会通过路径推断,被自动认领为当前的 Project Session。如果在这次变更落地过程中，一个一次性的开发者导入辅助工具被证明确实有用，它也应当保持为一个显式的命令，并在这种旧格式被视为过时之前被删除。

## 17. 交付阶段

### 第 1 阶段——共享的 Local Project 身份（已完成）

1. 添加核心的 Project 契约与 JSON 捆绑存储库。
2. 添加 Git common directory 与非 Git 根目录的解析逻辑。
3. 为本地 Session 元数据和 Session 索引添加 `project_id`。
4. 让 CLI 的 new/continue/resume 以及 TUI 的 Session 列表具备 Project 感知能力。

6. 保持 Session 在物理上仍是全局的,并验证主检出/工作树的分组是否正确。

第 1 阶段不改变任何模型上下文。它建立起了 Memory 所需要的所有权边界，并且可以独立测试。

### 第 2 阶段——有边界的 Project Memory（已完成）

1. 添加 Memory 文件、frontmatter 解析、锁、摘要值、原子化的单条 Memory 替换，以及生成出来的 `MEMORY.md` 索引。

4. 曾考虑由用户触发的会话审查命令，但它不属于已完成的范围。普通工作中的显式 `MemoryWrite`、直接编辑 Markdown 和现有查看界面，已经提供一条写入路径和一个可见的事实来源，无需增加第二次模型调用或提议界面。
5. 添加轨迹来源元数据以及诊断检查。
6. 为 CLI/TUI 和 Desktop 编写查看/编辑/清空/禁用行为的文档。

### 第 3 阶段——界面控制（按已接受范围完成）

1. Desktop 列出 Memory 并一次打开一条正文；TUI `/info` 和 `buildmax info` 查看同一个存储库。`buildmax project forget` 删除或清空 Memory，`--no-project-memory` 为单次运行禁用它。

## 18. 验收标准

- 在主检出以及一个关联的工作树中分别启动 CLI，两者解析出的 Project ID 和 Project Memory 相同，同时各自保留不同的 Workspace 根目录。
- 两个互不相关的目录，以及两个独立的克隆，都不会被自动合并。
- 在某个工作树中，CLI 的 `--continue` 只会选中记录在该 Workspace 中的 Session，绝不会选中同一 Project 下另一个 Workspace 中记录的 Session；扩大范围必须是显式的，并且会打印出它将运行的根目录。默认的 Session 选择器只显示当前 Project；显式的全 Project 视图和 `--resume <id>` 仍然可用。
- 通过一个符号链接路径访问到的 Workspace，会解析到与 Git 所报告的那条路径相同的 Project，不会因此创建出第二个 Project。
- 打开一个已被移动的仓库,会创建一个新的 Project，并在同一份输出中,报告出未能解析的定位器以及重新关联命令。
- 针对同一个仓库分别打开 Desktop 和 CLI，两者列出的 Project Session 相同，渲染出的 Memory 索引也相同。
- 在一个 Session 中写入的一条 Memory，会出现在同一 Project 下另一个 Session 下一次模型迭代所渲染的索引中，并且在那里也能读取到它的正文。
- 两个 Session 分别写入两条不同的 Memory 都会成功，最终的索引会同时列出这两条。
- 替换一条本次运行未曾读取过的 Memory 会被拒绝，并提示先去读取它。替换一条自本次运行读取以来正文已经发生变化的 Memory——无论是因为某个并发 Session 的写入，还是因为用户的直接编辑——同样会被拒绝，并且保留存储的 Memory 不变。这两种拒绝都仅凭工具的返回结果就能观察到；任何一个工具的输入 schema 中都不会出现 Memory 版本 token。
- 创建一条 slug 尚不存在的 Memory,不需要事先读取即可成功。
- 一段 description 中如果字面包含了 `project-memory` 定界符,渲染时不会破坏这个区块的边界。
- 除非是通过一次显式的 `MemoryRead` 调用，否则任何 Memory 正文都不会被渲染进上下文。
- Project Memory 绝不会出现在 system prompt 的指令层中，索引也绝不会作为一个复制出来的上下文区块,被持久化进 Session 日志。
- 一条 Memory 不能覆盖 `AGENTS.md`、工具权限、Hook、沙箱，或者用户当前的纠正。
- 一个空的或被禁用的存储库不会增加任何 prompt token，也不会暴露任何一个工具。
- 一次本地子 Agent 运行不会渲染任何索引，也不会注册任何工具，但仍然会记录父 Agent 的 `project_id`。
- 一次超出 Memory 数量上限、description 长度限制、正文长度限制，或触发了凭证检测器的写入会失败，并给出有用的、面向模型的输出，同时保留原有存储的 Memory 不变。
- 一个手动编辑过的、frontmatter 无法解析或正文超出预算的 Memory 文件会被跳过，并且会在运行开始时的界面上被点名，而不只是出现在 `doctor` 中，同时不会妨碍其他 Memory 正常渲染。
- 删除一条 Memory 会移除它的文件和索引中对应的那一行；索引是从各文件重新生成的，绝不会为一个已经不存在的文件保留一个条目。
- 轨迹会记录 Project、Workspace、指令层、Memory 数量与索引大小，以及压缩是否发生，但不会存储它们的原始文本。
- 用户可以在 CLI/TUI/Desktop 中查看 Project Memory，直接编辑可读的 Markdown 文件，使用 `buildmax project forget` 删除或清空，并使用 `--no-project-memory` 为单次运行禁用它；这些操作独立于 Session。
- Project/Session 的删除绝不会因为路径上的巧合而产生级联效应。

## 19. 已否决的方案

### 19.1 把 `memory/` 放在一个经过转义的工作区路径下

简单且便于浏览，但路径会因此变成身份标识。工作树、移动和别名会把同一个仓库拆分成好几个互不相通的 Memory 域。稳定的 Project ID 加一个定位器，是避免这种问题所需要付出的一点点额外的层次。

### 19.2 把 Session 迁移到 `projects/<id>/sessions/` 下

物理上的嵌套看起来很直观，但并没有提供任何 `project_id` 本身不能提供的语义能力。它会带来迁移操作、跨 Project 恢复的复杂性，以及为无 Project 归属的 Session 人为构造出一个归属目录的问题，同时还会打乱一个已经拥有全局 ID、锁、索引、轨迹和恢复机制的持久化存储库。

### 19.3 用 `AGENTS.md` 作为 Project Memory

这个方案现成可用，但在含义和所有权上都是错误的。`AGENTS.md` 是一个规范性的用户/仓库指令来源；而 Memory 是模型整理出来的、可能出错的内容。如果让 Agent 去改写 `AGENTS.md`，就等于悄悄地把经验转化成了策略。

### 19.4 把压缩摘要当作长期 Memory

压缩摘要是有损的，并且和特定的 Session、特定的分支绑定。把它提升为长期 Memory，会把任务叙述和过时的结论带入毫不相关的未来 Session 中，同时丢掉了用来纠正它所需要的原始证据。

### 19.5 用远程 URL 或仓库内容来标识 Git Project

远程 URL 会变化，可能泄露凭证，也无法区分不同的克隆；内容哈希会随着提交而变化，并且可能在不同的 fork 之间发生冲突。Git common directory 才是关联的工作树之间那种确切的本地关系，而且不会比这更宽泛。

### 19.6 现在就引入嵌入向量与语义检索

在当前这个规模下，一份由模型自己阅读并选择的索引已经足够作为检索手段，而且它是可检查的、与 provider 无关的、确定性的。嵌入基础设施会在数据量真正需要它之前，就先带来分块、排序、模型兼容性、删除和可解释性等一系列问题。只有当固定上限被证明造成具体问题时，才有理由重新讨论排序；这份已完成的设计不为此收集产品遥测。

### 19.7 每一轮都自动提取 Memory

这会给每一次任务都增加一次模型调用或一套隐藏的推断策略，持久化更多令人意外的内容，并且在用户控制机制被验证之前，就让虚假的 Memory 变得司空见惯。显式的 Agent 写入加上直接的用户编辑，才是更安全的第一个有实测数据支撑的路径。

实际交付的是普通工作中的显式 `MemoryWrite`，以及用户直接查看和编辑。单独的审查命令会增加另一次模型调用和另一条写入流程，但现有路径已经满足需求。

### 19.8 一份统一的、始终整体加载的文档

本记录此前曾规定使用单一的 `MEMORY.md`，长度为几千个字符，每次整体替换，并在每次调用时完整渲染。在检查了另一种形态的一个实际运作中的存储库之后（见 §4.1），这个方案被否决了。

单一文档在三个方面更差。每条 Memory 都是常驻的，所以预算被花在了当前任务并不需要的知识上，并且接纳一条新 Memory 最终就意味着要删掉一条旧的——存储库恰恰在开始变得有用的那个节点上，停止了增长。每一次写入都要在同一份文档上竞争，所以两个 Session 记录互不相关的事实也会毫无必要地发生冲突，而一次过时的写入会危及整个存储库,而不只是一条条目。而且一个必须容纳一切内容的预算，会迫使每条 Memory 被压缩成一句要点，而这恰恰就是**Why**被丢掉、一条 Memory 变成一句无法被证伪的断言的地方。

索引加文件的形态，在更新路径上多花了一次工具调用，并且在使用一段正文之前需要先读取它。这就是上述三个优点所需要付出的代价，而这个代价很小，因为在任何一个给定的轮次中，大多数 Memory 根本不会被读取。

## 20. 已关闭的后续项

本实现以以下范围决策关闭这份记录：

- v1 上限保持为 20 条 Memory 和约 3,200 字符的索引。具体失败可以促成新的设计；本记录不增加分组、排序或自适应容量。
- BuildMax 不收集索引转读取比例、写入频率、冲突或用户纠正方面的产品遥测。工具调用和轨迹仍可作为单次本地运行的诊断证据，而不是分析管道。
- 本地子 Agent 继续不接收 Memory 索引或相关工具。父 Agent 在委派任务中显式提供相关上下文。
- 不提供由用户触发的会话审查命令。Agent 在普通工作中显式写入，用户可以查看或编辑 Markdown 文件。
- 仓库移动后仍以显式的 `buildmax project relink` 作为恢复机制；不会在 Git common directory 中写入标记。
- Desktop 保留按 Project 一次只运行一个任务的协调方式。支持 Desktop 进入工作树或不同并发方式，需要独立的用户结果和设计，而不是扩展 Memory。
- Project 是唯一的跨 Session Memory 作用域。全局用户、Space 和可复用 Agent Memory 不在此处规划，也不能从这种文件格式推断出来。

这些是范围边界，不是实现积压。只有当已完成的 Project Memory 契约无法满足一个已证明的用户结果时，才重新打开其中一项。
