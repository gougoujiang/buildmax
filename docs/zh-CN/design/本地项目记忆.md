## 1. 决策

BuildMax 将为 CLI/TUI 和 Desktop 增加一个共享的本地 Project 模型，并让 Project 拥有首个跨 Session 的 Memory 作用域。

设计将三个概念故意分开：

| 概念 | 含义 | 权威性 | 示例 |
|---|---|---|---|
| Instructions | Agent 必须遵循的协议 | 规范性 | Runtime system prompt、全局 `AGENTS.md`、工作区 `AGENTS.md`、额外 system prompt |
| Memory | Agent 整理的、可能出错但有助于未来工作的回忆 | 描述性 | Session notes、todos、Project 偏好、Project 决策 |
| Session history | 一次任务对话中发生了什么的有序证据 | 历史性 | 用户和 Assistant 消息、工具调用及结果、生命周期记录 |

压缩摘要不会因为有助于 Agent 记忆就被提升为 Memory。它是 Session history 的有损投影；日志保持权威，摘要仍绑定到它所总结的 Session 及其分支。

地方层次结构将成为：

```text
Local Project (stable identity and shared memory)
  ├── Workspace A (one actual execution root)
  │     └── Sessions that ran there
  ├── Workspace B (a worktree of the same Git repository)
  │     └── Sessions that ran there
  └── Project Memory (shared by those sessions)
```

Session 仍物理存放在 `<BUILDMAX_HOME>/sessions/` 下。Project 成员关系通过 `project_id` 表示，是逻辑关系；它不是把 Session 捆绑包移动到 Project 目录中的理由。

对于 Git 仓库，一个 Project 覆盖主检出以及所有报告相同 Git common directory 的关联工作树。它不会自动合并独立克隆或无关目录。对于非 Git 目录，一个规范化根目录对应一个 Project。

Project Memory 是存储在 Project 捆绑包中的一组小型、用户可读的 Markdown 文件：每条 Memory 一个文件，并生成一个 `MEMORY.md` 索引。每次模型调用只呈现索引，将其作为低权威的上下文块，而不是系统提示指令层。索引行显示相关时，Agent 再读取 Memory 正文，并且一次只写入一条 Memory。用户可以查看、编辑、删除、清空或禁用它们。首个实现不提供自动提取流程。

## 2. 为什么必须区分这些概念

“Memory”一词承载了几种互不兼容的含义。这会让存储决策显得比实际简单，并造成权威性错误：摘要变成指令，用户偏好变成不可变规则，或者把转录当成经过整理的事实库。

内容的语义类别由其契约决定，而不是由传递给模型时使用的角色或字段决定。压缩摘要目前可能因实现原因被追加到系统消息中，但它仍然是派生历史。Project Memory 可以作为 user-role 上下文消息追加，但仍不是用户请求。传输方式不能悄悄提升其权威性。

### 2.1 指令

指令说明 Agent 必须做什么。它们由运行时或人员编写/选择，而不是从普通任务经验中推断出来。

目前的指令层仍然是：

1. Runtime prompt 和能力特定的运行时层；
2. `<BUILDMAX_HOME>/AGENTS.md`。
3. `<workspace>/AGENTS.md`。
4. 本次运行的额外 system prompt。

两个 `AGENTS.md` 文件已经提供所需的全局层和仓库层。Project Memory 不会取代它们，Agent 也绝不会自主写入其中任何一个。当观察到的偏好应升级为强制策略时，Agent 可以建议修改 `AGENTS.md`，但由用户决定并执行或授权这种升级。

### 2.2 Memory

Memory 是 Agent 从经验中选择、认为可能改善后续工作的内容。它有用，但不具备权威性，可能不完整、过时或错误，因此必须有明确范围、可检查、可编辑且可遗忘。

本设计之后，BuildMax 有两种 Memory 生命周期：

| 生命周期 | 现有或规划中的状态 | 用途 |
|---|---|---|
| 工作/Session Memory | 现有 notes 和 todos | 在一个 Session 的裁剪与压缩过程中保留当前决定、约束和工作状态 |
| Project Memory | 规划中的按 Project 存储的 Memory 文件 | 在 CLI/Desktop Session 及相关 Git 工作树之间传递稳定的项目知识 |

全球用户内存，空间内存和可重复使用的Agent内存仍然是分离的未来范围.全球强制偏好已经可以成为`<BUILDMAX_HOME>/AGENTS.md`中的指令；这并不使其成为用户内存。

区分二者的不是范围，而是来源。用户**明确说出的**偏好具有规范性，属于用户编写且可见的指令层。Agent **从重复交互中推断出的**模式——例如“我提供的选项列表总被截断为第一项，因此应先给出推荐项”——并非用户明确表达，用户也可能不同意。未经确认的个人断言不能写入规范文件，因此这类内容按其来源属于 Memory，而不是指令。§9.2 会限制允许推断的内容。

### 2.3 Session History

Session History 是重建一次对话所需的有序记录：

- 用户和 Assistant 消息；
- Assistant 工具调用和工具结果；
- 提供商所拥有的消息状态和非文本部分；
- turn、恢复、回退和压缩记录；以及
- Session 范围 notes 和 todos 的替换记录。

`history.jsonl` 仍是权威来源。Project Memory 不会复制到每个 Session 日志中，否则会形成过时快照，让共享文档看起来属于某个 Session。`MemoryWrite` 调用及其结果仍记录在 Session 日志中，作为变更的来源；`MemoryRead` 返回的正文也只是普通工具结果，Memory 本身存放在 Project 捆绑包中。

### 2.4 冲突规则

当这些来源发生冲突时，BuildMax 使用以下语义规则：

1. 指令保持规范性，Memory 不能覆盖它们。
2. 用户当前明确的纠正会覆盖过时 Memory。
3. Session notes 和 todos 描述当前任务，通常优先于对该任务的旧 Project 回忆。
4. Project Memory 只是辅助上下文，不能证明某个事实仍然成立；如果工作区可以直接回答，Agent 应进行验证。
5. 压缩摘要只是此前历史的有损视图；用户或诊断界面检查实际发生情况时，原始日志优先。

这些是含义级别的规则，而不是一个新的模型角色等级。 提示文本必须说明它们，因为提供商协议不了解BuildMax的分类。

## 3. 当前状态与缺口

### 3.1 当前已有内容

BuildMax 已具备 Session 本地状态的一半：

- `NoteWrite` 和 `TodoWrite` 会替换并持久化 Session 日志中的有界状态；
- 每次模型调用都会重新渲染这些状态，并在压缩后保留；
- 压缩前检查点为模型提供最后一次更新机会；
- 压缩摘要会累积并保持分支范围；以及
- 四层指令由 `agentapp` 组合。

持久化的 Session 结构已经可靠：

```text
<BUILDMAX_HOME>/sessions/
  index.json
  <session_id>/
    meta.json
    history.jsonl
    traces/<run_id>.jsonl
    writer.lock
```

### 3.2 缺失的能力

目前没有机制让 Agent 在某个 Project 的 Session 结束后保留项目特定事实。用户可以把事实写入 `AGENTS.md`，但这会把描述性记忆变成强制指令，并要求 Agent 修改它不应拥有的策略文件。

适合 Project Memory 的例子包括：

- 维护者在本仓库优先运行范围狭窄的 Desktop 测试；
- 某个库之所以应拒绝，是因为它无法保存提供商状态；
- 生成的 Artifact 应放在普通测试数据目录之外，原因在仓库中并不明显；或
- 用户在多次 Session 中做出相同纠正，而记录这一点有用，但不应变成每个 Agent 都必须遵守的规则。

不属于 Project Memory 的例子包括：

- “永远不要推送到主分支”这类指令；
- Session History 中某个决定的完整对话；
- “下次运行失败测试”这样的 todo；
- 从 Session History 得出的综合摘要；
- 可以从现有来源廉价且可靠获取的事实；或
- 凭证、访问令牌、私钥或复制的 Secret 载荷。

### 3.3 当前 Project 身份与 Session 身份分离

Desktop 当前拥有私有 `Project` 记录（名称和 `session.Meta`），存储在 `<BUILDMAX_HOME>/projects/projects.json`。CLI 不解析或记录 Project。

这已经造成了明显的不一致性：

- CLI 的 `--continue` 选择全局最新 Session，而不是当前仓库的最新 Session；
- TUI 和 Desktop 的 Session 列表也是全局的；
- Desktop 通过匹配工作区路径来筛选 Project Session；以及
- 摘要及其关联工作树看起来像不同文件，尽管现有 Worktree 功能把它们视为同一个仓库。

把 Memory 直接添加到当前 Desktop Project 会固化这种分裂：Desktop 和 CLI 可能在读取不同 Memory 的情况下操作同一仓库，或者 CLI 根本不读取 Memory。因此，必须先建立共享 Project 身份，再建立共享 Project Memory。

## 5. 目标与非目标

### 5.1 目标

- 为 CLI/TUI 和 Desktop 提供权威的本地 Project 身份。
- 让 `--continue`、Session 列表、Session 清除和 Desktop 组合使用 `project_id`，而不是依赖路径巧合。
- 在相关 Session 和 Git 工作树之间共享范围明确的 Project Memory。
- 保持实际工作区根目录作为工具、沙箱、工作区配置、差异和 `AGENTS.md` 的根。
- 让 Memory 可见、可编辑、可清除、可禁用，并能追溯到最后一次变更。
- 在两个 Session 同时更新 Memory 时避免过时写入。
- 保持 CLI 为纯 Go 单二进制，并复用现有 JSON/Markdown 本地存储方式。
- 记录加载了哪些指令和 Memory 来源，同时不复制运行敏感内容。

### 5.2 非目标

- Worker、Space、组织或共享 Server 上的 Project Memory；Portal 不在范围内。
- 全局用户 Memory 或跨机器自动同步（§20）。
- 为无关目录创建任意 Project。
- 仅凭远程 URL 将两个独立克隆识别为一个 Project。
- 嵌入式数据库、向量数据库、语义搜索或检索排序。
- 自动从每次对话中提取 Memory。
- 未经用户明确授权写入或重写 `AGENTS.md`。
- 将 Session 捆绑包移动到 Project 目录下。
- 导入 Claude 或 Codex Memory 格式。
- 通过 Desktop 的 `projects.json` 定义跨产品共享的 Project 身份。

## 6. 领域模型与不变量

### 地方Project

局部Project是一个稳定的不透明ID加上元数据，可以识别一个局部工作单位在会议中。

```go
type Project struct {
    ID               string
    Name             string
    Kind             Kind // git or directory
    DefaultWorkspace string
    GitCommonDir     string // git only
    CreatedAt        time.Time
    UpdatedAt        time.Time
    LastUsedAt       time.Time
}
```

持久的形状使用了明确的`snake_case` JSON标签和存储器现有的不透明公众身份识别生成器.执行过程中可能会发生变化.这些不变性不能： Go

- Project ID是稳定的，是关系关键。
- 名称是表达元数据，而不是身份。
- 据法典,Git Project的共同目录，本地识别Git。
- 索引Project由一个定律绝对根标识。
- 默认开启一个新的Desktop运行，而不是集 `DefaultWorkspace`
列表中可能包含Project的目录。
- 作为Project成员，从来没有扩大工具的允许文件系统根。
现在还有一个工作空间。

### 6.2 工作空间

工作空间仍然是目前执行会议的具体目录。

- 文件系统和Bash控制；
- 沙盒可写的绑定；
- 工作空间,MCP配置，技能和子体定义；
- 工作空间`AGENTS.md`；
- 果 Git
- 在`turn_started`上记录的路径。

工作树交换器改变工作空间和衍生工作空间配置，同时不改变Project及其内存。 `project_id`

### 6.3 会议

Session 的 `session.Meta` 新增 `project_id`：

```json
{
  "id": "<session uuid>",
  "project_id": "<local project id>",
  "workspace": "/repo/.buildmax/worktrees/memory-design"
}
```

对于普通的本地CLI/Desktop会议，它在创建时是必需的，并不会后来改变.一个会议可能会在属于Project的工作空间根之间移动，但它不会默默地移动到另一个Project.一个叉子继承了Project ID.一个本地子继承它以原产为依据；它不继承记忆背景，根据 §9.4。

由于任务运行和其他非本地会议不获得虚假的本地Project仅仅是为了满足形状，因此在序列化边界仍然是可选的。 CLI Desktop

### 6.4 一个Project可能涵盖多个工作目录

这是故意的，但有限制的：

```text
/work/buildmax                         ─┐
/work/buildmax/.buildmax/worktrees/a  ─┼─ same git common dir ─ one Project
/work/buildmax/.buildmax/worktrees/b  ─┘
```

两个不相关的目录从来不会自动连接.两个具有相同的远程控制器的克隆也没有连接：远程控制器可以改变，叉子可以共享URL形状，身份证也可能会出现在URL中.明确的未来多根功能需要自己的控制,UI和删除规则。

## 7. Project 解析

Project分辨率是CLI和Desktop使用的共享相关标识符操作.它接收了一个工作空间路径，返回一个Project加上正常化工作空间根。 `agentapp`

### 7.1 规范工作场所

解决器：

1. 让道路是绝对的，是清洁的；
2. 解决当前工作空间机器已经存在的文件系统位
能这样做；
3. 验证它是否指定可访问目录；以及
4. 问Git是否属于一个工作树。

代号分辨率意味着评估符号链接，而不仅仅是清理字符串.`filepath.Clean`加上`filepath.Abs` 今天`workspaceAliases`所做的对定位器不够，因为Git返回了共同目录的自己的拼写：在相关标识符上，通过相关标识符获得的工作空间和相关标识符下报告的共同目录是相同的目录，并不会产生两个Project.在每个边的比较之前，两个键都必须被解决或比较。 `/var` `/private/var` macOS

会议仍然记录了运行时间所选的可用路径，并且现有工作空间代号处理仍然适用于旧或用户输入的拼写。

### 查询的时间 Git Project

对于一个Git工作空间，请解决既工作树顶层，也是绝对的Git共同目录。 共同目录由主要支票和其链接的工作树共享，因此它是本功能所需的本地存储库密钥。

查询命令：

1. 找一个现有Project，其正规`git_common_dir`与它相匹配。
2. 如果发现，请触摸`last_used_at`，然后使用它。
3. 如果没有，请创建一个新的稳定ProjectID，这个名字来自
工作树上层目录，这个工作空间是`default_workspace`。

共同目录路径是位数，而不是公众身份.移动整个存储库可以无效。 V1 处理使用者打开移动文件时通过明确的重链接处理；它不会写一个未请求的标记到`.git`，从远程URL推断身份，或投机式结合存储库.重链接流显示失踪位数的候选人，要求用户选择；没有任何休斯斯蒂克默地加入记忆域。

订单决定是否能达到该流量.一个移动存储库会错过搜索，所以步骤3已经创建了第二个Project，在用户可以要求任何东西之前就已经空存储器.因此，创建必须在目录中包含Projects，其定位器不再解决：创建了新的Project 一个运行从未被封锁在命名决定上，表面表示创建了新的Project，并且现有的相关标识符有缺失位置，命名 relink命令器.没有那么，恢复路径存在，永远不会发现，并且看起来像复制功能。

### 7.3 非Git Project查找

对于非Git工作空间，搜索使用了可行绝对目录。 移动也需要明确的重链接。 同一个现有的根的符号链接别名不能创建重复。

### 7.4 解决方案和腐败

模糊匹配是一个错误，而不是任意选择.从Project元数据中重建一个损坏的Project指数.重建过程中发现的重复定位器被报告，直到修复之前，没有一个Project被选择。

自动创建是安全的，因为它只创建在`BUILDMAX_HOME`下的元数据；它不会编辑存储库.失败的Project写会停止新的本地会议创建，而不是启动一个无法持续的身份的会议。

解决方案可能会创建或重新链接Project，取了目录编写器锁，在收购后重复搜索，然后才写.第二次搜索是阻止CLI和Desktop进程同时创建两个ProjectID。

### 8.1 Project元数据和指数

`projects/<project_id>/meta.json`是 Project身份和元数据的权威。 `projects/index.json`是一个可重建的选定位器投影，并行于会议指数.它包含足够的信息，以解决一个工作空间，而不需要打开每个 Project捆绑。

转载数据库使用私人权限和原子更换.该索引通过扫描Project转载数据，在缺失，无效或不一致时重建.它从来不是唯一的Project身份副本.`projects/writer.lock`是一个操作系统的咨询锁，围绕创建，重新链接，更名和硬删除；普通搜索阅读稳定索引，而不需要它.就像在会话锁定时一样，内核所有权决定寿命，而废弃的锁文件不是权威。

### 8.2 为什么会话保持高水平

据了解，在 Projects 下的嵌套会议被考虑并被拒绝。

- 项目重新连接或修复可能需要移动每个会议目录；
- 全球会议ID，锁定，追踪，隐藏的子组和索引
已在没有Project路径的情况下修复工作；
- 总体而言,`--resume <id>`是全球搜索；
- 未来无项目或服务器原始的会议不需要人工
产品的母目录。

逻辑`project_id`提供了过和所有权，而没有这些成本。

### 8.3 记忆文件

一个内存是一个文件。 `<slug>.md`是该内存的权威，并且是有意读取的：

```text
projects/<project_id>/memory/
  MEMORY.md            # generated index
  writer.lock
  merge-commit.md
  rejected-sse-transport.md
  fixture-layout.md
```

文件名是 slug,slug是内存的身份 没有第二个识别符可以不同意它.每个文件是前面材料加体：

```markdown
---
name: rejected-sse-transport
description: SSE was rejected for the event stream; it cannot resume mid-turn
type: project
session_id: <session uuid that last wrote it>
updated_at: 2026-08-29T10:00:00Z
verified_at: 2026-08-29
---

The event stream uses WebSocket, not SSE.

**Why:** SSE was tried in the worker-stream spike and dropped because a
reconnect cannot resume a turn already in flight.

**How to apply:** do not re-propose SSE for streaming without addressing
resume. Related: [[worker-stream-contract]].
```

前面材料场所使用`snake_case`，与存储库的持续-JSON公约相匹配.`session_id`和`updated_at`给每个内存的起源，这就是为什么没有侧车元数据文件：之前的单档案设计需要一个，因为单独的Markdown文件没有任何地方记录谁写的，并且每文件前面材料删除了需要而不是移动它。

记忆器可以在不声称是当前的情况下总结一些昂贵的东西，而`verified_at`是可选的。

相关标识符是一个**生成的投影**，而不是手工维护的文件：它在每次写完后从内存文件中重建，就像相关标识符从Project元数据中重建一样，同样的原因一个可能与其来源不同意的索引是没有补偿能力的缺陷表面.用户编辑记忆，而不是索引.手动删除的记忆文件在下一次重建时简单丢失其线。 `MEMORY.md` `projects/index.json`

没有任何信息，不易分析或超出预算的身体，被报告并被跳过，而不是猜测。

没有Project记忆修订日志在v1。 创始会话已经记录工具调用和结果，复制每一个替换到另一个仅附录文件将在保留需要之前创建无限的第二历史。

## 9. Project Memory 契约

### 9.1 内容的形状和预算

一个Project最多可以存储20个记忆**.每个都有一个`description`最多100个字符**和一个最多的**2,000个**.每一个限制都被执行在写作上，而不是默默地缩短在染时。

两项预算是有争议的，因为两项成本不同。

**指数是居民成本.** 它在每次通话中呈现出消息列表之后，后续区块从来不是下次通话请求的前，因此它们在Project 中每次每次会议的每次代中都以新输入代币支付.不仅每次写一次.限制输入通过构造限制:20行枪加上100字符的描述地近3,200字符，这是故意地对变量，笔记和所有都适用于天花板`RenderSessionState`。 传递器也直接执行3,200，因此手动编辑的商店也不能超过它，如果超越永久记忆限制。

类似的预算是，而不是额外的系统提示.用户选择支付的用户创建的标准文本的额外系统提示上限为8,192边;Project 记忆是模型创建的错误文本，比系统提示更接近生成，因此它保持在其他总被发射的区块的标准下。

**体体是检索成本，只需读取。 **每 2000 个字符都是慷慨的，正因为它不是居民：记忆可以承担为什么和如何使其可操作的，而不是被压缩成一个弹，通过降低其原因存活的预算.其中的二十个是40 kB的磁盘，没有运行一次加载。

这就是使形状工作的分区。 一个总是加载的文件必须删除旧的内存才能允许新的；在这里，增长成本是一个索引线，压力降到数量和写一个值其线的描述而不是知识本身。

20 是一个选择在用户填写后在证据上提升而不是降低的起始限。

如果直接文件系统编辑使文件不有效 UTF-8 或超出预算，则该内存被报告并跳过 (§8.3).如果整个存储器无法读取  缺失目录不是错误，但不可读的是  运行时间不会发送可能误导的部分索引：它会禁用它进行运行，省略了两种工具，并报告了通过诊断和运行开始的表面所需的确切修复.一个默默缺失的来源是整个会议的故障，因此`doctor`不是唯一出现的地方。

### 9.2 什么是Agent可能记住

工具描述和运行时间提示使用精度优先政策：

- 记住稳定的项目偏好，决策及其原因，
纠正，不明显的公约和昂贵的死胡同；
- 没有复制现有文件或命令可以廉价回答的事实；
- 勿存储临时任务状态，对话叙述或原始工具
输出；
- 没有将观察转化为强制性说明；
- 永远不会存储凭证或令人惊的敏感内容；以及
- 当当前证据或用户相反时，更新或删除记忆。

每个内存都携带一个`type`：

| 类型 | 保持 |
|---|---|
| `feedback` | 用户提供了关于如何在此Project  修改和确认方法的指导 |
| `project` | 持续的工作，目标，决策和限制，不能从代码或其历史中得出 |
| `reference` | 向外部资源的指标：仪表板，门票，规格 |

检查布局中的第四种类型，一个`user`范围， 蓄意不存在用户身份：即全球用户内存， Project

一个`feedback`或`project`的体格表示事实，然后 **为什么**它被认为是什么时候，它是什么时候来，它是什么时候替代的，然后 **如何应用它.这种形状是什么分离记忆与事实碎片：一个不同意为什么的读者可以丢弃记忆在证据上，而不是猜测它的授权。

记忆录记录用户想要的东西，永远不会是用户的东西。 "带来建议而不是调查"是一个偏好，可以被用户纠正，并在下次回转中有用。 "不熟悉同步"是一个关于一个人的判断，并且它以存储物事实无法的方式失败：没有什么可以验证，将会被操作几个月，用户永远不会被告知为什么答案改变.更糟糕的是，它自证了 Agent 解释了更多，用户适应了这一点，推论看起来验证。 `feedback`

关于用户的推断需要重复，而不是洞察力.在几个会议中重复的相同纠正是证据；一个令人困惑的交流不是，属于该会议.身体必须携带它依赖的场合，这样用户可以读出来说模式是巧合。

`feedback`是指令界限测试的地方，所以这个记录解决了它，而不是离开第2.1节，下面的"明确记住 - - 这是一个强大的信号"规则，以拉对对抗.一个`feedback`内存记录 **用户喜欢某种东西和为什么**；它永远不会成为一个规则.Agent引用为自己的权威，它不是证据，它与当前指令或当前用户声明冲突时.当一个偏好应该绑定每一个未来运行，无论内存是否启用，目的地是`AGENTS.md`和相关标识符

录取测试是，这个事实在任何分支都保持真实.Project 记忆是由Project的每个工作空间共享的，所以只在达到的分支内持有的结论不属于那里，它是会话状态,`NoteWrite`已经在适用的位置保留它.这是第一个失败模式，而不是理论的：一个工作树每个任务工作流程产生稳定的供应，读起来像持久的知识，文件的拒绝图书馆的例子只有当原因存活在分支时才持久.工具描述测试在这些词中说。

"不要复制文件可以回答什么"需要一个精炼，因为检查的布局发现了记忆和重新计算之间存在问题.重建和缓慢改变的东西是昂贵的.多阶段计划的位置，哪些子系统仍然未构建.即使存储库的读取足够长的时间会回答，这种记忆值得记忆.这样的记忆命名其真相来源，并将`verified_at`设置为最后一次检查日期，其身体告诉读者在行动之前要验证.这是诚实的关于缓存；一个声明不一样的事实.廉价的查找仍然不会成为内存。

对于这个项目来说，明确的"记住这一点"是强烈的写信信号.一个在不值得信赖的网页或工具输出中看到的事实是不是.重复是证明有用性的证据，而不是证明真相。

身体可以用`[[slug]]`链接到其他记忆.运行时间不会解决，验证或跟随这些链接；它们是阅读辅助器，并且连接到尚未存在的记忆标志着值得写的东西而不是破碎的参考.设计中的任何东西都不取决于图表的完整性。

### 9.3 工具表面

首要本地Agent收到两个工具.它们以操作而不是范围命名，因为`NoteWrite`和`TodoWrite`是会议范围的，并且没有范围前；如果设计了第二个内存范围，这些工具上的范围参数比第二个工具更好，因此未设置的名称是幸存下来的。

子代理 `MemoryRead`

```json
{ "names": ["rejected-sse-transport", "fixture-layout"] }
```

它返回这些体，并命名那些不存在的，而不是失败的呼叫。 这里需要一个阅读工具，

`MemoryWrite` 创建或取代一个内存：

```json
{
  "name": "rejected-sse-transport",
  "description": "SSE was rejected for the event stream; it cannot resume mid-turn",
  "type": "project",
  "content": "The event stream uses WebSocket, not SSE.\n\n**Why:** ..."
}
```

没有附加模式和没有力模式。 `content`

运行时间规则是**只取代了这次运行读到的内容**，而比较的代币从来没有离开运行时间.创建一个没有slug的内存始终被接受.取代现有的内存需要这次运行呈现或读取现在在磁盘上的版本；运行时间记录了它向模型交付的每个体的消化，在运行环境中，并将其比较在锁下.想要更改一个内存的模型只看到一个索引线，被告知先阅读它，这是诚实的答案，因为它不能融合从未见过的内容。

发送版本代币到模型中并预计它将会将正确性代币引导到循环中最不可靠的组件中，并将添加一个遗漏参数的案例，唯一可行的倒退是无条件的重写。

行动：

1. 验证弹药，描述，类型和机器预算，并应用一个
在持续前最好的功率认证检测器；
2. 采用Project内存写字符锁；
3. 换取，将本次阅读的消化与本次阅读的消化相比较
磁盘；
4. 原子上只写`<slug>.md`在匹配上，或者在创建时；
5. 从文件中再生`MEMORY.md`；以及
6. 返回所改变的内容和结果的内存数量在有用的工具输出中。

在冲突中，当前的编写或直接用户编辑，因为该运行读取了体，没有任何东西被写到，工具说了.Agent可以读取当前版本并故意合并。

## 10. 模型上下文组成

记忆不加入可缓存的指示前置.在每个模型调用时，运行时间在正常历史后，并且在现有的会议状态之前，将索引转换为，而不是体体： Project

```text
... conversation history ...

<project-memory project_id="...">
Fallible project recall, not instructions. Each line is a pointer; read a
memory with MemoryRead before relying on or changing it. Current user
messages and verified workspace state override stale entries.

- rejected-sse-transport — SSE was rejected for the event stream; it cannot
  resume mid-turn
- fixture-layout — generated fixtures sit outside testdata/ on purpose
</project-memory>

<session-state>
... notes and todos for this session ...
</session-state>
```

序列是故意的:Project 记忆是较老的，共享的背景；会议状态更具体于任务，并且保持在生成最接近.空或禁存储不会生成任何块。

区块：

- 是使用者角色的文本信息，使用与
现有的会议状态；
- 根据文本窗口和代币估计计算；
- 对于每一个请求，都会被再生，所以另一个会议的提交写作是
在下一次代中可见；
- 没有在会议历史中持续；以及
- 具有Project范围，以便模型和痕迹能够识别源头
没有把它当作一个指令。

描述是一个指针，而不是模型可以采取行动的总结。 区块这样说，因为这个失败邀请是在一个单项子上采取行动，而没有打开带有为什么的体，从标题中得出结论。 轮到时读到的体体是普通的工具结果，像其他任何工具一样活在历史中；只有指数才会重新呈现。

商店对写作进行比较的消化器，在运行环境中记录在读取尸体时，并且从来没有向模型展示；见9.3节。

染器在描述中避免字面上打开或关闭`project-memory`界限序列.这保留了结构界限；它不会使内存可靠，这就是为什么低权威警告和冲突规则仍然适用于其内部的每个行，并返回阅读工具的每个体。

快速缓存稳定性不是将可变的内存放在系统提示器中的一个理由，缓存成本不是选择启动的原因.消息列表后的转载块已经在每一个可重复使用的前之外：在下一次调用时，历史在它们面前增长，因此，随着一个后续块的支付，无论它是否改变，都会用新输入代币进行.因此,Project写字不予以验证.实际成本是保持索引的恒定每次调用成本，这就是第9.1节预算的原因，并且保持内存在指示层之外的原因是其较低权威。

## 19. 已否决的方案

### 19.1 将`memory/`置于逃离工作空间路径下

简单且可浏览，但路径变得身份.工作树，移动和号将一个存储库分成几个内存域.稳定的Project ID加一个定位器是避免这一点的小额外层。

### 19.2 移动会议在`projects/<id>/sessions/`下

物理嵌套看起来很直观，但没有提供`project_id`没有的语义能力.它增加了动作，跨项目复杂的恢复，以及无项目会议的人工家园，同时破坏了已经拥有全球身份证，锁，索引，痕迹和恢复的持久商店。

### 19.3 使用`AGENTS.md`作为Project内存

已有，但含义和所有权错误.`AGENTS.md`是一个规范用户/存储库指令源；内存是模型策划和可错误的.让Agent重写它将默默地转化体验为政策。

### 19.4 作为长期记忆，应将压缩总结视为

缩写总结是损失的，具体的会议，具体的分支。 推广它将带来任务叙述和不相关的未来会议中陈旧的结论，同时丢弃了纠正所需的原始证据。

### 19.5 关键Git Projects 通过远程URL或存储库内容

远程URL变化，可以暴露凭证，并且不能区分克隆；内容哈希与提交变化，并且可以在叉子之间发生冲突。 Git

### 19.6 现在添加嵌入式和语义检索

模型读取和选择的索引是这个规模的足够检索，并且可以检查，提供商中立，并且是确定性的.嵌入基础设施在需要足够的数据之前添加了零碎，排名，模型兼容性，删除和解释问题.索引直到完整，直到第17阶段测量，不会成为排名问题。

### 19.7 每次自动提取记忆

这将在每个任务中添加一个模拟调用或隐藏推理政策，保持更令人惊的内容，并在用户控制被证明之前使虚假内存成为常见的.明确的Agent写加上直接的用户编辑是最安全的第一种仪器路径。

由于这种方式，用户可以使用自动提取的命令，而不是使用者所要求的命令。 这使得人所要求的成本和惊喜保持下去， Agent

### 19.8 一份总装载的边界文件

此记录之前指定了一个单个`MEMORY.md`，数千个字符，被取代为整体，在每次通话中呈现完整。 在检查其他形状的工作库后，它被拒绝 (§4.1)。
