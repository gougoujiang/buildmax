## 1. 问题

Worker 代表 Space 执行模型选择的命令，需要有用的凭证：驱动 `git` 和 `gh` 的 Agent 需要 GitHub 权限，调用内部服务需要其凭证，部署任务需要云平台权限。

没有Space-scoped 秘密资源.一个凭证只有在部署将其放在工人的环境中才能获得运行，这使得每个Space和每个Agent都具有相同的价值，没有旋转，没有每一个Agent的选择，没有审计.[插件空间分布.md](plugin-space-distribution.md) §5在报告环境释放名称时停止阅读；它不决定谁提供它们。

环境路径的两个特性使其不适用，而不是仅仅粗：

- `internal/infra/sandbox/env_scrub.go` 会从每个沙箱子进程中删除 Secret 形状的名称，包括 `GITHUB_TOKEN` 以及以 `_TOKEN`、`_KEY`、`_SECRET` 或 `_PASSWORD` 结尾的名称。由于 CLI 默认关闭沙箱而 Worker 默认开启，同一配置在本地可用、在 Pod 中却可能静默失败。
- 工人仍然在Space的业务中获得非其身份证
部署的对象存储密钥，在直接模式下提供商API
关键。 § 13记录了必须离开的东西。

## 2. 决策

BuildMax 增加服务端 Secret Broker：

1. 代表一个秘密作为一个Space所有的版本资源，或作为参考
向外部秘密管理员；
2. 结合其使用不可变的Agent修订，声明其秘密
需要和如何交付；
3. 当工人要求获得许可时，将该许可的快照放到一个TaskRun上；
4. 仅实现该运行计算的值；
5. 输出每个值作为环境变量，一个染值
证书文件，或两者都，无论是Agent所声明的。

所有面向用户的 API 都是只写值；不存在 reveal 操作。

### 2.1 交付以 Run 为单位，而不是按消费者交付

交付问题有一个答案，值得指出的是作为决定而不是细节：一个凭证交付给**运行**，而不是给内部的命名过程。

早期设计只向命名消费者交付值：stdio MCP 服务器的显式环境、类型化 HTTP 授权槽，或交给单个进程的文件；它拒绝交付给模型选择的命令。这个方案不适用于 BuildMax Agent：Agent 会在运行时组合 shell 命令并调用它选择的工具，包括运行中写出的工具。以“每个工具一个适配器”为工作单位的机制面对无界工具集合，可能认证了 `gh`，却没有认证模型稍后写出的 Python 脚本；这不是本功能的缩小版，而是没有解决问题的另一项功能。

因此，这两个支持的模式都在运行水平。 § 17 记录了此次运行成本和所放弃的成本。

## 3. 它不保护什么

两种交付模式都会把值放入运行中，因此 Agent 的命令可以读取它们。`printenv` 会显示环境注入的值，`cat` 会显示文件注入的值；这里没有任何机制阻止这一点，任何使用面都不应声称可以阻止它。

剩下的东西，每一个部分的价值：

| 控制 | 它们买什么 |
|---|---|
| Space 所有权 | 一个 Space 的值不会因为另一个 Space 的运行而泄露 |
| Agent 配置 | 一个运行只接收 Agent 配置的项目，而不是 Space 的完整集合 |
| 子 TaskRun | 经验证的授权在 TaskRun 上固定，不能从运行内部扩展 |
| 短暂凭证 | 暴露的值会过期；运行开始时的交换是主要控制点 |
| 提供商范围 | 存储系统的令牌不能在其作用域之外使用，无论谁持有它 |
| 加密存储 | 数据库或备份披露没有产生值 |
| 没有披露 API | 通过管理表面无法恢复值，只使用于授权运行 |
| 审计和撤销 | 每个补贴都是可归因的，可以撤销的 |
| 精确值编辑 | 减少日志，痕迹和工具结果中意外出现；不是保密的边界 |

这项设计的边界是围绕**哪个运行可以行使哪个权威，多长时间，代表谁**。 这不是一个边界围绕运行被授权使用的字节值。

两种后果,Portal复印和用户文件必须带来，因为误读它们的Space将授予它不应该授予的凭证：

- Agent可以读取其运行所授予的每一个秘密；以及
- 能激活共享Agent的成员可以获得Agent的值
没有获得自行强制或阅读许可。

无法接受这一条件的Space应缩小证书的供应商范围，缩短其使用寿命，或使用不同的Agent。 交付模式不是杆。

## 4. 范围和所有权

**Space是唯一的所有权范围.**一个秘密属于一个Space，这是拥有Agents，插件激活和审计的相同边界.一个Agent定义可能只消耗自己的Space中的秘密；在修改时，拒绝使用另一个Space的秘密的配置，而不是运行时。

本设计有意不提供部署全局、独立于 Space、可由多个 Space 的 Agent 引用的
Secret。确实存在这种需求——持有一份共享内部凭证的运营人员更愿意只录入一次——
但全局值没有可归属的所有者、无法从某个 Space 单独撤销，也无法回答“哪些
Space 的运行可以读取它”。若两个 Space 需要同一凭证，应分别创建值相同的
Secret；这种重复是保持所有权模型清晰可追责的显性代价。

这不描述BuildMax自己的凭证.数据库密码,JWT签字密钥,KEK，对象商店管理凭证和管理供应商密钥是运营商拥有的部署配置，从来没有Space秘密，从来没有作为赠款运行。

本设计也不会引入服务器端 Project 或部署环境实体来限定 Secret。Space 是
Server 的所有权边界；`internal/core/localproject` 中的本地 `Project` 是
客户端概念，与此无关。

## 5.资源模型

实现后，`internal/infra/db` 中的 `xxxRow` 结构仍是数据库 schema 的事实来源；
下文模型说明这些结构必须表达的内容。公共标识符按
[实体身份](entity-identity.md)使用 `NewPublicID`；时间戳遵循
[时间戳表示](timestamp-representation.md)。

模型是故意的两个表格：一个秘密，和一个每次运行审计快照。 运行消耗一个秘密是不是一个表格，它是配置在 Agent修改 (§6)，这已经仅是添加，所以修改什么运行消耗而秘密的值保持活跃和可旋转。

### 5.1 `secret`

一个Space所有的秘密.一个**秘密是一个集团**：一个名称包含几个名为**项目** `access_key_id`和`secret_access_key`，或`username`和`password`.一个单值凭证只是一个项目的集团。

| 领域 | 意思 |
|---|---|
| `id`， `public_id` | 数字关系键和不透明的公共手柄 |
| `space_id` | 拥有权和授权的边界；见第4条 |
| `name` | 唯一的非秘密显示名称,Space |
| `description` | 选择性限制解释；不能包含项目值 |
| `provider` | 运营商配置的外部供应商名称 `embedded` |
| `state` | 类型： 相关内容， `active` `disabled` `destroyed` |
| `ciphertext`， `nonce` | AEAD加密项目地图或加密供应商描述符 |
| `item_names` | 现在的钥匙，存储在清晰的 |
| `wrapped_dek`， `key_id` | 通过KEK封闭的DEK，并且KEK封闭的 (§9.1) |
| 时间标记： `created_by` | 管理权 |

所有项目作为一个加密 JSON 对象保存在同一行中。其值为
`map[string]string`——从项目名到项目值——并整体密封。这种形式便于小型部署
理解、备份和使用 KMS 封装，也能在没有版本表的情况下保证轮换正确：替换整张
映射是一次原子写，运行读取到的始终是自洽集合，不会看到新的
`access_key_id` 搭配旧的 `secret_access_key`。这正是项目必须成组保存的原因。

由于名称不是值，并且因为Portal列表和第6条验证必须在没有解密任何东西的情况下工作.项目名称是标识符 `[A-Za-z_][A-Za-z0-9_]*`，在写上验证，因此整个组可以作为环境变量 (§6.2) 注入，没有任何项目可以默默地成为。 `item_names`

每个项目都是通过API进行写的； §15没有披露操作。 转载文件的非秘密参数也需要集群的服务器URL和CA证书,AWS区域不是项目： §6.3将它们作为字面字体提供在Agent上，在那里它们仍然可读。 位置表达了分类，因此没有项目携带了秘密或配置旗，创建一个秘密只是输入项目名称和值。

变更名称显示了元数据，而不是身份.禁用拒绝了新的运行补贴和新的现实化.破坏在没有活跃的参考后会删除可回收的材料；它不会重写审计历史。 `(space_id, name)`

组合已经给出了原子旋转，这是版本表所购买的唯一正确性；其余的在飞行中运行保持旧值是争论的，因为运行在索赔时间发生一次，不会再读.两次在旋转的两侧索赔的两次运行每个得到一个内部一致的集合，这是诚实的保证.§17记录了什么版本将添加，为什么它不值得重量在这里。

故意没有`kind`字段.将一个秘密标记为一个凭证家族将使存储负责解释值，并将声称一个秘密是一个整的染文件.将 kubeconfig的非秘密服务器URL和CA证书密码.物品名称包含任何一个凭证的结构，染是选择在Agent。

### 5.2 `task_run_secret`

没有秘密的审计记录，

| 领域 | 意思 |
|---|---|
| `task_run_id` | 对应的运行 |
| `secret_id`、`item_name` | 实际解析的是哪个 Secret 的哪个条目 |
| `agent_revision_id` | 授权本次使用的消费配置 |
| `provider_version` | 已解析的准确外部版本（如有） |
| `delivery` | `env` 或 `file` |
| `env_name`、`file_target` | 解析后的交付目标 |
| `status` | `pending`、`materialized`、`revoked`、`expired` 或 `failed` |
| `expires_at` | 交换或租赁的凭证何时失效 |
| `materialized_at`、`revoked_at` | 运行时生命周期证据 |

其中不包含密文、明文、租约令牌、Provider 错误正文或值的哈希。低熵条目的哈希会让攻击者能够离线猜测其值，而且解释运行过程并不需要它。

### 5.3 区分不同凭证类别

同一套存储与交付机制不应吸收生命周期已经不同的凭证。

| 类别 | 示例 | 所有者 | 处理方式 |
|---|---|---|---|
| 部署启动凭证 | 数据库密码、JWT 签名密钥、Secret KEK | 运维人员 | 由部署注入；绝不是 Space Secret |
| 服务器管理的上游凭证 | 模型 API Key、对象存储管理凭证 | 运维人员 | 加密存储或引用外部系统；绝不交付给 Space 运行 |
| Space 执行凭证 | GitHub Token、Slack Token、内部服务凭证 | Space | 由本设计管理 |
| 临时运行权限 | 运行令牌、预签名 URL、STS 凭证、Vault Lease | 服务器或外部签发方 | 运行时签发或交换；短 TTL；不是可重复使用的 Space Secret |
| 用户认证凭证 | 密码验证值、刷新令牌、Webhook Key | 账户子系统 | 使用现有哈希、轮换和撤销模型 |

## 6. 消费配置

运行消耗方式 秘密是根据Agent配置的，根据Space的要求，在Agent定义时设置这个.它不是一个独立的绑定资源：它是一个结构化的领域，基于Agent定义，仅包含每个附录的Agent修订，并且被秘密服务验证，除非工作者要求运行。

修改键是修改键的替代，修改键是修改键的替代，所以"该运行使用了什么"是从不可变状态中可回答的，而这些名称背后的项目值仍然活跃和可旋转。

### 6.1 一个Agent所宣告的内容

采用Agent的消费配置是列表的报名，每个都是一份环境补贴或文件补贴。 补贴可以从Agent的任何秘密中获取项目；一个Agent通常混合了几个组。 Space

每次补贴都包含`required` (默认正确).在Agent开始之前，未能获得的要求补贴失败；另一个选项被跳过，跳过记录。

### 6.2 环境变量

两种形式，选择是Agent：

- **选择的项目.** 名称一个`secret`和一个`item`，以及一个变量名称。
其他项目以此名称来。
一个秘密的`GITHUB_TOKEN`和另一种的`SLACK_TOKEN`
常规情况和建议的默认情况，因为配置读为
列表Agent使用的精确物质。
- **整个集团.** 给一个没有物品的`secret`，每个物品都到达
在自己的名称下，可选使用`prefix`。 这就是Kubernetes' `envFrom`
作为一个便利的支持，所以一个已经组合了一个 Space
证书不需要重新表达每个成员，
它们的名称是使它们很清楚的定义。

整个组表单将Agent未单独命名的运行项目交给，扩大了第3条已经承认的内容.这是Space的呼叫，不是默认的寻求,Portal显示它作为整个组的补贴，而不是将其扩大到一个指每个项目都被选出的列表。

修订的已解决的变量名称不得在两个全组补助中，或一个全组和一个选定的之间碰撞，并且在配置保存时拒绝碰撞，以便解决它,`prefix`。

### 6.3 证书文件

文件授予一个**renderer**的名称，并绘制其参数。 染器是BuildMax代码，它知道一个凭证家族的文件布局;Agent从一个秘密项或字母中提供每个参数。

| 发射器 | 目标 | 参数 |
|---|---|---|
| `aws_credentials` | `~/.aws/credentials` | `access_key_id`， `secret_access_key`， `session_token?`， `region?` |
| `kubeconfig` | `~/.kube/config` | `server`， `certificate_authority_data`， `token` |
| `git_credentials` | `~/.git-credentials` (+ `~/.gitconfig`) | `host`， `username`， `password` |
| `netrc` | `~/.netrc` | `machine`， `login`， `password` |
| `npmrc` | `~/.npmrc` | `registry`， `auth_token` |
| `docker_config` | `~/.docker/config.json` | `registry`， `username`， `password` |

一个参数通过`{secret, item}`引用或字面来满足.字面是一个集群的服务器URL和CA证书属于Agent，可读，不密封在一个秘密.一个`region`是字面；只有真正的秘密参数是一个项目。

`target_path` 和文件 `mode` 由渲染器而非自由文本控制，因此第 8.3 节的写入
限制可以强制执行：Agent 选择渲染器并填写参数，但不能自行指定输出路径，
所以无法写入 `.bashrc`。内置渲染器覆盖常见凭证类型；对 BuildMax 未内置的
类型提供 Space 自定义模板，是阶段 2 的开放问题（第 20 节），不属于首版模型。

一个文件验证当满足每一个要求参数，每个引用的秘密属于Agent的Space，每个引用的项目都出现在该秘密的`item_names`。

### 6.4 两次使用一项物品

同一项目可以同时供给环境变量和文件参数，例如一个令牌既可作为 `GH_TOKEN`，
也可作为 `git_credentials` 渲染器的 `password`。两者都从该次运行读取到的
Secret 当前项目中解析，快照则分别记录每个目标。

## 7. Run生命周期

```text
Space Owner                 Server                         Worker
    |                         |                              |
    |-- write/rotate Secret -->| re-encrypt the item map    |
    |-- configure consumption->| validate same-Space ownership|
    |                         |                              |
    |                    dispatch TaskRun                    |
    |                         |-- resolve Agent revision     |
    |                         |-- read its consumption config|
    |                         |-- snapshot task_run_secret   |
    |                         |                              |
    |                         |<---- claim with run token ---|
    |                         |-- require live matching run  |
    |                         |-- decrypt current items      |
    |                         |-- exchange short-lived creds |
    |                         |-- return computed bundle --->|
    |                         |                              |-- set declared env grants
    |                         |                              |-- render declared files
    |                         |                              |
    |                         |<---- report terminal state --|
    |                         |-- revoke leases, close grant |
```

快照发生在 Agent 修改和插件针已经解决：当工作者声称运行时.项目被解密一次，在要求时，所以运行会读取一个自相一致的地图，即使转换后一刻。 解析从来不使用工作者提供的值，并且工作者不能浏览Space状态。

面向工人操作返回为一个TaskRun计算的捆绑.它不接受任何秘密ID，名称或供应商路径.它的路线注册在`internal/server/handlers/routes.go`，并在建造时被描述在`internal/server/static/openapi.json`。

材料化需要所有：一个有效的运行代币，运行与路径匹配；一个预期执行状态中的非终端运行；固定修改的消费配置；一个启用的秘密，目前的项目仍然满足该配置；以及一个配置，健康的后端。

响应使用TLS，设置`Cache-Control: no-store`，并绕过体内记录。 尝试重新检查失败的检查是允许的。 如果丢失的响应永久失败了否则有效的运行，并且记录了每一个成功的物化，则"一次阅读"是不有用的。

## 8. 交货方式

两个模式.一个Agent修改配置每个独立； § 6说明如何。

### 8.1 条件：实施了Run-Scoped `HOME`

运行模式都没有很好的定义，直到运行拥有其操作系统`HOME`。 一个工人已经获得了运行范围的`BUILDMAX_HOME` (运行全球目录,`RuntimeTaskRunGlobalDir`) 和空间持久文件的运行范围的目录 (`RuntimeTaskRunHomeDir`)，但其OS`HOME`是容器图像集，在每个运行中都共享该容器中的图像。

这一问题已经解决。`taskrun` 为每次运行创建专用且为空的操作系统 `HOME`：
`<run-dir>/oshome`。它与上述两个目录分离，以 `0700` 权限创建，在 Agent
运行期间同时设为 `HOME` 和 `USERPROFILE`，并随运行的临时目录树删除。
它有意不使用 `RuntimeTaskRunHomeDir`，因为后者保存物化后的 Space 文件，
不适合放运行私有工具状态或渲染后的凭证；它也不使用 `BUILDMAX_HOME`，
因为该全局目录会在运行后上传，而凭证文件可能位于 `~/.config`。

### 8.2 环境变量

运行时间将每个`env`授予的命令放在运行执行的命令的环境中：选择Agent选择的变量名称下的项，或选择性前 (§6.2) 的组的每个项，以其自己的名称。

这种模式是通用的.它不需要工具的合作，涵盖非HTTP协议，并适用于运行期间编写的程序.它是任何文件公约不存在的认证家族时的倒退，并且是实施的第一个模式。

两条规则：

- 授予的资金是以"定制"为名称而非其他名称，
没有经过预测别名的额外出口；
- 运行环境是否则第13.1条的默认拒绝基线，不是
报名的补贴不是一个理由
停止隐藏部署自己的证书。

### 8.3 Run-Scoped证书文件

运行时间运行一个染器 (§6.3) 来写一个文件在运行的`HOME`下，在配置的凭证家族已经定义，工具发现它自己.每个参数在Agent开始之前从一个秘密项或字母中解决。

单元是凭证家族，而不是工具这就是保持工作的界限.一个呈现的`~/.aws/credentials`服务于AWS CLI，每个语言SDK和Terraform同时.一个呈现的`~/.git-credentials`与其`~/.gitconfig`服务于`git`和所有用于`git`的东西.模式存在于两个不同的原因：

- 一些家庭根本没有可用的环境表格 `~/.kube/config`
单个变量不能承载结构的`~/.docker/config.json`；以及
- 如果环境表格确实存在，文件表格还可到达工具
只有读取配置。

写下所有强制性的限制：

| 限制 | 原因 |
|---|---|
| 目标在运行的`HOME`内解决 | 在工作空间下的一个文件是一个`git add -A`从提交，并且是对Artifact上传的候选 |
| 没有`..`穿越，没有下列符号链接 | 另一条路线 |
| 模式`0600`，永远无法执行 | 凭证文件是数据 |
| 拒绝弹启动和命令载有目标  `.bashrc`， `.profile`， `.zshrc`， `git`配置密钥命名命令 | 转换到其中一个注入代码，而不是提供证书 |
| 运行结束时移除 | 运行目录无论如何都被删除； |

### 8.4 两者均使用

Agent可以将一个项目放置在变量中，并将相同项目将在染器参数中 (§6.4)。 两个项目都在给定的运行中从秘密的当前项目中解决，快照将每个目标单独记录。 如果一个家庭的文件表格引用一个变量而不是嵌入值，染器使用该表格。

### 9.1 嵌入式加密存储器

这是开箱即用私有部署的默认方案。MySQL 中只存储密文和被包装的数据加密密钥。

每个 Secret 的条目映射都使用 AES-256-GCM 或经过同等审查的 AEAD 加密；每次编辑都会生成新的随机 DEK 和 nonce，并整体重写。关联数据把密文绑定到 Space 公共 ID，因此把密文移动到另一个 Space 的数据行会认证失败，这正是威胁模型要防御的跨 Space 隔离问题。关联数据不再绑定其他内容。不同部署本身已经通过密码学隔离：另一个部署使用不同的 KEK，在执行 GCM 前就无法解包 DEK；反过来，如果把部署 ID 写入关联数据，会破坏灾难恢复副本在共享 KEK 后读取相同行的能力。关联数据也不绑定 Secret 公共 ID：该 ID 在数据行插入时才生成，晚于值的密封；而在同一 Space 内交换密文需要数据库写权限，该权限属于威胁模型已经信任的部署运维人员。

### 9.2 外部秘密参考

外部后端存储一个加密描述符命名供应商，提供商管理的秘密，以及版本选择器.BuildMax不复制值到其数据库中.在解析时，服务器通过其工作负载身份进行验证，检索值或动态凭证，记录准确的供应商版本，并在可用时，并应用相同的授予和交付规则。

提供商配置是部署范围和操作员管理的.一个Space不能提交任意的Vault地址或云端点，将服务器的提供商身份发送到其他地方：操作员定义命名的提供商,TLS根，区域，允许的路径前置和身份验证方法，并且Space记录只选择其中。

库存是第一个外部集成，因为私人部署是产品的承诺，而库存服务于本地静态和动态机密.AWS和谷歌遵循相同的界面.提供商平衡不是第一批要求。

| 发射器参数不满意 | 在Agent启动之前失败，命名参数；不要写部分文件 |

| 提供商不可用 | 在一个有限的启动预算内再尝试，然后失败了无毒的提供商类错误 |
| 无效或运行终端的Run代币 | 拒绝不透露是否存在秘密 |
| 交换的证书或租期限在运行中期到期 | 提供商允许的更新；否则失败，而不是继续作为未认证的工作 |
| 终端状态后撤销失败 | 保存终端结果，记录一个消毒撤销失败，再次试图在一个限制范围内 |

## 15. API形状

面向用户的操作采用常规资源 API，但项目值始终只写：列出和获取包含
`item_names` 的 Secret 元数据；创建带项目的 Secret；编辑项目；禁用、重新启用
和销毁。编辑项目在同一操作上支持两种请求形式：供逐行编辑器使用的逐项目补丁
（设置或删除命名键），以及供原始 JSON 编辑器使用的整张映射替换。Portal 同时
提供两种编辑方式，它们不能演变成两套分叉代码路径。Agent 修订的消费配置通过
Agent API 写入，并在那里针对 Space Secret 做验证。

没有回应包含项值.写回复只返回元数据和`item_names`.包含值的请求字段不包括请求记录，验证错误和审计细节。

面向工人的表面只返回已经计算的补贴组，它运行没有列表，名字或供应商搜索.它是`GET /api/worker/task-runs/{task_run_id}/secrets`，通过运行代币进行验证，其响应载有解密值，因此它设置了`Cache-Control: no-store`，并乘坐了自己的路线而不是载有插件和说明的运行捆绑。

路线字符串在`internal/server/handlers/routes.go`中存在,`internal/server/static/openapi.json`必须描述它们，包括没有揭示操作。

## 17. 拒绝其他选择

### 仅为每位消费者注射

仅将值输送到命名的进程中 一个工作室MCP服务器环境，一个输入HTTP授权插槽，一个向一个消费者交付的文件，并拒绝向模型选择的命令输送。

它是唯一拒绝的选择，它将使一个值保持在一般运行环境之外，并且将使一个发布消化成为可执行的交付条件。 它被拒绝，因为它只达到消费者BuildMax已经适应，这是无限集的错误面:Agent的中心功能是调用它在运行时选择的工具，而在这个模型下，这些工具没有收到任何东西.它仍然是真正的一个命名的过程，并与它需要的插件-消化结合。

### 证书助手和`PATH`包装

注册一个凭证助手，一个AWS `credential_process`，或者一个`kubectl` exec插件，指向BuildMax经纪人；或者在运行的`PATH`上放置相同名称的包装二进制品，以便令牌只达到孩子。

由于上述原因，这两种工具都与无限的工具组相对适应.通过运行缩写的配置文件配置的版本控制凭证辅助器是一个特殊的案例，它不花费任何钱，因为它是一个生成的配置线，而不是适配器。

### 在沙盒的代理中注射证

终止现有循环回归代理 (`internal/infra/sandbox/proxy.go`) 的 TLS，每个目标主机将一个 `Authorization` 头接，并重新建立 TLS 上游.该值将留在工作者内存中，永远不会进入运行。

这就是唯一的评估选择，可以改变第3条的诚实声明:Agent可以行使权力，而永远不会拥有价值，由于代理看到方法和路径，请求级的政策将成为可能.它也可以根据目标主机而不是工具进行扩展。

它是基于成本而不是功劳而被拒绝的.它需要一个运行范围的CA和一个故意的中部人员在运行中；证书接工具破裂;CA必须按语言运行时间安装，这是它自己的列表；它对非HTTP协议没有任何帮助.它被记录在这里，因为它需要的部分循环代理,`HostMatcher`的每个主机模式，以及`Manager.ChildEnv`的代理路由已经存在，所以稍后重新查看它是一个小步骤。

### 一个`kind`领域在秘密

标签每个秘密一个凭证家族 `github_token`， `kubeconfig`，并使用它来选择默认文件染器。

拒绝，因为它使存储解释值，并声称一个秘密是一个整体染文件，这将密封一个beconfig的非秘密服务器URL和CA证书在加密的块内.项目名称携带一个凭证的结构，和6.3的染器在Agent上选择。

### 每个物品上都有一个秘密或配置的旗

标记每一个项目只能写或可读，所以非秘密配置可以住在凭证旁边，仍然可见分 Kubernetes图像在秘密和ConfigMap之间，和GitHub 秘密和变量之间的行动。

由于它对每一个写作中每一个Space每项分类，以服务于一个已经被放置的案例.A Secret 包含应该仅仅是写作内容； §6.3 的翻译字体包含一个集群共享的内容，并且应该可读.配置在它居住的地方可见，并且创建一个 Secret 仅仅是键入项目名称和值。

### 编译一个秘密的内容

按写字保持一个不可变的版本，所以运行标记一个准确的版本，转换永远不会扰乱它。

由于运行没有重新读取，所以其余的属性是无疑的，因为运行不会再读取，并且使用的消费配置表示*什么*运行已经被Agent修改固定.一个版本将添加第二个历史记录来调整，一个保留问题，一个废弃运行的保留问题，以及一个解密旧版本的路径，以保证单行重写的时间已经没有.如果它在此后要求证据，则可以在此处恢复添加值；它将关闭。

### 部署环境仅是变量

保持当前的模型，并要求运营商将所有凭证放入员工环境中.没有新的数据库，加密,UI或供应商代码，没有Space范围，没有每一个Agent帐户的选择，没有轮换，没有可用的审计.每个Agent的每次运行都得到了每一个值。

### 部署全球的秘密范围

见第4条。 拒绝，因为全球值没有所有者可以归因于它，没有Space可以撤销它，并且没有Spaces'运行的答案可以读取它。

### 只有外部秘密管理人员

要求Vault或云提供商，员工通过工作负载身份检索值，提供强大的提供商生命周期，而没有BuildMax值存储.它违反了外盒私人部署承诺，在每个提供商的授权不同，并且只要没有仔细经纪，员工提供商搜索能力.外部后台属于第9.2条，而不是代替它。
