## 1. 目的

一个长时间运行的 Agent 会遗忘。这并不是模型本身出了问题，而是因为消息列表本质上是一个队列：`TrimHistory` 会丢弃队列头部，压缩（compaction）则会用一份有损摘要替换掉头部。任何只以消息形式存在的东西，终将不复存在。

有两样东西不能受此影响：

- **Agent 是谁。** 用户撰写的角色设定及其硬性约束（“你是一名法律顾问”“绝不要推送到 main 分支”）。在一次会话的生命周期内是静态的。
- **Agent 知道什么、正在做什么。** 已经做出的决策、已经排除的路径、用户在第 3 轮里说过一次的约束，以及当前正在进行的工作单元。这些是动态的、由 Agent 自己产生的，并在整个运行过程中不断更新。

如今第一项只被部分解决，第二项则完全没有解决。本文档定义了一条存储规则、一个渲染插槽，以及能让两者都得以留存的压缩集成方式。

它同时修复了现有压缩路径中的一个缺陷（§3.3）：该缺陷会导致最早的上下文被彻底丢失，而不是被摘要保留。

## 2. 当前基线

已经生效的部分，以及其中的接缝所在。

**系统消息不受裁剪影响。** `callLLM`（`internal/core/agent/agent.go:245`）只裁剪 `history`，然后无条件地在前面拼上系统消息：

```go
history = TrimHistory(history, systemTokens, contextWindow, 0)
messages := append([]llm.Message{{Role: "system", Content: systemPrompt}}, history...)
```

这正是整个设计所依赖的那条性质。任何从实时状态渲染进系统消息里的内容，都会在每次调用时重新生成，因此永远不会因为陈旧而被淘汰。

**Sub-agent 已经拥有自定义角色。** `SubAgentDef`（`internal/tool/agent_def.go:17`）解析 frontmatter 加一段 Markdown 正文，该正文成为这一类 Agent 的系统提示词。主 Agent 却没有对应的机制：`BuildEffectiveSystemPrompt`（`internal/agentapp/assembly.go:16`）由 `DefaultSystemPrompt` + 模型说明行 + 全局 `AGENTS.md` + 工作区 `AGENTS.md` 拼接而成，没有按 Agent 区分的层。

**压缩机制已经存在，并且能跨回合持久化。** `RunLoop` 会在上下文窗口用到 80% 时执行压缩，保留 20% 的逐字保留区（`internal/core/agent/context.go:12`），`Session.AddCompaction`（`internal/core/session/session.go:109`）会推进边界，使后续回合从压缩后的视图开始。

**`TodoWrite` 依设计是无状态的。** `internal/tool/todo_write.go:29` 明确说明了这一点：它只校验并格式化一份列表，不存储任何东西。这份列表只以工具结果消息的形式存在——因此它会像任何其他消息一样被压缩掉，而由于它是唯一的副本，这就是真正的丢失。

## 3. 差距

### 3.1 主 Agent 没有可持久化的按次运行指令——已修复 ✅

用户无法说“这个 Agent 是一名法律顾问”，并让这句话在整个会话期间持续生效。工作区级的 `AGENTS.md` 是最接近的替代方案，但它的作用域是工作区，而不是 Agent，而一个工作区可能承载多种 Agent 角色。

### 3.2 Task 与情境状态只存在于消息中——已修复 ✅

Agent 在一次运行中学到的一切——目标、验收标准、在方案 A 失败后改用方案 B 的决策、合同受纽约州法律管辖这一事实——都只以消息的形式存在。压缩被要求保留这些内容（`internal/agentapp/compactor.go:9`），但这不过是让一个 LLM 在无上限的材料上尽力而为，而且每压缩一次质量就会下降一次。

### 3.3 压缩摘要不会累积——更早的上下文会丢失——已修复 ✅

这是一个缺陷，而不是设计上的空缺。

`RunLoop` 调用 `opts.Compactor.Compact(ctx, toSummarize)`，其中 `toSummarize` 是 `history` 的一个前缀。上一次的摘要**并不在** `history` 里——它存放在 `Session.CompactionSummary` 中，并由 `internal/agentapp/app.go:500` 渲染进系统提示词。而 `AddCompaction` 会直接把它整个覆盖掉：

```go
s.CompactionSummary = summary
```

于是第 *N* 次压缩产生的摘要中，不包含第 *N-1* 次压缩的任何内容。两次压缩之后，最早的上下文就不再是被摘要了——而是彻底消失了。会话越长，开头部分消失得就越彻底。这正是“Agent 忘记了最初的指令”这一现象背后的直接机制。

一个相关的外观问题：一次运行内的压缩发生后，系统提示词里会带有两个 `<context_compaction>` 块，因为 `app.go:500` 已经追加了持久化的那一份，而 `agent.go:152` 又追加了新的一份。

### 3.4 永久插槽没有边界——摘要已加边界 ✅

`CompactionSummary` 被拼接进系统提示词时没有任何大小限制。系统提示词是唯一没有降级路径的地方——它在每次调用中都会以全价重新发送，也无法被裁剪。任何新增的永久状态（§5.3）都继承了这个隐患，因此必须在构造时就被限定边界。

### 3.5 注意力稀释——重申不变量 ✅

即便一条指令原封不动地出现在系统提示词中，随着上下文被工具输出填满，模型对它的遵从度也会下降。这是模型本身的特性，而不是上下文管理的 bug，因此无法靠存储来修复，只能靠在靠近生成点的位置重新陈述那一小组不变量来修复。

### 3.6 细节：阈值注释与常量不一致——已修复 ✅

`internal/core/agent/context.go:12` 的文档写的是 0.75，而常量实际是 0.80。顺手修改此文件时一并修正这条注释。

## 4. 方向

下面这条规则统摄本文档的其余部分：

> **必须留存的状态存在于消息列表之外，在每次调用时重新渲染，并在构造时就被限定边界。**
>
> 消息列表是一个缓存，不是存储。它必须可以被丢弃，而不造成信息损失。

由此推出的一些结论，塑造了本文档接下来的内容：

- **不要手工对 Agent 分类。** 早期草案曾让 Agent 定义声明 `memory: todo | facts | none`。这被否决了：它把一套本体强加给了用户，而 Agent 并不需要这套本体。只需要一个存储、自由格式的内容；一个对话型 Agent 完全可以让它保持为空，一个任务型 Agent 则可以用一份清单填满它。形态应当从使用中自然浮现。
- **优先选择运行时保证的写入，而不是依赖模型的自律。** 一个需要模型自己记得去调用的工具，恰恰会在上下文压力最大的时候被忘记调用。凡是写入至关重要的地方，都由运行时来触发它（§5.5）。
- **整体替换，而非追加。** 只追加不删减的状态会腐化、会膨胀。每次写入都重写整份文档，能把淘汰过程当作副作用强制执行。
- **有边界的渲染是存储契约的一部分**，而不是后续才做的优化（§5.6）。

## 5. 范围之内

### 5.1 分层的系统提示词

`BuildEffectiveSystemPrompt` 新增一层，并采用固定顺序：

| # | 层 | 来源 | 生命周期 |
|---|---|---|---|
| 1 | 运行时基础层 | `DefaultSystemPrompt` + 模型说明行 | 静态 |
| 2 | 用户指令 | `<BUILDMAX_HOME>/AGENTS.md` | 每次会话内静态 |
| 3 | 工作区指令 | `<workspace>/AGENTS.md` | 每次会话内静态 |
| 4 | **附加系统提示词** | flag、定义文件正文，或 Agent 记录（§5.2） | 每次会话内静态 |
| 5 | 压缩摘要 | `Session.CompactionSummary` | 随压缩变化 |

第 1–4 层在一次会话内保持稳定，因此构成一段可缓存的前缀。第 5 层会变化，因此放在最后。锚定块（§5.4）是在消息之后渲染的，而不是在这里，所以它永远不会使这段前缀失效。

### 5.2 附加系统提示词

第 4 层是一个承载自由文本的插槽。这里有两个相互独立、分别回答的问题：这个插槽里放什么内容，以及谁有权限往里面填内容。

有一点命名上的说明，因为第一版草案在这里搞错了。这个插槽最初被称为“Agent 角色（agent role）”，而每一位读者都必须被告知这个字段装的其实是提示词文本，而不是某个角色的名字——需要这样一句额外说明，本身就证明这个名字取错了。在代码里它叫 `AdditionalSystemPrompt`，准确说明了它装的是什么；`--agent` 只是填充它的三种方式之一，而不是它本身。“角色”这个说法只在描述意图时才会在下文中保留。

#### 这个插槽

自由文本，追加在第 3 层之后。它是**增量式的**——它永远不会替换第 1–3 层，因为替换掉 `DefaultSystemPrompt` 会剥离运行时所依赖的工具使用约定，而由此产生的失败看起来会像是模型出了问题，而不是配置出了问题。

只有一条结构上的约定：一个可选的 `## Invariants` 小节会被提取出来，并额外在锚定块中重新陈述一遍（§5.4）。它唯一的目的，是为 §3.5 提供一份小型的、由用户明确选择的内容，而不必每个回合都重复整段角色设定。插槽中的其余内容一律视为不透明文本。

上限为 8 KB（§5.6）。

#### 写入方

| 写入方 | 界面 | 传输方式 |
|---|---|---|
| `--append-system-prompt TEXT` | CLI，print 模式 | Flag |
| `--append-system-prompt-file PATH` | CLI，print 模式 | 指向文件的 Flag |
| `--agent NAME` | CLI，print 模式 | 解析出一个定义文件；其正文填入该插槽 |
| Agent 定义记录 | Portal → worker | Worker API 字段（**不是** argv——见下文） |
| Agent 选择器 | Desktop | 进程内，无传输过程 |

当不止一种方式同时适用时，按以下顺序拼接：先是具名定义的正文，然后是临时文本。一个 Portal Agent 完全可能同时拥有一个可复用的基础角色和一份针对本次实例的定制内容。`--append-system-prompt` 与 `--append-system-prompt-file` 互斥。

这里刻意没有提供一个会整体替换的 `--system-prompt` flag。

#### Portal 不传递 flag

调度器只用一个参数来启动 worker（`internal/server/scheduler/runner.go:57`）：

```go
cmd := exec.CommandContext(ctx, r.workerPath, "--task-run-id", run.TaskRunID)
```

worker 需要的其余一切，都要回头向服务器拉取——`GET /api/worker/task-runs/{id}`，解码为 `workerclient.GetTaskRunResponse`。因此，一段由 Portal 撰写的系统提示词，要以 **Worker API 契约中新增字段**的形式传递，沿用 `internal/infra/workerclient/api_types.go` 中 `TaskRunLLM` 的先例，包括它的向后兼容约定：字段缺失就代表这是一个在该字段出现之前构建的 worker，行为与以往一致。

argv 在这里是错误的传输方式，原因这个仓库其实早就记录过了，就在启动调用的前三行：运行令牌是通过环境变量而不是命令行参数传递的，原文是*“因为机器上的任何进程都能读到命令行参数。”* 一段用户撰写的系统提示词，正是这条理由所针对的那类内容——Portal 的这个字段，正是有人会粘贴案情背景、客户约束、内部政策的地方。同样的理由也促使本地场景采用 `--append-system-prompt-file`，因为在开发者共享的机器上，`ps` 命令同样能读到命令行参数，而且多行文本本来就不方便通过 shell 传递。

argv 还有一个硬性上限：Linux 把单个参数限制在 `MAX_ARG_STRLEN`（128 KB）以内。8 KB 的上限远低于这个数字，但触及这个上限时的失败表现很糟糕，这也是传输方式不应该成为大小限制因素的另一个理由。

#### 解析与可见性

这个插槽是**在运行开始时，由负责组装这次运行的一方**解析的，最后一个写入方生效。不存在跨运行的角色加锁机制。

- Portal 在每次运行时都会重新从 Agent 定义记录中解析，因此编辑该字段会在下一次运行时生效。这正是一个人编辑某个字段时会期望的行为；拒绝这种行为才是缺陷，而不是保障。
- CLI 在会话创建时写入解析后的值，并在恢复会话时复用它，除非再次传入了 flag。
- 会话中存储的是**这次运行实际使用的值**。它是一条记录，而不是权威来源。

真正让“最后写入方生效”这条策略安全的，是可见性，而不是强制约束：运行轨迹会记录本次运行加载了哪些系统提示词层及其大小。这并不是一项新要求——信任保障 §3.6 早已指出，Agent 应当公开一次运行都加载了哪些记忆来源，而该文档的 §3.3 把这一点列为目前尚未实现。这样一来，身份的变化就变成了可观察的事实，而不必依赖某个错误去阻止它。

（本节此前的一版草案曾提议：当一次会话在不同角色下被恢复时报错。这一提议已被取代：它会破坏 Portal 中最普通的编辑场景，而轨迹这项要求已经覆盖了它原本想要防范的顾虑。）

#### 具名定义与 sub-agent 命名空间

`--agent NAME` 从 `config.AgentDefsSearchPaths`（`internal/config/config.go:136`）中解析——依次是 `<workspace>/.buildmax/agents/`，然后是 `~/.buildmax/agents/`——用的正是 `Task` 工具已经在加载的那批文件，采用同样的 `SubAgentDef` 格式（`internal/tool/agent_def.go:17`）。没有新的文件格式，也没有新的发现路径：

```markdown
---
name: law-consultant
description: Answers contract questions for the current matter
---
You are a law consultant. Cite the governing statute for every claim.

## Invariants
- Never state a conclusion without naming the jurisdiction it rests on.
- If the jurisdiction is unknown, ask before advising.
```

这一版中接受了两者之间的重叠：每个 sub-agent 都可以作为主角色启动，每个角色也都会作为一个 `Task` 委派目标出现。已知的摩擦点在于，`description:` 字段本是写给负责委派的那个 LLM 看的，当它被用作主角色描述时会显得有点奇怪。如果这真的成为一个实际问题，一个可选的 `scope: primary | subagent | both` frontmatter 字段可以解决它——但这被推迟到有人真正遇到这个问题时再做，而不是提前凭空添加一个概念。

`--agent` 是对这些 flag 的一种便利封装，而不是主要接口。真正的主要接口是那个自由文本插槽。

### 5.3 Session Notes

一份有边界的、由 Agent 维护的简短条目列表，存储在会话上，并在每次调用时渲染出来。

命名：面向 LLM 的工具名为 **`NoteWrite`**，与 `internal/tool/names.go` 中的 PascalCase 命名约定以及 `TodoWrite` 的配对方式保持一致。其他备选名称被否决的理由值得记录下来，因为工具名本身就是模型每次调用都会读到的提示词素材：

| 被否决的名称 | 原因 |
|---|---|
| `KeyNote` | 在英语里读起来像 “Keynote”——苹果的演示软件，或者“主题演讲” |
| `Whiteboard`、`Scratchpad` | 隐含“可随意丢弃的草稿空间”之意，与这里要提供的持久性保证正相反 |
| `Memory` | 已经被向量存储检索类系统占用，会造成过度承诺 |
| `Journal` | 暗示只追加、按时间顺序记录，而这正是 §4 所否决的模式 |
| `Notebook` | 与 Jupyter 撞名 |

存储方式——在 `session.Session` 上新增一个字段，持久化在会话文件中：

```go
// Note is one durable session note. Notes survive history compaction and are
// re-rendered on every model call.
type Note struct {
    Text             string `json:"text"`
    WrittenIteration int    `json:"written_iteration"` // iteration index; recorded, not rendered
}
```

形态上的约束，由工具而非模型的自觉来强制执行：

- 最多 **15 条**，每条最多 **200 个字符**。
- 每条都是纯粹的一行文字。这不是一份自由格式的文档：散文式的内容会无声无息地腐坏，而一份简短的列表始终保持可读、自我限定边界。
- 每次调用都携带**完整**列表，并替换掉已存储的那一份。
- 超出上限的调用会失败，工具结果中会说明具体上限，并要求模型合并或丢弃部分条目。按照本仓库的约定，这类失败输出必须对 LLM 有用，而不能只是一条干巴巴的错误信息。

工具描述承载着行为契约，而这比名字本身更重要：

> 这些笔记会在会话历史被压缩后依然留存，并在每一个回合都展示给你。只记录那些之后无法恢复、但你仍然会用到的内容：已做出的决策及其理由、已经排除的方案、用户说过一次的约束条件，以及后续回答会依赖的情境事实。不要记录那些重新读一遍文件就能恢复的内容，也不要记录你当前正在做什么这类流水账。传入完整列表；它会替换掉已存储的那一份。

`TodoWrite` 保留了它自己的工具身份——“开始一个任务，把它标记为 in_progress”是一种值得保留的强触发约定——但它变成了有状态的，并且由同一个会话存储支撑，因此它的列表也能在压缩后存活，并渲染在同一个块里。这两个工具最终是否会合并，留作未决问题（§11）。

读和写走的是不同的路径，这种分离是由运行时已有的一项特性所决定的，而不是出于对称性而刻意选择的。

**读取**通过 history 上的一个可选接口实现，与 `CompactionHistory` 这种扩展方式（`internal/core/agent/agent.go:41`）如出一辙，因此 `internal/core/agent` 不需要对会话持久化产生任何依赖：

```go
// NotesHistory is an optional extension of MessageHistory implemented by
// histories that carry durable session state.
type NotesHistory interface {
    MessageHistory
    NoteStore
}
```

**写入**没法走这条路，因为一个工具拿不到 history 的引用。工具也不能持有 session：`AgentApp` 按模型名缓存了一个工具注册表（`internal/agentapp/app.go`），因此同一个模型下的每一个会话都共享同一个工具实例，如果在工具上放一个 session 指针，就会把一个会话的笔记泄漏到另一个会话里。因此这个存储是通过 context 传递给工具的，与本就通过这条路径传递的会话 ID 放在一起：

```go
type NoteStore interface {
    Notes() []Note
    SetNotes(notes []Note, iter int)
    Todos() []Todo
    SetTodos(todos []Todo, iter int)
}

func CtxWithNoteStore(ctx context.Context, s NoteStore) context.Context
func NoteStoreFromContext(ctx context.Context) (NoteStore, bool)
```

`iter` 这个参数，是让一个条目在整份列表被重写之后依然能保留其“年龄”的关键：一个文本没有变化的条目，会保留它第一次出现时的迭代序号，只有真正的新条目才会被打上当前的迭代序号。对于 todo 而言，判定“是否相同”的键是内容*加上*状态，因此把一个任务标记为 `in_progress` 会重新计时——这正是值得上报的那个数字。`RunLoop` 会在执行工具调用之前，把当前的迭代序号放进 context。

一次运行如果其 context 中没有携带存储，这并不算错误。工具会退回到只格式化列表，并明确说明这份内容没有被保存，因为报告“保存成功”，而它随后又消失了，要比干脆报告“没有保存”更糟糕。

### 5.4 锚定块

一个块，在每次调用时渲染在消息列表之后，承载着 §3.5 要求必须靠近生成点的那些状态：

```text
<session-state>
## Invariants
- Never state a conclusion without naming the jurisdiction it rests on.

## Notes
- [i12] Matter is governed by New York law; client is the lessee.
- [i40] Approach A (rescission) ruled out — outside the limitation period.

## Todo
- [in progress, 38 iterations] Draft the notice of default
- [pending] Check the cure period against §4.2
</session-state>
```

渲染规则：

- 在 `callLLM` 中，作为一条 `user` 角色的消息，追加在 `history` 之后渲染。这在本仓库使用的与 OpenAI 兼容的传输层上（`internal/infra/llm/client.go`、`internal/infra/llmwire`）是安全的，因为它接受连续的 user 消息。未来若引入原生的 Anthropic 传输层，则必须合并连续的 user 消息，因为该 API 要求角色交替出现。
- **空的小节会被省略；若整个块都为空，则完全不渲染。** 一个从不写笔记的对话型 Agent 不需要为此付出任何代价。这正是替代那种被否决的“按 Agent 分类”方案的做法：是否存在内容本身就是信号。
- 不持久化进会话历史。它是一次投影，每次调用都会重新生成，绝不能作为消息累积下来。
- 只有当它同时也被排除在请求之外时，才会被排除在 `EstimateTokens` 的统计之外；否则它会像任何一条消息一样计入上下文窗口。

### 5.5 压缩集成

三处改动，按价值从高到低排列。

**a. 压缩前的强制检查点——已上线 ✅。** 在执行摘要之前，给 Agent 一个有边界的回合，让它先更新自己的笔记，并向它提示即将丢失的材料：

> 下面这段记录即将从对话中移除。其中任何你之后还会需要的内容，现在都必须写进你的笔记——这是这些材料存在的最后时刻。

这是本文档中价值最高的单项改动。它把记笔记这件事，从“寄希望于模型记得去调用工具”，变成了在信息被销毁的那一刻、由运行时保证执行的一个检查点，直接针对性地解决了 §1 所描述的失败模式。它的代价是每次压缩多一次模型调用——这是可以接受的，因为压缩本身已经要付出一次调用的代价。

具体实现如下：

- 这个检查点是一个接口，`agent.StateCheckpointer`，位于 `RunLoopOpts` 上，采用 `ContextCompactor` 早已确立的那种形态：由 `internal/core/agent` 定义接口，由 `internal/agentapp` 用本次运行的 LLM 客户端来实现它。`internal/core/agent` 自己无法构建工具——是 `internal/tool` 导入了它，所以依赖方向只能是单向的。
- 它在 `checkpointAndCompact` 内部触发，发生在 `PreCompact` hook 已经放行这次压缩之后。它本身不是一个 hook：`PreCompact` 运行的是用户配置的外部命令，而一次被阻止的压缩不会销毁任何东西，因此也就没有什么需要设检查点。
- 回合预算是**两次**，而不是一次。一次因校验失败而被拒绝的写入——比如一份过长的笔记列表——如果只有一次机会，就会在材料唯一还能被抢救的那一刻彻底丢失它，所以这次拒绝会作为工具结果返回，让模型再有一次改正的机会。一旦某个回合干净地完成写入，或者不再产生任何工具调用，这个过程就会立刻停止。
- 这里能用的工具集恰好只有 `NoteWrite` 和 `TodoWrite`。如果让模型此时还能用上文件或 shell 工具，它就会把这个检查点当成一个可以继续干活的回合。
- 被丢弃的消息会被压平成一段文字记录，而不是作为结构化消息重新回放。回放它们的话，会呈现出助手调用了一些这个检查点根本没有提供的工具，而一段文字记录读起来更贴合这里提出问题的方式——它是一份供审阅的记录，而不是一段要继续下去的对话。
- 失败会被记录日志，压缩照常进行。丢失一次检查点，损失的只是上下文；而如果因此跳过它所守护的那次压缩，损失的会是整次运行。

**b. 累积摘要——修复 §3.3。** 上一次的摘要必须能传到压缩器手里。把它作为一条合成消息，拼接在 `toSummarize` 的最前面，这样第 *N* 次压缩摘要的对象就是*（摘要 N-1 + 新近被丢弃的消息）*，而不只是这些消息本身。`AddCompaction` 保留其“整体替换”的语义，而此时这个语义是正确的，因为新摘要已经涵盖了旧摘要的内容。

**c. 用实时状态锚定摘要质量——已上线 ✅。** 当前的笔记和尚未完成的 todo，会作为一种相关性信号被传入压缩提示词：*这些内容是活跃的——凡是与它们相关的内容都要保留细节；其余一切都压缩成一行。* 在此之前，`compactionSystemPrompt` 完全没有给模型任何“什么还悬而未决”的信号，导致它把预算平均花在了价值极不均衡的材料上。

`LLMCompactor` 是从它本就被传入的那个 context 中读取存储的，因此 `ContextCompactor` 不需要为此扩大接口范围。

这一轮改动中还包含：去重 `<context_compaction>` 块，使 `RunLoop` 替换掉持久化的那个块，而不是再追加第二个（§3.3）。

### 5.6 预算

每一个永久性插槽都要有一个明确的上限。系统提示词无法被裁剪，因此在那里无限增长，比丢失一条消息更糟糕。

| 插槽 | 上限 | 达到上限时的行为 |
|---|---|---|
| 附加系统提示词（第 4 层） | 8 KB | 在解析阶段拒绝，并给出明确错误，指出是哪个写入方（flag、文件，还是 API 字段） |
| `## Invariants` | 1 KB | 渲染时截断；仅警告一次 |
| 压缩摘要 | 约上下文窗口的 2% | 在下一轮压缩时对摘要本身再次摘要 |
| Notes | 15 条 × 200 字符 | 工具调用失败，模型必须合并 |
| Todo | 30 条 | 已完成的条目折叠为一个计数 |
| 锚定块整体 | 约 800 个 token | 按优先级丢弃：不变量 > 进行中的 todo > 笔记 > 待处理的 todo > 已完成的 todo |

## 6. 范围之外

- **跨会话记忆。** Notes 的作用域是单次会话。`AGENTS.md` 文件是指令，不是记忆。CLI/Desktop 共享的 Project 身份，以及第一个跨会话记忆作用域，在[本地项目记忆](本地项目记忆.md)中单独设计；全局用户记忆与 Space 记忆都不在这两份记录的范围之内。
- **自动漂移检测。** 运行时其实可以统计“进行中”的 todo 上一次变化之后已经过去了多少次迭代，并在超过阈值后注入一条更强的提醒——这是对现有 `loopGuard`（`internal/core/agent/policy.go:36`）在任务层面的一种泛化。这里刻意推迟实现：它需要先有 §5.3 中那个有状态的 todo 作为前提，而且它应当基于实际观察到的漂移情况来设计，而不是凭空猜测阈值。`written_iteration` 字段现在就被规定下来，正是为了让这项未来的设计一旦启动就能立刻拿到数据。
- **把记笔记做成 sub-agent 的一项功能。** sub-agent 的运行通常很短，其结果会被返回给父 Agent，因此这里没有围绕它们保留笔记这件事做任何设计。但隔离性并非可选项：父 Agent 的存储会随着 context 一起传给它派生出的 sub-agent，因此 `internal/tool/subagent_runner.go` 会把它重新指向 sub-agent 自己的会话。如果不这样做，一个 sub-agent 调用 `TodoWrite` 就会覆盖掉委派它的那次运行的任务列表。sub-agent 的状态会在它返回时被丢弃。
- **用于查看和编辑笔记的 Portal/Desktop 界面。** 信任保障 §3.6 要求记忆必须可被检视、可被用户控制；这里的存储机制让这一点成为可能，具体界面则由相应的产品面来规定。
- **对笔记做语义化的类型标注。** 没有分类，除了文本加迭代序号之外没有任何 schema。§4 已经说明了原因。

## 7. 运行时流程

`RunLoop` 的一次迭代，新增的步骤已标出：

1. 从会话中读取 `history`。
2. 如果预估的 token 数超过压缩阈值：
   - **先触发 `PreCompact`，再给 Agent 一个回合，让它针对即将被丢弃的消息更新笔记（§5.5a）；**
   - 拆分为 `toSummarize` / `toKeep`；
   - **把上一次的摘要拼接到 `toSummarize` 的最前面（§5.5b）；**
   - **把当前的笔记与未完成的 todo 传给压缩器（§5.5c）；**
   - 存储摘要，推进边界，触发 `PostCompact`。
3. 构建系统提示词：第 1–4 层（稳定）+ 第 5 层（摘要，**替换**掉任何已持久化的块，而不是追加）。
4. 把 `history` 裁剪到剩余预算之内。
5. **根据实时状态渲染锚定块；如果非空，追加在 `history` 之后（§5.4）。**
6. 调用模型。
7. 如果模型调用了 `NoteWrite` 或 `TodoWrite`，**直写会话状态**并持久化；工具结果仍然是一条普通消息，之后可以自由地被裁剪掉，因为它已经不再是唯一的副本。

第 7 步正是让裁剪变得安全的关键：一旦状态在消息列表之外有了自己的归宿，历史上的工具结果就成了冗余，丢弃它们不会损失任何东西。压缩因此变得更便宜，也更安全。

这一阶段在 Portal 路径上修复的问题，比原计划设想的更严重。此前，一个 Portal Agent 的 `Instructions` 是由 `buildTaskInputFromAgent` 渲染进**任务输入**里的——也就是一条用户消息，因而是可被压缩的，这正是 §1 所描述的失败模式在生产环境中真实发生。更糟的是，一个自带输入创建出来的任务会把这些指令完全丢弃，导致一个 Agent 的身份设定只对那些没有其他提示词的任务才生效。第 4 层修复了这两个问题。

刻意没有改动的地方：`buildTaskInputFromAgent` 在创建一个没有自带输入的任务时，仍然会把这些指令渲染进输入里。移除它们会改变 Portal 上可见的任务输入以及自动生成的标题，而这是一个本记录不涉及的产品决策。代价是，这样一个任务会把这些指令携带两遍——一遍持久地存在于系统提示词中，另一遍存在于第一条消息里，而后者最终会被压缩丢弃。这一点值得在重新审视 Portal 界面时再考虑。

第 1 阶段与第 2 阶段各自独立地就有价值。第 3 阶段依赖第 2 阶段。第 4 阶段独立于第 1–3 阶段，可以根据路线图需要重新排序。

## 9. 验收

- 在一次会话的第一个回合中陈述的事实，在经历三次压缩之后仍然可供模型使用——这是靠笔记做到的，而不是靠运气。
- 一个用户撰写的角色设定在整个会话期间持续生效，不会因压缩而被削弱。
- 一个从不写笔记的对话型 Agent，不会因为这项功能而在每个回合都多付出 token 成本。
- 没有任何永久性插槽会无限增长；每一个都规定了达到上限时的行为。
- 从消息列表中丢弃所有历史上的 `NoteWrite` / `TodoWrite` 工具结果，不会造成任何状态损失。
- 压缩失败依然遵循“失败即放行”的原则，与轨迹和 Hook 的既有约定一致：一次失败的笔记检查点会以警告级别记录日志，运行继续进行。

## 10. 分层

没有任何架构边界发生移动。`internal/core/agent` 只通过 `NotesHistory` 接口了解笔记，正如它此前只通过 `CompactionHistory` 了解压缩一样；`internal/core/session` 拥有这份数据；`internal/tool` 拥有 `NoteWrite`；`internal/agentapp` 负责把它们接线组装起来。`internal/core` 中没有任何部分因此对 config、infra 或 service 包产生新的依赖，因此 `internal/architecture` 中的测试不受影响。

## 11. 未决问题

- **`NoteWrite` 和 `TodoWrite` 最终会合并吗？** 带有状态字段的笔记本可以涵盖 todo 的能力。反对的理由是：`TodoWrite` 的触发约定很强、模型也已经学得很好，合并会付出这方面的代价。等第 2 阶段积累了实际使用数据之后再做决定。
- **锚定块应该放进系统提示词的末尾，还是保持放在消息之后？** 系统提示词更简单，也与具体 provider 无关；放在消息之后则更靠近生成点，理论上应当有更好的遵从度。本设计选择了放在消息之后；如果实践证明遵从度并无明显差异，把它移入系统提示词可以消除 §5.4 中提到的那条传输层附加说明。
- **第 4 层应该能够压制继承下来的层吗？** 它是增量式的，因此一个在 Go 代码仓库中运行的 `law-consultant` 提示词，同样会收到该工作区 `AGENTS.md` 里的贡献规则。这通常无伤大雅，因为更靠后的层权重更高，但“给我一个干净的角色”也是一个合理的诉求。一个 frontmatter 字段 `inherit: false` 可以满足这个需求。目前推迟，因为在看到真实使用情况之前，无法判断什么样的默认行为才是正确的。
- **笔记在持久化之前应该被脱敏吗？** 它们是模型撰写的内容，最终会落在会话文件里，而持久化运行轨迹已经把会话文件视为需要脱敏的对象。答案很可能是肯定的，复用轨迹的脱敏器即可——留待第 2 阶段期间确认。
