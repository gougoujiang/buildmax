## 1. 目的

长期运行的 Agent 会遗忘上下文，不是模型本身失效，而是消息列表像队列一样增长：`TrimHistory` 丢弃头部，压缩则用有损摘要替换头部。任何只存在于消息中的信息最终都会消失。

有两件事不得受此约束：

- **Agent 是谁。** 用户定义的角色及其硬约束（“你是一名法律顾问”“永远不要推送到主分支”），属于长期稳定的会话身份。
- **Agent 知道什么以及正在做什么。** 已做出的决定、排除过的路径、用户反复声明的约束，以及当前工作的状态。这些内容是动态的，由 Agent 创建并在运行中更新。

今天第一个部分解决了，第二个根本没有解决。这个
文档定义了1个存储规则、1个渲染槽、以及压缩
整合使双方都能生存。

它还修复了现有压缩路径（第 3.3 节）中导致
最古老的背景将被彻底丢失而不是被总结。

## 2. 当前基线

已经起作用的内容以及接缝在哪里。

**系统消息不受修剪。** `callLLM`
(`internal/core/agent/agent.go:245`) 仅修剪 `history`，然后在前面添加
无条件系统消息：

```go
history = TrimHistory(history, systemTokens, contextWindow, 0)
messages := append([]llm.Message{{Role: "system", Content: systemPrompt}}, history...)
```

这是整个设计所依赖的属性。任何渲染到
每次调用都会重新派生来自活动状态的系统消息，并且不会过期。

**子代理已具有自定义角色。** `SubAgentDef`
(`internal/tool/agent_def.go:17`) 解析 frontmatter 加上 markdown body，并且
正文成为该代理类型的系统提示符。主代理没有
等效：`BuildEffectiveSystemPrompt` (`internal/agentapp/assembly.go:16`)
组成 `DefaultSystemPrompt` + 模型线 + 全局 `AGENTS.md` + 工作区
`AGENTS.md`，没有每代理层。

**压实存在并持续跨匝。** `RunLoop` 压实率为 80%
上下文窗口，保留 20% 的逐字保留
(`internal/core/agent/context.go:12`) 和 `Session.AddCompaction`
(`internal/core/session/session.go:109`) 推进边界，以便稍后转弯
从压缩视图开始。

**`TodoWrite` 设计为无状态。** `internal/tool/todo_write.go:29` 说
如此明确：它验证并格式化列表，并且不存储任何内容。名单
仅作为工具结果消息存在 - 因此它像其他任何消息一样被压缩
消息，并且因为它是唯一的副本，所以这是真正的损失。

## 3. 差距

### 3.1 主要代理没有持久的每次运行指令 - 已修复 ✅

用户不能说“此代理是法律顾问”并保留该代理的身份
整个会议。工作区 `AGENTS.md` 是最接近的，但它是
工作区范围，而不是代理范围，一个工作区可以托管多个代理
角色。

### 3.2 Task 和情况状态仅存在于消息中 — 已修复 ✅

Agent 在运行过程中学到的所有内容 — 目标、接受标准、
A 失败后决定使用方法 B，事实上合同是
受纽约法律管辖——仅作为消息存在。要求压实
保留它（`internal/agentapp/compactor.go:9`），但这是一个LLM的
尽最大努力处理无限数量的材料，并且它会随着每一次的退化而退化
通过。

### 3.3 压缩摘要不会累积 - 早期上下文丢失 - 已修复 ✅

这是一个缺陷，而不是设计差距。

`RunLoop` 调用 `opts.Compactor.Compact(ctx, toSummarize)`，其中 `toSummarize`
是 `history` 的前缀。之前的总结**不是**在`history`中——它
位于 `Session.CompactionSummary` 中，并通过以下方式呈现到系统提示符中
`internal/agentapp/app.go:500`。 `AddCompaction` 然后直接覆盖它：

```go
s.CompactionSummary = summary
```

因此，压缩 *N* 生成的摘要不包含压缩中的任何内容
*N-1*。经过两次压缩后，最早的上下文并未被总结 - 它是
走了。会话时间越长，开始消失得越彻底。
这就是“Agent忘记了原来的”背后的直接机制
指示”。

相关的外观问题：运行中压缩后系统提示符
两个 `<context_compaction>` 块，因为 `app.go:500` 已经附加了
保留一项，`agent.go:152` 追加新一项。

### 3.4 永久槽没有限制 — 摘要有界 ✅

`CompactionSummary` 连接到系统提示符中，没有大小限制。
系统提示符是唯一一个没有降级路径的地方 - 它会在以下位置重新发送：
每次通话均为全价，且无法削减。任何新的永久状态
（§5.3）继承了这种危险，并且必须受到结构的限制。

### 3.5 注意力稀释——不变量重述 ✅

即使系统提示中逐字存在指令，也必须遵守
随着上下文充满工具输出而降级。这是一个模型属性，而不是
上下文管理错误，并且存储无法修复它。它是由
重新陈述靠近生成点的一小组不变量。

### 3.6 次要：阈值注释与常量不一致 — 已修复 ✅

`internal/core/agent/context.go:12` 文档 0.75；常数为 0.80。修复
触摸此文件时的评论。

## 4. 方向

一条规则控制以下所有内容：

> **必须在消息列表之外生存的状态，重新呈现
> 每次调用，并且受构造限制。**
>
> 消息列表是缓存，而不是存储。它必须是可丢弃的，无需
> 信息丢失。

影响本文档其余部分的后果：

- **不要手动对代理进行分类。** 早期草案有代理定义
  申报`memory: todo | facts | none`。被拒绝：它将本体论推向
  Agent不需要的用户。一家商店，内容自由；一个
  会话代理只是将其留空，任务代理则用
  清单。形状是从使用中显现出来的。
- **更喜欢运行时保证的写入而不是模型规则。** 模型的工具
  必须记住，当上下文压力发生时，调用将被遗忘
  最高。当写入很重要时，运行时会触发它（第 5.5 节）。
- **完全替换，从不追加。** 仅追加状态会腐烂和增长。
  每次写入时重写整个文档会强制驱逐，这是一个副作用。
- **有界渲染是存储合约的一部分**，而不是以后的内容
  优化（§5.6）。

## 5. 范围

### 5.1 分层系统提示

`BuildEffectiveSystemPrompt` 增长一层且固定顺序：

| 相关标识符 ＃|层 |来源 |终身|
|---|---|---|---|
| 1 |运行时基础 | `DefaultSystemPrompt` + 模型线 |静态|
| 2 |使用说明| `<BUILDMAX_HOME>/AGENTS.md` |每个会话的静态|
| 3 |工作区说明 | `<workspace>/AGENTS.md` |每个会话的静态|
| 4 | **附加系统提示** |标志、定义主体或代理记录 (§5.2) |每个会话的静态|
| 5 |压实总结| `Session.CompactionSummary` |压实变化|

第 1-4 层对于会话来说是稳定的，因此它们形成可缓存的前缀。第5层
变化，因此排在最后。锚定块（§5.4）在之后渲染
消息，不在这里，所以它永远不会使前缀无效。

### 5.2 附加系统提示符

第 4 层是一个保存自由文本的插槽。两个问题是分开的
分别回答：槽位包含什么，以及允许谁填充。

命名说明，因为初稿写错了。该插槽被称为
“代理角色”，并且必须告诉每个读者该字段包含提示文本
而不是角色的名称——需要免责声明作为证据
名字错了。在代码中它是`AdditionalSystemPrompt`，它说明了它所包含的内容；
`--agent` 是填充它的三种方法之一，而不是东西本身。 “角色”得以生存
下面仅描述意图。

#### 插槽

自由文本，附加在第 3 层之后。它是 **附加** - 它永远不会替换
第 1-3 层，因为替换 `DefaultSystemPrompt` 会剥夺工具使用
运行时所依赖的约定，导致的失败看起来像
糟糕的模型而不是糟糕的配置。

一种结构约定，并且只有一种：可选的 `## Invariants` 部分是
提取并在锚定块中另外重新陈述（第 5.4 节）。它的鞋底
目的是为§3.5提供一个小的、用户明确选择的有效负载，而不是
每回合重复整个角色。插槽中的其他所有内容都是不透明的
文本。

限制为 8 KB (§5.6)。

#### 作者

|作家 |表面|交通 |
|---|---|---|
| `--append-system-prompt TEXT` | CLI，打印模式|旗帜|
| `--append-system-prompt-file PATH` | CLI，打印模式|标记命名文件 |
| `--agent NAME` | CLI，打印模式|解析定义文件；它的身体填补了这个空缺|
| Agent 定义记录 | Portal → 工人 | Worker API 字段（**不是** argv — 见下文）|
| Agent 拾取器 | Desktop |加工中，无需运输 |

当多个应用时，按以下顺序连接：命名定义的
首先是正文，然后是临时文本。 Portal 代理可以合法地同时拥有
可重用的基本角色和每个实例的自定义。 `--append-system-prompt`
和 `--append-system-prompt-file` 是互斥的。

故意不替换 `--system-prompt` 标志。

#### Portal 未传递标志

调度程序使用一个参数生成工作程序
（`internal/server/scheduler/runner.go:57`）：

```go
cmd := exec.CommandContext(ctx, r.workerPath, "--task-run-id", run.TaskRunID)
```

工作人员需要的其他所有内容都会从服务器拉回 -
`GET /api/worker/task-runs/{id}`，解码为
`workerclient.GetTaskRunResponse`。因此Portal编写的系统提示
作为**工人 API 合同中的新字段**，遵循
`TaskRunLLM`先例于`internal/infra/workerclient/api_types.go`，包括
它的向后兼容性约定：缺席意味着在该字段之前构建了一个工人
行为一如既往。

Argv 在这里是错误的传输，因为该存储库已经
记录下来，生成调用上方三行：运行令牌在
环境而不是在命令行上，*“其中每个进程
机器可以读取它。”* 用户编写的系统提示符正是这种
参数适用的内容 — Portal 字段是某人粘贴
事件背景、客户约束、内部政策。一样的
推理也在本地激励 `--append-system-prompt-file`，因为 `ps` 是
在开发人员的共享盒子上的可读性也丝毫不减，因为多行文本是
首先穿过贝壳就很尴尬。

Argv 也有一个硬上限：Linux 将单个参数限制为
`MAX_ARG_STRLEN` (128 KB)。 8 KB 界限远远低于它，但失败
天花板上的模式很差，这是运输不应该的另一个原因
成为尺寸限制因素。

#### 分辨率和可见性

插槽在运行开始时由组装运行的人员**解析，并且
最后一位作家获胜。角色没有交叉运行锁定。

- Portal 每次运行时都会从代理定义记录中重新解析，因此进行编辑
  该字段在下一次运行时生效。这就是某人编辑字段的内容
  期望；拒绝它将是一种缺陷，而不是一种保障。
- CLI 在会话创建时写入解析值并在恢复时重用它，
  除非再次传递标志。
- 会话存储**实际用于运行的值**。这是一个记录，
  不是权威。

最后写入者获胜的安全性在于可见性，而不是强制执行：运行跟踪
记录加载了哪些系统提示层及其大小。这不是一个
新要求 - trust-harness §3.6 已规定 Agent 应
公开为运行加载了哪些内存源，以及该文档的第 3.3 节
将其列为当前推迟。身份的改变变得明显
而不是错误必须阻止的事情。

（本节的早期草案建议恢复会话时出现错误
在不同的角色下。被取代：它将打破普通的Portal
编辑案例，跟踪要求涵盖了它所保护的关注点。）

#### 命名定义和子代理命名空间

`--agent NAME` 从 `config.AgentDefsSearchPaths` 解析
(`internal/config/config.go:136`) — `<workspace>/.buildmax/agents/` 然后
`~/.buildmax/agents/` — `Task` 工具已加载的相同文件，位于
相同的 `SubAgentDef` 格式（`internal/tool/agent_def.go:17`）。没有新文件
格式，没有新的发现路径：

```markdown
---
name: law-consultant
description: Answers contract questions for the current matter
---
You are a law consultant. Cite the governing statute for every claim.

## Invariants
- Never state a conclusion without naming the jurisdiction it rests on.
- If the jurisdiction is unknown, ask before advising.
```

此通道接受重叠：每个子代理都可以作为
主要角色，每个角色都显示为 `Task` 委派目标。已知的
摩擦是 `description:` 是为委托 LLM 编写的，其内容为
奇怪的是作为主要角色的描述。如果这成为一个真正的问题，
可选的 `scope: primary | subagent | both` frontmatter 字段解决了它 -
推迟到有人击中它为止，而不是在猜测中添加一个概念。

`--agent` 是标志上的便利，而不是主要接口。的
主要界面是自由文本槽。

### 5.3 会话注释

存储在会话中的有界的、由代理维护的短条目列表
每次调用时都会呈现。

命名：面向 LLM 的工具是 **`NoteWrite`**，与 PascalCase 匹配
约定和 `TodoWrite` 配对在 `internal/tool/names.go` 中。
替代方案被拒绝的原因值得记录，因为
工具名称是模型在每次调用时读取的提示表面：

|被拒绝 |原因 |
|---|---|
| `KeyNote` |英文读作“Keynote”——Apple 的演示应用程序，主题演讲 |
| `Whiteboard`，`Scratchpad` |意味着一次性的暂存空间；保证的相反|
| `Memory` |由矢量存储检索系统声明；过度承诺 |
| `Journal` |暗示仅附加年表，§4 拒绝 |
| `Notebook` |与 Jupyter 碰撞 |

存储 — `session.Session` 上的新字段，保留在会话文件中：

```go
// Note is one durable session note. Notes survive history compaction and are
// re-rendered on every model call.
type Note struct {
    Text             string `json:"text"`
    WrittenIteration int    `json:"written_iteration"` // iteration index; recorded, not rendered
}
```

形状约束，由工具而不是模型的善意强制执行：

- 最多 **15 个条目**，每个条目最多 **200 个字符**。
- 参赛作品都是简单的单行文字。不是自由格式的文档：散文腐烂
  无形中，简短的清单保持清晰且具有自我约束力。
- 呼叫携带**完整**列表并替换存储的列表。
- 超出限制的调用失败，工具结果会命名限制并询问
  模型来合并或删除条目。根据存储库约定，该失败
  输出必须对 LLM 有用，而不是纯粹的错误。

工具描述携带行为契约，比
名称：

> 这些注释在对话历史记录的压缩中幸存下来，并显示为
> 每个回合都有你。只记录事后无法恢复的内容
> 你仍然需要：决定及其理由、已经裁定的方法
> out，用户曾经陈述过的约束，有关后来情况的事实
> 答案取决于。不要记录重新读取文件将恢复的内容，并执行
> 不要叙述你目前正在做什么。通过完整的清单；它取代了
> 已存储的一个。

`TodoWrite` 保留自己的工具标识——“启动一个任务，将其标记为 in_progress”
是一个值得保留的强触发约定 - 但变得有状态并且
由相同的会话存储支持，因此它的列表可以承受压缩和渲染
在同一个街区。这两个工具最终是否合并仍悬而未决（§11）。

读写走不同的路线，强制分割
运行时的现有属性，而不是为了对称性而选择的属性。

**阅读**通过历史记录上的可选界面，镜像
`CompactionHistory`扩展（`internal/core/agent/agent.go:41`），所以
`internal/core/agent` 不需要依赖于会话持久性：

```go
// NotesHistory is an optional extension of MessageHistory implemented by
// histories that carry durable session state.
type NotesHistory interface {
    MessageHistory
    NoteStore
}
```

**写入**不能使用该路由，因为工具没有引用
历史。工具也无法保留会话：`AgentApp` 缓存一个工具注册表
每个模型名称 (`internal/agentapp/app.go`)，因此共享一个工具实例
使用该模型的每个会话，工具上的会话指针都会泄漏
将一个会话的笔记复制到另一个会话中。因此，商店通过以下方式获取工具：
上下文，以及已经以这种方式传输的会话 ID：

```go
type NoteStore interface {
    Notes() []Note
    SetNotes(notes []Note, iter int)
    Todos() []Todo
    SetTodos(todos []Todo, iter int)
}

func CtxWithNoteStore(ctx context.Context, s NoteStore) context.Context
func NoteStoreFromContext(ctx context.Context) (NoteStore, bool)
```

`iter` 参数让条目在整个列表中保持其年龄
重写：文本未更改的条目保留其首次出现的迭代
at，并且只有真正的新条目才会带有当前条目的标记。对于待办事项
关键是内容*加*状态，因此将任务移动到 `in_progress` 会重新启动其
时钟——这是值得报告的数字。 `RunLoop` 将迭代放在
执行工具调用之前的上下文。

上下文不包含存储的运行不是错误。工具回落到
格式化列表并明确表示它没有保留，因为报告
一张纸条的成功然后消失比什么都不报告更糟糕。

### 5.4 锚定块

一个块，每次调用时在消息列表之后渲染，携带状态
§3.5 要求接近生成点：

```text
<session-state>
## Invariants
- Never state a conclusion without naming the jurisdiction it rests on.

## Notes
- [i12] Matter is governed by New York law; client is the lessee.
- [i40] Approach A (rescission) ruled out — outside the limitation period.

## Todo
- [in progress, 38 iterations] Draft the notice of default
- [pending] Check the cure period against §4.2
</session-state>
```

渲染规则：

- 渲染为附加在 `callLLM` 中 `history` 之后的 `user` 角色消息。
  这在此存储库使用的 OpenAI 兼容传输上是安全的
  （`internal/infra/llm/client.go`，`internal/infra/llmwire`），接受
  连续的用户消息。未来的本机 Anthropic 传输必须合并
  连续的用户消息，因为 API 需要交替。
- **省略空白部分；不会渲染完全空的块。** A
  从不写笔记的会话代理无需支付任何费用。这就是
  替换被拒绝的每个代理分类：缺席就是信号。
- 不保留到会话历史记录。它是一个投影，每次调用都会重新生成，
  并且绝不能累积为消息。
- 仅当也从 `EstimateTokens` 会计中排除时，才从 `EstimateTokens` 会计中排除
  请求；否则它会像任何消息一样计入窗口。

### 5.5 Compaction 集成

三个变化，按值降序排列。

**a。压缩前强制检查点 — 已发货 ✅.** 在总结之前，
Agent 被赋予有限的轮次来更新其笔记，并提示材料
即将丢失：

> 下面的文字记录即将从对话中删除。任何东西在
> 你现在仍然需要的东西必须记在你的笔记里——这是最后一刻
> 材料存在。

这是本文档中单个最高值的项目。它将笔记转换为
从“希望模型记得调用该工具”转变为运行时保证
检查点在信息被破坏的那一刻直接
解决§1 的故障模式。每次压缩都会花费一次额外的模型调用 -
可以接受，因为压缩已经花费了 1。

已实现：

- 检查点是 `RunLoopOpts` 上的接口 `agent.StateCheckpointer`，
  在已建立的形状 `ContextCompactor` 中：`internal/core/agent`
  定义它，`internal/agentapp` 使用运行的 LLM 客户端实现它。
  `internal/core/agent` 无法自行构建工具 - `internal/tool` 导入
  它，因此依赖项仅以一种方式运行。
- 在 `PreCompact` 挂钩后，它在 `checkpointAndCompact` 内部触发
  允许压实。它本身不是一个钩子：`PreCompact` 运行
  用户配置的外部命令，并且阻止的压缩不会破坏任何东西，
  所以没有什么可检查的。
- 回合预算是**两个**，而不是一个。被验证拒绝的写入 —
  笔记列表过长——否则会直接丢失材料
  瞬间无法恢复，因此拒绝作为工具结果返回
  并且模型得到一次修正。一转写干净就停止
  或不产生任何工具调用。
- 工具组正是 `NoteWrite` 和 `TodoWrite`。使用文件或 shell 工具
  在到达时，模型将检查点视为继续工作的轮次。
- 丢弃的消息被扁平化为转录本，而不是重播为
  结构化消息。重播它们会显示辅助工具调用命名
  检查站不提供的工具，并且转录本的读取方式
  提出了问题——要审查的记录，而不是要继续的对话。
- 记录失败并继续进行压缩。失去检查点会损失上下文；
  跳过它所保护的压缩将会导致运行成本。

**b。累积摘要 - 修复 §3.3.** 之前的摘要必须达到
压实机。将其作为合成消息添加到 `toSummarize` 之前，以便压缩 *N*
总结*（总结N-1 +新丢弃的消息）*而不是消息
独自一人。 `AddCompaction` 保留其替换语义，这是正确的
因为新的摘要包含了旧的摘要。

**c。用于摘要质量的实时状态锚定 — 已发货 ✅.** 当前注释
并将打开的待办事项作为相关信号传递到压缩提示中：
*这些是实时的——保留与其相关的任何细节；压缩
其他一切都集中在一行*。在此之前，`compactionSystemPrompt`给出了
模型没有任何信号表明什么仍然开放并且预算均匀地花费在
价值非常不平等的材料。

`LLMCompactor` 从已经给定的上下文中读取存储，因此
`ContextCompactor` 不必加宽。

同样在此过程中：对 `<context_compaction>` 块进行重复删除，以便 `RunLoop`
替换持久化块而不是附加第二个块（第 3.3 节）。

### 5.6 预算

每个永久插槽都有一个明确的上限。系统提示不能
修剪，因此无限制的增长比丢失一条消息更糟糕。

|插槽|绑定 |行为极限 |
|---|---|---|
|附加系统提示（第4层） | 8 KB |在解析时拒绝，并出现命名写入器的明显错误（标志、文件或 API 字段）|
| `## Invariants` | 1 KB |渲染时截断；警告一次 |
|压实总结|上下文窗口的 ~2% |下次再总结总结 |
|笔记| 15 个条目 × 200 个字符 |工具调用失败，模型必须合并 |
|都都 | 30 个条目 |已完成的条目可折叠为计数 |
|总锚固块| ~800 个代币 |按优先级下降：不变量 > 待办事项进行中 > 注释 > 待处理的待办事项 > 已完成 |

## 6. 超出范围

- **跨会话内存。** 注释是会话范围的。 `AGENTS.md` 文件是
  指令，而不是内存。共享CLI/Desktop Project身份和第一个
  跨会话内存范围是单独设计的
  [本地项目内存.md](本地项目记忆.md);全局用户和空间
  内存保留在两个记录之外。
- **自动漂移检测。** 运行时可以计算自
  正在进行的待办事项最后更改并注入更强的提醒
  阈值 — 现有 `loopGuard` 的任务级概括
  （`internal/core/agent/policy.go:36`）。故意推迟：它需要
  §5.3 中的有状态待办事项首先存在，并且应该针对
  观察到的漂移而不是猜测的阈值。 `written_iteration`字段是
  现在指定，以便在设计开始时数据可用。
- **子代理记笔记作为一项功能。**子代理运行时间短且
  他们的结果返回给父级，因此没有围绕他们设计任何内容
  做笔记。然而，隔离不是可选的：父母的商店到达
  在子代理继承的上下文上，所以 `internal/tool/subagent_runner.go`
  在子代理自己的会话中重新指向它。如果没有这个，子代理会调用
  `TodoWrite` 将覆盖委托给它的运行的任务列表。
  子代理的状态在返回时被丢弃。
- **Portal/Desktop 用于查看和编辑注释的 UI。** Trust-harness §3.6
  要求内存可检查且用户可控；这里的存储
  使这成为可能，并且表面指定了它。
- **注释的语义输入。** 除了文本加之外没有类别，没有模式
  迭代。第 4 节解释了原因。

## 7. 运行时流程

`RunLoop` 的一次迭代，其中标记的新步骤：

1. 从会话中读取 `history`。
2. 如果估计的令牌超过压缩阈值：
   - **启动 `PreCompact`，然后给 Agent 一轮以更新注释
     即将被丢弃的消息（§5.5a）；**
   - 拆分为 `toSummarize` / `toKeep`；
   - **将之前的摘要添加到 `toSummarize` (§5.5b) 之前；**
   - **将实时笔记和打开待办事项传递给压缩器（§5.5c）；**
   - 存储摘要，推进边界，射击`PostCompact`。
3. 构建系统提示：层 1–4（稳定）+层 5（摘要，**替换**
   任何持久化块而不是附加）。
4. 将 `history` 削减至剩余预算。
5. **从实时状态渲染锚定块；将其附加在 `history` 之后，如果
   非空（§5.4）。**
6. 调用模型。
7. 如果模型调用 `NoteWrite` 或 `TodoWrite`，**写入会话
   声明**并坚持；该工具结果保持正常消息并且可以自由
   稍后进行修剪，因为它不再是唯一的副本。

步骤 7 使修剪变得安全：一旦状态在消息之外有了归属
列表中，历史工具结果是多余的，删除它们就会失败
什么也没有。压实变得更便宜，同时也更安全。

## 9. 接受

- 会话第一轮中陈述的事实仍然可供模型使用
  经过三次压缩——通过笔记，而不是通过运气。
- 用户创建的角色在整个会话期间有效，并且不会被削弱
  压实。
- 从不写笔记的会话代理无需支付每回合代币费用
  对于这个功能。
- 永久槽位不会无限增长；每个都有特定的行为
  限制。
- 删除所有历史 `NoteWrite` / `TodoWrite` 工具结果
  消息列表不会丢失任何状态。
- 压缩失败保持失败开放，匹配跟踪和钩子
  约定：失败的注释检查点会在警告处记录并继续运行。

## 10. 分层

没有架构边界移动。 `internal/core/agent` 只学习笔记
通过 `NotesHistory` 接口，正如它已经了解的那样
通过`CompactionHistory`压实； `internal/core/session` 拥有数据；
`internal/tool`拥有`NoteWrite`； `internal/agentapp` 对其进行接线。里面什么都没有
`internal/core` 获得对配置、基础设施或服务包的依赖，因此
`internal/architecture` 测试不受影响。

## 11. 未决问题

- **`NoteWrite` 和 `TodoWrite` 最终合并吗？** 带有状态的注释
  字段将包含待办事项。反对：`TodoWrite` 的触发约定是
  强大且博学多才，而合并则需要付出代价。第 2 阶段完成后做出决定
  用法。
- **锚定块应该放在系统提示符尾部而不是之后
  消息？** 系统提示更简单且与提供商无关；之后
  消息更接近生成点并且应该更好地粘附。这个
  设计选择消息后；如果坚持证明无法区分，
  将其移至系统提示符中可消除第 5.4 节中的运输警告。
- **第 4 层是否应该能够抑制继承层？** 它是累加性的，因此
  在 Go 存储库中运行的 `law-consultant` 提示符也会收到
  工作区的 `AGENTS.md` 贡献规则。通常是无害的，因为后来
  图层的重量更大，但“给我一个干净的角色”是一个合理的要求。一个
  frontmatter `inherit: false` 将覆盖它。推迟是因为权利
  在看到实际用法之前，默认值是不可知的。
- **在持久化之前应该对注释进行编辑吗？** 它们是模型创作的并且
  登陆会话文件，持久运行跟踪已将其视为
  需要编辑。可能是的，重用跟踪编辑器 - 期间确认
  阶段2.
