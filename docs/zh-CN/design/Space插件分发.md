## 1. 决策

Space 可以为其后台运行激活已发布的插件版本。激活记录精确指定插件、版本和
摘要；Worker 验证后，将完全一致的内容物化到该次运行专属的
`BUILDMAX_HOME`。运行启动时绝不解析“最新版本”。

激活规则按内容能做什么划分，而不是按作者身份划分：

- **指令内容**——技能和子 Agent——只需由 Space 管理员激活。它们可能
  引发工具调用，但每次工具调用仍会经过工具权限、钩子门控和沙箱。
- **可执行内容**——钩子和 MCP 服务器——还要求系统管理员将该版本标记为
  可用于无人值守运行。它们会在运营方拥有的基础设施上启动进程、建立连接，
  只有运营方能跨 Space 衡量这种风险。

激活是 Space 对“哪些插件可以使用”的决定。当前由 Agent 定义选择实际使用项；
第 16 节增加未来的 Task 级环境，它可以在不修改 Agent 或 Space 的情况下，
从已获准的目录中再选择插件。一次运行只加载为其记录的不可变环境；插件不会
仅因被 Space 激活就自动进入运行。参见第 5.3 节和第 16 节。

并非每个 Space 都愿意逐项维护插件列表。Space 可选择两种模式：**策展模式**
由管理员逐个激活插件；**开放模式**允许 Agent 引用整个目录，并在首次引用时
自动创建激活记录。开放模式是默认值。两种模式都会生成相同的固定记录，区别
只是谁填写列表，而不是是否存在列表。参见第 4.1 节。

密钥传递有意不纳入本设计。激活记录只说明某个发布会读取哪些环境变量；
实际提供这些变量需要独立记录和独立的信任边界。

## 2. 已经跨越此边界的内容

问题比看起来更窄，因为空间内容已经达到Worker。

空间将空间的持续 `home` 转载到运行目录中，而 `WriteRunAgentsMd` 则将家庭的 `AGENTS.md` 转载到工作空间中.空间可以在每一个下发的背景运行前置任意的指示，没有激活，没有审查，没有记录在文件本身之外。 `internal/agentapp/taskrun`

空间的文件落地在`<run>/home`，而工作空间子则从`<run>/.buildmax/hooks.yaml`读取，因此一个空间的家不能为今天的运行贡献一个子，尽管它可以为提示贡献.到达一个Worker的指示不是新的.到达一个执行内容是。

因此，这个设计的边界不是"空间内容到达一个Worker".它是**执行的空间内容到达一个Worker**.一个技能是代理可以读的散文；一个`command`是运行程序的程序，无论代理是否读任何东西.要求比产品已经要求的技能更多的仪式是不一致的，这就是为什么§1分开在它做。 `AGENTS.md`

另外两个事实联系着这项工作：

- Worker的`BUILDMAX_HOME`每次运行都创建得新鲜
它们的插件目录是空的，没有插件 `RuntimeTaskRunGlobalDir`
现在，市场没有接触Worker。
- 级别1的对话建立自己的工具登记库，并拨打`agent.RunLoop`
直接而不是组装`agentapp`，所以它们也不加载插件。
增加插件到第1级是一个独立的决定，

## 3. 为什么激活属于 Space 决策

部署的目录说明了现有内容.它不能说明一个空间的背景运行应该有什么，因为发布插件的人和运行任务的人不是同一个人，并没有共同的目的。

激活也是回答"为什么这次运行具有这种能力"的记录，一旦发布给所有人，再没有什么能回答。 Worker运行是未经监督的：没有人批准工具调用，没有人注意到。 取代这种存在的是一个早些时候，由一个名人做出的决定，一个踪迹记录。

空间是正确的所有者，因为Space已经是Portal资源的所有权和授权边界，

对于一个不想做这个决定的插件，一个空间仍然会做出这样的决定：它选择了开放模式，一次，并且这个选择本身是记录的和归因的。

## 4. 激活记录

每个空间和插件的一个行：

| 领域 | 意思 |
|---|---|
| 空间 | 空间的背景运行得到它 |
| 插件 | 产品目录身份 |
| 版本，消化 | 确切的释放，固定 |
| 启用 | 激活或悬挂，不损失 |
| 产地 | 一个管理员激活了它或`automatic` (§4.1) `curated` |
| 通过，通过 | 谁决定，什么时候 |
| 更新_by，更新_at | 谁最后移动了子 |

是点.市场设计的第10条禁止在运行开始时解决"最新"问题，而是使这一点成为真实的而不是有望的：五分钟前发布的发布不能改变已经下发的运行即将完成的内容。 转向更新的发布是一个具有自身的审计活动的空间行动，由一个观察新发布能力报告的人来执行。

拉开的释放保持固定，继续工作。 延克从默认选择中删除一个释放；它不会进入空间的激活，因为这样做会改变空间的运行行为，没有人决定.它所做的就是界面：激活读取是被绑定到被撤回的释放，原因，所以空间可以故意移动。

存档插件的行为同样，没有删除。

### 4.1 关闭和开放的Spaces

编辑一个列表是工作，一个不会做的空间不应该被迫选择做错误或没有插件。

| | 管理 | 开放 |
|---|---|---|
| 代理人可以说什么 | 空间激活了什么 | 整个目录 |
| 谁会产生激活 | 一个管理员，故意 | 系统，当一个代理首先命名插件时 |
| 在 | 管理员选择的版本 | 现在的最新资格，没有被释 |
| `activated_by` | 这位管理员 | 谁拯救了代理修改，它命名 |
| 运营商的资格 (§5.1) | 强制执行 | 强制，不变 |
| 笔，消化，审计事件，跟踪 | 同样 | 同样 |

开放是默认的，因为跨空间的关键是资格，而不是保养， 任何需要保养的部署都能说出，

**开放模式是自动激活，而不是无激活.** 列在代理命名插件时创建，而不是运行开始时，因此通过分辨率 (§7) 总是有一个固定的行来解决.因此空间的列表存在于两个模式中：在策划模式中它是门户，在开放模式中它是账本.从开放到策划后的空间转换不需要重建。

**自动脚不自动移动.**一旦创建，它就会像一个被策划的脚一样：一个新版本没有改变任何东西，直到一个人移动脚.这是不是一个可以以后优化的监督。 "脚只会移动当有人移动它"是不变的 §4 依赖于，原因 §7 停止担心时间；使其依赖于空间设置将在这个记录中的每个论点下设置"除非空间是开放的"例外.开放模式购买的是没有人不得不 *创建*脚；保持它为所有人而言是相同的故意行为， §10 让它成为可见的，而不是空间必须去寻找东西。

**权威不变.** 指定插件在代理中已经需要`ActionManageAgents`，这是同一的所有者或管理员权威 §5提供激活.开放模式删除步骤，不是许可：没有人可以激活插件之前可以激活它。

## 5. 谁可以激活什么

| 内容 | 管理局 |
|---|---|
| 技能，副职员 | Space所有者或管理者 |
| 服务器:Hooks,MCP | 系统管理员的无监督使用可签证的发行版， **和** Space |

Space 拥有者或管理者与 相应标识符 和 `ActionManageWorkflows` 匹配。 在 `internal/server/access` 中，管理共享自动化资产已经是该权威，并且激活是该决定的形式.设置空间的策展模式 (§4.1) 是同样的权威，在开放模式中，自动激活是由已经要求的编辑代理引起的。 `ActionManageAgents`

### 5.1 无监督的资格

资格是**发布**的属性，而不是空间，管理员将其设置在他们已经控制的发布上。 这是一个标志而不是每个空间的批准队列，它将决定放在知识的位置：运营商可以考虑如何启动该过程，其基础设施成本；空间管理员通常不能。

关键模式不达到这个旗.一个开放模式空间可能会命名任何插件在目录中；它可能不命名一个贡献或MCP服务器，没有管理员标记了符合条件，自动激活拒绝这样的发布，就像一个关键激活一样.开放模式放松了空间的自己的保洁，从来没有运营商的门。

现在，三个界面有这种形状：Worker，打印模式和Portal对话.命名界面将使第一个出现的第四个错误的旗。

标记一个发布符合条件意味着管理员读取其功能报告，它启动的可执行文件，它访问的主机，它记录的事件，并接受它们运行，没有人会被要求.这是关于该发布的声明，所以不会转移到下一个版本：一个新发布开始不符合条件，这使得阅读不成为正式性。

### 5.2 资格不符合的条件

它不允许.一个技能，一个子器件和一个MCP服务器的工具作为要求的东西达到模型：工具权限，门关闭和敏感路径检查适用于它们，就像它们适用于空间的配置一样，它们都不扩大了运行可能做的事情。

子命令是例外，这就是为什么有资格.它运行无论代理要求什么，还是不，它本身都不受工具权限.它仍然不能扩大代理的权限.子可能会阻止工具调用，并且没有办法批准一个，但它确实运行了代码，运行的权限.这是一个管理员在5.1节中接受的，第9节说什么是什么，什么是什么不绑定它。

### 5.3 颗粒度:Space激活,Agent 选择

由于"后台运行范围"的插件已经退休，这提出了质疑本记录最初假设的细分性。 ** 决定：两个级别。 * * 空间的激活说明了其后台运行 * 可能* 使用； 代理定义说明了运行 * 运行 * 运行 * 运行.单独的任何级别都不对。 空间范围的列表给每个代理一个特权级别。 只有代理的列表没有任何地方检查操作员资格，没有空间级别的答案"我们的后台运行可能使用什么" (§13)。

| 内容 | 子代理 Space | 子代理 Agent |
|---|---|---|
| 技能，副职员 | 允许列表和 | 只有当代理人给它命名时才加载 |
| 服务器:Hooks,MCP | 允许列表，点和操作员的资格 | 只有当代理人给它命名时才加载 |

**没有什么被遗传.** 此记录的早期草案使得无效内容继承 一个代理命名没有插件得到了每个技能和子件其空间已经激活了 在论点上，一个不需要的技能只花费代币，而一个不需要的火在每个工具调用.不对称被拒绝.一个代理是一个运行行为被声明的地方，一个功能因为别人编辑了一个空间设置而到达的没有被声明任何一个代理读者可以看到的地方.廉价不是看不见的。

参16中采用Task的扩展补充并未逆转这一规则.它们是在插件环境修订中记录的明确，审计的Agent行动，而不是继承的Space激活列表。

两件事都发生了，

**激活是纯粹的允许的.**激活一个释放不会改变现有代理的行为；它改变一个代理可能会编辑给名称.这使激活是一个安全的行动，没有爆炸半径警告，它让问题"为什么这次运行有X"的答案由代理单独。

**没有代理的运行没有插件。 ** `Task.AgentID`是`*string`，所以这是一个现实状态而不是假设，并且根据名字或输失的规则，它只有一个一致的答案：没有什么声明了需要.一个针对代理的工作流动步骤使用该代理的选择；一个针对没有代理的步骤是无代理的案例。

**一个代理命名插件，而不是发布.**版本和消化来自空间的激活；一个代理的选择是目录身份的集合.这就是阻止第二层重新创建不合格的插件单列的缺陷的原因：将插件移动到新版本留在一个地方，因此阅读新功能报告是一个真正的步骤，而不是人们点击对话.这也是为什么在N代理中命名插件是一个可接受的成本，而在N代理中将版本粘贴并非。

**空间的天花板是代理可能命名的.** 在策划模式中，这是空间的激活列表；在开放模式中，它是目录，并命名创造了激活 (§4.1).无论如何，代理都会命名插件其空间的记录，然后是针，运营商的资格 (§5.1) 与该记录进行检查。

**激活集是运行空间，而不是代理的.** Worker已经拒绝了一个没有任务空间的代理 `a.SpaceID == task.SpaceID`在Worker运行路线中，该路线中解决了代理的指示.插件选择遵循该规则而不是发明第二个规则：针头解决了`Task.SpaceID`，一个失败的代理在空间检查上面采取无代理的路径。

**一个名为插件的插件，但其空间尚未激活，失败运行。 * * 不加载警告，也不跳过： §7 已经拒绝启动一个运行，其固定包未能验证，因为一个背景运行的输出是由没有观看的某个人操作的.一个名为插件的代理宣布它需要一个，而一个安静地做不到其定义所说的运行是相同的错误失败。 检查运行在三个点都是因为一个原因。 选手提供空间模式允许的东西，写字或拒绝一个未被激活的名称或激活它 (§4.1)，并且再次拒绝，因为一个代理是仅添加，所以一个空间暂停漂移，或运行到关闭，经过该代理被关闭，不能被删除。 选择的名称是为了保持一个操作模式，而不是在修改，他们会静默地停止修改，因此在修改文中，他们会停止修改，而不是在修改文模式中进行修改。

两个级别的成本是，激活插件，直到代理命名它，它不会被使用.这就是上述段落的价格， § 10 支付其另一半的两个地方，当插件不在一个预期的地方时，通过显示一个空间的激活集和哪些代理在一个地方命名每个条目。

** 细分性在这里停止.** 插件是两个级别的单元：既不是激活，也不是代理选择的名称的一部分发布.第三个，内发布级别必须由购买第二个测试支付，没有为此做出任何案例 (§15)。

## 6. 密钥不在本设计范围内

现在，一个Worker环境是部署自己的，加上`BUILDMAX_HOME`和运行代币，产品中没有任何一个空间秘密。 MCP

系统的设计没有添加一个.它添加的是诚实的失败：一个激活记录了环境变量名称，发布读取，从检查中取出了已经存储的目录，并运行报告了其中哪些已经被卸载.一个服务器需要代币的插件将启动，无法验证，并说它在本地的方式。

传递秘密意味着决定一个Worker能命名一个值，它将存储在哪里，它如何旋转，以及一个审计轨迹对一个值没有人应该读到什么.这是一个自己的记录，并且在这个里面建立它将使这两者都更糟.直到它存在，这个设计的有用的一半是技能，副用品，以及MCP服务器，这些服务器不需要凭证。

## 7. 物化一次运行

```text
server                                        worker
  │                                             │
  │                    claims the run ◄─────────┤  GET /worker/task-runs/{id}
  ├─ read the run's space's activations          │
  ├─ intersect with the agent's named set (§5.3)│
  ├─ resolve each to (name, version, digest)    │
  ├─ record the pins on the run ────────────────►
  │                                             ├─ for each pin:
  │                                             │    GET the package with the run token
  │                                             │    verify the digest before extraction
  │                                             │    extract with the hardened reader
  │                                             │    inspect; refuse what would not load
  │                                             └─ place under <global>/plugins/<name>/
```

每个解决这个问题的都已经存在，在两个策略模式中：当一个代理命名插件时，创建一个开放模式的激活，而不是当运行开始时 (§4.1)，因此，解析从来不需要发明一个。

## 10. 产品界面

由于Portal是空间共享自动化管理和审计轨迹阅读的位置，因此Portal拥有激活。

空间的插件部分列出了目录，标记了该空间激活了什么版本，并为每个版本显示了它所贡献的内容：相同的清洁报告显示了安装本地.一个不符合未监督使用的版本表示如此，并表示管理员决定，而不是提供一个失败的按。

部分还包含空间的策划模式 (§4.1) 并明确表示每个值的含义：在策划模式下，管理员在代理人命名之前激活；在开放模式下，命名激活.一个自动激活的入口被标记为这样，该代理人和其编辑导致的人，因此开放模式空间的列表会被读作历史，而不是被某人策划的列表。

由于一个子在任何模式中都不会自动移动，因此在此部分中，延迟也必须可见：一个具有更新的版本的激活表示如此，随着该版本的变化，更新作为一个故意的行动.一个选择不编辑的空间选择不永远运行上季度的插件。

由于选择是基于代理 (§5.3)，该部分还回答了两个层次的问题：每次激活的释放时，它会说空间中的哪个代理命名它，并且由于没有遗传的任何活动，没有代理名称被显示为激活和未使用而不是默默使用.一个代理的页面列出了它命名什么，其空间激活了什么，而不是它.两个层次是可负担的，当两个都能从一个地方看到；它们不是发现意味着阅读每个代理定义时。

代理的插件场提供了其空间模式允许的内容。 在策划时，激活列表，在打开时，目录表示它显示哪个，因为"这个名称将激活整个空间的插件"并不是什么可以学习的。 它在任何模式中都没有版本：版本是空间的 (§5.3)，并且一个暗示的选择器将把相同的针放在尽可能多的地方，如有代理。

随着Portal的推广，它仍然没有任何地方机器的权利。 空间激活是关于该空间的背景运行；有人在笔记本电脑上安装的东西仍然是`buildmax plugin list`。

CLI得到了读取路径 该空间激活了什么，在哪个版本 ，这样一个调试运行的人可以在没有浏览器的情况下看到它.改变激活的路径仍然存在于 Portal，在那里审计路径和空间的其他共享自动化已经存在。

## 13. 被否决的方案

### Space 安装在共享目录中

给每个空间一个持久的插件目录，它管理，像它的家一样，不需要激活模型.它还删除了：运行开始时，任何在目录中的东西都是运行得到的，这就是可变的源 §10 拒绝的。

### 定义Agent 定义而不是Space列表

让一个代理定义命名自己的版本，没有空间级别列表，将功能放在行为已经存在的地方，并且`AgentRevision`仅是附加，因此修改中的针对一个代理在任何时候的内容进行了准确的回答。 `ActionManageAgents`

由于它被两个基层反对意见拒绝。 脚将存在N个位置，因此将一个版本转移到一个新版本意味着编辑每个命名的代理，每个代理被认为是阅读新的能力报告之前。 摩擦破坏了它存在的审查。

根据第5.3条，它有一个，它没有任何负载。 这种答案也可用于只使用代理的模型，因此它不是空间水平的论点。

拒绝的是一个代理定义，而不是一个空间列表.在代理定义中的空间列表中选择是决定的另一半，并被通过；见5.3节。

### 没有操作员参与的激活

让空间管理员激活任何发表的内容是更简单的，并且可以辩护的，如果空间是一个公司的部门.如果部署的空间是单独的客户，则不能辩护，因为空间管理员会导致任意的程序在共享基础设施上运行.使资格成为一个发布的属性而不是一个每空间批准，使运营商的决定足够便宜，这不是一个有意义的速度损失。

### 后代版本继承了资格

运行旗从一个版本到另一个版本将使激活感觉不像文件工作。 它也将使管理员的阅读成为正式性：他们接受的报告描述了不再存在的字节.一个新的版本开始不合格是保持旗意味着什么。

### 关闭一个Space的或档案

关闭一个开关，将每个激活关闭到该版本，是诱人的.它改变了一个空间的运行做什么没有任何人在该空间决定，它使开关一个更重的行动比"从默认选择中删除"，这就是那么将阻止管理员使用它.存在的杀开关是部署的：标记释放不合格，这立即停止执行的半个。

### 开放模式解决每Run的最新版本

让一个开放模式空间完全跳过 每次运行开始时解决最新的资格释放 是"我们不想维护这个"听起来像它要求的，

根据第4条的保证，在五分钟前发布的发布不能改变运行即将完成的内容，这将适用于策划空间而不是开放空间，并且每个论点都基于此进行重新阅读.第5.1条的重新阅读，第7条的自由迟到解决，第13条的拒绝共享目录需要"除非空间开放"条款.两个空间将得到不同的答案"，为什么这次运行与上一次运行行为不同"，这是整个记录存在的答案.货币值得购买的可见 (§10)，而不是随着变化。

### 让每个Space的保养是必不可少的

要求在任何地方进行调节是安全听起来的默认，并被拒绝为默认而不是作为功能.大多数空间的插件使用是技能和子件，这在2节中显示，空间已经可以通过`AGENTS.md`在Worker的面前置于任何仪式.要求他们进行激活步骤而不是`AGENTS.md`将是产品已经没有产品的决定，预测结果是使用不使用插件而不是调节的空间的空间.不必须选的是操作员资格，这是一种独立的控制，开放模式不会触摸 (§5.1)。

### 解决Worker上的激活

让一个Worker在开始时读取其空间的激活，将从发射中删除一个字段.它还通过后门重新引入"最晚开始"，这意味着运行令牌可以读取空间状态.这两件事都是设计已经决定的原因，但没有改变。

## 16. Task 级自主获取

采用Agent，可能会发现其记录的选择缺乏目前Task所需的功能.BuildMax将支持打字搜索，检查和安装，而不会使`BUILDMAX_HOME/plugins/`变成耐用状态。

Space激活仍然是上限，而一个独立的 Space 政策决定运行 Agent是否可以要求自主收购；普通 Task执行权限并不意味着插件管理权限.在策划模式下，允许的请求只可以选择激活的版本.在开放模式下，它可能导致相同的固定自动激活，今天授权的 Agent编辑导致，归因于相应标识符和启动分辨率主.运营商授予资格，可执行内容门，许可，和秘密补贴；仍然没有任何秘密安装包。 TaskRun

长期的结果是不可变的**插件环境修订**.它记录了Agent修订的基线选择以及Task-扩展的补充，作为精确的包参考，版本，消化，安装器来源，和解决许可修订.运行的`buildmax-home/plugins/`下扩展目录是该记录的一次性投影：

```text
Space activation ceiling + Agent revision + Task additions
                             |
                             v
              immutable Plugin environment revision
                             |
                             | verify and materialize
                             v
          <task-run>/buildmax-home/plugins/<name>/
```

已在目录中引用的包裹，不会再上传.一个私人或Agent生产的包裹在环境可以引用之前，在插件包店中进行正常化，检查，消化验并存储一次.下载，提取碎片，缓存，凭证和未宣布的可变的插件状态从未通过扩展目录进行捕获.真正需要持久可变状态的插件必须声明一个独立管理的运行,Task,相应标识符，或Space状态范围；这种状态不是包装。

一个TaskRun 永远不会改变其载的插件组.工具方案，提示层,MCP服务器，子，沙箱规则和秘密要求在运行时间组装时固定.成功的安装只能影响后来的TaskRun.继续使用Task的插件环境头；重复试验重建重复运行的基础环境.即时能力转移可能会在会议和工作空间后创建继任者TaskRun，但它可能不会热载当前的过程.在船只进行转移之前，必须设计出准确的转变。

自主收购未达到Task范围，以便一个目标可以提高其能力，而不默默地改变Agent的未来使用。 晋升到Agent定义或Space激活是单独的授权和审计行动。

本节不仅延伸到描述出货D1路径，其工作空间，会议和物化界限在[任务-工作空间-检查点.md](./Task工作区检查点.md)中指定。
