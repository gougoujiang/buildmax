## 问题

BuildMax 可以执行耗时较长的本地工作,但它无法把这项工作放到一边、同时
保持对话本身仍然可以响应:

- `Bash.Execute` 会阻塞在 `cmd.Run` 上,默认超时为 120 秒,最长超时为
  10 分钟。
- `Task.Execute` 会阻塞,直到子 Agent 给出最终回复为止。
- 并行的工具执行只会让相邻的只读调用重叠;`Bash` 和 `Task` 都是写入
  屏障。
- TUI 和 Desktop 都只允许每个会话或每个项目同时存在一个顶层运行。其他
  消息会在它后面排队(参见[queued messages](排队消息.md)),而不会创建
  独立的工作。

这里缺失的能力,远远不止一个 `run_in_background` 布尔值那么简单。一旦
发起调用的那次工具调用返回,进程里就没有任何东西真正拥有这项操作了:
没有身份、没有状态、没有有界的输出、没有取消机制、没有完成时的投递
方式,也没有轨迹关联。Monitor 又带来了额外一项要求——它需要在存活期间
持续发出事件,并让 Agent 能够对这些事件作出反应。

## 范围

本设计只覆盖**本地界面**:CLI/TUI 和 Desktop。Portal 的 Tier 1 对话
编排器和 Tier 2 的 `Task`/`TaskRun` 执行不在本文范围内,也不受影响。
一个本地 job 是一个与进程生命周期绑定的对象;`TaskRun` 仍然是那个
持久化的 Space 执行对象。二者未来或许会共享一些状态命名和
`@buildmax/gui` 的呈现方式,但永远不会共享存储或服务层面的归属。

第一版明确不涉及的范围:

- 要求必须有一个 BuildMax Server 才能进行本地后台工作。
- 能够在 BuildMax 进程退出后继续存活的 job。
  [持久化不在计划之内](#持久化不在计划之内)说明了做到这一点需要什么,
  以及为什么把它排除在外。
- 从 `buildmax -p`、评测,或 Worker 执行中发起后台任务。打印模式没有
  一个宿主进程可以拥有一个 job;评测和 Worker 只有在具备明确的无人
  值守生命周期和策略时,才会获得后台工具。
- 定时任务、循环提示、Agent 之间的空间、点对点消息,或嵌套委派。
- 对同一工作区的并发编辑进行自动合并。
- 把 Monitor 当作一种安全边界;它能观察到的,只是它的命令在正常工具
  和沙箱策略之下所能触及的东西。

## 决策

TUI 和 Desktop 共享**一个由 `AgentApp` 拥有的本地 job 管理器**。被否决
的替代方案:

| 方案 | 为什么不采用 |
|---|---|
| Shell 的 `&` / `nohup` | 没有身份、输出捕获、进程树停止、轨迹、归属或清理机制 |
| TUI 和 Desktop 各自独立实现 | 违反共享运行时规则,重复实现进程和安全语义 |
| 在本地复用 Portal 的 `TaskRun` | 把服务器和数据库层面的概念拉进直接本地模式;而且仍然没有按行驱动的 Monitor 事件 |

### 按维度划分的替代方案

在产品层面的这个选择之下,实现方案的空间可以分解成四个相互独立的维度。
本设计在每个维度上都选定了一个点;以下是认真考虑过的替代方案及其结论:

| 维度 | 选定方案 | 最有力的替代方案 | 结论 |
|---|---|---|---|
| 管理器拓扑 | 由 `AgentApp` 拥有的进程内管理器 | 位于 Unix socket 之后的本地守护进程(docker / tmux-server 那种形态),可以免费获得跨界面的 job 存活能力 | 推迟,而非否决——它正是一个能跨进程存活的 job 所需要的 supervisor,而这[不在计划之内](#持久化不在计划之内)。管理器的契约本来就与具体传输方式无关,所以即便将来真的需要迁移,也不需要重写它之上的任何东西 |
| 事件投递 | 带串行化唤醒机制的会话收件箱,叠加在可查询的 job 工具之上 | 一个永不退出、阻塞在事件通道上的运行循环(actor 模型) | 否决:这会重写 `RunLoop` 契约、按运行作用域的轨迹,以及压缩时机,而这些付出换来的优雅,收件箱方案早已具备。基于 Hook 的投递只是一个观测点,永远不是主通道 |
| 进程适配器 | 带进程组/Job Object 的 `exec` | 基于 PTY 的宿主方式(Windows 上是 ConPTY),这样按行缓冲的程序能够实时发出输出 | 作为第一版明确写出的一项限制推迟;等到真实场景倒逼时再增加 PTY 适配器 |
| Monitor 的形态 | 一个通用命令,其 stdout 的每一行就是一个事件 | 带类型的原生监视器(文件监视、HTTP 轮询),从设计上就是有界的 | 属于以后可以加的锦上添花之物,而不是竞争方案:如果大多数 Monitor 都是在盯着一个文件,可以在同一套 job 与事件管线上加一种带类型的种类。"快照加对比"式的采样,可以作为其中一种合并策略保留下来 |

在拓扑这个维度上,还考虑过并否决了以下方案:使用 PID 文件的孤儿进程
(存在 PID 复用问题,也没有实时事件流——尽管它的磁盘格式恰好正是一个
输出 spool 所需要的),以及委托给 tmux 或操作系统自带的服务管理器
(这违反了单一二进制文件的原则,而且三个平台各有三套不同的语义)。

术语说明:本设计用 **job** 来称呼这个本地运行时对象,这样就不会与
Portal 的 `Task` 实体或 `Task` 这个子 Agent 工具发生名称冲突。

| 术语 | 含义 |
|---|---|
| Background job(后台 job) | 一个由某个 `AgentApp`、工作区和本地会话所拥有的、作用域限定在进程内的单元 |
| Command job(命令 job) | 运行一条 shell 命令,并发布一个终态结果 |
| Subagent job(子 Agent job) | 运行一个隔离的子 Agent 上下文,并发布它的最终回复 |
| Monitor job | 运行一条命令,它的 stdout 每一行都会成为一个事件,直到退出、超时、停止,或关闭为止 |
| Job event(job 事件) | 一条有界的、带明确来源信息的生命周期、输出、完成或监控记录 |
| Agent 唤醒 | 由排队的 job 事件所引发的一次新的、串行化的顶层轮次,绝不会是对会话历史的一次并发写入 |

Job 是**作用域限定在进程内、但归属于某个会话的**:当用户在同一个进程内
切换会话时,一个 job 可以继续运行,但它产生的事件和结果属于最初启动它
的那个会话。关闭拥有它的那个 `AgentApp`,或者关闭整个应用程序,都会
停止它。

## 运行时模型

### 管理器与归属

`AgentApp` 为它的工作区拥有一个 job 管理器——Desktop 本来就已经为每个
项目缓存一个 `AgentApp`,TUI 则为每个进程拥有一个——这让这个管理器
拥有一个比任何一次工具调用都更长的生命周期,而不需要引入一个新的全局
进程。这个管理器的操作包括:启动、列出、获取、基于游标的输出读取、
停止、按会话订阅,以及关闭。

这份契约刻意与具体传输方式无关:没有请求上下文、共享对象或回调闭包
会跨越它,订阅本身就是流。这个约束现在不需要付出任何代价,却保留了
将来把这个管理器搬到一个本地 socket 背后、而不需要重写 `internal/tool`
或任意一个界面的可能性。

包的归属遵循现有的边界划分:`internal/agentapp` 负责协调 job 和会话;
进程创建与进程树终止是 `internal/infra` 中的平台相关代码;面向 LLM 的
参数校验和工具输出留在 `internal/tool` 中;`internal/core/agent` 不
导入上述任何一个包。

每个 job 在启动时都会捕获一份不可变的来源信息:job ID 和种类;工作区
和会话 ID;当由某个工具发起时的父轨迹 ID 和父工具调用 ID;子 Agent
job 的模型和子 Agent 类型;已解析出的沙箱和权限事实;各个时间戳;
终态状态,以及一份有界的错误摘要。沙箱边界是在启动时捕获下来的,这样
一次设置重新加载就不会悄悄改变一个正在运行的 job 的边界。

### 状态机

```text
starting → running → succeeded
                   → failed
                   → canceled
```

`canceled` 表示 BuildMax 接受了一次停止请求、且这次操作已经结束,并且
携带一个 `stop_reason`(`user_stop`、`shutdown`,或 `timeout`)。一个
被停止的 persistent(持久)Monitor 状态是带着相应原因的 `canceled`,
而不是第四种终态:状态机保持最小化,动机则放在一个字段里表达。从发起
调用的那次工具调用中返回,是成功的分离(detachment),而不是取消。

## Command Job

面向 LLM 的形态,是在现有 `Bash` 工具上新增一个可选的
`run_in_background` 字段。`Bash` 仍然是参数校验、风险分类、权限、
沙箱包装和环境清理方面唯一的权威;转入后台绝不能构造出第二条更弱的
shell 路径。权限关卡会在分离之前同步执行完毕;一旦获得许可,这个工具
返回的是 job 身份和初始状态,而不是命令的输出内容。

这个进程适配器必须在不阻塞子进程的前提下捕获 stdout 和 stderr,在一个
游标背后保留有界的近期输出,能够区分退出码、超时、停止请求和启动失败
这几种情况,能够终止**整棵进程树**,在为该次已批准调用解析出来的沙箱
与已清理环境下运行,并且在管理器关闭时停止自己拥有的每一个子进程。

进程树终止是全新的工作,不是复用已有能力:今天的 `exec.CommandContext`
只会向直接子进程发信号,所以杀掉 `bash` 本身、而它派生出的服务器进程
却继续存活,正是当前的实际行为。Unix 的进程组和 Windows 上的等价机制
都需要专门的测试;一次让孙进程继续运行的"停止",即便注册表里记的是
`canceled`,也应当算作一次失败的停止。

第一版让子进程运行在管道之上,而不是 PTY 之上。许多开发服务器一旦发现
输出对象不是 TTY,就会切换成块缓冲,导致输出延迟出现、甚至只在进程
退出时才一次性出现;Monitor 示例中使用 `--line-buffered` 也是出于同样
的原因。这是一项被明确写出的限制,而当真实场景倒逼需要解决它时,已知
的修复方案是增加一个 PTY 适配器(Windows 上是 ConPTY)。

## Subagent Job

在现有的 `Task` 工具上加入同样的可选字段。一个后台子 Agent 会获得一个
全新的上下文,并立即返回一个 job 身份。现有的递归限制(子 Agent 内部
不能再使用 `Task`)予以保留。

审批环节不需要任何新机制:子 Agent 本来就在没有审批处理器的情况下
运行,而循环在处理器为 nil 时,会把一次 `Ask` 解析为拒绝。一个后台子
Agent 继承的正是这套行为——一个本应发起询问的操作会被拒绝,同时附带
一个有用的 job 结果,供用户在前台重试之前查看。真正新增的只是呈现
方式:这次拒绝会以一个 job 结果的形式送达用户,而不是作为一次前台
工具调用的结果。

一个后台子 Agent 会共享工作区,就像现在的前台子 Agent 一样。这是一项
正确性方面的风险,而不只是一个细节:两个写入方可能发生竞争,父级看到
的视图也可能因此变得陈旧。第一版**在工具输出和界面中明确声明这个共享
工作区的边界,建议而非强制要求隔离**;如果强制要求工作树隔离,就等于
把这项能力的使用门槛,建立在它本不需要的基础设施之上——毕竟这里主要
是以读取为主的委派场景。基于工作树隔离的写入方本可以把这一点变成一项
保证;但它们[不在计划之内](#持久化不在计划之内)。

## Monitor Job

一个 Monitor 是一种专门化的 command job,而不是第二个调度器。它的命令
预期会一直保持安静,直到发生了值得投递出去的事情;它 stdout 的每一行
都会变成一个有界的 `monitor_event`,进程退出会变成一个普通的生命周期
事件,而 stderr 是不会唤醒 Agent 的诊断性 job 输出。Monitor 要经过与
`Bash` 相同的风险检查、权限策略、沙箱和环境规则。一个 `persistent`
Monitor 指的是"存活时长与应用会话相当",而不是"能在进程退出之后继续
存活"。

背压机制会在任何内容到达模型之前就生效:逐行的字节上限(采用
UTF-8 安全的截断方式)、有界的逐 job 队列、事件速率限制、当消费方
跟不上时进行合并并附带一份被丢弃事件的摘要,以及在写入持久化轨迹字节
之前先做脱敏处理。如果没有这些机制,对着一个繁忙的日志跑 `tail -F`,
就会变成一个消耗上下文的工具。

**反应策略是在每个 Monitor 启动时单独决定的。** 默认值是 `notify`:
事件会到达界面和会话收件箱,但不会调用模型。发起该 Monitor 的 Agent
可以声明 `react`,这种情况下,排队的事件会按照下文的串行化规则唤醒
所属会话。一次隐藏的自动模型调用既有成本又有副作用,所以它绝不会是
静默的默认行为;一个从不引发推理的 Monitor,作为一种纯粹的观察手段
仍然是有用的。

## 事件投递与唤醒

投递方式是分层的,首先是拉取模式。job 的 list/get/output 这几个工具,
构成了阶段 1 全部的投递方式——模型在关心结果的时候自己去读——它们会
永久保留下来,作为兜底和调试通道。下面描述的收件箱唤醒机制,是叠加在
它们之上的阶段 3 增量能力,而绝不是对它们的替代。

### 带类型的来源信息,而不是排队的用户输入

`RunLoopOpts.PendingInput` 专门用于用户亲自输入的内容:它会运行
`UserPromptSubmit` 这个 Hook、追加一条用户消息,并发出
`EventUserInput` 事件。job 事件绝不能借道于此——否则轨迹记录就会显示
用户说了他们其实没说过的话,而且套用的 Hook 契约也会是错误的。投递
机制使用一种带类型的来源标识,至少要区分以下几种:

```text
user_prompt | command_result | subagent_result | monitor_event
```

各个模型供应商之间没有一种通用的、可移植的"历史中段事件"角色,所以
一个事件在传输层面上可能仍然要以 user 角色消息的形式表示——但持久化
的消息记录和轨迹记录都携带着这份带类型的、非用户的来源信息,信封会把
这份载荷框定为一份不受信任的观察结果,而不是一条指令,而且**压缩过程
必须保留这份来源信息**,否则一次压缩就会把一行 Monitor 输出重新变成
用户曾经说过的话。

### 强制执行"单一会话写入方"

一个 job 事件绝不能与同一个会话上的一次轮次并发执行。今天,这项保证
只是一种表面上的约定:`Session.Append` 和会话管理器本身没有加锁,而
"串行化"之所以成立,只是因为每个界面本来就只允许一次运行。而 job
管理器让生产者的数量变多了,所以第一版加入了一个**会话轮次协调器**,
让"单一写入方"这条规则变成一次被拒绝或排队的调用,而不是一次数据
竞争。投递的具体顺序是:

1. 记录这个事件,并立即通知界面。
2. 如果当前有一个顶层运行处于活跃状态,就把这个事件排队或与其他事件
   合并。
3. 在支持的情况下,于一个合法的迭代边界处投递排队的事件;否则就在
   当前活跃的运行结束之后,开启一次新的内部轮次。
4. 如果该会话处于空闲状态,可以选择立即开启一次内部轮次。
5. 通过现有的会话管理器路径,把最终结果持久化进历史记录。

### 什么情况下"完成"会唤醒模型

每一个生命周期事件都会到达界面;但并不是每一个事件都会唤醒模型。
**只有当发起调用时明确要求投递结果时,"完成"才会唤醒所属的会话。**
一个 Monitor 会按照它自己声明的模式来决定是否唤醒。进度类的输出只会
更新活动界面。在关闭过程中被停止的一个 job,会被记录下来,并在下一次
进程内查看时展示出来,而不会唤醒任何东西。

## 权限、信任与安全

转入后台改变的是一次调用什么时候算结束,而不是它是否被允许执行。

- 命令类和 Monitor 类的启动,在管理器真正启动它们之前,都要经过正常的
  参数风险评估、权限检查、Hook、沙箱和环境解析流程;一个 pre-tool
  Hook 可以拒绝这次启动。
- `PostToolUse` 观察到的是**"job 已被接受"**这个事实,因为这才是真正
  返回的那个工具结果。job 的完成是一种全新的生命周期通知,而不是给一次
  早已应答过的调用补发一个延迟的 `PostToolUse`。这扩展了 Hook 契约,
  所以 [hook-system.md](Hook系统.md) 以及 Hook 相关的指南,必须在
  发布这些事件的同一次改动中一并更新——不能让 Hook 的作者自己去猜测
  这些语义。
- job 的输出、Monitor 的行,以及子 Agent 的回复,都属于不受信任的
  输入;事件信封会告诉模型要去分析它们,而不是服从它们。
- 启动一个 Monitor,并不会预先授权它引发的后续反应。由此产生的每一次
  工具调用都要经过正常的策略检查——如果挂接着一个前台界面,就走交互式
  审批;如果没有人挂接在场,一次反应可以做分析和通知,但绝不会把
  `Ask` 重新解释成 `Allow`。

## 输出、保留与轨迹

原始的 job 输出不属于对话历史的一部分。每个 job 都保留一个有界的、
基于游标做增量读取的近期输出环形缓冲区。这个环形缓冲区只存在于内存中,
一个 job 的输出没有任何部分能在进程退出后存活下来。这一点[已经是
定论,而不是悬而未决](#持久化不在计划之内)。

由于父级运行轨迹无法在发起调用返回之后继续保持打开状态,后台工作会
拥有自己的一条 job 事件流,通过所属会话 ID、父轨迹 ID、父工具调用 ID
以及 job 的 ID 和种类来关联。它至少会记录:启动、边界、停止请求、退出、
错误、输出截断、被丢弃的 Monitor 事件,以及任何由此引发的唤醒。
Subagent job 保留它们现有的子运行轨迹。轨迹写入失败仍然遵循失败开放
原则,输出在持久化之前会先做有界化和脱敏处理,依据的是
[durable trace design](持久化运行轨迹.md)。

工具调用之间的关联关系是一个前置条件,而不是一条现成就有的接缝:今天
子 Agent 的轨迹携带的是父级**运行**的 ID,但发起调用的那个工具调用 ID,
既到不了轨迹运行的上下文,也到不了某个工具的 `Execute` 方法里。这项
管线工作必须在阶段 2 之前就位。

## 生命周期与限制

管理器拥有一个独立于任何发起调用的根上下文。它不会在一个请求上下文上
使用 `context.WithoutCancel`——那样会把任意的值一并带过去,掩盖了
身份信息;启动时会把明确的来源信息,拷贝进一个由管理器自己拥有的
上下文中。

关闭过程是有界的:停止接受新 job、在各处发起取消请求、等待一段较短的
宽限期、终止仍然残留的进程树,并记录哪些 job 没有干净地退出。管理器
会强制执行一套保守的限制——最大并发的 command job 数、subagent job
数和 Monitor 数,以及有界的排队启动数——在证据表明可以放宽默认值之前,
会明确拒绝超出限制的请求,而不是默默地放行。

## 交付阶段

阶段 1 是已确定交付的第一片:即便完全没有模型唤醒机制,单靠 command
job 本身也是有用的,而且它们逼出了后续种类可以廉价复用的、最厚重的
那部分基础设施——管理器、状态机、进程树,以及关闭流程。这三个阶段
均已交付。

1. **本地 job 基础设施。** 共享的管理器、job 身份、状态机、有界输出、
   list/get/stop、关闭流程、进程树相关测试;TUI 和 Desktop 上的后台
   `Bash`;界面上的生命周期通知和一个活动视图(TUI 上的 `/tasks` 或
   类似功能,Desktop 上的项目活动界面);完成状态可见、可查询,但没有
   唤醒机制。
2. **后台子 Agent。** 把 `Task` 分离到管理器背后运行;把父级工具调用
   ID 接入轨迹关联;让最终回复可以通过 job 相关工具查询到;在工具输出
   和界面中说明共享工作区的冲突问题。把回复主动推送出去是阶段 3 的
   工作:它需要那套带类型的收件箱机制,如果在这里就实现,就等于把那套
   机制发明两遍。
3. **Monitor 与响应式投递。** Monitor 这种命令种类、按行分帧、速率
   限制、合并、停止;历史记录和轨迹中带类型的事件来源信息;基于
   `notify`/`react`(逐 Monitor 配置)的串行化唤醒;在 TUI/Desktop 中
   提供控制噪声过大或已暂停的 Monitor 的界面。

共享的呈现方式可以放在 `@buildmax/gui` 里;但生命周期和进程相关的行为
绝不能放在那里。

## 持久化不在计划之内

这里曾经设想过第四个阶段,作为持久化方面的后续工作:一个输出 spool 和
job 元数据恢复机制、一个本地 supervisor(用于让 job 能在界面退出后
继续存活)、Desktop 系统通知、基于工作树隔离的写入方,以及建立在同一套
收件箱与 job 模型之上的调度能力。这些都不会被构建,也没有被排进计划。

其中 spool 是看起来最像是能独立带来价值的那一部分,理由是:无论
supervisor 将来是否会出现,持久化的输出和元数据在崩溃之后都是有帮助
的。但放在本设计的框架下看,这个理由并不成立。`Manager.Close` 会取消
每一个正在运行的 job,并等待一段宽限期,所以进程退出这件事本身*就是*
job 的结束,而一个 spool 只会让人有机会读取一个已经不存在的 job 的
输出。这种"事后剖析"所需要的大部分东西其实已经存在了:
`<traces>/jobs/<id>.jsonl` 记录了每个 job 的启动、边界、退出码和停止
原因,连同一个 Monitor 产生的各行内容也一并记录在内。唯一缺失的是
command job 的 stdout 正文本身——如果将来真的需要这个,合乎比例的
答案是在现有的 `job_end` 记录上加一段有界的尾部内容,而不是再造一套
拥有自己的保留策略、游标语义和恢复路径的第二个存储系统。

这个阶段剩下的部分都建立在 supervisor 之上,而 supervisor 本身建立在
一种目前没有人展示过的需求之上。能够跨进程存活的执行能力,本身就是
一个独立的产品与安全边界问题——也就是[按维度划分的替代方案](#按维度划分的替代方案)
中被推迟的那种本地守护进程拓扑——接受它就意味着要负责 job 在界面
退出、升级和崩溃过程中的整个生命周期。持久化 job 元数据,也会把一个
job 提升为一个实体,这就带来了 [entity-identity.md](实体身份.md) 中的
一整套规则;而今天的 `jb_` 标识符,其正当性恰恰建立在"一个 job 只存在
于恰好一个进程之内"这个前提上。

真正能重新打开这个问题的,是[扩大范围之前需要的证据](#扩大范围之前需要的证据)
中的最后一项:人们真的会在 job 运行期间去做别的前台工作,而不是把这个
活动视图当成第二个终端来用。这项证据才是能够证明 supervisor 有必要的
理由,而 supervisor 才是能够赋予 spool 存在意义的前提。这个顺序不能
颠倒——先造出来的 spool,只是一堆没有配套能力的存储。

## 前置条件

以下工作可以独立评审,上面的各个阶段都依赖它们:

1. **会话写入串行化**——让"单一写入方"规则得到强制执行的轮次协调器
   (阶段 1,须在任何事件投递能力之前完成)。
2. **`internal/infra` 中的进程树终止能力**——需要在 macOS、Linux 和
   Windows 上进行测试,包括一个会派生出子服务器的 shell 场景
   (阶段 1)。
3. **把父级工具调用 ID 接入**轨迹运行上下文和子 Agent 的运行选项中
   (阶段 2)。
4. **针对 job 生命周期事件的 Hook 契约扩展**,与实现同步更新到
   [hook-system.md](Hook系统.md) 中(阶段 1–3)。

## 开放问题

- 确切的工具名称和事件名称。工具名称是 Hook 匹配器和子 Agent
  `tools:` 字段中的公共契约;只能确定一次,之后要同步更新
  `internal/tool/names.go` 以及执行测试所检查的文档。
- ~~job ID 的格式~~——已决定:采用可读的 `jb_` 前缀,这是因为该 ID
  会以裸字符串的形式出现在工具输出中被模型看到,而不是因为某个 job
  会被持久化。Job 始终是瞬态的。
- ~~纯内存的输出环形缓冲区,还是一个 `BUILDMAX_HOME` spool~~——已
  决定:采用纯内存方案,依据见[持久化不在计划之内](#持久化不在计划之内)。
- 在一台笔记本电脑上,安全的默认并发数和事件速率限制应该是多少。
- 除了启动这道关卡之外,还有哪些 Hook 应该能够观察到 job 的生命周期。
- 由插件声明的 Monitor,以及它们在交互式工具出现之后应有的信任级别。

## 扩大范围之前需要的证据

- 一个原型,展示一条长时间运行的命令在后台执行的同时,TUI 和 Desktop
  各自还能完成另一次提示,然后再展示并停止同一个 job。
- 竞争条件测试,证明 job 的完成不会对一个会话产生并发追加,也不会与
  审批提示相互重叠。
- 一项"吵闹的 Monitor"测试,证明内存是有界的、注入上下文的内容是
  有界的、被丢弃事件有清晰的计数,并且界面依然保持响应。
- 一次轨迹检查,完整追踪从父级工具调用,到 job、子 Agent 运行、
  Monitor 事件,再到由此引发的一次轮次的全过程。
- 权限方面的测试,证明转入后台绝不会扩大一条已获许可命令的权限范围,
  而且一个已分离的子 Agent 不会永远等待一个没有人能够回答的审批。
- 来自用户的证据,证明人们确实会在 job 运行期间继续做前台工作,而不是
  把这个活动视图当作第二个终端来使用。
