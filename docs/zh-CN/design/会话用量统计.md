## 1. 问题

关于一次运行花了多少钱、做了什么，BuildMax 几乎记录了所有值得知道的信息，但这些记录彼此互不相通。`-p` 模式的页脚只展示其中一小部分；Portal 展示的是单个 TaskRun 的轨迹摘要和调用账本。用户用上一周之后想问的问题，却没有一处能回答：钱花到哪去了、哪个工具最吃上下文、提示词缓存是否真的划算、总耗时里模型占多少、本地工具又占多少。

其中两处记录还恰好朝同一个方向出了错，见 §3。

## 2. 决策

引入一个 **stats（统计）视图**：在本地界面上，按会话对会话与轨迹已经记录的内容做一次只读折叠——落地在 `buildmax info` 和 TUI `/info` 浮层的 session 标签页。

Stats 只是一个读取者。除了一个可重建的投影之外，它不引入任何持久状态，也不改变一次运行如何执行。凡是它需要而当时没有被记录下来的数字，修复都落在记录环节本身，而不是落在读取端的启发式估算上。

三个数据来源各有不同的契约，因此分开呈现而不是混为一谈：

- **会话文件**是 Token 数与费用的权威来源。它们按每一轮当时生效的费率逐轮累加；读取时不会重新计算，因为用现在的配置反推出一个总额，等于用不同的价格重新计算已经付过款的历史轮次。它也是单个工具结果字节数的唯一来源，做法是把 `tool_call_id` 关联回发起该调用的助手消息。
- **运行轨迹**是一切与时间相关内容的权威来源，也保存着会话文件从未记录过的单次运行细节：耗时、拒绝、失败类型、运行的是哪个模型、一次委派做了多少工作。
- **托管调用账本**（`llm_call`）是唯一能看到某个界面发出的每一次 HTTP 调用的来源。它仍归 Portal 所有；基于它的 Space 级分析不在本记录的范围内——那是不同的问题，涉及不同的授权边界，[提示词缓存控制](提示缓存控制.md) §6 已经勾勒出它所属的那个支出视图。

这三者不会被合并成一个数字，因为它们完全可能出现合理的不一致：一次运行在写下 `run_end` 之前就被终止，它会计入会话的总额，却不会出现在轨迹的折叠结果里；如果只展示一个混合后的数字，读者根本无从察觉这种差异。

## 3. 由此引出的计量修复

构建这个视图的过程中，暴露出会话自身统计里的两个漏洞。这两个问题都在视图上线前修复了，因为发布一个连项目自己的诚实性规则都判定为错误的数字，比什么都不发布更糟。

1. **子 Agent 的运行没有被计入。** 子 Agent 运行器调用 `agent.RunLoop` 后，把返回的 `RunStats` 直接丢弃了，导致父会话的 Token 数与费用漏算了每一次 `Task` 委派。现在，子运行会把自己的总额上报给一个 `DelegatedUsage` 累加器，这个累加器由父级循环挂在 Context 上；循环在每次迭代后读取并清空它，因此无论走哪条退出路径——正常回复、取消、出错、达到迭代上限——都会得到一致口径的总额。选择通过 Context 传递而不是扩展工具接口，是因为一次委派在循环看来只是一次普通的工具调用；如果为了让某一个工具能上报花费而扩大 `llm.Tool.Execute` 的接口，就等于把计费职责摊派进了注册表里的每一个工具。

   运行总额因此变成了**包含式**的，`RunStats.Delegated` 则给出其中委派部分的明细——这与提示词 Token 总数和其中缓存 Token 数之间的关系是一样的。工具调用次数是个例外，是**额外**计入的：一次委派本身算作父运行的一次调用，子运行内部产生的调用不会在别处被重复计数。

2. **压缩调用此前完全没被计入任何地方。** `LLMCompactor.Compact` 直接调用客户端，绕开了循环的事件流，因此既不贡献 `RunStats`，也没有轨迹记录——只留下一条表示"发生过压缩"的 `context_compacted`。现在 `ContextCompactor.Compact` 会返回 `llm.Usage`，循环像处理其他调用一样为它计价，费用记在已有的 `context_compacted` 记录上，而不是伪造一条 `llm_end`：压缩确实是这次运行付费购买的一次调用，但它不是一轮对话，把它当作一轮对话来上报，会在轨迹里凭空出现一条这次对话从未有过的回复。

同时还顺带修复了两个相关缺陷：

3. **子 Agent 的轨迹无法被找到。** 运行器此前会创建一个临时会话，返回时就把它丢弃，而轨迹文件却归档在这个临时会话的 ID 下——形成了任何会话都不可能引用到的目录。现在子 Agent 的轨迹归档在父会话名下，用 `is_subagent` 加以区分，并用 `parent_run_id` 关联回去。自[本地会话存储](本地会话存储.md)落地以来，子 Agent 拥有自己的一份会话包，只是被隐藏了，但轨迹依然应当归属于父会话。

4. **失败的工具调用是不可见的。** 循环原本已经区分了失败情形（它会触发 `PostToolUseFailure`），但在任何持久化记录看到错误之前，就已经把它压平成一段 `error: …` 的结果文本。现在 `tool_end` 会携带 `error_kind` 字段。它是一种分类，而不是一个布尔标志，因为不同种类的含义并不相同：`invalid_args` 是模型误用了工具，`tool_error` 通常出在环境上，`panic` 则是本项目自身的缺陷。参数无法解析的调用现在也会像其他调用一样正常发出 `tool_start`/`tool_end`——`tool_start` 本来就表示"模型发出了这次调用"，而不是"执行已经开始"，毕竟一次被拒绝的调用也会发出它。

   **`error_kind` 报告的是一次未能完成的调用，绝不是一次完成得不好的任务。** 命令以非零状态退出，仍然是一次成功的 `Bash` 调用：工具会特意返回一条可读的消息，而不是错误。把这个字段当成失败率来读，恰恰会让表现最差的那些运行显得最体面，所以 CLI 把它标注为"未能完成的调用"，并就地说明这一点。

标题生成本来就已经纳入了计量，这也是为什么上面这处不一致此前很容易被忽略。

## 4. 代码所在位置

- `core/session.Stats` 折叠已存储的历史记录。它是纯函数，只接收一个 `*Session`，不需要运行处于存活状态，因此即便轨迹已经不在了，也能回答关于某个会话的统计。
- `infra/trace.SummarizeSession` 折叠一个会话记录过的每一次运行。它掌管 `<traces>/<session_id>/<run_id>.jsonl` 这套目录结构，因为记录器本身就归它管。
- `agentapp.LoadSessionStats` 把两者组合起来。`agentapp` 同时拥有这两个目录，也是唯一有资格这么做的层；`internal/service/*` 属于服务端领域，放在那里是放错了地方。架构测试强制要求 core 不得导入 infra，因此这个组合逻辑不会向下游漂移。
- `interface/cli` 提供两套渲染：带 `--json` 的 `buildmax info [session-id]`，以及 TUI 的 `/info` 浮层。这两种版式是刻意分开的——一个几十列宽的方框浮层和一个完整的终端窗口，需要不同的呈现形状——但数据本身和注意事项列表是共享的，因为一个界面被允许声明什么，答案应当只有一个；如果某条警告只出现在其中一个界面上，就没有人会真正信任它。该面板折叠的是**存活中**的会话，而不是磁盘上的文件，因为会话是在每次助手回复之后才落盘的，若在一轮执行中途回读文件，得到的只会是上一轮的结果。

## 5. 诚实性规则

这些不是新规则，只是把既有的约定用到了一个专门用来陈述数字的视图上。

- 一个未被测量的量应当是缺失的，而不是零。某个提供方没有报告缓存用量，并不代表它报告了一次未命中，所以这种情况下根本不打印缓存这一行。
- 一个没有任何模型定过价的会话，应当明确说明这一点，而不是显示 `0.000000`。
- 一个不完整的总额要标明自己不完整：`cost_incomplete`，并附上一条警告，点名哪些运行从未写下结束记录。
- 只有当 `Baseline > Total` 时才会报告"节省了多少"。如果一次运行只写入了缓存条目，实际花费反而比不用缓存更高，视图就应当如实说明这一点。
- 父运行与被委派运行的花费会被正确相加，并且展示两者的拆分。绝不会只给出一个悄悄代表了较小那部分的数字。
- 当各工具耗时之和超过墙钟时间时——并行工具执行会让这成为常态——就不再打印模型/工具的耗时拆分，而不是打印出一个负数的模型耗时。

## 6. 待解决问题

- **跨会话汇总。** 也就是回答"这一周花了多少钱"，并按工作区、模型、日期分组。设想中的实现机制，是在 `sessions/index.json` 的对应行上加一个小的投影字段，随每一轮本就会发生的元数据写入一并写下——那个文件本就明确可重建，所以一个错误的值是可以修复的，不构成一次迁移。这是主动推迟，而不是被什么卡住了。
- **按轮次记录。** 这样做可以去掉对轨迹的依赖，让一个会话自描述。[本地会话存储](本地会话存储.md)已经落地，因此现在有地方放它了：`meta.json` 保存着累计总额，按轮次的明细理应放在它旁边，而不是再从日志里反向折叠出来。
- **轨迹保留策略。** 目前没有任何机制会清理一个会话的 `traces/` 目录。Stats 视图既是支持制定保留策略的一个理由，也会是该策略缺位的受害者；在保留策略确定之前，这个视图能做到的最好程度，就是明显地降级，而不是悄悄地给出残缺的结果。
- **缓存诊断。** 等[提示词缓存控制](提示缓存控制.md) §6 所要求的请求模式、能力、策略、结果这几个字段进入轨迹之后，缓存部分应当直接报告记录下来的结果，而不是从计数中反推。
- **Desktop。** 需要绑定的内容，汇总逻辑已经全部暴露出来了，只是还没有做。
- **Worker 运行不贡献任何数据，这是设计使然**：一次 Worker 运行是在一个运行专属的 `BUILDMAX_HOME` 里组装起来的。这是正确的——Worker 的花费理应是账本的职责——之所以在此明确记录下来，是为了让这一点是被陈述出来的事实，而不是日后被意外发现的现象。
