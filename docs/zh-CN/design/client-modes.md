## 1. 决策

| | 本地模式 | 托管模式 |
|---|---|---|
| 触发条件 | 没有已存储的登录 | 存在已存储的登录（§3） |
| 模型列表 | `settings.yaml` 中的 `models[]` | 从服务器获取 |
| 提供商凭证 | 存储在本机 | 永不离开服务器 |
| LLM 调用 | 本机调用提供商 | 本机调用服务器 |

两种模式**互斥**。托管会话看不到本地模型条目，本地会话也看不到服务器模型。执行 `buildmax logout` 离开托管模式，执行 `buildmax login` 进入托管模式。

这样获得了三个性质，按重要性排列如下：

- **由一个事实决定模式。** 不需要模式开关、不保存偏好，也不需要规定二者之间的优先级。用户和代码要判断“当前处于哪种模式”时，都只需检查同一个地方。
- **不合并列表。** 如果把本地模型和服务器模型合并，就必须设计重名冲突规则、优先顺序，以及两边都匹配时 `--model` 的含义。列表只有一个来源时，这些规则都不需要存在。
- **不存在隐式回退。** 服务器故障不能把提示词改发到个人提供商密钥，因为托管模式下根本没有可供回退的本地条目。这原本已是网关规则；单一来源的列表把它变成了结构性保证。

代价是离线工作前必须执行 `buildmax logout`。这是可以接受的：它只需一条明确命令，并且如实表达了发生的变化——提示词现在会被发送到另一个目的地。

## 2. 解决的问题

托管模式过去需要通过手动编辑 `settings.yaml` 进行配置：

```yaml
- name: Space default
  model: default
  transport: buildmax
  server_url: https://buildmax.example.com
  space_id: tm_example
```

除 `model` 外，每个字段都已经由登录过程确定；`buildmax models --space <space_id>` 甚至会输出这段配置让用户复制，等于直接暴露了设计缺口。

根本原因是结构性的：**`settings.yaml` 只能读取。** 仓库中唯一会写入它的是 `buildmax init`，该命令根据模板生成整个文件；`internal/config` 没有保存函数。因此，登录这一有状态操作与“使用 Space 模型”这一配置编辑从未打通，也无法打通。

这还会产生悬空状态。执行 `buildmax logout` 后，托管模式条目仍留在 `settings.yaml` 中，`buildmax doctor` 则报告它们缺少登录。配置保存了依赖会话状态的内容，两者自然会失去同步。

## 3. 模式解析

存储的登录是唯一的输入。它存在或不存在。

`auth.json` 是该登录记录的整体。操作系统凭证存储保存访问令牌和刷新令牌，文件只保留服务器 URL、用户和电子邮件等非秘密部分。因此，`auth.Info` 读取两部分信息，而不是只用 `os.Stat` 判断文件是否存在。模式的含义没有改变，秘密仍由凭证存储管理。

Desktop 的第三个模式标志已删除：`mode.go`、`desktopState` 和 `UseLocalMode` / `ConnectToServer` 绑定都不再存在。`GetAuthStatus` 中“可用登录优先于记住的本地选择”的判断，原本是两个事实来源并存时的补丁。现在 Desktop 与 CLI 一样直接打开 Agent，登录只是账户菜单中的操作，而不是启动时的模式入口。因此，

Startup 没有要询问的模式问题。存储的登录信息意味着受管理；
没有什么意味着本地的。

**已存储但不可用。** `auth.Info` 可以报告凭证存在但登录已过期；这足以决定是否提供账户命令。模式解析只读取 `auth.StoredLogin` 是否存在，凭证是否仍有效由[§8](#8-登录过期时不静默回退)处理。过期会话不能静默转换成本地模式。

## 5. 模型在部署内全局共享

空间是协作边界 — 共享问题、代理、工作流程。它是
**不是**模型授权边界。目录中的每个型号均可用
部署的每个用户。

这是对 [llm-gateway.md §4.2](llm-gateway.md) 的故意缩小，其中
数据库中计划的每个空间模型策略。该能力被撤销，
没有推迟。每个空间的门控模型意味着一个用户属于多个空间
space 必须声明提示适用于哪个空间 - 工作空间选择概念
该产品没有且未添加。

当决定时，代码已经在部署范围内：`llm.aliases`
`server.yaml` 将相同的集合暴露给每个空间，以及每个空间的数据库
政策从未制定。所以这删除了一个未构建的抽象而不是
改变行为。

## 6. 移除别名层

`llm.aliases` 和 `llm.default_alias` 从 `server.yaml` 中消失。客户姓名
`llm_model.name` 的模型。 `llm:` 块本身保留下来，持有一键
幸存下来：`default_model` ([§7](#7-默认模型))。

别名层的存在是为了给空间提供在提供者中生存的稳定名称
路由变化。 `llm_model.Name` 已经完成了这项工作：它是
`uniqueIndex; not null`，面向操作员，在整个部署中是独一无二的。
重新指向不同上游的名称正在编辑该行的 `api_url` 和
`model`——这个名字永远不会动。唯一名称之上的别名到 ID 映射是
没有第二项工作的间接，并且解析器已经承认了这一点：它
将别名描述为可以解决问题的面向空间的一半
直接目录条目。

由于解析路径中存在空格，那一半就什么都没有了。
分辨率来自：

```text
(space_id, alias) -> catalog ID -> LLMClient
```

到：

```text
name -> llm_model row -> LLMClient
```

## 7. 默认模型

两种模式都需要回答“新会话从哪个模型开始”，并且两者都需要回答“新会话从哪个模型开始”
当没有其他说明时，回到第一个条目。

- **本地：** `settings.yaml` 中的新顶级 `default_model` 密钥，命名为
  `models[]` 中的条目。
- **托管：** `server.yaml` 中的 `llm.default_model`，在中命名一行
  `llm_model`。服务器解析它并在模型列表中标记该条目
  返回，因此客户端仍然只是读取一个标志。

默认是配置，而不是目录状态。 [第 7 条
llm-gateway.md](llm-gateway.md) 认为目录不是配置，而是它的
原因是目录保存了提供者凭证，该凭证不得在
ConfigMap 携带的文件。型号名称不是凭证，因此原因
没有达到这个领域。

有两件事确实达到了这一目标。首先，`server.yaml`已经持有部署的
其他型号选择 — 适用于 Tier 1 的 `conversation.model` 和 `worker.llm.model`
用于任务运行。将客户端默认值放在其他地方会分解一个问题，
“此部署默认是什么”，跨越两个地方。第二，
`worker.llm.model`空时回落到该值；如果默认居住在
在数据库中，`server.yaml` 无法再在没有
查询。

重新启动更改它不是新成本：`conversation.model` 已经
需要一个，并且推广新的默认模型是一种深思熟虑的、
每个人都看到它的变化而不是例行公事。因此，

解析链是：一个显式名称，否则为 `llm.default_model`，
否则是第一个目录行。 `default_model` 命名不存在的行
**在启动时停止服务器**，与空目录检查的原因相同
确实如此——它解析得很干净，否则每个会话都会在第一次时失败
打电话。

`/model` 保持会话范围且不持久，这就是代码的内容
已经这样做了。模型选择是您正在进行的对话的一个属性，
不是一个设置；下一个会话再次从默认值开始。没有什么需要
写入磁盘以切换模型，这使得切换变得便宜。

## 8. 登录过期时不静默回退

登录可能存在但已失效：刷新令牌已过期，或者会话已过期
撤销。当这种情况发生时，托管模式一定不能悄悄地变成本地模式 -
这正是无回退规则对受管流量的重定向
存在是为了防止。

表面显示登录已过期并提供一个操作：返回本地模式。
接受它**删除`auth.json`**，这才是实际返回客户端的内容
本地模式，因为文件的存在就是模式。直到用户接受为止，
会话不运行。

在 CLI 上，该操作是 `buildmax logout`，在错误中命名，而不是
提示 — 命令在终端和脚本中读取相同的内容，并且
在第二个提示符中将没有任何内容可读取。 Desktop提供一个按钮，
因为它已经有地方可以放了。

删除文件而不是将其标记为过时是使§3 保持正确的原因。保留了一个
但无效的 `auth.json` 将是第三种状态，每个读者都需要
了解“有登录名”和“有有效登录名”之间的区别。

## 9. 用量归属于具体用户

`llm_call` 账本记录用户。 `space_id` **从行中删除**，
未设为可为空：账本已包含 `task_run_id`，并运行 → 任务 →
每当提出问题时，空间就会重建空间。上有一个空格柱
每个调用都是非规范化，只有前台调用 - 这
不属于任何空间——可能无法填充。

重建复合唯一索引 `idx_llm_call_client` 以引导
用户密钥，这也是它所保护的幂等性密钥的正确范围：
密钥属于发送它的调用者。

读取运行的账本是通过授权运行来授权的——它属于
正好一个空格 - 因此 `ListLLMCallsByTaskRun` 仅需要运行和处理程序
首先检查所有权。

每个空间的配额超出了此处的范围。仅当空间工作空间时才返回
曾经添加过选择，因为每个空间的上限需要每个调用都属于
正好有一个空格，而今天的前台调用却没有。

## 12. 范围之外

- **Space 工作区选择。** 如果没有它，则按空间配额和按空间模型
  政策无法制定，两者都置身事外。每次调用都需要每个空间的上限
  只属于一个空间，而前台调用不属于任何空间。
- **迁移。** BuildMax 是 alpha； `AutoMigrate`应用了新的行形状和
  现有部署不存在兼容性路径。
- **合并的模型列表。** 在 §1 中被拒绝，未推迟。
- **缓存获取的列表。** 托管模式在每次启动时进行获取，这会产生成本
  一个请求并保持最新的答案。缓存将是第三位
  模式会被记录，过时的条目会错误报告部署提供的内容。
