## 1. 目的

[trust-harness.md](./信任保障.md) §3.3 要求提供一份**持久化的运行轨迹**，用以说明一次 Agent 运行期间发生了什么：模型调用、工具调用、审批决策、Hook 执行、文件变更、压缩、错误/重试、令牌用量与耗时、子 Agent 关系、沙箱模式，以及所使用的记忆/指令来源。

共享的 Agent Core 已经会发出一条结构化的内存事件流（通过 `RunLoopOpts.EventSink` 发出的 `core/agent.Event`），但没有任何东西会把它持久化下来。一次运行结束后，唯一留下的持久产物是会话消息和轮转的日志文件——两者都无法还原出*Agent 做了什么、为什么这样做*。

本文档定义了一种建立在现有事件流之上的持久化、有边界、经过脱敏处理的轨迹，将其挂接在每个界面都已经使用的唯一关卡上（`agentapp.RunPrompt`），这样 CLI/TUI、Desktop、Agent 评估以及 worker 都无需各自编写代码即可生成轨迹。

这是 §3.4（活动视图）、§3.7（子 Agent 可追溯性）、§3.8（worker 诊断）以及 Portal 运行诊断的前提条件。

## 2. 方向

- **建立在事件流之上，不要另起一条并行的流。** 轨迹是一个 `EventSink` 的消费者。只有当事件流本身还无法表达某件事时，才会新增记录类型（本轮改动没有新增——它把现有的 9 种 `EventKind` 加上一个合成的 `run_start` 映射了出来）。
- **一个关卡。** `agentapp.RunPrompt` 是 CLI（`print.go`、`tui_model.go`）、Desktop、评估以及 worker（`agentapp/taskrun`）共用的唯一调用点。把记录器接入这里就覆盖了所有界面。
- **始终 fail open。** 轨迹写入失败（磁盘已满、权限被拒绝、编码错误）绝不能中断或拖慢一次运行。每个记录器错误都以 warn 级别记录后直接丢弃。
- **默认有边界且经过脱敏。** 过大的工具结果和模型内容会被截断；常见的密钥形态在落盘前会被清除。
- **可供检视，但尚不是产品功能。** 第一阶段持久化 JSONL，供活动视图（§3.4）和未来的 `buildmax trace` 命令读取。本轮不涉及 UI。

## 3. 存储模型

### 3.1 布局

```
<BUILDMAX_HOME>/sessions/<session_id>/traces/<run_id>.jsonl
```

- 每次 `RunPrompt` 调用（即每次运行）对应一个文件。
- 按会话分组，使一次会话内的多次运行放在一起。
- 本记录最初把该目录放在 `<BUILDMAX_HOME>/traces/<session_id>/`。[local-session-storage.md](./本地会话存储.md) §10 把它挪进了会话包内；每次运行的约定没有变化，变化的只是文件所在的位置。traces 根目录仍然保留，用来存放不属于任何会话的内容——本地后台作业会写入 `<BUILDMAX_HOME>/traces/jobs/<job_id>.jsonl`。
- `run_id` 采用带前缀的 ID 格式（CLAUDE.md §6.3），前缀为 `rt_`（“run trace”）：`rt_<20 位 base36 字符>`。
- JSONL：每行一条自描述记录，只追加不修改。JSONL 能在运行中途崩溃时幸存下来（每一条写完的行都是合法的），而且流式写入的开销很低。
- 每条记录写入时都会立即刷盘，而不是缓冲到关闭时才写。上面说的“能在崩溃中幸存”正是这种格式存在的意义，一旦引入缓冲尾部，这个特性就被悄悄拿走了：记录恰恰会在运行出问题的那些场景下丢失，而磁盘上留下的最后一个事件会早于实际发生的最后一个事件——这会把排查故障的人引向错误的位置。轨迹的写入量每次模型调用只有寥寥几条记录，不值得为了这点开销去换取上述代价。

### 3.2 记录结构

所有键均为 snake_case（CLAUDE.md §6.1）。用一个带 `omitempty` 字段和 `type` 判别字段的 Go 结构体表示；与某条记录类型无关的字段会被省略。

```jsonc
// run_start — synthesized by the recorder at construction
{"ts":"2026-06-03T10:00:00Z","type":"run_start","run_id":"rt_…","session_id":"c_…",
 "workspace":"/path","model":"…","is_subagent":false,"trace_version":1}

// run_start for a worker executing a TaskRun — created_by, created_by_type,
// trigger_source, and retry_of_task_run_id are that TaskRun's provenance
// (docs/design/portal-work-and-execution-experience.md), carried through
// verbatim rather than reconstructed from the trace file's own location.
// Every surface without a TaskRun -- CLI, TUI, Desktop, eval -- omits all
// four, which is the honest answer, not a guess.
{"ts":"…","type":"run_start","run_id":"rt_…","session_id":"c_…",
 "workspace":"/path","model":"…","is_subagent":false,"trace_version":1,
 "created_by":"u_…","created_by_type":"user","trigger_source":"issue_agent_run"}

// subagent run_start — parent_run_id is the immediate parent, so a trace tree
// can be reconstructed one edge at a time. Top-level runs omit the field.
// A subagent's own run_start omits TaskRun provenance too: its parent_run_id
// already reaches the top-level record that carries it, and a TaskRun has one
// origin, not one per delegated call.
{"ts":"…","type":"run_start","run_id":"rt_child","parent_run_id":"rt_parent",
 "session_id":"…","is_subagent":true,"trace_version":1}

// sandbox_boundary — synthesized at construction; added after phase 1 so a run
// states the boundary it ran under. Written even when nothing confined the run,
// because an absent record reads as "not checked" rather than "not confined".
{"ts":"…","type":"sandbox_boundary","sandboxed":false,"backend":"none",
 "sandbox_mode":"auto_allow","sources":["default:worker","policy"]}

// plugins — synthesized at construction, for the same reason: naming what the
// run loaded from outside the workspace, and for a repository plugin whether
// that input could still change under it. Bounded metadata only, never package
// content. See design/plugin-marketplace.md §10.
{"ts":"…","type":"plugins","plugins":[
  {"name":"code-review","source":"repository","remote_url":"git@…",
   "commit":"…","branch":"main","dirty":false},
  {"name":"release","source":"marketplace","version":"1.2.0",
   "digest":"sha256:…"}]}

// iter_start  (EventIterStart)
{"ts":"…","type":"iter_start","iter":1}

// llm_start   (EventLLMStart)
{"ts":"…","type":"llm_start","iter":1,"context_tokens":1234,"context_window":128000}

// llm_end     (EventLLMEnd) — content bounded
// The cache counts are a breakdown of prompt_tokens, not an addition to it, and
// are omitted entirely when the provider reported none.
//
// prompt_tokens and friends are the run's totals so far; the call_* fields are
// what this one call did. Both are here because subtracting consecutive
// records to get the second goes wrong as soon as a call in between failed.
// cost is this call's, in nano-currency-units, and is absent when the model
// was unpriced — which is not the same fact as a call that cost nothing.
{"ts":"…","type":"llm_end","iter":1,"has_tool_calls":true,
 "prompt_tokens":1200,"completion_tokens":80,
 "cache_read_tokens":900,"cache_write_tokens":100,
 "call_prompt_tokens":1200,"call_completion_tokens":80,
 "call_cache_read_tokens":900,"call_cache_write_tokens":0,
 "cost":{"currency":"USD","uncached":900000,"cache_read":270000,"cache_write":0,
         "output":1200000,"total":2370000,"baseline":4800000},
 "content":"…"}

// tool_start  (EventToolStart) — args bounded + redacted
{"ts":"…","type":"tool_start","tool":"writefile","tool_call_id":"call_1","args":"{…}"}

// tool_end    (EventToolEnd) — result bounded + redacted
{"ts":"…","type":"tool_end","tool":"writefile","tool_call_id":"call_1",
 "result":"ok","duration_ms":12}

// tool_denied (EventToolDenied)
{"ts":"…","type":"tool_denied","tool":"bash","deny_reason":"policy"}

// context_compacted (EventContextCompacted)
{"ts":"…","type":"context_compacted","summarized":3,"kept":5}

// user_input  (EventUserInput) — a message queued mid-run, joining at an
// iteration boundary; bounded + redacted, because it is part of what the run
// was told to do and a trace that omitted it would misreport its instructions.
{"ts":"…","type":"user_input","iter":3,"content":"also check the tests"}

// user_input_blocked (EventUserInputBlocked) — a UserPromptSubmit hook refused it
{"ts":"…","type":"user_input_blocked","iter":3,"content":"…","deny_reason":"no secrets"}

// run_end     (EventRunEnd)
// cost here is the run's, summed from the calls above. cost_incomplete says a
// call did work that could not be priced, so the total understates the run.
{"ts":"…","type":"run_end","tool_calls":2,"prompt_tokens":1200,
 "completion_tokens":80,"cache_read_tokens":900,"cache_write_tokens":100,
 "cost":{"currency":"USD","total":2370000,"baseline":4800000},
 "error":""}
```

`EventLLMDelta` **不会**被持久化——流式增量与最终的 `llm_end` 内容重复，持久化只会让文件膨胀。`llm_end.content` 携带的就是经过边界截断处理的最终助手文本。

### 3.3 边界截断

- `content`、`args`、`result` 各自会被截断到 `maxFieldBytes`（默认 4096），并附加 `… [truncated N bytes]` 后缀。截断点会向前回退到 UTF-8 的字符边界，确保不会切断一个多字节字符——被切断的字符会被 JSON 编码器重新编码为 U+FFFD。
- 每次运行有一个记录条数上限（`maxRecords`，默认 10000），用来防止失控的循环；一旦触达上限，后续记录会被丢弃，并记录一条 `truncated` 警告。`run_end` 记录始终会尝试写入。

### 3.4 脱敏

在写入前会对 `content`、`args`、`result` 应用以下规则：

- `Bearer <token>` → `Bearer [redacted]`
- `sk-<≥16 个字符>` → `[redacted]`
- `(?i)(authorization|api[_-]?key|token|secret|password)` 后跟 `=`/`:` 和一个值 → 键保留，值 → `[redacted]`

脱敏规则刻意保持保守（基于关键字/形态匹配），以避免破坏正常输出。这套模式原计划放在记录器旁边的一个独立文件里，最终落在了 `internal/util/secretscan` 中，因为作业日志和项目记忆需要同一套模式；这样它就可以在不改动记录器的情况下继续增长，现在也不必再改动它另外两个调用方。

## 4. 分层

镜像 Hook/MCP 的分层方式（契约在 core 中，实现在 infra 中，组装在 agentapp 中）：

```
internal/core/agent/event.go        # Event/EventKind — exists, unchanged
internal/config/trace.go            # TracesDir(), TraceEnabled(), env key
internal/infra/trace/record.go      # Record struct + FromEvent mapper + bounding
internal/util/secretscan/           # redaction patterns, shared with joblog and memory
internal/infra/trace/recorder.go    # Recorder: open file, Record(Event), Close()
internal/agentapp/app.go            # RunPrompt tees EventSink into a Recorder
```

导入合规性：`infra/trace` 导入 `core/agent` 和 `config`（两者对 `infra` 来说都是允许的）；`agentapp` 本来就已经导入了 `infra/*` 和 `config`。

## 5. 运行时流程

```
agentapp.RunPrompt(ctx, sess, prompt, stream, approval, eventSink)
  │
  ├─ resolveRunContext → model, client, session
  │
  ├─ trace.NewRecorder(TracesDir, meta{run_id, session_id, workspace, model})
  │     └─ writes run_start,           (nil + warn on error → fail open)
  │        then sandbox_boundary, context_sources, plugins
  │
  ├─ sink := tee(recorder.Record, eventSink)   // recorder first, then caller
  │
  ├─ agent.RunLoop(… EventSink: sink …)
  │     └─ emits iter/llm/tool/compaction/run_end → recorder + caller both see them
  │
  └─ recorder.Close()                  // flush + close file; no extra run_end
```

- 记录器是 tee 的*第一*条分支，这样即使调用方的 sink 发生 panic 也不会丢失轨迹数据；两条分支都是尽力而为。
- `RunResult` 新增了 `TraceID string` 字段，让调用方可以据此定位查看对应的文件。即使在错误返回路径上（`RunLoop` 失败、`finalizeTurn` 失败）它也会被填充——`RunLoop` 会在返回前发出带错误信息的 `run_end`，所以轨迹是完整的，而失败的运行恰恰是调用方最需要它的时候。
- **提示被 Hook 阻断**（在 `RunLoop` 之前提前返回的情况）：记录器会先写入 `run_start`，再写入 `run_end{error:"blocked by hook: <reason>"}` 并关闭，因此被阻断的回合仍然会留下一行说明。

## 6. 配置

- `config.TracesDir()` → `<DataDir>/traces`。
- `config.TraceEnabled()` → 除非 `BUILDMAX_TRACE_DISABLED` 取真值（`1/true/yes/on`），否则为 true。默认开启；已注册在 `env_spec.go` 的 `EnvVars()` 清单中，并记录在 `docs/reference/configuration.md` 中。
- worker 继承相同的环境变量，因此 worker 运行默认也会记录轨迹；它们的轨迹目录位于运行范围内的 `global/` BUILDMAX_HOME 下，使轨迹数据随运行一起留存，便于后续上传/诊断。

## 7. 本轮不涉及的范围

- TUI/Desktop 中的活动视图 UI（§3.4）——留待以后读取这些文件时再做。
- `buildmax trace` 这个 CLI 检查/列表/导出工具。
- Hook 执行和审批授予记录：从今天的事件流中只能看到 `tool_denied`（reason 为 `hook`/`user`）。专门的 `hook_*`/`approval_*` 记录需要新增事件，故予以推迟。
- 文件变更记录、沙箱决策记录、重试记录——要等事件流把它们暴露出来之后再说。
- 区分一次运行*为什么*失败。`run_end.error` 携带一条消息，但因依赖不可用而失败的运行，读起来和模型或任务本身失败的运行没有区别。`/readyz` 能回答某个依赖现在是否不可用，却无法回答某次运行当时为什么失败。要对失败原因分类，需要在 `run_end` 上加一个带类型的成因字段，而事件流目前不携带这项信息。
- 轨迹目录的保留/轮转/垃圾回收。**需要主动接受的后果：** 轨迹默认开启且从不删除，因此会话包会无限增长——每次运行一个轨迹文件，每个文件的上限是 10000 条记录 × 约 4KB 的有边界字段。本地使用大概率不会察觉；真正暴露风险的是长期存活、跨多次运行保留同一个 `global/` 主目录的 worker 容器。在保留策略落地之前，运维人员可以根据单次运行的上限来估算这块存储的大小，或者直接设置 `BUILDMAX_TRACE_DISABLED`。

### 子 Agent 关联

子 Agent 的轨迹会记录其直接父级的 `parent_run_id`。这样就能一条边一条边地重建出一棵轨迹树，而不必让子节点依赖某个根运行的标识符：顺着链接追溯就能得到根节点，未来的嵌套子 Agent 也以同样的方式组合。当父级记录器未能启动时，不会写入任何子轨迹，而不是写一个具有误导性的、无法关联的子记录——这保持了 fail-open 的行为。

## 9. 验收

- 在任意界面上执行任意一次 `RunPrompt` 之后，`<DataDir>/sessions/<session>/traces/<run>.jsonl` 都存在，并包含一条 `run_start`、逐次迭代的 LLM/工具记录，以及一条终止性的 `run_end`。
- 超过边界的工具参数/结果和模型内容会被截断；Bearer/`sk-`/关键字类密钥会被脱敏。
- 通过 `BUILDMAX_TRACE_DISABLED=1` 禁用后不会产生任何文件，也不会报错。
- 强制制造一次记录器失败（目录不可写）会记录一条警告，运行依然正常完成。
- worker 的任务运行会在运行范围内的 `global/` 主目录下留下一条轨迹。
