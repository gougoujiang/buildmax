## 1. 问题

大多数服务器实体携带两个标识符：一个自增`id`和一个
公共 `varchar(64)` 前缀 ID，例如 `t_9f3k2m8x1qwe7rt4zy0p`。数字
键是内部键，但它不是关系键——每个外部引用，
join、授权过滤器和配额聚合使用公共字符串。的
模式支付两个标识符的费用，但没有获得任何好处： 身份
是重复的，并且关系是广泛的、依赖于排序规则的字符串。

当前树的完整清单确认了规模。横跨28排
`internal/infra/db` 中的结构体，**99 列被声明为 `varchar(64)`**。一个
少数是值——层名称、审计操作、版本、摘要、模型
别名 - 其余的是标识符，其中大多数是关系引用
在每个子行上重复并重新索引。承载最多的桌子是那些生长的桌子
有活动 — `task`、`task_run`、`llm_call`、`conversation_message`、
`workflow_step_run`、`issue_comment`、`audit_event`、`artifact` — 不是这些
随着管理配置的增长而增长。

接下来是另外三个成本：

- MySQL 在数据库的 `utf8mb4` 排序规则下比较这些标识符。
  `database.go` 中的创建者选择 `utf8mb4` 并且没有列覆盖它，因此
  身份比较是排序决策而不是字节比较。
- 核心型号同时带有`ID uint`（标记为`json:"-"`）和公共字段
  如`TaskID string`。 MySQL 实现细节可见
  `internal/core/model`，每个模拟和替代商店都必须复制。
- 类型前缀是一种约定，而不是边界。生产代码中没有任何内容
  对其进行调度或验证：树中仅有的三个 `HasPrefix` 检查
  正在测试中（`llm_call_test.go`、`routes_test.go`、`service_test.go`）。

BuildMax 处于 Alpha 阶段，不做出标识符兼容性承诺。这是
决定当前格式是否为合同的最后便宜时刻。

## 2. 目标和非目标

**目标。** 普通关系使用数据库本机键。公共标识符
保持不透明、不可枚举且独立于数据库拓扑。每个
标识符只有一个作用。没有数据库主键到达 API
响应、URL、JWT 声明、日志行、跟踪、工作流程定义或
对象存储路径。一种连贯的 Alpha 模式更改，没有双读取路径。

**非目标。** 标识符不是授权凭证 - 每次查找
仍然强制执行空间成员资格并返回相同的 `404`，无论
标识符熵。订购从不使用公共标识符；持久订购
仍然是 `created_at` 加上数字键作为决胜局。提供商 ID、工具调用
ID、代理会话 ID、跟踪运行 ID 和幂等密钥均由外部拥有
实体模型并且未受影响。将原始 ID 隐藏在 Portal 中的名称后面是一种
单独的演示文稿更改。存储库的无数据库外键规则是
不默默逆转； §8明确决定。

## 3. 决策

`internal/core/model` 命名域结构所在的包
被写了。此后，它被分成每个域一个包 - `core/task`，
`core/space`、`core/issue`、`core/conversation` 以及其余的 — 根据
【约定】(../contribute/conventions.md)；以下每项决定均适用于
这些包裹在一起。

| ＃|决定|
|---|---|
| D1 | `id` 是 `bigint unsigned auto_increment`，并且是关系密钥。 `public_id` 是外部手柄，仅在需要时出现。 |
| D2 |公共 ID 是 96 位的加密随机数据，呈现为 20 个小写 base32 字符。修改§17：规范文本也是存储形式，`char(20)` ascii_bin，而不是原始字节。 |
| D3 |严格的单类型关系成为`uint64`列。此更改中没有 `FOREIGN KEY` 约束。 |
| D4 |核心域结构仅携带公共身份。结构体自己的句柄是 `ID string`，序列化为 `id`。 |
| D5 | 18 个表携带 `public_id`，8 个表不携带 `public_id`，2 个表保留自然密钥。 |
| D6 |仅当引用是多态的、外部拥有的或值时，引用才保持不透明字符串。 |
| D7 |公共到数字的转换发生在 `internal/infra/db` 内部，并且永远不会产生 N+1 读取。 |
| D8 |无兼容层。 Alpha 数据库和对象存储被重置。 |
| D9 |一种标识符格式。类型前缀仅在自由散文中的裸露标识符到达读者时才存在。 |

## 4. 公共 ID 格式

### 4.1

96 位的值 `crypto/rand`，以其规范文本形式存储在
`char(20) CHARACTER SET ascii COLLATE ascii_bin`（§17；原判决
将原始 12 个字节存储在 `BINARY(12)` 中）。

当一张表中有 10 亿个值时，生日限制的冲突概率为
关于`6.3e-12`。唯一索引仍然是最后的守卫：命中的创建
`uq_<table>_public_id` 上的重复项会在一小段时间内重新生成并重试
固定限制，并且所有其他重复键错误均按原样返回。与一个
十亿个实时值，统一猜测以大约概率命名其中一个
`1.3e-20`。这种不透明性是太空授权背后的纵深防御，
无法区分的未找到响应，永远无法替代它们。

该值不是UUIDv7，不携带时间戳，并且不显示任何插入
顺序或近似的资源数量。索引局部性来自
自增键；随机值是一个辅助唯一索引而不是
复制到每个其他索引中的聚集键。

每个表的公共 ID 都是唯一的。 BuildMax没有全局资源解析器，并且
路由或 JSON 字段始终提供类型上下文。跨表注册表
会增加写入瓶颈并且不会获得授权或冲突的好处。

### 4.2 文本形式

RFC 4648 base32，无填充，小写：字母 `a-z2-7`，正好 20
字符，解码为恰好 12 个字节。

```text
ivyoh5qcfu6ypfkhyedq
```

该提案指定了16个字符的base64url。 Base32 又多花四块钱
特征并消除当前的一整类边界危险
lowercase-base36 格式会默默地防范，而 base64url 则不会：

|边界| Base64url (`A-Za-z0-9-_`) | Base32 (`a-z2-7`) |
|---|---|---|
| Kubernetes 作业名称 - `util.WorkerJobNameForTaskRun` 小写运行 ID 并将每个非 DNS-1123 字符替换为 `-` |外壳和`-`/`_`崩溃。在同一秒内创建的两次不同的运行可以生成一个作业名称，因为唯一的后缀是第二分辨率时间戳 |通过消毒剂后未发生变化 |
|不区分大小写的文件系统上的本地 FS 对象存储（默认为 macOS），其将工件内容键为 `spaces/<space>/artifacts/<id>/content` |仅当静默共享一条路径时，两个 ID 才会有所不同。数据库唯一索引在原始字节上，看不到冲突 |不可能发生 |
|复制、粘贴和听写裸 ID |区分大小写，`_` 在下划线下不可见 |不区分大小写，一双击单词 |

案例折叠下的残余熵使得本地 FS 危险成为现实
而不是理论上的：折叠 base64url 留下 38 个符号字母表，所以
一个空间中的十亿个值以 `2.6e-8` 左右的概率折叠碰撞 — 四
比原始边界差几个数量级，并且故障模式是无声的
内容覆盖而不是数据库错误。

### 4.3 编解码器

`internal/util/id.go` 是两个函数，没有别的（§17 折叠了
原始解析/格式化字节对为一，因为没有调用者持有任何字节
更多）：

```go
func NewPublicID() (string, error)              // 20-char canonical text
func CanonicalPublicID(s string) (string, bool) // any-case text -> canonical text
```

`NewPublicID` 返回错误而不是恐慌：`crypto/rand` 失败
必须表现为失败的创建，而不是请求内的进程中止。

`CanonicalPublicID` 接受不区分大小写的输入并规范化为
小写，因此从标题文档中重新输入的 ID 仍然可以解析。它
拒绝其他所有内容，并保证每个文件都只有一种规范文本形式
通过解码、重新编码并要求结果匹配来获取值。那张支票
是消除 Base32 尾随位歧义的原因：20 个字符携带 100 位，
最后四位必须为零——并且，在存储文本的情况下，什么保持一
占据十六个不同的唯一索引条目的价值。

该检查的一个可见结果：规范 ID 始终以 `a` 或
`q`，因为这是唯一两个低四位为零的字符。安
以其他任何内容结尾的发明的固定装置不是公共 ID。参加测试
来自生成器的值，而不是来自想象的值。

`FormatPublicID` 位于非 12 字节的切片上是一个编程错误，并且
返回空字符串，存储的读取路径将其视为损坏。

### 4.4 前缀已停用

`id.go` 中的前缀常量与前缀表一起被删除
[约定.md](../contribute/conventions.md#entity-ids-are-opaque-public-handles),
`NewPrefixedID` 本身也是如此。登录链、跟踪文件和 Desktop
项目不是数据库行，但这从来不是前缀的参数 -
这只是这个变化的边界。它们都不是由一个人或
已下发，因此没有人保留。

有一个。后台作业的 ID 作为工具内的裸字符串到达模型
输出 — `job: jb_ivyoh5qcfu6ypfkhyedq` 在命令行和文件路径旁边 —
自由散文是周围环境尚未命名的地方
类型。该前缀位于 `internal/agentapp/job` 中，它拥有以下概念：
而不是 `internal/util`。

## 5. 模式形状

```sql
CREATE TABLE task (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    public_id       CHAR(20) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    conversation_id BIGINT UNSIGNED NOT NULL,
    space_id         BIGINT UNSIGNED NOT NULL,
    issue_id        BIGINT UNSIGNED NULL,
    agent_id        BIGINT UNSIGNED NULL,
    last_run_id     BIGINT UNSIGNED NULL,
    created_by      BIGINT UNSIGNED NOT NULL,
    -- status, input, title, output, timings, session_id unchanged
    PRIMARY KEY (id),
    UNIQUE KEY uq_task_public_id (public_id),
    KEY idx_task_space_created (space_id, created_at),
    KEY idx_task_conversation (conversation_id)
);

CREATE TABLE task_run (
    id                   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    public_id            CHAR(20) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    task_id              BIGINT UNSIGNED NOT NULL,
    previous_task_run_id BIGINT UNSIGNED NULL,
    retry_of_task_run_id BIGINT UNSIGNED NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_task_run_public_id (public_id),
    KEY idx_task_run_task (task_id)
);
```

名称携带角色：

|名称 |意义|
|---|---|
| `id` |该行的内部数字主键 |
| `public_id` |这一排不透明的外部手柄，仅在需要的地方使用 |
| `<entity>_id` |与数据库内该实体的数字关系 |
| `<concept>_public_id` |故意存储的外部或多态句柄。罕见，且名称明确 |

两个机械规则与之相伴。保留的数字字段是 `uint64`，从不
依赖于架构的 `uint`。公共 ID 的 Go 字段为 `string`
与 `gorm:"type:char(20) CHARACTER SET ascii COLLATE ascii_bin"` (§17) —
store 仅写入编解码器生成或规范化的内容，因此恰好是一个
每个值的小写拼写都会到达该列，并且 `ascii_bin`
保留比较 memcmp 而不是整理决策。

数字转换也是使复合索引正确的时刻。一个
按 `created_at` 排序的空间范围列表需要 `(space_id, created_at)`，而不是
单列 `space_id` 索引留下的字符串模型。

## 7. 哪些引用保持不透明

当列准确命名一种服务器实体类型和
应用程序将关系视为实时数据模型的一部分。一切
下面的测试失败并保留其字符串列，重命名为
`<concept>_public_id`，其中该值为公共句柄：

|专栏 |为什么它留下来 |
|---|---|
| `audit_event.actor_id` / `target_id` |多态性。 `actor_type`和`target_type`搭载型号；一个数字列无法寻址多个表中的行 |
| `issue.assignee_id` |多态性。 `assignee_kind` 是 `person`、`agent` 或 `workflow` |
| `issue_comment.author_id` | `author_kind`下的多态|
| `artifact.created_by_id`，`artifact.source_id` | `created_by_type` 和 `source_type` 下的多态 |
| `task_run.created_by` |由 `created_by_type` 键入，承认 `user`、`webhook` 和 `system` |
| `system_grant.granted_by` |授予部署权限的操作员不一定是用户行|
| `task.session_id`、`task_run.session_id`、`llm_call.session_id` | Agent 会话 ID 命名运行 `BUILDMAX_HOME` 下的文件，而不是一行 |
| `task_run.trace_path` |命名跟踪文件 |
| `conversation_message.tool_call_id` |提供商的工具调用 ID |
| `llm_call.target_id`、`llm_call.alias`、`llm_call.upstream_model` |见下文 |
| `login_code.code_hash`、`user_refresh_token.token_hash` / `session_id`、`user_webhook_key` 秘密哈希 |其身份验证合约拥有的格式 |
|工作流程定义中的步骤 ID JSON |在定义内编写，而不是行 |

`task.created_by`、`conversation.created_by`、`issue.created_by`、
`workflow.created_by`、`workflow_run.created_by`，两个修订表
`created_by`、`plugin.created_by` 和 `plugin_release.published_by` /
`yanked_by` **做**成为数字：没有一个伴随的类型列，并且
每个无条件都是一个用户行。 `task.created_by` 甚至是任务的所有者
用于 webhook 和系统运行，它们携带配置的用户身份。

历史数据本身并不是保留字符串的理由。没有外键，
可为空的数字引用仍然可以记录已删除行的前一个键。

## 8. 数据库外键

无 GORM 关系，无 `FOREIGN KEY` 约束。数字参考是
普通索引列和引用完整性仍然是一个应用程序
责任。

该问题处于开放状态，等待删除语义审查。该评论如下，
它结束了这个问题，而不是再次推迟它。

**BuildMax 不删除父项。** 商店有五种删除方法，并且
它们都不会删除任何其他引用的行：

|方法|它删除了什么 |
|---|---|
| `RevokeKey` |其所有者撤销的 Webhook 凭证 |
| `DeleteIssueComment` |一条评论 - 该架构唯一对用户内容进行硬删除 |
| `PruneAuditEvents` |超过保留窗口的事件，按年龄，而不是按目标 |
| `DeleteExpiredLoginCodes` |无法再兑换的代码 |
| `DeleteExpiredRefreshTokens` |代币已过期 |

`DeleteAgent` 是重命名：它设置 `deleted_at` 以便记录命名代理
还是决心。其他一切消失的东西都会以同样的方式消失——
`deleted_at` 位于工件上，`archived_at` 位于插件上，`revoked_at` 位于
在帐户上授予 `disabled_at`。不存在删除用户的路径
空间、任务、运行、对话、问题或工作流程。

因此 `RESTRICT` 会防范不存在的危险，并对其收费
立即。每个创建用户的装置都必须拆除七个
按依赖顺序排列的表 - 商店测试中的 `deleteTestUser` 已经这样做了
正是这样，用手，这就是每条清理路径都会采取的形状。那
是相对于当前为零的收益的实际成本。

当真正的删除功能到来时，答案就会改变——“删除这个空间并
其中的一切”是显而易见的。该功能必须指定顺序
数据库是否强制执行，以及是否值得添加约束
在同样的更改中，无论如何都会写下订单。添加它们
首先只意味着将订单写两次。

同时不得将数字引用理解为暗示 `CASCADE`。
`internal/architecture` 中的 `TestNoDatabaseForeignKeys` 保持了这一点：
行结构旁边的 bigint 列是远离约束的一个关系标记
`AutoMigrate` 会发出信号，树中的其他任何东西都不会注意到。

## 9. 存储边界

公共 ID 跨进程和持久性系统边界。数字 ID 则不然。

|边界|代表|
|---|---|
| HTTP 请求和响应 |公共ID |
| Portal 路由和客户端状态 |公共ID |
|访问令牌`sub`；运行代币 `sub`、`tid`、`rid`、`kid` |公共ID |
|日志、痕迹、工具输出 |公共ID |
|对象存储密钥 |公共ID |
| Workflow 定义 JSON |公共ID |
| Kubernetes 职位名称 |源自公共ID |
| `internal/core`下的域包和每个存储库接口|公共ID |
| `internal/infra/db` 中的行结构和 SQL |数字 ID |

核心包不得增加第二个内部 ID API 来保存查找。那
将把 MySQL 实现细节推到 `internal/infra/db` 之上并强制
每个模拟和替代商店都可以复制它。行结构拥有两者
陈述；领域模型只拥有公共模型。

### 9.1 解析

一个未导出的帮助器将公共 ID 解析为数字键和类型包装器
将表命名为：

```go
func lookupKey(ctx context.Context, tx *gorm.DB, table, publicID string) (uint64, error)
```

失败的公共 ID `ParsePublicID` 和未命名任何行的公共 ID 均返回
`apierr.ErrNotFound` — 处理程序层已拒绝格式错误的输入
与 `400` 一样，格式良好的未知值一定不会成为存在
神谕。

### 9.2 不使用 N+1 进行读取

以公共资源为根的读取选择其数字键一次并加入
它必须返回每个相关的公共 ID。每个连接都是一次主键查找。
任务聚合（提案要求的原型）是：

```sql
SELECT  t.*,
        c.public_id  AS conversation_public_id,
        tm.public_id AS space_public_id,
        i.public_id  AS issue_public_id,
        a.public_id  AS agent_public_id,
        lr.public_id AS last_run_public_id,
        u.public_id  AS created_by_public_id
FROM        task         t
JOIN        conversation c  ON c.id  = t.conversation_id
JOIN        space         tm ON tm.id = t.space_id
JOIN        user         u  ON u.id  = t.created_by
LEFT JOIN   issue        i  ON i.id  = t.issue_id
LEFT JOIN   agent        a  ON a.id  = t.agent_id
LEFT JOIN   task_run     lr ON lr.id = t.last_run_id
WHERE   tm.public_id = ? AND t.public_id = ?;
```

在 Go 中，这是一个包含行结构加上连接句柄的读取结构，并且
一个 `taskSelect()` 构建器，由详细读取、列表读取和
运行输出读取，因此连接集不能在它们之间漂移。

该行必须是标记为 `gorm:"embedded"` 的**命名**字段，绝不是匿名的
一。 GORM 读取带有自己的 `TableName` 的匿名嵌入结构
作为一个关联并且不扫描它的任何列 - 连接的句柄到达并且
该行自己的字段保持为零值，没有任何错误。一个空间
read 返回一个无名空间而不是失败，因此没有任何东西可以捕获它，直到
在字段上测试断言。列表形式
与 `WHERE tm.public_id = ? 是相同的语句按 t.created_at DESC 排序，
t.id DESC LIMIT？`, which is why `idx_task_space_created`存在。

写入以另一种方式进行：解析根一次，然后从中获取所有其他密钥
该行已读取。创建任务可以解决对话并读取其内容
`space_id` 来自同一行，而不是再次解析空间。

锁定读取永远不会连接。 `SELECT ... FOR UPDATE` 通过连接锁定
也加入了行，因此在其锁定读取中解析刷新令牌的所有者
将在轮换长度内锁定帐户并序列化
该帐户打开的每个会话。如果锁定的行必须报告句柄，
手柄通过按键单独读取。

### 9.3 键集游标

键集游标是调用者合法需要平局的地方
行键提供。审计导出走`created_at`排序的页面
加上行键，因为`created_at`具有一秒分辨率和几个
事件通常会共享一秒钟。

`model.AuditCursor` 因此通过其命名前一页的最后一个事件
**public** 句柄，并且存储将该句柄解析为
键集谓词：

```sql
WHERE created_at < ?
   OR (created_at = ? AND id < (SELECT id FROM audit_event WHERE public_id = ?))
```

每页一次索引查找，而不是每行一次，并且没有往返：替代方案 --
将行键交给调用者，以便下一个请求可以将其发回 - 是
这种设计正是为了防止泄漏。任何未来的光标都跟随
相同的形状。

### 9.4 聚合

`SpaceUsageInWindow` 当前加入`task ON task.task_id = task_run.task_id
AND task.space_id = ?` — 每行两个字符串比较。空间公开后
ID 在顶部解析一次，都变成数字，并且查询永远不会触及
又是一个字符串。这是 `EXPLAIN` 输出是必需证据的查询
在第 12 节中。

### 9.5 碰撞重试 [阅读中文镜像](实体身份.md) 中的

`llm_call.go`中的`isDuplicateKey`没有说明哪个索引被违反，所以它
无法区分公共 ID 冲突（重新生成和重试）与真实冲突
唯一性冲突，例如重复的电子邮件或幂等性密钥（返回
不变）。它获得了一个索引感知的兄弟，可以读取索引名称
MySQL的`1062`消息，最多创建3次重试
`uq_<table>_public_id`单独。

生成在每个实体的 `internal/infra/db` 内移动。今天
`internal/service/artifact/service.go` 在商店上方铸造工件 ID，
这使得重试循环无法到达生成器。

## 10. API 合约

HTTP 资源拓扑不变。中的每条路径
[routes.go](../../../internal/server/handlers/routes.go) 和 `space`、`work`、
`artifact`、`admin` 和 `worker` 处理程序包保持其形状和
语义参数名称；仅参数的值格式发生变化。

```text
GET  /api/spaces/{space_id}/tasks/{task_id}
GET  /api/spaces/{space_id}/task-runs/{task_run_id}/trace
GET  /api/artifacts/{artifact_id}
POST /api/worker/task-runs/{task_run_id}/llm/completions
```

`public_id` 是数据库名称，从未出现在 JSON 中。一个资源代表
其自己的句柄为`id`；关系保留语义名称：

```json
{
  "id": "ivyoh5qcfu6ypfkhyedq",
  "space_id": "lzmomgl6mzg2bve3bgka",
  "conversation_id": "2l73h相应标识符6fcl7eecggda",
  "status": "SUCCEEDED"
}
```

这会重命名每个实体响应上的自处理字段 —
`task_id` → `id`、`task_run_id` → `id` 等 — 横跨 `internal/core/model`
JSON标签，`internal/server/websocket/protocol.go`，
`internal/infra/workerclient/api_types.go`、Portal 的 `lib/api/types.ts` 和
`lib/api/mappers.ts`和Desktop。关系字段如 `space_id` 和
`conversation_id` 不受影响。创建返回相关句柄的响应
以语义名称保存它；此更改不需要无关的
响应形状流失。

Agent 和工作流程修订响应丢失其 `id`：已识别修订
由其父级加上其修订号，以及 `POST .../revisions/{revision}/restore`
已经这样解决了。修订路径参数保持整数。

一个共享编解码器验证来自路径参数、查询参数和 JSON 的 ID
机构：

|输入|结果 |
|---|---|
|不是规范文本 | `400 Bad Request` |
|规范，名称无行| `404 Not Found` |
|规范，在调用者空间之外命名一行 | `404 Not Found` |

空间范围的查找首先解析空间的公共 ID，然后约束
资源由其公共 ID 和数字空格键组成，因此有效的公共 ID
无法成为跨空间的存在神谕。

访问令牌 `sub` 和运行令牌 `sub`、`tid`、`rid`、`kid` 继续携带
采用新格式的公共 ID。Worker路线仍然比较规范的`rid`
路线为 `task_run_id`。 `/api/webhook` 仍通过
webhook 秘密，永远不会使用密钥的公共 ID。

切换使每个访问令牌、刷新会话、运行令牌无效，
Portal 链接和书签。这就是没有双读的预期成本
路径，并且在 Alpha 中一次是可以承受的。

## 12. Alpha 转换

无兼容层，无双重读取，无混合格式。

Alpha 数据库和对象存储已重置。没有部署持有
任何人都需要的数据：本地参考环境是从头开始重建的
`./make kind down && ./make kind up`和`./make e2e local`拥有其Compose
一次运行时堆栈。因此，切换根本不会带来兼容性负担。

这就是重置而不是迁移成为正确仪器的原因。
`AutoMigrate` 无法表达这种变化——它是重命名、重新键入和
立即回填每个关系列 - 并将其写为
`schema_migration` 条目将编码数据形状，无需部署
保存，然后让该代码永远存在，不会给任何人带来好处。

`internal/infra/db/migration.go` 中的 `migrations` 列表是仅附加的，并且
它的三个现有条目（`0001`–`0003`）描述了一个不再
存在。它们会随着重置而被删除：保留它们会留下迁移
无法针对此二进制文件可以创建的任何数据库运行。

## 13.执行计划

六次堆叠变化，全部落地。各自编译，通过`./make test`，

### PR 1 — 编解码器

`internal/util/id.go` 增益 `NewPublicID`、`ParsePublicID`、`FormatPublicID`
并保留`NewPrefixedID`。其他一切都没有改变；没有呼叫者使用新的

- 测试：字母表、精确的 20 个字符长度、规范往返、拒绝
  非规范尾随位、不区分大小写的输入、错误的长度、空
  字符串、非字母字符和 `crypto/rand` 故障作为
  错误而不是恐慌。
- 断言 `WorkerJobNameForTaskRun` 的测试使 Base32 ID 保持不变。
- 检查：`./make test ./internal/util`、`./make check go`。

  中间有一张桌子。描述性的一半保留在 PR 6 中。

## 14. Measured Plans

五个查询命名的计划，从MySQL 8 转换后读回。
每个人最多通过其唯一索引解析一次句柄，然后连接
之后在行键上。

|查询 |访问路径 |
|---|---|
|配额：运行计数 | `idx_task_space_created`（`ref`，覆盖）上的 `task`，然后 `idx_task_run_task_created`（`ref`，覆盖）上的 `task_run` |
|配额：头衔代币| `idx_task_space_created` 上的 `task`（`range`，索引条件）|
| Space 任务列表 | `idx_task_space_created` 上的 `task` 作为**向后索引扫描** — 无排序 — 然后所有六个连接 `PRIMARY` 上的 `eq_ref` |
| Conversation 消息 | `uq_conversation_public_id`（`const`，覆盖）上的 `conversation`，然后 `idx_conversation_message_conversation`（`ref`）上的 `conversation_message` |
| Run 输出读取 | `uq_conversation_public_id` (`const`) 上的 `conversation`，然后是 `user`、`task`、`task_run`、 `task_run_artifact` 各上一键|

该表中的三件事是转化本身的回报。任务清单
通过向后读取其复合索引而不是对行进行排序来排序，这
单列`space_id`索引留下的字符串模型做不到。
两个配额查询均仅从索引中得到答复 - `Using index`，无行
读取 — 因为 `bigint` 空间参考适合其中一个。每一次加入都是
`eq_ref` 在主键上，这就是使列表成为一个查询而不是
每行一个查询。

每个查询句柄只出现一次，作为对唯一的 `const` 查找
索引超过`BINARY(12)`。这是执行计划中的翻译边界：
在根处进行一次索引查找，其后到处都是数字。

## 17. 修正：文本形式是存储形式（2026-08）

D2 最初将原始 12 字节存储在 `BINARY(12)` 中并生成文本
仅在 Go 中形成。存储条款颠倒：`public_id` 为
`char(20) CHARACTER SET ascii COLLATE ascii_bin`，恰好持有20
每隔一个边界已经显示小写字符。叙述的部分
原始转换（§5 的原始 DDL、§6.1、§13、§14）保留记录
该工作已执行；如果他们说 `BINARY(12)`，则适用此修正案。

反转是一个操作参数，与
在§4.2中选择了base32而不是base64url：格式遵循ID到每个地方
它已被读取。最初的决定权衡了存储宽度，但从未定价
可读性。实际上，数据库是人们读取 ID 的地方之一 -
在每次调试和支持会话期间，`SELECT` 位于 MySQL 客户端中 - 以及
`BINARY(12)` 将每个句柄渲染为不可读的斑点。的
首先尝试替代方案 - 手动安装的存储函数，在中执行 base32
SQL，`HEX()` 每个查询的包装器 - 在每个查询之前放置一个翻译步骤
直接查询永远。存储文本会删除翻译边界
存储一半； `lookupKey` 仍然规范化输入，但什么也没有
在出去的路上转变。

最初决定购买的内容以及保留的内容：

- **宽度。** 每个值 8 个字节，位于列及其唯一索引上。在此
  项目的行数是噪音；它从未被视为一种约束。
- **memcmp 身份。** 保留，由 `ascii_bin`：比较是字节相等，否
  大小写折叠，无排序规则扩展。 §1 对字符串同一性的反对
  针对的是 `utf8mb4` 通用排序规则，而不是固定宽度的 ascii_bin
  带有封闭字母的列。
- **每个值一个拼写。** 保留，现在更重要：编解码器的
  每次写入之前都会强制执行规范形式（小写，零松弛位）
  和查找，因此唯一索引只看到一种拼写 - 其中松懈
  store 会让一个值的十六种拼写作为不同的行共存。

编解码器结果在 §4.3 中：没有调用者持有字节，
`ParsePublicID`/`FormatPublicID` 折叠为 `CanonicalPublicID`。的
强制执行 `binary(12)` 的架构测试现在强制执行
`char(20) CHARACTER SET ascii COLLATE ascii_bin` 和 `string` 字段。

现有数据库不会迁移，符合 D8 和 §16 的重置答案：
目前还没有正式部署，本地环境
重新生成（`./make kind down && ./make kind up`，或删除 Compose
量）。预修改数据库在第一次读取 `public_id` 时失败；
重新创建它。
