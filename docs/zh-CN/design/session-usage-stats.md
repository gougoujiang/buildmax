## 1. 问题

BuildMax 几乎已经记录了所有值得了解的运行成本与行为信息，但这些记录彼此分离。`-p` 页脚只展示其中一小部分；Portal 则展示单个 TaskRun 的追踪摘要和调用账本。用户使用一周后想知道的问题仍无人回答：费用花在了哪里、哪个工具最占上下文、提示词缓存是否真正节省成本、总耗时中模型与本地工具分别占多少。

其中两类记录还以相同方向统计错误，详见 §3。
## 2. 决策

提供一个 **统计信息**视图：在本地界面中，按会话只读汇总现有的会话与追踪记录。入口为 `buildmax info`，以及 TUI `/info` 浮层中的 session 标签页。

统计视图只是读取器。除可重建的投影视图外，它不引入任何持久状态，也不改变运行方式。需要但尚未记录的数字，应修复其记录路径，而不是在读取器中用启发式方法估算。

三个来源各有不同契约，必须保持区分：

- **会话文件**是 Token 与成本的权威来源。这些值按每轮当时生效的费率累计；读取时不重新计算，因为使用当前配置推导历史总额，会用新价格重述已经按旧价格付费的回合。它也是单工具结果字节数的唯一来源：通过 `tool_call_id` 关联回发起调用的助手消息得到。
- **运行追踪**是所有时间类数据的权威来源，也保存会话文件从未记录的单次运行细节：持续时间、拒绝、故障类型、所用模型，以及委派任务的工作量。
- **托管调用账本**（`llm_call`）是唯一能看到某个界面发出的每次 HTTP 调用的数据源。它仍归 Portal 所有；基于它进行 Space 级分析不在本记录范围内，因为那是不同的问题和授权边界。[提示词缓存控制](prompt-cache-control.md) §6 已勾勒它所属的支出视图。

这些来源不会被合并成一个数字，因为它们完全可能合理地不一致：例如，一次运行在写入 `run_end` 前被终止，它会计入会话总额，却不会出现在追踪汇总中。如果只展示一个混合数字，读者将无法发现这种差异。
## 3. 为此实施的计量修复

构建该视图时发现会话自身的总额存在两个缺口。两项问题都在视图交付前修复，因为发布一个按项目自身诚实性规则判断为错误的数字，比不发布数字更糟。

1. **子 Agent 运行未被计入。** 子 Agent 运行器调用 `agent.RunLoop` 后丢弃了返回的 `RunStats`，因此父会话的 Token 与成本没有包含任何 `Task` 委派。现在，子运行会把自己的总额报告给父循环安装在 Context 上的 `DelegatedUsage` 累加器；循环在每次迭代后读取并清空它，因此回复、取消、错误、达到迭代上限等所有退出路径都会报告相同口径的总额。数据通过 Context 传递，而不是扩展工具接口，因为委派对循环而言只是普通工具调用；若仅为了一个工具报告费用而扩展 `llm.Tool.Execute`，就会把计费职责扩散到注册表中的每个工具。

   运行总额因此改为**包含子运行**，`RunStats.Delegated` 则给出其中的委派明细——关系与提示词 Token 总数及其中缓存 Token 数相同。工具调用次数是例外，需要额外相加：委派本身算父运行的一次调用，子运行内部的调用不会在其他地方重复计数。

2. **压缩调用此前完全没有计量。** `LLMCompactor.Compact` 直接调用客户端，处在循环事件流之外，因此既不贡献 `RunStats`，也没有追踪记录，只有一个表示压缩发生的 `context_compacted`。现在 `ContextCompactor.Compact` 返回 `llm.Usage`，循环像其他调用一样计算其价格，并把成本记录在现有的 `context_compacted` 事件中，而不是伪造一个 `llm_end`：压缩确实是本次运行付费的调用，但它不是一轮对话；将其报告为对话轮次，会在追踪中虚构一条会话里从未出现的回复。

同时修复了两个相关问题：

3. **子 Agent 追踪无法访问。** 运行器原先会创建临时会话，返回后立即丢弃，而追踪文件却存放在这个临时会话 ID 下，形成任何会话都无法引用的目录。现在子 Agent 追踪归档在父会话下，通过 `is_subagent` 区分，并用 `parent_run_id` 关联。自[本地会话存储](local-session-storage.md)实施后，子 Agent 拥有自己的隐藏会话包，但追踪仍应归属于父会话。

4. **失败的工具调用不可见。** 循环原本已经区分故障并触发 `PostToolUseFailure`，但在任何持久记录看到错误前，就把它展平为 `error: …` 结果文本。现在 `tool_end` 会记录 `error_kind`。这里使用分类而非布尔值，因为不同类别含义不同：`invalid_args` 表示模型误用了工具，`panic` 始终表示缺陷，`tool_error` 则表示环境或工具自身错误。每个 `tool_start` 现在都对应一个 `tool_end`；这与既有语义一致，因为即使调用被拒绝也会发出 `tool_start`，它表示“模型发起了这次调用”，而不是“执行已经开始”。

**`error_kind` 只表示调用未完成，绝不表示任务完成但结果不理想。** 命令以非零状态退出仍属于成功完成的 `Bash` 工具调用：工具会有意返回可读消息和 `nil` 错误。把该字段直接解释成任务失败率，会遗漏最差的运行，因此 CLI 将它标记为“未完成的调用”，并以折线趋势展示。

标题生成调用原本就已经纳入计量，因此上述不一致很容易被忽略。

## 4. 代码位置

- `core/session.Stats` 汇总已存储的历史。它是纯函数，只接收 `*Session`，不要求运行仍处于活动状态，因此即使追踪已经丢失也能回答会话统计。
- `infra/trace.SummarizeSession` 汇总会话记录的每次运行。追踪记录器拥有 `<traces>/<session_id>/<run_id>.jsonl` 布局，因此该函数也归这一层负责。
- `agentapp.LoadSessionStats` 合并两者。`agentapp` 同时拥有两个目录，并且是唯一允许组合它们的层；`internal/service/*` 属于服务器域，不适合承担这项职责。架构测试强制 core 不得导入 infra，因此组合逻辑也不能向下漂移。
- `interface/cli` 提供两种渲染：带 `--json` 的 `buildmax info [session-id]`，以及 TUI 的 `/info` 浮层。两种布局有意分开，因为几十列宽的框式浮层与完整终端需要不同形式；但数据与注意事项列表共享，因为每个界面可以作出的声明必须一致，若警告只出现在其中一个界面，就不值得信任。面板汇总的是**实时**会话而不是磁盘文件，因为会话会在每次助手回复后持久化，执行中途重新读取文件只会得到上一轮的结果。

## 5. 诚实性规则

这些不是新规则，只是把现有约定应用到一个专门展示数字的视图：

- 未测量的量应缺失，而不是显示为零。提供商没有报告缓存用量，并不表示缓存未命中，因此完全不显示缓存行。
- 会话中没有任何模型配置价格时，应明确说明，而不是显示 `0.000000`。
- 部分总额必须标明不完整：设置 `cost_incomplete`，并警告哪些运行从未写入结束记录。
- 只有 `Baseline > Total` 时才报告节省。如果某次运行只写入缓存条目，其成本反而高于不使用缓存，界面应如实说明。
- 父运行与委派运行的支出必须正确相加，并展示拆分；不能只显示一个暗中代表较小范围的数字。
- 并行工具执行可能使工具耗时之和超过墙钟时间，此时不展示模型/工具耗时拆分，而不是显示负数的模型耗时。

## 6. 开放问题

- **跨会话汇总。** 回答“本周花费多少”，并按工作空间、模型和日期分组。预期做法是在 `sessions/index.json` 的行上增加小型投影，并在每轮已有的元数据写入时更新。该文件明确可重建，因此错误值可修复，无需迁移。此项是主动推迟，并非受阻。
- **按轮记录。** 这可以去除对追踪的依赖，使会话自包含。[本地会话存储](local-session-storage.md) 已交付，因此现在已有合适位置：`meta.json` 保存累计总额，按轮明细应与它相邻，而不是再从日志中反向汇总。
- **追踪保留。** 当前不会清理会话的 `traces/`。统计既是制定保留策略的理由，也会受到该策略影响；在保留策略确定前，视图只能显式降级，不能静默给出不完整结果。
- **缓存诊断。** 当[提示词缓存控制](prompt-cache-control.md) §6 要求的请求模式、能力、策略和结果字段进入追踪后，缓存区域应报告已记录结果，而不是根据计数推断。
- **Desktop。** 所需绑定不超出当前汇总已经暴露的数据，尚未实现。
- **Worker 运行按设计不贡献本地统计。** Worker 在运行级 `BUILDMAX_HOME` 中组装。这是正确行为——Worker 支出属于托管调用账本——此处明确记录，以免使用时才意外发现。
