## 1. 决策

在统一的 Artifact 对象之上新增两项能力，二者彼此独立：

1. **预览。** 任何一个 Space 成员本来就能读取的 Artifact，现在都能在
   Portal 内获得一个渲染后的视图。Markdown 会被渲染成格式化文本；HTML 会
   在一个沙箱化的框架里以真实页面的形式呈现；图片和纯文本保留现有的内联
   视图；其余类型仍然只能下载。这不需要任何新的授权——它只是把调用方本来
   就有权获取的内容，呈现得更好而已。

2. **公开分享。** 一个 Artifact 可以被赋予一个显式的、可撤销的公开链接，
   任何没有 BuildMax 账号的人都能打开它。打开链接会落到一个 Portal 页面上，
   该页面渲染预览内容并提供下载。这是按 Artifact 逐个开启的选项，绝不是
   规范 ID 本身自带的属性，也绝不会默认开启。

公开链接是一个**存储在数据库里的、可撤销的分享令牌**，不是无状态的签名
URL，也不是对象存储的预签名 URL。令牌本身是高熵的随机数据；系统只存储它的
哈希值，连同创建者、过期时间、撤销时间和检索次数一起保存。这正是《统一
工件》§6.2 早就设想好的模型；变化的只是它从“暂无计划”变成了真正落地。
选择存储式令牌而不是自验证的 HMAC/JWT，原因在于撤销：一个无状态令牌如果
没有服务器端的拒绝名单，就无法在到期之前被收回——而这恰恰是 §13 否决预签名
URL 方案的同一个缺陷。一个签名 URL 能提供的其他一切特性——公开可访问、
会过期、无需登录、无需会话即可校验——存储式令牌同样都能提供，而且还额外
带来了集中撤销和使用记录。

这个对外可达的链接由**服务器**渲染，来自服务器所配置的一个新的公开
base URL。worker 永远不会得知或构造这个公开地址；它没有这个地址，而且
它自己的 `worker.server_url` 本来就被刻意设计成一个集群内部的监听地址。
服务器同时持有分享记录和公开 base URL，是唯一有能力命名这个链接的地方，
因此这件事也就理所当然由它来做。

## 2. 产品目标

一个 Agent 为某个人写了一份文件——最常见的是一份 Markdown 文档，有时是一个
HTML 原型——并希望把一个“打开即可用”的链接交给对方：

- 打开链接就能直接看到渲染后的内容，不需要先下载再打开这一道弯路；
- 对于一个 HTML 原型，打开链接看到的是真正在运行的页面，而不是它的源代码；
- 在需要的时候，这个链接可以发给 Space 之外的人；
- 所有者之后可以撤销这个链接，并能看到它是否被打开过。

接收方不需要账号，也不需要了解 Space、Artifact 或存储键这些概念。这个链接
在过期或被撤销之前会一直有效。

## 3. 本文重新打开了什么

《统一工件》当初刻意关闭了对外分享的能力，并列出了如果要重新打开这道口子，
必须先解决哪些问题（其 §10 第 3 阶段）：获批的角色、过期时间的默认值、
可撤销的令牌、匿名访问、恶意软件扫描、审计留存期限。本文针对产品现在真正
需要的这一切片，逐一给出答案：

- **获批的角色**——见本文 §10。
- **过期默认值**——见 §9（`BUILDMAX_ARTIFACT_SHARE_TTL`，有上限的默认值）。
- **可撤销的令牌**——见 §5，`artifact_share` 行及其 `revoked_at` 字段。
- **匿名访问**——见 §6，无会话的 `/shared/artifacts/{token}` 路由。
- **恶意软件扫描**——仍然不在范围内，仍然由运维者自行决定；见 §4.2。分享
  能力不会改变上传本身接受哪些内容。
- **审计留存**——见 §10，在现有的仅存元数据的审计轨迹上新增分享创建/撤销/
  检索事件。

本文并不会开启“默认公开托管”“跨组织身份”，也不会改变规范 Artifact ID 本身
授予的权限。这些内容仍然不在范围内。

## 4. 范围

### 4.1 范围之内

- 一条 `artifact_share` 记录：对应一个 Artifact、一个哈希化的公开令牌、
  创建者、可选的过期时间、撤销时间、检索次数。
- 无会话的公开 API 路由，负责把一个分享令牌解析为元数据和内容，并拒绝已
  撤销或已过期的令牌。
- 一个无需登录即可访问的 Portal 公开预览页面，渲染被分享的 Artifact 并
  提供下载。
- Markdown 与 HTML 的预览渲染，由已认证的详情页和公开页面共用同一套实现。
- 给 `UploadArtifact` 增加一个选项，让 Agent 能一步完成“发布文件并拿到
  公开链接”，此外再提供一个独立的操作，用来为已存在的 Artifact 创建或
  撤销链接。
- 服务器端的公开 base URL 配置，以及让服务器把链接渲染进工具输出和 API
  响应里的相应管线。
- 谁有权创建和撤销一次分享的授权规则，以及相应的审计事件。

### 4.2 范围之外

- 默认公开访问：规范 ID 及其 `/api/artifacts/{id}` 路由仍然要求 Space
  成员身份。分享是一项独立的、增量式的授权，而不是替代它。
- 跨组织的已认证分享（即带账号的、指名道姓的外部用户）。本次这一切片只做
  匿名链接。
- 上传时的恶意软件扫描、DLP 或 MIME 限制——运维策略保持不变；分享暴露的
  就是上传本来就已经接受的那些字节，不多不少。
- 密码保护的链接、按收件人区分的链接、超出“检索次数”之外的查看分析，以及
  水印。
- 编辑已分享的 Artifact：内容始终保持不可变，因此一份修正过的文件就是一个
  新的 Artifact 和一个新的链接。
- 服务器端渲染 HTML 预览（即由服务器把 Markdown 转成 HTML）。渲染工作在
  Portal 一侧的客户端完成；服务器只负责用安全的响应头提供原始字节。

## 5. 领域模型

### 5.1 `artifact_share`

一次分享是它自己独立的一条记录，而不是 `artifact` 表上的一列。一个
Artifact 可以同时拥有多个存活中的链接（比如一个短期的和一个长期的），
每个链接都可以独立撤销，而 Artifact 本身那一行数据保持不变。

```go
type ArtifactShare struct {
	ID              uint       `json:"-"`
	ShareID         string     `json:"share_id"`     // opaque public handle for management
	ArtifactID      string     `json:"artifact_id"`  // the shared artifact's public handle
	SpaceID          string     `json:"space_id"`      // denormalized for authz and listing
	TokenSHA256     string     `json:"-"`            // sha256 of the token; the token itself is never stored
	CreatedByType   string     `json:"created_by_type"`
	CreatedByID     string     `json:"created_by_id"`
	ExpiresAt       *time.Time `json:"expires_at,omitempty"`
	RevokedAt       *time.Time `json:"revoked_at,omitempty"`
	RetrievalCount  int64      `json:"retrieval_count"`
	LastRetrievedAt *time.Time `json:"last_retrieved_at,omitempty"`
	CreatedAt       time.Time  `json:"created_at"`
}
```

这个令牌沿用了代码库里现成的不透明凭证模式（`login_code`、
`user_refresh_token`、`workspace_webhook_key`）：一个前缀加上
`crypto/rand` 生成的字节、十六进制编码，只交给调用方一次，此后只以其
SHA-256 哈希的形式存储。一个前缀（例如 `share_`）能让一旦泄露的令牌方便
被 grep 出来，也方便密钥扫描工具识别它。解析一个链接只是一次基于
`token_sha256` 的索引查找；这里没有逐请求的签名校验，因为它本来就没有
签名。

`internal/infra/db` 中的 `xxxShareRow` 结构体才是 schema 的事实来源，遵循
[《数据模型》](../contribute/architecture/data-model.md)所定的规则。它在
`token_sha256` 上有唯一索引，在 `(space_id, created_at)` 上有索引，服务于
管理列表页。`artifact_id` 以内部的 `uint64` 外键形式存储（就像
`artifact.space_id` 一样），并通过读取投影，以公开句柄的形式对外暴露。

### 5.2 与 Artifact 的关系

一次分享指向一个存活中的 Artifact。删除（打上墓碑标记）该 Artifact，会让
每一个指向它的分享都解析出与规范路由相同的 404——分享的查找逻辑会关联
Artifact 并检查它的 `DeletedAt`。保留策略清除字节数据时也是同样的效果：
一个指向已被清除 Artifact 的分享会直接消失，而不是变成一个指向缺失内容的
悬空链接。撤销一次分享则完全不会影响 Artifact 本身。

## 6. 公开 URL 与路由

### 6.1 对外分发的链接

公开链接是给人看的，所以它不带 `/api` 前缀。整个公开界面都放在一个专用的
顶级命名空间 `/shared/` 之下，紧跟着资源类型作为下一段——
`/shared/artifacts/…`——这样将来如果要分享 Issue 或 Conversation，就是一个
平级的新增（`/shared/issues/…`），而不是特例；这个命名空间也永远不会与
应用自身的 `/artifacts` 资源路由冲突，即使后者未来真的改成基于路径的形式：

```text
<public_base>/shared/artifacts/{token}          # the link the agent cites — opens the rendered preview
<public_base>/shared/artifacts/{token}/raw      # the bytes (?dl=1 forces a download)
```

`public_base` 是该部署对外可达的源（见 §9）。打开
`/shared/artifacts/{token}` 会落到一个渲染后的预览页面，而不是原始字节的
转储；页面上的下载按钮以及任何内嵌的 `<iframe>`，指向的都是
`/shared/artifacts/{token}/raw`。令牌放在路径里，而不是查询字符串里，
这样它就不会像 `?token=` 那样，通过 `Referer` 请求头或查询字符串访问日志
泄露出去。

之所以要区分这两条路径，是因为当 Portal 和 API 在反向代理背后共用同一个
源时，这样才能让命名空间保持可路由——这也正是应用自身的路由要带上 `/api`
前缀的原因。反向代理把这两个具体的叶子路径转给后端，其余的裸令牌路径则
留给 SPA 自己处理：

```text
location ~ ^/shared/artifacts/[^/]+/(raw|meta)$  ->  API backend   # bytes and metadata
location /shared/                                 ->  Portal SPA    # the preview page
location /api/                           ->  API backend   # the authenticated app, unchanged
```

在源分离部署下（Portal 跑在 nginx 上，API 跑在 Go 服务器上，正是 Compose
今天的运行方式），同样这几条路径会分别解析到各自的源上，不需要额外的规则；
`public_base` 就是它们对外统一呈现出来的那个源。

### 6.2 公开路由——无会话、只认令牌

三条匿名路由，只靠令牌授权，不经过 `access.Guard`：

```text
GET /shared/artifacts/{token}        # the preview page (Portal SPA; renders per §7)
GET /shared/artifacts/{token}/meta   # JSON metadata the page needs: filename, media type, size, title
GET /shared/artifacts/{token}/raw    # the bytes — inline-previewable per §7, or an attachment with ?dl=1
```

`/meta` 和 `/raw` 解析令牌的方式，与 `worker.requireRunToken` 在守卫之外
解析运行令牌的方式相同：查哈希值，对缺失、已撤销或已过期的分享一律返回
`404`（绝不是 `403`，也绝不区分“已撤销”和“从未存在过”——一个令牌不应该
成为判断资源是否存在的探针，这与规范路由“不可枚举”的规则是一致的）。
一个有效的令牌会取得对应的 Artifact，其内容通过与已认证内容处理器完全相同
的代码路径流式传输出去。`/shared/artifacts/{token}` 这个页面本身是静态的
SPA HTML，不携带任何秘密信息；它从自己所在的 URL 里读取令牌，再去调用
`/meta` 和 `/raw`。

### 6.3 分享管理——需要认证

创建、列出和撤销一个链接，是由已登录成员或某次 Agent 运行执行的应用内
操作，而不是匿名访客能做的事，所以它货真价实是一个 API 界面，保留 `/api`
前缀：

```text
POST   /api/artifacts/{artifact_id}/shares              # create a link (returns the token once)
GET    /api/artifacts/{artifact_id}/shares              # list this artifact's live links
DELETE /api/artifacts/{artifact_id}/shares/{share_id}   # revoke
```

这几个接口都会先解析出目标 Artifact，读取它所在的 Space，再依据 §10 的
规则要求调用方具备相应角色——用的是与规范 ID 路由相同的
`MemberOfResourceSpace` 结构，只是在创建/撤销操作上叠加了一层角色检查。

## 7. 内容分发与预览

### 7.1 渲染矩阵

预览功能是一个基于存储、由服务器验证过的媒体类型的白名单，绝不依赖浏览器
自己的猜测。它由已认证的 `#/artifact/{id}` 详情页和公开的
`/shared/artifacts/{token}` 页面共用——一套渲染器，两个入口。公开页面从
路径里读取自己的令牌（一个由 SPA 兜底路由处理的、干净的非哈希 URL），
而不是从 `#` 片段里读取。

| 媒体类型 | 预览效果 | 实现机制 |
|---|---|---|
| `text/markdown` | 渲染后的 Markdown | `react-markdown` + `remark-gfm`，Portal 中已在使用；**不加 `rehype-raw`**，所以嵌入的 HTML 会被转义而不是被执行 |
| `text/plain` | 纯文本 | 现有的 `<pre>` |
| `image/*`（白名单内） | 图片 | 现有的 `<img>` |
| `text/html` | 实时页面 | 沙箱化 `<iframe>`（见 §7.2） |
| 其余所有类型 | 仅提供下载 | 附件 |

Markdown 是在 Portal 自己的源上渲染的，之所以安全，正是因为
`react-markdown` 默认不会执行嵌入的 HTML 或 `javascript:` 链接（它的
URL 转换逻辑会直接丢弃它们）。我们不会加入 `rehype-raw` 或
`dangerouslySetInnerHTML`。如果将来需要语法高亮，那是后续可以增量添加的
插件，不会改变这里的安全论证。

### 7.2 HTML 预览的安全性

在这里，真正危险的部分是提供 Agent 或用户编写、且会运行脚本的 HTML 内容，
《统一工件》§6.3 也正是因为这一点才强制要求 HTML 只能下载。本文针对预览
这一特定场景，在一个具体的安全模型下解除了这条限制，而不是全面放开。

具体机制是一个不透明来源（opaque-origin）的沙箱，由两层共同强制执行：

1. **响应头。** HTML 内容会带着
   `Content-Security-Policy: sandbox allow-scripts allow-popups allow-forms;`
   这样的响应头提供（不带 `allow-same-origin`）。CSP 的 `sandbox` 指令
   即使在*直接导航*到这个 HTML 响应的情况下，也会把它放进一个独一无二的
   不透明来源里，因此一个共享原型里的脚本无法读取 cookie、
   `localStorage`，也无法向 BuildMax 发起同源请求——不管它是被嵌入
   iframe，还是在自己独立的标签页里打开。`nosniff` 依然保留。
2. **frame 属性。** Portal 用
   `<iframe sandbox="allow-scripts allow-popups allow-forms">` 来嵌入这份
   内容——同样不带 `allow-same-origin`，正是这一点才能防止这个 frame
   触达 Portal 自己的令牌存储。`allow-scripts` 和 `allow-same-origin`
   一旦同时出现，文档就能自己解除自己的沙箱，所以这两者绝不会同时使用。

给在意纵深防御的运维者留了一条路：由于 `public_base` 可以是一个与 API
和 Portal 都不同的独立源，一次部署完全可以从一个专门的、不承载其他任何
内容的“内容源”来提供被分享的内容，就像大型厂商把用户内容隔离在单独域名下
一样。这个设计并不要求一定要有第二个源，但也没有任何地方阻止这么做，配置
本身也留出了把内容指向另一个源的空间。

SVG 仍然只能下载。它和 HTML 一样是一种可执行的活动文档，但比起作为页面
查看，它被嵌入使用的场景要常见得多；而且一个用 `<img>` 嵌入的 SVG 根本
拿不到 frame 沙箱的保护。要不要把它当作可以安全预览的类型，是留给 §14 的
一个独立问题。

### 7.3 下载

下载功能使用现有的安全内容处置（content disposition）方式，同时提供两种
文件名形式（ASCII 加 RFC 5987），数据均来自已存储的元数据。在
`/shared/artifacts/{token}/raw` 上加 `?dl=1`，即使对一个本可预览的类型，
也会强制使用附件处置方式，这样无论是公开页面上的下载按钮，还是一个直接
分享出去的链接，拿到的都是保存文件，而不是渲染页面。

## 8. Agent 工具契约

### 8.1 带链接发布

`UploadArtifact` 新增一个可选参数，让“写一份文档、把链接交给用户”这个
最常见的 Agent 流程，能够一次调用就完成：

| 参数 | 是否必填 | 规则 |
|---|---|---|
| `path` | 是 | 不变 |
| `title` | 否 | 不变 |
| `purpose` | 否 | 不变 |
| `share` | 否 | 为 true 时，服务器会同时创建一个公开链接并把它返回；默认 false |

默认值为 false，延续了《统一工件》§4.2“默认不公开”的原则：除非 Agent 本身
或其配置显式选择开启，否则发布出来的内容都是私有的。当 `share` 为 true
时，工具的返回结果会附上公开的 Portal 链接及其到期时间：

```text
Published newton.md as artifact tuiowdqwjwwmyxcnvo3a (5123 bytes).
Public link (expires 2026-10-05): https://buildmax.example.com/shared/artifacts/share_9f...c1
Download: https://buildmax.example.com/shared/artifacts/share_9f...c1/raw?dl=1
Cite the public link in your final answer so the person can open it.
```

发布者端口（`tool.ArtifactPublisher`）会扩展出携带 `share` 这一意图并
返回链接的能力；两个适配器（供已登录本地会话使用的
`internal/interface/client`，以及供 worker 使用的
`internal/infra/workerclient`）都会把这个意图传给服务器，再由服务器——
唯一持有 `public_base` 的一方——负责把 URL 填进去。两个客户端都不会自己
去构造这个公开地址。

### 8.2 为已存在的 Artifact 分享

还有一项独立的能力，用来为一个已经存在的 Artifact 创建或撤销链接，覆盖
“先有文件、后决定要不要分享”这种情况。这究竟应该是一个独立的运行时工具
（`ShareArtifact`），还是只做成一个 Portal 操作，是留给 §14 的开放问题；
不过 §6.2 里的 API 两者都支持，而 Portal 这一侧的操作无论如何都在本文的
范围之内。

## 9. 配置

新增一项服务器端配置值，在 `internal/config/env_spec.go`（bootstrap 环境
变量的事实来源）和 `ServerConfig` 中声明：

- **`BUILDMAX_PUBLIC_BASE_URL`**——人们用来打开 BuildMax 的、对外可达的
  base 地址（可能是 Portal 的源，也可能是单一源反向代理部署下那个共用的
  源）。服务器会用它来渲染分享链接。如果没有设置这个值，创建分享的请求会
  被拒绝并给出清晰的错误，而不是发出一个打不开的内部 URL——本文要避免的
  正是这种“链接谁都打不开”的问题，所以服务器宁可不发出一个自己都无法
  确认能公开访问的链接。

这个值刻意不从 `worker.server_url`（一个被校验过、确保*不是*公开端口的
集群内部监听地址）推导出来，也不从 `BUILDMAX_SERVER_URL`（进程用来*连接*
服务器的地址，而不是它对外宣称的地址）推导出来。`BUILDMAX_CORS_ORIGIN`
已经为 CORS 目的命名了 Portal 浏览器的源；新的这个值在单一源部署下可能与
它取值相同，但二者关注的是两件不同的事（渲染链接 vs. 允许哪些请求来源），
因此分开声明。

分享 TTL 的上限：

- **`storage.artifact_share_ttl_hours`**（server.yaml）——分享链接的默认
  与最大生命周期，有一个上限的默认值（30 天，与刷新令牌的有效期一致）。
  创建请求可以要求更短的时限，但绝不能要求更长。它只以配置文件项的形式
  发布，没有早期草案里提到的环境变量覆盖：公开 base URL 是一个部署在
  运行时注入的值，而 TTL 则是运维者只需要写一次的策略。

单文件大小上限、Space 存储配额和保留清扫这些机制都不受影响；一次分享本身
不占用任何独立的字节存储。

## 10. 授权、治理与限制

分享是一项由 Space 权限控制的操作。首个切片的矩阵是对《统一工件》§8（当时
把创建分享标记为“暂不支持”）的扩展：

| 操作 | Member | Admin | Owner | Space 之外 | 持令牌的匿名者 |
|---|---:|---:|---:|---:|---:|
| 为一个 Artifact 创建分享 | 是¹ | 是 | 是 | 否 | — |
| 撤销一个分享 | 仅自己创建的² | 是 | 是 | 否 | — |
| 列出某个 Artifact 的分享 | 是 | 是 | 是 | 否 | — |
| 打开分享的内容 | — | — | — | — | 是，直到过期/被撤销为止 |

¹ 一个 Member 可以分享自己能读取的 Artifact。如果某个部署需要把分享权限
收紧到只有 Admin/Owner 才能操作，那属于 §14 里提到的一种有界的收紧调整；
目前这个宽松的默认值，契合的是“Agent 把链接交给自己的操作者”这一产品
目标。² 一个 Member 可以撤销自己创建的分享；Admin 或 Owner 可以撤销任何
分享。

一个 Agent 或 worker 通过 `UploadArtifact(share=true)` 创建分享时，用的是
其所在运行自身的身份。运行令牌本来就携带着 `UserID`/`SpaceID`（见
《Worker 运行令牌》），所以一次由 worker 创建的分享，会把发起该运行的用户
记录为创建者，把对应 Space 记录为所有者——这个分享是可追溯来源的，创建时
并不匿名。Agent 只能创建链接，不能撤销或列出别人创建的链接。

审计事件（仅存元数据）会记录在现有的审计轨迹上：**分享创建**、**分享
撤销**，以及**分享过期**（像 Artifact 过期一样，按每次分享单独记录，因为
这是一次没人主动请求、但确实发生了的状态变化）。每次检索会让计数加一并
更新 `last_retrieved_at`；单次检索本身**不会**逐条写入审计——那属于用量
分析的范畴，而审计轨迹是用来记录权限变化的。审计记录中永远不会包含令牌
本身；§8 里“签名 URL 和分享令牌都不进入审计轨迹”的规则没有变化，现在只是
多了一个具体的令牌需要被排除在外。

删除与保留策略的优先级高于分享：一个被打上墓碑标记或被清除的 Artifact，
它所有的链接都会解析为 404，不需要另外单独执行一次撤销操作（见 §5.2）。

## 11. 失败语义

- **在没有配置 `public_base` 的情况下创建分享**→拒绝并给出有意义的错误；
  不发出任何链接。工具会如实报告这一点，这样模型就不会引用一个根本打不开
  的 URL。
- **令牌解析到一个已撤销/已过期/已删除的 Artifact**→返回 404，与一个
  从未存在过的令牌得到的结果没有区别。
- **在组合调用 `UploadArtifact(share=true)` 中，Artifact 上传成功之后，
  创建分享这一步失败了**→Artifact 依然会被创建，其 ID 也会正常返回；
  工具会同时报告这个 Artifact 和一个“分享创建失败”的错误，而不是让整个
  上传失败，也不会假称存在一个实际不存在的链接。上传和分享是两次独立的
  提交；分享失败绝不会回滚已经持久化的内容。
- **写入检索计数失败**→内容依然照常提供；这个计数器只是尽力而为的遥测
  数据，不是能否交付内容的门槛，一次失败的计数递增只会被记录到日志里，
  不会呈现给下载者。

## 13. 被否决的备选方案

### 无状态的签名（HMAC/JWT）下载令牌

用现有的 `JWTSecret` 对 `artifact_id` 加上过期时间铸造一个 HS256 令牌，
在一个完全没有数据库记录参与的无会话分支里校验它——这是能想到的最轻量的
实现，完全复用 `authtoken` 现成的模式。之所以否决它作为主要机制，是因为
一个无状态令牌如果没有服务器端的拒绝名单，就无法在到期之前被撤销——而这
又会重新引入存储式令牌本来就要付出的那份存储成本；而且它也没办法在不往
URL 里塞进过多声明的前提下，携带检索次数或每个链接各自的创建者信息。在
确实不需要撤销能力的场景下，它是正确的工具；但“把文件分享给 Space
之外的人”这件事，恰恰就是“我发错人了，赶紧把链接杀掉”必须能生效的场景。
存储式令牌的代价只是一次索引查找，换来的是撤销、列表和审计能力。

### 对象存储预签名 URL

被否决的理由与《统一工件》§13 给出的一致：它绕开了 BuildMax 自己的授权
体系，无法被集中撤销，把一个已经保存下来的链接和具体的对象存储配置绑死，
而且各家提供商的实现也各不相同。让服务器在自己的令牌之后流式传输字节，
才能让这套契约在本地文件系统和 S3/MinIO 之间保持可移植。

### 默认公开的 Artifact ID

让 `/api/artifacts/{id}` 对任何持有该 ID 的人都可读。被否决：规范 ID
只是一个标识符，不是凭证（见 §6 的“不可枚举”原则），而且《统一工件》§4.2
已经排除了“默认公开托管”这条路。分享必须是一个显式的、可撤销的、增量式的
动作。

### 同源渲染 HTML 预览

在 Portal 或 API 自己的源上渲染 HTML（比如用带 `allow-same-origin` 的
iframe，或者直接用 `dangerouslySetInnerHTML`）。被否决：一个被分享的原型
可能包含任意脚本，而同源执行会把 Portal 的令牌存储、以及 API 那个“不靠
cookie 但依然真实存在”的界面都暴露给它。正是这个不透明来源的沙箱
（见 §7.2），才是 HTML 能够被预览的全部前提。

### 由 worker 构造公开链接

让 worker 像渲染今天的内部地址一样，自己渲染分享 URL。被否决：worker
根本没有公开 base URL，而且按照网络边界方面的设计，它也不应该有——它唯一
知道的服务器地址就是一个集群内部的监听地址。持有公开 base URL 和分享
记录的是服务器，命名这个链接的也应该是服务器。

## 14. 开放问题

1. **事后分享工具。** 究竟有没有必要单独做一个 `ShareArtifact` 运行时
   工具，还是说“Portal 的创建操作” 加上 `UploadArtifact(share=true)`
   就已经够用？新增一个工具是有代价的（会占用模型的工具面），所以先推迟，
   等到真的有 Agent 流程需要分享一个自己刚才并没有上传的文件时再说。
2. **谁有权创建分享。** 目前的矩阵默认对任何 Member 开放。有些部署会希望
   限制成只有 Admin/Owner 才行。这暂时留作一项有界的 Space 策略，而不是
   写死在代码里，等到有明确需求时再做。
3. **安全的 SVG 预览。** SVG 是一种可执行的活动文档；它能否在同一套沙箱
   模型下被安全预览，还是必须继续只能下载，需要单独研究。
4. **检索计数的统计粒度。** 目前提议的是一个单一计数器。是否值得为“预览”
   和“下载”分别计数，或者设置一个按链接封顶的下载次数上限，目前还没有
   得到验证；先从一个简单的计数开始。
5. **共享缓存中的链接隐私。** 被分享的 HTML 内容天生就是可缓存的；被分享
   内容与私有内容各自应该用怎样的 `Cache-Control`，以及一个被撤销的链接
   是否必须让已经缓存的副本失效，这些都需要在内容处理器里明确写清楚。
   目前暂时按 `private, no-store` 交付，与已认证路由的做法一致，这样
   撤销能够立即生效，代价是无法利用共享缓存。
6. **分享过期清扫及其审计。** 过期目前是惰性判定的：在 `expires_at`
   之后再去解析会直接返回 404，但没有任何机制会去记录这次过期，所以审计
   轨迹上只有“创建”和“撤销”，没有“过期”。参照 Artifact 过期的记录方式，
   引入一个类似 `ArtifactRetainer` 的清扫任务，为每个失效的分享打上墓碑
   标记并写入审计——这就是能补上这个缺口的后续工作。

## 15. 验收标准

达到以下条件时，这次增量即算完成：

- 一个 Space 成员打开任意一个自己可读的 Artifact 的 Portal 详情页时，
  能看到渲染后的 Markdown，以及在沙箱框架里运行的 HTML Artifact，不可
  预览的类型仍然提供下载；
- 一个 Agent 调用 `UploadArtifact(share=true)` 后，能在工具结果里同时
  拿到一个基于所配置的公开 base URL 构造出的公开 Portal 链接和一个原始
  下载链接；
- 一个没有 BuildMax 账号的人打开这个公开链接，能看到同样渲染出来的预览
  内容，并能下载文件；
- 一个被分享的 HTML 原型里的脚本运行在一个不透明来源里，既触达不了
  Portal 存储的会话，也无法以已认证调用方的身份触达 BuildMax 的 API；
- 在没有配置公开 base URL 的情况下创建分享，会被明确拒绝并给出清晰的
  错误，且不发出任何链接；
- Owner、Admin 或分享的创建者本人都可以撤销一个链接，撤销之后这个链接
  解析出的结果，与一个从未存在过的令牌所得到的 404 完全一样；
- 删除或清除一个 Artifact，会让指向它的每一个链接都解析为 404，且不需要
  另外执行任何单独的撤销步骤；
- 令牌在创建之后不会出现在任何 API 响应里，除了那一次性的链接之外也不会
  出现在任何工具输出、任何轨迹或任何审计事件中；
- 分享的创建与撤销会出现在审计轨迹上；单次检索不会；过期事件则推迟到
  分享保留清扫任务实现之后（见 §14 第 6 项）。
