## 1. 决策

BuildMax 支持两种明确的 LLM 连接模式：

| 模式 | LLM 传输方式 | 提供商凭证归属 | 预期用途 |
|---|---|---|---|
| `direct` | CLI、Desktop 或 Worker 直接调用 OpenAI 兼容端点 | 运行 Agent 的机器 | 本地优先、离线、BYOK，以及已经运行门户的部署 |
| `managed` | 客户端调用 BuildMax 远程 LLM 服务器 | BuildMax 部署 | 集中管理凭证、Space 模型策略、用量、配额和审计元数据 |

托管模式是可选的。直接模式仍是完整的一等路径，不需要 BuildMax Server。两种
模式之间不会自动回退；静默改变提示词和源代码实际采用的路径会违背运营人员预期。

服务器端点采用**BuildMax 推理协议**，而不是面向公众的 OpenAI 兼容通道。远程
客户端实现 `internal/core/llm.LLMClient`，负责在进程内契约与该协议之间转换；
Agent 循环和工具仍在调用方运行。

目录目标会声明其使用的线协议，网关据此构建匹配的客户端。OpenRouter、LiteLLM
或其他由运营方管理的兼容网关仍可通过 `openai_compatible` 覆盖多种上游；
目标也可以直接使用 OpenAI Responses（`openai`）或 Anthropic Messages
（`anthropic`）。新的适配器必须通过第 13 节的一致性测试。适配器的依据是
共享能力能否由契约表达，而不是某个供应商是否有专用名称。详见
[LLM 提供商适配器](LLM提供商适配器.md)。

引入网关的原因是**BuildMax 的治理能力**，而不是供应商数量：

- 提供商的凭证不需要向用户或工人分配；
- 空间选择稳定模型别名，而不是提供商模型标识符；
- 每次托管调用都可以授权、计量、限流，并与 BuildMax 运行关联；
- 无需修改客户端配置即可替换提供商路由。

## 2. 产品目标

采用私有 BuildMax 部署的运营人员应能在不向用户或 Worker 分发提供商密钥的
情况下，为 Space 提供批准的模型。运营人员还应知道哪个 Space、哪个用户发起
了托管调用，调用采用哪个批准的目录目标，消耗了多少令牌，以及调用是否成功。

本地用户必须能够仅凭 `settings.yaml` 和提供商或本地推理端点运行 CLI/Desktop。
直接模式不能把 Server 可用性、登录或 Space 成员资格变成本地使用的前置条件。

## 3. 当前基线

已有的边界包括：

- `internal/core/llm.LLMClient` 是 Agent 循环使用的共享契约；
- `internal/infra/llm` 提供当前的 OpenAI 兼容实现，以及流式传输、重试、超时、
  错误分类和用量捕获；
- `internal/agentapp` 负责组装运行时；
- `settings.yaml` 中的模型列表供 CLI 和 Desktop 使用；
- `server.yaml` 中的 `conversation.model` 供 Tier 1 Server 和 Worker 使用。

目前的调用路径不同：

| 界面 | Agent 循环运行位置 | 提供商调用位置 | 凭证来源 |
|---|---|---|---|
| CLI / TUI | 本地进程 | 本地进程 | `settings.yaml` |
| Desktop | Desktop 进程 | Desktop 进程 | `settings.yaml` |
| Portal Tier 1 | Server | Server | `server.yaml` |
| TaskRun | Worker | Worker | 运行时注入的 `server.yaml` |

当前配额统计以运行 为中心，汇总 TaskRun 令牌和 Task 标题令牌。Tier 1 对话和
本地调用尚未产生完整的 Server 侧 LLM 调用账本；仅靠 Portal 无法补足这一点，
调用级持久化必须作为本设计的一部分明确建立。

认证也有不能被设计掩盖的限制。CLI 和 Desktop 默认把访问令牌与刷新令牌存储在
操作系统凭证库中，或在本机保存 `auth.json`。目前已有刷新流程，因此登录可以
在访问令牌过期后继续，且会话可以被撤销；访问令牌本身仍不能单独撤销，因为
系统没有撤销列表，已签发令牌会一直有效到期。Server 可以检查 Space 成员资格
并移除 Space 访问，但不能把访问令牌描述成可独立撤销的网关凭证。

## 4. 为什么需要 BuildMax 网关

### 4.1 凭证托管

直接模式要求执行机器持有上游凭证，适合 BYOK，却不适合希望集中管理凭证、
或希望 Worker 不持有通用供应商访问权的运营人员。

托管模式以 BuildMax 凭证替代上游凭证，凭证权限由 Server 授权和 Space 模型策略
共同限制。

### 4.2 Space 模型策略

本地模型条目直接选择提供商 URL 和模型。托管客户端改为选择稳定名称，例如
`default`、`fast` 或 `reasoning`；Server 将该名称映射到运营人员定义的目录目标，
并拒绝不可用或未获批准的名称。

客户端不得向托管端点提交上游 URL、提供商凭证或任意上游模型标识符。这样模型
选择始终处于 Space 授权边界内，也避免把网关变成带身份认证的 SSRF 代理。

### 4.3 用量与配额

每次托管调用都会创建或完成一条调用账本记录。它支持用量展示、配额评估、
事件调查和最终成本报告，但不存储提示词实体。

简单的调用前配额检查不能保证严格支出上限：并发调用可能在最终用量写入前同时
通过，而且推理开始前并不知道输出规模。首版可以拒绝已经超额的 Space，并在调用
后记录实际用量；严格执行还需要配额预留、逐调用输出上限和并发控制，届时网关才
能被称为多租户安全边界。

### 4.4 与提供商解耦

支持更多提供商本身不是构建网关的理由；现有客户端已经可以指向 OpenRouter、
LiteLLM、本地推理或其他 OpenAI 兼容端点。

网关仍提供一个清晰的接缝：客户端使用 BuildMax 协议和稳定名称，Server 路由器
选择 `LLMClient` 的具体实现。未来可以在路由器后增加原生适配器，而无需修改
CLI、Desktop、Worker 或 Agent 核心的传输代码。

## 5. 备选方案

| 选择 | 强度 | 限制 | 决定 |
|---|---|---|---|
| 仅保留直接调用 | 系统最小，本地隐私和可用性最佳 | 提供商密钥、策略和用量仍然分散 | 保留为 `direct` 模式 |
| 由 Server 下发模型配置 | 集中别名和引导体验 | 凭证仍会到达客户端，调用仍未计量 | 不能单独解决问题 |
| OpenAI 兼容透明代理 | 现有客户端只需修改 `api_url`，也方便第三方调用方 | 暴露过宽的公共契约、泄漏上游语义，并使 BuildMax 策略和错误难以演进 | 不作为首版端点 |
| BuildMax 托管推理协议 | 内部契约稳定、授权明确、错误标准化，并为提供商能力演进留出空间 | 需要远程客户端和协议测试 | 采用 |
| 现在实现所有原生提供商 SDK | 最大化访问提供商特性 | 永久兼容性表面，但当前核心没有此需求 | 延后 |
| 强制使用 LiteLLM，不构建 Server 网关 | 外包提供商标准化 | 无法整合 BuildMax 身份、Space、运行和配额 | 可作为部署选项，不是产品决策 |

如果BuildMax打算为第三方应用提供服务，则可后续添加一个符合OpenAI的公共终端。 这是一个单独的产品和安全决定，而不是向BuildMax客户提供模型。

## 6. 架构与归属

```text
CLI / Desktop ── RemoteLLMClient ─┐
                                  │
Worker ──────── RemoteLLMClient ──┼─ HTTP auth entry points
                                  │          │
Portal Tier 1 ────────────────────┘          ▼
                                      LLM Gateway service
                                             │
                                model policy + call ledger
                                             │
                                             ▼
                                        Model router
                                      ┌──────┼──────┐
                                      │      │      │
                              OpenAI-compatible   future native adapters
                                      │
                         OpenRouter / LiteLLM / provider / local model
```

图表显示了逻辑重复使用，而不是HTTP自动调用.服务器所有的Tier 1推理将模型路由器和计量服务调用在进程中.它不得通过自己的公共HTTP听器回发请求.远程工作者使用员工认证的HTTP入口点，因此不需要上游凭证。

| 关注 | 业主 |
|---|---|
| 信息，工具定义，工具调用，使用合同 | `internal/core/llm` |
| 执行Agent循环和本地工具 | `internal/core/agent` |
| 地方模型组装和远程客户选择 | `internal/agentapp` |
| 提供商调用（当前为 OpenAI 兼容） | `internal/infra/llm` |
| 远程 BuildMax 协议客户端 | `internal/infra/llmremote` 或同等基础设施包 |
| 其他国家， 空间政策， 配额协调， 呼叫账本 | 新的`internal/service/llmgateway` |
| 用户和工人HTTP适配器 | `internal/server/handlers` |
| 进程组装和提供商凭证 | `internal/bootstrap`、`internal/config` |

网关不能进口服务器，配置或提供商包.网关消耗核心合同；它不会将网络政策或基础设施移动到域层。 `internal/core`

## 7. 模型目录与解析

Server 需要一个由运营方管理、独立于单一 Tier 1 模型的目录。每个目录条目包括：

- 不透明的目录 ID；
- 面向运营方的名称；
- 提供商类型或客户端工厂；
- 上游端点和凭证引用；
- 上游模型标识符；
- 上下文窗口和超时；
- 明确声明的能力；
- 启用状态。

早期设计曾让 Space 策略把稳定别名映射到目录条目；当前实现已撤回该层，
托管客户端直接使用 `llm_model.name`，解析关系为：

```text
(space_id, alias) -> authorized catalog entry -> LLMClient
```

目录存储在 `llm_model` 表中，并由 `buildmax-server model` 编辑。它不是普通配置：
其中包含不应随 Kubernetes ConfigMap 文件传输的提供商凭证，而且可在 Server 运行时
变化。凭证保存在目录行中，由构建提供商客户端的查询读取；因此，静态存储时的
保护责任属于运营方的数据库备份策略，而不是配置文件策略。

Space 策略也应进入数据库，因为 Space 是相应的所有权边界。在该能力落地前，
`server.yaml` 中的部署级默认模型会把运营方批准的小集合暴露给所有 Space。
`conversation.model` 仍是 Server 自己的引导模型，因此目录尚未有条目时，部署仍
可以先回答对话。

提供商能力必须显式声明，不能从提供商名称推断。第一组能力与当前核心契约一致：
文本聊天、工具调用、文本流式传输和用量报告。需要未声明能力的请求应在调用上游
之前失败。

## 8. 托管协议

只有注册到 `internal/server/handlers/routes.go` 的路由才是权威路由。用户入口为：

```text
GET  /api/spaces/{space_id}/llm/models
POST /api/spaces/{space_id}/llm/completions
```

工作者进入点为执行任务的范围：

```text
POST /api/worker/task-runs/{task_run_id}/llm/completions
```

两个HTTP适配器都调用相同的服务.用户路线验证当前用户，并验证每个调用时的空间会员.工作者路线从服务器状态中导出空间，任务和运行；它不依赖由工作者提供的属性字段。

### 8.1 要求

版本请求 DTO仅包含了BuildMax理解的字段：

```json
{
  "call_id": "client-generated idempotency key",
  "model": "fast",
  "messages": [],
  "tools": [],
  "stream": true,
  "call_profile": "agent_turn",
  "metadata": {
    "surface": "desktop",
    "session_id": "optional correlation value"
  }
}
```

DTO 反映了 `core/llm` 的语义内容，但它是版本化的线协议契约，而不是直接暴露 Go 结构的 JSON。初始版本拒绝未知请求字段；提供商特定的请求体、凭证、URL 和任意生成参数均不被接受。

`call_id`识别了一个逻辑调用。 在客户端知道服务器是否接受调用之前，它支持连接失败时重复检测。

调用者表示，调用是为 `agent_turn`,`title`,`compaction`,`evaluation`，或`probe`。 它是操作输入，而不是授权输入：服务器将其与批准目标的自己的缓存政策结合起来，因此，一个客户端不能选择缓存模式，保留，或一个缓存键，运营商未批准的缓存.该字段是添加式，可能会被遗漏；服务器没有证据表明前将被读回，这不是写一个原因.非服务器的值不被要求收取，所以可以认为一个新的相关标识符 `call_profile` [快速缓存控制.md](提示缓存控制.md)

转载数据是相关性文本，而不是授权输入.服务器从身份验证中提取用户ID和空间ID，并从工作者路线中提取任务运行身份。

### 8.2 无流媒体响应

```json
{
  "content": "...",
  "tool_calls": [],
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 20,
    "total_tokens": 120
  }
}
```

响应故意返回BuildMax工具调用和使用形状.它不暴露上游响应机构或提供商的凭证标题。

### 8.3 流媒体响应

流媒体使用类型为SSE事件，而不是字节对字节的上游块：

| 事件 | 实用载荷 | 意思 |
|---|---|---|
| `delta` | 含量达尔塔 | 给当地水槽送达的文字 |
| `result` | 终端内容，工具调用，使用 | 完成`LLMClient`呼叫 |
| `error` | 稳定代码，安全消息，可回调的旗 | 通过错误结束调用 |

现有核心合同在流媒体期间暴露内容的部分，并在流媒体结束后返回组装的工具调用.管理协议应该保留该合同，而不是暴露供应商特定的工具调用部分。

每个事件都会迅速被掉.客户端断开连接会取消上游文本.在支持的部署中使用的反向代理必须禁用响应缓冲，并且允许比配置模型调用时间更长的空置时间。

### 8.4 错误

服务器返回稳定的BuildMax错误代码，用于身份验证，空间访问，未知的称，未支持的功能，配额，截止时间，取消，利率限制，上游身份验证，上游可用性和上游错误的响应。

安全供应商详细信息可能会记录在服务器诊断中，但原始供应商错误体不会默认返回.它们可能包含帐户识别符，终点详细信息，请求碎片或政策信息.远程客户端将稳定错误分类映射到本地供应商客户端提供的相同可读性行为中。

## 9. 流式传输、重试与幂等性

只有直接调用上游供应商的组件拥有提供商重试政策.在管理模式下，这是服务器端供应商客户端.远程客户端不得在完成或部分流通的门口调用周围添加另一个独立的重试循环。

适用于以下规则：

1. 服务器可以根据提供商客户政策重新尝试上游调用
在第一个反应德尔塔发射之前。
2. 没有一个层自动重新尝试，
3. 已运行的重复 `call_id` 只需协议
否则会导致冲突。
4. 已完成的重复 `call_id`可能会返回其存储的终端元数据，但
在第一版本中，不需要重播生成的全部内容。
5. 通过处理器和路由器传递到
提升要求。
6. 每次尝试和逻辑调用都在服务器诊断中可区分
因此，重试不会增加用户可见的呼叫数量。

缓慢或断开通的调用器不得允许在服务器内存中无限排列的提供商分类。

## 10. 调用账本、配额与审计

每个管理的逻辑调用记录至少：

| 领域组 | 数据 |
|---|---|
| 身份 | 呼叫 ID，空间 ID，身份验证的用户 ID或任务运行 ID |
| 相关性 | 交付时的表面，交付时的会话ID，输出时的任务和运行ID |
| 模型 | 要求的名，解决的目录ID，提供商类型，上游模型标识符 |
| 时间 | 接受，上游开始，第一次达尔塔，完成时间印 |
| 结果 | 状态，稳定错误类，重试/试验计数 |
| 使用 | 快速，完成和总代币；是否报告使用，估计或不可使用 |

默认情况下，即时文本，工具参数，工具结果，源代码和生成的内容都被排除在呼叫账本中.持久的本地痕迹继续拥有运行细节.任何未来的选择体捕获都需要单独的保留，编辑，访问控制和数据分类决定。

现有任务运行代币字段仍然是有用的总结，但集成必须避免在本书中一次和一次通过任务运行总数计算相同的工人调用。

配额执行阶段发展：

| 阶段 | 行为 | 保障 |
|---|---|---|
| 显现性 | 记录电话后的实际报告使用 | 仅计量 |
| 软强制 | 已超过记录使用限度时拒绝；限制要求的持续时间和输出 | 同时调用可能超越 |
| 保留执行 | 预计的预算在发送前储备，完成后调整 | 限制过渡 |
| 多租户控制 | 增加每空间和全球同步率/利率限制 | 保护服务器容量，限制噪音的邻居 |

在保留执行和同时控制的存在之前，文件不能声称门户提供了严格的支出上限或是安全的无信任的多租户SaaS部署。

审计事件记录了模式政策变化，拒绝模型使用和凭证管理等配置和授权行动。 电话每次运营记录的大量记录属于电话账本，而不是管理审计日志。

## 11. 身份验证与安全

管理推理增加了服务器的数据分类，因为提示，工具方案和工具结果通过它.威胁模型必须包括：

- 记录，跟踪，崩报告和指标中的快速和源代码曝光；
- 由于配置，标题或上游错误导致的凭证泄露；
- 跨空间模式的访问；
- 无限请求机构，工具方案，流量和同步性；
- 由于用户控制的路由，上游终端SSRF；
- 工人使用其基础设施凭证在其分配的运营之外；
- 长期的通话超过了访问令牌。

需要的控制是：

- 托管局外的TLS；
- 每次用户调用时进行验证和空间授权；
- 服务器衍生任务，运行，空间和模型政策对员工调用；
- 只有运营商配置的上游终端点；
- 要求，消息，工具方案，响应，时间限和同步限制；
- 在正常访问日志或呼叫簿记录中没有即时机器；
- 证书的删除和安全误差正常化；
- 取消传播和有限的流量排队；
- 呼叫元数据的明确保留政策。

共同工作者代币不是一个模型门户的足够的凭证，因为它没有针对一个运行，因此工作者路线从来没有接受它.它取代了一个运行代币：一个使用者，空间和运行的短暂凭证，在运行发送时刻.见[工人运行代币.md](Worker运行令牌.md).自此以来，共享代币已从每个工作者路线中删除，因此运行代币是工作者持有的唯一凭证。

用户访问代币默认为7天，这对于早期的可信度部署实验是可接受的，但不是完全的管理客户端生命周期.自此更新已经发送，因此登录比一个访问代币还活了久，并且会话可以被撤销.该功能被描述为生产准备之前仍然缺失的是本土秘密存储，绝对的会话寿命和观众扩展的凭证。 [客户会议和API证书](../../proposals/client-sessions-and-api-credentials.md)

## 12. 客户端配置与用户体验

管理模式必须在模型配置中明确.重复使用`api_url`并将JWT登录到`api_key`中将混合两个凭证系统，重复代币到`settings.yaml`，使直接和管理行为难以解释。

图形形如下：

```yaml
models:
  - name: Space Fast
    model: fast
    transport: buildmax
    server_url: https://buildmax.example.com
    space_id: tm_example
```

终端字段仅在实现时成为用户文档.远程客户端读取来自`auth.json`的身份验证；模型输入不复制凭证.`buildmax login`和Desktop登录流建立服务器身份，而模型发现列出了选择空间可用的名。

直接输入保持其现有的提供商URL和API键形状.如果直接和管理模型具有相同的显示名称,UI还必须显示运输和服务器/空间背景，以便用户可以知道数据将到哪里。

管理到导向的倒退从未隐含.操作员或用户可以配置两个输入并选择它们之间，但服务器中断不能默默地将受管理的流量转向个人提供商密钥。

## 13. 提供商策略

导路由器模型为协议构建客户端，解决目标声明 `openai_compatible`,`openai`,`anthropic`，或`ollama`.运营商可以向OpenRouter,LiteLLM，兼容的提供商终端点或本地推断指向兼容目标.BuildMax并不能保证每个提供商特定功能都会存活一个兼容的OpenAI中介。

`ollama`是唯一一个没有凭证的目标类型：它命名了一个本地运行时间，部署直接达到，什么授权呼叫是能够达到 daemon，这是部署的网络而不是目录的属性。 `llm.ProviderNeedsCredential`是该豁免的声明，它是故意一个提供商宽一个主机目标缺失其关键是一个错误配置，必须在选择而不是发送一个未认证请求。 [地方-大发快三提供商.md](本地Ollama提供商.md)

适配器在[提供商-适应器.md](LLM提供商适配器.md)中指定.它们没有改变这个协议:`llmwire`携带消息，工具定义，工具调用和使用，因此它已经描述了门户端可以服务的每个协议。

只有在所有以下条件下，本地供应商适应器才是合理的：

1. 共同的Agent产品需要一个能力，而不是一个表面
要求提供商特定的快捷方式；
2. 采用该功能的提供商中立表示,`core/llm`
3. 能力显著改变了正确性，质量，延迟或成本；
4. 支持的兼容上流不能可靠提供；
5. 适配器具有合约，流媒体，使用，错误和工具调用测试。

提供商功能示例包括结构化内容块，即时缓存控制，推理元数据，多模入口和提供商特定使用.它们不仅仅是因为供应商API暴露它们。

## 14. 运维影响

管理模式将服务器转化为推理数据平面.与目前的协调工作负载相比，它增加了长寿命的响应，更开放的连接，上游退出，压力，提供商速度限制，以及服务器停机的更大的爆炸半径。

因此，部署工作必须包括：

- 逆代理流和缓冲配置；
- 要求，上游，空置和优雅的关闭时间；
- 连接，调节和记忆尺寸；
- 全球和空间均同步限制；
- 提供商退出政策和秘密注射；
- 服务器，路由器和上游故障的健康信号；
- 调用率，第一代代币延迟，持续时间，使用可用性等指标
取消和稳定错误类。

预计额外的网络跳跃与推理相比较小，但在代理运行中相结合。 测量，而不是这种假设，必须确定支持的部署拓是否可接受。

## 15. 交付计划

### 合同和流程路由器

- 定义提供商中性路由器和模型分辨率界面
`internal/core`。
- 添加运营商模型目录和整个部署的默认别名。
- 在路由器后面再使用现有的OpenAI兼容客户端。
- 路由服务器所有的Tier 1通话通过服务在过程中，没有
改变外部行为。
- 测试号，禁用目标，不支持的功能，安全秘密
错误

### 电话账本和非流媒体网关

- 加入调用账本持久性合同和数据库实现。
- 通过JWT和空间授权，注册拟议的用户路线。
- 执行非流媒体管理的呼叫和稳定的错误。
- 添加一个远程`LLMClient`和对本地实现进行合约测试。
- 在要求执行配额之前记录使用和增加可见性。

### 流媒体，取消和无能

- 添加输入SSE事件，并迅速刷。
- 扩散断路取消。
- 执行重复试验规则，并复制`call_id`行为。
- 测试内容的分量，最后的工具调用，使用，上游中流故障，
慢客户，然后断开连接。

### 客户端发现和明确管理模式

- 增加空间模型的发现。
- 添加明确的直接/管理配置和选择到CLI和Desktop。
- 阅读管理的凭证来自`auth.json`，而不是`settings.yaml`。
- 文件数据流，模型优先级，代币过期和失败行为。

### 通过和治理 Worker

完成：运行范围的入口点和凭证，并从管理的工人中取消提供商凭证。 Space运行的代币计数与呼叫账本保持分开，因此配额仍然总结`task_run`总数只有。

剩下的：

- 增加软配额执行，限制请求，同步限制，
操作员诊断。
- 增加对模型政策和凭证变更的审计活动。
- 在创建时将一个批准的别名绑定到任务或工作流程，所以运行模型
转载可复制，而不是发送时的部署默认情况。

### M6。 根据合理的理由，严格的配额或本地供应商

- 增加保留和调和，如果严格的支出限制成为一个
产品要求。
- 仅用明确的政策和会计语义来添加路由或故障过关。
- 只有满足第13节的标准时，只需添加本地供应商适配器。

每个里程碑都必须在没有服务器的情况下离开直接模式.用户可见的配置和路线需要在运输时对应的更新到`guide/`,`reference/`,OpenAPI文档，配置示例和架构文档。

## 16. 验证

执行直到以下行为被涵盖之前才完成：

- 直接模式运行没有服务器URL或登录状态；
- 评估运行在 `evaluation/`使用直接模式下，因此结果不是
受到空间模型政策，别名分辨率，配额状态或服务器的影响
CLI适配器直接拒绝一个管理主体
测量与表格要求不同的运输；
- 管理的封锁和流通呼叫产生相同的核心内容，工具
呼叫和使用形式作为直接呼叫同一个目标；
- 用户不能在选择空间的政策之外使用一个别名；
- 呼叫者不能选择上游URL或提供商凭证；
- 服务器所有的1级推断不使HTTP自动调用；
- 员工归因取决于执行任务而不是请求元数据；
- 提示和工具内容不进入正常日志或呼叫账本；
- 排放的第一个果之后，向上进行重试停止；
- 断开连接取消达到上游请求；
- 慢消费者不能无限地增长记忆；
- 提供商使用不完整或不可用是诚实地表达的；
- 一次管理的员工调用不计两次；
- 访问符号的过期和空间成员删除失败，出现明显的错误；
- 直接和管理型号的输入可以分辨于CLI,TUI和Desktop。

使用存储器任务运行器检查，以每次实现变化比例.最终的网关集成套件需要一个定性假的上游，并且不需要一个真正的模型API密钥。

## 17. 初始版本范围外事项

- 公共OpenAI兼容的API，用于任意的第三方客户。
- 产生的Anthropic,Bedrock,Vertex或其他供应商适配器。
- 提供商特定的特征，并非在`core/llm`中所表达。
- 嵌入式，图像，音频和其他非聊天推理终点。
- 语义反应缓存。
- 货币发票。
- 提供商钥匙，由用户提供。
- 当服务器或提供商不可用时，自动直接倒车。
- 无人信任的公共多租户SaaS运营。

## 19. 建议的首项变更
