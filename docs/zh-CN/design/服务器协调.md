## 1. 现状

生产参考清单运行两个 `buildmax-server` 副本，而三处实时协调状态却保存在单个进程的内存里。本记录决定部署如何获得正确的多副本语义：一个默认关闭、每个副本都可达的共享协调后端，使实时状态不再是进程私有。持久状态从来不是问题——它已经通过 MySQL 与对象存储收敛；实时状态才是。

## 2. 问题

三处服务器结构保存着只有一个进程能看到的状态：

- **流缓冲**（`internal/server/websocket/hub.go`）缓存一次任务运行的流式增量并扇出给该任务的 SSE 订阅者。Worker 把增量推给其 HTTP 调用落到的那个副本；浏览器订阅落到它 SSE 请求落到的那个副本。两者不同时，浏览器在持久结果到达前什么也看不到。
- **连接注册表**（`internal/server/websocket/registry.go`）持有实时 WebSocket 连接，把事件扇出给关注某 space 的每个连接。在一个副本上产生的 `task.status.changed` 失效事件只能到达该副本恰好持有的 socket；另一个副本上的浏览器仍显示陈旧状态。
- **回合队列**（`internal/server/turnqueue/turnqueue.go`）串行化一个会话的回合，使两个回合永不交错读写同一条消息历史。锚定在进程上的串行看不到另一副本上正在运行的回合。这一处会**损坏数据**而非仅降级视图：一个会话的两个回合在两个副本上被接纳，各自都认为自己是唯一写入者。

调度器与陈旧运行回收器在 N 副本下已经安全：它们通过原子条件 `UPDATE` 认领工作，所以更多副本是更多轮询者而非重复工作。上面三处结构没有这样的锚点。

## 3. 决策

引入一个由配置选择的共享协调后端：

- `coordination.mode: local`（默认）保持今天的进程内实现不变。这是 CLI 相邻的单实例与每个开发部署所用；只要模式为 `local`，受支持拓扑就是恰好一个服务器副本。
- `coordination.mode: redis` 把三处结构都路由到 Redis，使 N 副本共享实时状态。运行多于一个副本的部署必须设置它。

Redis 承载全部三者，因为它们的需求——可回放的按任务流、低延迟的按 space 广播、按会话的互斥租约——都是一等的 Redis 原语，故一个依赖、一个连接池即可覆盖整个面。基于 MySQL 咨询锁与独立消息代理的混合方案按 Occam 被否决：它在不消除低延迟扇出真正需要的那个后端的前提下增加了后端数量。

**失败即关闭。** 当配置为 `mode: redis` 而 Redis 在启动时不可达，服务器拒绝启动。在两副本下静默退回 `local` 会重新引入本记录要防止的回合串行损坏——与沙箱同一原则：绝不因后端不可用而在无约束下运行。

## 4. Coordinator 接缝

`coordination.Backend` 位于 `internal/infra/coordination`。它持有共享 Redis 客户端，在构造时做一次健康检查，并向服务器 vend 所需的三个后端实现：

- 一个 `websocket.StreamHub`（该接口已预留 Redis 实现位置），
- 一个连接注册表广播所经的事件发布/订阅器，
- 一个回合队列在运行回合前获取的 `turnqueue.Locker`。

每个消费者依赖自己定义的小接口，由 infra 包实现——依赖方向是 `server → infra → core`，绝不反向。传入 `nil` 后端即选择进程内行为，因此 `local` 模式不是第二条代码路径，而是共享路径的缺席。`bootstrap` 从 `ServerConfig` 构造后端并交给今天直接创建三个内存结构的 `NewHandler`。

## 5. 流式投递

Redis 流缓冲把 `StreamHub` 映射到键为 `stream:{task_id}` 的 Redis Stream。

- `Append(taskID, delta)` 是带 `MAXLEN ~` 近似裁剪的 `XADD`，像 2 MiB 内存缓冲那样限制内存，并刷新 TTL 使废弃运行的流过期而非泄漏。
- `Subscribe(taskID)` tail 订阅点之后追加的条目（从当前末尾 id 起 `XREAD BLOCK`），投递实时增量——与内存版语义一致，因此 SSE handler 保持不变、两种后端共用一条代码路径。
- `Buffer(taskID)` 返回当前快照（`XRANGE - +`，去掉终止标记），使迟到订阅者补齐，与内存版完全一致。`Subscribe` 与 `Buffer` 之间的小重叠窗口可能重复一个片段；这与内存版可接受的行为一致，对追加式文本只是外观问题。
- `Done(taskID)` 追加一条终止标记条目并设置短 TTL；读到该标记的订阅者发出 `[[DONE]]` 哨兵并停止。

于是一个副本上的 worker `XADD` 与另一副本上的浏览器 `XREAD` 现在看到同一条流。

## 6. 事件扇出

每个副本仍完全保留自己的连接注册表：一个 socket 物理上归它接入的那个副本，只有该副本能写。跨副本可达性靠发布而非共享 map 来补齐。

- `Broadcast(space, user, type, payload)` 把事件信封发布到单一 Redis Pub/Sub 频道，而非遍历本地 socket。
- 每个副本在该频道上跑一个订阅者。每收到一个信封，就做 `Broadcast` 过去内联做的那件事——对自己的 socket 执行 `audience(space, user)` 本地扇出。
- 发布方也会通过 Pub/Sub 收到自己的消息并在那里扇出，所以发布路径从不本地扇出。一条代码路径把消息投递到每个副本上的每个连接，且无重复发送。

选择单一频道而非按 space 分频道以求简单；信封携带 space id，各副本自行过滤。若跨 space 流量将来足以证明，再拆为按 space 分频道作为后续优化。串流服务端自发回合增量的 `BroadcastSink` 沿用同一 `Broadcast`，因此无需自身改动即成为多副本正确。

## 7. 会话回合串行

回合队列保留其进程内机制——按会话的 goroutine、待运行列表、位置上报、`OnDequeue` 与排空——因为同副本两个回合仍在那里廉价串行。一个分布式租约守护那个必须跨副本成立的边界：开始一个回合。

- 在调用某作业的 `run` 前，队列 goroutine 获取 `lock:conv:{conversation_id}`（`SET NX PX`，带有界等待的阻塞）。一个看门狗在回合运行期间按间隔续租；释放则丢锁。
- 无法获锁的副本等待，这正是所需的跨副本串行。回合途中死亡的副本，其租约会过期，于是另一副本接管而非死锁。
- 租约携带单调的 **fencing token**，暴露在租约上。租约及其续期是本设计交付的互斥；把该 token 接入消息历史写入路径——使租约过期后复活的持有者无法在夺锁副本之后交错写入——是对超过 TTL 的暂停的安全网，是一项被追踪的后续项，见 §11。
- 队列**位置**变为按副本、因而跨副本近似。这是可接受的：位置只是界面显示的 UX 提示而非保证，而它所提示的串行现在由租约强制。

由于租约在滚动升级短暂的两副本重叠期也生效，服务器保留 `maxUnavailable: 0` 的 `RollingUpdate`——B-i 消除了退回 `Recreate` 策略或单副本上限的需要。

## 8. 配置与失败策略

`server.yaml` 新增 `coordination` 段：

```yaml
coordination:
  mode: local            # 或：redis
  redis:
    address: redis:6379   # host:port
    username: ""          # 可选（Redis 6+ ACL）
    password: ""          # 可选；可由 BUILDMAX_COORDINATION_REDIS_PASSWORD 覆盖
    db: 0                 # 逻辑数据库
    tls: false            # 通过 TLS 连接
```

- `mode` 默认为 `local`。除 `local` 或 `redis` 外的任何值都是使服务器拒绝启动的配置错误。
- Redis 密码沿用与数据库密码相同的环境覆盖模式：`BUILDMAX_COORDINATION_REDIS_PASSWORD` 覆盖文件，使凭据无需落盘。
- 当 `mode: redis`，构造时连接 Redis 并发一次 `PING`。失败即致命——服务器退出而非在多副本清单下以进程私有协调提供服务。

## 9. 部署拓扑

- `deployment/production/buildmax.yaml` 新增一个 Redis `Deployment` 与 `Service`，在服务器 `ConfigMap` 中设置 `coordination.mode: redis` 与地址，并把 `buildmax-server` 保持为两副本——现在是受支持拓扑而非潜在缺陷。误导性的“服务器不保留要紧的本地状态”注释被更正，指明该主张现在所依赖的协调后端。
- 在首个受支持拓扑中 Redis 本身是单实例。它的状态可重建——流与锁是实时而非持久的，Redis 重启至多损失在途流增量与短暂的会话租约重获——故无需持久卷。此限制记录在部署文档中而非隐藏。
- Compose 与 kind 运行单个服务器并保持 `mode: local`，这对单副本是正确的；在那里搭一个 Redis 以在生产之外演练 `redis` 路径是后续项，而非二者可用的前提。

## 10. 测试

- 单元测试用进程内 Redis 伪实现（miniredis）覆盖每个后端实现，故它们在普通 `./make test` 与 CI 中无需外部基础设施即可运行；真实 Redis 集成可通过一个地址提供。
- 一个跨实例测试构造共享一个 Redis 的两个后端，断言三条保证：一个上的 `Append` 被另一个上的 `Subscribe` 读到；一个上的 `Broadcast` 到达注册在另一个上的 socket；一个持有的回合租约阻塞另一个上同一会话的回合。
- 一个失败即关闭测试断言 `mode: redis` 配合不可达地址使服务器构造返回错误而非可用 handler。
- 一个架构测试断言生产清单的 `buildmax-server` 副本数与所配置的协调后端一致，故一个在不设 `coordination.mode: redis` 的情况下扩展服务器的清单会使构建失败。

## 11. 范围之外与未决问题

- Redis 高可用（Sentinel 或 Cluster）在首个受支持的多副本拓扑中并非必需，留给运维自己的 Redis。
- 跨设备共享持久 Session 状态是另一个方向（[持久 Agent 会话提案]），本记录只覆盖实时服务器协调。
- 在消息历史写入路径中强制执行会话 fencing token 是一项后续项。租约交付互斥；该 token 只守护进程暂停超过其租约 TTL 的病态情形，其写入路径检查推迟到该写入路径被打通以携带它时。
- 按 space 的 Pub/Sub 频道、慢订阅者的背压指标，以及一个降级而非退出的 Redis 故障就绪信号，都推迟到一个运行中的多副本部署证明它们确有需要。
