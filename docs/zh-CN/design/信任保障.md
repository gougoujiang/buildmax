## 1. 目的

P0 已经让共享的 Agent Core 稳定到可以支撑 CLI、Desktop、Portal 和 Worker 的任务运行。P0.5 的目标是让这个核心更值得信任、更易于运维。

本文档刻意停留在产品能力层面：只列出 BuildMax 接下来应当支持的关键事项，不规定具体的实现形态。

## 2. 方向

P0.5 应当首先聚焦共享的 Agent Core。CLI、Desktop、Portal 和 Worker 应当以各自界面适合的方式，暴露相同的核心能力。

目标是：

> 用户和运维人员能够理解、控制并调试 Agent 的运行。

## 3. 需要支持的关键能力

### 3.1 Runtime Hooks —— 已交付 ✅

Runtime Hook 系统已经实现，详细设计见[Hook 系统](./Hook系统.md)。要点如下：

**配置位置**——两层的配置项会叠加合并：
- 全局：`<BUILDMAX_HOME>/settings.yaml` 中的 `hooks:` 字段
- 工作区：`<workspace>/.buildmax/hooks.yaml`

**传输方式**——每个条目通过 `type:` 选择一种：
- `command`（默认）—— shell 命令，通过 stdin 传入 JSON
- `http` —— 向某个 URL 发送 POST JSON 请求
- `mcp_tool` —— 调用已连接 MCP Server 上的工具
- `prompt` —— 单轮 LLM 评审

**已交付的事件（13 个）**：

| 事件 | 是否阻断 | 锚点 |
|---|---|---|
| `SessionStart` / `SessionEnd` | 否 | `agentapp.OpenSession` / `CloseSession` |
| `UserPromptSubmit` | **是** | `agentapp.RunPrompt`（写入历史之前） |
| `PreToolUse` | **是** | `applyPolicyAndExecute`（策略检查之后、执行之前） |
| `PostToolUse` / `PostToolUseFailure` | 否 | 工具成功/出错路径 |
| `Notification` | 否 | 围绕审批流程（`approval_required`、`permission_denied`） |
| `PreCompact` | **是** | 上下文压缩之前 |
| `PostCompact` | 否 | 压缩成功之后 |
| `SubagentStart` / `SubagentStop` | 否 | 子代理运行器 |
| `Stop` | 否 | 主 Agent 成功退出 |
| `StopFailure` | 否 | 任意错误退出（主 Agent 或子代理） |

由此解锁的使用场景：格式化/静态检查（`post_tool_use`）、策略检查（`pre_tool_use`）、外部审批（`notification` + `pre_tool_use`）、审计导出（`stop` / `subagent_stop` / `post_tool_use_failure`）。

**子代理继承**：子代理共享父级的 HookManager；子代理运行产生的每个事件负载都会打上 `is_subagent` 和 `agent_type` 标记，方便审计 Hook 归因。子代理无法绕过父级 Hook。

**推迟**到后续工作：`agent` 传输方式（Claude Code 的实验特性）、Skill/子代理 frontmatter 中的 Hook（会话级生命周期）、`async` 命令标志、`buildmax hooks` 检查器。详见[Hook 系统](./Hook系统.md) §10（实施阶段 F）。

### 3.2 沙箱与执行边界 —— 本地沙箱、Worker 使用面、进程限制和 Hook 边界均已交付 ✅，`buildmax sandbox overrides` 仍待完成

命令执行现在拥有明确的沙箱模式，详细设计见[沙箱边界](./沙箱边界.md)，其中 A–E 阶段均已实现。沙箱隔离的是 **Bash 子进程**（macOS 上使用 Seatbelt，Linux/WSL2 上使用 `bwrap`，其他平台不可用）；非 Bash 工具仍然沿用既有的权限边界。配置由 `settings.yaml`、`policy.yaml` 与 `BUILDMAX_SANDBOX_ENABLED` 合并解析，并带有按使用面区分的默认值；`buildmax sandbox status|deps|mode|enable|disable` 以及 TUI 页脚会显示当前生效的模式。

对照上文清单，边界覆盖情况如下：

- 工作区文件系统访问 —— ✅ 操作系统后端的绑定/配置规则
- 外部目录访问 —— ✅ `filesystem.allow_write`、`deny_read` 等规则
- 网络访问 —— ✅ Go 端 HTTP/SOCKS 代理，按域名允许/拒绝
- 环境变量暴露 —— ✅ 形似密钥的变量会从 Bash 环境中被清除
- 进程执行限制 —— ✅ `sandbox.process.{max_cpu_seconds,max_memory_mb,max_processes,max_open_files}` 会转换为前置在包装命令之前的 `ulimit` 语句，每项限制单独一条；已经在真实的 Alpine 和 macOS shell 上验证，其中包括在 Linux 上由 CPU 时间限制实际杀死一个忙循环（`max_memory_mb` 在 macOS 上是文档记录过的无效项——Darwin 的 `setrlimit` 没有 `RLIMIT_AS`）。详见[沙箱边界](./沙箱边界.md) §13 阶段 D。
- Worker/容器执行模式 —— ✅ **已经接入，并针对生产环境的 Pod 安全上下文完成验证**：`agentapp/taskrun` 设置的是 `SandboxSurface: config.WorkerSandboxSurface()`，只有当 `BUILDMAX_SANDBOX_BACKEND_INSTALLED` 被设置（两个 Worker Dockerfile 中都有的一行 `ENV`）时，才会选中 `SandboxSurfaceWorker`——最初曾尝试无条件选中这个严格基线，结果在裸机 Linux 主机或原生 Windows 上直接搞垮了所有 Worker 任务（因为 `fail_if_unavailable: true` 却没有后端可以满足它），这个问题是被 CI 捕获的，而不是在本地开发时发现的，因为 Mac 上 Seatbelt 始终存在。`internal/infra/k8s/job.go` 原本使用的 `RuntimeDefault` seccomp 配置文件，会在 Worker Pod 的能力（capabilities）被清空后拦掉 `bwrap` 所需的系统调用，因此被替换成了专门为此构建的 `Localhost` 配置文件（[deployment/seccomp/README.md](../../../deployment/seccomp/README.md) 记录了完整的根因链路，包括另一个独立的内核限制——在容器内 `--unshare-pid` 下挂载 `/proc` 会被拦截）。已经针对一个具备 Worker 真实安全上下文的实际 Pod，以及参考 `DaemonSet` 实际分发的那份配置文件完成验证，并通过部署冒烟测试现在自动执行的一次自然端到端运行加以确认：让模拟模型驱动一次真实下发的任务经由真正的 server → worker → Job 路径调用 `Bash`，然后断言的是工具的执行结果，而不是任务预先写好的最终文本；详见[沙箱边界](./沙箱边界.md) §13 阶段 F。

`command` 和 `http` 这两种 Hook 传输方式现在也会咨询 `SandboxView`——Hook 会执行与 `Bash`/`WebFetch` 相同的 `WrapBashCommand`/`HostAllowed` 调用，而且没有类似 `dangerously_disable_sandbox` 的逃逸入口，因为 Hook 是配置写就的自动化流程，不是由运维者逐轮盯着、LLM 主动选择发起的调用。已经针对一个真实的 `sandbox.Manager`（Seatbelt）完成验证，而不只是一个测试替身。[沙箱边界](./沙箱边界.md)中仍然待完成的是：`buildmax sandbox overrides`（§8）尚未实现。因此 §3.2 **并未**完全收尾，但只剩下这一个面向运维者的命令及其文档——强制执行引擎、Worker 使用面、进程限制、降级标记和 Hook 边界都已经落地。

### 3.3 持久化运行轨迹 —— 第一阶段已交付 ✅

持久化运行轨迹现在会为每次运行保存运行时事件流，详细设计见[持久化运行轨迹](./持久化运行轨迹.md)。第一阶段已经交付：在唯一的 `agentapp.RunPrompt` 关卡处写入一份有界、脱敏的 JSONL 轨迹，因此 CLI/TUI、Desktop、评估和 Worker 的运行都能产生轨迹，而不需要各个使用面各写一份代码。每次运行会写入 `<DataDir>/sessions/<session_id>/traces/<run_id>.jsonl`（Run ID 前缀为 `rt_`），内容包括一条 `run_start` 记录、一条 `sandbox_boundary` 记录、逐轮迭代的 `llm_*`/`tool_*`/`context_compacted` 记录，以及末尾的 `run_end` 记录。可以通过 `BUILDMAX_TRACE_DISABLED` 关闭。失败即放行：轨迹写入失败绝不会打断或拖慢一次运行。

轨迹经过大小限制和脱敏处理，既能用于调试，又不会泄露密钥。

对照 §3.3 完整目标的覆盖情况（✅ 表示第一阶段已经支持）：

- 模型调用 —— ✅ `llm_start` / `llm_end`
- 工具调用 —— ✅ `tool_start` / `tool_end` / `tool_denied`
- 上下文压缩 —— ✅ `context_compacted`
- 错误 —— ✅ `run_end.error`；重试尚未在事件流中体现
- Token 用量与耗时 —— ✅ 每次调用的 Token 数、工具耗时、记录时间戳
- 审批决定 —— 部分支持：只有 `tool_denied`（原因为 `hook`/`user`）
- Hook 执行 —— ❌ 需要专门的 Hook 事件
- 文件变更 —— ❌ 需要文件变更事件
- 子代理的父子关系 —— ✅ 每个子代理的轨迹都携带其直接父级的 `parent_run_id`
- 沙箱模式与边界决策 —— 部分支持：每次运行都会写入一条 `sandbox_boundary` 记录，包含解析后的启用状态/模式/后端和来源链条，未受任何限制的运行会被明确标记为 `sandboxed: false`。逐条命令级别的边界决策与违规记录仍是 ❌（见 §3.2）
- 本次运行使用的记忆与指令来源 —— ❌ 推迟处理

推迟到后续工作（见[持久化运行轨迹](./持久化运行轨迹.md) §7）：活动视图 UI、`buildmax trace` 检查器、上面标记为 ❌ 的记录，以及轨迹目录的保留策略/垃圾回收。

### 3.4 活动视图

在本地使用面中支持轻量级的活动视图。

TUI 和 Desktop 应当让用户能够查看：

- Agent 当前正在做什么
- 使用了哪些工具
- 发生了哪些审批
- 有哪些变更
- 运行为什么失败或停止

正常的对话界面应当保持简洁，活动信息通过渐进式披露呈现。

### 3.5 自检与诊断

支持一个针对本地环境搭建和运行时问题的诊断流程。

它应当检查：

- 模型配置
- 工作区权限
- Git 是否可用
- 当前生效的沙箱模式
- 当前生效的记忆和指令来源
- MCP 配置及其健康状况
- Skill 与子代理的发现情况
- Hook 配置
- BuildMax 数据目录的健康状况

诊断结果应当给出可执行的提示信息，以及一份脱敏后、可在调试时分享的摘要。

### 3.6 记忆与指令

三份契约需要保持彼此独立：指令是规范性的协议，记忆是 Agent 自行整理、可能出错的回忆，会话历史则是一次对话按顺序留下的证据。压缩摘要是一种有损的历史投影，即便它有助于回忆，也不能因此把它当作长期记忆。

记忆应当有明确的作用域并且可见。会话笔记和 todo 是目前已经交付的工作记忆作用域。CLI/Desktop 共享的 Project 身份以及有边界的 Project 记忆，规划见[本地项目记忆](本地项目记忆.md)。全局用户记忆、Space 记忆和可复用的 Agent 记忆仍然是各自独立、留待未来实现的作用域，不应当把它们的含义强加给 `AGENTS.md` 或 Agent 指令。

Agent 应当暴露本次运行加载了哪些指令、记忆和历史投影来源。用户应当能够查看、更新、删除或禁用记忆。BuildMax 应当避免静默保留敏感或出人意料的信息，而且记忆绝不能覆盖 `AGENTS.md`、Skill、子代理定义或 Agent 指令等指令来源。

### 3.7 子代理可追溯性

为子代理的执行提供更清晰的可见性。

用户应当能够看到：

- 运行的是哪个子代理
- 为什么会调用它
- 它接收到了哪些记忆和指令来源
- 它使用了哪些工具
- 应用了哪些运行时边界
- 它返回了什么结果
- 它与父运行之间的关系

子代理不得绕过父级的运行时策略。

### 3.8 更安全的 Worker 执行

为非交互式运行提供 Worker 专属的信任行为。

Worker 运行应当：

- 在原本需要审批的场景下直接失败关闭
- 在明确的沙箱边界内运行
- 记录足够的轨迹数据以支持 Portal 诊断
- 只加载适合该 Space/运行作用域的记忆和指令
- 让被拒绝的操作有清晰、可理解的原因
- 避免掩盖本地与远程能力之间的差异

### 3.9 谁来选择 Worker 的边界 —— 开放问题

承接自已经退役的《Agent 执行策略》提案。关于 Worker 执行，有四件事已经确定，并在上文或[沙箱边界](./沙箱边界.md)中有过描述：一次运行持有什么、运行在什么里面、它的资源边界，以及它记录了什么。尚未确定的是**权限归属**。边界目前是由部署清单固定下来的，而不是被主动选择的：集群运维人员可以把每个 Worker 加固到同一个程度，也可以完全不加固，没有哪个 Space 可以拥有不同的边界，也没有定义当所请求的约束不可用时应该发生什么。今天沙箱在所有使用面上都还是关闭的，所以这个问题暂时不会出现——接入 Worker 使用面（§3.2）正是让这个问题浮现出来的原因。

其中一部分现在已经解决：Worker 如何连接到*服务器*。Worker 控制通道运行在它自己的内部监听端口上、通过 TLS 提供服务，前面挡着一个内部 Service 和一条只放行带标签的 Worker Pod 的 NetworkPolicy——见[Worker API 网络边界](./Worker API网络边界.md)。这限定了 Worker 到服务器之间的流量，但并不决定 Worker 访问 Git 主机、镜像仓库或模型端点这类出站流量。

剩下的具体缺口是通用的网络出站访问。一个 Worker Pod 能够访问集群所允许的任何目的地，`deployment/production/README.md` 如实记录了这一缺失，而不是暗示一个实际并不存在的边界。

我们考虑过四种方案。按用户设置的运行时配置首先被排除：它无法给运维人员一个具有权威性的 Worker 边界。完全交给集群清单去决定虽然自洽，却会让 BuildMax 无法记录或解释一个自己并未建模的边界，而这正是 Beta 门槛所要求的。因此当前活跃的选择是：`server.yaml` 中的一份部署级统一配置，对比运维者/Space/Task 分层叠加的配置——**在有证据证明需要之前，维持部署级统一配置**，因为它的成本明显更低，按 Space 划分的边界应当由提出这个需求的运维人员去承担，而不是默认提供。

仍然悬而未决的问题，以及分别需要什么来解决：

| 问题 | 什么能解决它 |
|---|---|
| 按 Space 划分边界是不是一个真实的需求？ | 需要运维人员明确表态，无论支持还是反对。在此之前，维持部署级统一配置 |
| 一个不适用的配置该让运行失败，还是降级并记录警告？ | 既然轨迹现在会把未受沙箱保护的运行如实报告为未受保护（§3.3），降级是站得住脚的选择。这一点必须在 Worker 使用面上线之前定下来，因为那条基线设置了 `FailIfUnavailable: true` |
| Worker 究竟合理地需要访问哪些目的地？ | 生产参考配置中的一条默认拒绝的 NetworkPolicy，并通过一次仍能完成任务的 kind 冒烟运行来证明。允许列表必须立足于真实运行会访问到的东西——软件包仓库、Git 主机、Space 配置的其他地址——而不是凭空假设。这究竟应该只靠 NetworkPolicy，还是靠沙箱契约中 `HostAllowed`/`ProxyAddress` 已经建模的主机允许列表的代理来强制执行，也是同一个问题的一部分 |
| 这里到底要不要一道审批关卡？ | 无人值守的计划任务是一个主要使用场景，而今天没有任何东西会拦住它，所以举证责任在于要不要新增一道关卡 |
| 配置变更如何版本化，并关联到既有的 TaskRun 记录？ | 取决于最终采用哪种方案 |

无论最终走向哪个方案，以下内容都不在范围内：一门通用的策略语言，以及取代操作系统、Kubernetes、云平台或网络层的控制手段——配置应当*驱动*一条 NetworkPolicy，而不是重新实现一条。

当前最容易补齐、却仍然缺失的输入，是一份覆盖恶意提示词和模型自主选择的 shell 命令的威胁模型，并且要针对现有的隔离机制去评估，而不是针对隔离机制出现之前的状态。有了它，出站允许列表才能成为一个有证据支撑的决定，而不是一个猜测。

[Agent 沙箱策略](./Agent沙箱策略.md)针对上表前两行给出了一个方案，范围比笼统的“分层的按 Space 配置”要窄：它只针对 `SandboxConfig` 里的 `Network`/`Filesystem` 这两个维度重新采用“默认部署级统一”的思路，把这两个维度收敛成一小组固定的、按 Agent 版本划分的档位，其他维度以及运维人员 `policy.yaml` 设置的上限则完全维持本节已经确定的做法。集群出站访问这一行仍然悬而未决，属于本节而不是那份文档要解决的问题。

## 4. 当前明确不在范围内

当前 P0.5 范围内不应包含以下内容：

- 检查点与回滚
- 完整的工作区恢复
- 完整的 Portal 审计产品
- 重写 Workflow 引擎
- 插件市场
- IDE 扩展
- 用 Go 实现容器/seccomp
- 大范围的版本化工作区实现

如果未来某个时候真的启动了版本化工作区能力——目前既没有计划，也没有对应的设计记录——检查点与回滚可以重新被讨论，但它们不应当阻塞这一轮 P0.5 的工作。

## 5. 建议优先级

建议的实施顺序：

1. 持久化运行轨迹
2. 沙箱与执行边界
3. 记忆与指令
4. 活动视图
5. 自检与诊断
6. Runtime Hooks
7. 子代理可追溯性
8. 更安全的 Worker 执行打磨

这个顺序先让这个领域获得更好的可见性，再获得更好的控制力，最后再扩展更多能力。

## 6. 验收标准

满足以下条件时，P0.5 才算成功：

- 用户可以查看一次运行中发生了什么
- 用户可以理解工具审批和拒绝的决策依据
- 用户和运维人员可以理解当前生效的沙箱边界
- 本地环境搭建问题容易诊断
- Worker 运行会产生有用的诊断轨迹
- 记忆是有作用域、可查看、可由用户控制的
- Hook 能够支持常见的自动化使用场景
- 子代理的行为可以被追溯归因，并且受策略约束
