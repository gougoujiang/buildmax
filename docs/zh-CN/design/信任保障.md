## 1. 目的

P0 已使共享 Agent Core 足够稳定，可供 CLI、Desktop、Portal 和 Worker TaskRun 使用。P0.5 的目标是提高核心的可信度和可运维性。

本文刻意停留在产品能力层面：列出 BuildMax 接下来应支持的关键能力，但不规定具体实现结构。
## 2. 方向

P0.5 应首先聚焦共享 Agent Core。CLI、Desktop、Portal 和 Worker 应以适合各自界面的方式暴露相同的核心能力。

目标是：

> 用户与运维人员能够理解、控制并调试 Agent 运行。
## 3. 需要支持的关键能力

### 3.1 Runtime Hooks（已交付）

Runtime Hook 系统已经实施，详细设计见[Hook 系统](./Hook系统.md)。

**配置位置。** 两层输入合并为一套配置：
- 全局：`<BUILDMAX_HOME>/settings.yaml` 中的 `hooks:`；
- 工作空间：`<workspace>/.buildmax/hooks.yaml`。

**执行方式。** 每个条目通过 `type:` 选择一种：
- `command`：在 stdin 上接收 JSON；
- `http`：发送 JSON 请求；
- `mcp_tool`：调用已连接 MCP Server 上的工具；
- `prompt`：执行单轮 LLM 评审。

### 3.4 活动视图

本地界面应提供轻量的活动视图。

TUI 和 Desktop 应让用户查看：

- Agent 当前正在做什么；
- 使用了哪些工具；
- 发生了哪些审批；
- 发生了哪些变更；
- 运行为什么失败或停止。

正常聊天应保持简洁，活动信息采用渐进式披露。

### 3.5 自检与诊断

支持面向本地配置和运行时问题的诊断流程。

应该检查：

- 模型配置
- 工作空间权限
- Git 提供商
- 活动沙箱模式
- 活跃记忆和指令来源
- 子代理 MCP；
- Skill 与工具发现；
- 子代理配置；
- BuildMax 数据目录健康状况。

诊断应产生可执行的建议和脱敏摘要，便于共享和调试。

### 3.6 记忆与指令

保持三份契约彼此分离：指令是规范性协议，记忆是可能出错的 Agent 调度回忆，会话历史是对话的顺序证据。压缩摘要是有损的历史投影，不是长期记忆；它只是为了帮助模型回忆。

记忆必须有明确范围并可见。会话笔记和 todo 属于当前会话的工作记忆；共享 CLI/Desktop Project 身份和有限的 Project 记忆见[本地项目记忆](本地项目记忆.md)。全局用户记忆、未来的 Space 记忆和可复用 Agent 记忆仍是独立范围，不能把 `AGENTS.md` 或 Agent 指令误当成记忆。

Agent 应暴露本次运行加载了哪些指令、记忆和历史投影来源。用户应能检查、更新、删除或禁用记忆。BuildMax 不应静默保留敏感或令人意外的信息；记忆也绝不能替代 `AGENTS.md`、Skill、子代理定义或 Agent 指令等规范来源。

### 3.7 子代理可追溯性

为子代理执行提供更清晰的可见性。

用户应该能够看到：

- 哪个子代理在运行；
- 为什么被调用；
- 它收到的记忆和指令来源；
- 它使用了哪些工具；
- 运行时限制；
- 结果是什么；
- 它与父运行的关系。

应避免只能显示“正在运行”而无法解释原因的黑盒状态。

### 3.8 更安全的 Worker 执行

为非交互式运行提供 Worker 特有的信任保证。

Worker 运行应：

- 在需要审批时明确失败，而不是静默放行；
- 在明确的沙箱边界内运行；
- 记录足够的轨迹供 Portal 诊断；
- 只加载适合 Space/运行范围的记忆和指令；
- 让拒绝原因可理解；
- 避免本地与远程能力悄然漂移。

### 3.9 谁选择 Worker 的边界（开放问题）

该问题承接已退役的 *Agent 执行策略* 提案。Worker 执行的四个方面已经确定，并在上文或[沙箱边界](./沙箱边界.md)中描述：运行持有什么、运行在哪里、资源限制以及记录什么。尚未解决的是**谁拥有决定权**。边界不能只由部署脚本隐式决定：集群运维人员可能加固每个 Worker，也可能完全不加固，而系统没有定义请求的限制无法使用时应发生什么。过去沙箱并未覆盖所有界面，因此这个问题一直没有被明确提出。

其中一部分已经解决：Worker 如何访问*服务器*。Worker 控制 API 通过独立的 TLS listener 提供，由内部 Service 和 NetworkPolicy 保护，只允许带标签的 Worker Pod 访问，见[Worker API 网络边界](./Worker API网络边界.md)。这限制 Worker 到服务器的流量，但不决定 Worker 能否访问 Git 主机、软件包注册表或模型端点。

真正的空白是一般网络出站访问。当前 Worker 可以访问集群允许的任何目的地；`deployment/production/README.md` 应明确记录这一缺口，而不是让人误以为已经存在域名边界。

我们考虑过四种形状。按用户或按运行配置被排除：它们无法给运维人员提供权威的 Worker 边界。完全交给集群表达虽然一致，却让 BuildMax 无法记录或解释自身不建模的边界，也不满足 Beta 门槛。因此当前选择是 `server.yaml` 中按部署生效的配置，层级高于运维/Space/Task 配置。**在有证据证明需要更细粒度之前，保持部署级范围**，因为它更简单；需要 Space 级限制的运维人员必须明确提出并承担相应复杂度。

仍待决定的问题，以及每个问题需要的证据：

| 问题 | 什么会解决这个问题 |
|---|---|
| 问题 | 需要什么证据 |
|---|---|
| Space 级边界是否真的需要？ | 运维人员明确声明需求，而不是默认推断。 |
| 配置文件缺失时应失败，还是记录警告后降级？ | 当前更倾向于降级，并在轨迹中报告无沙箱运行（§3.3）；`FailIfUnavailable: true` 可用于强制失败。 |
| Worker 合法需要访问哪些目的地？ | 生产参考配置应默认拒绝网络访问，并通过完整冒烟运行证明任务仍能访问实际需要的包注册表、Git 主机和模型端点。允许列表应来自真实运行证据，而不是假设。 |
| 这里是否需要审批门？ | 当前重点是无人监督的自定义工作，暂不增加额外审批门。 |
| 如何对配置文件变更版本化，并附加到现有 TaskRun 记录？ | 需要先确定配置模型和运行轨迹格式。 |

无论最终采用何种形式，都不应发明一门取代操作系统、Kubernetes、云平台或网络设备控制面的通用策略语言。配置文件应该*驱动*这些网络策略，而不是重新实现它们。

当前最便宜、也最关键的缺失输入，是针对恶意提示和模型选择命令的威胁模型；评估应与现有控制比较，而不是与过去没有控制的状态比较。

当前建议比“每层 Space 一个配置文件”更窄：重新启用 `SandboxConfig` 的 `Network`/`Filesystem` 轴，并保持其他轴和运维人员的 `policy.yaml` 上限不变。集群出站访问仍属于本节的开放问题，而不是本记录已解决的内容，见[Agent 沙箱策略](./Agent沙箱策略.md)。

## 4. 当前明确不在范围内

当前 P0.5 范围不包括：

- 检查点与回滚
- 完整工作空间恢复
- 完整的 Portal 审计产品
- 重写 Workflow 引擎
- 插件市场
- IDE 扩展
- 使用 Go 实现容器或 seccomp
- 广泛的版本化工作空间实现

如果未来采用版本化工作空间能力，可以重新讨论检查点与回滚；目前没有对应计划或设计记录，但它们不应阻塞本次 P0.5 工作。
## 5. 建议优先级

建议实施命令：

1. 持久化运行轨迹
2. 沙箱与执行边界
3. 记忆与指令
4. 活动视图
5. 自检与诊断
6. 子代理 Runtime
7. 子代理可追溯性
8. Worker 执行安全的完善

这个顺序先提高可见性，再增加控制，最后扩展到更广泛的运行安全。

## 6. 验收标准

满足以下条件时，P0.5 才算成功：

- 用户可以检查运行中发生的事情；
- 用户可以理解工具被允许或拒绝的原因；
- 用户和运维人员可以理解当前生效的沙箱边界；
- 本地配置问题容易诊断；
- Worker 运行产生有用的诊断轨迹；
- 记忆可衡量、可检查、可控制；
- 子代理支持常见自动化场景；
- 行为可以归因到具体的运行和调用方。
