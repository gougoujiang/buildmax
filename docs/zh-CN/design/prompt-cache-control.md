## 1. 问题

Agent 会反复提交很长且稳定的前缀，包括系统指令、工具定义、技能、
工作区指令，以及逐步增长的对话历史。提示缓存能显著降低后续调用的成本和
延迟。这是常规运行时问题，而不是面向单个用户的微优化。

目前的实施是有用的基础，但不是完整的政策：

| 范畴 | 当前行为 | 缺口 |
|---|---|---|
| Anthropic | Agent 轮次默认使用 `auto`，包含静态和滚动断点，并可显式选择 1 小时保留（阶段 2）。 | — |
| OpenAI Responses | 发送派生且带作用域的 `prompt_cache_key`，可选择 24 小时保留（阶段 3）。 | `prompt_cache_options` 尚未验证，因此有意不发送。 |
| OpenAI 兼容端点 | 声明不具备缓存能力，不发送控制字段；通过资格验证后，命名的 `integration` 可选择启用（阶段 4）。 | 所有集成名称目前都被拒绝；第 10 节决定保持这一状态，因为兼容路径已能报告其上游行为。 |
| 计量 | `core/llm.Usage`、运行统计、追踪、会话汇总、本地结果、托管账本和 Portal 均携带缓存读写令牌数（阶段 1）。 | 无法区分“请求了某种策略”和“提供商未报告结果”。 |
| 成本控制 | 已配置价格的模型可报告每次调用和运行成本，并按令牌类别与未缓存基线拆分（阶段 3）。 | 无法解释未命中原因：第 6 节诊断虽逐调用解析，但尚未离开 `internal/infra/llm`。 |

项目不得宣称无法证实的节省。缓存写入可能比普通输入更贵；短的一次性请求
无法摊薄写入成本；提供商还会规定因模型而异的最小长度和保留窗口。

## 2. 决策

BuildMax 将根据运行时意图和提供商能力，把提示缓存实现为**一等的逐调用策略**。

1. 当目标声明支持缓存时，常规 Agent 轮次默认使用 `auto`，而不是关闭。
2. 标题生成、压缩、探测等一次性实用调用默认使用 `off`；`force` 只留给
   预期会复用缓存的调用方。
3. 只向提供商发送其明确支持的控制字段；绝不假设
   `openai_compatible` 支持 OpenAI 或 Anthropic 的字段。
4. 缓存用量仍是提示/输入令牌的细分；成本根据提供商和模型价格另行计算，
   绝不从令牌数量推断。
5. 缓存遥测随每次调用结果传递，但账本和追踪不存储提示、缓存键或工具参数。

需要覆盖两条彼此独立的执行路径：

| 路径 | 调用方 | 策略权威来源 | 提供商调用 |
|---|---|---|---|
| 直接客户端 | 使用 `transport: direct` 的 CLI 和 Desktop | 本地选中的模型条目 | 本地进程调用 `internal/infra/llm`。 |
| 托管网关 | 使用 `transport: buildmax` 的 CLI/Desktop，以及调用托管补全路由的 Worker | Server 批准的目录目标和部署策略 | Server 解析目标并调用 `internal/infra/llm`；远程客户端不直接调用提供商。 |

两条路径使用同一套缓存策略词汇和遥测，但托管调用方绝不接收或控制提供商
缓存键、TTL 或原始提供商选项。网关是托管推理的最终策略决策点。

默认值变化只适用于符合条件的 Agent 轮次；它不会把每个模型请求都变成
缓存写入，也不会静默启用延长保留。

## 3. 目标与非目标

### 目标

- 减少支持供应商重复使用Agent预写的成本和延迟。
- 保持直接模式可移植性和管理门户的空间界限。
- 解释要求控制，提供商报告以及远程测量能力缺失。
- 允许运营商故意选择提供商支持的保留。
- 保持供应商政策在`internal/core/agent`之外；核心表示意图和
适配器将它翻译。

### 非目标

- 建立一个BuildMax所有的提示/KV缓存或本地保留提示。
- 处理缓存是免费的，或者是为了逃避代币配额。
- 提供商，凭证，模型，工具集，静态的可靠性
预示或保留窗口。
- 增加一个本土适配器，仅仅是为了暴露一个缓存。

## 4. 策略模型

配置采用结构化政策：

```yaml
models:
  - model: claude-sonnet-5
    provider: anthropic
    cache_control:
      mode: auto             # auto (default), off, force
      ttl: provider_default  # provider_default, 5m, 1h, 24h where supported
```

模型目录显示相同的形状。 持久目录字段仍然是明确的，并且`snake_case`；电线形状是实现细节。

| 模式 | 转向Agent | 实用/一次性通话 | 没有支持的目标 |
|---|---|---|---|
| `auto` | 要求提供商的经济违约行为。 | 不要要求缓存。 | 没有发送控制器； 报告`unsupported`。 |
| `off` | 没有控制。 | 没有控制。 | 没有控制。 |
| `force` | 要求缓存，即使无法确定重复使用。 | 要求缓存。 | 拒绝配置，而不是假装它工作。 |

取代的`prompt_cache: bool`是删除的，而不是作为简体字母.它被写成是兼容路径，这是预发行项目的错误呼叫：没有任何东西被部署，必须继续工作，两家商店无法同意`false`的意思。 `*bool`

### 4.1 每次调用的意图

配置本身不能决定调用是否会重复使用.共享的LLM请求边界获得打入的调用配置文件：

| 个人资料 | 产品： | 默认缓存模式 |
|---|---|---|
| `agent_turn` | `core/agent.RunLoop` | 解决模型政策 (默认情况下`auto`) |
| `title` | `agentapp.SessionManager` | `off` |
| `compaction` | `agentapp.LLMCompactor` | `off` |
| `evaluation` / `probe` | 直接选择呼叫者 | 没有选择的`off` |

合同从定位 `messages, tools`参数发展到包含消息，工具和配置文件的请求对象.在未打字的 `context.Context`中通过政策，或从即时文本中推断，被拒绝：一个充电的提供商行为必须是可见的给调用者和测试。

核心拥有`agent_turn`，但从来没有进口供应商类型或选择TL.`agentapp`标签标题/紧缩工作;`internal/infra/llm`解决了配置文件和模型设置在供应商请求中。

### 4.2 直接客户端和管理网关解决方案

直接CLI/Desktop调用解决在`agentapp.LLMClientCache.build`中选定的`settings.yaml`模型的政策，然后将有效请求配置文件传递给本地提供商适配器.这是用户本地设置可以选择自己的提供商帐户的缓存控制的唯一途径。

管理的CLI/Desktop调用使用`infra/llmremote`和空间完成端点.Worker调用使用工作者完成端点和运行代币.在两种情况下，远程请求只携带`call_profile`；它既不携带`mode`,TTL，提供商集成配置文件，也没有缓存密钥.服务器：

1. 验证调用者，解决空间或任务运行身份；
2. 解决其目录目标的批准别名；
3. 验证目标缓存能力和部署政策；
4. 将该政策与收到的呼叫配置文件结合起来；以及
5. 创建提供商请求并记录返回的诊断。

客户端提供的配置文件是操作输入，而不是授权输入.网关将未知的配置文件视为无效，从来不允许请求选择`force`或延长存储.这阻止本地客户端通过手工制作BuildMax终端点请求来绕过运营商的缓存，存储或租户隔离政策。

相关标识符获得了添加式，验证的 `call_profile` 字段。 相关标识符仅获得安全有效的诊断和使用数量；它从来没有返回一个不透明的缓存密钥或上游供应商配置.空间，工作者和 HTTP 完成处理器必须分享这个服务器侧分辨率功能，以便他们的行为不能漂移.服务器所有 Tier 1 调用相同的功能在进程中，而不是通过发出HTTP 调用回服务器。 `llmwire.CompletionRequest` `CompletionResponse`

## 5. 提供商能力契约

缓存支持属于模型目标，而不是协议标签.目录功能集获得缓存描述符；直接设置从其提供商和明确的本地集成配置文件中获得一个。

| 目标类 | 子代理 `auto` | 操作员控制 | 电测 |
|---|---|---|---|
| 关于""的信息 Anthropic | 系统/工具后稳定断裂点加上最高级别滚动断裂点。 | 默认5分钟的TTL;1小时是明确的选择。 | 读写代币，要求的战略，有效的TLT。 |
| 博相关标识符 答案 OpenAI | 稳定范围的`prompt_cache_key`；隐含缓存，除非模型支持明确模式。 | 具有能力的TTL/保留和明确/隐含的选择。 | 缓存输入，缓存写入，返回时请求/有效的选项。 |
| 查看OpenAI 聊天完成在OpenAI | 只有模型文件的控制。 | 答案的能力限制政策。 | 提供商报告的计数器。 |
| 适合OpenAI | 默认`unsupported`；一个命名的门户配置文件可能会选择。 | 仅验证的特定集成领域。 | 仅有文档化集成领域。 |

描述符在直接模型或目录目标加载时验证，并被包含在路由客户端缓存键中.操作员编辑不能将旧的缓存政策附加到缓存客户端中。

### 5.1 Anthropic放置

随着系统的缓存,相关标识符将可缓存输入作为工具，系统，然后是消息。 BuildMax在稳定的系统区块后保留了明确的断点，缓存工具和指令，以及一个高级自动标记器用于不断增长的对话.后者并没有取代前者：自动回顾只发现之前在滚动终点附近写的前置。 Anthropic

如果没有系统块，但可重复使用的工具存在，则适配器必须仍然标记稳定工具边界；它不能仅缓存变化的最终用户消息。 当提供商报告没有读或写，诊断报告已知原因，如不支持的平台或短先fix，当可检测而无猜测。

### 5.2 OpenAI缓存密钥隔离

OpenAI 密钥是一个缓存路由提示，而不是授权界限，但它不能将无关的提示群体带入。 BuildMax 从：

```text
provider-account/credential identity + target/model + space (managed only)
+ system-prompt fingerprint + toolset fingerprint + cache-policy version
```

它不包括原始提示内容，工作空间路径，用户名，消息，凭证和用户提供的识别符.它从未存在于账本，追踪,Portal,CLI输出或日志中.它随着静态输入变化而改变，有利于正确的缓存。

## 6. 用量、成本与诊断

已有相关标识符的`CacheReadTokens`和`CacheWriteTokens`；这两者仍然是`PromptTokens`的子集。 请求结果还包含有限的诊断： `core/llm.Usage`

| 领域 | 意思 |
|---|---|
| 要求模式 | 解决了`off`,`auto`或`force`政策。 |
| 提供商的能力 | 子代理 `supported` `unsupported` |
| 战略 | 其他类型的子代理， `anthropic_static_and_rolling` `openai_implicit` `none` |
| 有效的TTL | 只有在不含糊的情况下要求或返回。 |
| 结果 | 相关标识符,`write`,`mixed`,`miss`，或`unreported`；从零点上永远不要推断错误。 `hit` |

场地通过Agent事件流,`RunStats`，耐用跟踪，本地会议/转换结果,`llmwire`，管理`llm_call`响应,Portal API视图.本书已经存储计数器；其公开总结必须暴露它们.一个跟踪计数和政策结果记录，而不是缓存密钥。

对于直接的CLI/Desktop电话，该流程始于本地适配器结果.对于一个管理的电话，服务器将有效的诊断和使用连接到完成响应后，它关闭了提供商电话账本；远程客户端只将结果转发到本地Agent。 任何路径都不能取代提供商报告的数量以本地猜测的击中。

费用是单独的.一个版本的模型定价记录提供了基入，缓存阅读，缓存写和输出率加上货币/有效日期.只显示了估计，只显示了所有费用和使用率；否则显示了`unavailable`。 视图分离了未缓存的输入，读取和写入；显示了一个反事实的基入成本；只报告了节省，只会是正确的。

库存折扣不能使一个空间看起来已经完成了更少的工作或默默放宽现有的代币限制。

## 7. 安全与保留

快速缓存是提供商保留快速预写，而不是无害的本地性能标志。

- 能力配置文件声明保留选择；延长保留是选择。
- 直接用户选择提供商/账户的风险。
选择目标；空间不获得规则规避的过失。
- 密钥和个人资料由凭证和空间来确定，以管理推断。
- 静态指示中的可能秘密的警告`force`或延长保留。
警告不是完全的秘密探测器，也不会阻碍正常工作。
- 总计，跟踪和诊断只包含数量和结果，从来没有
预置，哈希输入，不透明密钥或提供商响应机构。

## 8. 备选方案

| 其他方法 | 为什么没有选择 |
|---|---|
| 保持一个选择的布尔式 | 无法区分一个标题与多转工具循环，使得核心Agent保存被禁用。 |
| 缓存所有请求 | 写作可能比输入更贵， |
| 处理每个兼容的终端点为OpenAI | 具有JSON兼容性不是特征保证； 字段可以被忽视或拒绝。 |
| 只有适配器中放出政策 | 电话的目的，配置和远程测量将在提供商和表面上漂移。 |
| 建立一个本地提示缓存 | 它改变了保密性，无效性，内存和工作者语义，同时无法重复使用提供商KV状态。 |
| 仅从代币计数中获得储蓄 | 价格因模型,TLT，读写类和提供商而异。 |

## 9. 交付计划与验收

### 阶段1 真实基线和远程测量 (出货)

- 纠正过时的缓存文件。
- 扩散现有缓存计数器到统计数据，事件，痕迹，本地结果，
管理完成响应，管理本书API和Portal。
- 直接覆盖CLI/Desktop的建筑和所有管理完成终点：
服务器的流程级1路径。
- 加入缓存计数/诊断器到运行支出视图，并保留`unreported`。
- 添加所有当前协议使用形状和管理的回路。

**接受：**从Agent转向表面，无双计数提示令牌可见提供商报告的缓存读/写。

计数旅行相关标识符 → `agent.RunStats`和 `agent.Event` → 追踪`llm_end`和 `run_end` → `session.Session`总数 → `agentapp.RunResult`/`RunUsage` → CLI， 相关标识符，以及 为管理的相关标识符 总数 → 报道提供商测试相关标识符 `llm.Usage` `llmwire.Usage` `llm_call` `0 / 0` Desktop Portal

部分6 所要求的模式，能力，战略，有效的TTL，结果的诊断不属于第一阶段。

### 阶段 2 政策和Anthropic默认 (出货)

- 添加结构化政策，兼容性分析，呼叫配置文件和功能
验证
- 启用`auto`在符合条件的Anthropic Agent转中；保持静态和滚动
断点；支持明确的1小时的选择。
- 默认关闭标题/紧缩/探测号。
- 让门口，而不是`llmremote`，解决有效管理
预存文件的目标目录和验证的呼叫配置文件。

**接受：**直接CLI/Desktop和每个管理终端点都做出相同的目标政策决定；一个具有资格的连续工具循环，具有不变的静态输入，观察到写入，然后读取；仅使用`auto`的标题调用，没有控制。

执行过程中达成了两个决定，并且在这里记录，因为上述计划没有：

`prompt_cache`缩写部分4已经消失。 实施它表明为什么：设置文件可以用指针区分缺席的 `false`，而非零列不能，因此同一场字段将意味着"关闭"在一个商店和"默认"在另一个商店。 预发行项目没有理由携带这一点。 `cache_mode`是商店都声明这一点的唯一方式，而一个未设置的行则默认。

拒绝`force`是没有缓存说明的目标，而拒绝`auto`是.拒绝`auto`将使默认模式无法用于大多数目标；在那里默默地服务`force`，因为没有缓存将回答没有人问的问题。

部分6诊断 要求模式，能力，战略，有效的TLT，结果 每次通话都得到解决，但尚未离开`internal/infra/llm`.将其带到表面是剩余的债务，它属于4阶段：读者需要它们的原因是错误背后的解释，并标识第10节的资格运行比错误，所以除了计算之外，还没有什么可说的真实。

### 阶段3  OpenAI原产控制和成本估计 (运输)
