## 1. 目的

模型早已能够批量发出工具调用，但运行时并不会并发执行它们。

`DefaultSystemPrompt` 告诉模型“在同一条消息里调用多个工具，使它们可以并行运行”
（`internal/agentapp/prompt.go:51`），`Glob` 的描述也重复了这条建议。传输链路确实
遵守了这一点：一条 assistant 消息可以携带 N 个调用，阻塞式客户端和流式客户端都会
重建完整的调用列表（`internal/infra/llm/client.go:115`、`:247`）。但随后
`executeToolCalls`（`internal/core/agent/agent.go:347`）用一个普通的 `for` 循环
逐个执行它们。

所以今天的批量调用只换来一件事——更少的 LLM 往返次数。它买不到实际的挂钟时间：
一次读取五个文件的回合，要老老实实地把五次文件读取都执行完；一次抓取三个 URL 的
回合，要串行付出三次网络往返的代价，而网络受限的工具正是损失最大的地方。

本文档要定义的是：相邻的工具调用如何并发执行，同时**不改变本次运行产生的结果**——
无论调度器如何工作，消息历史、Hook 触发顺序、批准提示都保持相同的先后次序。

## 2. 当前基线

先说明已经可用的部分，以及哪些环节假定同一时刻只有一个工具在执行。

**单次调用的流水线是一个函数。** 对每一次调用，`executeToolCalls` 会反序列化
参数、在注册表中查找工具、发出 `EventToolStart`、检查循环保护，然后交给
`applyPolicyAndExecute`——由它解析策略、请求批准、运行 `PreToolUse` Hook、调用
`tool.Execute`、发出 `EventToolEnd`，再运行 `PostToolUse`。结果被追加到历史记录，
循环继续处理下一个。

**事件本身已经携带调用 ID。** `Event.ToolCallID` 会被设置在 `EventToolStart`、
`EventToolEnd` 和 `EventToolDenied` 上（`internal/core/agent/event.go:69`），
轨迹记录器和 Desktop 都以它为键。也就是说事件流本身早已为并发做好了准备；唯一把
这个 ID 丢弃的消费者是 CLI TUI。

**流水线所触及的状态，以及它们能否在并发下存活：**

| 组件 | 共享状态 | 目前是否并发安全 |
|---|---|---|
| `trace.Recorder.Record` | 文件、缓冲区、计数器 | 是 —— `r.mu` 保护每一次写入 |
| `HookManager.Run` | 匹配器缓存、配置 | 缓存安全；配置不安全 —— 已在 §5.7.1 中修正 |
| `Read`、`Glob`、`Grep`、`Skill` | 无 | 是 —— 在工作区根目录下无状态 |
| `WebFetch` | 响应缓存 | 是 —— 由 `cacheMu sync.RWMutex` 保护 |
| `Bash` | 无（`WithSandbox` 返回副本） | 结构体本身安全，但其副作用不安全 |
| `loopGuard.counts` | `map[string]int` | **否** —— 未加同步的 map |
| `Session.Append`、`SetNotes`、`SetTodos` | Session 上的切片 | **否** —— 没有互斥锁 |
| `Model.currentToolArgs`（TUI） | 用于当前调用的单个槽位 | **否** —— 假定同一时刻只有一次调用 |
| `DesktopApprovalHandler.pending` | 单个响应 channel | **否** —— 第二个请求会让第一个变成孤儿 |

前五行意味着：读取、搜索和抓取这些不产生副作用的负载，本来就可以安全地并发执行。

## 3. 缺口

### 3.1 循环完全没有并发能力

`executeToolCalls` 只是对 `toolCalls` 做一次顺序遍历。`internal/core/agent`
和 `internal/tool` 中都没有任何地方启动 goroutine。

### 3.2 运行时不知道哪些工具会写入

`llm.Tool` 只有四个方法，没有 effect（副作用）的概念，也无法从策略层反推出这个
分类：`ReadFile.CheckArgs` 和 `WriteFile.CheckArgs` 逐字节完全相同——对敏感路径
都返回 `Ask`，其余情况都返回 `Allow`（`internal/tool/read_file.go:57`、
`internal/tool/write_file.go:51`）。那条轴线衡量的是*敏感度*，而不是*副作用*。

因此运行时无法区分一次文件读取和一次文件写入，除了按最坏情况调度之外没有别的
依据。

### 3.3 循环保护和会话都假定只有一个写入者

`loopGuard.exceeded` 会递增一个裸 map。`Session.Append` 和 `Session.SetNotes`
在没有任何锁的情况下修改切片，而 `NoteWrite`/`TodoWrite` 则通过 `Execute` 内部
的 `NoteStoreFromContext` 触达会话。

### 3.4 TUI 会把结果和错误的参数配对

`eventSinkToChannel` 在构建 `toolStartMsg` 和 `toolEndMsg` 时丢弃了
`ToolCallID`（`internal/interface/cli/tui_model.go:151`），而 Model 只保留一个
`currentToolArgs` 字符串供 `handleToolEnd` 读取。当两个调用同时在跑时，渲染出来
的那一行会把第二个调用的参数和第一个调用的结果配对在一起。

### 3.5 一个批准提示的生命周期超出了它所属的运行——已修复 ✅

这个缺口最初被当作并发缺陷来记录：`RequestApproval` 只保存一个 `pending`
channel，两个并发的提示会让第一个变成孤儿。但这个判断是错的，而第 1 阶段的实现
恰恰证明了这一点。批准始终留在循环 goroutine 上处理（D1），因此处理器根本不会
看到并发的调用——并发问题是被架构提前挡住的，而不是被修复掉的。

真正的缺陷是取消（cancellation），而它压根不需要任何并发能力。
`ApprovalHandler.RequestApproval` 不接收 context，只是阻塞在一个 channel 上。
如果用户在提示还挂着的时候取消了一次 Desktop 运行，运行所在的 goroutine 就会
一直等待一个永远不会到来的答案；它的延迟清理逻辑永远不会执行，
`runCancels[projectID]` 也就永远不会被删除，导致该项目永久停留在“已有一次运行
正在进行”的状态。

修复方式是把运行的 context 交给处理器，并让两种实现都对 `ctx.Done()` 做
select。单个 `pending` 槽位被原样保留了下来，因为根本没有并发的调用会触达它。

## 4. 方向

六条不变式。第 5 节的一切都由它们推导而来。

- **D1 —— 串行决策，并发执行。** 参数解析、循环保护、策略解析、批准，以及
  `PreToolUse` 门控，全部在循环 goroutine 上按调用顺序执行。只有 `tool.Execute`
  会跑在 worker 上。
- **D2 —— 绝不重排。** 调用按模型发出的顺序执行。只有*相邻*的只读调用才会被
  归为一组；任何一次写入都是一道屏障。
- **D3 —— 历史记录与调度器无关。** 结果按调用顺序追加。同一次运行的消息列表，
  无论并发上限是 1 还是 16，都必须逐字节相同。
- **D4 —— 每次调用永远只对应一个结果。** assistant 消息里的每一个 `tool_call`
  都会得到恰好一条 `role: "tool"` 消息，无论是被拒绝、发生 panic 还是被取消。
  一批调用即便只执行了一半，也要为下一次 LLM 调用留下一段格式完好的历史记录。
- **D5 —— 只有只读调用才会重叠执行，且必须显式声明。** 一个工具自己声明它的
  调用是否只读；任何未声明的调用都按写入处理，像今天一样串行执行。
- **D6 —— 串行路径始终可达。** 把并发上限设为 1，就能精确恢复今天的行为，作为
  一个兜底的应急开关。

## 5. 范围内

### 5.1 调度依据的是什么

分类本身不在本文档中定义。`llm.Access` 和 `llm.AccessDeclarer` 由
[tool-permissions.md](./工具权限.md) 第 5.1 节定义，工具通过它声明一次调用是否
会改变任何东西：

```go
const (
    AccessWrite Access = iota // zero value: undeclared tools are writes
    AccessReadOnly
)
```

这项设计消费该声明，并在其上叠加一条义务：

> **`AccessReadOnly` 是一次调用能与相邻调用重叠执行的必要条件，但不是充分
> 条件。** 这次调用还必须能安全地被多个 goroutine 同时执行，而这并不会仅仅
> 因为它只读就自动成立。

`WebFetch` 正是证明这个缺口存在的例子。它相对于工作区是只读的，却仍然会修改
进程内的一份响应缓存；它之所以够资格并发，只是因为 `cacheMu` 保护了那份缓存。
如果去掉这把锁，它依旧只读，权限判断依旧是 `Allow`，却不再可以被调度器并发
执行。

所以调度器的资格规则是：

```text
eligible = Access(args) == AccessReadOnly  AND  the tool is goroutine-safe
```

后半句是工具作者在声明 `AccessReadOnly` 时所接受的契约，记录在
`docs/contribute/architecture/tools.md` 中，并由 `./make test race` 而不是
类型系统来强制执行。一个什么都不声明的工具就是 `AccessWrite`，单独执行——这正
是 D5，也意味着这个特性落地时不需要改动任何一个已有工具。

权限层对同一个分类做了不同的映射——只读映射到 `Allow`，写入映射到 `Ask`，并
允许逐工具覆盖。这两个消费者可以合理地得出不同结论：`TodoWrite` 和
`NoteWrite` 在权限层是 `Allow`（它们只写 Agent 自己的草稿状态），但在调度层
不合格（那份状态没有锁）。一个事实，两种映射；参见 tool-permissions.md §5.2。

### 5.2 分组

解析一次调用——反序列化参数、在注册表中查找工具——没有副作用，因此会被提到
整批调用执行之前完成。分组随后只遍历一次已解析的调用，向每一个调用询问它的
`Access`，并在每一个非只读调用处切出一个新的组：

```text
[Read a, Read b, Grep c]              -> one group of 3
[Read a, Write b, Read c]             -> [Read a] [Write b] [Read c]
[Read a, Read b, Bash x, Read c]      -> [Read a, Read b] [Bash x] [Read c]
```

参数反序列化失败、或工具未知的调用，会独自成组，永远不会和相邻调用合并。

各个组严格按顺序处理。组内部，门控按调用顺序执行，执行阶段可以重叠，提交阶段
仍按调用顺序进行。只有一个调用的组，其代码路径与今天逐位相同——这正是 D6 成本
低廉的原因。

### 5.3 重写后的循环——已交付 ✅

```go
func executeToolCalls(ctx context.Context, opts RunLoopOpts, toolCalls []llm.ToolCall, guard *loopGuard) (int, error) {
    count := 0
    for _, group := range groupCalls(opts.ToolRegistry, toolCalls, opts.MaxParallelTools) {
        // 1. Gate — loop goroutine, call order: guard, policy, approval, PreToolUse.
        for i := range group {
            gate(ctx, opts, guard, &group[i])
        }
        // 2. Run — workers, bounded, only for calls the gate let through.
        runGroup(ctx, opts, group)
        // 3. Commit — loop goroutine, call order: PostToolUse, then history.
        for i := range group {
            firePostHook(ctx, opts, &group[i])
            if err := opts.History.Append(llm.Message{
                Role: "tool", Content: group[i].result, ToolCallID: group[i].call.ID,
            }); err != nil {
                return count, err
            }
            count++
        }
    }
    return count, nil
}
```

`runGroup` 用一个信号量限制并发度，并从工具的 panic 中恢复，这样一个出问题的
调用既不会拖垮整次运行，也不会让同组的其他调用被搁置：

```go
func runGroup(ctx context.Context, opts RunLoopOpts, group []pendingCall) {
    sem := make(chan struct{}, opts.MaxParallelTools)
    var wg sync.WaitGroup
    for i := range group {
        if group[i].decided { // denied, unknown, or bad arguments
            continue
        }
        wg.Add(1)
        go func(c *pendingCall) {
            defer wg.Done()
            defer func() {
                if r := recover(); r != nil {
                    c.result = fmt.Sprintf("error: tool %q panicked: %v", c.call.Name, r)
                }
            }()
            sem <- struct{}{}
            defer func() { <-sem }()
            c.result = execute(ctx, opts, c) // tool.Execute + EventToolEnd
        }(&group[i])
    }
    wg.Wait()
}
```

每个 worker 只写入 `group` 中属于自己的那个元素，`wg.Wait()` 构成了提交循环
读取这些结果之前的 happens-before 边界，因此结果本身不需要加锁。

### 5.4 各步骤运行在哪里

| 步骤 | Goroutine | 顺序 |
|---|---|---|
| 解析参数、注册表查找 | 循环 goroutine | 调用顺序 |
| `EventToolStart` | 循环 goroutine | 调用顺序 |
| 循环保护 | 循环 goroutine | 调用顺序 —— 计数结果与今天一致 |
| 策略解析、批准提示 | 循环 goroutine | 调用顺序 —— 一次只弹出一个提示 |
| `PreToolUse` Hook | 循环 goroutine | 调用顺序，在任何同组调用执行之前 |
| `tool.Execute` | worker | 重叠执行 |
| `EventToolEnd` | worker | 按完成顺序 |
| `EventToolDenied` | 循环 goroutine | 调用顺序 —— 每一次拒绝都在门控阶段就已决定 |
| `PostToolUse` / `PostToolUseFailure` | 循环 goroutine | 调用顺序，在整组汇合之后 |
| `History.Append` | 循环 goroutine | 调用顺序 |

有两处不对称是刻意为之。

**`EventToolEnd` 由 worker 在工具真正执行完毕时发出。** 事件流是一条实时反馈；
每个事件都携带 `ToolCallID`。如果非要等到同组里最慢的那个调用返回才报告完成，
UI 就会对“还有什么正在运行”这件事撒谎。

**`PostToolUse` 在组汇合时按调用顺序触发。** 后置 Hook 只是建议性质——它的
判断结果会被丢弃——但它同时也是一个审计界面，一个只是往日志里追加内容的脚本，
理应得到确定的顺序。代价是，一个建议性的 Hook 要等到组内最慢的成员完成。这笔
交易是划算的：一个在负载下会把顺序打乱的审计 Hook，比一个晚几百毫秒触发的
Hook 缺陷更严重。如果将来某个 Hook 确实需要按完成时间投递，那应该是一个新的
事件，而不是把现有事件的顺序打乱。

让整组的 `PreToolUse` 都先跑完、再执行任何一个成员，对于那些在调用之间检查
文件系统状态的 Hook 来说是一个真实的行为变化。但这也是不可避免的——调用本来
就是被设计成重叠执行的——而且这种情况只会发生在工具自己声明为安全的调用上，
根据 §5.1，这些调用不会写入任何东西。

### 5.5 事件契约

`RunLoopOpts.EventSink` 原本的文档说明是“由 `RunLoop` goroutine 同步调用”。
现在它变成了：*由循环 goroutine 或某个工具 worker 调用；运行时会将这些调用
串行化，因此 sink 每次只会看到一个事件，但仍然不能阻塞。*

`RunLoop` 在入口处对调用方传入的 sink 包装一次：

```go
func serializedSink(sink func(Event)) func(Event) {
    if sink == nil {
        return nil // nil stays nil: no allocation, no lock, zero overhead
    }
    var mu sync.Mutex
    return func(e Event) {
        mu.Lock()
        defer mu.Unlock()
        sink(e)
    }
}
```

这样一来，这个保证就留在运行时内部，而不必让 TUI、Desktop、轨迹、Portal 这些
消费方各自解决一遍。

### 5.6 批准与两个 UI

批准始终留在循环 goroutine 上（D1），因此 `ApprovalHandler` 永远不会看到并发
调用，两种实现也都不需要变成可重入的。Desktop 处理器上单一的 `pending` 槽位
因此原样保留：它看起来存在的问题其实是取消，而不是并发，而这个问题已经通过把
运行的 context 交给处理器解决了（§3.5）。

拒绝不会取消同组的其他调用。被拒绝的调用会把拒绝说明作为自己的结果，组里剩下
的调用继续执行——这和今天的行为一致，一次拒绝不会阻止批次中后续的调用。

TUI 有两处改动：工具消息携带了 `CallID`，`currentToolArgs string` 变成了一个
有序的 `[]activeTool`。两者都在第 1 阶段交付。多个并发工具应该如何*呈现*，是
一个体验问题而不是正确性问题——见第 11 节。

### 5.7 哪些工具符合资格

这里的 `Access` 取值，来自 tool-permissions.md §6 中的赋值。

| 工具 | Access | 是否符合资格 | 原因 |
|---|---|---|---|
| `Read` | 只读 | 是 | 在工作区根目录下解析路径并以只读方式打开；无共享状态 |
| `Glob` | 只读 | 是 | 文件系统遍历 |
| `Grep` | 只读 | 是 | 文件系统遍历 |
| `Skill` | 只读 | 是 | map 查找加 `os.ReadFile` |
| `WebFetch` | 只读 | 是 | 只写入自己的缓存，且由 `cacheMu` 保护；受网络延迟制约，因此单项收益最大 |
| `Write` | 写入 | 否 | 创建或截断文件 |
| `Edit` | 写入 | 否 | 对文件内容执行读—改—写 |
| `Bash` | 写入 | 否 | 副作用任意，无法从命令字符串判断 |
| `TodoWrite` | 写入 | 否 | 修改 `Session`，而它没有互斥锁 |
| `NoteWrite` | 写入 | 否 | 修改 `Session`，而它没有互斥锁 |
| `Task` | 取决于 Agent 类型 | 有时 | 嵌套的 `RunLoop` 会写入其子 Agent 工具所写入的一切，而工具集是被声明的 —— 见 §5.7.1 |
| MCP 网关调用 | 写入 | 否 | 第三方服务器在这两条轴线上都没有做出任何承诺 |

有两行特别值得关注，它们说明了为什么这条轴线衡量的是*副作用*，而不是*是否
触碰了文件系统*：

- `TodoWrite` 和 `NoteWrite` 从不写文件，却依然不合格。它们通过
  `NoteStoreFromContext` 修改会话状态，而 `Session.SetNotes` 没有锁
  （`internal/core/session/session.go:139`）。进程内的状态也是状态。
- `WebFetch` 则正好相反：它每次调用都会写入点什么，却依然合格，因为它写入的
  唯一东西是一份它自己拥有并加锁保护的缓存。

`Bash` 是一项如实承认的损失。Agent 发出的大多数 shell 命令其实都是读取——
`git status`、`ls`、`cat`，或者一次测试运行的前半段——但没有一个能够从命令
字符串出发，以调度器所要求的置信度被正确分类。所以它只能单独运行。

#### 5.7.1 `Task` 按 Agent 类型给出答案

前面的表格把 `Task` 简单地写成写入，并留到第 6 节处理，理由是嵌套的
`RunLoop` 会写入其子 Agent 所写入的一切。这个理由是对的，但这个问题其实可以
回答：子 Agent 的工具集不是从提示词里猜出来的，而是在运行开始之前就已经按
名称解析进了 `AgentTypeConfig.Tools`。逐一询问这些工具各自声明了什么，就能得
到调度器对整个嵌套循环所需要的同一个答案。

因此 `TaskTool.Access(args)` 会读取请求中的 `subagent_type`，只有当该类型能
触达的每一个工具都自我声明为只读时，才返回 `AccessReadOnly`。内置的
`explore`（`Read`、`Glob`、`Grep`）符合条件；`general` 和 `shell` 不符合，
`tools:` 列表中只要包含一个写入工具的用户自定义 Agent 同样不符合。有三种情况
被刻意判定为写入：

- **未知的类型**，因为这次调用即将失败，而一次失败的调用不应该和任何其他调用
  重叠过。
- **`run_in_background: true`**，因为它会修改任务管理器，并启动一段生命周期
  超出本次调用的工作。它在速度上的诉求其实也已经被满足了——它本来就会立即
  返回。
- **`nil` 参数**，这是一次能力清单查询（`internal/agentapp/app.go` 在手上
  没有具体调用的情况下报告某个工具的 access），而不是一次待调度的调用。

一个空的工具集出于同样的理由被判定为写入：一个所有工具名称都解析失败的类型，
不能因为找不到反例就被判定为合格。

这样做之所以安全，关键在于答案的来源。这里没有任何一步是从参数字符串里推断
副作用；这个分类读取的是每个工具本就会做出的声明，所以它出错的可能性，仅仅
取决于那些声明本身是否出错——而这些声明，正是串行路径在权限判断上早已信赖的
同一批声明。

第 5.1 节规则里关于并发安全的那一半，由子 Agent 运行本身的结构就已经满足了。
每一次运行都会构建自己的 `session.NewSession`、自己的注册表和自己的
`NoteStore`；它的 `EventSink` 指向自己的轨迹记录器，而不是父级的 sink；它的
`RunLoopOpts` 不携带任何 `Approval`，因此 `interactive()` 为 false，也就不
可能触达任何提示。嵌套运行在生产环境里本来就已经和父级重叠——自本地后台任务
第 1 阶段起，`run_in_background` 就已经把子 Agent 交给任务管理器去独立运行
了。把这种重叠变成同步且有界的，只是一小步，并不像原文最初设想的那么大。

确实有一处共享的缝隙需要修复：`HookManager.Run` 在读取 `m.cfg` 时没有持有
`m.mu`，而 `Refresh` 写入它时是持锁的。串行门控掩盖了这个问题；一旦子 Agent
的重叠运行从多个 goroutine 触达 `Run`，竞态检测器就会发现它。现在 `Run` 会
在锁内取出配置的副本，再基于这份副本分派。这也关闭了第 11 节里的最后一项。

#### 5.7.2 子 Agent 也要参与调度

`MaxParallelTools` 原本只到达了一层 `RunLoop`。子 Agent 的嵌套循环得到的是
零，这意味着每个组只能容纳一个调用，也就意味着——本设计刚刚让其合格的那些
只读 Agent 类型——它们自己的读取和搜索仍然严格一次一个地串行执行。现在运行
器会把父级的限制一并带入（`WithSubAgentMaxParallelTools`）。

Portal 对话运行时出于同样的原因存在同样的缺口。它的只读工具是 `ListTasks`
和 `GetTask`；两者现在都声明了 `Access`，整个回合按默认上限运行。`StartTask`
和 `ContinueTask` 仍然是写入，仍然是屏障。

### 5.8 配置

```yaml
agent:
  max_parallel_tools: 4   # 1 disables parallel execution entirely
```

`config.Settings` 下新增一个 `AgentConfig`，带有 `max_parallel_tools` 的
mapstructure 标签，并暴露为 `RunLoopOpts.MaxParallelTools`。零表示未设置，
会解析为默认值 4；取值会被限制在 `[1, 16]` 区间内。

选择 4，而不是“不设上限”：这个上限的存在，是为了保护文件描述符、大文件读取
所占用的内存，以及——对 `WebFetch` 和未来的 MCP 调用而言——远端的速率限制。
模型实际发出的批次通常是两到五个调用，因此 4 已经能拿到几乎全部的可得收益，
同时让失败模式保持无聊、可预期。

### 5.9 取消与失败

- **Context 被取消。** 各个 worker 共享运行的 context。正在执行的工具会返回
  各自的 context 错误，并成为该调用的结果字符串。提交循环仍然会为每一次调用
  追加一个结果（D4），因此历史记录保持格式完好，`RunLoop` 现有的取消路径会
  像今天一样返回那部分已完成的回复。
- **工具返回一个错误。** 行为不变：错误字符串就是结果，`PostToolUseFailure`
  在提交阶段触发。
- **工具发生 panic。** 每个 worker 会把它恢复为一个错误结果。今天 `Execute`
  里的一次 panic 会拖垮整个进程；这是“组需要汇合”这个需求顺带带来的一点小小
  改进。
- **`History.Append` 失败。** 和今天一样，立即带着目前为止的计数返回。已经
  提交的调用保留各自的结果。

## 6. 范围外

- ~~**并行执行 `Task` 子 Agent。**~~ 已交付——见 §5.7.1 和 §8 第 5 阶段。这里
  最初的推理经不起时间考验，值得把它记下来作为一个错误案例：这里列出的三个
  障碍（嵌套运行自己的事件流、它的批准提示、它的会话状态）其实都已经被子
  Agent 运行器解决了；第四个障碍——轨迹归属——则在这份记录被搁置未排期期间，
  由 durable-run-trace 和 local-background-jobs 交付了。真正剩下的问题是一个
  诚实的问题：“嵌套循环是否会写入”，而这最终被证明是一个由已声明工具集决定
  的属性，而不是需要靠推断才能知道的事。
- **在文件级加锁的前提下并行执行 `Bash` 或 `Edit`。** 预测一条 shell 命令会
  涉及哪些文件，不是运行时能够诚实做到的事。
- **让下一次 LLM 调用与工具执行重叠。** 推测执行是另一种设计，风险特征完全
  不同。
- **跨迭代的并行。** 一条 assistant 消息才是调度的单位。

## 7. 运行时流程

```text
assistant message: [Read a] [Read b] [Write c] [Grep d]
                          |
                   parse + group
                          |
        +-----------------+--------------+-----------+
        |                                |           |
   group 1 (parallel)              group 2 (solo)  group 3 (solo)
   [Read a, Read b]                [Write c]       [Grep d]
        |                                |           |
   gate a, gate b       (loop, in order) gate c      gate d
        |                                |           |
   exec a || exec b     (workers)        exec c      exec d
        |                                |           |
   join                                  |           |
        |                                |           |
   post+append a, then b (loop, in order) post+append post+append
```

批次执行完之后的历史记录：result a、result b、result c、result d——无论并发
上限是多少，永远是这个顺序。

## 8. 实施步骤

### 阶段 1 —— 让接缝变得安全（不改变行为）——已交付 ✅

- `RunLoop` 用 `serializedSink` 包装 `EventSink`；`RunLoopOpts` 的注释现在
  说明，sink 可能会被某个 worker 调用，因此必须按 `ToolCallID` 而不是按到达
  顺序去配对工具事件。
- TUI：`toolStartMsg`/`toolEndMsg`/`toolDeniedMsg` 都带上了 `CallID`，
  `currentToolArgs` 被替换为一个有序的 `[]activeTool`。用切片而不是 map，是
  为了让实时视图不会在帧与帧之间发生重排；当 ID 缺失时，匹配会回退到同名调用
  中最旧的一个，因此任何界面都不会漏掉一个转圈的 spinner。
- 批准逻辑接收运行的 context，并在取消时返回（§3.5）。Desktop 的 `pending`
  槽位**没有**按调用 ID 建键——至于为什么那对于一个真实存在的 bug 来说是一个
  错误的修复方式，见 §3.5。

### 阶段 2 —— 拆分循环（不改变行为）——已交付 ✅

- `executeToolCalls` 变成了 解析 → 分组 → 门控 → 执行 → 提交。`runGroup` 仍
  然是串行的；分组逻辑已经生效，但每个 surface 上的 `MaxParallelTools` 都是
  0，因此每个调用仍然各自成组。
- `internal/core/agent` 里所有既有测试都原封不动地通过了。这正是这个阶段的
  意义：如果这次重构有问题，问题会先在这里暴露出来——此时画面里还没有并发。
- 组是这一批调用的窗口（`calls[start:end]`），而不是副本，因此各个阶段修改
  的是真实的元素，提交阶段能看到执行阶段写下的内容。这一点由一个测试固定
  住，因为后续如果不小心混入一次 `copy`，会悄无声息地破坏结果，而不会大声
  报错。
- `TestHistoryIsSchedulerIndependent` 会比较并发上限为 1 和为 8 时的完整消息
  列表。它今天能通过，是因为单靠分组本身不会重排顺序；之所以现在就把它写出
  来，是为了让第 3 阶段在不满足这一条的情况下无法落地。

### 阶段 3 —— 声明与 worker ——已交付 ✅

- `runGroup` 会把一组调用放到有界数量的 worker 上执行，并从工具的 panic 中
  恢复，使其既不会拖垮整次运行，也不会让同组的其他调用被搁置。
- 门控逻辑也随之搬迁。`applyPolicyAndExecute` 不复存在：策略解析、批准提示
  和 `PreToolUse` 现在都是循环 goroutine（D1）上 `gateCall` 的一部分，执行
  变成了 worker 上的 `executeCall`，后置 Hook 在汇合时触发。这一步原本没有
  被规划进第 3 阶段的工作范围，但 §5.4 要求如此——如果不做这一步就直接加
  goroutine，批准提示就会跑到 worker 上去。
- `settings.yaml` 中的 `agent.max_parallel_tools`，通过
  `config.ResolveMaxParallelTools` 解析，默认值为 4，限制在 `[1, 16]` 区间
  内。一个加载测试守护着这个 mapstructure 标签：标签写错会得到零，而零会
  解析成默认值，于是这项设置会看起来在生效，实际上什么都没做。
- 对于只有一个调用的组，`runGroup` 仍然是内联执行——在默认配置下，只要还没
  有一批读取到来，每个组都是这种情况。常见场景下不会启动任何 goroutine。

### 阶段 4 —— 文档——已交付 ✅

- `contribute/architecture/agent-loop.md`：新增一个“工具执行”小节，包含
  阶段表、哪些会重叠哪些不会，以及那两处刻意为之的不对称。
- `contribute/architecture/tools.md`：新增一个“并发”小节，说明声明
  `AccessReadOnly` 所背负的义务，并以 `WebFetch` 为例说明只读和并发安全是
  两回事。
- `reference/configuration.md` 和 `manual/tools.md`：记录
  `agent.max_parallel_tools`，并为用户补充一段说明“哪些会重叠执行”。
- `design/hook-system.md`：说明 `PreToolUse` 会在整组任何成员执行之前触发；
  后置 Hook 在汇合时触发，仍按调用顺序。
- 在 `CHANGELOG.md` 的 `## [Unreleased]` 之下记录变更。

### 阶段 5 —— 子 Agent ——已交付 ✅

- `TaskTool.Access` 根据所请求 Agent 类型的工具集给出答案（§5.7.1）。这个
  分类只在 `NewTask` 里计算一次，因为工具集之后不会再变化，逐次调用都重新
  遍历一遍只是重复劳动。
- `WithSubAgentMaxParallelTools` 把父级的上限带入嵌套循环，Portal 对话运行
  时则按默认上限运行（§5.7.2）。`ListTasks` 和 `GetTask` 声明了
  `Access`——如果没有这一步，这个上限就会变成一项没有任何东西可调度的空
  设置。
- `HookManager.Run` 现在在锁内读取配置，关闭了第 11 节的最后一项。用之前的
  代码跑这个测试，在 `-race` 下会失败——而这也是唯一能确认一把锁是不是真正
  承重的方法。

## 10. 排期

`tool-permissions.md` 会先行交付，而且不仅仅是因为它拥有 `Access` 的定义权。

它的第 1 阶段引入了 surface 的概念，并且触及了和本设计相同的那五个
`RunLoopOpts` 调用点。如果反过来先落地本设计，就意味着先为了调度器把
`Access` 穿进循环，再回头去推导它对用户提示意味着什么——用一个事后选定的
权限模型，去迁就一个本来是为 goroutine 设计的分类。用户可见的决策应该塑造
分类，调度器则应该把它当作既定事实来接受。

实际的前置条件很窄：tool-permissions.md 的第 1 和第 3 阶段——在每一个内置
工具上声明 `Access`，包括 MCP 路径。它的第 2、4、5 阶段（session 授权、
配置、文档）是相互独立的，可以和本设计的工作并行进行。

*本设计*的第 1 阶段——事件 sink 的串行化、TUI 调用 ID 的修复、Desktop 批准
逻辑的键控——完全没有依赖，随时都可以落地。无论如何都值得尽早落地：§3.5 是
一个真实存在的死锁，而 tool-permissions.md 的第 2 阶段会给同一个批准提示再
增加第三种结果。

## 11. 待解决问题

- **TUI 呈现方式。** 当有四个工具同时在跑时，TUI 应该显示一份活跃行的列表、
  一个计数，还是只显示最近的一个？正确性已经在 §5.6 中解决，呈现方式还没

- **轨迹是否应该标记分组？** 带有调用 ID 和时间戳的 `tool_start`/`tool_end`

  了然，代价是要升一次 schema。
- **MCP。** 一旦网关拥有了能力描述符，并发性就可以按每个 server 声明，而不
  是一律拒绝。
- **子 Agent 的并发上限是否应该是一项独立的设置？** 目前它继承父级的上限。
  父级四个调用各自跑四个嵌套工具，就是十六个同时在飞——这正好碰到了限制的
  上限，却没有任何人主动要求过这么多。真实的批次要小得多，所以这是一个应该
  靠实测数据、而不是靠猜测来回答的问题。
- ~~`HookManager.Run` 在没有持有 `m.mu` 的情况下读取 `m.cfg`。~~ 已在第 5
  阶段修复；正是子 Agent 的重叠运行让这个问题变得可以被触达。
