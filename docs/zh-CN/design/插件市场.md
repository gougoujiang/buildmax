## 1. 决策

BuildMax 将插件视为一个可复用目录，其中直接包含已经能在 `.buildmax/` 下运行的
能力。插件增加分发和生命周期管理，不增加另一套运行时或扩展 API。

插件目录直接包含受支持的内容，**不会再嵌套另一个 `.buildmax/` 目录**：

```text
code-review/
├── plugin.yaml
├── README.md
├── skills/
├── agents/
├── mcp.json
├── hooks.yaml
└── hooks/
```

安装的插件直接在：

```text
<BUILDMAX_HOME>/plugins/<plugin-name>/
```

默认路径是 `~/.buildmax/plugins/<plugin-name>/`。遵守 `BUILDMAX_HOME` 可以让
测试、Worker 和隔离安装远离贡献者真实的主目录。

BuildMax 在同一目录格式上支持两种分发模式：

1. 直接克隆到插件目录的 Git 仓库；
2. 发布到部署私有插件市场、由用户显式下载的不可变版本。

两种模式共享验证、发现、运行时解析和诊断，但更新和信任语义有意不同：仓库是
开发者控制的工作树；市场发布是管理员发布的 Artifact，以版本和摘要标识。

## 2. 为什么需要两种分发模式

两种模式服务于同一生命周期的不同阶段，而不是竞争谁成为唯一安装器。

| 维度 | 仓库克隆 | 私有插件市场 |
|---|---|---|
| 适用场景 | 只有你依赖这份副本 | 其他人也依赖这份副本 |
| 设置 | 在插件目录执行 `git clone` | 浏览并点击/运行安装 |
| 迭代 | 就地编辑和测试 | 发布新的不可变版本 |
| 更新 | 显式 Git 操作 | 显式市场更新 |
| 身份 | 插件名加仓库 URL | 目录 ID 加插件名 |
| 可复现性 | 提交加工作树状态 | 发布版本加 SHA-256 摘要 |
| 治理 | 仓库访问和代码审查 | 稳定身份及撤回开关 |
| 凭证 | 用户 Git/SSH 凭证 | 现有 BuildMax 登录 |
| 是否需要 BuildMax Server | 否 | 发布和安装时需要 |
| 运行时 Server 依赖 | 克隆后没有 | 下载后没有 |
| 未来 Worker 使用 | 不适合作为可变源 | 适合作为固定 Artifact |

### 2.1 为什么支持仓库克隆

要求作者每次编辑后都打包、上传、发布再下载，会让插件开发不必要地缓慢。

```bash
git clone git@code.example.com:agents/code-review.git \
  ~/.buildmax/plugins/code-review
```

仓库可能处于某个分支、游离提交或本地脏状态。这些变化对开发有用，应当显式可见。

BuildMax 不会自动拉取仓库。Git 已经负责分支、凭证、合并冲突和脏工作树；在更新器中复制这些规则会很脆弱。未来的 `buildmax plugin clone` 命令可以提供便利包装，但直接 `git clone` 仍是受支持的路径，也不需要 BuildMax 生成的锁定记录。

### 2.2 为什么市场仍然保存打包字节

市场不应把发布者的仓库克隆到每个成员的机器上，否则会：

- 要求每个消费者都拥有Git主机凭证；
- 根据消费者的角度，使分支或标签变化；
- 将安装可用性绑定到 Git 服务器；
- 让管理员审核过的字节难以在日后识别；
- 让撤回、审计和确定性回滚变得含糊。

因此，市场存储由同一插件根目录制成的归档。发布版本不可变，并由
`(plugin, version, digest)` 标识。用户必须显式执行下载/安装；单纯发布永远不会
改变本地能力。

### 2.3 一份副本应属于哪种模式

把两种模式简单描述为“开发”和“生产”会误导。真正决定模式的问题是：**还有谁依赖这份副本？**一个人在自己的机器上维护、只供自己使用的插件完全可以永久保持克隆状态；把它送进管理员发布流程不会带来价值。一个被三个 Space 日常使用的插件，即使每周都在变化，也很早就需要稳定身份和撤回开关。

由此产生两个结论：

- **部署不是使用插件的前提。**市场属于 BuildMax 部署（§7.1），从市场安装需要 Server 登录；CLI 可以作为不依赖 Server 的单二进制运行，这是产品优先级，而不是降级模式。对这种安装形态而言，克隆或手动放置的目录就是唯一模式，也是最终形态，而非临时阶段。
- **拥有市场的部署也不能假定所有插件都来自市场。**目前只有系统管理员可以发布（§7.1），工程师若要把真正有用的插件提供给自己的 Space，没有自助建立稳定身份的路径，其中一些人仍会保留克隆。大规模悄悄违反的约定比没有约定更糟，因为它会制造“来源已解决”的假象。§4.5 给运维人员提供了在确有需要时落实该规则的方式，开放问题 4 记录了造成这种压力的权限缺口。

### 2.4 单一晋升路径

预期的流量是：

```text
Git repository
    ↓ clone and edit in ~/.buildmax/plugins
local validation and testing
    ↓ pack and publish a named version
private Marketplace release
    ↓ explicit user install
managed local copy in ~/.buildmax/plugins
```

仓库安装和市场安装之间没有自动同步。将一种来源转换为另一种来源需要显式替换操作，因此 BuildMax 永远不会覆盖工作树。

## 3. 插件目录契约

### 3.1 支持的内容

插件根目录只能提供工作区 `.buildmax/` 已支持的内容：

| 路径 | 意思 |
|---|---|
| `skills/<name>/SKILL.md` | 技能指令及其附属资源 |
| `agents/<name>.md` | 子 Agent 定义 |
| `mcp.json` | MCP Server 定义 |
| `hooks.yaml` | Hook 定义 |
| `hooks/` | `hooks.yaml` 引用的脚本或资源 |

运行时内容可以附带 `README.md` 和 `LICENSE`。未知运行时文件会由验证报告，而不会被默默视为新的插件功能。

插件可以只包含其中一部分。只提供 Skill 的插件有效；只提供 MCP 配置而不提供 Skill 的插件也有效。

### 3.2 `plugin.yaml`

对于作者来说，该领域的参考是[其他类型的设备](../../guide/plugins.md)；以下是为什么格式在它所做的位置停止。

简单包含了目录本身无法获得的身份，在发布之前值得指出的兼容性绑定，以及插件希望操作员提供的环境。

```yaml
name: code-review
version: 1.2.0
description: Company code review skills and agents.

display_name: Code Review
homepage: https://code.example.com/agents/code-review
maintainer: Platform Space <platform@example.com>
license: Apache-2.0

min_buildmax_version: 0.9.0

env:
  GITHUB_TOKEN:
    description: Token the github MCP server authenticates with.
  REVIEW_WEBHOOK_URL:
    description: Where the post_tool_use hook posts review results.
    required: false
```

| 领域 | 要求 | 意思 |
|---|---|---|
| `name` | 没有 | 稳定本地身份和默认目录弹。 小字母，字符串分开。 |
| `version` | 发表 | 没有在一个永远不会发表的树上很好。 |
| `description` | 没有 | 列表的搜索和列表文本。 |
| `display_name` | 没有 | 对于Desktop和Portal的可读标题。 默认的`name`。 |
| `homepage` | 没有 | 用户阅读更多的内容，显示，却从来没有收到。 |
| `maintainer` | 没有 | 无码表格所有者字符串 谁要问。 没有身份证实BuildMax。 |
| `license` | 没有 | 标识器，用于显示。 |
| `min_buildmax_version` | 没有 | 已知该插件使用的最古老的BuildMax。 |
| `env` | 没有 | 环境变量，用载荷预期，按名称键。 |

仅需要`name`才能加载目录.四个显示字段是无效的：运行时间中没有什么能读取它们，错误的值会误地信息读者而不改变行为。

#### 版本属于"公开"，而不是"出版命令"

插件由一个人发布命令对一个目录，这可能根本不是一个Git存储库，所以同样的规则会失败：从标签中导出版本需要Git，打破`local`源类型，并重新引入相关标识符合式的2.2排行。 BuildMax

放出版本在表格中，使得弹成为一个可查看的线在一个差异而不是一个一个人格历史上的论点，它给了`409`在复制 `(plugin, version)`一个明显的补救：编辑和提交表格。

版本是关于*下一个*版本的声明，

| 来源 | 标识本地复印件的内容 |
|---|---|
| `repository` | 提交和污染状态.表格版本显示为 *声明*，而不是安装身份。 |
| `local` | 导录路径，同样的治疗。 |
| `marketplace` | 发布行：版本和摘要， |

，一个脏的工作树仍然说`1.2.0`没有说谎任何事情 状态从来不声称它是 1.2.0。

#### 一个低边界，没有限制语法

`min_buildmax_version`是一个单个版本，而不是范围表达式.值得表达的案例是"这个插件使用了加在0.9.0中的事件".上限和范围操作员会要求一个罕见的案例的限制解析器，通常是未发生的未来的猜测。

| 情况 | 行为 |
|---|---|
| 客户年龄较大。 | 装备和更新垃圾，并命名边框。 一个已经安装的副本仍然加载，附警告。 |
| 客户报告`dev`或未被标记的构建 | 作为满足所有限制的行为;`validate`指出，检查被跳过。 |
| 缺席的场地 | 没有任何限制。 |

拒绝安装和警告在加载是故意的：安装是用户仍然可以选择另一个版本的时刻，而降级后阻止开发人员现有的克隆将会比运行更糟糕的失败。

另外，它还能让发布选择一些可以使用的东西.没有`--version`的相关标识符选择了最新版本，它不是预发布，没有被拉开，并且客户端满足的`min_buildmax_version`.像`1.3.0-rc.1`这样的预发布版本通常发布，并且只有精确版本才能达到。 `buildmax plugin install <name>`

#### 环境合同是文件，经过检查

验证已经取出了环境变量 (名字) 什么值载荷引用.它无法取出的是一个名称是什么或插件是否没有它，这是用户在安装时最常见的东西。 `env`提供了正确的，而没有其他：名字，散文，以及一个可选的 `required`旗，默认为 `true`。

由于没有人检查的声明变成虚构，验证者将其与衍生的使用进行比较：

| 情况 | 结果 |
|---|---|
| 声明和引用 | 报告为插件的环境合同 |
| 声明，没有引用 | 警告：陈旧的声明 |
| 引用，未声明 | 警告：无证要求 |
| 运行时组装时未设置的 `required: true` | 报告情况和诊断；运行过程 |
| 在一个输入下面的值式键 | 章不应该有秘密 |

设置不但需要不阻止运行，与MCP和已经降级相匹配：一个无法启动的服务器报告称它无法启动.表的任务是使原因在故障之前可读，而不是添加新的门口。

#### 不知名的领域

解析器接受未知的字段，以便格式可以增长,`buildmax plugin validate`列出它们.在两方向保持沉默将使`descripton:`变成一个无形的错误；错误会导致每个老客户端拒绝更新的插件.`manifest_version`是保留和未设置的意思 1.它应该只需要当一个不兼容的变化实际存在时。

#### 显明中还没有说明的内容

| 没有包含 | 为什么？ |
|---|---|
| 内容列表 (`skills: [...]`) | 复制已经是真相来源的目录，然后在下一个添加的文件上腐烂 |
| 声明的权限或工具允许列表 | 插件不能允许自己 (§8)，声明可能与其旁边的有效载荷不同意 |
| 其他插件的依赖性 | 需要解决方案，锁文件，以及钻石冲突的故事。 |
| 贡献名称的名称空间或前置 | 现在，在第5条中，碰撞是严重的错误。 |
| 可配置的有效载荷路径 (`hooks_file:`) | 公约已经找到所有支持的文件 |
| 关键词和类别 | 单个部署的目录足够小，使得`description`成为搜索表面 |

### 3.3 插件相关文件

子配置可能需要引用与插件捆绑的脚本。 BuildMax提供一个源扩展值： MCP

```text
${BUILDMAX_PLUGIN_ROOT}
```

它解决包含`plugin.yaml`的目录.每个插件的MCP和配置在配置合并之前用自己的根扩展.这是BuildMax提供的值，而不是一个插件可以取代的过程环境变量。

技能在调用时已经获得了技能目录，不需要新的路径规则。 `WORKSPACE_ROOT`保持了其当前的含义：代理运营的工作空间，而不是插件目录。

## 4.发现和地方状态

### 4.1 目录 发现是真理的源泉

在启动时,BuildMax扫描了以下每一个直接的子目录：

```text
<BUILDMAX_HOME>/plugins/
```

具有有效的`plugin.yaml`的目录是一个插件.这是故意足够的让手动克隆的库存工作.发现不依赖于由BuildMax生成的注册表。

开始于`.`的目录仅用于BuildMax的阶段化，缓存和状态，而不是插件。

标签表的`name`是插件的身份，而不是它所在的目录.一个市场安装总是创建`<BUILDMAX_HOME>/plugins/<name>/`，但`git clone`采用了目的地参数，开发人员有时会指向它到别的地方.一个名字与标签表的负载不同的目录，如果不匹配报告，它将会拒绝一个插件，因为没有任何后果的细节.两个索引声称一个名字是4.3冲突：负载，并且两个目录都命名，因为目录顺序不能默默地选择赢家。

### 4.2 管理员状态是补充的

相关标识符保持补充状态： BuildMax

```text
<BUILDMAX_HOME>/plugins/.state.json
```

输入按目录名称而不是插件名称进行键盘化.目录是表格解析之前唯一存在的身份，而不解析的表格则是禁用旗仍然可读时。

记录安装人员所知的事实，如：

- 源类型:`repository`,`marketplace`，或`local`；
- 存储器URL和最后一次观察 commit，如果可用；
- 市场服务器，目录识别器，发布版本和消化器；
- 如果插件已被禁用；
- 设置和更新时间标签。

状态文件不列出插件内容，也不需要用于发现.手动克隆的库存器显示为未经管理的库存器，直到BuildMax检查其`.git`元数据.一个普通目录显示为本地插件.BuildMax从来没有写出源元数据进入插件目录，因为这样做会污染Git清算。

状态变更使用过程锁和原子更换.如果`.state.json`丢失或损坏，有效的插件目录仍然会加载，但BuildMax报告说，市场来源或禁状态无法恢复。

### 4.3 源代价

同一个插件名称不能从两个目录或来源中活跃.特别是，市场安装拒绝重写现有Git工作树.用户必须明确删除，更名或更换它。

市场更新按一个保留的点目录进行了测试，并与活跃目录进行了核实和原子交换.之前的管理副本可以保留在缓存中进行反弹.存储库更新仍然是普通的Git操作。

### 4.4 运行时快照

`agentapp`在启动时解决插件，并保存该快照，以维持组装运行时间的寿命。 克隆，拉，安装，更新，禁用或删除不会改变飞行中运行。 CLI在下一次调用时看到变化； Desktop在管理的插件操作后重建了运行时间。

运行过程中编辑的存储库仍然可以改变一个未读的文件.因此，在运行开始时，追踪记录存储库的污染状态，而UI将存储库插件描述为开发源而不是不可变的输入.需要可复制性的作者使用清洁提交或市场发布。

### 4.5 运营商来源政策

部署意味着"只有管理员发布的插件运行在这里"需要检查一些东西，而不仅仅是说一些东西。 `<BUILDMAX_HOME>/policy.yaml`是现有的操作员控制的文件，所以这是一个已经存在的机制的另一个块：

```yaml
# <BUILDMAX_HOME>/policy.yaml
plugins:
  allowed_sources: [marketplace]
```

存储库分布由公约而不是新的服务器协议支持：

1. 作者将`plugin.yaml`和插件内容放在存储库根上。
2. 开发人员在插件下复制或检查该库
文件目录
3. 相关标识符分析了所有贡献的能力和 `buildmax plugin validate <path>`

4. 随着运行时间的启动,BuildMax将直接加载储存器。

状态报告，当Git元数据可用时：

- 远程URL；
- 分支或独立状态；
- 完全提交哈希；
- 无论是否存在跟踪或未跟踪的变化。

BuildMax不需要远程，在发现过程中不会检索，也不会在任何地方发送Git凭证.私人存储器身份验证仍然是用户现有的Git/SSH设置。

发现保持离线留下一个真正的风险：一个克隆从来没有更新，没有什么告诉其所有者它落后了.因此,`buildmax plugin status --fetch`只在用户要求它时与远程相比较**，并报告到底是多少后退.明确和按要求保持无网络在发现期间的不变态势完整，同时使一个故障模式实际上咬长寿命的克隆显现。

库存分布是库存来源而不是市场发布来源.这是后面可以命名的差异，而不是审查质量的差异：一个分支保护的内部库的克隆具有比一个管理员从笔记本电脑上传的目录更强大的审查来源.市场增加的是一个事件存活的身份 版本和消化，有人可以指数几个月后 和一个开。 §7.2 保持两种来源连接在一起，而不是让出版物抛弃第一种。

- 清晰的能力，来源，污染状态和来源表达。

接受：用户可以在不编辑配置或手动处理档案的情况下发现和使用 Marketplace 插件。 Portal 的帐户区域列出部署发布的内容，并交付命令； Desktop 解决发布，显示它所贡献的内容，并安装它。

插件从来没有被安装.安装发生在代理运行的地方，服务器无法看到机器，并且有一个按会在它运行的地方躺着.所以,Portal提供命令，而Desktop提供按，每个按可以在边界边缘上尊重。

## 13. 拒绝其他选择

### 仅在市场

这样才能获得最清洁的管理故事，但使每一个开发编辑都通过发布机器。 这将推动作者回到手动复制目录，在产品之外.支持直接克隆的仓库使作者的循环保持明显，并推广相同的字节后入市场。

### 仅使用Git

对于开发人员而言，这对广泛的公司消费来说是愉快的，但对于较为穷人来说，它需要Git的凭证和知识，暴露可变的审核法官，并且没有中央出版，审计或稳定的消化.它仍然是一个源模式，而不是管理的公司目录。

### 市场支持Git克隆在安装时

仅存储存储器URL和文件的文件在目录看起来比存储档案更便宜，但移动可变性,Git身份验证，并可在每个安装中。 审查版本必须是用户下载的字节，所以市场存储包。

### 只有出版时才有版本

一个早期的草案将明示文件保留在`name`和`description`上，并从`publish --version`中取出版本，理由是作者不应该在Git中代时击一个字段。

旗实际上花费了多少钱，这是一个真相来源.该版本仅存在于一个人的 history中，因此`409`没有明显的补救措施，释放行和包装的字节可能不同意，并没有任何评论显示释放即将发生.将其移动到表格中使得撞击变化，并防止第3.2节永远被误认为是安装的身份。

### 复制到全球配置中

复制技能到`<BUILDMAX_HOME>/skills`并合并JSON/YAML破坏所有权信息.更新和卸载无法区分用户作者内容和插件内容.每插件保持一个目录使其源和生命周期可检查。

### 总插件 Runtime

动态二进制或新的SDK除了技能，子件,MCP，以及子之外，还会创建另一个扩展合同，并扩大执行界限。
