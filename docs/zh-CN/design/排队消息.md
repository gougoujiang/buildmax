## 问题

过去每个界面都会拒绝在 Agent 工作期间输入的消息，而且各自的拒绝方式都不一样：

- TUI 在 `busy` 期间吞掉了 `Enter` 键，但按键仍然被送入隐藏的输入框。运行期间输入的文字在运行结束前完全不可见，运行结束后又毫无解释地重新出现。
- Portal 会对第二条 WebSocket 消息回复 `conversation.error: "a conversation turn is already in progress"` 并直接丢弃它。回合进行期间输入框被禁用，用户甚至无法输入。
- Desktop 会返回 `"a run is already in progress for this project"`。
- Portal 的 HTTP 路径完全没有做任何串行化：两个并发的 `POST .../messages` 都读取了消息历史，都向其追加内容，两个回合的写入相互交错。

一个在运行途中又想到一件事的用户，只能把它记在脑子里，等运行结束后再重新输入一遍。这本该是运行时该做的事。

## 方法

运行期间到达的消息会被**排队**，具体的投递方式取决于界面：

- CLI/TUI 和 Desktop 把队列交给运行本身，由运行在下一个迭代边界处清空队列。消息会在当前这一批工具调用之后到达模型，而不必等到整个运行结束。
- Portal 把消息排在正在运行的回合之后，作为它自己的一个回合。Portal 的 Tier 1 回合很短，而且它的队列是共享的服务端状态——参见[为什么 Portal 不做注入](#为什么-portal-不做注入)。

无论哪种方式，边界都是某种粒度的回合边界，任何消息都不会落在一批工具调用的中间。

队列本身是一个共享的基础组件：`internal/core/agent/queue.go` 中的 `agent.MessageQueue`，支持带位置的入队、先进先出的出队、丢弃最后一条（相当于撤销）、清空全部，以及用于展示的快照。每个界面拥有各自的队列，并在自己的回合边界处清空；这个基础组件本身并不关心清空的时机是什么。

每个会话的容量是 `agent.DefaultMaxQueuedMessages`（10）。队列满时会**拒绝**新消息，而不是驱逐最旧的一条：丢弃最旧的消息会在用户毫不知情的情况下悄悄丢掉一个他们以为已经排上队的回合。

### 取消会丢弃队列

停止一次运行会丢弃排在它后面的全部排队消息。这些消息本来是为用户刚刚叫停的那项工作准备的，事后再执行它们，就相当于以用户的名义重新发起了那项工作。Desktop 在 `App.CancelRun` 中会在取消运行的 context 之前先做这一步。

**失败**的运行不会丢弃队列。失败不是用户做出的决定，让用户的消息滞留在一个已经没有运行可以释放它们的地方，比让每条消息各自独立地失败一次更糟糕。

### 各界面在哪里排队

| 界面 | 队列归属者 | 运行期间输入时 | 清空点 |
|---|---|---|---|
| CLI/TUI | `Model.queue` | 排队，打印一行暗色的 `⏸ queued #n` | `RunLoop` 在下一次迭代时清空；`agentDoneMsg` → `drainQueueMsg` 作为兜底 |
| Desktop | 按 project 划分的 `App.queues` | `SendMessageStream` 返回排队位置 | `RunLoop` 在下一次迭代时清空；运行所在 goroutine 的回合循环作为兜底 |
| Portal | 按会话划分的 `Handler.turns` | `conversation.message.queued` 事件 | `turnRegistry` 的清空 goroutine |

两个本地界面上的兜底机制仍然有意义：如果一条消息是在运行已经停止读取队列之后才排入的——也就是最后一次迭代和运行返回之间的那个窗口——它会被当作一次新的运行来处理。

TUI 拒绝为斜杠命令排队：这类命令作用于实时的 UI 状态（切换模型、加载会话、面板），延后一个回合执行就会把它作用到与用户当时所见完全不同的状态上。

Desktop 把队列位置作为 `SendMessageStream` 的**返回值**报告，而不是作为一个事件，因为它回答的正是调用者自己发起的这次调用。`QueuedMessages` 则让前端能够重新读取一个它当初并未挂载的队列。

### Portal：注册表从连接上移开了

`turnqueue.Registry`（`internal/server/turnqueue`）是服务端范围的，按会话（conversation）建立键。它取代了原先挂在 WebSocket 连接上的一个 `map[string]*sync.Mutex`——那是一个错误的归属者：一个会话的生命周期比任何一个 socket 都长，而且它还能被一个重新连接的 socket、另一个浏览器标签页、HTTP API，以及一个报告某个任务已完成的系统回合访问到。把串行化锚定在连接上，会让这些访问者中的两个交错地读写同一段历史。

这个注册表同时服务于两种调用形态：

- `Submit` 是即发即弃的，供 WebSocket 回合和系统回合使用。系统回合过去会占用一个 goroutine 去阻塞地等待 `Lock`；现在它们和其他一切一样进入队列排队。
- `RunSync` 提交并等待，供需要把自己的回合流式返回的 HTTP 请求使用。一个流式请求会在等待之前先写出它的 SSE 响应头，这样客户端就能看到流已经打开。如果调用方在自己的回合开始之前就断开了连接，对应的任务会被标记为已丢弃，队列继续往下推进。

空闲的会话队列会被释放，因此一个长期运行的服务端不会为它服务过的每一个会话都积累一条常驻记录。

新增的 WebSocket 事件有：`conversation.message.queued`（带一个从 1 开始的位置）和 `conversation.message.dequeued`（表示该消息现在开始处理）。`conversation.message.completed` 携带 `queued_remaining`，因此客户端能够区分"空闲"和"回合之间"这两种状态，并在这段间隙中让输入框保持忙碌样式。队列已满的拒绝表现为一个 `code: "queue_full"` 的 `conversation.error`——此时正在进行的回合仍在运行，客户端不能把这个错误当成会话已经转为空闲的信号。

## 限制

队列存在于内存中。服务端重启会丢失尚未开始的排队回合，而且一条排队消息在它自己的回合真正开始之前不会被写入 `conversation_message`——这样一来，正在运行的回合所看到的历史，就始终精确等同于模型当时正在回答的那份历史。Desktop 和 TUI 的队列出于同样的原因也是进程内状态。

从一个浏览器标签页排队的 Portal 消息，只会通知到那一个连接。另一个正在观察同一会话的标签页，只有在该回合真正开始时才会看到它，而不是在它等待期间。

## 运行中注入

`RunLoopOpts.PendingInput` 会在每次迭代开始时被清空。所有等待中的消息都会在历史被读取、以及压缩检查之前，作为用户消息追加到历史中，因此这些消息既是该次迭代推理所依据的内容，也会被计入上下文压力的判断。

迭代边界是唯一安全的插入点：在这个点上，上一次迭代的工具结果已经完整，因此用户消息不会插到一条 `assistant(tool_calls)` 消息与它对应的 `tool` 回复之间——那样的插入会被各家模型提供商拒绝。

被注入的消息会像其他任何提示一样经过 **`UserPromptSubmit` Hook**。一个负责检查用户所发内容的 Hook，绝不能因为消息恰好是在运行途中到达而被绕过；否则，一个原本要在提示中拦截敏感信息的部署，就会出现一个宽度恰好等于这项功能的漏洞。被拦截的消息会以 `EventUserInputBlocked` 的形式被丢弃，而不会被追加，运行会继续处理它已经拥有的内容。

`EventUserInput` 会宣布一条消息已被注入，以便界面可以把它从"已排队"状态切换为"已发送"状态；这两个事件都会被写入运行轨迹：一条在运行开始之后才进入的消息，仍然是这次运行指令的一部分,如果轨迹遗漏了它，就会错误地记录这次运行实际收到的指令。

`*MessageQueue` 实现了 `PendingInput` 接口，因此同一个队列可以同时服务这两种投递方式：无论是运行本身还是界面先取到一条等待中的消息，谁先取到就归谁处理，而互斥锁使这种竞争变得无害。

### 为什么 Portal 不做注入

Portal 保留了回合边界排队的做法：

- Tier 1 回合很短。它们大多只是把工作派发给 Tier 2，真正耗时的运行发生在那里——而且一次 Task 运行无论如何都不会在中途接受用户输入。注入所能省下的等待时间本就很小。
- Portal 的队列是服务端状态，被所有正在观察该会话的客户端共享。注入会把两条用户消息合并进一个回合，导致 `conversation.message.completed` 不再能标识"恰好有一条消息被回答完毕"，每个客户端对"还有什么在等待"的理解都得围绕一个不同的事件重新构建。
- 会话运行时根本没有接入任何 `EventSink`，所以要宣布一次注入，就得先给 `ConversationService` 穿一条线过去。

这遵循了本仓库自己的规则：能力应该存在于共享的运行时中，每个界面再按照自己的需要以合适的方式把它暴露出来。

## 刻意未做的事

**持久化。** 队列始终是进程内状态。一次重启会丢失尚未开始的回合，而排队的人本人依然在场，可以重新发送一遍。让队列变得持久化，还会顺带回答一个更大的问题：一条在自己的回合开始之前就被写入的排队消息，会变成任何正在观察这个会话的其他会话都能看到的消息，这和"为某一个用户保留他的下一个回合"是完全不同的功能。

**Portal 注入。** 没有构建，原因见[为什么 Portal 不做注入](#为什么-portal-不做注入)——它能省下的等待时间很小，而且会把两条用户消息合并进一个回合。一旦 Tier 1 回合变得足够长以至于需要它，核心的接口早已留好，随时可以接上。
