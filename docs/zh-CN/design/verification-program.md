## 1. 决策

BuildMax 维护一个按风险加权、包含四道门的验证计划：

| 门口 | 目的 | 依赖性 | 预期的随机 |
|---|---|---|---|
| Pull Request | 快速拒绝确定性代码、契约、授权、持久性和关键流程回归。 | Go、前端范围所需的 Node，以及 CI 中隔离的 MySQL。 | 每次变更。 |
| 计划部署 | 验证真实进程、浏览器、存储、直接/托管推理、Worker 生命周期和受控故障。 | Compose 和 kind。 | 合并后、定时或手动触发。 |
| 发布候选 | 在私有部署中证明不可变 Artifact、外部依赖、恢复、升级、回滚和凭证轮换。 | Kubernetes、外部 MySQL、S3、TLS。 | 每个候选版本。 |
| 产品评估 | 衡量受支持模型可靠使用正确产品的程度。 | 真实模型凭证和明确的 token 预算。 | 有意安排的资格运行。 |

门口回答不同的问题.一个实例模型的分数不能证明授权，持久性或取消是正确的.一个确定性烟雾不能证明模型可靠地使用这种行为.也不能取代外部恢复和升级练习。

该程序扩大了现有的任务运行器和工作流表.新测试行为属于`tools/mk`和现有的工作流程家庭；它不得引入平行 shell-script命令界面。

## 6. 失效注射

无需记录注射点，随机杀死服务会产生噪音，而不是证据。

### 6.1 Worker生命周期

增加员工解雇的控制和案件：

- 在索赔后和模型执行前；
- 在工具调用期间；
- 在装载Artifact时；
- 产出后，但在终端报告之前；
- 终端报告后，但在可选的Conversation投影之前。

每个案例都证实了已记录的终端状态，心跳和收获时间，部分证据保留，没有幻觉结果，以及重新尝试的明确路径。 没有运行可以在限定的恢复间隔之后保持`RUNNING`。 同样的案例必须证明，直接的Agent Task不需要Conversation输送才能达到或暴露其终端结果。

### 6.2 MySQL

组合故障套件暂停或拒绝访问数据库，当：

- Worker要求逃跑；
- 服务编写状态过渡；
- 结果交付扫地租工作；
- 在关闭期间，服务器会排泄。

断言涵盖`/readyz`，限度复试，重新连接后的无能，终端状态和错误分类.测试必须区分故意注射与无关的基础设施故障。

### 6.3 物体存储

提供控制故障模式：

- 拒绝上传；
- 拒绝下载；
- 存储的字节，随后是丢失的响应；
- 在对象不在的情况下，提交的元数据；
- 存在于关系关系关系失败时的存储物体。

任何失败的路径都不能宣告下载不存在的Artifact。 恢复操作必须明确调整或墓石不一致状态。

### 6.4 模式和流媒体

覆盖率限制，服务器错误，时间外出，部分流，无效的工具调用，重复工具调用ID，文本耗尽，以及WebSocket断开/重新连接.结果将故障分为Agent/模型，产品， grader或基础设施；它们不能将每个故障分为错误的能力分数。

扩大现有部署烟雾工作流程，而不是添加无关的管弦仪。

计划矩阵是：

| 环境 | 模式 | 要求范围 |
|---|---|---|
| 编写 | 直接 | 服务器，本地处理器，物体存储,Portal，Artifact，直接供应商路径。 |
| 编写 | 管理 | 管理门户，每次运行授权，呼叫账本和配额。 |
| 类型 | 直接 | 进入， Kubernetes 工作人员， 片边界报告， Artifact， 取消。 |
| 类型 | 管理 | 通过部署的路径，工作人员代币，管理门户，本书和配额。 |
| 编写 | 失败 | 采用从第6节开始的存储，模型和关闭注射。 Worker MySQL |
| 类型 | 生命周期 | 取消，失去了工作人员，服务器重新启动，再连接。 |

标准： 标准： Workflow

- 构建或选择测试中的确切提交图像，并记录它们的
消化；永远不要用更老的可变形象证明承诺；
- 使用每个矩阵的独特空间，用户，任务，运行和Artifact标识符
电池；
- 诊断试验可能会再次进行，但
结果中仍存在原始故障；
- 传输成功和失败的第12条证据包；
- 在它能够被除之前，标签每个故障产品，测试/接或基础设施
无视于获释资格；
- 隔离的片测试仍然可见在矩阵中，拥有者；
隔离不是一个沉默的通行。

## 8. 获释候选人资格

每个Beta或后期候选人都会进行演习，

### 8.1 环境

- 专用Kubernetes环境；
- 外部MySQL和S3兼容的存储器；
- 发布的终端点的TLS；
- 克相应标识符 职业人员 Kubernetes
- 一个服务器复制到共享流传输和分布式对话
系统化和编译
- 没有固定开发登录或提供商凭证；
- 直接推断和管理推断，分别合格；
- 精确的图像消化，依赖版本，配置消化，操作符，
在执行前记录的日期。

### 8.2 运营商的旅行

运营商必须：

1. 启动第一个系统管理员；
2. 创建或提供正常账户和空间；
3. 通过Portal登录；
4. 创建Agent,Issue和Workflow资源；
5. 完成一场前对话；
6. 完成背景任务并检查其结果；
7. 下载Artifact并检查跟踪，审计，管理呼叫和配额数据；
8. 取消飞行中运行，再试一次失败运行；
9. 优雅地重新启动服务器；
10. 没有报道，就杀了Worker。
11. 断开数据库访问和对象存储访问分别；
12. 恢复数据库和桶作为一个对；
13. 通过一个改变方案的候选人进行升级，并练习N-1二进制
转型；
14. 转换JWT，数据库，对象存储和提供商凭证，使用
记录的排水/重新启动程序。

### 8.3 接受

- 每次运行都达到可解释的终端状态；
- 没有悬挂跑超过记录的恢复间隔；
- 任何保留的Artifact参考在恢复后会消失或明确消失
石头石头；
- 数据库和桶状态在对复元后一致；
- 转移行为符合支持的迁移合同；
- 没有实施变化的操作员可以诊断每一个注射的
没有使用记录的界面和收集的证据；
- [beta-readiness.md](../../deploy/beta-readiness.md) 引用不可变证据包，并记录每项已接受的限制。

## 9.人工智能生成测试的质量控制

每个改变行为贡献都包括其编辑，更改说明或拉动请求描述中的以下审查区块：

```text
Behavior:
Observable result:
Persistent result:
Forbidden side effects:
Failure cases:
Tests added:
Not tested:
```

实施和接受使用不同的背景。 实施通过可能增加专注测试。 新的接受通过接收要求，公共界面和差异，并试图通过发现缺失结果，禁止副作用和共享假设来伪造行为。

审查规则：

- 授权，执行政策，配额，移民和国家机器变化
包含至少一个负例；
- 试验结果：一个错误修正首先获得一个失败回归案例，使用一个独立的预言器；
- 公共 API，文件系统，数据库，跟踪，审计或Artifact状态优先
作为接受者语句，通过私人执行调用；
- 它们不重新实现供应依赖性和协议事件；
试验中的规则
- 仅仅`err == nil`是行为声明的；
- 试验必须显示出有效的诊断，如果它们失败；
- 检查者问，移除或逆转改变的警卫是否仍然可以让
测试通过。

## 10. 和突变测试

这些技术针对高风险的不变物，而不是随便运行存储库。

### 10.1 射目标

添加Go的射目标：

- 工作流程定义分析和验证；
- 公开身份证和路径封锁；
- 工具参数解码；
- 网络连接有效载荷和消息路径提取；
- 追踪编辑和限量序列化；
- 配置层合并和环境分析；
- 会议/历史解码和恢复；
- 作为纯域逻辑可以分离的状态过渡输入。

每一次发现的撞车，吊车，逃跑路径或不变违规，都会成为一个已犯下的回归种子。

### 10.2 突变目标

开始从空间政策,Task/TaskRun过渡规则，登录代码消费，配额，工作流验证，沙箱政策和Artifact授权。

重要突变是删除授权检查，反转角色比较，改变终端状态预测，限制限制变化，取消后成功，以及取消空间过器.这些突变可能无法生存.该程序不需要为DTO，生成结构或简单的适配器进行全球突变分数。

## 11. 产品评估和狗

### 11.1 产品自主评估

在使用评估释放资格之前，将目前的三个任务扩展到代表性1220任务组。

- 文件搜索和多文件编辑；
- 没有必要的Bash回答；
- 免费许可证的拒绝后安全恢复；
- 缩减和会议简历；
- 读取和更新Project 记忆
- 代表代表团；
- 产品生产；
- Worker访问空间文件；
- 工具故障和错误的结果恢复；
- 取消和截止时间响应；
- 结果通过追踪解释。

偏好确定性评级器：文件哈希,JSON方案，命令，目录状态，跟踪事件，禁止工具调用和数据库终端状态.仅使用模型评级器来对待对人的判断后真正主观质量。

实际模型运行选择一个小型支持的模型集，重复每个任务以显示变化性，使用明确的代币预算，并单独报告Agent，产品，级别和基础设施故障.外部基准仍然是坐标，而不是产品的发布门。

### 11.2 狗

保持一个轻量级的手动验证日志，包含提交，界面，模型，实际任务，成功，干预，混乱行为和相关问题.重复一组小的有用任务：一个Go错误修正，一个多文件配置更改，一个Portal Issue由一个Worker完成，取消和重新尝试，恢复会议，和Artifact生成/下载。

手动使用并非替代自动化，它检测到各种故障类别，其中每一个被宣称的事实都是真的，但产品仍然是混乱或不实用的。

## 12. 证据合同

每个计划或发布运行都会写一个有限的捆绑在：

```text
.artifacts/verification/<commit>/<environment>/<journey>/
  manifest.json
  result.json
  server.log
  worker.log
  portal.log
  trace.jsonl
  audit.json
  db-state.json
  artifacts.json
  screenshots/
  playwright-trace/
  junit.xml
```

没有适用的文件被省略并记录在`manifest.json`中，因为不适用；空置证据并非成功。

显著的记录：

- 犯罪和污秽状态；
- 图像消化；
- 操作系统和架构
- 类型： 相关内容， MySQL Kubernetes
- 直接或管理的推断模式；
- 旅行和场景版本；
- 开始和结束时间；
- 注射故障和注射点；
- 终结合格/未合格的分类；
- 限制对不能出口的私人日志或Artifact的引用。

按默认情况下，包裹是私有，编辑凭证和模型敏感内容，并遵循明确的保留限制.一个CI总结将包裹链接起来，显示终端分类，而不需要维护员下载每个日志。

## 13. 交付订单和完成标准

依赖顺序执行：

1. 建立验证矩阵与V01V20并将现有的证据联系起来；
2. 添加拉动请求MySQL命令和CI任务；
3. 让 V04、V05、V07、V08、V10、V11、V14 和 V15 这些确定性流程通过；
4. 添加Worker,MySQL，对象存储，模型和关闭故障控制；
5. 进行规划的组合/物质运行，发出证据合同；
6. 执行外部Kubernetes恢复，升级，反弹和凭证
轮回演练；
7. 增加目标化，突变检查，评估宽度，持续
狗。

门的规则：

- 无需再试验，通过拉动要求确定性检查；
- 预期故障将保持可见，直到分类，
失败阻碍了推广；
- 申请人重复每一个要求的证据，并具有自己的不可变的证据
消化物；
- 只有在其矩阵行中单元/合同时才完成路线图能力
根据其边界的证据和确定性端到端的证据；
- 另外,Beta还需要实际部署，故障，恢复和操作员
证据；
- 实际模型评估与确定性系统分别报告
它们是正确的。

任何V01V20行都具有其最低门所要求的证据，一个运营商未实施候选人进行了释放试验，并且没有生产准备性要求依赖于一个无声无声跳过其实际依赖性的测试。
