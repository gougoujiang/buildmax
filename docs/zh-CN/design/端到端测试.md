## 1.决策

端到端（E2E）验证是本地开发和AI代理反馈
循环。它不是必需的拉请求门。

Pull 请求保持快速、确定性的检查：构建、lint、单元测试、
集成测试和范围前端测试。贡献者或代理运行
更改用户流程后最小的相关 E2E 套件，然后使用其工件
来诊断故障。合并后运行全面的部署验证，
按计划或明确派遣时；它提供了释放信心
无需让每次迭代都等待容器、浏览器或集群。

“全面”意味着每一个重要的用户结果都至少有一个
确定性的端到端路径。这并不意味着重建单元测试套件
通过用户界面。后者速度较慢，可诊断性较差，并且会产生反馈
循环更糟。

## 2.为什么

BuildMax有四个执行面，其边界是普通测试无法做到的
一起证明：

|界面| E2E 测试必须证明的边界 |
|---|---|
| Portal |已发布的浏览器捆绑包、运行时 API 配置、身份验证、双向对话的套接字以及可见空间工作流程都与实际部署相匹配。 |
|服务器和Worker |已部署的服务器、存储、调度程序、工作线程、工件路径和托管模型传输进行协作。 |
| CLI 和 TUI |发布的二进制文件、终端交互、审批门、本地工作区、会话持久性、策略和跟踪行为相互配合。 |
| Desktop | React UI、Wails 绑定和事件、本地运行时、批准和持久项目/会话状态进行协作。 |

正常的测试金字塔仍然是主要的回归机制。一个纯粹的
显示决策属于前端单元测试，Go 中的服务合同
测试，以及 HTTP/集成测试中的处理程序规则。预留E2E测试
一个否则将仍未得到证实的边界。

## 3. 当前基线

存储库已经有有用的部署证据，但有一个差距
比看起来更大。

- `./make compose smoke` 和 `./make kind up` 进行真实部署
  确定性模拟模型。它们涵盖登录、个人空间、文件存储、
  对话任务、工作人员完成和工件检索。管理模式
  烟雾还证明工作人员通过
  网关。
- `./make e2e <cli|desktop|local|compose|kind|all>` 选择套件。 Portal 运行
  串行 Chromium Playwright 检查 `portal/e2e/`：登录、会话
  恢复、Portal shell、运行时 API 配置、审核和管理
  路线、运行跟踪视图、空间文件、工作流程以及什么是未经授权的
  显示帐户。 `kind` 和 `compose` 连接到已部署的部署
  运行时，`local` 拥有一次运行的 Compose 堆栈，而 `cli` 不需要
  完全部署。
- `./make agent-smoke` **不是**确定性验证。它构建了 CLI
  并运行`buildmax -p "/smoke 0"`，它驱动`.buildmax/skills/smoke`
  技能：真实模型执行工具检查并报告自己的通过/失败
  表。因此，它需要提供者 API 密钥，生成不同的转录本
  每次运行，判断自身，并返回一个退出代码，该退出代码仅反映是否
  该过程完成了。这是一个有用的手动代理练习，它不是
  CLI 套件：即 `internal/e2e/cli`，它驱动构建的二进制文件
  脚本化模型。它被称为`./make smoke`，直到这个名字与两个
  确定性的事情，现在它在开始之前说明了它需要什么。
- `./make eval` 针对 `evaluation/suite/` 中的 CLI 任务运行内置的 CLI。
  工作任务可以选择加入 `--surface worker`，`--surface all` 可以同时运行这两种任务。
  这是对代理质量的行为评估，而不是边界验证，
  它故意位于下面的套件之外 - 但它运行相同的二进制文件
  在临时工作区中，因此 CLI 套件和 eval 运行程序必须共享
  他们的流程启动和隔离助手，而不是成长两个不兼容的
  那些。
- Desktop 有 Go 桥接测试和前端单元测试，但没有 UI E2E 套件。
- `gui` 在 CI 中既没有测试也没有 ESLint 步骤； Portal 浏览器套件是
  今天是唯一执行共享组件包的东西。自从
  Portal 和 Desktop 都消耗它，将 E2E 移出 PR 门控可以消除该影响
  包的唯一拉取请求时间覆盖范围。参见第 8 节。

最近的两种设计改变了这些套件必须涵盖的内容以及它们的使用方式
驱动：

- **批准门是真实的。** [tool-permissions.md](./工具权限.md)
  填充了空的权限层，因此写入工具现在在运行之前进行询问。
  `settings.yaml` 中的 `tools.permissions` 引脚任何工具以允许、询问或拒绝，
  这就是让套件确定性地达到批准提示的原因
  希望该模型能生产出一款。它还限制了如何：
  Surface 没有批准处理程序，因此 `Ask` 会折叠为 `Deny`。打印
  模式是这些界面之一——参见§6。
- **一个回合会调用多个工具。**
  [parallel-tool-execution.md](./并行工具执行.md) 相邻运行
  只读并发调用并承诺没有任何可观察到的变化：
  相同的消息历史记录、挂钩序列和批准提示
  顺序，无论调度程序做什么。这个承诺正是这样的主张
  单元测试无法进行，并且它使批量回复成为
  模型线束而不是漂亮的东西。

Portal 架构文档是现有
浏览器套件及其从API部署烟雾中刻意划分；看到
[贡献/架构/portal.md](../contribute/architecture/portal.md)。

当前部署烟雾工作流程从相关拉取中运行 Compose 和 kind
请求。这种设计改变了预期的策略：全面部署
浏览器 E2E 必须移出所需的 PR 门控。它们仍然有价值
合并后、计划的和手动下发的证据。

## 4.先决条件：确定性模型框架

下面的每个套件都依赖于模拟模型，并且现有模型无法承载
他们。 `deployment/smoke/mock-llm` 应答单线协议
硬编码的句子并且不保留任何状态。这对于“任务
已完成”；它不能表达一个工具调用、一批工具、第二次转动、一个
拒绝，或者失败。最重要的黄金道路——批准和
拒绝工具调用、验证预期的文件更改、恢复会话、
在 Desktop 中处理审批 — 都是多轮刀具调用路径。
将模拟视为已解决的原语将留下最困难的设计问题
未设计在单行合约行内，因此它是第一次交付
而不是后来未经审查的细节。

线束必须满足以下条件。

|关注|所需行为 |
|---|---|
|脚本化回合 |场景装置声明一次运行的有序回复：辅助文本、具有精确参数的工具调用、流形状、提供程序错误或令牌/使用负载。模拟按顺序重播它们，并且从不从请求内容推断回复。 |
|一个回合就是一批|一个场景条目可以承载多个工具调用，因为运行时现在会同时调度它们。假设每轮调用一次的格式无法表达第 6 节所要保护的情况，并且对其进行改造将使每个已提交的场景无效。 |
|精疲力尽就是失败|以未使用的条目结束的场景会使套件失败。这就是捕获提前一回合停止调用模型的代理的原因——最终输出上没有断言可以看到的错误。 |
|每条线路协议 |该模拟服务于 `internal/infra/llm` 中的所有三个协议 - Anthropic 消息、OpenAI 聊天完成和 OpenAI 响应 - 通过路由选择，每个套件都声明它运行哪一个。单协议模拟会默默地免除 [llm-provider-adapters.md](./LLM提供商适配器.md) 中描述的三个适配器中的两个，这正是最有可能在提供程序更改时中断的代码。 |
|无容器要求 |它作为 CLI、Desktop 和 Go 级别套件的普通 Go 进程运行，并作为 Compose 和 kind 的现有映像运行。一次实现，两次包装；部署烟雾保持不变，包括它今天声称的答复。 |
|固定装置与他们的套房一起生活|场景在使用它们的套件旁边提交，并且无需运行任何内容即可读取，因此可以通过根据保留的脚本读取脚本来诊断故障。 |

该线束为测试支持，因此属于`internal/testsupport`，其中
生产代码可能无法导入，并且会强制执行 `internal/architecture` 中的测试。
该规则扫描 `internal/`，因此 `deployment/smoke/` 下的薄 `main`
将线束包装为位于其外部的容器，并且可以导入该包。
这是故意的而不是疏忽，而且这种变化要么会推动
一半应该这么说。

线束着陆为 `internal/testsupport/mockllm`。它服务于所有三个
协议包括阻塞和流式传输，并且一个步骤描述一个回复
获取它的方式——在它们之间切换的套件不会编写脚本
两次。它的测试驱动`internal/infra/llm`中的真实适配器，因为
对照手写解析器进行的模拟检查只能证明它与自身一致。

`deployment/smoke/mock-llm` 现在是相同代码的包装而不是
第二个实现，因此回复形状仅在一处是正确或错误的，
部署烟雾可以通过安装一个来重演场景。它的默认值
场景重复其单个步骤：部署烟雾断言运行的内容
生成，而不是生成它需要多少模型调用。重复是选择加入
正是出于这个原因 - 在其他地方，脚本末尾之后的调用
是发现。

## 5. 本地线束合同

每个本地 E2E 套件必须满足这些条件。

|关注|所需行为 |
|---|---|
|决定论|使用上面的模型工具及其承诺的场景。不需要提供商 API 密钥、付费模型、个人帐户或外部 SaaS。达不到这一点的套房不是套房；这是一项手动练习，必须命名为 one。 |
|隔离|为每次运行创建临时 `BUILDMAX_HOME`、工作区和唯一命名的测试资源。切勿使用贡献者的真实家庭、会话、凭证或工作空间。 |
|政策是写出来的，不是希望的|依赖于批准的套件将工具与 `tools.permissions` 固定在其临时 `settings.yaml` 中。通过猜测模型将调用什么或内置当前默认值来达到提示，会使套件在默认更改当天失败，这是有充分理由的。 |
|测试数据|夹具助手在可行的情况下通过公共边界创建最小的帐户、角色、空间、项目和内容。他们清理自己创建的内容，或者在部署必须保留证据时报告准确的安全清理目标。 |
|生命周期|套件可以附加到指定的运行部署进行诊断，也可以拥有其一次性本地部署生命周期。该命令必须说明它选择了哪种模式。 |
|诊断 |失败时，保留剧作家跟踪/屏幕截图、命令输出、经过编辑的服务器/工作日志、模型场景及其生成的记录，以及一个可预测工件目录下的简短再现命令。 |
|便携性|在`tools/mk`下添加任务运行器命令；不要创建特定于操作系统的 shell 脚本测试路径。特定于平台的本机 Desktop 烟雾是一个明确的异常，并报告其不受支持的平台。 |
|时间 |每个套件都声明正常持续时间和超时，并遵守第 5.1 节中的预算。失败的预检会命名缺少的依赖项或服务，而不是稍后在浏览器断言中超时。 |
|命名|命令名称说明了它是什么。 `smoke` 意味着三种不同的东西 - 模型驱动的技能运行、确定性部署检查和未来的 CLI 套件 - 因此模型驱动的套件现在是 `./make agent-smoke` 并在预检中宣布其 API 关键要求。 |

### 5.1 工期预算

预算是设计的一部分，而不是事后衡量的结果。一个
未达到预算的套件是该套件的一个缺陷：它构建的循环
服务停止运行。

|套房 |正常 |超时 |为什么是这个数字 |
|---|---|---|---|
| CLI + TUI | 60 岁以下 | 3 分钟 |它必须足够便宜才能加入默认的 `./make test` 循环。五分钟的 CLI 套件是正确的且未使用。预算涵盖了第 6 节所需的伪终端路径，因此每次击键花费几秒的终端驱动程序超出了算术范围。 |
| Desktop 桥| 5 分钟内 | 10 分钟 |一个Wails 开发流程加上一些流式交互。 |
| Portal + 撰写 | 10 分钟内 | 20 分钟 |包括调出堆栈；这是每日部署默认值。 |
| Portal + 实物 | 20 分钟内 | 35 分钟 |集群创建和镜像加载占主导地位；运行它以进行部署、入口、存储或工作更改。 |

### 5.2 夹具隔离与附加部署

每次运行的唯一资源和现有附加部署模式的引入
相反的方向，现有的行为是经过深思熟虑的：部署
Smoke与`./make e2e`共享固定账户`deployment-smoke@buildmax.local`，
容忍“已经存在”和“已经持有”作为成功，并传递
一次性登录代码带外，因为浏览器无法获取登录代码。剧作家
然后出于同样的原因在一个共享会话上运行一名工作人员。

因此，这两种模式采用不同的规则，而不是一种妥协：

- **拥有的生命周期。** 该套件创建了部署，因此每个帐户，
  空间和资源每次运行都是唯一的，没有什么需要清理 -
  部署被整个丢弃。
- **附上。** 套房是客人使用的。它保留了现有的固定诊断
  帐户，仅在其下创建唯一命名的资源，清理这些资源，
  并且永远不会假设它是唯一的客户。其命令输出表明
  它所附加的部署以及它留下的内容。

## 6. 黄金路径

第一个路径故意较少且具有代表性。新功能
仅当其跨界结果没有更低、更快时才添加端到端路径
测试。

|套房 |最初的黄金路径|
|---|---|
| Portal + 撰写 |登入;创建和使用空间资源；开始跑步；读取其输出、跟踪和工件；验证重要的特定于角色的视图。 Compose 是每日默认设置，因为它是最快的实际部署。 |
| Portal + 实物 |通过 ingress 和 Kubernetes 工作路径证明相同的已发布捆绑合约。 Run 本地用于部署、入口、存储或工作人员更改。 |
|服务器+Worker |保留现有的直接和托管部署烟雾，然后添加取消、重试、授权拒绝和故障恢复的部署级别一半 - 请参阅第 6.1 节。 |
| CLI + TUI |使用模拟模型在隔离的工作区中启动构建的二进制文件；下发提示；批准和拒绝固定工具调用；验证预期的文件更改、会话恢复、跟踪和有用的故障。证明批量轮流会产生一个规范的历史记录和提示顺序。 |
| Desktop 桥 |使用脚本化模型驱动绑定方法：创建项目；流式传输响应；处理批准和拒绝；重新开启会话；并暴露提供商失败的情况。它断言前端将收到的事件，因为这些是 React 应用程序可以知道的全部内容。 |
|原生Desktop 烟|在受支持的本机运行器上，启动打包的应用程序并证明一项关键交互。这比桥接套件的频率要低，因为本机 WebView 因平台而异，并且它涵盖了窗口、webview 和 React 应用程序 - 桥接套件都无法触及这些内容。 |

Portal 路径应该更喜欢语义可访问的定位器。设置不是
测试对象可以使用夹具 API，但断言的用户结果必须符合
通过被测试的界面。这保留了现有的运行跟踪模式
无需将每个设置形式变成每个断言的依赖项。

**伪终端是必需的，不是可选的。** 批准是交互式的
功能：没有批准处理程序的界面将 `Ask` 折叠成
`Deny`，打印模式就是这样的界面。所以`buildmax -p`可以证明否认
并且永远无法证明批准，而 CLI 套件的中心路径 - 写入
询问、批准和更改文件的工具 - 仅存在于终端下。
打印模式仍然承载未门控的所有内容：输出形状、会话
持久性和恢复、跟踪内容和失败文本。分割套房
这种方式使终端驱动部分保持足够小以留在内部
§5.1 预算：两次测试即可回答提示，其他一切都保持便宜。

伪终端后面没有模拟器，因此线束扮演该角色并且
回答 TUI 在启动时写入的功能查询。他们没有得到答复
当 TUI 等待自己的超时时，测试花费五秒，读取
是代理速度慢而不是终端缺席。

**Desktop 桥需要一条接缝，这值得大声说出来。** 哀号
通过位于其内部之一的接口下发到前端
包，因此该模块之外的任何内容都不能代替前端。该应用程序
现在通过它自己的单行间接发出，生产从未
重新分配并用记录器替换测试。没有它 Desktop 界面
根本就没有确定性的覆盖范围——替代方案是
运行 `wails dev` 和显示器，这是打包应用程序 Smoke，而不是套件
任何人在更改代码时都会运行。

**必须证明并发性不会改变任何事情。**
[parallel-tool-execution.md](./并行工具执行.md) 承诺相同
无论调度程序做什么，都可以观察到行为。批量场景 - 多个
一轮只读调用，以及一批将门控写入与只读混合的批次
邻居 - 断言结果消息历史记录、挂钩序列和提示
针对固定装置的订单。低于这个水平的任何东西都不能做出这样的断言，
因为它下面没有任何东西会根据真正的批准来运行真正的调度程序
门。

### 6.1 服务器和工作路径必须添加什么

取消、重试和授权拒绝已经有处理程序级别 Go
在真实的路由器和商店上进行测试。在这里重复他们的规则就是
重建该设计的单元测试被拒绝。因此，每个路径必须命名
部署级事实没有处理程序测试可以到达：

- **取消** - 信号到达实时执行并停止它：a
  运行Kubernetes Job或worker子进程结束，运行的终端
  状态与部署实际执行的操作相匹配。
- **重试** — 第二次运行真正执行而不是记录：新的运行
  发出令牌，第二个工作线程运行，并且托管路径留下第二个工作线程
  账本行归属于相同的用户和空间。
- **授权拒绝** — 拒绝在部署边缘保持，通过
  入口和发布的路由，不仅在被测试的处理程序中。
- **故障恢复** — 在运行中死亡的Worker将运行留在一个
  终端、可诊断状态及其可检索的工件和日志。

重试和授权拒绝首先被部署烟雾覆盖。
现在涵盖了取消，第 6.2 节记录了如何取消——该机制不是唯一的机制
本节最初提出，其未提出的原因值得保留。

该提案是让部署模拟服务于多个场景，
由运行使用的模型别名选择。它不能像写的那样建造：什么都没有
在 Portal 路径中，每次运行都会选择一个模型。一个任务携带一个输入和一个
可选`agent_id`； `agentdef.Agent` 带有指令和插件，没有
根本没有模型。该模型来自部署配置 - `llm.default_model`，
或 `worker.llm.model` 用于托管运行 - 因此堆栈中的每次运行都会回答来自
通过构造相同的别名。通过别名选择场景意味着添加
每次运行模型选择，这是关于谁可以选择模型的产品决策
以及如何授权，而不是测试管道。这里没有什么可以强迫的
决定。

两个断言都会轮询而不是读取一次。之前有任务报告`SUCCEEDED`
它的运行输出是可查询的，因此在运行时单个读取失败
一切都好；该排序是部署的一个属性，并且
忽略它的断言测量的是时钟而不是系统。

### 6.2 故意慢速 Run

负案例必须在运行仍在进行时对运行起作用。脚本化的
模型立即回答，因此要求部署取消运行的烟雾
通常会发现它已经完成 - 并且由于运行结束而通过的情况
其本身并不能证明取消。

脚本化回合的持续时间因此是可控的，并且它是唯一的
关于转弯的事情就是这样。一步可带`delay_ms`，模拟一套
无法重新编写 - 一个已经内置到图像中，回答堆栈套件
仅达到 HTTP 之上 — 从 `POST /control/stall` 开始失速。两者都没有
从请求包含的内容推断出任何内容。 §4 规则保持不变：
模拟回答了它认为被问到的问题就不再是证据了。多长时间
答案没有说明代理做了什么，这正是它的原因
安全拨号。

该摊位在带外武装并适用于以后的每个回复，因此它不能
目标是一次跑动——甚至是一个呼叫者。创建一个任务，其标题为
它自己的模型调用，因此创建也会等待停顿结束；烟雾
给予客户足够的耐心，而不是试图武装摊位
创建后。到目前为止，稍后武装它是更不稳定的选择：抽烟
run 测量到工作进程生成和运行成功之间有 30 毫秒，
必须在这两个事件之间滑动 HTTP 调用的情况是一枚硬币
折腾。这就是为什么取消案例在
部署烟雾：一旦武装起来，后面的任何事情都会等待
模拟而不是部署。需要针对一次运行进行摊位的情况
几个并发之间需要不同的机制，应该这么说
而不是依赖于呼叫恰好到达的顺序。

仅控制路由在堆栈外部发布 - 下的发布端口
在 kind 下组成单个 `Exact` 入口路径。模型协议本身
保留在内部网络上，因为到达它的运行是内部网络的一部分
烟雾正在证明。两者均只吸烟； `deployment/production/`下什么都没有
暴露一个测试替身。

取消案例所主张的是第 6.1 节中命名的部署级别一半：
运行到达 `CANCELED` 而不是 `FAILED` 或什么都没有，它仍然是
当再次询问时，`CANCELED`，它列出的每个工件都可以下载。它
**尚未**证明取消之前产生了部分输出
幸存下来，因为在第一次模型调用时停止的运行没有产生任何结果。那
一半需要一个在停顿之前确实有效的场景，这需要停顿
目标是跑一圈——见上文。

## 7. AI Agent Workflow

该工具是代码更改代理的一流工具，而不仅仅是 CI
事后的想法。面向贡献者的指南和工作区 `AGENTS.md` 必须
告诉代理：

1. 哪个套件映射到更改的子系统或用户流程；
2.哪个命令可以安全运行以及是否拥有Docker，kind，a Wails
   进程，或者只是一个临时目录；
3. 预期持续时间和测试的确定性固定假设；
4. 故障工件和编辑日志在哪里；和
5. 何时运行更广泛的套件而不是反复重试狭窄的套件。

代理从最窄的受影响路径开始。它读取保留的工件
在更改代码之前，修复指定的边界，并重新运行相同的套件。它
不会用手动测试或运行完整的测试来替代 E2E 故障
默认矩阵。

Runbook 本身是当前行为，而不是基本原理，因此它存在于
[`../contribute/testing.md`](../contribute/testing.md)，与`AGENTS.md`
仅携带套件选择摘要和链接。此设计记录保留
权衡；它绝不能成为操作手册。

## 8. CI 政策

|触发|验证|
|---|---|
|拉取请求 |仅快速现有支票。 E2E不是必需的门。 |
|合并到 `main` |部署和浏览器端到端，失败时保留工件。 |
|预定运行 |完整的直接和托管部署矩阵以及可用运行程序支持的平台本机 Desktop 烟雾。 |
|人工调度|用于发布准备或可疑环境回归的任何昂贵套件。 |

路径过滤器可以决定哪个合并后套件值得运行，但它们必须
永远不要默默地将跳过的 E2E 结果变成用户旅程已通过的证据。
工作流摘要必须将测试标识为正在运行、被策略跳过或失败。

将E2E移出PR门是有成本的，而且必须明确支付这些成本
而不是后来才发现。

- **并发必须停止取消证据。** `deployment-smoke.yml`
  目前`github.ref`与`cancel-in-progress: true`分组，这是
  对于拉取请求是正确的，对于 `main` 是错误的：ref 在那里是恒定的，所以
  第二次合并取消了第一次的验证，并且永远不会提交
  证明了。合并后作业不得取消，或按提交 SHA 分组。
  取消的运行报告为已取消，而不是被策略跳过。
- **红色 `main` 需要一个所有者和一个截止日期 - 以及一些强制执行的东西
  ** 合并后 E2E 故障由合并作者进行分类
  打破了它；如果一个工作日内未修复或恢复，则合并
  恢复了。该项目符号通常是作为规则编写并作为句子下发的，并且它
  只要有人恰好在观看，就一直持续：套件就消失了
  在一次合并中为红色，并在另外四次合并中保持红色，其中没有一次合并
  有理由注意到，直到运行中出现不相关的更改。

所以红色状态现在停止下一次合并。 `ci.yml`的**部署烟雾
  health** 作业读取在 `main` 上运行的最后完成的 `deployment-smoke.yml` 和
  当运行失败时，拉取请求也会失败，命名运行和提交
  这使它变成红色。它不会验证前面的拉取请求 -
  它拒绝添加到未经验证的`main`，这就是这颗子弹的压力
  假设并且从未有过。修复套件的拉取请求包含
  `deployment-smoke-fix` 标签并让其通过。

另一种选择是将浏览器套件移回到拉取请求门上。
  这会更早地捕捉到这个特定的中断，但代价是堆栈
  在每个拉取请求之前 - 它将问题视为延迟检测。
  问题是没有人拥有每个人都能看到的休息时间。
- **薄片被隔离，而不是重试。** 间歇性失败的测试是
  同一天，带着问题离开了门禁组。毯子
  不添加重试：浏览器套件故意设置 `retries: 0`，并且
  隐藏的薄片比可见的薄片更糟糕。
- **`gui` 封装失去了其唯一的 PR 时间覆盖范围。** 此处已接受
  只是因为更换起来便宜，而且一直是：`gui` 有自己的
  组件测试和前端作业运行它们，因此共享组件
  在再次合并之前捕获回归。包的 lint 步骤仍然是
  缺失，并保持阻塞状态，直到 typescript-eslint 支持 TypeScript
  它构建的版本。

## 9. 交货单

1. **构建确定性模型工具。** 脚本化多轮场景，
   批量工具调用，所有三种有线协议，可作为普通进程运行
   并作为现有图像。每个涉及工具调用的套件都会等待
   这个。
2. **首先在曲面中添加 CLI 路径。** CLI 是主要路径
   单二元界面，今天还没有确定性验证，而且它是
   唯一一款无需 Docker 即可在几秒钟内运行的套件 - 所以它就是那个
   实际上提供了该设计所针对的反馈循环。真正的二进制，
   临时家、固定权限、脚本化模型；打印模式为
   无门控路径和一个小型伪终端套件，用于批准和
   TUI 特定行为。集装箱套件推迟后订购
   作品的全部要点。
3. **稳定现有的Portal和部署套件。** 这样就可以运行
   如果有两个人可用，则与步骤 2 一起：在
   上面的两种生命周期模式，清理，可重现的工件，预检
   诊断，以及一个本地生命周期拥有的包装器以及当前的
   附加到部署模式。将全面的工作流程从 PR 门控转移到
   合并后、计划和手动触发器，并修复并发和
   §8 中指定的所有权规则在同一更改中。
4. **添加 Portal 黄金路径**用于问题/代理执行、工作流执行、
   文件、设置和成员/所有者/系统管理员授权
   矩阵。保留原来的API烟雾集中于部署行为，并给出
   服务器和工作进程路径第 6.1 节中的部署级断言。
5. **添加Wails桥套件**，然后添加一个小的本机打包应用程序smoke
   支持的平台运行者。桥接套件已登陆
   `internal/interface/desktop`中的`TestBridge*`，由`./make e2e desktop`运行。

第二个套件 `./make e2e desktop-ui` 已推出：它驱动
   桌面/前端的真实 React 应用程序及其通过 `wails 绑定的 Go 方法
   dev`自己的浏览器开发服务器（请参阅tools/mk/desktop_ui.go）。这涵盖了
   React 应用程序和桥接在一起，对抗真实的（如果无头启动）
   Chromium - 故意比此步骤最初要求的范围更窄：
   它没有说明本机窗口如何呈现同一页面，并且
   关于已签名的打包版本没有任何内容。 `wails dev` 打开本机窗口
   也是启动的副作用，但该套件没有断言
   它。本机窗口和打包构建烟雾仍然是开放工作。

这一步原来有一个先决条件，这条记录没有命名。直到
   `desktop-package.yml`，**根本没有 CI 作业生成打包的应用程序**：
   `go build ./...`通过`!desktop`半编译桌面包
   构建标签，前端作业构建 `desktop/dist` ，而无需
   嵌入它。烟雾无法发射，除非有东西建造出烟雾，所以
   步骤的前半部分是构建 - 现在每周运行合并后，
   并通过 `./make build desktop` 在 macOS 和 Windows 上按需。

签名不是该先决条件的一部分，这一点值得说明，因为它
   读起来应该是这样的。网守拒绝收到带有以下内容的包裹
   下载的隔离属性；在同一台机器上构建和启动
   没有，这就是为什么 `./make build` 那么 `./make run desktop` 是
   记录的贡献者路径。跑步者也是同样的情况。签约和
   公证门**分配**——这就是`.goreleaser.yaml`离开的原因
   应用程序发布，以及为什么构建作业没有发布工件 - 而且他们没有
   门冒烟。

真正未经证实的是托管运行器是否为已启动的应用程序提供了
   可用的 GUI 会话。这是烟雾必须首先回答的问题，并且
   现在可以根据真实的构建来回答它。
6. **在 `docs/contribute/` 中发布贡献者和代理运行手册**，
   包括套件选择、先决条件检查、工件位置和
   释放时全矩阵命令。登陆为
   [`../contribute/testing.md`](../contribute/testing.md)，与`AGENTS.md`
   携带摘要和链接，并以 `./make e2e all` 作为矩阵。

按照步骤 3 重命名模型驱动的 `./make smoke` 骑行。给予 `gui`
测试与步骤 4 一起进行，即 Portal 路径开始的时间，具体取决于
共享组件；它的 lint 步骤被阻止，直到 typescript-eslint
支持它构建时使用的 TypeScript 版本。

## 10. 成功标准

当开发人员或 AI 代理可以从干净的状态开始时，此方向就完成了
checkout，选择没有隐藏凭证的相关本地套件，执行
不触及个人数据，并获得足够的保留证据
修复故障。具体来说：

- 没有套件需要提供程序 API 密钥，并且没有像测试这样命名的命令
  默默地做；
- CLI 套件在其预算内的默认 `./make test` 循环内运行，
  包括终端驱动的审批路径；
- 证明批量转动可以产生一个规范的历史和即时的顺序；
- 每次合并后运行都会报告每个套件正在运行、被策略跳过、已取消、
  或失败，并且没有提交通过静默验证达到发布版本
  取消；
- 失败时交回场景、文字记录、经过编辑的日志和一个
  重现它的命令。

拉取请求延迟仍然由快速检查控制，而合并后和
计划运行不断验证更广泛的部署和本机界面
索赔。
