## 1. 问题

今天已经可以连到本地模型：`provider: openai_compatible` 配合 `api_url: http://localhost:11434/v1` 可以对接 Ollama 的兼容端点，简单的对话是能跑通的。[quickstart.md](../../../manual/quickstart.md) 和 [configuration.md](../reference/configuration.md) 里都是这么写的。

可一旦这个端点承载的不是一次对话，而是一次 *Agent* 运行，就会暴露出四个问题。

**本地运行仍然被要求提供凭证。** `buildmax init` 会写入 `REPLACE_WITH_YOUR_API_KEY`，`internal/interface/cli/root.go` 里的 `checkModelConfig` 会拒绝在这个值上启动，`doctor.go` 里的 `checkModels` 也会把 `api_key` 为空的条目判为失败。用户唯一的解法是编一个假密钥。一个纯本地用户和 BuildMax 的第一次接触,就是被要求提供一个根本不存在的密钥，外加一份把明明健康的配置诊断成有问题的报告。

**上下文窗口是猜出来的，而且猜错了也不会有任何声响。** `knownContextWindows` 是按 OpenRouter 风格的标识符建立索引的；`qwen3:8b` 不在其中,所以一个没有写 `context_window` 的条目会退回到 `config.DefaultContextWindow`（32000）。于是 BuildMax 会把历史裁剪到 32000 个令牌再发送出去。但 Ollama 不会拒绝一个过长的提示：它会把提示截断到 `num_ctx`，而这个值的默认值远小于 32000，然后照样给出回答。被丢掉的恰恰是提示的*前半部分*——系统提示和工具定义。表现出来的症状是模型不再调用工具，而是开始描述自己打算做什么,这看起来像是"这个小模型不擅长做 Agent 那一套"，但事实并非如此。OpenAI 兼容端点根本不接受任何 `options` 透传，所以 `num_ctx` 从这条路径完全够不着。

**没有任何东西知道本机装了什么。** 拉取了哪些模型、它们有多大、是否支持工具调用/视觉/思考——这些信息在守护进程里全都看得见，对 BuildMax 却完全不可见。配置一个不支持工具调用的模型，会产生和上面一样的静默退化，还得靠人工排查才能诊断出来。

**没有任何东西知道守护进程处于什么状态。** 没启动、模型没拉取、模型处于冷启动——这三种截然不同的失败,今天全都会以一个"为托管 API 而写的库"所抛出的 HTTP 错误的样子呈现出来，看不到任何下一步该怎么办。

第一个问题属于配置形态。第二个问题是兼容传输方式无法修复的正确性缺陷。第三、第四个问题属于本地运行时的生命周期,这是任何托管提供商都没有、任何 OpenAI 兼容端点都不会暴露的东西。

## 2. 决策

新增 `ollama` 作为第四个 `provider` 取值，使用 Ollama 的**原生** API：

| 端点 | 用途 |
|---|---|
| `POST /api/chat` | 补全调用，支持阻塞和流式两种方式 |
| `GET /api/tags` | 查询已安装了哪些模型 |
| `POST /api/show` | 查询某个模型的上下文长度与能力 |

围绕它，还有三项本地优先的行为：

- 一个 `provider: ollama` 的条目**不需要 `api_key`**，所有原本要求它的地方都要知晓这一点；
- `num_ctx` 会在**每一次**调用中发送，它取自 BuildMax 用来裁剪历史的同一个数字，因此两者不会出现分歧；
- `buildmax models --local` 和 `buildmax doctor` 会读取守护进程并汇报它持有的内容；`models` 命令还会打印一段可以直接粘贴使用的本地 `settings.yaml` 条目。

指向 `http://localhost:11434/v1` 的 `provider: openai_compatible` 配置会照常继续工作,不受影响。`ollama` 是可选启用的推荐路径,而不是替代方案：LM Studio、llama.cpp 的服务器以及 vLLM 仍然应该按兼容端点的方式部署，因为那才是它们实际使用的协议。

这个新提供商的默认 `api_url` 是守护进程的根地址 `http://localhost:11434`——而不是带 `/v1` 后缀的那个地址，后者属于这个适配器不会用到的兼容端点。

## 3. 为什么原生适配器是合理的

[llm-gateway.md](LLM网关.md) §13 规定,只有同时满足五个条件才允许引入一个原生适配器。逐条对照：

1. **是共享的产品需求，不是某个界面的取巧做法。** 针对本地模型运行,是贡献者在没有密钥、不产生账单的情况下测试 Agent 循环的方式，也是私有化部署得以真正运行起来的方式。CLI、TUI、Desktop、评测和 Task 运行都是通过同一个 `core/llm.LLMClient` 接入它的。
2. **存在一种与提供商无关的表示形式。** 文本、工具调用、流式传输和用量统计已经存在于 `core/llm` 中，不需要任何改动。`num_ctx` 和 `keep_alive` 是这一套运行时自身的传输旋钮，而不是新的模型能力，它们被限定在 `llm.Config` 和适配器内部。
3. **它实质性地改变了正确性。** §1 中的截断问题是一个错误的答案，而不只是一个慢的答案，兼容路径没有任何办法阻止它发生。它还把网络和凭证彻底从这个环节里拿掉了。
4. **兼容的上游提供不了这些能力。** 兼容端点不接受任何 `options`，因此 `num_ctx`、按调用设置的 `num_predict`、以及 `keep_alive` 都够不着。`/api/tags` 和 `/api/show` 也没有能够携带能力信息和上下文长度的 OpenAI 兼容等价物。
5. **测试。** §14 把跨适配器一致性测试套件扩展到四种协议，并补上了这套协议自身特有的测试。

条件 2 值得再强调一遍：这个设计换来的是一个*部署层面*的属性，而不是一种新能力。`core/llm` 本身不会因此增长。

## 4. 值得关注的协议差异

在 [llm-provider-adapters.md](LLM提供商适配器.md) §4 那张表的基础上再加一列：

| | Chat Completions | Ollama `/api/chat` |
|---|---|---|
| 系统提示 | `role: "system"` 消息 | 相同 |
| 历史单元 | 消息 | 消息 |
| 工具调用 | 带 `id` 的 `tool_calls[]` | `message.tool_calls[]`，**没有 id**，参数是 JSON **对象** |
| 工具结果 | 以 `tool_call_id` 为键的 `role: "tool"` | 带 `tool_name` 的 `role: "tool"`，按位置匹配 |
| `max_tokens` | `max_tokens` | `options.num_predict` |
| 上下文窗口 | 无法表达 | `options.num_ctx`，缺失时静默取默认值 |
| 流式传输 | SSE，`choices[].delta` | 换行分隔的 JSON 对象，每个分块携带 `message.content` |
| 用量统计 | `usage` 对象，流式模式下缺失 | 最终的 `done` 对象上有 `prompt_eval_count` / `eval_count`，两种模式下都有 |
| 图像 | content 片段中的 data URL | `message.images[]`，原始 base64，没有 data-URL 前缀 |
| 推理 | 无 | 请求中的 `think`，回复中的 `message.thinking`，没有签名 |
| 模型驻留时间 | 无 | 每次请求的 `keep_alive` |
| 模型不存在 | 形似身份验证失败的错误 | 直接命名该模型的 404 |

其中有两行无法干净地对应,并且直接驱动了 §6 的设计：工具调用没有标识符，参数是以已解析的对象形式到达，而不是字符串。

## 5. 架构

### 5.1 包结构

`internal/infra/llm` 依然是唯一的入口点，第四种协议只是这个包里新增的几个文件，理由和适配器设计文档 §5.1 说过的一样：

```text
internal/infra/llm/
  client.go            NewClient dispatches a fourth value
  ollama.go            the /api/chat adapter
  ollama_inventory.go  /api/tags and /api/show, for diagnostics and discovery
```

`ollama_inventory.go` 刻意放在同一个包里，而不是新开一个包。它复用了 base-URL 的处理逻辑和中性的 `apiError`，没有引入适配器本身还没有的依赖；而它的调用方——`internal/interface/cli` 里的 `doctor` 和 `models`——本来就被允许导入 `internal/infra`，`internal/architecture` 里的分层规则对此并无异议。

### 5.2 分发位置

依然是已经存在的那两处,各自新增一个 `case`：

- `internal/agentapp/app.go` 的 `LLMClientCache.build` ——直连路径；
- `internal/bootstrap/llmgateway.go` 的 `newClientFactory` ——受管路径，它只需要 §12 中的凭证豁免，别无其他要求。

### 5.3 依赖

**不引入新模块。** 这个适配器是手写的 `net/http` 加 `encoding/json`。

这与适配器设计文档 §5.3 里为 `anthropic-sdk-go` 所做的取舍正好相反，原因是这里的取舍条件不一样。那笔"交易"换来的是上游代为维护那些经常变动的流式事件格式和请求字段。而 Ollama 暴露的表面只有三个端点，加上一种单一对象形状的换行分隔流；官方 Go 客户端则内嵌在 `ollama/ollama` 服务端模块里，引入它就等于为一个大约两百行的解码器拖进来一整个庞大模块——以及它自己的发布节奏。等协议将来新增一个字段，在这里加它的成本也就是给结构体加一个字段。

## 6. 适配器的职责

**合成工具调用标识符。** 这套协议里没有标识符，而规范格式又要求必须有。适配器按照它们在对话中的位置来编号——同时考虑请求里已经带有的调用数量，以及其中出现过的最大 `call_<n>`，因为历史裁剪会缩短对话，仅凭计数本身可能会撞号——而且它什么都不记：在收到回复时，一条 `role: "tool"` 消息的 `ToolCallID` 会去比对前一条 assistant 消息里的工具调用，真正发到线上的是那次调用对应的名字，填在 `tool_name` 里。因此标识符只在一个回合内保持稳定，从来不会被发往上游——这正是让一个会话可以跨提供商移植的关键属性，也是适配器设计文档 §6 所承诺、并由重放测试锁定的那个属性。

一个对不上号的 `ToolCallID`——可能是在 `TrimHistory` 或一次压缩摘要之后出现的——会导致对应的孤立结果被丢弃，而不是让整次调用失败，这和 Anthropic 适配器处理未配对块的方式一致。

**序列化参数。** `ToolCall.Arguments` 是一个 JSON 字符串，而协议本身发送和接收的是一个对象。适配器在发出请求时做序列化，在收到回复时做反序列化；如果模型给出了无法解析的内容，适配器会把原始文本直接当作参数放进这次工具调用里，而不是干脆丢掉整个回合——Agent 循环本来就会把参数错误回报给模型，这是一种可以恢复的状态，比丢失一次调用要好得多。

**每次调用都发送 `num_ctx`。** 见 §7。

**映射各个旋钮。** `MaxTokens` 映射到 `options.num_predict`，只在设置了的时候才发送。`Reasoning` 只要不是 `off` 就映射为 `think`，在这里它是一个开关而不是一个档位。`message.thinking` 会被丢弃，并且**不会**作为 `ProviderState` 保存下来，因为这套协议既不携带签名，也不需要重放——一段没有任何人会再发回来的标记内容，没有必要为它去做状态迁移，而且推理文本混在转录里和一个正式答案根本无法区分。`Vision` 决定是否携带 `message.images`，用的是原始 base64，而不是 OpenAI 系协议采用的 data URL。`PromptCache` 什么也不做：这套运行时会在多次调用之间复用自己的 KV 缓存，但没有任何请求侧的控制手段，如果去汇报一个它本来就不公开的缓存命中数，那就是在编造数据。

**规范化用量统计。** `prompt_eval_count` 和 `eval_count` 分别对应到 `PromptTokens` 和 `CompletionTokens`，`TotalTokens` 是二者之和。两种模式都会在最终的对象里给出这些数字，因此 `transport.go` 里那段专为其他协议写的"从 SSE 里硬抠用量"的变通逻辑，不会被这套协议牵连进来。

## 7. 上下文窗口只有一个数字

规则是：**`num_ctx` 永远会被发送，而且它和 BuildMax 用来裁剪历史的数字是同一个。** 一个只存在于其中一处的窗口值，就是 §1 描述的那个 bug。

对一个 `provider: ollama` 的条目，在构建客户端时按以下顺序解析：

1. 如果模型条目里设置了 `context_window`——以操作者写的数字为准；
2. 否则调用该模型的 `/api/show`，其 `model_info` 携带了该架构训练时使用的上下文长度；
3. 否则退回到 `config.DefaultContextWindow`。

`knownContextWindows` **不会**被查询，也不会新增任何 Ollama 的标识符：它是一份托管模型目录的快照，而本地守护进程本身就能针对实际安装的模型回答同样的问题。

有两个后果值得事先说明,而不是等人踩坑才发现：

- **这次探测是失败开放的。** `/api/show` 使用一个较短的超时；如果守护进程响应慢或者短暂不可用，会记一行日志然后退回默认值,而不会让这次运行失败。唯一不允许发生的情况——完全不发送 `num_ctx`，任由服务端自己去挑——在任何分支下都不会发生。
- **窗口越大越吃内存，所以不会取到最大值。** 请求模型完整的训练长度,可能会超出这台机器的承受能力，其后果是分配失败或者严重的换页。因此上面第 2 种情况会把守护进程报告的长度当作一个*上限*，而不是一个目标值：它会被限定在一个保守的默认值上，想把它调高就该用 `context_window` 去设置。`doctor` 会把已配置的值和模型的最大值对照展示,让还有多少余量一目了然。

## 8. 本地清单

`ollama_inventory.go` 暴露了两个调用：`OllamaInventory` 列出已经拉取的模型（标识符、体积、参数规模、量化方式、模型家族），`OllamaShow` 描述单个模型的上下文长度和能力列表（`tools`、`vision`、`thinking`、`completion`）。之所以分成两个调用，是因为 `/api/tags` 能一次性回答前一个问题、覆盖所有模型，却完全回答不了后一个问题。

它只有两个调用方，没有别的：

- **`buildmax models --local`** 会列出这些模型，并针对其中一个打印出一段可以直接粘贴的 `settings.yaml` 片段，其中的 `provider`、`api_url`、`context_window`,以及从能力列表推出来的 `vision` 和 `reasoning`,都已经帮你填好了。
- **`buildmax doctor`**，见 §9。

能力信息只是被*汇报*出来，从不会在调用时被临时推断。一个模型条目仍然要显式写明 `vision` 和 `reasoning`，原因是适配器设计文档第 3 阶段已经定下的规则：能力是对"这个模型会被怎样调用"的一种声明，如果一个请求把图像传给一个读不了图像的模型，那次请求就应当被直接拒绝。发现机制省掉的是写这一行配置时的猜测,而不是替用户悄悄把这一行写上。

## 9. 各界面

**`buildmax init --ollama [--model <id>]`** 会写入一个不带密钥的条目：

```yaml
models:
  - model: qwen3:8b
    name: Qwen3 8B (local)
    provider: ollama
    api_url: http://localhost:11434
    context_window: 32000
```

完全没有 `api_key` 这一行。当守护进程可以访问时，模型会默认选取一个已安装的模型，`context_window` 按 §7 解析得出；当守护进程访问不到时，这个文件依然会被写出来，同时打印出下一步该做什么。

**`checkModelConfig`** 不再把缺少密钥当作 `ollama` 条目的错误。占位符检测逻辑本身没有变化——只是这个提供商根本不会写入任何占位符。

**`buildmax doctor`** 在 `checkModels` 里新增了一个 ollama 分支，沿用现有的严重性规则：只有第一条不通过才算失败：

| 条件 | 报告 |
|---|---|
| 守护进程不可达 | fail ·"使用 `ollama serve` 启动它" |
| 模型不在 `/api/tags` 中 | fail ·"`ollama pull <model>`" |
| 模型不具备 `tools` 能力 | fail ·该模型无法运行 Agent 循环 |
| `context_window` 超过该模型的最大值 | warn ·说明哪些内容会被截断 |
| ollama 条目上设置了 `api_key` | warn ·会被忽略，应当删除 |
| 其他情况 | ok · `<name> -> <url> (<params>, ctx <n>)` |

可达性检测只是对本地守护进程发起两次 HTTP 调用，这也是为什么 `doctor` 可以做这件事：这个命令本来就被明确记录为只读且几乎不产生网络开销，而这里涉及的网络就是回环地址。

**`buildmax models`** 打印 ollama 条目时会把守护进程的地址作为目标展示，并按 §8 新增了 `--local` 选项。

## 10. 配置面

新增一个键，另有一个既有的键变为可选：

| 键 | 默认值 | 含义 |
|---|---|---|
| `keep_alive` | `""`（守护进程自身的默认值） | 守护进程在一次调用之后保留模型驻留内存的时长。可以是一个时长字符串，`0` 表示立即卸载，`-1` 表示常驻不卸载。其他所有提供商都会忽略这个键。 |
| `api_key` | — | 当 `provider: ollama` 时不需要，即便填了也会被忽略。 |

`keep_alive` 之所以值得设立一个专门的键，是因为它控制的正是本地环路里最主要的延迟来源：一个在两个回合之间被卸载的模型,下一次调用时要重新从磁盘加载，对一个较大的本地模型来说，这就是"能用的会话"和"不能用的会话"之间的区别。它是按条目设置的旋钮而不是全局设置，因为同一台机器上完全可能同时跑一个常驻的小模型和一个偶尔才用的大模型。

`reasoning`、`vision`、`max_tokens`、`context_window` 和 `call_timeout` 仍保留它们原有的含义。`cache_control` 会被接受但不产生任何效果，这一点和 `openai_compatible` 上的行为一致。

配置参考文档会新增这一行，提供商列表会加入 `ollama`；快速上手文档里讲本地模型的那一段也会指向它。

## 11. 错误、重试与冷启动

错误分类逻辑依然是共享的。每种情况都会变成 `errors.go` 和 `retry.go` 已经能理解的一个中性 `apiError`，并携带一条指明下一步该做什么的消息——因为对本地运行时来说，下一步永远是用户自己就能做的事：

| 情况 | 可重试 | 消息 |
|---|---|---|
| 连接被拒绝 | 否 | 守护进程没有在 `<url>` 上运行 |
| `/api/chat` 返回 404 | 否 | 模型 `<id>` 尚未拉取；执行 `ollama pull <id>` |
| 400 | 否 | 原样返回发出去的请求内容 |
| 500 | 是 | 走共用的退避重试逻辑 |

这里没有需要重试的速率限制，也不应该把请求一直重试到把一台内存已经耗尽的机器压垮。

冷启动是一个超时问题，不是一个错误问题。加载一个模型可能要花上几十秒，而且这个过程发生在第一次调用内部，所以现有的 `call_timeout`（默认 300 秒）已经能覆盖它。唯一不能出的问题是让它看起来像卡死了：对一个冷模型的第一次调用会记录一条"守护进程正在加载"的日志，剩下的部分则由 TUI 原有的流式等待状态来承接。

**刻意不做自动拉取。** BuildMax 不会仅仅因为一次运行需要某个模型，就去下载一个体积以 GB 计的模型文件。失败信息会直接给出该执行的命令，由用户自己去运行它。按需自动拉取只会把一行写错的 `model:` 配置变成一块被塞满的磁盘。

## 12. 受管网关

一次部署同样要能服务这个提供商，无论是作为一个目录目标，还是作为 `conversation.model`。真正的障碍从来都不是适配器本身，而是模型目录自身的凭证不变式——`model add --api-key` 是必填项，`resolveCredential` 在凭证为空时会直接失败——这条规则对每一个真正需要密钥的提供商来说都是不可或缺的。

现在这条不变式被明确写了出来，而不再是一个隐含的假设。`llm.ProviderNeedsCredential` 是唯一一处说明"哪些协议需要身份验证"的地方，`validateModelInput` 和 `resolveCredential` 都会去查询它。这个豁免被刻意限定在这一个提供商范围内：一个托管目标如果缺了密钥，那是一个必须在选择阶段就失败的配置错误，而不该变成一次未经身份验证就发出去的调用。

有三点值得提前说明，而不是等人踩坑才发现：

- **这个端点连接的是部署所在的网络，而不是调用方所在的网络。** 一个写着 `localhost` 的目标指的是*服务端*自己的 localhost，一个容器里的 localhost 就是那个容器本身。只有系统管理员才能新增一个目标，也从来没有任何客户端请求能够自己指定一个端点——这正是为什么一个由操作员配置的回环地址是一项部署决策，而不会变成一个伪造请求端点的攻击面。
- **本地目标和其他目标一样会被计量。** 它每个令牌不产生任何费用，但依然会以 `provider_type: ollama` 的形式记入 `llm_call` 账本，这也正是它的用处所在：可以在不花钱的情况下,把网关、配额和审计这几条路径实际跑一遍。
- **从集群里访问宿主机上的守护进程,是操作员自己要解决的问题，而且每个平台各自都有一个正确答案。** 在 Docker Desktop 下，`host.docker.internal` 能在 Pod 内部被解析,并转发到一个绑定在宿主机回环地址上的守护进程；在 Linux 上，则要用 Docker 网桥网关配合 `OLLAMA_HOST=0.0.0.0`。把守护进程直接运行在*集群内部*是一个错误的默认做法：一个 Pod 访问不到宿主机的 GPU，于是推理只能退回到集群所在那台虚拟机的 CPU 上。这件事应该写在部署指南里，而不是写进代码里，具体内容在 [../deploy/local-kind.md](../deploy/local-kind.md) 中。

## 13. 交付计划

**第一阶段——适配器——已发布。** `provider: ollama`、`/api/chat` 的阻塞与流式调用、合成的工具调用标识符、始终发送的 `num_ctx`、用量统计、错误分类、在 `LLMClientCache.build` 里完成分发，以及扩展到四种协议的一致性测试套件。手动编辑 `settings.yaml` 就可以用起来。

**第二阶段——本地界面——已发布。** `/api/tags` 和 `/api/show`、§7 描述的上下文窗口解析逻辑、`models --local`、`doctor` 分支、`init --ollama`、凭证豁免、`keep_alive`，以及相应文档。正是这一阶段让这项功能变得"可以被发现"；没有它，第一阶段做出来的东西不过是一个没人知道的配置键。

之所以这样拆分两个阶段，是为了把风险较高的那一半——一套线上协议——放在不需要守护进程就能运行的测试背后，而把需要守护进程的那一半从适配器里分离出去。

**第三阶段——受管目标——已发布。** `internal/service/llmgateway` 中的 `ProviderNeedsCredential`，由 `validateModelInput` 和 `resolveCredential` 遵照执行；配套的部署示例和 kind 指南。已经在一个真实的 kind 集群上验证过：一个不带凭证的目录目标,通过 `host.docker.internal` 连到了宿主机上的守护进程，调用记录也进入了账本。

## 14. 验证

- **一致性测试套件覆盖四种协议。** `conformance_test.go` 里现有的场景表新增了一份 Ollama 测试夹具，用换行分隔的 JSON 编码出与其他协议相同的一套标准回复：文本、单个工具调用、多个工具调用、连续的工具结果、流式增量、有用量统计和没有用量统计的情况，以及各种错误分类。断言的是四种协议最终输出的规范形式完全一致。
- **标识符往返测试。** 一个包含两次工具调用的 assistant 回合，结果以相反的顺序返回，验证每一次都能得到正确的 `tool_name`。
- **跨协议重放。** 一个在 `ollama` 下写入的会话可以在 `anthropic` 下重放，反过来也一样，这正是把合成出来的标识符钉死为"在任何地方都可用"的关键测试。
- **`num_ctx` 永不缺席。** 断言适配器构建出的每一个请求都携带这个字段，覆盖 §7 中全部三条解析分支,包括探测失败的那一条。
- **清单解析测试**，针对录制下来的 `/api/tags` 和 `/api/show` 响应体，包括一个没有能力列表的模型。
- **`doctor` 输出测试**，覆盖 §9 表格中的每一行，以及 `checkModelConfig` 和 `checkModels` 中对凭证豁免的断言。
- **真实守护进程不是 CI 的依赖项。** 以上所有内容都跑在 `httptest` 之上。针对一个真正运行中的 Ollama 的手动烟雾测试,应该放在 [testing.md](../contribute/testing.md) 里 `agent-smoke` 旁边——那里本来就是放"需要真实模型"这类检查的地方。`deployment/smoke/mock-llm` 仍然保持 OpenAI 兼容。

## 15. 已考虑的替代方案

**把兼容端点的文档写得更好。** 免费，但解决不了 §1 里的截断问题：`num_ctx` 从那条路径上依然够不着，失败依旧会发生，只是解释得更清楚了一点。

**告诉用户自己写一个 Modelfile。** 在一个派生模型上设置 `PARAMETER num_ctx` 确实能定住窗口大小。但这把一个本该由 BuildMax 完成的必要配置步骤,挪到了 BuildMax 之外,而且是按模型逐个处理；BuildMax 依然不知道最终生效的数字是多少——于是它自己裁剪历史所用的窗口,和服务端实际使用的窗口就变成了两个碰巧一致的独立数值，直到有人改动了其中一个为止。

**做一个通用的"本地运行时"抽象**，同时覆盖 Ollama、LM Studio 和 llama.cpp。为时过早：后两者本来就已经说 OpenAI 兼容协议，这个抽象层就会只有一个真正的实现和一个纯粹的透传，而第二种实现该长什么样子还完全未知。`provider` 本身已经是区分它们的那个维度了，再加一个"是否本地"的维度只是把同一件事说了两遍。

**在每次调用时根据 `/api/show` 推断能力。** 被否决，理由已经在 §8 说过：这会让一个请求里包含什么内容,取决于一次探测的结果，也和"`vision`、`reasoning` 是一种声明"这条已经定下的规则相矛盾。

## 16. 不在范围内

嵌入向量与 `/api/embed`；从 BuildMax 内部拉取或删除模型；在本地条目和托管条目之间做模型路由或自动选择；针对小模型的按模型定制提示词或工具集配置——一个小模型工具调用的质量本来就是这个模型自身的属性,把它藏在一个被裁剪过的工具集背后只会让评测失去意义；针对 LM Studio、llama.cpp 或 vLLM 的原生适配器。

## 17. 未决问题

1. **Ollama 的最低版本要求。** 工具结果上的 `tool_name`、`/api/show` 返回的 `capabilities` 列表，以及 `think`，是在不同版本中先后出现的。目前还没有定下一个下限版本：实现是针对 0.32 验证过的，更旧的守护进程只会表现为功能退化，而不会被明确告知"版本太旧"。要定出一个下限版本，并让 `doctor` 去检测它，需要对实际发行版本做一次调研，这是这项工作里唯一一件测试夹具回答不了的事。
2. **§7 第 2 种情况里默认的 `num_ctx` 上限。** 这需要的是一个具体数字，而不是一条原则：定得太低会浪费一台性能不错的机器，定得太高又会把一台配置一般的机器拖入换页。目前提议的起点是 `config.DefaultContextWindow`，同时让 `doctor` 显示出该模型的最大值，这样想调高只需要改一处配置。
3. **`keep_alive` 应该放在 `ModelEntry` 里,还是放进一个按提供商划分的子块里。** 目前是以平铺的方式发布的，这个问题依然悬而未决。它是第一个只属于某个提供商的旋钮；如果再来第二个，这个平铺的条目结构就会开始列出一堆对大多数提供商毫无意义的键。仅凭一个键还不足以证明有必要引入嵌套结构，所以暂时保持平铺，等第二个这样的旋钮出现时,这个结构就值得重新考虑了。
