## 1. 本记录存在的原因

几份在相隔几天内写成的记录，对 Agent 如何运行、前台聊天与持久执行之间的关系、以及 Task 如何在多次运行之间保留文件，给出了相互重叠、甚至在一处相互矛盾的设计。其中两份记录用两种不同方式提出了同一种能力。本记录就此做出决定，使代码库在每个问题上只保留一个方向，而不是留给读者一堆需要自行裁决的备选方案。

本记录不会重新讨论源记录已经解决的问题：Task 加 TaskRun 是唯一的持久执行平面；Conversation 只是可选的前台发起入口，永远不是执行的所有者；Workflow 是构建在该平面之上的确定性图，而不是第二套引擎。这些结论保持不变。

## 2. 各方已经达成的共识

- **只有一个执行平面。** 无论走哪条路径——直接的 Agent 运行、Issue 或 Workflow 节点、由 Conversation 发起的 Task、还是 API 调用方——都会创建一个归属于某个 Team/Space 的 Task 和 TaskRun，并通过同一套共享运行时执行。不允许再长出第二套工具调用循环、调度器、轨迹或 Artifact 存储。
- **模型提议，运行时决定。** 模型的输出在被一次确定性的状态迁移校验并记录之前，只是数据，不构成事实。
- **连续性是狭窄的，而不是带版本的工作区。** 不提供工作区历史、任意回滚、变更集、分支/合并，也不会自动回写共享文件。每条线程只沿着一条状态向前推进。
- **恢复是诚实的。** 会话与工作区会在 Agent 启动前，从一个指定的前序状态恢复，且每一次结果都是可查询的事实。一次运行绝不会在悄悄从头开始的同时，把自己包装成一次延续。

## 3. 编排模型——推迟决定

**决定：推迟。** 是否要开放有边界的 Agent 到 Agent 委托，以及未来是否要为此设立一个一等公民的“Assistant”概念，**目前都不做决定**。[助理/工作流边界提案](../proposals/assistant-orchestration-and-workflow-boundary.md)仍在讨论中；其中的 Option C 委托实验并未被本记录排入日程。

不受这一推迟影响、已经成立的结论（来自源记录，未作改动）：面向开放式任务，基线仍是单个强大的 Agent；Conversation 仍然只是一个前台界面，永远不是 Task 的所有者；Workflow 仍然是 R5 阶段的持久确定性自动化平面。被推迟的只是*新提出*的委托/Assistant 问题。

## 4. 工作区连续性——仅采用检查点

**决定。** [`task-workspace-checkpoints.md`](Task工作区检查点.md)是唯一的工作区连续性记录。与之竞争的 `task-workspace-continuity.md`**被全面撤回**，且**不做任何并入**：检查点设计按其原文原样采纳。

**为什么选择检查点而不是另一个方案：**

- 它已经在被实际依赖：`product-vision.md` 把 Task 工作区检查点列为执行平面中被接受的狭窄例外，`agent-execution-and-task-threads.md` §6.4 也把它作为连续性契约中文件系统那一半的依据来引用。另一个方案则是一份悬空、无人引用的伴生文档。
- 它是更完整的设计：包含 `seed`/`successful`/`partial` 三种检查点分类、带归档安全规则的内容寻址存储、Kubernetes 存储配置方案、RPO/RTO 矩阵，以及——起决定性作用的——另一方案完全没有涉及的两个子系统：**Plugin 环境版本**和 **`buildmax-home/` 的类型化重建**。

另一方案中的思路（对当前共享文件的独立实时视图、一套忽略/大小策略、一个读取历史 Artifact 的工具）**不会**被沿用。§5.1 记录了这一决定所确定的具体行为。

## 5. 已敲定的子议题

### 5.1 共享文件在种子阶段被冻结

一个 Task 在首次运行时，会从所有者的共享文件中为自己的私有 `workspace/` 播种，并将这一状态捕获为 seed 检查点。**此后对共享文件的修改不会再流入已经启动的 Task。** 被继续的运行不会另外获得一份当前共享文件的只读实时视图；Task 只基于自己携带的检查点工作。这就是检查点设计原文所写的行为，也是对两份源记录唯一分歧之处给出的明确答案。

### 5.2 恢复失败即失败关闭（fail closed）

一次指定了前序状态的 Continue，如果无法恢复其会话或工作区，就不会启动 Agent；绝不允许一边从头开始，一边却对外呈现为一次延续。降级延续只能作为一次明确的、被记录在案的用户恢复操作而存在。两份源记录在这一点上是一致的。

### 5.3 Plugin 环境与 `buildmax-home/`

一个 Task 携带一个不可变的 Plugin 环境版本；Continue 使用其最新版本，Retry 则重建被重试运行当初所用的基线，而自主安装只在跨越新的 TaskRun 边界时才会生效。`buildmax-home/` 是从类型化状态可重新构建出的投影，而不是一份被快照下来的目录。这一设计按检查点记录所写的方式采纳。

### 5.4 Retry 回到基线，恢复结果是类型化的事实

Retry 恢复的是被重试运行所记录的基线，绝不是它的部分结果。每一次恢复与提交的结果，都是按维度（工作区、会话、Plugin 环境）分别可查询的字段，而不是一行日志。

## 6. 术语——Space

**决定。** 所有权与授权边界统一命名为 **Space**，而不是 Team：领域模型、数据库、API、对外可见的标识符、测试、fixture、文档以及 UI 都要如此。目前的代码和大多数记录里仍然写着 Team，UI 也只完成了一半迁移。这是一次在 Alpha 规则下——不欠任何兼容层——刻意做出的重命名。

这次重命名是一项体量大但机械性的改动，会作为**单独一个 pull request** 落地，并配一份经过评审的变更清单（领域包、表名、`team_id`→`space_id` 列与 `AutoMigrate`、`/api/teams`→`/api/spaces` 路由及 OpenAPI 精确匹配测试、`tm_`→`sp_` 公共 ID 前缀、handler 与 worker 的 wire 类型、mock 与 fixture，最后是文档和剩余的 UI）。它不会被并入任何其他改动。在它落地之前，各记录里出现的“Team”仍然只是被替换的旧名字，而不是另一个概念。

## 7. 结构化输出——已列入路线图

**决定。** 在共享 Agent 运行时中加入一套与模型提供方无关的结构化输出契约，并将其列为一项具名的路线图条目。它是 Workflow 的类型化路由、规划器与评估器，以及更丰富的 Task 结果封装所共同依赖的前提条件；目前运行时并不存在这样的契约，Task 的结果只是自由文本。该条目已记录在 [`ROADMAP.md`](../ROADMAP.md) 的 R5 之下。

## 8. 行动项

随本记录一并落地（一个 pull request）：

1. 撤回 `task-workspace-continuity.md`，并删除其在设计文档 README 中的条目，只保留 `task-workspace-checkpoints.md` 作为唯一的连续性记录。
2. 在 R5 下新增结构化输出这一路线图条目。

作为独立的专项改动分别跟踪：

3. **Space 重命名**（§6）——单独一个 pull request，先出清单再动手。
4. **Task 页面的 SSE** ——把 Portal 的 Task 页面接到已有的 `GET /api/teams/{…}/tasks/{…}/stream` 端点上（worker 已经把增量流式写入进程内的 hub，只是前端还没有订阅）。这项改动现在就为单副本部署上线；面向多实例的共享发布/订阅是另一项独立的 R1 工作，不是它的前置条件。
5. **工作区检查点的实现** ——仍然规划在 R0–R4 可靠性工作之后进行。它会把会话恢复可见性的修复（把今天悄悄失败开放的行为，变成一个被记录、被展示出来的结果）作为该实现的一部分，而不是拆成单独一块来做。

依据 Alpha 变更规则，以上任何一项行动都不会重新引入兼容层。

## 9. 推迟且待证据支持的事项

- **编排模型（§3）：** 有边界的委托以及任何“Assistant”概念——先衡量价值，再做决定。
- **命名：** “Assistant”、一个具名的 Agent、还是“Coordinator”；“Workflow”还是“Automation”。这些名字要和对应的概念一起决定，而不是提前定下来。
- **会话树与 Agent 邮箱：** 该[提案](../proposals/session-tree-and-agent-mailbox.md)描述了一种更丰富的分支工作区与自动恢复模型，而本记录采纳的狭窄连续性方案有意不去构建它；它的扇出/扇入必须先与 Workflow 的规划器/map 能力收敛，才能在两者之上再做扩展。它目前仍然只是一份提案。
