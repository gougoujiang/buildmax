## 1. 问题

Agent 会反复提交一段庞大且稳定的前缀：系统指令、工具定义、技能、工作区指令，
以及逐渐累积的对话历史。提示缓存可以让后续调用显著更便宜、更快。这是一个
常规的运行时问题，而不是针对单个用户的微优化。

当前的实现是一个有用的基础，但还不是一套完整的策略：

| 范畴 | 当前行为 | 缺口 |
|---|---|---|
| Anthropic | Agent 轮次默认使用 `auto`，包含静态断点和滚动断点，并可显式选择启用 1 小时保留（阶段 2）。 | — |
| OpenAI Responses | 发送派生且带作用域的 `prompt_cache_key`，并可选择 24 小时保留（阶段 3）。 | `prompt_cache_options` 尚未验证，因此有意不发送。 |
| OpenAI 兼容端点 | 声明不具备缓存能力，也不发送任何控制字段；命名的 `integration` 在通过资格验证后可以选择启用（阶段 4）。 | 目前所有集成名称都会被拒绝，第 10 节决定保持这一状态：兼容路径已经能报告其上游的实际行为。 |
| 计量 | `core/llm.Usage`、运行统计、轨迹、会话汇总、本地结果、托管账本以及 Portal 均携带缓存读写令牌数（阶段 1）。 | 无法区分"请求了某种策略"与"提供商未报告任何内容"。 |
| 成本控制 | 已配置价格的模型会按令牌类别拆分，报告每次调用和每次运行相对于未缓存基线的成本（阶段 3）。 | 无法解释未命中的原因：第 6 节的诊断信息虽然按调用解析，但尚未走出 `internal/infra/llm`。 |

本仓库不能宣称一项无法证实的节省。缓存写入的成本可能高于普通输入，一次性的
短请求无法收回这个成本，而且各提供商还对不同模型规定了各自的最小长度和
保留窗口。

## 2. 决策

BuildMax 将把提示缓存做成**一等的、按调用生效的策略**，由运行时意图和提供商
能力共同决定。

1. 当目标声明支持某种缓存能力时，常规 Agent 轮次默认使用 `auto`，而不是关闭。
2. 一次性工作——标题生成、压缩、探测等实用调用——默认使用 `off`；`force`
   只保留给预期会复用缓存的调用方。
3. 提供商只会收到它明确支持的控制字段；绝不假定 `openai_compatible`
   支持 OpenAI 或 Anthropic 的字段。
4. 缓存用量始终是提示/输入令牌的一个细分；成本根据提供商/模型的价格单独
   计算，绝不从令牌数量推断。
5. 缓存遥测数据随每次调用结果一起传递，但账本和轨迹中不存储提示内容、
   缓存键或工具参数。

存在两条彼此独立的执行路径，二者都在本文范围内：

| 路径 | 调用方 | 策略权威 | 提供商调用 |
|---|---|---|---|
| 直接客户端 | 使用 `transport: direct` 的 CLI 和 Desktop | 本地选中的模型条目 | 本地进程直接调用 `internal/infra/llm`。 |
| 托管网关 | 使用 `transport: buildmax` 的 CLI/Desktop，以及调用托管补全路由的 worker | Server 批准的目录目标和部署策略 | 由 Server 解析目标并调用 `internal/infra/llm`；远程客户端从不直接调用提供商。 |

两条路径使用同一套缓存策略词汇和遥测机制，但托管调用方永远不会收到或控制
提供商的缓存键、TTL 或原始提供商选项。网关是托管推理的最终策略决策点。

这一默认值变化只适用于符合条件的 Agent 轮次，它不会让每一次模型请求都变成
缓存写入，也不会静默启用延长保留。

## 3. 目标与非目标

### 目标

- 在受支持的提供商上，降低 Agent 重复前缀带来的成本和延迟。
- 保持直接模式的可移植性，以及托管网关的 Space 边界。
- 在遥测中说明所请求的控制、提供商的报告，以及能力缺失的情况。
- 允许运维人员刻意选择提供商支持的保留时长。
- 将提供商策略留在 `internal/core/agent` 之外；core 只表达意图，由适配器
  负责翻译。

### 非目标

- 构建一个 BuildMax 自有的提示/KV 缓存，或在本地保留提示内容。
- 把缓存读取当作免费操作，或用它来规避令牌配额。
- 承诺跨提供商、凭证、模型、工具集、静态提示或保留窗口都能命中缓存。
- 仅仅为了暴露一个缓存开关而新增一个原生适配器。

## 4. 策略模型

配置采用结构化的策略：

```yaml
models:
  - model: claude-sonnet-5
    provider: anthropic
    cache_control:
      mode: auto             # auto (default), off, force
      ttl: provider_default  # provider_default, 5m, 1h, 24h where supported
```

模型目录暴露相同的结构。持久化的目录字段始终显式使用 `snake_case`；线上
传输的形状只是实现细节。

| 模式 | Agent 轮次 | 实用/一次性调用 | 不支持的目标 |
|---|---|---|---|
| `auto` | 请求提供商的经济性默认行为。 | 不请求缓存。 | 不发送任何控制字段；报告 `unsupported`。 |
| `off` | 不发送任何控制字段。 | 不发送任何控制字段。 | 不发送任何控制字段。 |
| `force` | 即使无法确定会被复用，也请求缓存。 | 请求缓存。 | 拒绝该配置，而不是假装生效。 |

本设计取代的 `prompt_cache: bool` 字段被直接移除，而不是作为简写保留下来。
此前的方案曾把它写成一条兼容路径，但对一个尚未发布的项目而言，这是错误的
选择：没有任何已部署的东西必须保持可用，而两个存储对 `false` 的含义也无法
达成一致——设置文件中的 `*bool` 能区分"缺省"和"false"，而一个非空列做不到，
于是同一个值在一处意味着"关闭"，在另一处却意味着"默认"。移除它，也就移除了
这种分歧。

### 4.1 逐调用意图

单靠配置无法决定一次调用是否会被复用。共享的 LLM 请求边界因此新增了一个
带类型的调用画像：

| 画像 | 产生方 | 默认缓存模式 |
|---|---|---|
| `agent_turn` | `core/agent.RunLoop` | 解析模型策略（默认为 `auto`） |
| `title` | `agentapp.SessionManager` | `off` |
| `compaction` | `agentapp.LLMCompactor` | `off` |
| `evaluation` / `probe` | 由调用方显式选择 | 默认为 `off`，除非主动开启 |

该约定从位置参数 `messages, tools` 演变为一个包含 messages、tools 和画像的
请求对象。通过未定型的 `context.Context` 传递策略，或从提示文本中推断策略，
都被否决：一项会产生费用的提供商行为，必须对调用方和测试可见。

core 拥有 `agent_turn`，但从不导入提供商类型，也不选择 TTL。`agentapp`
为标题/压缩工作打上标签；`internal/infra/llm` 把画像和模型设置一起解析为
提供商请求。

### 4.2 直接客户端与托管网关的解析

直接的 CLI/Desktop 调用会在 `agentapp.LLMClientCache.build` 中解析
`settings.yaml` 里所选模型的策略，然后把生效的请求画像传给本地提供商适配器。
这是唯一一条能让用户通过本地设置为自己的提供商账号选择缓存控制的路径。

托管的 CLI/Desktop 调用使用 `infra/llmremote` 和 space 补全端点；worker
调用则使用 worker 补全端点和一个 run 令牌。两种情况下，远程请求都只携带
`call_profile`，既不携带 `mode`、TTL、提供商集成画像，也不携带缓存键。
Server 会：

1. 验证调用方身份，解析 space 或 task-run 身份；
2. 将已批准的别名解析为其目录目标；
3. 校验该目标的缓存能力和部署策略；
4. 将该策略与收到的调用画像相结合；以及
5. 创建提供商请求，并记录返回的诊断信息。

客户端提供的画像是操作性输入，不是授权性输入。网关会把未知画像视为无效，
并且绝不允许一次请求选择 `force` 或延长保留。这样可以防止本地客户端通过
手工构造 BuildMax 端点请求，绕过运维人员设定的缓存、保留或租户隔离策略。

`llmwire.CompletionRequest` 新增一个经过校验的、纯增量的 `call_profile`
字段。`CompletionResponse` 只新增安全的生效诊断信息和用量计数；它绝不会
返回不透明的缓存键或上游提供商配置。space、worker 和 HTTP 补全处理器必须
共享这同一个服务端解析函数，以避免行为出现分歧。Server 自有的 Tier 1 调用
会在进程内直接调用同一个函数，而不是再对 Server 发起一次 HTTP 回调。

## 5. 提供商能力契约

缓存支持属于某个模型目标，而不是某个协议标签。目录的能力集合新增一个缓存
描述符；直接设置则从其提供商和显式的本地集成画像中派生出一个。

| 目标类别 | `auto` 行为 | 运维人员可控项 | 遥测 |
|---|---|---|---|
| Anthropic Messages | 在 system/tools 之后设置一个稳定断点，另加一个顶层滚动断点。 | 默认 5 分钟 TTL；1 小时保留需显式开启。 | 读写令牌数、请求的策略、生效的 TTL。 |
| OpenAI Responses | 稳定且带作用域的 `prompt_cache_key`；除非模型支持显式模式，否则使用隐式缓存。 | 按能力开放的 TTL/保留设置，以及显式/隐式的选择。 | 缓存命中的输入量、缓存写入量，以及返回时的请求/生效选项。 |
| OpenAI 上的 OpenAI Chat Completions | 只使用模型文档中记载的控制字段。 | 与 Responses 相同的、按能力开放的策略。 | 提供商报告的计数器。 |
| OpenAI 兼容端点 | 默认 `unsupported`；命名的网关画像可以选择启用。 | 仅限已校验的、集成特定的字段。 | 仅限有文档记载的集成字段。 |

该描述符会在加载直接模型或目录目标时被校验，并被纳入路由客户端的缓存键中。
运维人员的一次编辑，绝不能让旧的缓存策略残留在一个已缓存的客户端上。

### 5.1 Anthropic 的放置位置

Anthropic 把可缓存的输入按 tools、system、messages 的顺序排列。BuildMax
在稳定的 system 块之后保留一个显式断点，用来缓存 tools 和指令，另外为
不断增长的对话设置一个顶层的自动标记。后者并不能取代前者：自动回溯只能
找到此前写在滚动端点附近的前缀。

如果没有 system 块，但存在可复用的 tools，适配器仍必须标记一个稳定的
tools 边界；它不能只缓存不断变化的最后一条用户消息。当提供商既未报告读取
也未报告写入时，只要能在不猜测的前提下检测出原因，诊断信息就会给出已知
原因，例如平台不支持或前缀过短。

### 5.2 OpenAI 缓存键的隔离

OpenAI 的缓存键是一个缓存路由提示，而不是授权边界，但它绝不能把互不相关
的提示群体分到同一个桶里。BuildMax 会从以下内容派生出一个不透明的、带
版本的键：

```text
provider-account/credential identity + target/model + space (managed only)
+ system-prompt fingerprint + toolset fingerprint + cache-policy version
```

它不包含原始提示内容、工作区路径、用户名、消息、凭证或用户提供的标识符，
也从不会被持久化到账本、轨迹、Portal、CLI 输出或日志中。只要静态输入发生
变化，它就会随之改变——宁可牺牲命中率，也要保证分桶正确。

## 6. 用量、成本与诊断

`core/llm.Usage` 已经包含 `CacheReadTokens` 和 `CacheWriteTokens`，二者
始终是 `PromptTokens` 的子集。请求结果还会额外携带一组有界的诊断信息：

| 字段 | 含义 |
|---|---|
| 请求的模式 | 解析出的 `off`、`auto` 或 `force` 策略。 |
| 提供商能力 | `supported`、`unsupported`，或命名的集成画像。 |
| 策略 | 例如 `anthropic_static_and_rolling`、`openai_implicit` 或 `none`。 |
| 生效的 TTL | 仅当被明确请求或明确返回时才有值。 |
| 结果 | `hit`、`write`、`mixed`、`miss` 或 `unreported`；绝不仅凭数量为零就推断为未命中。 |

这些字段会流经 Agent 事件流、`RunStats`、持久化轨迹、本地会话/轮次结果、
`llmwire`、托管的 `llm_call` 响应、Portal API 以及 Portal 的花费视图。
账本已经存储了这些计数器，它对外的汇总必须把它们暴露出来。轨迹只记录
数量和策略结果，不记录缓存键。

对于直接的 CLI/Desktop 调用，这个流程从本地适配器的结果开始。对于托管
调用，Server 会在关闭提供商调用账本之后，把生效的诊断信息和用量附加到
补全响应上；远程客户端只是把这个结果转发给本地 Agent。这两条路径都不得
用本地猜测的命中结果，替换提供商报告的实际数量。

成本是单独计算的。一条带版本的模型定价记录提供基础输入、缓存读取、缓存
写入和输出这几项费率，以及币种/生效日期。只有当所有费率和用量都齐备时
才显示估算值，否则显示 `unavailable`。该视图会把未缓存输入、读取和写入
分开展示，给出一个反事实的基础输入成本，并且只有在节省为正值时才会报告
节省。

在配额被单独重新设计之前，它仍然是一种工作量/令牌控制。缓存带来的折扣
绝不能让一个 space 看起来做的工作变少了，也不能悄悄放宽既有的令牌限制。

## 7. 安全与保留

提示缓存本质上是提供商一侧对提示前缀的保留，而不是一个无害的本地性能
开关。

- 能力画像声明保留选项；延长保留需要主动开启。
- 直接用户自行选择要向哪个提供商/账号暴露数据；托管场景下由运维人员为
  目标做出选择，Space 不会得到可绕过策略的覆盖权限。
- 键和画像的作用域由凭证限定；在托管推理场景下，还会进一步由 space 限定。
- 使用 `force` 或延长保留时，如果静态指令中可能包含密钥，会给出警告；
  这个警告并非完整的密钥检测器，也不会阻塞正常工作。
- 账本、轨迹和诊断信息只包含数量和结果，绝不包含前缀内容、哈希输入、
  不透明的键或提供商的响应体。

## 8. 备选方案

| 备选方案 | 未采用的原因 |
|---|---|
| 保留一个可选启用的布尔值 | 无法区分标题生成与多轮工具循环，会让 Agent 核心场景的节省能力保持关闭。 |
| 缓存每一次请求 | 写入成本可能高于输入本身，还会造成不必要的保留。 |
| 把每个兼容端点都当作 OpenAI 处理 | JSON 兼容并不等于功能保证；字段可能被忽略或拒绝。 |
| 只在适配器里放策略 | 调用意图、配置和遥测会在不同提供商和界面之间产生偏差。 |
| 构建本地提示缓存 | 会改变机密性、失效、内存和 worker 语义，却无法复用提供商侧的 KV 状态。 |
| 仅从令牌数量推算节省 | 费率因模型、TTL、读写类别和提供商而异，这样做只是虚假的精确。 |

## 9. 交付计划与验收

### 阶段 1 —— 如实的基线与遥测（已交付）

- 纠正过时的缓存文档。
- 把现有的缓存计数器传播到统计、事件、轨迹、本地结果、托管补全响应、
  托管账本 API 以及 Portal。
- 覆盖直接的 CLI/Desktop 构造过程，以及所有托管补全端点：space、
  worker task-run，以及 Server 进程内的 Tier 1 路径。
- 为运行花费视图新增缓存计数器/诊断信息，并保留 `unreported` 状态。
- 为当前所有协议用量形状和托管往返调用新增测试夹具。

**验收：** 提供商报告的缓存读/写从 Agent 轮次到最终界面全程可见，且不会
重复计算提示令牌。

计数沿着这样的路径流动：`llm.Usage` → `agent.RunStats` 和 `agent.Event` →
轨迹中的 `llm_end` 与 `run_end` → `session.Session` 汇总 →
`agentapp.RunResult`/`RunUsage` → CLI、Desktop；对于托管调用，则再经过
`llmwire.Usage` → `llm_call` 账本行 → space 的 run-ledger 路由 → Portal
的运行花费视图。每一个界面只有在提供商确实报告了细分数据时才会打印出来：
如果永远显示 `0 / 0`，在许多根本不报告任何数据的提供商上，会被误读成一次
实测的未命中。

第 6 节的诊断信息——请求的模式、能力、策略、生效 TTL、结果——不属于阶段 1
的范围。阶段 2 会按调用解析它们；把它们带到各个界面的进展记录在下文。

### 阶段 2 —— 策略与 Anthropic 默认值（已交付）

- 新增结构化策略、兼容性解析、调用画像和能力校验。
- 为符合条件的 Anthropic Agent 轮次启用 `auto`；保留静态断点和滚动断点；
  支持显式开启 1 小时保留。
- 标题/压缩/探测调用默认保持关闭。
- 由网关而不是 `llmremote`，根据目录目标和已校验的调用画像来解析生效的
  托管缓存策略。

**验收：** 直接的 CLI/Desktop 与每个托管端点会针对同一目标做出相同的策略
决定；在静态输入不变的前提下，一个通过资格验证的连续工具循环会先观察到
一次写入、再观察到一次读取；仅用于标题的 `auto` 调用不发送任何控制字段。

有两项决定是在实现过程中敲定的，上面的计划并未涵盖，因此记录在这里：

第 4 节最初保留的 `prompt_cache` 简写字段已经不复存在。实现过程本身说明
了原因：设置文件可以用指针区分"缺省"和 `false`，而一个非空列做不到，于是
同一个字段在一处存储中意味着"关闭"，在另一处却意味着"默认"。一个尚未发布
的项目没有理由背负这种负担。`cache_mode` 是两种存储表达这一点的唯一方式，
未设置的行会采用默认值。

当某个目标完全不接受缓存指令时，`force` 会被拒绝，但 `auto` 不会。如果在
那里也拒绝 `auto`，会让默认模式在大多数目标上都无法使用；而如果把 `force`
静默地当作不缓存来处理，则是在回答一个没人问过的问题。

第 6 节的诊断信息——请求的模式、能力、策略、生效 TTL、结果——已经按调用
完成解析，但尚未走出 `internal/infra/llm`。把它们带到各个界面是遗留的
债务，属于阶段 4 的范围：读者需要它们，是为了解释一次未命中背后的原因，
而第 10 节的资格验证运行刻画的是命中而非未命中，因此除了数量之外，目前
仍没有更多可以如实陈述的内容。

### 阶段 3 —— OpenAI 原生控制与成本估算（已交付）

- 按需升级原生客户端/库，以支持所需的缓存字段。
- 派生相互隔离的 `prompt_cache_key` 值，并校验缓存选项。
- 新增带价格版本的估算，以及明确的不可用状态。

**验收：** 请求形状测试固定住键/选项；键会随 space/静态前缀边界的变化而
变化；报告的计数器能得出可复现的成本。

定价记录存放在哪里，前文一直悬而未决，这里给出定论：不存在单独的历史
价格表。当前费率就挂在它所描述的对象上——托管目录条目上是 `llm_model`，
直接模型条目上是设置里的 `pricing` 块——历史记录则保存在花费发生的地方：
网关在接受调用时，会把当时生效的费率复制到每一行 `llm_call` 上；本地会话
则在运行过程中逐轮累加成本。这样一来，不可变性恰好落在真正需要的地方——
实际被计费的记录上——而不需要一份没人会维护的带版本目录。重新给一个模型
定价，只会改变下一次调用的成本，不会改变以往调用的成本。

费率是整数——单位是每百万令牌的纳货币单位——在配置中以十进制字符串的
形式书写。一个公开发布的费率没有精确的二进制表示，几百次调用积累下来的
浮点误差，最终会体现在有人拿去和账单核对的那个数字上。

`prompt_cache_options` 不会被发送。库虽然暴露了这个字段，但 BuildMax 尚未
弄清它的 `mode` 取值在真实账号上分别意味着什么；发送一个词汇尚未验证的
字段，与假定某个 OpenAI 兼容网关实现了 OpenAI 的缓存字段，是同一种错误。
这个显式/隐式的选择会一直搁置，直到阶段 4 的资格验证套件能针对真实提供商
加以确认；`24h` 保留则取自第 4 节所修正的词汇表，同样在待确认的清单上。

### 阶段 4 —— 兼容画像与资格验证（机制已交付）

- 只为经过测试的兼容网关新增命名画像。
- 在真实提供商上验证首次写入、连续命中、TTL 过期、前缀变化、长历史回溯、
  流式传输、重试以及并发冷启动等场景。

**验收：** 在某个模型或端点的请求形状与用量响应通过资格验证套件之前，
不得将其描述为具备缓存能力。

该套件以 `./make cache-qualify` 的形式存在：它会针对由
`BUILDMAX_CACHE_QUALIFY_*` 指定的提供商运行上述场景，并报告该提供商的
实际行为。和 `agent-smoke` 一样，它不是一项测试，也没有任何检查会运行它：
它会调用一个付费提供商，未指定提供商时会跳过。

#### 资格验证运行的发现

于 2026-08-23 针对 OpenRouter 运行，通过三种方式访问它：作为
`openai_compatible`（其 Chat Completions 端点）、作为 `anthropic`
（其位于 `/api/v1/messages` 的 Messages 端点），以及作为 `openai`
（其位于 `/api/v1/responses` 的 Responses 端点）。

**原生 Anthropic Messages —— 通过验证。** 冷启动前缀写入了 11793 个
令牌；下一次针对未改变前缀的调用读回了 11421 个；对话增长了八轮之后，
仍然读到了这个静态前缀；一次流式调用读到了 11250 个，这是这些计数能在
该协议的事件流中保留下来的第一个证据；改变前缀后则没有读到任何内容。
`5m` 和 `1h` 两种保留时长都被接受。

**原生 OpenAI Responses —— 通过验证。** 冷启动前缀写入了 10865 个令牌；
下一次调用读到了 10517 个，只写入了增量的 14 个令牌；对话增长后读到
10800 个、写入 136 个；流式传输读到 11068 个；改变前缀后没有读到任何
内容。`24h` 保留被接受，这也印证了本文此前仅凭词汇表就认定的值。

**缓存键在提供商一侧隔离不同的桶。** 两次调用在不同的 `CacheScope` 下
发送字节完全相同的提示：第一次写入了 10788 个令牌，第二次自己写入了
10788 个，却*完全没有*读到第一次的内容；随后第一个作用域又读回了自己的
10788 个。这是验证第 5.2 节论断的唯一方式——在一个隐式缓存的协议上，一次
读取命中并不能证明键的隔离性，只有在不同作用域下出现未命中才能证明。

**通过兼容端点访问时，只有 Anthropic 什么都不报告：**

| 上游模型 | 通过 `openai_compatible` 的缓存读取 |
|---|---|
| `openai/gpt-5.6-luna` | 是 |
| `google/gemini-3.7-flash` | 是——12243，流式 12250 |
| `deepseek/deepseek-v4-flash` | 是——10496，流式 11264 |
| `z-ai/glm-5.3` | 是——12160，流式 12416 |
| `anthropic/claude-haiku-4.5` | 否——所有场景均为零 |

最后一行并不是网关的缺陷。Anthropic 不会隐式缓存任何内容，而 Chat
Completions 适配器又不发送任何断点，因此自然无从报告。同一个模型通过
同一个网关，走 Messages 端点却能完全通过验证。这里的教训关乎路由：无论
前面是谁，通过 OpenAI 兼容协议访问的 Anthropic 模型都完全无法缓存。

**对以上所有结论的一点保留。** 这里验证的是 OpenRouter 对 Messages 和
Responses 协议的*实现*，而不是 `api.anthropic.com` 或 `api.openai.com`
本身。这对 BuildMax 的请求形状和用量解析而言是有力的证据，因为一个模拟
某协议的网关没有理由凭空发明缓存语义；但它终究不是官方端点，不应被当作
官方端点来报告。

**不过这仍然解决了画像的问题，而且原因比预想的更加清晰。** 这些结果的
初稿曾显示，能力似乎因上游模型而任意变化。但只要前缀足够大，事实并非
如此：所有隐式缓存的模型都会通过网关如实报告，唯一的例外是那些需要某个
兼容适配器从不发送的请求字段的模型家族。一个网关级别的
`integration: openrouter` 画像仍然是错误的——它会替那些在该协议上根本
无法缓存的 Anthropic 模型代言——但正确的解法是把它们原生路由过去，而
BuildMax 已经支持这一点，这次运行也端到端地验证了它，包括工具调用在内。

因此 `compatibleProfiles` 保持为空，所有 `integration` 取值仍然会被拒绝。
没有谁真正需要它：兼容路径已经如实报告了其上游的行为，而需要更多能力的
那个模型家族则拥有原生适配器。

**一项提议，尚未决定。** 上面的两个发现其实源于套件本身的问题，而不是
提供商的问题：一个接近模型最小长度的前缀会间歇性地被缓存，而固定不变的
前缀意味着保留窗口内的第二次运行并非冷启动。这两个问题都已修复。剩下的
一个棘手之处在于：`cacheCapabilityFor` 是按协议来确定键的，但真正决定
能否缓存的是协议*加上*上游模型两者共同作用的结果。既然一个模型条目已经
明确指定了唯一的上游，那么声明能力最自然的位置就是这个条目本身，由已经
针对自己的目标运行过 `./make cache-qualify` 的运维人员来填写。这是对
第 5 节能力契约的一项改动，应当在动工之前先做出决定。

第 6 节的诊断信息也属于同一批工作。它们的价值在于解释一次未命中，而在
套件确定每个目标上真实的未命中究竟是什么样子之前，除了数量本身已经说明
的内容，`strategy` 或 `outcome` 字段里并没有更多可以如实填写的东西。
