## 1. 决策

BuildMax 将 TaskRun 的活动文件系统保留在本地临时存储中，并将 Task 可恢复的工作区作为不可变检查点持久化到配置的对象存储中。

默认执行配置文件是：

```text
Task workspace checkpoint in S3 / MinIO / local persistent storage
                              |
                              | materialize
                              v
                  TaskRun emptyDir/workspace
                              |
                              | capture after quiescence
                              v
                  immutable next checkpoint
```

检查点而不是 Pod 卷才是权威状态。Kubernetes `emptyDir` 仍是默认工作盘，因为它速度快、按 Pod 隔离、可移植，而且 Worker Job 已经在使用。将来可以用持久卷加速大型工作区，但它不会取代对象存储中的检查点，也不会改变 Task 语义。

本文只引入一个有意收窄的能力：**Task 工作区连续性**。它不会恢复已经撤回的通用版本化工作区产品。本设计不提供工作区时间线、任意回滚、分支模型、变更集审查、合并或自动写回共享 Space 文件。

恢复单元是 `workspace/` 的完整不可变快照。首个实现采用带版本的压缩归档；在测量证明完整归档不足之前，不引入增量文件系统协议。

## 2. 问题与当前基线

Worker 已经将一次运行划分为四个文件系统区域：

| 区域 | 当前用途 | 当前持久性 |
|---|---|---|
| `home/` | Space Home 的物化副本，即 Agent 工作的文件 | 运行结束后不上传 |
| `artifacts/` | 运行输出，包括 `result.md` 和显式生成的文件 | 在终态报告时上传 |
| `global/` | 运行范围的 `BUILDMAX_HOME`：Session、trace、日志、设置和 Plugin | 在终态报告时上传选定文件 |
| `oshome/` | 供工具和凭证文件使用的私有操作系统 Home | 永不上传 |

`internal/agentapp/taskrun.prepareRunWorkspace` 会创建这些目录，在有可用会话时恢复之前的 Agent 会话，并将当前 Space Home 物化到 `home/`。`reportPersistedRunState` 会上传 `global/` 和 `artifacts/`，但不会上传 `home/`。

这个布局是本设计要替换的基线，而不是目标布局。当前运行时把整个 TaskRun 目录作为 Agent 工作区根目录，因此文件工具、Artifact 发布、工作区配置发现、Bash 工作目录和沙箱并不一致地把 `home/` 视为工作区。提示词要求 Agent 不要写入 `global/`，但把运行时状态放在可写工具根目录下并不能构成访问边界；它还允许合法的顶层写入，而未来只检查点 `home/` 时会悄悄遗漏这些写入。

因此，继续执行一个 Task 时，可能恢复出“某文件已修改”的模型可见历史，却收到一份没有该修改的全新 Space Home。即使两条恢复路径分别报告成功，模型与文件系统仍可能互相矛盾。

现有会话恢复还会在不记录结果的情况下失败开放：只要捆绑包缺少一半内容，就会被丢弃并从新运行开始。在 Continue 成为用户可见的契约之前，这种行为尚可接受；对于声称具备连续性的 Task 则不可接受。

Kubernetes 也无法弥合这一缺口。同一 Pod 内的容器重启不会删除 `emptyDir`，但 Pod 被移除后其中内容会永久消失。Job 控制器可能在 Pod 失败后创建替代 Pod，而 Kubernetes 明确要求 Job 应用处理临时文件、锁、部分输出和可能的重复启动。因此，持久化边界必须由 BuildMax 定义，而不能依赖某个 Pod 的生命周期假设。

## 3. 目标与非目标

### 3.1 目标

- Continue 运行获得其 Task 已提交的最新工作区。
- Retry 获得它所重试的那次运行使用的准确工作区基线。
- Session 历史、工作区状态和 Plugin 环境都从明确且兼容的前序状态恢复；Task 声称连续性时，任何一项都不能悄悄回退。
- 即使 Pod 被删除、后续 TaskRun 在另一节点或另一集群执行，只要连接到同一数据库和对象存储，也能继续运行。
- 无需读取日志或对象存储键名，就能查询每次恢复结果。
- 在进程退出、请求重试，以及 MySQL 与对象存储之间不存在跨系统事务的情况下，检查点发布仍然安全。
- 默认方案适用于私有部署，不要求 Kubernetes 为临时存储之外再提供 CSI 驱动。
- Agent 可写工作区、运行时管理的 `BUILDMAX_HOME` 和隐藏的进程临时目录，都有实际的文件系统边界，而不是依赖提示词约定。
- Space 文件只为 Task 创建私有工作区快照；之后 Space 的变化不会修改已有 Task，Agent 编辑也不会隐式写回。
- Artifact 发布仍是独立服务，不要求 Agent 文件系统中存在 `artifacts/` 或 `output/` 目录。
- Agent 可以为后续运行获取 Plugin，而不必把扩展后的 `plugins/` 目录作为持久化记录。

### 3.2 非目标

- 恢复同一次模型调用、令牌流或正在运行的 Bash 进程。
- Worker 被要求接管后自动重新执行 TaskRun。
- 从 `SIGKILL`、OOM kill、节点丢失或存储分区中实现零 RPO 恢复。
- 面向用户展示每个工作区状态的历史。
- 任意回滚、文件级恢复、分支、合并或协作编辑。
- 将 Task 工作区重新同步到可变的 Space 文件。
- 把检查点当作 Artifact，或公开其存储位置。
- 将 `buildmax-home/`、Artifact 暂存目录、操作系统 Home 或隐藏的运行时临时文件持久化到工作区归档中。
- 将新获取的 Plugin 热加载到已经组装的 TaskRun 中。
- 把 Git 作为必需或隐藏的持久化引擎。
- 在第一次实施中，大型工作场所加速。

## 4. 所有权与术语

持久化概念仍然彼此独立：

| 概念 | 所有者 | 含义 |
|---|---|---|
| Space 文件（当前 Space Home） | Space | 在 Task 之外管理的、可变的共享输入文件 |
| Task 工作区 | Task | 针对一个 Agent 目标持续存在的私有文件状态 |
| Agent Session | Task | 模型可见的执行历史和压缩后的连续性状态 |
| Plugin 环境 | 默认由 Task 所有 | Task 可用的不可变 Plugin 包版本集合 |

**工作区检查点**是 Task 在某个边界上的 `workspace/` 的完整不可变表示，由服务器元数据和一个存储载荷组成，不能直接编辑。

**基线检查点**是 TaskRun 获准读取和修改的工作区，并在第一次模型或工具调用前固定。**结果检查点**是运行静默后捕获的工作区。**部分检查点**是在取消、中断或执行失败后捕获的结果；它作为恢复证据保留，但默认不会成为 Task 头部。

**Task 工作区头部**是最近一次被接受为 Task 可恢复状态的检查点：最初是种子，之后是每个成功的结果检查点。它是数据库指针，而不是可变的对象存储键。

Task 负责线性工作区谱系，理由与它负责 Agent Session 谱系相同：Task 是持久化线程。TaskRun 负责它收到的基线、尝试发布的结果，以及本次执行的恢复事实。Space 仍是所有这些资源的授权边界。

Artifact 有意不属于这个布局。`UploadArtifact` 通过 Artifact 服务发布从 `workspace/` 选定的普通文件；运行时不会创建 `artifacts/` 或 `output/` 目录，TaskRun 的最终回复由 TaskRun 结果服务直接持久化。

### 4.1 目标运行时目录边界

Agent 运行时有两个逻辑根目录：

```text
<task-run-root>/
├── workspace/       # Agent cwd; freely readable and writable; checkpointed
└── buildmax-home/   # runtime-managed session, Plugin, settings, and diagnostics
```

实现可能还需要操作系统 Home、归档暂存区、套接字、锁和临时文件。这些属于隐藏的进程临时空间，不是第三个面向 Agent 的目录，也永远不会进入检查点。

`workspace/` 是提供给 Read、Write、Edit、Glob、Grep、Bash、工作区配置发现、沙箱和 `UploadArtifact` 的唯一根目录。模型不会通过通用文件系统工具访问 `buildmax-home/`；运行时组件通过类型化存储和配置 API 使用它。模式位或“不要写入”的指令都不构成边界。

运行时不会在工作区上方写入生成的 TaskRun `AGENTS.md`。运行时上下文由提示词携带，而 `workspace/AGENTS.md` 和 `workspace/.buildmax/` 会从实际工作区根自然发现。

### 4.2 `buildmax-home/` 持久化策略

`buildmax-home/` 目录本身可以丢弃；系统只持久化明确列入允许清单的类型化状态：

| 数据 | 是否持久化 | 恢复到后续运行 | 权威来源 |
|---|---:|---:|---|
| Session `meta.json` 和 `history.jsonl` | 是 | 是 | Session 检查点 |
| Notes、todos、压缩记录、工具结果和 Session 头部 | 是，写入日志 | 是 | Session 检查点 |
| 运行 trace 和有界日志 | 按保留策略 | 否 | TaskRun 证据 |
| 已解析的模型、Agent、沙箱、权限、MCP 和 Plugin 修订版本 | 是，保存脱敏清单 | 重新解析并物化 | 服务器和目录 |
| Plugin 包字节 | 若尚不存在则保存一次 | 按不可变包引用物化 | Plugin 包存储 |
| 未来显式声明的 Plugin 可变状态 | 仅限声明的范围和 schema | 按该范围 | Plugin 状态服务 |
| 索引、锁、套接字、下载、缓存和临时文件 | 否 | 否 | 重新创建或丢弃 |
| 凭证、运行令牌、Secret 授权和生成的认证文件 | 永不 | 通过 Secret/凭证权威重新获取 | Secret 服务 |

保存诊断信息并不意味着允许恢复它。trace 和日志仍是证据；原始 `settings.yaml`、`mcp.json` 和展开后的 Plugin 目录会被脱敏的已解析清单及不可变源引用取代。如果将来引入长期 Agent 记忆，它也应是独立的授权资源，而不是 `BUILDMAX_HOME` 的偶然子目录。

## 5. 连续性合同

### 5.1 首次运行与 Space 种子

第一次 TaskRun 从 Space 共享文件的快照开始。Worker 会：

1. 认领 TaskRun；
2. 将选定的 Space 文件快照物化到空的 `workspace/` 中，并保留工作区根目录下的相对路径；
3. 捕获并发布 `seed` 检查点；
4. 将该检查点记录为 TaskRun 基线；然后才
5. 启动 Agent 运行时。

物化后的文件会成为私有且可写的分支，Agent 编辑不会隐式写回 Space。之后 Space 的上传、替换和删除都不会改变已有 Task；Continue 会恢复 Task 工作区检查点，而不是再次导入最新共享文件。刷新或写回操作应是未来明确的产品动作，并具备冲突和授权语义。

种子就是首次运行实际看到的目录。若源端能提供，检查点会记录源 Space 快照身份；否则记录物化文件清单及其摘要。与旧的非事务性物化并发的上传仍可能混入不同的 Space 写入，但提交的种子会在 Agent 产生外部副作用前冻结并标识那份确切副本。

如果种子无法提交，Agent 不会启动；运行会在模型或工具执行前失败，因为它没有可复现的基线。

### 5.2 Continue

创建新 TaskRun 时，Continue 会固定两个前序引用：

- `previous_task_run_id` 提供 Agent Session；
- `workspace_base_checkpoint_id` 提供 Task 工作区。

两项恢复都必须在 Agent 启动前完成，并记录结果。检查点缺失、损坏、未授权或不受支持时，运行会直接失败；Session 捆绑包缺失或损坏时同样如此。以新 Session 或当前 Space 文件开始，却把操作呈现为 Continue，是禁止的。

未来的明确恢复动作可以允许用户从最近的持久化工作区头部继续，而不依赖紧邻的前一 Session，反之亦然。这是新的用户决定，不能作为隐式回退。

### 5.3 Retry

Retry 会重复一次执行尝试，因此其工作区基线就是所指 TaskRun 的基线：

```text
run A: base C1 ---- execution ---- partial or result C2
retry A: base C1 -- new execution -- result C3
```

Retry 不从 C2 开始，即使 C2 可用。失败尝试可能让仓库停在迁移中途、在旧清单旁留下生成文件，或产生无法从文件推断的外部副作用。复用其部分状态会把 Retry 变成 Resume。

Retry 仍按现有重试规则恢复 Task Session。Retry 记录的 Session、工作区和 Plugin 环境引用必须描述实际提供的组合；界面不能暗示 Retry 会重建外部副作用。

### 5.4 Plugin 环境连续性

`buildmax-home/plugins/` 是物化投影，永远不是检查点。持久化对象是 **Plugin 环境修订版本**：由 `plugin_id`、版本、包摘要、包引用、来源、安装器、声明范围和已解析权限修订组成的不可变有序集合。

Agent 可以使用类型化的 `PluginSearch`、`PluginInspect` 和 `PluginInstall` 能力，但不能通过 Bash 写入 `buildmax-home/plugins/` 来完成持久安装。目录中的包可以被引用，不必重复上传其字节。私有包或 Agent 生成的包必须先规范化、检查、验证摘要并存入 Plugin Store，环境修订版本才能引用它。展开后的目录、下载内容、缓存、凭证和未声明的 Plugin 状态都不会上传。

已组装的工具注册表、系统提示、MCP 服务器、Hook、沙箱规则和 Secret 要求在一个 TaskRun 内保持不变。因此安装 Plugin 会形成能力变化边界：Worker 先让当前运行静默，提交当前 Session 和工作区，记录新的 Plugin 环境，再创建一个物化该环境的新 TaskRun 以继续同一 Task。产品界面可以把它呈现为自动继续，但执行记录必须保留这条边界。

自主安装默认属于 `task` 范围，仍需 Space 允许自主获取；普通 Task 执行权限不等于 Plugin 管理权限。提升到 Agent 或整个 Space 的范围需要明确的授权动作。引入可执行工具、MCP 服务器、Hook、更广泛文件系统或网络访问权限，或要求 Secret 的 Plugin，都必须通过相应的策略和审批门；安装包从不隐式授予 Secret。

Continue 使用 Task 当前的 Plugin 环境头部；Retry 使用被重试 TaskRun 的基线 Plugin 环境。失败或中断的安装可能留下待垃圾回收的未引用包，但不会推进 Task 的 Plugin 环境头部。

### 5.5 完成成功

在Agent循环和所有产生的每个子进程停止后，工人捕获`workspace/`，上传有效载荷，验证它，并要求服务器执行`successful`结果检查点。

成功检查点描述器与终端TaskRun报告一起运行.服务器记录检查点并在接受该报告的交易中提前`task.workspace_head_checkpoint_id`.一个过时或重复的终端报告可能会随时恢复成功，但它不能改变由首个接受的报告选择的头。

TaskRun 状态与工作区持久化相关，但属于不同事实。如果 Agent 生成了成功答案，而最终检查点发布失败，运行仍为 `SUCCEEDED`，并记录 `workspace_checkpoint_status=failed`。最终回复和独立发布的 Artifact 仍有效；Task 工作区头部不前进，在用户明确选择恢复基线或检查点修复前，Continue 会被拒绝。把整个运行标为失败会诱导 Retry，仅仅因为执行后的存储失败就重复外部副作用。

### 5.6 失败，取消和中断

对于执行失败，用户取消或优雅的过程中断，工人可以在用于终端报告的相同的限制报告窗口内发布`partial`检查点。

一部分检查点：

- 通过其TaskRun进行连接；
- 没有自动向前推进Task工作空间头；
- 没有被 Retry 使用；
- 保存用于诊断和未来明确的复习行动；以及
- 报告期限过短时可能缺席。

检查点故障不能删除或重写已通过执行确定的终端结果。 TaskRun

### 5.7 硬的Worker损失

子代理 `SIGKILL` TaskRun Task

采用BuildMax，并不能默默地再次发送相同的TaskRun。 模型选择的工具可能已经在工作空间之外写了，称为API，推出了分支或打开了拉动请求.只有明确的Retry或未来的简历才能创建新的执行尝试。

## 6. TaskRun 生命周期

目标生命周期是：

```text
PENDING
   |
   v
SCHEDULED
   |
   | atomic worker claim
   v
RUNNING
   |
   | restore or create workspace and session bases
   | materialize the immutable Plugin environment
   | record restore outcome
   | no model/tool call before this gate
   v
EXECUTING (logical phase; not a new public TaskRun status)
   |
   | quiesce Agent and owned children
   | capture and upload result/partial checkpoint
   v
terminal TaskRun status + workspace/session/Plugin environment outcomes
```

没有新的公共TaskRun执行状态.工作场所的准备，检查点和插件环境的实现是专门列中记录的子属状态.将相关标识符或`CHECKPOINTING`添加到TaskRun状态词汇中，将使每个状态消费者理解存储实现细节，并且仍然无法正确表达成功与检查点失败。 `PREPARING`

工人心跳开始在原子运行声称后，并继续在物质化，执行和检查点上传期间.因此，活力收获器可以检测到一个工人在任何这些阶段中丢失.长时间的物体储存工作不应该出现作为沉默。

捕获前，跑步时间必须静止：

- 没有新的工具调用可启动；
- 首页工具调用已返回或取消；
- 运行时间所属的儿童流程已退出或已被杀；以及
- 在分别上传之前，会话日志关闭。

经过一个不追踪的作者活动时，检查树的检查不能提供一致的边界。

## 7. 存储和档案格式

### 7.1 运载配置

首个有效载荷格式是`tar.zst.v1`：每一个检查点每一个Zstandard压缩的土档案.存储密钥是所有者Space内内容地址：

```text
<prefix>/<space_id>/workspace/blobs/sha256/<64-lowercase-hex>
```

检查点排列记录了有效载荷格式，消化，存储的大小，未压缩的常规文件字节和输入数量.对象商店适配器取出了钥匙；没有API或痕迹暴露它。

采用Space的内容处理允许在一个授权边界内安全重复使用，而不会透露另一个Space是否存储相同内容.第一项实现可以使用`ObjectExists`以避免重复上传.它仍然必须对记录的消化进行检查。

文件内容的显示之前选择一个单个档案，因为源树通常包含许多小文件.一个档案需要一个流通的GET，避免LIST加上数千次请求回路.格式列为后续分块或显示支持的表示留下了空间，而不会改变检查点域模型。

### 7.2 佳能档案规则

文件库创建按词汇分断分类顺序行走的路径.每个标题使用与`workspace/`相对的路径.实现保存：

- 常规文件字节；
- 目录；
- 执行式和普通的许可比特；
- 修改时间；以及
- 安全的相对象征性链接。

它不保留所有者，组,ACL，扩展属性，稀疏文件布局，设备节点，插座或FIFO。 UID和GID正常化为零，名称是空的.Setuid,setgid和粘贴的位被剥离。

绝对路径,`..`穿越，重复正常化的路径，硬链接，设备节点，插座,FIFOs，绝对符号链接和逃离档案根的相对符号链接使捕获失败.提取应用相同的验证独立；仅仅因为BuildMax生成了档案，它将对象存储腐败变成文件系统逃脱。

版本1中没有隐含的忽略规则.`.git`，生成的文件和`workspace/`内的缓存是检查点的一部分，因为沉默的排斥将使工作空间错误.操作员限制了可容量的尺寸.后来可能会设计明确的排斥政策，但其遗漏的路径和恢复后果必须在TaskRun上看到。

### 7.3 材料化

恢复文件库在目标文件系统上的新临时目录中，验证每个输入和总数限制，验证有效载荷消化，然后将目录更名为现实。 Agent

工作者不会通过对象存储列表发现一个检查点.它从服务器接收一个不可变的描述符并执行直接的GET.因此,LIST一致性和无关的对象不能影响恢复。

### 7.4 为什么档案不是一个Artifact

检查点是自动执行状态，可能包含源，缓存或私有中间文件.一个Artifact是一个有稳定的用户身份的故意出版物.自动注册检查点档案为Artifacts将违反`unified-artifacts.md`中明确发布决定，并将一个实施格式作为产品内容暴露。

## 8. 提交协议与一致性

MySQL 与对象存储无法参与同一个事务。因此，发布流程采用**先写入不可变字节，再更新权威指针**的顺序：

1. 将归档捕获到有大小限制的本地临时文件中，同时计算 SHA-256 和各项计数；
2. 将其上传到按内容寻址的键，或确认该键下已经存在完全相同的字节；
3. 按需读取元数据或流式读取对象，以验证准确的对象键；
4. 通过准备调用发送种子描述符，或在终态 TaskRun 报告中携带结果或部分检查点描述符；这些请求都通过运行令牌认证的 Worker API 发送；
5. 验证 Space、Task、TaskRun、检查点类型、摘要、格式和边界；
6. 在一个 MySQL 事务中插入检查点，并更新 TaskRun 和可选的 Task head；对于结果或部分检查点，这就是接受运行终态结果的同一个事务；
7. 将已提交的检查点标识返回给 Worker。

完成调用是无效的.重复相同的TaskRun，检查点类型，消化和元数据返回现有检查点.重复一个类型的不同字节是冲突；它从来没有重写接受的检查点。

只有第一个有效终端过渡才能推进Task头.更新检查TaskRun的预期状态,Task的活跃运行，以及该运行记录的基准检查点.这防止一个迟来的工人，复制Pod，或重新尝试HTTP请求将头部移动到后面或后面运行。

没有承诺的检查点行的上传有效载荷是孤儿，而不是检查点.保留扫描可能会删除比保守的宽限期更老的未引用的斑点.扫描必须从数据库引用中获得活力，并且必须容忍同时完成的上传；最近的对象永远不会成为候选人。

数据库行从来没有指向未经验证的字节.如果数据库提交在上传后失败，旧的Task头仍然是权威的.如果提交后的响应丢失，无效的最终化返回相同的行。

AWS S3 提供了个别键的原子更新和强大的读取后写一致性，但BuildMax 也支持S3兼容的商店.该协议使用不可变的键和明确验证，而不是将 AWS 行为视为每个兼容的后端上的无证要求。

## 9.关系模型

### 9.1 `workspace_checkpoint`

由于恢复选择可能需要将其命名在API边界之上，因此`workspace_checkpoint`是一个服务器实体.它从`util.NewPublicID`获得一个不透明的公共手柄；内部关系使用数字密钥。

目标行：

| 列表 | 类型 | 零 | 备注 |
|---|---|---:|---|
| `id` | `bigint unsigned` | 没有 | 内部主要钥匙 |
| `public_id` | `char(20) ascii_bin` | 没有 | 唯一的公共手柄 |
| `space_id` | `bigint unsigned` | 没有 | 授权所有者，索引 |
| `task_id` | `bigint unsigned` | 没有 | 工作空间所有者，以创建顺序进行索引 |
| `source_task_run_id` | `bigint unsigned` | 没有 | 捕获了它的Run |
| `base_checkpoint_id` | `bigint unsigned` | 没有 | 后代前任 |
| `kind` | `varchar(32)` | 没有 | 类型： 相关内容 `seed` `successful` `partial` |
| `payload_format` | `varchar(32)` | 没有 | 起初是`tar.zst.v1` |
| `payload_sha256` | `char(64) ascii_bin` | 没有 | 存储的字节消化 |
| `storage_key` | `varchar(1024)` | 没有 | 隐私后端关键，从未连串化 |
| `size_bytes` | `bigint` | 没有 | 存储的有效载荷字节 |
| `uncompressed_bytes` | `bigint` | 没有 | 常规文件大小的总和 |
| `entry_count` | `bigint` | 没有 | 常规文件，目录和标志链接 |
| `created_at` | `datetime(6)` | 没有 | UTC 提交时间 |

独特性是`(source_task_run_id, kind)`.一个TaskRun至少有一个种子，一个成功结果和一个部分检查点.`payload_sha256`在全球范围内并不独特，因为单独的检查点行可以故意命名相同的不可变的有效载荷并保留单独的来源。

采用`storage_key`的存储密钥则与Artifact相同：它是基础设施数据，并且不在域名JSON中，可见于工人的TaskRun响应，日志和痕迹。

### 9.2 `task`

添加无可归的`workspace_head_checkpoint_id`。 它指向被接受的最新检查点作为这个Task的可归还状态：它的初始种子或后来的成功结果。 它是一个在检查点完成相同的交易中保持的投影，因此,TaskRun终端过渡。

标志器是无效的，对于一个Task，其第一次运行没有承诺其种子或成功结果.一个种子可以成为首位在第一次执行之前，这样一个难以输掉仍然留下一个决定性重试基础。

添加无可取消的`plugin_environment_head_id`。 它指向下一个继续使用的不可变的插件环境修改.没有自主安装的Task可以继续从Agent修改和Space激活中提取其环境.超越Task的推广范围通过拥有Agent或Space服务而不是改变这个相关标识符的功能。

### 9.3 `task_run`

加入：

| 列表 | 意思 |
|---|---|
| `workspace_base_checkpoint_id` | 在执行之前选择的不可变的基础 |
| `workspace_result_checkpoint_id` | 承诺时成功的结果检查站 |
| `workspace_partial_checkpoint_id` | 部分检查站，当已实施 |
| `workspace_restore_status` | 类型： 相关内容， `not_requested` `pending` `restored` `failed` |

相关标识符拥有以下规则： `internal/core/task`

## 12. 安全，限制和保留

### 12.1 文件系统安全

捕获和恢复从来没有遵循`workspace/`之外的路径。 提取器创建了控制的API而不是调用系统`tar`二进制。 它拒绝不支持的输入类型，并删除具有特权的模式位。

档案中仅包含`workspace/`。 仅包含`buildmax-home/`，扩展的插件树，操作系统主机，档案编辑，凭证，日志，痕迹，缓存和其他运行时间的划痕。 没有Artifact或输出目录可以排除。

文件上传是不隐含的运行时间配置补贴。 控制轴承路径如相关标识符和`.buildmax/`是从普通文件上传表面保留的，或者只通过明确的Space配置许可和审计事件可编写.共享文件贡献者不得通过选择文件名获得快速，,MCP，或插件权。 `AGENTS.md`

环境秘密授予仍然可以通过模型选择的命令故意复制到`workspace/`.Space已经授权Agent读取这些值，因此检查点不会创造新的保密界限，但会延长保留.在运输之前，威胁模型必须决定在常规工作空间文件中发现的确切的授予秘密值是否导致警告，检查点拒绝或编辑诊断.沉默删除会破坏工作空间，并且不允许。

### 12.2 物品存储局

采用Worker的运行代币仅在HTTP边界接收，但当前的生产存储路径也可能会让Pod的工作负载身份访问桶.检查点键在运行的Space名字空间内留下，服务器在提交之前取出或验证每个存储参考。

长期最小特权改进是经过运行的上传/下载租或预签署的请求，没有通过工人API暴露任意的桶钥匙.本记录不声称改进已经出货。

### 12.3 资源限制

工人约伯必须获得两者：

- 容器`ephemeral-storage`要求和限制；以及
- 工作空间，跑时家庭和`/tmp`卷的`emptyDir.sizeLimit`。

控制台的存储入口限制包括现实化工作空间，扩大的插件包，临时压缩的有效载荷，日志和普通的工具抓取空间.控制台的自己的限制仅包括`workspace/`.控制台捕获停止在耗尽Pod的存储限制之前，并记录有限的故障，而不是等待Kubelet驱逐。

检查点的限制包括至少：

- 存储的字节；
- 没有压缩的常规文件字节；
- 进入数量；
- 路径的最大长度；
- 个人文件最大规模；以及
- 减压扩张比率。

在本记录中，未选的默认数据必须来自代表源，构建和数据工作空间的基准证据，并在实施时必须记录在配置参考中。

### 12.4 保留

成功的检查站遵循Task保留.一个TaskRun或后来的检查站引用它们时，种子检查站仍然存在.部分检查站可能具有操作员配置的更短的保留时间，但在可见的恢复行动命名期间，它们永远不会被删除。

内容地址的点只会在没有检查点行引用存储密钥时被删除，并且点比孤儿宽限期更老.数据库和桶备份/恢复仍然是一对：如果没有另一个恢复，则可以让转载数据没有有效负载或转载数据没有有效负载。

检查点字节与一个不同的工作空间状态配额相比计算.它们不算是Artifact字节，也不出现在Artifact配额或列表中。

| 失败点 | 持续的观察 | 自动行为 | 恢复基础 |
|---|---|---|---|
| 在工人索赔之前 | Run保持在 `SCHEDULED` 状态，直到现有的发送处理解决。 | 相关标识符可能在索赔之前再次尝试启动 Kubernetes | 没有要求 |
| 文件快照演化失败 Space | 恢复状态`failed`；没有模型/工具调用 | 关闭 Run 失败 | 没有Task工作空间 |
| 种子上传或提交失败 | 检查点状态`failed`；没有模型/工具调用 | 关闭 Run 失败 | 没有，因为执行从来没有开始 |
| 继续工作空间恢复失败 | 恢复状态和边界错误 | 关闭 Run 失败 | 显而易见的修复或恢复选择 |
| 继续会议恢复失败 | 恢复会议状态和边界错误 | 关闭 Run 失败 | 显而易见的修复或恢复选择 |
| 插件环境实现失败 | 插件环境状态和界限错误 | 关闭未能完成的 Run | 记录的基层环境 |
| 自主插件安装失败 | 安装状态和边界错误 | 电流运行保持其不可变的基础；没有能力交换 | 记录的基层环境 |
| 执行工具失败 Agent | 正常的结果失败；试图部分捕获 | 没有自动重试 | 记录的基础 |
| 用户取消 | 取消结果；试图部分捕获 | 没有自动重试 | 记录的基础；仅部分由明确的未来简历 |
| 或驱逐 | 失败/中断结果；试图限制部分捕获 | 报告后的流程出口 | 记录的基础，加上部分，如果已承诺 |
| //节点损失 | 活生的记录失去了工人 | 没有自动重新发送 | 记录的基或之前的Task头 |
| 结果使用载荷上传失败 | 报告中仍有Run结果；检查点状态`failed` | 头不进步 Task | 上一个Task头 |
| 运载成功,DB提交失败 | 老头仍然存在； 载荷是孤儿 | 无力再次尝试可能会犯下 | 上一个Task头，直到提交 |
| 电脑的反应失去了 | 检查点和头部是耐用的 | 无效重复试验返回现有行 | 新承诺的检查站 |
| 后者消失/腐败 | 恢复验证显而易见失败 | 没有回归 | 运营商恢复桶或选择另一个基地 |
| 恢复数据库没有桶 | 缺失的有效载荷是可见的 | 没有回归 | 复原复合备份 |

首项实施的恢复目标是故意限制的：

| 事件 | 结果 | 驱动因素 |
|---|---|---|
| 终端运行成功 | 终极承诺的检查站 | 文件下载和提取 |
| 无限的取消/中断 | 部分检查点，如果符合报告预算；以其他方式记录的基础 | 物体存储库的可用性和档案规模 |
| 工作者或节点损失 | 最后承诺的基础/头；所有当前未承诺的文件系统工作可能会丢失 | 活力优势加上新运行的安排和恢复 |

没有数字的RTO承诺，直到实现与支持的部署配置文件进行比较.Portal报告测量捕获和恢复时间，以便运营商可以设定基于证据的目标。

## 14. API， Portal，以及可观察性

### 14.1 Worker API

确切的路线仍然是注册时间实施细节，但工人需要三个类型的操作：

1. 获取运行所选的不可变基分类符；
2. 记录基底恢复成功或失败；以及
3. 记录种子检查点，或携带成功/部分检查点描述符
关于终端TaskRun报告。

所有需要运行代币。 运行准备期间允许对`RUNNING`进行基点检索。 完成只允许用于同一运行和一个合法的检查点类型。 服务器从代币的相关标识符中提取Space和Task； 工作者从来没有提供权限持有者身份证。 TaskRun

服务器接收和验证元数据，而不是通过其HTTP过程代理多吉加字节的档案。

### 其他类型的子代理， Task TaskRun API

详细的Task揭示了其当前工作空间主管的公众身份和总结，而不是一个存储密钥。 TaskRun

- 根据现有情况，成功结果和部分检查点的身份；
- 恢复会议，工作空间和插件环境的结果；
- 检查点的公布结果；
- 存储和不压缩的尺寸加上入口数量；
- 捕获和恢复时间；以及
- 如果任何操作都失败，则会出现有限的错误。

第一个实现不添加一个通用检查点列表或下载路线，这些将使内部连续状态变成面向用户的版本历史记录，需要单独的产品决定。

### 14.3 Portal

页面中显示一个紧的工作空间状态， Task

- **恢复** 基因身份和恢复时间；
- **保存** 结果检查点和尺寸；
- **部分状态保存**  只有故障/取消，不自动使用；
- **工作空间未保存** 可见警告，最后一个持久的头；或
- 运行未执行。

由于该错误只能在该操作设计和授权后实现明确恢复操作；它从来没有默默地取代当前的Space文件或不同的Plugin环境。

### 14.4 追踪和指标

追踪记录限制了元数据事件，从来没有存档内容或私有存储密钥：

- `workspace.restore.started/completed/failed`；
- `workspace.checkpoint.started/completed/failed`；
- 子代理 `plugin.environment.materialize.started/completed/failed`
`plugin.install.requested/committed/failed`；
- 检查点类型，公开身份证后的承诺，大小，入口数量，消化前，
持续时间和源运行；以及
- 报告预算过期，否被跳过捕获。

计量包括捕获/恢复延迟，压缩和未压缩字节，压缩比，限类失败，孤儿数量，以及存在后续持续缓存配置文件时缓存击中。

16.4 的破坏性条目与第 13 节的失败矩阵——取消与 SIGTERM 的 partial 捕获、

## 17. 拒绝其他选择

### 17.1 默认情况下每Task一个PVC

片在Pod删除后保存文件系统状态，但使每一个Task拥有Kubernetes存储对象，其容量决定，垃圾收集，备份，拓，附件延迟和CSI可用性.它也不会提供跨集群恢复.这对可移植默认部署非常具体，并且仍然是一个可能的缓存配置。

### 17.2 一个RWX Space工作空间

不同Tasks将成为共享可变状态的同步编写者.线性单字符不变量为Task，而不是Space,RWX不提供应用级冲突或来源语义.此选项解决了安装，同时使所有权不太正确。

### 17.3 与本地光伏或`hostPath`的节点亲密性

节点的时间表，维护和容量压力成为正确性依赖.本地磁盘可能会缓存一个验证的检查点，但不能成为其权威。

### 17.4 作为一个必要的平台组件的分布式文件系统

斯FS,CephFS,NFS和云NAS可以在规模上有用，但需要一个将添加一个运营控制平面和狭窄的私人部署可移植性之前BuildMax有工作负载证据要求它。

### 17.5 InitContainer 下载和副车上传作为协议

简单的数据集中的数据集，可以在线数据集中进行转换，但它们都不能使用 TaskRun 权限，静止，血统，终端状态，或 MySQL 指针.生命周期子不能在硬损失后运行.它们可能会在后面实现数据路径的一部分；它们无法定义提交协议。

### 17.6 Git作为工作场所管理局

并非每个Task工作空间都是Git存储库,Git自然不拥有大型二进制，生成的树木，任意上传，或者是Git的确切非Git状态.使Git隐藏不会删除其存储库和融合语义；它只会隐藏它们.[阅读中文镜像](Task工作区检查点.md)工作空间内容当存在时，不保持相关标识符引擎的耐用性。 Agent BuildMax

### 17.7 单独上传每个文件

现在的Space文件 (Space Home) 适配器一次列表并下载对象，一次.重复对Task检查站的设计使请求计量与文件计量相对，并且对源树表现不佳.单个版本的档案是较小的第一次正确性表面.增量表现仍然存在证据门。

### 17.8 丢失的TaskRun自动简历

文件系统状态不能说工具的外部副作用是否发生。 工作人员丢失后自动重新启动可以复制电子邮件,API调用，提交，发布评论或部署.恢复为新尝试提供了明确的基础；它不会删除对Retry或未来简历语义的需要。

### 17.9 检查点 扩展的插件目录

装载`buildmax-home/plugins/`将保留Agent获得的包字节，但它还将保存提取Artifact，缓存，未宣布可变状态，可能的凭证和字节，这些字节不再证明他们的目录消化.它每次运行都重复相同的不可变包，并绕过恢复时的安装政策.BuildMax相反，在必要时存储一个正常化的私人包，记录在插件环境中不可变的编辑，并重新材料化每个相关标识符的目录。 TaskRun
