## 1. 决策

BuildMax 会把一次 TaskRun 活跃的文件系统保留在本地临时存储上，并把一个 Task 可恢复的工作区,以不可变检查点的形式持久化到已配置的对象存储中。

默认的执行方案是：

```text
Task workspace checkpoint in S3 / MinIO / local persistent storage
                              |
                              | materialize
                              v
                  TaskRun emptyDir/workspace
                              |
                              | capture after quiescence
                              v
                  immutable next checkpoint
```

真正权威的是检查点,而不是 Pod 卷。Kubernetes 的 `emptyDir` 仍然是默认的工作磁盘，因为它速度快、按 Pod 隔离、可移植，而且 worker Job 本来就已经在用它。将来也许会用一个持久卷来加速大型工作区，但那不会取代对象存储里的检查点，也不会改变 Task 的语义。

本文档引入的是一项刻意收窄的能力：**Task 工作区连续性**。它不是要复活那个已被撤回的通用版本化工作区产品。这套设计里没有工作区时间线、任意回滚、分支模型、变更集审查、合并,也没有向共享 Space 文件的自动写回。

恢复的单元是 `workspace/` 的一份完整、不可变的快照。第一版实现使用带版本号的压缩归档；在有测量证据表明完整归档方案不够用之前，不会引入增量式文件系统协议。

## 2. 问题与当前基线

Worker 已经把一次运行拆分成了四个文件系统区域：

| 区域 | 当前角色 | 当前的持久性 |
|---|---|---|
| `home/` | Space Home 的物化副本；Agent 实际操作的文件 | 运行结束后不上传 |
| `artifacts/` | 运行输出，包括 `result.md` 和刻意生成的文件 | 在终态上报时上传 |
| `global/` | 运行范围内的 `BUILDMAX_HOME`：会话、轨迹、日志、设置、Plugin | 在终态上报时上传选定文件 |
| `oshome/` | 供工具和凭证文件使用的空白私有操作系统 home 目录 | 从不上传 |

`internal/agentapp/taskrun.prepareRunWorkspace` 会创建这些目录，在存在前序 Agent 会话时恢复它，并把当前的 Space Home 物化到 `home/` 中。`reportPersistedRunState` 会上传 `global/` 和 `artifacts/`，但不会上传 `home/`。

那套布局是本设计要取代的基线，而不是目标布局。具体来说，当前的运行时把整个 TaskRun 目录都当作 Agent 的工作区根目录传递出去，因此文件工具、Artifact 发布、工作区本地配置发现、Bash 的工作目录,以及沙箱,彼此之间并不认同 `home/` 就是工作区。提示词要求 Agent 不要写入 `global/`，但把运行时状态嵌套在可写的工具根目录之下，并不构成一条访问边界。这还允许一次合法的顶层写入，而未来一个只针对 `home/` 的检查点会悄无声息地漏掉它。

于是，一个被继续（Continue）的 Task 可能会恢复出一段"某文件已被修改"的、模型可见的历史，却同时拿到一份不包含这次改动的全新 Space Home 副本。即便两条恢复路径各自都报告成功，模型和文件系统仍然可能相互矛盾。

现有的会话恢复也会在不记录结果的情况下失败开放：捆绑包只要缺了一半,就会被直接丢弃，运行从头开始。在 Continue 成为一项用户可见的契约之前，这种行为还算可以接受；但对于一个声称具备连续性的 Task 来说，这就不可接受了。

Kubernetes 本身也无法弥补这个缺口。同一个 Pod 内的容器重启不会影响 `emptyDir`，但 Pod 一旦被移除，其中内容就会被永久删除。Job 控制器可以在一个 Pod 失败后创建一个替代 Pod，Kubernetes 也明确要求 Job 类应用要自行处理临时文件、锁、部分输出，以及可能出现的重复启动。因此,持久化边界应当由 BuildMax 自己定义，而不能建立在"某个 Pod 会一直活着"这种假设之上。

## 3. 目标与非目标

### 3.1 目标

- 一次 Continue 运行,拿到的是其所属 Task 已提交的确切工作区头部（head）。
- 一次 Retry,拿到的是它所重试的那次运行所使用的确切工作区基线。
- 会话历史、工作区状态和 Plugin 环境，都从明确、兼容的前序状态恢复；只要 Task 声称具备连续性，其中任何一项都不允许悄悄回退。
- 一个 Pod 可以被删除，之后的 TaskRun 完全可以在另一个节点甚至另一个集群上执行，只要它们连接的是同一个数据库和对象存储。
- 每一次恢复的结果都可以直接查询到，不需要去读日志或对象存储的键。
- 即便进程中途死亡、请求被重试，也不存在一个横跨 MySQL 和对象存储的事务，检查点的发布依然是安全的。
- 默认方案要能跨私有化部署保持可移植性，除了 Kubernetes 本身为临时存储所需要的东西之外，不要求任何额外的 CSI 驱动。
- Agent 的可写工作区、由运行时管理的 `BUILDMAX_HOME`，以及隐藏的进程临时空间，三者之间要有真正强制执行的文件系统边界，而不只是提示词层面的约定。
- Space 文件只用来为一个 Task 私有工作区的快照提供种子；之后 Space 一侧的变更不会改动一个已存在的 Task，Agent 的编辑也不会隐式写回。
- Artifact 发布依然是一项独立的服务，不需要 Agent 文件系统里存在任何 `artifacts/` 或 `output/` 目录。
- Agent 可以为了之后的执行获取一个 Plugin，而不必让展开后的 `plugins/` 目录本身成为持久化记录。

### 3.2 非目标

- 恢复同一次模型调用、同一段令牌流，或者一个仍在运行中的 Bash 进程。
- 在 worker 认领之后，自动重新执行一次 TaskRun。
- 针对 `SIGKILL`、OOM kill、节点丢失或存储分区实现零 RPO 恢复。
- 面向用户展示每一个工作区状态的历史记录。
- 任意回滚、文件级别的恢复、分支、合并，或协作编辑。
- 把一个 Task 工作区重新同步回可变的 Space 文件。
- 把一个检查点当作 Artifact 对待，或者公开它的存储位置。
- 把 `buildmax-home/`、Artifact 暂存目录、操作系统 home，或隐藏的运行时临时空间持久化进工作区归档里。
- 把新获取的 Plugin 热加载进一个已经组装好的 TaskRun。
- 把 Git 当作一个必需或隐藏的持久化引擎。
- 在第一版实现里就做大型工作区的加速优化。

## 4. 所有权与术语

这几个持久化概念彼此保持独立：

| 概念 | 归属者 | 含义 |
|---|---|---|
| Space 文件（当前的 Space Home） | Space | 在 Task 之外管理的、可变的共享输入文件 |
| Task 工作区 | Task | 为一个 Agent 目标持续存在的私有文件状态 |
| Agent 会话 | Task | 模型可见的执行历史，以及压缩后的连续性状态 |
| Plugin 环境 | 默认归 Task 所有 | Task 可用的一组不可变的 Plugin 包版本 |

一个**工作区检查点**，是 Task 的 `workspace/` 在某个边界时刻的完整、不可变表示。它由 server 端的元数据加上一份存储载荷组成，不能被直接编辑。

一个**基础检查点（base checkpoint）**是一次 TaskRun 被授权读取和修改的那份工作区，它在第一次模型调用或工具调用之前就已固定。一个**结果检查点（result checkpoint）**是一次运行静默（quiesce）之后捕获的工作区。一个**部分检查点（partial checkpoint）**是在取消、中断或执行失败之后捕获的一份结果；它作为恢复证据被保留下来，但默认不会成为 Task 的头部。

**Task 工作区头部**是被接受为该 Task 可恢复状态的最新检查点：最初是它的种子（seed），之后则是每一次成功的结果检查点。它是一个数据库指针，绝不是一个可变的对象存储键。

Task 拥有这条线性工作区谱系的所有权，理由和它拥有 Agent 会话谱系的所有权是一样的：Task 才是那条持久化的线索。TaskRun 则拥有它所收到的基础、它试图发布的结果，以及这次执行的恢复事实。而 Space，始终是这一切的授权边界。

Artifact 被有意排除在这套布局之外。`UploadArtifact` 会通过 Artifact 服务，把从 `workspace/` 中选定的一个普通文件发布出去；运行时不会创建任何 `artifacts/` 或 `output/` 目录，TaskRun 的最终回复由 TaskRun 结果服务直接持久化。

### 4.1 目标运行时目录边界

Agent 运行时有两个逻辑根目录：

```text
<task-run-root>/
├── workspace/       # Agent cwd; freely readable and writable; checkpointed
└── buildmax-home/   # runtime-managed session, Plugin, settings, and diagnostics
```

具体实现可能还需要一个操作系统 home、归档暂存区、套接字、锁和临时文件。这些都属于隐藏的进程临时空间，不是第三个面向 Agent 的目录，也永远不会被纳入检查点。

`workspace/` 是提供给 Read、Write、Edit、Glob、Grep、Bash、工作区配置发现、沙箱，以及 `UploadArtifact` 的唯一根目录。模型不会拿到访问 `buildmax-home/` 的通用文件系统工具权限；运行时的各个组件是通过带类型的存储和配置 API 来使用这个目录的。一个权限位或者一句"不要写入"的指令,都构不成一条边界。

工作区之上不会写入任何生成出来的 TaskRun 专属 `AGENTS.md`。运行时上下文由提示词携带，而 `workspace/AGENTS.md` 和 `workspace/.buildmax/` 则会从真正的工作区根目录里被自然发现。

### 4.2 `buildmax-home/` 的持久化策略

`buildmax-home/` 作为一个目录本身是可以随意丢弃的。系统只持久化经过类型化、明确列入白名单的状态：

| 数据 | 是否持久化 | 是否恢复到之后的运行中 | 权威来源 |
|---|---:|---:|---|
| 会话的 `meta.json` 和 `history.jsonl` | 是 | 是 | 会话检查点 |
| 笔记、待办事项、压缩记录、工具结果，以及会话头部 | 是,写入日志内 | 是 | 会话检查点 |
| 运行轨迹与有界日志 | 按保留策略 | 否 | TaskRun 证据 |
| 已解析的模型、Agent、沙箱、权限、MCP 和 Plugin 版本 | 是，保存脱敏后的清单 | 重新解析并再次物化 | server 与各类目录 |
| Plugin 包字节 | 在尚不存在时保存一次 | 按不可变的包引用重新物化 | Plugin 包存储 |
| 未来明确声明的 Plugin 可变状态 | 仅在声明的范围和 schema 之内 | 按该范围恢复 | Plugin 状态服务 |
| 索引、锁、套接字、下载内容、缓存与临时文件 | 否 | 否 | 重新创建或直接丢弃 |
| 凭证、运行令牌、Secret 授权，以及生成出的认证文件 | 从不 | 通过 Secret/凭证权威机构重新获取 | Secret 服务 |

保存一份诊断信息，不等于允许恢复它。具体来说，轨迹和日志始终只是证据；原始的 `settings.yaml`、`mcp.json`,以及展开后的 Plugin 目录，都会被脱敏后的已解析清单加上不可变的来源引用所取代。将来如果引入长期的 Agent 记忆，它也应当是一种独立、经过授权的领域资源，而不是 `BUILDMAX_HOME` 底下一个偶然出现的子目录。

## 5. 连续性契约

### 5.1 首次运行与 Space 种子

第一次 TaskRun 从 Space 共享文件的一份快照开始。Worker 会：

1. 认领这次 TaskRun；
2. 把选定的 Space 文件快照物化到一个空的 `workspace/` 中，并在工作区根目录下保留相对路径；
3. 捕获并发布一个 `seed` 检查点；
4. 把这个检查点记录为该 TaskRun 的基础；然后才
5. 启动 Agent 运行时。

物化出来的文件会成为一份私有的、可写的分支。Agent 的编辑绝不会隐式写回 Space。之后 Space 一侧的上传、替换和删除都不会改变已经存在的 Task：Continue 恢复的是它自己 Task 的工作区检查点，而不是重新导入一遍最新的共享文件。刷新或者写回操作，应当是未来某个明确的产品动作，并且要有自己的冲突处理和授权语义。

这份种子就是第一次运行实际看到的那份确切目录。如果来源方能够提供一个身份标识，检查点就会记录那份来源 Space 快照的身份；否则,它会记录物化后的文件清单及其摘要。一次与旧的非事务性物化过程竞争的上传，仍然可能混入不同的 Space 写入,但已提交的种子会在 Agent 造成任何外部副作用之前，把那份确切的副本冻结并标识下来。

如果这份种子无法提交，Agent 就不会启动。这次运行会在模型或工具执行之前就失败,因为它根本没有一个可复现的基础。

### 5.2 Continue

Continue 在创建新 TaskRun 时,会同时固定两个前序引用：

- `previous_task_run_id` 提供 Agent 会话；
- `workspace_base_checkpoint_id` 提供 Task 工作区。

两项恢复操作都必须在 Agent 启动之前完成，并且两个结果都会被记录下来。检查点缺失、损坏、未获授权或不受支持时，这次运行会直接失败关闭；会话捆绑包缺失或损坏时同样如此。表面上呈现为 Continue，实际上却从一个全新会话或当前 Space 文件开始,是不被允许的。

未来一个明确的恢复动作,或许可以允许用户从最近一次持久化的工作区头部继续，而不依赖紧邻的前一次会话；反过来也一样。但那应当是一个全新的用户决定，绝不能作为一种隐式的回退行为。

### 5.3 Retry

Retry 重复的是一次执行尝试，因此它的工作区基础,就是它所指定的那次 TaskRun 的基础：

```text
run A: base C1 ---- execution ---- partial or result C2
retry A: base C1 -- new execution -- result C3
```

即便 C2 是可用的，Retry 也不会从 C2 开始。那次失败的尝试可能把某个仓库停留在迁移过程的中途,可能在一份旧清单旁边留下了一个生成出来的文件,也可能造成了某种无法从文件本身推断出来的外部副作用。如果复用它的部分状态，就会把 Retry 变成 Resume。

Retry 仍然按照既有的重试规则来恢复 Task 的会话。Retry 上记录的会话、工作区和 Plugin 环境引用，必须如实描述这次实际提供的组合；界面绝不能暗示 Retry 会重建那些外部副作用。

### 5.4 Plugin 环境的连续性

`buildmax-home/plugins/` 只是一份物化出来的投影，从来都不是一个检查点。真正持久化的对象是一个 **Plugin 环境版本**：由 `plugin_id`、版本号、包摘要、包引用、来源、安装器、声明的作用范围，以及已解析的权限版本组成的一组不可变的有序集合。

Agent 可以使用带类型的 `PluginSearch`、`PluginInspect` 和 `PluginInstall` 能力。它不能通过用 Bash 写入 `buildmax-home/plugins/` 的方式来完成一次持久化安装。目录中的一个包只需被引用,不必再次上传它的字节。一个私有的或由 Agent 生成的包,必须先经过规范化、检查、摘要校验，并存入 Plugin 包存储一次，之后一个环境版本才能引用它。展开后的目录、下载内容、缓存、凭证，以及未声明的 Plugin 状态,都不会被上传。

已经组装好的工具注册表、系统提示词、MCP server、Hook、沙箱规则,以及 Secret 需求，在一次 TaskRun 内部保持不变。因此，安装一个 Plugin 就会形成一条"能力发生变化"的边界：worker 会先让当前运行静默下来，提交当前的会话和工作区，记录下新的 Plugin 环境，再创建一个新的 TaskRun 去物化这个新环境，然后才继续同一个 Task。产品界面可以把这一切呈现为自动的无缝延续，但执行记录本身必须保留这条边界。

自主安装默认是 `task` 作用范围，并且依然需要 Space 允许自主获取；普通的 Task 执行权限并不意味着拥有 Plugin 管理权限。要把范围提升到某个 Agent 或整个 Space,需要一个明确、经过授权的动作。那些引入了可执行工具、MCP server、Hook、更广泛的文件系统或网络访问权限，或者需要 Secret 的 Plugin，都必须经过相应的策略和审批关卡；安装一个包本身，绝不会隐式地授予任何 Secret。

Continue 使用的是 Task 当前的 Plugin 环境头部。Retry 使用的是它所重试的那次 TaskRun 的基础 Plugin 环境。一次失败或被中断的安装，可能会留下一个未被引用、等待垃圾回收的包，但不会推进 Task 的 Plugin 环境头部。

### 5.5 成功完成

在 Agent 循环以及它拥有的每一个子进程都已停止之后,worker 会捕获 `workspace/`、上传这份载荷、对其进行校验，然后请求 server 提交一个 `successful` 的结果检查点。

这份成功检查点的描述符,会随着 TaskRun 的终态上报一起送达。server 会在接受这份上报的同一个事务里，记录下这个检查点，并推进 `task.workspace_head_checkpoint_id`。一份过期或重复的终态上报，可以幂等地返回成功，但它无法改变第一份被接受的上报所选定的那个头部。

TaskRun 的状态和工作区的持久化是两个相关但彼此独立的事实。如果 Agent 已经产出了一个成功的答案，但最终的检查点发布失败了，这次运行仍然会保持 `SUCCEEDED`，并记录下 `workspace_checkpoint_status=failed`。它的最终回复,以及任何被独立发布出去的 Artifact,都依然有效。此时 Task 的工作区头部不会前进，直到用户明确选择一个恢复基础，或者这个检查点被修复之前，Continue 都会被拒绝。如果把整次运行标记为失败，就会诱导出一次 Retry——而它可能仅仅因为执行结束后的一次存储失败，就重复一遍那些外部副作用。

### 5.6 失败、取消与中断

对于一次执行失败、用户取消，或一次优雅的进程中断，worker 可以在与终态上报共用的、同样有时限的上报窗口内,发布一个 `partial` 检查点。

一个部分检查点：

- 与它所属的 TaskRun 相关联；
- 从不会自动推进 Task 的工作区头部；
- 不会被 Retry 使用；
- 会被保留下来，用于诊断，以及未来可能出现的一次明确的 Resume 动作；并且
- 在上报的时限太短时，可能根本不存在。

这次 TaskRun 的终态始终是权威的。检查点方面的失败，不能抹去或者改写一个已经由执行过程本身确定下来的终态结果。

### 5.7 Worker 硬性丢失

`SIGKILL`、OOM kill、节点丢失、强制删除 Pod，以及一个已经死掉的节点，都不会给系统留下任何清理的机会。存活探测的回收器会像今天一样关闭这次 TaskRun。最后一次已提交的 Task 头部，以及这次运行不可变的基础，仍然是可以恢复的；但那个丢失进程里未提交的工作,则无法恢复。

BuildMax 不会悄悄地把同一个 TaskRun 再次派发出去。模型选择调用的工具,可能已经在工作区之外写入了内容、调用了某个 API、推送了一个分支，或者打开了一个 pull request。只有一次明确的 Retry，或者未来的 Resume，才会创建一次新的执行尝试。

## 6. TaskRun 生命周期

目标生命周期是：

```text
PENDING
   |
   v
SCHEDULED
   |
   | atomic worker claim
   v
RUNNING
   |
   | restore or create workspace and session bases
   | materialize the immutable Plugin environment
   | record restore outcome
   | no model/tool call before this gate
   v
EXECUTING (logical phase; not a new public TaskRun status)
   |
   | quiesce Agent and owned children
   | capture and upload result/partial checkpoint
   v
terminal TaskRun status + workspace/session/Plugin environment outcomes
```

这里不需要新增任何面向公众的 TaskRun 执行状态。工作区准备、检查点操作，以及 Plugin 环境物化，都是记录在专门列里的从属状态。如果把 `PREPARING` 或 `CHECKPOINTING` 加进 TaskRun 状态的词汇表里，会迫使每一个消费这个状态的地方都得去理解存储层面的实现细节，而且依然无法正确表达"成功但检查点失败"这种情况。

worker 的心跳会在原子性的 RUNNING 认领之后开始，并在物化、执行和检查点上传期间持续。因此，存活探测回收器能够在任何一个阶段检测出一个已经丢失的 worker。耗时较长的对象存储操作绝不能表现得像是陷入了静默。

在捕获之前,运行时必须先完成静默（quiesce）：

- 不再启动任何新的工具调用；
- 前台的工具调用已经返回，或者已被取消；
- 运行时拥有的子进程已经退出，或者已被杀死；并且
- 会话日志在被单独上传之前，已经被关闭。

一个刻意脱离运行时所有权、被单独守护化（daemonized）出去的进程，是一种不被支持的工作区变更来源。在一个未被追踪的写入者仍然活跃的情况下对一棵文件树做检查点，无法得到一个一致的边界。

## 7. 存储与归档格式

### 7.1 载荷布局

第一版的载荷格式是 `tar.zst.v1`：每个检查点对应一份经 Zstandard 压缩的 tar 归档。存储键在所属 Space 内部是按内容寻址的：

```text
<prefix>/<space_id>/workspace/blobs/sha256/<64-lowercase-hex>
```

这份摘要覆盖的是压缩后的确切字节。一行检查点记录会记下载荷格式、摘要、存储大小、未压缩的普通文件字节数,以及条目数。对象存储适配器负责推导出这个键；没有任何 API 或轨迹会把它暴露出来。

以 Space 为范围的内容寻址,允许在一个授权边界内部安全地复用内容，同时不会泄露另一个 Space 是否存储过相同的内容。第一版实现可以使用 `ObjectExists` 来避免重复上传，但它仍然必须针对记录下来的摘要,去校验取回的载荷。

之所以在按文件内容寻址的清单方案之前先选择单一归档方案，是因为源码树里往往包含大量的小文件。一份归档只需要一次流式的 GET，避免了一次 LIST 加上成千上万次请求往返。格式这一列,也为将来某种分块或基于清单的表示形式留下了空间，而不必改动检查点的领域模型本身。

### 7.2 规范归档规则

创建归档时,会按字典序、以斜杠分隔的顺序遍历路径。每个文件头使用的都是相对于 `workspace/` 的路径。这份实现会保留：

- 普通文件的字节内容；
- 目录；
- 可执行和普通的权限位；
- 修改时间；以及
- 安全的相对符号链接。

它不会保留所有者、用户组、ACL、扩展属性、稀疏文件布局、设备节点、套接字,或 FIFO。UID 和 GID 会被统一归零，名称留空。Setuid、setgid 和 sticky 位都会被剥离。

绝对路径、`..` 路径穿越、重复的规范化路径、硬链接、设备节点、套接字、FIFO、绝对符号链接，以及逃出归档根目录的相对符号链接，都会让捕获过程直接失败。解压时会独立地重新执行同样的校验；仅仅因为一份归档是 BuildMax 自己生成的就信任它，会把一次对象存储层面的数据损坏,变成一次文件系统层面的逃逸。

第一版里没有任何隐式的忽略规则。`.git`、生成出来的文件，以及 `workspace/` 内部的缓存,都是检查点的一部分——因为悄悄地排除它们，会让"这就是精确的工作区"这句话变成假话。运营方应当去限定可接受的体积大小,而不是去排除内容。将来也许会设计一套明确的排除策略，但它排除了哪些路径、会带来什么样的恢复后果,必须在 TaskRun 上清晰可见。

### 7.3 物化

恢复过程会把归档流式写入目标文件系统上的一个新的临时目录，校验每一个条目以及各项汇总限制,校验载荷的摘要，然后才把这个临时目录改名放到正式位置上。Agent 永远不会看到一个只解压了一半的工作区。

Worker 不会通过对象存储的列表操作来发现某个检查点。它是从 server 那里收到一个不可变的描述符，然后执行一次直接的 GET。因此,LIST 操作的一致性问题,以及无关对象，都不会影响到恢复过程。

### 7.4 为什么这份归档不是一个 Artifact

一个检查点是自动产生的执行状态,里面可能包含源码、缓存,或者私有的中间文件。而一个 Artifact，是一次带有稳定、面向用户身份的、有意的发布行为。如果自动把检查点归档注册成 Artifact，就会违反 `unified-artifacts.md` 中"必须经过明确发布"这条决定，还会把一种实现层面的格式,当成产品内容暴露出去。

## 8. 提交协议与一致性

MySQL 和对象存储无法参与同一个事务。因此，发布过程采用的是**先写入不可变字节，再更新权威指针**的顺序：

1. 把归档捕获到一个有大小限制的本地临时文件里，同时计算它的 SHA-256 和各项计数；
2. 把它上传到按内容寻址得到的键上，或者确认相同的字节已经存在；
3. 按需读取元数据，或者流式读取这个对象，以校验这个键确实准确无误；
4. 通过它的准备调用发送一个种子描述符，或者在 TaskRun 的终态上报里携带一个结果或部分检查点描述符——这一切都通过经运行令牌认证的 worker API 发送；
5. 校验 Space、Task、TaskRun、检查点类型、摘要、格式和各项边界；
6. 在同一个 MySQL 事务里插入这个检查点，并更新 TaskRun 以及可能存在的 Task 头部；对于一个结果或部分检查点来说，这正是接受终态运行结果的同一个事务；并且
7. 把已提交的检查点身份返回给 worker。

这个最终确认调用是幂等的。用同样的 TaskRun、检查点类型、摘要和元数据重复调用，会返回已有的那个检查点。用同一种类型、不同的字节重复调用，则是一种冲突；它绝不会改写已经被接受的检查点。

只有第一次有效的终态迁移，才能推进 Task 头部。这次更新会检查 TaskRun 预期的状态、Task 当前活跃的运行，以及那次运行上记录的基础检查点。这样可以防止一个迟到的 worker、一个重复的 Pod，或者一次被重试的 HTTP 请求，把头部移动到一次更晚运行的后面或者绕开它。

一份已经上传、却没有对应已提交检查点行的载荷，是一个孤儿,而不是一个检查点。保留清扫任务可以删除那些超过一段保守宽限期、且不再被引用的对象。这项清扫必须从数据库引用中判断某个对象是否还"活着"，并且必须能容忍一次正在并发完成的上传；足够新的对象永远不会成为候选对象。

一行数据库记录绝不会指向一份尚未被校验过的字节内容。如果数据库提交在上传之后失败了，旧的 Task 头部依然是权威的。如果响应在提交之后丢失了，幂等的最终确认调用会返回同一行记录。

AWS S3 为单个键提供原子更新和强一致的"写后读"保证，但 BuildMax 同时也支持 S3 兼容的存储。这套协议使用的是不可变的键加上显式的校验，而不是把 AWS 的行为当作每一个兼容后端都必须满足、却又没有写进文档的隐性要求。

## 9. 关系模型

### 9.1 `workspace_checkpoint`

`workspace_checkpoint` 是一个 server 端实体，因为一次恢复选择,可能需要在 API 边界上指名道姓地引用它。它从 `util.NewPublicID` 获得一个不透明的公开句柄；内部的关联关系则使用数字键。

目标行结构：

| 列 | 类型 | 可空 | 备注 |
|---|---|---:|---|
| `id` | `bigint unsigned` | 否 | 内部主键 |
| `public_id` | `char(20) ascii_bin` | 否 | 唯一的公开句柄 |
| `space_id` | `bigint unsigned` | 否 | 授权归属方，已建索引 |
| `task_id` | `bigint unsigned` | 否 | 工作区归属方,按创建顺序建索引 |
| `source_task_run_id` | `bigint unsigned` | 否 | 捕获出这个检查点的那次运行 |
| `base_checkpoint_id` | `bigint unsigned` | 是 | 谱系上的前序检查点 |
| `kind` | `varchar(32)` | 否 | `seed`、`successful` 或 `partial` |
| `payload_format` | `varchar(32)` | 否 | 初期为 `tar.zst.v1` |
| `payload_sha256` | `char(64) ascii_bin` | 否 | 已存储字节的摘要 |
| `storage_key` | `varchar(1024)` | 否 | 私有的、后端相关的键，从不被序列化输出 |
| `size_bytes` | `bigint` | 否 | 已存储的载荷字节数 |
| `uncompressed_bytes` | `bigint` | 否 | 各普通文件大小之和 |
| `entry_count` | `bigint` | 否 | 普通文件、目录和符号链接的数量 |
| `created_at` | `datetime(6)` | 否 | UTC 提交时间 |

唯一性约束是 `(source_task_run_id, kind)`。一次 TaskRun 至多有一个种子、一个成功结果，以及一个部分检查点。`payload_sha256` 并不是全局唯一的，因为不同的检查点行可以有意地指向同一份不可变载荷，同时各自保留独立的来源记录。

`storage_key` 遵循和 Artifact 存储键一样的规则：它属于基础设施层面的数据,不会出现在领域 JSON、worker 可见的 TaskRun 响应、日志或轨迹里。

### 9.2 `task`

新增一个可为空的 `workspace_head_checkpoint_id`。它指向被接受为这个 Task 可恢复状态的最新检查点：可能是它最初的种子，也可能是之后某次成功的结果。它是一个投影字段，会在检查点最终确认的同一个事务里更新——如果是一次结果检查点，则连同 TaskRun 的终态迁移一起更新。

对于一个还没有提交过种子或成功结果的 Task，这个指针可以为空。一个种子可以在第一次执行之前就成为头部，这样即便发生一次硬性丢失，依然会留下一个确定性的重试基础。

新增一个可为空的 `plugin_environment_head_id`。它指向供下一次 Continue 使用的那个不可变 Plugin 环境版本。一个没有发生过自主安装的 Task，可以继续从 Agent 的版本和 Space 的激活状态里推导出它的环境。超出 Task 范围的提升,要经过对应的 Agent 或 Space 服务，而不是直接改动这个 Task 指针。

### 9.3 `task_run`

新增：

| 列 | 含义 |
|---|---|
| `workspace_base_checkpoint_id` | 执行之前选定的不可变基础 |
| `workspace_result_checkpoint_id` | 提交时的成功结果检查点 |
| `workspace_partial_checkpoint_id` | 提交时的部分检查点 |
| `workspace_restore_status` | `not_requested`、`pending`、`restored` 或 `failed` |
| `workspace_restore_error` | 面向运营方、经过边界限制的原因说明 |
| `workspace_checkpoint_status` | `not_requested`、`pending`、`committed` 或 `failed` |
| `workspace_checkpoint_error` | 面向运营方、经过边界限制的原因说明 |
| `plugin_environment_base_id` | 为执行而物化出的不可变 Plugin 集合 |
| `plugin_environment_result_id` | 提交时,这次运行请求的新 Plugin 集合 |
| `plugin_environment_status` | `unchanged`、`pending`、`committed` 或 `failed` |
| `plugin_environment_error` | 经过边界限制的安装或物化原因说明 |

这些状态字段之所以要单独存储，是因为仅凭一个缺失的指针,无法区分"从未请求过"和"尝试过但失败了"这两种情况。错误信息是用于诊断、经过边界限制的文本，而不是包含了端点或凭证的原始供应商响应。

会话恢复,在同一次所有权变更里,会得到对等的记录结果。一次 TaskRun 的详情必须能够直接回答：工作区、会话和 Plugin 环境是否都按承诺提供了,而不需要从日志里重新拼凑出这个答案。

### 9.4 状态规则

`internal/core/task` 拥有以下规则：

- 一个工作区基础,在执行开始前就会变得不可变；
- Continue 选择的是由它的前序运行固定下来的那个 Task 头部；
- Retry 选择的是它所指定的那次运行的基础；
- 一个种子会建立起 Task 的第一个头部，此后只有一次成功的结果,才能自动推进一个已存在的头部；
- 一个 Plugin 环境的基础,在一次 TaskRun 内部是不可变的；
- Continue 使用的是 Task 的 Plugin 环境头部，而 Retry 复用的是它所指定的那次运行的基础环境；
- 部分检查点从不会隐式地成为工作区头部；并且
- 一个检查点只能属于它的来源 TaskRun 所归属的那个 Space 和 Task。

数据库存储层会原子性地执行这些状态迁移，但不会重新定义它们。Handler、worker 和调度器都要委托给同一个所有者来做决定。

## 10. 包与接口边界

这项能力的落地不会颠倒本仓库既有的依赖方向：

| 区域 | 职责 |
|---|---|
| `internal/core/task` | 检查点类型、恢复/检查点结果取值，以及 Task/TaskRun 的状态迁移规则 |
| `internal/service/task` | 选择 Continue 和 Retry 的基础；暴露恢复相关的选择 |
| `internal/service/workspace` | 校验并最终确认检查点元数据；提供保留策略所需的引用查询 |
| `internal/service/plugin` | 校验自主获取；创建不可变的 Plugin 环境版本；对提升范围进行授权 |
| `internal/agentapp/taskrun` | 物化、捕获、静默,并调用 worker 客户端；不做任何授权决策 |
| `internal/infra/objectstore` | 流式传输归档载荷、推导私有的键、校验摘要，并实现本地/S3 存储 |
| `internal/infra/db` | 行结构，以及检查点/TaskRun/Task 的原子更新 |
| `internal/infra/workerclient` | 经运行令牌认证的检查点准备/最终确认 DTO |
| `internal/server/handlers/worker` | 认证并转发 worker 端的检查点调用 |
| `internal/infra/k8s` | 临时卷和 ephemeral-storage 资源的边界设置 |

`internal/service/workspace` 之所以有理由作为一个独立边界存在，仅仅是因为它拥有本文所描述的这种跨存储提交和保留能力。单纯的归档编码,依然属于基础设施层面，绝不能因此创建出一个通用的"工作区管理器"包。

建议由消费方各自拥有的接口：

```go
type CheckpointPayloadStore interface {
    Put(ctx context.Context, spaceID, sha256 string, src io.Reader) (storageKey string, err error)
    Open(ctx context.Context, storageKey string) (io.ReadCloser, int64, error)
    Exists(ctx context.Context, spaceID, sha256 string) (bool, error)
    Delete(ctx context.Context, storageKey string) error
}

type CheckpointFinalizer interface {
    RecordBase(ctx context.Context, in RecordBaseInput) (*task.WorkspaceCheckpoint, error)
    FinalizeResult(ctx context.Context, in FinalizeResultInput) (*task.WorkspaceCheckpoint, error)
}
```

确切的接口应当放在各自消费方的附近，并且可以和这份草图有所不同。没有必要仅仅因为每一种实现最终都会调用 S3，就把它们和现有的 Home、Run、Artifact、Plugin 包，或者会话存储合并到一起。

## 11. Kubernetes 运行时与存储方案

### 11.1 默认方案：对象检查点 + `emptyDir`

默认的 worker Job 会为 `workspace/`、`buildmax-home/` 和隐藏的临时空间挂载 `emptyDir`。它会在执行之前恢复工作区检查点、物化 Plugin 环境，然后在执行结束时通过应用层协议发布下一个工作区检查点。

这套方案保留了 Pod 自由调度的能力，能够跨节点、跨集群工作，用的是生产拓扑本来就需要的对象存储，也没有任何按 Task 划分的 PVC 生命周期需要管理。它的代价是每次运行要下载一次归档，而当工作区发生变化时，还要在边界处上传一次归档。

`k8s_job` 和 `local_process` 这两种 runner 使用的是完全相同的检查点语义。本地文件系统的实现,存储的是同样的归档和元数据契约，不会假装 worker 自己的目录本身就是那份持久化记录。

### 11.2 未来可选方案：持久化缓存

如果有证据表明工作区规模确实很大，可能值得引入一个 `persistent_cache` 方案。它可以为每个 Task 挂载一个 CSI 卷，把它当作物化缓存或者活跃的工作磁盘来用。对象存储里的检查点依然是权威的，仍然会在 TaskRun 的各个边界上被提交。

当严格的单 Pod 挂载很关键的时候，应该用的访问模式是 `ReadWriteOncePod`，而不是 `ReadWriteOnce`：RWO 只是把挂载限制在一个节点上，那个节点上仍然可以有多个 Pod 挂载它;而 RWOP 需要 CSI 支持，在现代 Kubernetes 里已经是稳定特性。

这套缓存方案在使用之前,必须先校验挂载的状态是否和 Task 的检查点摘要一致。一份陈旧、缺失或者来路不明的缓存,会被丢弃并重建；它绝不会去移动数据库里的头部。

### 11.3 暂不提供的方案

- 对于这套线性的 Task 契约来说,RWX 是不必要的,因为它最多只允许一次活跃的 TaskRun。引入 RWX 只会带来一个共享文件系统的依赖，却没有并发写入者这种真实场景。
- 本地 PV 和 `hostPath` 至多只能算是缓存。节点丢失不能变成一种"权威 Task 状态可以承受"的损失方式。
- JuiceFS、CephFS、NFS 和云 NAS，都可以用来实现某个运营方自己的持久化缓存或对象存储层，但 BuildMax 不会把这些具体产品编码进自己的领域模型里。
- 对象存储的 FUSE 挂载,不是默认的工作区文件系统。一棵本地的 POSIX 文件树,配合显式的检查点，能给出更清晰的写入、重命名和失败语义。

### 11.4 Sidecar 与生命周期钩子

将来一个 sidecar 也许可以提供压缩或者上传加速功能，但它不能拥有正确性方面的所有权。`PreStop` 只会在容器仍然存活、处于受管终止的情况下运行，共享的是 Pod 的终止宽限期，在进程或节点发生硬性丢失之后无法运行。

真正拥有静默和检查点最终确认所有权的，是 TaskRun 进程本身。SIGTERM 时的上报只是相对于"从最后一次已提交的检查点恢复"的一种优化手段，而不是另一个可信来源。

## 12. 安全、限额与保留

### 12.1 文件系统安全

捕获和恢复过程绝不会跟随任何跳出 `workspace/` 之外的路径。解压器使用受控的 API 来创建文件，而不是调用系统自带的 `tar` 二进制文件。它会拒绝不支持的条目类型，并剥离带有特权含义的权限位。

归档只包含 `workspace/`。`buildmax-home/`、展开后的 Plugin 目录树、操作系统 home、归档暂存区、凭证、日志、轨迹、缓存，以及其他运行时临时空间,都在它之外。这里也没有任何 Artifact 或输出目录需要排除。

Space 文件上传不是一种隐式的运行时配置授权。像 `AGENTS.md` 和 `.buildmax/` 这类带有控制含义的路径，要么被排除在普通的文件上传界面之外，要么只能通过一项明确的 Space 配置权限,并伴随一条审计事件,才能写入。一个共享文件的贡献者，绝不能仅仅因为选择了某个文件名，就获得提示词、Hook、MCP 或 Plugin 方面的权力。

一条环境 Secret 授权,仍然可能被一个模型选择执行的命令,有意地复制进 `workspace/`。Space 本来就已经授权 Agent 读取这些值,所以做检查点本身不会带来新的机密性边界问题，但它确实延长了这些值的保留时间。在正式发布之前，威胁模型必须定下来：在常规工作区文件里发现了确切的被授权 Secret 值时，应当告警、拒绝检查点，还是给出一份经过脱敏的诊断信息。悄悄删除是不允许的，那会破坏工作区的完整性。

### 12.2 对象存储权限

Worker 在 HTTP 边界上只会拿到运行令牌，但当前的生产存储路径,也可能同时让 Pod 的工作负载身份获得对存储桶的访问权限。检查点的键始终留在这次运行所属的 Space 命名空间内部，server 会在提交之前推导或校验每一个存储引用。

长远来看，最小权限方面的改进方向,是一种按运行范围的上传/下载租约或者预签名请求，而不是通过 worker API 暴露任意的存储桶键。本文档并不宣称这项改进已经落地。

### 12.3 资源限制

worker Job 必须同时获得：

- 容器级别的 `ephemeral-storage` 请求量和限额；以及
- 针对 workspace、运行时 home 和 `/tmp` 这几个卷的 `emptyDir.sizeLimit`。

Pod 的存储准入限额,要涵盖物化后的工作区、展开后的 Plugin 包、临时的压缩载荷、日志，以及普通工具产生的临时空间。而检查点自身的限额，只涵盖 `workspace/` 这一部分。检查点捕获过程,应当在耗尽 Pod 存储限额之前就主动停止，并记录一个有边界的失败，而不是坐等 kubelet 发起驱逐。

检查点的限额至少应当包括：

- 已存储的字节数；
- 未压缩的普通文件字节数；
- 条目数量；
- 最大路径长度；
- 单个文件的最大体积；以及
- 解压膨胀比。

本文档不会去选定这些默认值。它们必须来自针对具有代表性的源码、构建产物和数据类工作区所做的基准测试证据，并在实现时记录进配置参考文档里。

### 12.4 保留

成功的检查点遵循 Task 的保留策略。只要还有一次 TaskRun 或者更晚的一个检查点引用着某个种子检查点，它就会被保留下来。部分检查点可以有一个由运营方配置的、更短的保留期，但只要有一个可见的恢复动作还在引用它，它就绝不会被删除。

按内容寻址的对象,只有在没有任何检查点行引用它对应的存储键、并且它的存在时间已经超过孤儿宽限期时，才会被删除。数据库和存储桶的备份/恢复,始终应当成对进行：只恢复其中一个而不恢复另一个，可能会留下有元数据却没有载荷,或者有载荷却没有元数据的情况。

检查点占用的字节,计入一个独立的工作区状态配额。它们不算作 Artifact 字节，也不会出现在 Artifact 的配额或列表里。

## 13. 失败与恢复矩阵

| 失败点 | 持久化的观测结果 | 自动行为 | 恢复基础 |
|---|---|---|---|
| worker 认领之前 | 运行保持在 `SCHEDULED`，直到既有的派发处理逻辑解决它 | Kubernetes 可能在认领之前重试启动 | 无需任何操作 |
| Space 文件快照物化失败 | 恢复状态为 `failed`；没有任何模型/工具调用 | 运行直接失败关闭 | 尚不存在 Task 工作区 |
| 种子上传或提交失败 | 检查点状态为 `failed`；没有任何模型/工具调用 | 运行直接失败关闭 | 无，因为执行从未真正开始 |
| Continue 的工作区恢复失败 | 恢复状态与一条有边界的错误信息 | 运行直接失败关闭 | 需要一次明确的修复或恢复选择 |
| Continue 的会话恢复失败 | 会话恢复状态与一条有边界的错误信息 | 运行直接失败关闭 | 需要一次明确的修复或恢复选择 |
| Plugin 环境物化失败 | Plugin 环境状态与一条有边界的错误信息 | 运行直接失败关闭 | 记录下来的基础环境 |
| 自主 Plugin 安装失败 | 安装状态与一条有边界的错误信息 | 当前运行保持它原有的不可变基础；不切换能力 | 记录下来的基础环境 |
| Agent/工具执行失败 | 正常的 FAILED 结果；尝试进行部分捕获 | 不会自动重试 | 记录下来的基础 |
| 用户取消 | CANCELED 结果；尝试进行部分捕获 | 不会自动重试 | 记录下来的基础；部分检查点只能靠未来明确的 Resume 使用 |
| SIGTERM 或驱逐 | FAILED/中断结果；尝试进行有边界的部分捕获 | 上报之后进程退出 | 记录下来的基础，如果已提交则再加上部分检查点 |
| SIGKILL/OOM/节点丢失 | 存活探测回收器记录下丢失的 worker | 不会自动重新派发 | 记录下来的基础,或者此前的 Task 头部 |
| 结果载荷上传失败 | 运行结果仍会正常上报；检查点状态为 `failed` | Task 头部不会推进 | 此前的 Task 头部 |
| 上传成功，数据库提交失败 | 旧头部依然有效；该载荷成为一个孤儿 | 幂等重试可以最终提交它 | 此前的 Task 头部，直到提交为止 |
| 数据库已提交，响应丢失 | 检查点和头部都已经持久化 | 幂等重试会返回同一行记录 | 刚刚提交的这个检查点 |
| 对象事后消失或损坏 | 恢复校验会明确失败 | 没有任何回退方案 | 由运营方恢复存储桶，或者选择另一个基础 |
| 数据库已恢复但存储桶没有恢复 | 缺失的载荷会被明确观察到 | 没有任何回退方案 | 需要成对进行的备份恢复 |

第一版实现的恢复目标是刻意收窄的：

| 事件 | RPO | RTO 的决定因素 |
|---|---|---|
| 成功的终态运行 | 最后一次已提交的检查点 | 归档下载与解压所需时间 |
| 优雅的取消/中断 | 若能赶上上报的时限,则为部分检查点；否则为记录下来的基础 | 对象存储的可用性与归档大小 |
| Worker 或节点的硬性丢失 | 最后一次已提交的基础/头部；当前所有未提交的文件系统改动都可能丢失 | 存活探测的宽限期,加上新一次运行的调度和恢复耗时 |

在这套实现针对所支持的部署方案完成基准测试之前，不会承诺任何具体的数字化 RTO。Portal 会展示实测的捕获和恢复耗时，让运营方能够基于证据设定自己的目标。

## 14. API、Portal 与可观测性

### 14.1 Worker API

确切的路由属于注册阶段的实现细节，但 worker 需要三种带类型的操作：

1. 获取为这次运行选定的不可变基础描述符；
2. 记录基础恢复的成功或失败；以及
3. 记录一个种子检查点，或者在 TaskRun 的终态上报里携带一个成功/部分检查点描述符。

这一切都需要运行令牌。基础的获取操作在运行处于 `RUNNING`、正在准备阶段时是被允许的。最终确认操作只对同一次运行、且只对一种合法的检查点类型才被允许。server 会从令牌所对应的 TaskRun 里推导出 Space 和 Task；worker 从来不会自己提供任何带有权限效力的归属方 ID。

体积较大的载荷字节,依然直接流向对象存储。server 接收并校验的是元数据,而不是通过自己的 HTTP 进程去代理一份好几个 GB 的归档。

### 14.2 Task 与 TaskRun API

Task 详情暴露的是它当前工作区头部的公开身份和摘要,而不是一个存储键。TaskRun 详情则会暴露：

- 存在时,基础、成功结果和部分检查点各自的身份；
- 会话、工作区和 Plugin 环境的恢复结果；
- 检查点发布的结果；
- 存储大小、未压缩大小,以及条目数量；
- 捕获与恢复各自耗时；以及
- 当任一操作失败时的一条有边界的错误信息。

第一版实现不会新增一个通用的检查点列表或下载路由。那样做会把内部的连续性状态变成一份面向用户的版本历史,需要另一次独立的产品决策才能引入。

### 14.3 Portal

Task 页面会在每次运行旁边展示一个简明的工作区状态：

- **已恢复** ——基础身份和恢复耗时；
- **已保存** ——结果检查点和大小；
- **部分状态已保存** ——仅出现在失败/取消的情况下，不会被自动使用；
- **工作区未保存** ——一条可见的警告,配上最后一个持久化的头部；或者
- **恢复失败** ——这次运行没有真正执行。

只有在一个明确的恢复动作被设计并获得授权之后，Continue 才会在会话、工作区或 Plugin 环境无法恢复时提供这个动作；它绝不会悄悄地用当前的 Space 文件或者一个不同的 Plugin 环境去替代原有的东西。

### 14.4 轨迹与指标

轨迹记录的是有边界的元数据事件，从不记录归档内容或私有的存储键：

- `workspace.restore.started/completed/failed`；
- `workspace.checkpoint.started/completed/failed`；
- `plugin.environment.materialize.started/completed/failed` 以及 `plugin.install.requested/committed/failed`；
- 检查点类型、提交之后的公开 ID、大小、条目数量、摘要前缀、耗时,以及来源运行；以及
- 是否因为上报时限已到而跳过了捕获。

指标包括捕获/恢复延迟、压缩前后的字节数、压缩比、按有边界的类别划分的失败情况、孤儿数量,以及在未来存在持久化缓存方案时的缓存命中率。

## 15. 交付计划

### 阶段 0——接受这份契约

- 修订产品愿景文档，说明通用的版本化工作区依然缺席，而 Task 工作区连续性已被明确纳入计划。
- 修订 Agent 执行连续性文档，说明 Continue 会把会话和工作区绑定到同一个前序对象上。
- 把本文档加入设计索引，并在开始实现之前为它赋予一个路线图优先级。
- 修订 Plugin 分发文档，说明一个展开后的运行目录只是一个不可变环境版本的投影，而不是它真正持久化的状态。

### 阶段 1——载荷与元数据基础设施

- 加入归档创建/解压逻辑,并配合对抗性路径和膨胀测试。
- 为本地文件系统和 S3 兼容存储,加入检查点载荷存储。
- 一次性在所有地方加入 `workspace_checkpoint` 以及 Task/TaskRun 相关字段：领域模型、数据库行、存储层、线上 DTO、数据模型文档,以及测试。
- 在不改变运行时行为的前提下，加入幂等的元数据最终确认逻辑。

### 阶段 2——确定性的基础

- 在 Agent 执行之前，捕获第一次运行的种子。
- 在 `internal/service/task` 中固定 Continue 和 Retry 的基础选择逻辑。
- 把工作区恢复、会话恢复,以及 Plugin 环境物化，合并成一道失败关闭的准备关卡。
- 记录这三项各自的结果，并在 TaskRun 详情上展示出来。

### 阶段 3——结果检查点与部分检查点

- 让运行时静默下来,并捕获成功的结果检查点。
- 让 Task 头部随着已被接受的终态上报,原子性地推进。
- 针对失败、取消和优雅中断，尝试捕获部分检查点，同时不改变它们各自的终态状态。
- 展示检查点方面的失败，而不掩盖结果或 Artifact 本身的成功。
- 加入带类型的 Plugin 搜索、检查和按 Task 范围的安装；一次已提交的安装,会在新能力真正加载之前，先创建一个新的 TaskRun 边界。

### 阶段 4——Kubernetes 与产品证据

- 加入 ephemeral-storage 的请求量/限额,以及 `emptyDir.sizeLimit`。
- 加入 Portal 的工作区状态展示，以及 Continue 的门控逻辑。
- 加入孤儿清理和保留清扫。
- 通过部署测试套件，演练正常延续、取消、SIGTERM、SIGKILL、拒绝对象存储、数据库歧义,以及成对恢复这些场景。

### 阶段 5——由证据驱动的加速优化

只有基准测试证据才能启动这个阶段。候选方向包括归档并行化、变更文件索引、分块的按内容寻址载荷，以及按 Task 划分的 RWOP 持久化缓存。无论最终哪种物理层优化胜出，领域模型本身始终保持基于检查点的设计。

## 16. 验证

### 16.1 单元测试与属性测试

- 归档的往返过程保留了每一项受支持的条目属性；
- 归档的创建和解压会拒绝路径穿越、绝对路径、不安全的链接、特殊文件、重复路径、超出限额的输入，以及解压炸弹；
- 摘要不匹配时，绝不会物化出一个可见的工作区；
- 一次被中断的解压过程,会让目标目录完全不存在，而不是只存在一部分；
- Continue 和 Retry 会选择各自指定的基础；
- Continue 和 Retry 会选择各自指定的 Plugin 环境；
- 写入一个展开后的 Plugin 目录不能创建出持久化的安装状态，包的字节只有在摘要校验通过之后才会被接受；
- 部分检查点从不会推进 Task 头部；并且
- 最终确认操作是幂等的，在元数据发生变化时会产生冲突。

### 16.2 MySQL 集成测试

`./make test mysql` 必须证明：

- 检查点的插入、TaskRun 的终态迁移，以及 Task 头部的更新会一起提交；
- 两个最终确认器针对同一次运行发生竞争时，只会产生一个检查点和一个头部；
- 一份迟到的上报,无法替换一次更晚运行的头部；
- 跨 Space 和跨 Task 的检查点引用会被拒绝；
- Continue 的准入逻辑不能选中一个缺失的或者来自其他 Task 的头部；并且
- 保留策略查询不会删除仍被引用的载荷。

### 16.3 对象存储集成测试

针对已提交的 MinIO 测试装置和 S3 适配器的仿真实现：

- 流式的上传/下载能够处理超出内存预算的大型归档；
- 精确键的校验不依赖 LIST 操作；
- 重复的按内容寻址上传是无害的；
- 上传成功但数据库失败,会产生一个可回收的孤儿对象；
- 恢复时能够检测出数据损坏和删除；并且
- 本地文件系统实现和 S3 实现遵循同一份契约。

### 16.4 运行时与部署证据

kind 测试套件必须证明：

1. 运行 1 编辑了 `workspace/`；运行 2 的 Continue 看到的是完全一致的字节；
2. Retry 从失败运行的基础开始，而不是它的部分状态；
3. 在上报时限允许的情况下，优雅取消和 SIGTERM 都能保留部分状态；
4. 强制删除 worker Pod 只会丢失未提交的状态，明确的 Retry 依然能从记录下来的基础成功恢复；
5. 拒绝对象存储的写入操作,不会悄悄推进 Task 头部；
6. 拒绝对象存储的读取操作,会阻止执行，而不是转而用 Space 文件来替代；
7. 一次按 Task 范围的自主 Plugin 安装,能在一次新的运行里带着固定的包继续下去，而 Retry 则会重建原始的 Plugin 基础；
8. 一个替代 Pod 无法去执行一次已经被认领过的运行；并且
9. `ephemeral-storage` 限额触发的失败是可预期的，并留下一次可诊断的运行记录。

在交接之前，运行相关的 `./make test`、`./make test mysql`、`./make check go`、`./make check docs`、`./make lint`，以及 `git diff --check` 这几个范围。部署层面的证据不能被单元测试取代。

### 16.5 当前的覆盖情况

上文各节描述的是预期的验证目标。目前已经实现的部分是：

- 16.1 的检查点单元测试与属性测试已经就位——归档往返与对抗性拒绝、摘要不匹配与中断恢复时的安全性、基础选择、部分检查点从不推进头部，以及幂等的最终确认。其中与 Plugin 环境相关的几条,属于下文另一项独立的 Plugin 工作，不属于本特性的范围。
- 16.2 中"被引用载荷"的保留策略查询，以及 16.3 中的对象存储契约、内容寻址,以及"上传成功但数据库提交失败会产生孤儿"这些行为，都被 MySQL 门控测试和对象存储测试覆盖到了。
- kind 测试套件演示了 16.4 中"正常延续"和"成对恢复"这两行：第一次运行播下种子，一次 Continue 恢复了它的基础，成功和失败的运行分别捕获了结果检查点和部分检查点——这一切由部署冒烟测试、Portal 的运行轨迹浏览器测试，以及直接的数据库断言所证明。

16.4 中带有破坏性的那几行,以及第 13 节失败矩阵里的内容——取消与 SIGTERM 场景下的部分捕获、强制 Pod 丢失、拒绝对象存储、数据库提交竞态——是由上述单元测试证明的，而不是由部署自动化证明的。每一项都是那些测试直接演练到的失败关闭或失败开放行为：恢复过程在字节缺失或不匹配时会拒绝执行,并记录一个失败结果；一个无法提交的结果或部分检查点,会让已被接受的运行结果保持原样、且不移动 Task 头部；而头部的推进本身是一次比较后设置（compare-and-set）操作，一份重复或迟到的上报永远无法让它越过这一步线性前进。把"拒绝对象存储、杀掉 Pod、提交竞态"这类场景注入共享的部署集群，只是在为已经被证明过的行为搭建一套脆弱的脚手架，所以这些行为被记录在这里,而不是写成自动化脚本；未来的某次改动,或许可以把其中唯一具有确定性、真正需要真实集群的那一行——"拒绝对象存储会让恢复过程可见地失败"——自动化起来，运行详情里的 `restore_status` 现在已经能让这一点变得可断言。

16.4 第 7 项里的"按 Task 范围的自主 Plugin 安装"，以及 Plugin 环境连续性相关的几条，属于另一项独立的 Plugin 分发工作，不属于工作区检查点这项特性,目前也尚未构建。

本特性范围内尚未构建的是：为"运行成功但检查点未能提交"这种情况,设置并呈现一条 `workspace_checkpoint_status=failed` 记录，以及读取这条记录的 Continue 门控逻辑。目前，这类失败是失败开放的——运行结果照常成立，头部不会推进——这一点可以从运行日志以及头部原地不动这一事实中看出来；Portal 目前只是以只读的方式展示已提交和已恢复的状态。

## 17. 被否决的替代方案

### 17.1 默认给每个 Task 分配一个 PVC

一个 PVC 能在 Pod 被删除之后保留文件系统状态，但这会让每一个 Task 都拥有一个 Kubernetes 存储对象，以及随之而来的容量决策、垃圾回收、备份、拓扑关系、挂载延迟和 CSI 可用性问题。它本身也无法提供跨集群的恢复能力。对于一个需要保持可移植性的默认方案来说，这个做法和具体部署环境绑得太紧了，不过它仍然可以作为一种可选的缓存方案存在。

### 17.2 一个 RWX 的 Space 工作区

不同的 Task 会变成对同一份可变共享状态的并发写入者。线性的、单一写入者这条不变式,是按 Task 而不是按 Space 定义的，而 RWX 本身并不提供应用层面的冲突处理或者来源语义。这个选项解决了挂载问题，却让所有权关系变得不再正确。

### 17.3 用本地 PV 或 `hostPath` 做节点亲和性绑定

这种做法通过让节点丢失变得不可恢复来优化正常路径的性能。调度、维护和容量压力,都会变成正确性方面的隐患。本地磁盘也许可以缓存一份已校验的检查点，但不能成为它的权威来源。

### 17.4 把分布式文件系统当作必需的平台组件

JuiceFS、CephFS、NFS 和云 NAS,在大规模场景下都可能很有用，但要求必须使用其中之一,会在 BuildMax 还没有真正的工作负载证据要求它之前，就引入一个额外的运维控制平面，并削弱私有化部署的可移植性。

### 17.5 用 InitContainer 下载加 Sidecar 上传来充当协议

一个 InitContainer 可以物化字节内容，一个 sidecar 可以传输它们,但两者都不拥有 TaskRun 授权、静默、谱系、终态,或者 MySQL 指针方面的所有权。生命周期钩子在发生硬性丢失之后是无法运行的。它们将来也许可以实现数据传输路径的一部分，但它们无法定义整套提交协议。

### 17.6 把 Git 当作工作区的权威来源

并不是每一个 Task 工作区都是一个 Git 仓库，而且 Git 天生也不太擅长处理大型二进制文件、生成出来的目录树、任意的上传内容，或者一个 Agent 实际观察到的、确切的非 Git 状态。把 Git 隐藏起来，并不会消除它自身的仓库和合并语义，只会把它们藏起来。Git，在存在的时候依然只是工作区的内容,而不是 BuildMax 的持久化引擎。

### 17.7 逐个文件单独上传

现有的 Space 文件（Space Home）适配器,是一次列出并下载一个对象。如果给 Task 检查点也套用同样的设计，会让请求数量和文件数量成正比，对源码树这种场景表现很差。一份单一的、带版本号的归档,是一个更小的、首个正确性切面。增量式的清单方案仍然需要证据驱动才会引入。

### 17.8 自动 Resume 一个丢失的 TaskRun

文件系统状态无法说明一个工具的外部副作用到底有没有真正发生。在 worker 丢失之后自动重启，可能会重复发送一封邮件、重复调用一个 API、重复一次提交、重复一条 Issue 评论，或者重复一次部署。恢复过程只是为一次新的尝试提供一个明确的基础；它并不会因此消除对 Retry 或者未来 Resume 语义的需求。

### 17.9 对展开后的 Plugin 目录做检查点

上传 `buildmax-home/plugins/` 确实能保留一个 Agent 已经获取到的包字节，但它同时也会保留解压产物、缓存、未声明的可变状态、可能存在的凭证，以及一些已经无法再证明自己目录摘要的字节内容。它会让同一个不可变的包在每一次运行里都被重复保存一遍，还会在恢复时绕过安装策略。BuildMax 的做法与此相反：只在必要时把一个规范化后的私有包存储一次，在一个 Plugin 环境版本里记录下不可变的版本引用，然后为每一次 TaskRun 重新物化出这个目录。

## 18. 推迟的问题

以下这些问题不会阻碍第一版完整归档方案的实现：

1. 测量出来的哪些工作区大小和文件数量,才足以证明有必要引入一种分块清单格式，或者一个持久化缓存方案？
2. 是否应当允许用户从一个部分检查点 Resume，如果允许，需要什么样的警告和授权机制？
3. 在 `workspace/` 中发现确切的 Space Secret 值时，是应当告警,还是应当直接让检查点发布失败？
4. Space 文件服务是否需要拥有自己的原子版本机制，好让第一个 Task 种子代表的是一次上传事务，而不是 worker 当时看到的那份确切的物化清单和副本？
5. 哪一种 Task 删除或保留操作，会第一个让检查点载荷的回收变得对用户可见？
6. Workflow 的各个步骤,是应当显式传递一个前序 Task 的工作区，还是应当让它们各自的 Task 继续独立地从 Space 文件播种？
7. 需要什么样的证据，才能证明有必要在安全的工具边界上做检查点，而不只是在 TaskRun 边界上？

以下内容不属于本文档下被推迟的实现工作：通用的工作区历史、时间线恢复、合并、跨设备重建，以及自动向 Space 文件写回。要推进其中任何一项，都需要一份单独的、经过批准的产品设计和路线图决策。
