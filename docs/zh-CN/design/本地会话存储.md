## 1. 决策

将每个本地会话原先可变的整文件 JSON，替换为由该会话拥有的目录；目录中的每类记录分别承担清晰、独立的契约：

```text
<BUILDMAX_HOME>/sessions/
  index.json

  <session_id>/
    meta.json
    history.jsonl
    traces/
      <run_id>.jsonl
    writer.lock
```

- `meta.json` 是体积较小、通过原子替换更新的当前元数据记录。
- `history.jsonl` 是权威的、仅追加且可恢复的对话日志。
- `traces/<run_id>.jsonl` 沿用现有的有界、脱敏、失败开放的运行诊断；每次运行一个文件。
- `writer.lock` 用于保证只有一个可变状态所有者，而不会把已经过时的进程状态当作持久元数据。
- `index.json` 是用于会话选择器、可随时重建的投影视图。

本设计借鉴了基于 JSONL 的编码 Agent 所采用的持续条目持久化和链式对话历史，但不会把元数据、可恢复内容和运行诊断混杂在一个无限增长的文件中。

## 2. 当前状态与问题

目前，`internal/core/session.Session` 会直接序列化到 `<BUILDMAX_HOME>/sessions/<id>.json`。其中包含：

- 用户、助手和工具消息；
- 助手发起的工具调用及其结果；
- 由提供商拥有的推理状态和非文本内容部分；
- 累计的提示词与补全 Token 数；
- 压缩边界与摘要；
- 持久化的笔记与待办事项；
- 附加系统提示。

`SessionManager.Save` 会序列化完整对象，并在一轮对话完成后替换原文件。另一个 `sessions.json` 保存用于列表展示的标题、工作空间、创建时间和置顶状态。所选模型只存在于 `SessionContext` 中，因此当前重新打开会话时会回退到默认模型。

这种结构有四个问题，按严重程度排列如下：

1. 一轮较长的 Agent 执行可能在保存会话前已经完成多次模型调用和工具步骤。进程崩溃后，无法区分“工作从未开始”和“工作可能已经改变了外部世界”。
2. 扁平的 `Messages` 数组没有可持久识别的回退点或分叉点。
3. 直接覆盖可能在中断、磁盘耗尽或机器故障后，使唯一的文件无法解析。阶段 0 已解决此项：两个文件现在都通过 `util.WriteFileAtomic` 原子替换。
4. 每轮对话都要重写此前所有消息、工具结果、提供商状态和图像数据。

这里的顺序很重要。写放大是最显眼、却也是最不重要的问题：对本地单用户会话而言，它只是浪费，并非错误；单凭这一点只足以引入缓冲，而不足以更换格式。真正无法由当前结构表达的是不确定的工具结果和缺失的条目标识，本文其余设计正是为了解决它们。

原子替换本身值得实施，而且已经落地，但它只解决了第三个问题。它没有解决增量持久化、工具结果不确定性或链式历史，因此只是权宜措施，并非最终答案。
## 3. 目标与非目标

### 3.1 目标

- 每个已完成、可恢复的条目只持久化一次，不再重写完整历史。
- 精确保留 `llm.Message` 值，包括工具调用、提供商状态、内容部分和来源信息。
- 在一轮执行过程中提交足够状态，以便中断后安全恢复。
- 为每个历史条目提供稳定标识和逻辑父节点。
- 支持恢复、回退与分叉，同时不把运行追踪当作权威状态。
- 保持标题查找和会话列表快速。
- 分别处理元数据、历史、追踪和 writer lock 的故障策略。
- 存储格式不依赖产生某轮对话的模型提供商，并可扩展到当前版本尚未定义的记录。
- 为前台、后台和嵌套子 Agent 提供私有的持久会话，同时不把它们作为普通用户会话暴露。
- 保持单二进制的本地体验，并使 Agent Core 不依赖具体存储实现。

### 3.2 非目标

- 重放或回滚任意外部副作用。
- 捕获或恢复工作空间文件状态。回退只移动对话历史，不撤销对话已经造成的变化。
- 持久化凭证、审批授权、进程句柄或 Shell 会话。
- 把本地会话记录做成防篡改的审计证据。
- 实现服务器同步、Space 共享或远程授权。
- 在首个实现中让分叉会话共享物理历史前缀。
- 支持多个写入者同时修改同一会话。
- 保留或迁移 Alpha 阶段的整文件 JSON 格式。

## 4. 记录归属

| 数据 | 权威来源 | 原因 |
|---|---|---|
| Session ID、类型、创建时间 | `meta.json` 和历史标题 | 目录和日志都能独立识别自身 |
| 标题、置顶状态 | `meta.json` | 展示元数据不会影响模型上下文 |
| 选定模型 | `meta.json` | 下一轮运行的当前选择 |
| 下一轮使用的工作区根目录 | `meta.json` | 与选定模型一样，是当前选择 |
| 某轮运行实际使用的模型和工作区根目录 | `turn_started` 历史记录 | 某一轮运行的事实 |
| Token 总量 | `meta.json` | 本地聚合报告；单次调用证据保存在其他位置 |
| 消息和工具结果 | `history.jsonl` | 重建提供商历史所需 |
| 工具是否跨越执行边界 | `history.jsonl` | 安全分类中断效果所需 |
| 压缩摘要和边界 | `history.jsonl` | 改变特定分支的模型可见历史 |
| Notes、todos、额外提示 | `history.jsonl` | 注入后续模型请求的持久状态 |
| 当前历史头部 | `head_selected` 历史记录 | 加载时推导，不存入元数据，因此不会与它指向的分支不一致 |
| LLM/工具耗时、工作目录、沙箱、Plugin、拒绝诊断 | 每次运行的 trace | 有界运行证据，不是恢复输入 |
| 当前写入者 | 操作系统锁及 `writer.lock` 诊断 | 进程事实必须能够自动过期 |

`meta.json` 和 `history.jsonl` 有意不共享一个事务，也不是彼此的投影。它们各自拥有不同的权威范围：

- `history.jsonl` 对重建对话所需的一切负责：消息、工具结果、压缩和持久状态。
- `meta.json` 对 Session 当前选择和运行聚合负责：标题、置顶、工作区、选定模型、Token 总量和累计成本。这些是设置和计数，并非日志摘要；重放日志无法恢复它们，历史也不需要记录它们。
- `index.json` 是本设计中唯一的纯投影，也是唯一声明可以通过扫描重建的文件。

两个权威来源在这里是安全的，因为它们的失败影响并不对称：丢失当前选择会降低展示质量并触发默认值，而丢失历史会破坏恢复。过时的标题或索引行绝不能让对话恢复到错误状态。

这种拆分只有在没有任何字段跨越两者时才成立，因此 `meta.json` 不保存任何由 `history.jsonl` 决定的内容。当前头部由 `head_selected` 记录表示，并在加载时从日志推导（§6.2），不会镜像到元数据。最后序列号也不保存：打开 Session 时重放日志即可免费得到这两个值，把它们缓存到元数据只会增加一致性规则，并不会带来有意义的速度收益。

不可变字段的重复是另一回事，可以接受：Session ID、类型和创建时间同时出现在 `meta.json` 与历史标题中，使每个文件都能独立识别。创建时固定的值不会漂移；§6.1 已将二者不一致定义为损坏，而不是把其中一个当成过时副本进行协调。因此规则针对可变状态：两个记录可以重复同一个常量，但不能重复同一个变量。

## 5. `meta.json`

每个 Session 的元数据文件足够小，可以通过原子替换更新：

```json
{
  "version": 1,
  "id": "<uuid>",
  "kind": "user",
  "created_at": "2026-08-23T10:00:00Z",
  "updated_at": "2026-08-23T10:30:00Z",
  "title": "Design local session storage",
  "workspace": "/repo",
  "pinned": false,
  "selected_model": "anthropic/claude-opus",
  "prompt_tokens": 12000,
  "completion_tokens": 1800,
  "cache_read_tokens": 9000,
  "cache_write_tokens": 1200,
  "cost": {"currency": "USD", "total": 4200},
  "cost_incomplete": false
}
```

`kind` 为 `user` 或 `subagent`。子 Agent 会增加不可变的谱系元数据：

```json
{
  "kind": "subagent",
  "parent_session_id": "<uuid>",
  "parent_run_id": "<run id>",
  "parent_tool_call_id": "call_1",
  "agent_type": "explorer",
  "delegation_depth": 1,
  "hidden": true
}
```

分叉出的用户 Session 会增加：

```json
{
  "forked_from": {
    "session_id": "<parent uuid>",
    "head_id": "<history item id>"
  }
}
```

`cost` 的字面结构是 `llm.Cost`，包含缓存和基准分解。`cost_incomplete` 表示某一轮使用了没有定价信息的模型，或发生了货币转换；标记为“不完整”比悄悄丢掉半个 Session 的总成本更安全。缓存 Token 计数属于 `prompt_tokens` 的拆分，而不是额外相加；汇总 Session 时不应把三者全部相加。

标题、置顶状态、工作区和选定模型的变更会写入临时文件、同步并原子替换 `meta.json`，不会添加对话事件。

如果元数据损坏，Session 仍会恢复，并采用保守默认值：无标题、不置顶、配置的默认模型和零值聚合。用量报告会出现错误，这是可接受的，因为系统明确报告了错误。

默认值不会让恢复出错，因为本文件不包含模型可见的历史选择。当前头部也不在此文件中：回退之后，最后一条物理记录可能属于用户放弃的分支；如果把头部缓存为元数据，副本损坏就可能悄悄恢复这条已放弃的工作。

`workspace` 与 `selected_model` 一样是当前选择，而非展示元数据：它决定下一轮工具运行位置，以及将哪个工作区 `AGENTS.md` 加入系统提示。因此，丢失它会让恢复降级到配置的默认根目录；这个结果可见且可纠正，不会悄悄改变历史。

如果历史被破坏，有效的元数据可能会使此次会议可见，但不能使其重新启动。

`selected_model` 表示下一轮应使用什么模型；`turn_started.model` 记录已完成或中断的那一轮实际使用什么模型。这个区分既保留了历史事实，也不会把每次 UI 设置变化都变成对话历史。

## 6. `history.jsonl`

### 6.1 标题

首先是一个不可变的，自我识别的标题：

```json
{"type":"history","version":1,"session_id":"<uuid>","created_at":"2026-08-23T10:00:00Z"}
```

在解释记录之前，载件器拒绝未支持的版本.与目录或`meta.json`不一致的标题会议ID是腐败，而不是替代拼写。

### 6.2 物理和逻辑秩序

每个后续线都有物理序列和逻辑历史身份：

```json
{
  "seq": 42,
  "id": "<history item id>",
  "parent_id": "<parent history item id>",
  "ts": "2026-08-23T10:01:02.123456Z",
  "type": "message",
  "turn_id": "<run id>",
  "data": {}
}
```

| 领域 | 合同 |
|---|---|
| `seq` | 开始于1的物理附加顺序；也在第14条`Append`中的乐观货币代币 |
| `id` | 本历史项目的稳定身份 |
| `parent_id` | 关于本分支的前一个逻辑项；仅仅省略了根 |
| `ts` | 检测时刻；从来没有订单密钥 |
| `type` | 复制历史语义的关闭歧视器 |
| `required` | 读者不能解释`type`是否必须拒绝会议，而不是跳过记录；见6.4 |
| `turn_id` | 选项对运行及其跟踪的相关性 |
| `data` | 具有明确的`snake_case`字段的类型特定有效载荷 |

物理顺序仅在反转后保持添加.逻辑顺序是在当前头结束的母链：

```text
physical append: A B C D E F

logical history:
  A -> B -> C -> D
       \-> E -> F   (current head)
```

这样，废弃的分支就能使用，

头部是取自而不是储存在日记旁边的，而取自是一个规则： **头部是最后的物理记录.**

转换不需要特殊情况，因为它表达在母链而不是旁边.除了 `head_selected`，每个记录链接到其物理前身，其母是被返回的项目.因此，添加一个将链接转向，并且它下降后的所有东西都从目标.阅读头费看最后一条，没有第二位的答案可能与它不同意。

### 6.3 记录词汇

| 类型 | 实用载荷 | 恢复效果 |
|---|---|---|
| `turn_started` | Run ID，有效模型，工作空间根，文本窗口，输入类型 | 开一个转圈，并修复其运行时间的身份 |
| `message` | 一个完整的`llm.Message` | 添加用户或助理提供商历史记录 |
| `tool_execution_started` | 工具调用ID和工具名称 | 标志证明通过的呼叫过了副作用边界 |
| `tool_result` | 工具调用身份证，状态，全文，内容部分 | 相关标识符一个工具角色消息，并关闭呼叫 Projects |
| `compaction` | 覆盖的头/范围，完整的积累总结 | 在此分支的模型可见前置换 |
| `notes_replaced` | 完整的邮票列表 | 换成长期的纸币 |
| `todos_replaced` | 完整的邮票所有名单 | 替换耐用的 Todos |
| `additional_prompt_set` | 完整的验证文本 | 取代了持久的附加系统提示 |
| `head_selected` | 原因；返回的物品是其`parent_id` | 转向原始链到更早的项目 |
| `turn_finished` | 终端状态  `completed`， `failed`， `canceled`，或 `interrupted` 和可选错误分类 | 关闭转折 |
| `turn_recovered` | 打断转换和不确定工具调用ID | 在新工作之前，使冷恢复明确 |

`message`保存了全可移植的 `llm.Message`，而不仅仅是文字.因此，辅助记录包括工具调用和不透明的提供商状态.用户记录保存了背景来源和内容部分。

缩减器将其投射到供应商适配器所需的 `role: tool` 消息中。 `tool_result`

标题，脚，工作空间，选定的模型偏好，使用总数，插件，沙箱政策和时间刻意缺席.它们属于元数据或运行诊断，而不是对话日志。

### 6.4 提供商中立性和前期兼容性

两个属性在这里比单卖方转录更重要，因为BuildMax针对许多提供商，并预计将增长该文件未预见的功能。

** 关于生产协议中立.** 历史存储可移植的`llm.Message`，从来没有提供商的电缆有效载荷。 角色，工具调用，工具结果，内容部件和轮回生命周期是BuildMax自己的词汇库，因此与一个提供商交谈时写的日志反复对抗另一个。

记录的一个提供商形值是`ProviderState`，它被标记为产生它的协议，以便读者能够确定它是否仍然适用.在不同的协议下恢复一个切换模型，一个改变的门户端，一个重新指向的配置下降了其标签不匹配活跃的适配器而不是转发.将其丢弃就会损失缓存推理，这是降级；转发将一个供应商的不透明字节发送到另一个供应商的终点，这是一个缺陷.一个调整的对话中期模式的消息因此具有混合协议，并且每个会根据自己的标签而不是整个会议的假设进行判断。

**可扩展而不需要破坏旧读者.** `type`是这里定义的语义的闭式歧视符，但格式仍然必须承认记录，这个版本从未见过：后来的功能，或插件所贡献的类型.因此，每个记录都声明读者不理解它是否可以跳过它。

- 只有添加信息的记录可以跳过。
继续进行。
- 需要一个记录，改变模型看到的东西。
解释它必须拒绝会议，而不是恢复对话。
然地减少了。

具体案例表明，为什么比特被决定以记录而不是以格式版本.今天，运行不能在目录之间移动:Bash执行在工作空间根上的每一次调用，文件工具拒绝逃离的路径，因此没有记录需要说工具运行在哪里.如果运行时间后来获得了持久的工作目录，则对其的变化是可见的模型，将作为所需的记录而到来，旧二进制器将正确拒绝他们无法放置的会话，而不是反弹它与错误的树。

这一点是让第7.2条保持严格的，而不使格式变成版本陷.未知和可跳跃的是一个警告；未知和必要的被完全像腐败一样对待，因为在两种情况下，缩短的历史将是错误的.因此扩展是决定是否新的记录是模型可见的，这是这个设计已经问到 §6.3 每个记录类型。

## 7. 提交与恢复语义

### 7.1 转移承诺界限

```text
accept prompt
  append + sync turn_started
  append + sync user message

call model
  append + sync assistant message

for each approved tool call
  append + sync tool_execution_started
  execute external effect
  append + sync tool_result

before next model request
  verify the current history prefix is durable

finish turn
  append + sync state changes and turn_finished
  atomically refresh meta.json and index.json
```

影响简历的项目不得在历史认可之前成为Agent核心可见.在持久性失败时，转转停止.会议持久性不能使用运行轨迹的失败开放行为。

批量只允许跨越不改变故障分类的边界.`tool_execution_started`在工具可能改变世界之前达到稳定的存储.其结果在另一个模型请求消耗之前达到稳定的存储。

据悉，这项保证的强度是底层同步的强度，原始的是`os.File.Sync`.Go的运行时间已经将其映射到每个平台提供的强度最大的 `F_FULLFSYNC`上 macOS，它在驱动器的写存储器中等待设备，而不是返回,`fsync(2)`上 Linux和BSD。 `FlushFileBuffers` Windows

过程崩和功耗损失是不同的保证，并且这个设计并没有把它们混在一起.在平台最强的原始系统得到尊重的地方,7.3分类是声音的电源损失，并且在不存在的地方降低到崩:macOS 返回`fsync`，当`F_FULLFSYNC`返回`ENOTSUP`时，这是一些网络和虚拟文件系统所做的，并且没有任何软件原始程序能够存活一个报告流失的设备.只使用缓存流失后,相关标识符 记录可以丢失，并且恢复都不会被归类为相关标识符在系统下工作。 `tool_execution_started` `not_started`

文件目录录是单独的问题，有更便宜的答案.添加到现有日志不会改变其文件目录录，所以热路根本不需要文件目录同步.创建一个会议目录是。 故意取代`meta.json`不会： §4已经确定了输掉一个元数据写会降低当前的选择而不是恢复，因此每次支付一个文件目录同步保护它将是错误的东西。

这种选择是延迟预算和正确性预算.这个协议每轮至少同步5次加上每次批准的工具调用两次，因此10次平行工具调用的轮回在交互路上交叉约25个同步点.这是用户每轮支付的成本，并且是首先测量的成本。

### 7.2 尾裂和腐败

载体验证标题，图案，独特的ID，父母引用，记录关系.一个不完整的最后一行是撕裂的尾巴，并且在获得编写角色时可能被缩小到最后一行.不有效的JSON，未知所需类型，或在尾巴腐败之前不有效的关系，并未能加载路径和序列号。

`seq` 中的空白不在该列表中.只有一位作者和仅一个附录文件只能撕裂尾巴，所以空白意味着BuildMax以外的东西已经缩小或编辑了期刊。  §3.2将改证据排除在范围之外，或者一个记录缺失，这可以改变减小的任何地方，这项父链验证已经拒绝了。 仅限于一个废弃的分支的空白没有改变模型的任何东西。 对于一个失败的第二个信号，第一个已经报告的收购了严格而不是安全性，所以相关标识符仍然是一个订单和同步设备，并不是检查。

仅阅读检查永远不会修复文件。 开放为继续修复撕裂的尾巴，并在接受新的提示之前添加恢复状态。

拒绝继续并不是提供任何出路.在尾巴之前出现的腐败记录会导致继续负载失败，加载器还会暴露一个只读的保存模式，将有效的预先fix降低到第一个坏记录，并将其导出为新会话目录.损坏的原始永远不会在位置上重写.一个可以只报告为破产的本地会话，没有进入工作的路径，比保守的拒绝加上明确恢复命令更糟糕的结果。

### 7.3 工具的结果不清楚

助理工具调用证明了所要求的模型工作.一个`tool_execution_started`记录证明BuildMax批准了调用，即将进入工具.一个`tool_result`记录了观察结果。

| 长期历史 | 恢复类别 |
|---|---|
| 只有助理电话 | `not_started` |
| 助理调用加上`tool_execution_started` | `outcome_unknown` |
| 匹配`tool_result` | 已知`completed`,`failed`,`denied`，或已恢复的`unknown`结果 |

恢复告诉模型在重新尝试任何非无能效果之前验证可能的效果。 `outcome_unknown`

开放一个中断的会话添加一个`turn_recovered`记录命名中断的转折和其不确定工具调用ID，随后一个相关标识符，每个工具都具有状态`unknown`.模型所看到的合成结果因此本身是持久的，并出现在完全一次：第二次中断的开放扩展了分支，而不是重播相同的维修，没有读者需要知道哪些工具结果被观察到，哪些被重建，因为记录说。 `tool_result`

该期刊记录了Agent的观察状态.它不能证明文件系统，一个子过程，一个HTTP终端点，或远程数据库匹配该状态。

### 7.4 取消和关闭

转向以两个方式停止， 它们的轴不仅是任何一个人想的，

虽然BuildMax正在运行，它就会在运行水平上自行关闭.一个停止转变的人会获得`turn_finished`，状态是`canceled`；在转变中到达的关闭时会得到`interrupted`.这些是[`graceful-shutdown.md`](优雅关闭.md)在运行水平上已经分开的两个原因。 [`graceful-shutdown.md`](优雅关闭.md)在 相关标识符和 `ErrRunInterrupted`，在这种推理上，在此没有改变：一个停止，过程知道运行发生了事先，而不是沉默和被遗弃。 `ErrRunCanceled` Portal

关闭转圈不是被打断的转圈.下一个开放时看到`turn_finished`，不添加`turn_recovered`，而不是修理。

关闭一轮对话并不能确定其中工具调用的结果。一次调用跨过 `tool_execution_started` 后尚未返回，无论该轮是被取消、中断，还是随进程丢失，都属于 `outcome_unknown`：BuildMax 知道调用进入了工具，却不知道副作用是否已经发生；主动停止也无法让这件事变得可知。因此，进程仍持有调用 ID 时，会写入与 §7.3 恢复流程完全相同的记录——每个不确定调用对应一条状态为 `unknown` 的 `tool_result`——而不会虚构并不存在的确定性。

如果该过程在其自身取消过程中，在第二次中断或`SIGKILL`时，不需要什么特别的东西：转转被留开，下一个开放就像第7.2和第7.3节所描述的那样恢复。 优雅的关闭是优化对恢复而不是替代。

## 8. 回退与分叉

### 8.1 为什么没有检查站

一个早期的草案中有一个`checkpoint`记录，命名了一个头，所以可以返回后面.它已经消失了，原因被记录了，而不是被留给重新发现。

检查点是关于状态的承诺.在其他地方使用这个词，它意味着"把事情恢复到原有的状态" 文件包括.这个设计不能保持这个承诺:BuildMax没有版本工作空间功能，并没有设计记录，之前的记录已经被撤回而不是实施，因为[`trust-harness.md`](信任保障.md)和会议树提案都声明。

只有对话的检查点，因此，它会比它所提供的功能更有希望的名称.更糟糕的是，该名称会隐藏尖端边缘，而不是暴露它：在编辑文件，运行Bash或调用网络服务的转折之后，将所有这些效果都留在位.模型的历史回到一个早期的点，而世界没有，因此模型然后从一个图像中推断了工作空间不再是真的。

恢复一个代理改变的能力是值得拥有的，但它是一个不同的设计记录，在这里命名一个插槽将描述一个撤回的能力即将到来。

### 8.2 转

转换将用户自己的提示中的一个带回来.所选的消息离开了分支，以及其后的一切，其文本返回了输入框，以便编辑并再次发送，这就是操作的目的，以及为什么它不包括它，而是排除了消息。

转回将一个`head_selected`记录添加到，其母是转回消息之前的记录。

登陆记录是分支上的物理前身，而不是之前的消息：笔记， Todos，一个紧缩，和转折的`turn_finished` 在所有坐在两个消息之间，属于正在保存的工作.一个记录是`turn_started`，因为第7.1节在启动的提示之前打开了转折，并且登陆将会让转折内分支落下.一个提示没有任何东西之前的 首个会议 没有登陆，并没有提供；一个新的会议说同样的事情，而不发明一个空的分支。

叉提供了每一个结束的消息，包括头，但不是一个要求工具的答案：一个分支结束时，有一个没有结果的呼叫，只有一些提供商调节器剪切。 目标在有效载荷中没有重复：这是一个记录，故意指向其物理前身以外的地方，所以母链已经说出了目标字段会做的一切，并且将其存储两次只会产生一个可能不一致的对。 因为头取而不是存储，没有第二次写步，没有任何提示可以在中留下选择的分支。 旧尾巴在相关标识符 `history.jsonl`

转向转移会话，而没有其他任何东西.它不会恢复工作空间 (§8.1)，也不会改变工作空间根：该根是`meta.json`中的当前选择，因此转向在其他地方运行的转向会留下用户最后放出的下一转.转向转移的`turn_started`记录仍然显示了它使用的根，这使得区别可以检查而不是沉默。

缩写是分支范围的。 总结记录了它涵盖的历史头或范围。 叉点后生成的总结不能被未包含总结的记录的孩子重复使用。 原始历史仍然存在，直到所有反转和叉保留规则允许物理缩写。

### 8.3 叉子

叉在选定的消息中物理复制历史前，将其保存到一个新的会话目录中.它保存了项目ID，给孩子提供了一个独立的会话ID和元数据记录，并将叉源写入`meta.json`。

复制的内容是通过该消息的*分支*，而不是物理前：被重新回收的父母也保留遗弃的记录，并且携带这些记录的孩子永远不会达到自己的父母链.序列号不保存 `seq`是记录在持有该记录的日志中的位置，因此孩子从一个中重新编号，而父母中存在的空隙没有痕迹.物品ID是因为它们是使孩子的记录可识别的身份，就像父母做的工作一样。

孩子开始使用自己的产品，成本总数为零.继承父母的产品会增加一旦有人增加两个会议，就会增加一倍的钱.标题和工作空间被携带，因为它们描述了对话的持续，而不是产生它的运行。

物理复制是O(n)，但它给了Alpha实现的明确所有权：

- 删除父母不能破坏孩子；
- 充电从未进行了另一次会议；
- 授权和保留停留会议本地；以及
- 没有需要引用数的历史图表。

叉口复制日记前，而没有其他东西，因为历史将会话内容全部保持在线 (§11)。 没有一个独立的内容存储器，让孩子分享，因此没有引用数量会错误。

没有计划共享预置，复制在写的部分和数据库支持的历史图表.每个购买一个较小的副本以删除，保存和垃圾收集规则的价格，物理副本根本不需要。

后续记录不会复制到儿童简历文本中。 叉子元数据命名了该会议和标题，新的儿童运行创建了新的后续记录文件。

## 9. 子 Agent 会话

每个前景，背景或嵌套的子物都具有相同的目录形状，

苏巴根特会话是`kind: subagent`，隐藏于普通选手，并排除在`--continue`之外.它们的头条和元数据记录了直接的母会话，运行，工具调用,Agent类型和委托深度.母 Task结果仍然是面向模型的返回路径。

专用日志删除了当前行为，在回归时将子体的整个`session.Session`丢弃.它不会将当前的一次性子体转化为可见的叉子.父母崩不会自动重新启动Task工具：父母历史分类呼叫，而儿童日志表示孩子是否达到终端转折。

根据选择的保留政策，一个封闭的孩子被留在父母那里。 持续监督，邮箱，自动的父母简历，可见的儿童导航和工作场所隔离仍然是会议树的决定。

## 10. 追踪

现有运行轨道合同，除了物理共处外，没有变化：

```text
<session_id>/traces/<run_id>.jsonl
```

每次运行的一个文件保存独立的盖子，终端`run_end`，保留，上传和父母/孩子的痕迹相关性.为整个会议的单个`trace.jsonl`被拒绝，因为同时运行的儿童或背景运行，每次运行清理和腐败将分享一个无限的附录目标。

运行工具的位置也属于这里.运行不能在目录之间移动 (§6.4)，但单个Bash命令仍然可以在自己的调用中命名`cd`或命名绝对路径，因此实际触及的目录是操作证据而不是恢复输入.记录它每次调用在历史中将在每个记录上盖章变化的通话语境，这是第16.6条的做法拒绝；痕迹是局限的，已经是其所在的位置。

追踪保持局限，编辑，并未开放.历史保持不损失的恢复和未关闭的提交界限.一个追踪可能总结一个历史项目ID进行相关性，但一个追踪路径从来没有读取追踪内容作为状态。

## 11. 会话内容与隐私

历史存储内容直线：普通文本，结构化工具结果，以及非文本部分.没有单独的内容存储，没有尺寸门，并且没有在负载上解决的参考。 会议的对话是在拥有它的一份文件中.这里没有限制它变得多大；第13节说出了什么是成本和什么是不做。

会议内容不会被编辑，因为编辑会改变恢复模型所看到的内容.会议目录使用私人权限 (`0700`目录和支持时的`0600`文件).凭证和批准授权永远不会作为会议状态输入元数据，历史或痕迹。

## 12. 索引、锁与生命周期

采集器投影是`sessions/index.json`.它仅包含用户可见的会话，具有ID，标题，工作空间，针，类型，更新时间，以及足够的后代来组合叉子.它通过临时文件同步和原子改名编写，并在陈旧或损坏时通过扫描`meta.json`文件重建。

列表读取`index.json`，不扫描.投影存在于这样的情况下，开放选民每次每次会话只需要一个小文件，而不是一个`meta.json`，如果一个过时的投影静静地回到行驶目录，则存储就会消失.因此，重建是明确的修复，当索引缺失，无法解析或未能检查一致性时被触发。

会议日志有一个编写者.现有的进程中转换保护器仍然存在，文件后端添加了一个跨进程锁.`writer.lock`可能包含PID，进程启动时间或所有者诊断，但这些值不是权威：操作系统锁决定了所有权，一个废弃的文件不能永久地保持一个会议繁忙。

交叉过程锁是`writer.lock`上的OS咨询锁:`flock(2)`在macOS和Linux,`LockFileEx`在`LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY`上使用[阅读中文镜像](本地会话存储.md)，这两者都是通过`golang.org/x/sys`，这是已经成为依赖。 Windows

便携式替代品在上述要求上失败.一个`O_CREAT|O_EXCL`锁文件根本不需要平台代码，也不能自清：它比它制造的过程过来，因此从崩中恢复意味着判断记录的PID是否还活着.这个设计拒绝作为权威处理.一个内核锁在拥有过程出口时释放，但它出口，这是"一个废弃的文件不能永久地保持一个会议繁忙"的唯一版本，不需要任何修复。

锁定是采用`writer.lock`而不是`history.jsonl`，因为读者必须能够在写作者持有会议期间检查稳定的前置.锁定日志本身将阻塞这些读者或，用POSIX记录锁，暴露了关闭任何文件描述符的规则.一个独立的文件没有任何问题，也是因为`flock`在`fcntl`上被偏好。 Unix

咨询锁定并不普遍可用：一些网络文件系统拒绝它，有些则接受它，不做任何事情。 收购失败报告而不是假设成功，而无法锁定的文件系统是BuildMax这样说的，而不是假装会话仅仅举行。

只有读取的检查可以在写作器活跃的时候读取稳定前.第二个过程不能恢复，转转，从不稳定的头发中，或添加直到它拥有写作器锁。

删除一个会话将其目录直接删除.因为一个叉是物理副本 (§8.3)：没有其他会话的内容生活在该目录中，它之外没有什么指向.因为这是一个物质破坏性操作，调用者更能识别确切的会话，而不是在一个前上匹配。

## 13. 日志增长

任何东西都没有限制日记的规模。

复制式调整会员的重量比其可见的对话所示的速度更快，并且由于容易误读的原因，会更慢地打开：重播解析整个文件，以找到现场分支，因此开放式调整会记录磁盘上的总字节废弃分支，而不是模型实际看到的对话长度.显示相同的转录的两个会议可以以非常不同的速度打开。

物理剪裁是这项工作的结合，它不会出货.在分支或叉口出口取决于它，前不能被移除，并且在该可访问性规则和其恢复行为被指定和测试之前，不应该出货。

## 14. 所有权与接口

```text
internal/core/session
  history item types, validation, linked-history reducer, recovery analysis

internal/agentapp
  SessionManager, commit orchestration, metadata/index policy, lifecycle

internal/infra/sessionstore
  JSONL codec, atomic metadata files, locking, append/sync, tail repair
```

`internal/core/agent` 继续依赖历史和耐用状态接口.它不进口文件,JSONL，数据库或服务器客户端。 持久性接口表达会议语义而不是路径，它生活在`internal/core/session` 纯粹表达在核心类型方面，它没有对 infra 依赖，这使得`internal/infra/sessionstore` 取决于它而不是反之：

```go
type Store interface {
    Create(ctx context.Context, meta Meta) error
    Open(ctx context.Context, id string) (Writer, error)
    Load(ctx context.Context, id string, mode LoadMode) (Loaded, error)
    UpdateMeta(ctx context.Context, id string, update MetaUpdate) error
    List(ctx context.Context, includeHidden bool) ([]ItemSummary, error)
}

type Writer interface {
    Loaded() Loaded
    Append(ctx context.Context, items ...Item) error
    Close() error
```

## 16. 备选方案

### 16.1 原子全档案 JSON

作为对部分重写的防范，它仍然会重写完整的历史，并且会失去飞行工具状态，稳定的项目身份和廉价的叉点。

### 16.2 一个多重的JSONL文件

一个附加流将元数据，历史，运行时间状态和诊断提供一个总序，使一个会议很容易复制.它还将无损恢复数据进行组合，将删除的失败开放痕迹重复可变元数据，防止独立保留，并增长一个无限的方案和文件。

这对于一个单机写字符的产品来说是合适的，该产品将单个文件的可移植性视为比分政策更高。 BuildMax已经具有不同的会议，痕迹，Artifact，工人和Portal合约，因此目录捆绑是更好的边界。

### 16.3 仅提供平面信息的JSONL

没有稳定的项目ID，母链接，工具执行界限，紧缩和持久的内存，它无法安全地实现中断恢复，倒转或叉。

### 16.4 所有本地会议的SQLite

SQLite提供交易，索引和同步读者.它还在查询或同步证据需要之前，将数据库方案和迁移运行时间添加到单双本地路径中.它将是一个新的依赖而不是现有的重复使用:`internal/infra/db`是服务器存储器，通过GORM说话MySQL，因此今天没有本地路径链接SQLite驱动程序。

链接历史域名合同保持后端中立，以便SQLite后期获得资格。

### 16.5 阶段1的共享叉口前置

引用共享降低复制成本，但使儿童负载，父母删除，授权，保留和垃圾收集相互依赖。

### 16.6 与现有的JSONL代理的现场级兼容性

匹配其他编码代理的记录字段，使一个BuildMax日志在其工具中打开，或者其会议重播在这里被拒绝，因为它指向该项目错误的方向.BuildMax是一个开放的，多提供商运行时间.其存储形式应该保持中立，关于哪种模型或协议产生了转变，并且保持自由的记录，任何供应商格式预测的功能.采用一个供应商的方案都会交易：它将开放运行时间与它无法控制的格式关联，继承该格式的转变，并将每一个未来扩展变成对别人的产品的兼容性问题。 §6.4是被保护的财产。

范围也证实了同样的答案。 文件实际上跨越边界时，兼容性才会受到限制，

结构学案被采用，第1节则这样说： 连接的记录不是一个平面数组，每件完成的项目每一个持久的记录，以及一个自我识别的第一行.这些是一个形成良好的日志的属性，而不是任何人的产品。 两个常见的做法是故意不采用。 一个是单个多重流，在第16.2节中被拒绝。 另一个是将可变的每次会议文本 工作目录，分支，构建版本 印在每个记录上，这使日志膨胀并创造出尽可能多的答案，就像有线程一样； § 4 保持在`meta.json`和 § 6.2 保持记录标题最小。
