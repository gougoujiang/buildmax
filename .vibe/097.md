# Task 097: Save conversation_id for chat

## Goal

When a chat is created by the Tier 1 conversation agent (via the StartChat tool), persist the Tier 1 conversation’s `conversation_id` on the chat record so the system can associate the chat with the conversation that started it (e.g. for display, filtering, or resuming context).

## Context

- **Tier 1**: Conversation entity and messages live in `entity.Conversation` / `entity.ConversationMessage`; `conversation_id` identifies a multi-turn portal (or other channel) conversation.
- **Tier 2**: Chat + ChatRun represent a background task; created via `ChatStore.CreateChat` and optionally via the StartChat tool from the conversation loop.
- **Current gap**: `CreateChat` and the StartChat runner (`serverStartChatRunner` → `doStartChat`) do not receive or store a conversation ID. Chats created from POST /chats also have no conversation; only chats created via the Tier 1 StartChat tool should get one.

## In scope

1. **Chat model and DB**
   - Add optional `conversation_id` to the Chat model (`internal/model/models.go`): nullable string, snake_case in JSON, indexed for lookups. Follow existing pattern (e.g. `SessionID`, `AgentID`).
   - Migration or schema: add column to `chat` table (nullable `varchar(64)`, index). Project uses GORM; ensure new column is applied (e.g. AutoMigrate or migration script as per project practice).

2. **Persistence**
   - Extend `ChatStore.CreateChat` to accept an optional `conversationID *string`. Entity layer: `internal/storage/entity` (CreateChat implementation and interface in `interfaces.go`). When non-nil, set on the new Chat row.

3. **Tier 1 path**
   - When the conversation agent runs the StartChat tool, pass the current `conversationID` into the chat creation path:
     - Extend `tools.StartChatRunner` (and implementers) so the runner can receive and forward `conversationID` (e.g. optional parameter on `StartChat`, or runner constructed with conversationID when used from Tier 1).
     - Server: `startChatRunner(workspaceID, userID)` is used from `createConversationHandler` and `addConversationMessageHandler` where `conversationID` is in scope. Create the runner with `conversationID` and pass it into `doStartChat`; `doStartChat` passes it to `CreateChat`.
   - Chats created via **POST /api/workspaces/{id}/chats** (direct create) continue to have no conversation_id (nil); no change to that handler’s behavior.

4. **API and responses**
   - Expose `conversation_id` on chat where appropriate: e.g. chat list/detail responses (optional field, omit when empty). Align with existing snake_case and optional-field patterns in `chats.go` (e.g. `ChatResponse`).

## Out of scope

- Backfilling existing chats with a conversation_id.
- Changing Tier 2 worker or run semantics (worker does not need conversation_id).
- New endpoints or filters (e.g. “list chats by conversation_id”); can be added later.
- Portal UI changes to display or filter by conversation_id (backend-only in this task).

## Deliverables

- `internal/model/models.go`: Add `ConversationID *string` to `Chat` with appropriate tags.
- `internal/storage/entity`: Update `CreateChat` signature and implementation to accept and persist optional `conversationID *string`; ensure DB schema (AutoMigrate or migration) adds the column.
- `internal/storage/entity/interfaces.go`: Update `ChatStore.CreateChat` signature.
- `internal/tools/start_chat.go`: Extend `StartChatRunner.StartChat` (or runner construction) so conversationID can be passed when creating a chat from the conversation loop.
- `internal/server/conversation_tools.go` and related: Runner created with conversationID when invoked from conversation handlers; `doStartChat` accepts and passes it to `CreateChat`.
- `internal/server/chats.go`: Include `conversation_id` in chat responses (e.g. `ChatResponse`) where chats are returned; direct POST /chats and list/detail remain consistent (nil when not set).
- Call sites of `CreateChat` (server handlers, tests, mocks): pass nil for conversationID where not in a conversation context; pass the conversation’s id when creating from Tier 1.

## Acceptance

- [ ] Chat model has optional `conversation_id`; DB has nullable column and index; CreateChat persists it when provided.
- [ ] Chats created via Tier 1 (StartChat tool) have `conversation_id` set to the creating conversation’s id.
- [ ] Chats created via POST /api/workspaces/{id}/chats have `conversation_id` nil/omitted.
- [ ] Chat list/detail API responses include `conversation_id` when set (snake_case, optional).
- [ ] `go build ./...` and `go test ./...` pass; existing tests updated or extended as needed.
