# Task 056: Container image infra

## Goal

Enable building a container image for the BuildMax Go binary and loading it into the local kind cluster so the project can run BuildMax in Kubernetes (e.g. for server/executor or future workloads).

## Context

- **Build today**: `./make build` produces a single `buildmax` binary from `cmd/buildmax` (Go 1.26). No Docker or container usage yet.
- **Local K8s**: `./make setup` creates a kind cluster (`buildmaxdev` or `BUILDMAX_KIND_CLUSTER`), MinIO, MySQL, port-forwards; images must be loaded into kind via `kind load docker-image` to be available in-cluster.
- **Conventions**: Scripts live under repo root (`make`, `setup/`); AGENTS.md and DEVELOPEMENT.md document build and setup. Single-binary distribution is a project goal.

## Scope

### In scope

- **Dockerfile for BuildMax binary**
  - **Filename**: `Dockerfile.buildmax` in repo root. This naming allows a future `Dockerfile.portal` for the Portal image so the two are clearly distinguishable.
  - **Multi-stage build**: Yes. (1) **Build stage** — use a Go image to compile the binary *inside* the container (consistent Go version, no host Go required). Compile for **Linux** (`GOOS=linux`) so the binary runs in containers; kind only runs Linux-based container images. (2) **Runner stage** — minimal Linux runtime image (e.g. Alpine or distroless) that only contains the `buildmax` binary and what it needs (e.g. `ca-certificates` for HTTPS).
  - **Platform**: Containers in kind are always Linux. On macOS ARM64, `docker build` by default targets `linux/arm64`, which matches kind on Apple Silicon. So a default build on Mac ARM64 produces an image that runs in the local kind cluster. For kind clusters that use amd64 nodes (e.g. some CI or Intel Mac), the make target or docs may support an optional `BUILDMAX_IMAGE_PLATFORM` (e.g. `linux/amd64`) so users can build for the correct architecture; implementation can be minimal (document only, or pass `--platform` when set).
  - Image tag is deterministic for local use (e.g. `buildmax:local`).
- **Make integration**
  - New make sub-command (e.g. `./make pub_images` or `./make image`) that:
    1. Builds the Docker image using `Dockerfile.buildmax` (e.g. `docker build -f Dockerfile.buildmax -t buildmax:local .`). Honor `BUILDMAX_IMAGE_PLATFORM` if we support it (e.g. `--platform $BUILDMAX_IMAGE_PLATFORM`).
    2. Loads it into the kind cluster (e.g. `kind load docker-image buildmax:local --name <cluster>`).
  - Use existing `BUILDMAX_KIND_CLUSTER` or kind default cluster name so it aligns with `setup/setup.sh`.
- **Documentation**
  - Brief note in DEVELOPEMENT.md or README on how to build the image and load into kind (and that `./make pub_images` does both).

### Out of scope

- **Portal image**: A separate container image for the Portal (React/Vite) is explicitly out of scope; to be done in a future task.
- **Pushing to a registry**: Only local build + kind load; no `docker push`, no CI/CD or registry publishing.
- **Kubernetes manifests**: No Deployment/Service/Job YAML changes for running BuildMax in the cluster; only image availability.
- **Multi-arch manifest or custom base image**: Building a single platform per run is enough; optional `BUILDMAX_IMAGE_PLATFORM` for linux/amd64 on Mac ARM64 is in scope only if trivial; no multi-arch manifest lists.

## Deliverables

1. **Dockerfile.buildmax** (repo root) — multi-stage: build stage compiles `buildmax` for Linux inside container; runner stage runs it; minimal and secure (non-root optional but not required).
2. **Make target** — one command that builds the image and loads it into kind (e.g. `./make pub_images`).
3. **Docs** — short instructions (in DEVELOPEMENT.md or README) for building and loading the image.

## Acceptance criteria

- [ ] `docker build -f Dockerfile.buildmax -t buildmax:local .` produces an image that runs `buildmax version` successfully (e.g. `docker run --rm buildmax:local buildmax version`). On Mac ARM64 with default platform, the image is linux/arm64 and runs in local kind.
- [ ] `./make pub_images` (or the chosen target name) builds the image and runs `kind load docker-image ...` so the image is available in the kind cluster used by `./make setup`.
- [ ] After `./make pub_images`, `kubectl` / in-cluster workloads can use the image (e.g. `image: buildmax:local` in a Job/Pod spec runs the binary).
- [ ] Documentation describes `Dockerfile.buildmax`, how to build the image (and optional `BUILDMAX_IMAGE_PLATFORM` for linux/amd64 if implemented), and how to load it into kind (and references the new make target).
- [ ] Existing `./make build` and `./make test` remain unchanged and passing.
