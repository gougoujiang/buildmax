# Smell Proposal - internal package

## Scope

**Analyzed**

- Paths / packages: `internal/` (all Go packages under internal)
- Criteria: Tactical, local code smells: long functions, duplication, unclear names, mixed concerns, missing abstractions, redundant code.

## Summary

- **Proposals**: 8
- **High priority**: 2
- **Overview**: Main findings are repeated “require store” checks in the server, a long executor RunTask with mixed responsibilities, duplicated static-file serving and task ownership checks, and repeated tool argument parsing patterns. Several refactors would improve readability and testability without changing behavior.

---

## Proposals

### 1. Consolidate server “require store” helpers

**Location**: `internal/server/auth.go` — `requireWorkspaceStore`, `requireProjectStore`, `requireTaskStore`, `requireTaskRunStore`, `requireArtifactStore`, `requirePersistStorage`, `requireArtifactStorage` (lines 46–105)

**Current state**

- Seven nearly identical methods: each checks if a different `s.cfg` field is nil, writes 503 with a specific message, and returns a bool. The only variation is the store field and the message string (“workspaces not configured”, “projects not configured”, etc.).
- This duplicates the same pattern and inflates the Server API surface.

**Proposed change**

- Introduce a single generic helper, e.g. `requireStore(w, store interface{}, unavailableMessage string) bool`, or a small struct that holds the store and message, and call it from each handler. Alternatively, a single method that takes the store and message: `s.requireStore(w, s.cfg.WorkspaceStore, "workspaces not configured")`.
- Remove the seven individual methods and replace call sites with the single helper.

**Benefit**: Less duplication, easier to add new stores, consistent behavior and messaging.

**Priority**: Medium

---

### 2. Unify static file serving in server

**Location**: `internal/server/server.go` — `serveStaticJSON` and `serveStaticHTML` (lines 116–140)

**Current state**

- Two functions that differ only in the `Content-Type` header and the path passed in. Both read from `staticFS`, log on error, write 500 on failure, and write body on success. This is duplicated logic.

**Proposed change**

- Replace with a single function, e.g. `serveStatic(w http.ResponseWriter, path, contentType string)`, that sets the given `Content-Type`, reads the path from the embed, and handles errors once. Call it as `serveStatic(w, "static/openapi.json", "application/json")` and `serveStatic(w, "static/swagger.html", "text/html; charset=utf-8")`.

**Benefit**: Single place for static serving and error handling; easier to add more static assets.

**Priority**: Low

---

### 3. Split executor RunTask into smaller steps

**Location**: `internal/executor/executor.go` — `RunTask` (lines 36–124) and surrounding helpers

**Current state**

- `RunTask` is ~90 lines and does many things: validate inputs, create dirs, restore session from previous run, materialize workspace, build env, run buildmax, write result file, upload buildmax dir, update run on failure/success, handle artifact. Failure handling is repeated (update run to FAILED + return). The function is hard to test in isolation and hard to follow.

**Proposed change**

- Extract logical steps into well-named functions, e.g. `ensureRunDirs`, `restoreSessionFromPreviousRun`, `runBuildmaxCmd`, `persistRunResult`, `reportRunFailure`, `reportRunSuccess`. Keep `RunTask` as a short orchestration that calls these in order. Optionally group “update run status” into a small helper to avoid repeating the updater call pattern.

**Benefit**: Readability, testability (each step can be unit-tested or at least read in isolation), and clearer error-handling flow.

**Priority**: High

---

### 4. Extract task-in-workspace validation in server

**Location**: `internal/server/tasks.go` and `internal/server/artifacts.go` — repeated “get task, then if task == nil || task.WorkspaceID != workspaceID return 404”

**Current state**

- The pattern “fetch task by ID, then ensure task belongs to workspace (or task not found)” appears in multiple handlers: `createTaskRunHandler`, `getTaskConversationHandler`, and in artifacts handlers. Code is duplicated and the 404 message is repeated (“task not found” or similar).

**Proposed change**

- Add a helper on `*Server`, e.g. `getTaskForWorkspace(ctx, w, workspaceID, taskID) (*model.Task, bool)`, that loads the task, writes 404 if nil or workspace mismatch, and returns (task, true) only when the task exists and belongs to the workspace. Use it in all handlers that need “task scoped to this workspace”.

**Benefit**: Single place for task resolution and consistent 404 behavior; less duplication in handlers.

**Priority**: Medium

---

### 5. Simplify getTaskConversationHandler and conversation data source

**Location**: `internal/server/tasks.go` — `getTaskConversationHandler` (lines 229–296)

**Current state**

- The handler is long and mixes: auth, store checks, path param validation, task fetch and workspace check, session/lastRun checks, then two different data sources (PersistStorage vs local file via `config.RuntimeTaskRunBuildmaxDir`). The fallback to local file uses a global config path that may not match server’s `WorkspacesDir`, which is confusing and potentially wrong when server runs with overridden workspace root.

**Proposed change**

- Extract “load conversation bytes for task” into a helper (e.g. on Server or a small conversation loader): try PersistStorage first, then optionally a local path derived from `s.workspacesDir()` (or a dedicated runtime path from server config), so the server controls the path. Shorten the handler to: auth → get task for workspace → load conversation bytes → unmarshal → write JSON. Consider making the data source a single strategy (e.g. always PersistStorage when set, otherwise explicit local path from server config) to avoid mixed semantics.

**Benefit**: Clearer handler flow, consistent path resolution with the rest of the server, and easier to test conversation loading.

**Priority**: High

---

### 6. Introduce shared tool argument helpers

**Location**: `internal/tools/` — multiple files (readfile.go, writefile.go, editfile.go, grep.go, glob.go, bash.go, webfetch.go, todowrite.go, skill.go, task.go)

**Current state**

- Each tool’s `Execute` manually extracts and type-asserts args: `args["file_path"]`, `args["offset"]`, `args["limit"]`, etc. Repeated patterns include: “required string arg”, “optional string arg”, “optional number with default”. There is no shared helper for “get string arg or error” or “get optional int with default”, so the same boilerplate and float64 handling (e.g. in readfile’s `parseOffsetLimit`) could be centralized.

**Proposed change**

- Add a small internal helper package or file (e.g. `tools/args.go`) with functions like `RequiredString(args map[string]any, key string) (string, error)`, `OptionalString(args, key string) (string, bool)`, `OptionalInt(args, key string, defaultVal int) (int, error)` (handling JSON number as float64 once). Use these in tools so each `Execute` is shorter and type/error handling is consistent.

**Benefit**: Less duplication, consistent validation and error messages, and easier to add new tools.

**Priority**: Medium

---

### 7. Replace executor ptr helpers with a tiny generic or keep local

**Location**: `internal/executor/executor.go` — `ptrString` and `ptrInt64` (lines 162–163)

**Current state**

- Two one-line helpers used only to pass optional fields to `UpdateRunStatus`. They are fine but very local; if other packages need the same, they might duplicate similar helpers.

**Proposed change**

- Option A: Leave as-is (they are clear and local). Option B: Move to a small `internal/util` or `internal/ptr` package (e.g. `util.Ptr(s string) *string`) if multiple packages start needing pointer-to-scalar. Do not introduce a generic pointer helper only for executor; only centralize if a second consumer appears.

**Benefit**: Avoids proliferation of duplicate ptr helpers across packages if the need grows; no change if usage stays in executor.

**Priority**: Low

---

### 8. Reduce middleware logging of Authorization presence

**Location**: `internal/server/middleware.go` — `requestLoggingMiddleware` (lines 26–41)

**Current state**

- Every request is logged at Info level with method, path, remote, optional query, and whether an Authorization header is “present”. For high traffic or health checks this can be noisy; the “auth present” flag is a coarse signal and may be redundant if 401s are already logged elsewhere.

**Proposed change**

- Either log at Debug when only tracing is needed, or remove the “auth present” attribute to reduce log size and avoid implying auth details. Keep method, path, and remote for access-style logging. If request logging is only for debugging, consider making it conditional (e.g. via log level or a config flag).

**Benefit**: Cleaner logs, less noise in production, and avoids logging security-related hints unnecessarily.

**Priority**: Low

---

## Suggested order

1. **Extract task-in-workspace validation** (proposal 4) — do first so that proposal 5 can use the same helper and handlers stay consistent.
2. **Simplify getTaskConversationHandler** (proposal 5) — then refactor the conversation handler and data source using the new task helper.
3. **Consolidate require store helpers** (proposal 1) — quick win, no behavioral change.
4. **Split executor RunTask** (proposal 3) — improves readability and testability of a critical path.
5. **Shared tool argument helpers** (proposal 6) — can be adopted incrementally per tool.
6. **Unify static serving** (proposal 2) and **middleware logging** (proposal 8) — small, independent cleanups.
7. **ptr helpers** (proposal 7) — only if a second consumer appears; otherwise leave as-is.

## Out of scope

- **TUI model size / Bubble Tea structure** — The TUI model is large but coherent (viewport, input, footer, messages). Splitting it would be a larger refactor and belongs in a dedicated TUI redesign or arch review.
- **Storage/blob interface design** — Current interfaces are clear; no smell identified for this proposal.
- **Agent processLoop** — Loop is readable and well-scoped; `processOneToolCall` is already extracted. No change proposed here.
