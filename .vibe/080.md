# Task 080: Streaming mode in BuildMax CLI agent

## Goal

Enable streaming of LLM response content so the user sees assistant text as it arrives in both print mode (`buildmax -p`) and TUI mode, instead of waiting for the full reply.

## Context

- **internal/llm**: `Client.ChatWithTools` uses the go-openai `CreateChatCompletion` API (non-streaming). The same library provides `CreateChatCompletionStream` for token-by-token delivery; responses include content deltas and, at stream end, optional tool_calls.
- **internal/agent**: `Agent` uses `LLMCaller.ChatWithTools(ctx, messages, tools) (content, toolCalls, err)`. `Process` and `ProcessAfterUserAppended` run the loop (LLM → tool calls if any → repeat) and return the final assistant reply. Session is appended only with complete messages.
- **internal/cmd/print.go**: `runPrintMode` calls `res.Agent.Process(ctx, res.Session, prompt)` then `fmt.Println(reply)` once the full reply is available.
- **internal/tui**: `runAgentAfterUserAppended` calls `ProcessAfterUserAppended` in a `tea.Cmd`; the view shows a carousel ("Waiting for reply…" and ".", "..", "...") until `agentDoneMsg`; then `handleAgentDone` refreshes the viewport from the session. Viewport content is built by `buildViewportContent(sess, version, width, busy, carouselDots)` in `format.go`.
- **Conventions**: AGENTS.md — all-Go stack; no new runtime dependencies. Session and persistence semantics (append full messages, persist after reply) stay unchanged.

## Streaming (this task)

For this task, **streaming** means:

1. When the LLM returns a turn, we receive **content deltas** (e.g. token or chunk) as they arrive, and **optionally** tool_calls at the end of the stream.
2. We **stream only assistant text content** to the user (print: write to stdout; TUI: show in viewport). Tool calls are not streamed; we still execute tools and re-call the LLM; the session still gets the full assistant message (content + tool_calls) at the end of each turn.
3. The **session** is updated only when a turn completes (full content and any tool_calls appended as today). No partial messages in session.

We are **not** implementing:

- Streaming tool call names/arguments.
- Changing worker or remote run behavior (worker runs `buildmax -p`; streaming there can be a follow-up).
- Changing session format or persistence.

## Deliverables

1. **internal/llm**
   - Add a streaming path: either a new method (e.g. `ChatWithToolsStream`) or an option on the existing request that accepts a callback or writer for content deltas. Use go-openai’s `CreateChatCompletionStream`; map streamed deltas to the callback; on stream end return full content and any tool_calls so the agent can continue the loop. Handle stream errors and cleanup (close stream).

2. **internal/agent**
   - Support streaming into the CLI without tying the agent package to TUI or os.Stdout. Options (pick one and specify in design): (a) `LLMCaller` interface extended with a streaming method that invokes a `func(delta string)`; or (b) `Process` / `ProcessAfterUserAppended` accept an optional `StreamSink` interface (e.g. `OnDelta(delta string)`). When a turn returns **content only** (no tool_calls), deltas are sent to the sink; when it returns tool_calls, sink is not used (or only content delta before tool_calls, if any). Session still receives the full assistant message at end of turn. Non-streaming callers pass nil or a no-op sink and behavior remains “wait for full reply”.

3. **internal/cmd (print mode)**
   - In `runPrintMode`, pass a stream sink that writes each delta to `os.Stdout` (and optionally flushes). Final reply is still returned from `Process` for logging/persistence; session persist and title generation unchanged.

4. **internal/tui**
   - Run the agent with a stream sink that sends **tea.Msg** (e.g. `streamDeltaMsg{Delta string}`) for each delta. Model holds a **streaming buffer** (current turn’s assistant text) and passes it to the viewport (e.g. `RefreshAndGotoBottom(..., streamingBuffer string)`). On each `streamDeltaMsg`, append delta to buffer and refresh viewport (and GotoBottom); keep showing “Waiting for reply…” in the input area. On `agentDoneMsg`, append the full assistant message to the session, clear the buffer, refresh, persist, and (if needed) trigger title generation as today. Carousel can be removed when streaming is active, or kept for the brief period before first delta.

5. **Tests**
   - Unit test: LLM client streaming path with a mock or test server that sends a few deltas then stream end (with or without tool_calls). Agent test: mock `LLMCaller` that supports streaming and assert deltas are passed to the sink in the right order; assert session has full message at end.

## Out of scope (for later)

- Streaming in worker/remote runs (`buildmax -p` in executor).
- Exposing streaming over the HTTP API or Portal.
- Streaming tool call names/arguments.
- Config flag to disable streaming (can be added later if needed).

## Acceptance

- [ ] **Print mode**: Running `buildmax -p "Say hello in 3 short sentences"` prints assistant text incrementally to stdout as tokens arrive (no single block at the end).
- [ ] **TUI mode**: After submitting a message, the viewport shows the assistant reply growing in real time (streaming buffer), then finalizes and persists when the turn completes; session file contains the full message.
- [ ] **Tool calls**: When the LLM returns tool_calls, the loop still executes tools and re-calls the LLM; streaming is used only for content (and optional content before tool_calls in the same turn); no regression in tool-call behavior.
- [ ] **Session**: Only full assistant messages (content + tool_calls when present) are appended to the session; no partial or duplicate messages.
- [ ] **Build and tests**: `go build ./...` and `go test ./...` pass; existing agent and LLM tests still pass; new tests cover streaming path and sink behavior.
