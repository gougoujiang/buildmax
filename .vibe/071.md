# Task 071: Side panel redesign

## Goal

Redesign the Portal left sidebar and **remove the Project concept**: tasks are directly associated with the workspace only. The sidebar provides: (1) **New Chat**, (2) a **Workspace** block (current name, switcher, “new workspace”), and (3) under it **Agents** and **Chats** (workspace tasks). New user registration continues to result in a **default workspace** (no regression).

## Context

- **Current sidebar** (`LeftSidebar.tsx`): Flat nav — Projects, Explore, Activity, Agents. No workspace section, no “new chat”, no task list.
- **Product direction**: Remove Project concept. Tasks belong to workspace only; no project list or project-scoped views in the Portal.
- **Workspace switcher**: Today in `TopBar` (select + “+ New”); callbacks from `AppShell`. Sidebar will also show workspace block with switcher and “+”.
- **Data**: `useWorkspace()` provides `workspaceTasks`, `projects` (to be removed or ignored for nav), and route. Agents remain; sidebar links to agents views.
- **Backend**: Task create/list already support workspace-only (optional `project_id`). `EnsureDefaultWorkspaceForUser` is called on GET /api/workspaces, so new users get a default workspace after signup+login. Keep this behavior.
- **Routing**: Task route becomes workspace-only: `#<workspaceId>/task/<taskId>` (no `projectId`). Remove project from `Route` and from task detail URL.

## In scope

1. **Remove Project concept from the Portal**
   - Tasks are workspace-scoped only. Create tasks without `project_id`; list tasks by workspace only (no project filter in UI).
   - **Route**: Task route is `#<workspaceId>/task/<taskId>` only (no `projectId`). Update `Route` type, `parseHash`, `buildHash`, and all task links to use this form.
   - **Sidebar**: No “Projects” link or project list. Workspace “home” (`workspace` route) shows a simple landing (e.g. prompt to start a chat and/or recent Chats) — not a project list. Remove or repurpose Projects page; remove Project-specific routes (e.g. `project` route) from nav and router where they are no longer needed.
   - **Types and data**: Prefer treating `Task` as workspace-only in the UI (ignore or stop displaying `projectId`). Remove project-based navigation and project list from WorkspaceRouter/App; keep only workspace and task (and agents, explore, activity as below).

2. **Sidebar structure (left panel)**
   - **New Chat**: Prominent action at the top. On click: create a new task via `createTask(workspaceId, { input }, token)` (no `project_id`), then navigate to `#<workspaceId>/task/<taskId>` (using returned task id if available, else Activity).
   - **Workspace section**: Current workspace name, workspace switcher (same as TopBar), and “+” for new workspace.
   - **Under the Workspace block**:
     - **Agents**: Link to agents view(s) (existing routes).
     - **Chats**: List of workspace tasks; each links to task detail `#<workspaceId>/task/<taskId>`. Bounded list (e.g. most recent N) with optional “See all” to Activity.
   - **Explore** and **Activity** remain in the sidebar (same routes). No Projects entry.

3. **Task detail and routing**
   - `WorkspaceRouter` and `getTaskForDetail` resolve task by `workspaceId` + `taskId` only (no `projectId`). Task detail page works for all workspace tasks.
   - Breadcrumbs and any task links use the new task route format.

4. **Props and data**
   - `LeftSidebar` receives workspace name, workspaces list, `onWorkspaceChange`, `onNewWorkspace`, `workspaceTasks`, `route`, `workspaceId` (from `AppShell`; parent passes `workspaceTasks` and callbacks into `AppShell`).

5. **UI and styling**
   - Reuse/add sidebar CSS; keep accessible.

6. **Default workspace for new users**
   - No regression: after new user registration (signup + login), the first GET /api/workspaces must still create/return a default workspace (existing `EnsureDefaultWorkspaceForUser` behavior). No backend change required unless we remove project-related code paths; default workspace logic stays.

## Out of scope

- Removing the Project entity or project APIs from the backend (backend continues to allow optional `project_id`; Portal simply does not use it).
- Moving or removing the workspace switcher from the TopBar (optional follow-up).
- Redesign of the main content area or TopBar layout beyond what’s needed for the new sidebar and task route.
- Pagination or infinite scroll for the Chats list (bounded list is enough).
- Agent creation/editing flows (only link to existing agents views).

## Acceptance criteria

- [ ] **Project removed from Portal**: No Projects nav or project list; tasks are created and listed by workspace only. Task route is `#<workspaceId>/task/<taskId>` (no projectId).
- [ ] Sidebar shows **New Chat** at the top; clicking it creates a new task (no project_id) and navigates to that task’s detail (or Activity if task id not available).
- [ ] Sidebar shows **Workspace** section with current workspace name, workspace switcher, and “+” for new workspace.
- [ ] Under the Workspace section, **Agents** and **Chats** are present; Chats lists workspace tasks with links to task detail; list bounded with optional “See all” to Activity.
- [ ] **Explore** and **Activity** remain reachable from the sidebar.
- [ ] Workspace “home” (`workspace` route) is a simple landing (no project list); task detail works for all workspace tasks via `#<workspaceId>/task/<taskId>`.
- [ ] **Default workspace**: New user registration (signup + login) still results in a default workspace (GET /api/workspaces continues to call EnsureDefaultWorkspaceForUser; no regression).
- [ ] Sidebar styling and accessibility preserved or improved; build and tests pass.
