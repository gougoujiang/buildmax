# Architecture Refactor Proposal — 2026-02-17

## Scope

**Analyzed**

- Paths / scope: `internal/`, `cmd/`
- Criteria: package boundaries, dependency direction, layering, and module coupling

## Summary

- **Opportunities**: 5
- **High impact**: 1
- **Overview**: The codebase has a clear composition root (cmd), good use of store interfaces by the server, and a well-defined agent loop. Main structural opportunities are: (1) unifying the executor’s store dependency instead of redefining a custom interface, (2) inverting the tools→agent coupling for the Task (sub-agent) tool, (3) clarifying config usage and optional injection for testability, (4) splitting the large server package by domain, and (5) extracting shared domain types so consumers don’t pull in persistence details.

---

## Opportunities

### 1. Unify executor store dependency

**Scope**: `internal/executor`, `internal/store`

**Current state**

- The executor defines its own `TaskStore` interface that duplicates a subset of `store.TaskStore` plus `store.ArtifactStore.CreateArtifactWithItem`. It still imports `store` for the `store.Task` type and passes the concrete `*store.Store` from cmd.
- This duplicates the persistence contract: method signatures live in both `store` (interfaces) and `executor` (local interface). Any change to task/artifact usage in the executor requires updating two places.

**Proposed change**

- Have the executor depend only on the existing `store` interfaces. Accept `store.TaskStore` and `store.ArtifactStore` (or a single composed interface in `store` that groups the methods the executor needs), and use `store.Task` from the store package.
- Remove the custom `executor.TaskStore` type. In cmd, keep passing `st` (which implements both); no new types in store are strictly required if the executor takes two interface parameters.

**Benefit**: Single definition of the persistence contract; clearer dependency direction (executor → store interfaces only); easier to mock in tests without redefining methods.

**Impact**: Medium

---

### 2. Invert tools–agent coupling for sub-agent execution

**Scope**: `internal/tools` (task tool), `internal/agent`

**Current state**

- The `tools` package imports `agent` and calls `agent.NewAgent` and `agent.SystemPrompt` inside the Task tool to run sub-agents. So “tools” (capabilities used by the agent) depend on “agent” (orchestrator) for implementation details.
- Ideal layering would be “agent depends on tools”; here, tools depend on agent for constructing and running sub-agents, which tightens coupling and makes it harder to test or swap sub-agent execution.

**Proposed change**

- Introduce a small interface for “run a sub-agent” (e.g. `SubAgentRunner` or `RunSubAgent(ctx, systemPrompt, tools, userMessage) (string, error)`), defined in the `agent` package. The Task tool accepts this runner as a dependency instead of constructing `agent.Agent` itself.
- Wire the runner in cmd/setup: pass an implementation that calls `agent.NewAgent(...).Process(...)` (or equivalent). The tools package then only depends on this interface, not on `agent.NewAgent` or `agent.SystemPrompt` directly.

**Benefit**: Clearer dependency direction; sub-agent execution becomes injectable and testable; tools no longer depend on agent’s constructors and options.

**Impact**: High

---

### 3. Inject config or path functions for testability

**Scope**: `internal/config`, `internal/server`, `internal/executor`, `internal/log`, `internal/llm`

**Current state**

- Many packages call `config.*` directly (e.g. `config.PersistentWorkspaceDir`, `config.SessionsDir`, `config.LoadLLM`, `config.MySQLDSN`). Config is a global-style dependency: no interfaces, no struct injection.
- This makes it harder to test server handlers or executor logic with alternate paths or DSNs without mutating process environment or patching.

**Proposed change**

- Option A: For new or refactored code, pass path functions or a small config struct into components (e.g. server `Config` already holds `SessionsDir`; extend as needed so handlers use `cfg.SessionsDir` instead of `config.SessionsDir()`). Leave existing `config` package as the default source called from cmd/bootstrap.
- Option B: Introduce a minimal `Config` interface or struct (e.g. `WorkspacePaths`, `DataPaths`) implemented by `config` and injected into server and executor. Tests can provide a test double.

**Benefit**: Easier unit and integration tests with controlled paths and settings; explicit dependencies instead of global config calls.

**Impact**: Medium

---

### 4. Split server package by domain

**Scope**: `internal/server`

**Current state**

- The server package holds routing, middleware, and all HTTP handlers in many files (server.go, auth.go, login.go, otp.go, workspaces.go, projects.go, tasks.go, artifacts.go, upload.go, files.go, session.go, response.go, cors.go). All live in a single package with no subpackages.
- Finding handler logic for a given API area requires scanning several files; the package is a single large “API layer” without clear subdomain boundaries.

**Proposed change**

- Keep `internal/server` as the HTTP entry: routing, `Config`, `Server`, middleware (auth, CORS, logging). Optionally group handlers by domain into subpackages (e.g. `server/workspace`, `server/artifact`, `server/auth`) or at least into clearly named files and a short doc listing which file handles which route group.
- If subpackages are used, each can expose a single `Register(mux, cfg)` or similar so server.go stays a thin composition of routes. Handlers that need store interfaces receive them via the shared `Config` (or a per-handler options struct).

**Benefit**: Clearer boundaries; easier to locate and change API behaviour by domain; possible to test or document each area separately.

**Impact**: Low

---

### 5. Extract shared domain types from store

**Scope**: `internal/store`, `internal/server`, `internal/executor`

**Current state**

- Domain entities (User, Workspace, Project, Task, Artifact, ArtifactItem) and their JSON/persistence details live in `internal/store`. Any package that needs these types (e.g. server for responses, executor for `store.Task`) must import `store`, which pulls in GORM and the full persistence layer.
- Consumers that only need to work with “task” or “workspace” as data shapes are forced to depend on the store package.

**Proposed change**

- Move pure domain structs (and their JSON tags) to a neutral package, e.g. `internal/model` or `internal/domain`. Store then depends on model and implements persistence for those types; server and executor depend on model for types and on store only for interfaces (e.g. `store.TaskStore` returning `*model.Task`). If desired, keep store-specific fields (e.g. GORM tags) in store via embedding or adapter types.
- Ensure snake_case and naming conventions (AGENTS.md) still apply to the shared types.

**Benefit**: Consumers that only need types don’t pull in GORM; clearer separation between “domain shape” and “persistence”; store remains the single place that knows how entities are stored.

**Impact**: Medium

---

## Suggested order

1. **Unify executor store dependency** — Small, localized change; removes interface duplication and sets a clear pattern for “depend on store interfaces only.”
2. **Inject config or path functions** — Can be done incrementally (e.g. server `Config` first); unblocks tests and makes later refactors easier.
3. **Extract shared domain types** — Do after executor/store is cleaned up so that `store.Task` and friends can become `model.Task` in one pass; then server/executor use model.
4. **Invert tools–agent coupling** — Improves layering and testability; can be done once the SubAgentRunner interface is agreed.
5. **Split server package by domain** — Optional and mostly organizational; can follow when adding or changing API surface.

## Out of scope

- **Portal/frontend architecture** — Out of scope for this analysis; focus is Go backend and CLI.
- **Full config abstraction** — Only incremental injection and testability are proposed; no wholesale replacement of the config package.
- **Moving Tool/LLMCaller to a shared package** — Would allow full “tools do not import agent”; deferred as a possible follow-up to opportunity 2.
