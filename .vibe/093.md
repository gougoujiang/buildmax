# Task 093: Tier 1 conversation entity and agentic API (no Tier 2 integration)

## Goal

Introduce a **conversation** entity and **conversation_message** table to trace multi-turn chats from various sources (portal, cron, webhook, Telegram). Expose new APIs under `/api/workspaces/{workspace_id}/conversations` and conversation messages so users can create conversations, load message history, and add follow-up questions. Implement backend handling in **agentic mode**: create conversation → run an LLM loop with a single demo tool (`get_current_date`), persisting every message (user, assistant, tool) to the DB. Portal "New Chat" uses this new conversation API. Chat/chat_run APIs remain unchanged; Tier 1 and Tier 2 integration is left for later.

## Context

- **Design:** [design/007-two-tier-agent.md](../design/007-two-tier-agent.md) (two-tier concept). This task implements Tier 1 as a **separate surface**: new entity and APIs, no change to existing chat/chat_run.
- **Existing code:** `internal/storage/entity` (Store, User, Workspace, Chat, ChatRun, AutoMigrate); `internal/model` (domain types); `internal/server` (workspace-scoped routes, auth); `internal/llm` (Client, ChatWithTools); `internal/agent` (Tier 2 agent loop — not used for this Tier 1 path). Entity IDs: `internal/util` prefixes (e.g. `c_`, `r_`); add conversation prefix (e.g. `cv_`) and conversation_message id (e.g. `cm_`).
- **Conventions:** AGENTS.md; JSON snake_case for API and persisted data; singular table names; entity ID prefix; tool output meaningful for LLM.

## Scope

### In scope

1. **Conversation entity** — New entity: unique `conversation_id`, workspace-scoped, stores **channel** (portal, cron, webhook, telegram) at creation time so we know where the conversation was initiated.
2. **conversation_message table** — Stores messages for each conversation turn: user input, LLM response, tool call results. Each row has **role**: `user`, `assistant`, `tool`. For **user** messages, store the **channel** the message came from. Order by created_at or sequence for history.
3. **New APIs**
   - **GET/POST** `/api/workspaces/{workspace_id}/conversations` — List conversations in workspace; create new conversation (body: `channel`, optional initial `message` or empty to just create).
   - **GET** `/api/workspaces/{workspace_id}/conversations/{conversation_id}/messages` — Load message history for a conversation.
   - **POST** `/api/workspaces/{workspace_id}/conversations/{conversation_id}/messages` — Add a follow-up user message; backend runs the Tier 1 LLM loop (with demo tool), saves all new messages (user, assistant, tool) to DB, returns the assistant reply or stream/result as agreed.
4. **Backend agentic handling** — On create conversation (with or without first message) or on add message: run an LLM loop. Tools: **only** `get_current_date` (demo). No workspace file tools. During the loop: persist each message to `conversation_message` (user, assistant, tool) so history is fully stored in DB.
5. **Portal "New Chat"** — Use the new conversation API: create conversation (channel=portal), then add first message or create with first message; display messages from GET messages; follow-up via POST messages. Chat/chat_run APIs are not used for this flow.
6. **Tests** — Unit tests for conversation and conversation_message store; handler tests for new routes (create conversation, list, get messages, add message with LLM loop); mock LLM in tests where needed.

### Out of scope

- Tier 2 integration: no spawning of chat runs from Tier 1; no change to existing chat or chat_run handlers.
- Cron/webhook/Telegram adapters (only portal uses the new API for now; channel is stored for future use).
- Multiple tools beyond `get_current_date` (add more tools in a later task).
- Streaming response for conversation API (can be added later; for now a simple request/response is enough).

## Deliverables

1. **Model and entity**
   - **Conversation:** `conversation_id` (prefixed, e.g. `cv_`), `workspace_id`, `channel` (string: portal/cron/webhook/telegram), `created_at`, `created_by` (user_id). Table name singular: `conversation`.
   - **ConversationMessage:** `conversation_message_id` (prefixed, e.g. `cm_`), `conversation_id`, `role` (user, assistant, tool), `content` (text), `channel` (nullable; set for role=user to indicate which channel the message came from), `created_at`. Optional: `tool_call_id` / `tool_name` for tool messages if needed for ordering. Table name singular: `conversation_message`.
   - Add `PrefixConversation` and `PrefixConversationMessage` in `internal/util/id.go`. Add types in `internal/model` and entity layer in `internal/storage/entity`; AutoMigrate the new tables.

2. **Store interface and implementation**
   - ConversationStore (or methods on Store): `CreateConversation(ctx, workspaceID, channel, createdBy) (*Conversation, error)`, `GetConversation(ctx, conversationID) (*Conversation, error)`, `ListConversationsByWorkspace(ctx, workspaceID, limit, offset) ([]Conversation, int, error)` (or equivalent), ensure conversation belongs to workspace for auth.
   - ConversationMessageStore: `AppendMessage(ctx, conversationID, role, content, channel *string) error` (or structured args), `ListMessages(ctx, conversationID) ([]ConversationMessage, error)` ordered by created_at. When running the LLM loop, append user message, then assistant message, then tool messages as they occur.

3. **Tier 1 agent loop (conversation)**
   - Dedicated loop (in `internal/server` or `internal/conversation`): load conversation messages, build LLM messages (user/assistant/tool), call LLM with one demo tool `get_current_date` (returns current date string). On each assistant turn and tool result, persist to `conversation_message`. Loop until no tool calls or max iterations. Use a simple system prompt (e.g. helpful assistant, can call get_current_date). No use of `internal/agent` Tier 2 tools or workspace.

4. **HTTP handlers**
   - **GET** `/api/workspaces/{workspace_id}/conversations` — Auth; return list of conversations (e.g. id, workspace_id, channel, created_at, created_by). Pagination optional.
   - **POST** `/api/workspaces/{workspace_id}/conversations` — Body: `{ "channel": "portal", "message": "optional first user message" }`. Create conversation; if `message` present, append user message (channel=portal) and run LLM loop, persist all messages; return conversation id and optionally first assistant reply.
   - **GET** `/api/workspaces/{workspace_id}/conversations/{conversation_id}/messages` — Auth; verify conversation in workspace; return ordered list of messages (role, content, channel if user, created_at).
   - **POST** `/api/workspaces/{workspace_id}/conversations/{conversation_id}/messages` — Body: `{ "content": "user follow-up text" }`. Append user message (channel from conversation or request); run LLM loop; persist all new messages; return assistant reply (e.g. last assistant content or summary).
   - Register routes in `server.go`; add ConversationStore and ConversationMessageStore (or Store that implements them) to Config.

5. **Portal**
   - "New Chat" flow: call POST `/api/workspaces/{id}/conversations` with channel=portal and the user's first message (or create then POST messages with first message). Navigate to a conversation view that uses GET messages and POST messages for follow-up. Adjust routing/UI so the new conversation API is used instead of createChat/createChatRun for this flow.

6. **Tests**
   - Entity/store: create conversation, append messages (user, assistant, tool), list messages; list conversations by workspace.
   - Handlers: create conversation (with/without first message), get messages, add message; mock LLM so no real API; assert messages saved.
   - `go build ./...` and `go test ./...` pass.
