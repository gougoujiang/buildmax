# Task 093: Two-tier agent — Phase 3 — Tier 1 LLM conversation for portal

Add a real Tier 1 conversation engine for portal: maintain conversation history and use an LLM to decide whether to reply only, ask for clarification, or spawn a Tier 2 task. Portal (and later IM) use this; cron/webhook do not.

**Design:** [design/007-two-tier-agent.md](../design/007-two-tier-agent.md) §8 Phase 3, §6.1 (Chat as conversation container), §7 (latency/cost mitigations). **Important:** §3.1 — Tier 1 agent differs from Tier 2: different tools (no workspace file access; delegate via spawn task), different system prompt (conversation/planning), no heavy workspace use; all workspace work is done by creating chat runs (Tier 2).

**Deliverables:**
- Conversation history storage for Tier 1: per-chat (or per-conversation) message history used only by Tier 1 engine (separate from Tier 2 agent session). Option A: extend Chat or add a small store (e.g. conversation_turn or messages table / blob).
- LLM-based conversation engine: implements `ConversationEngine`; loads Tier 1 history, calls LLM with tools or structured output to decide action (reply / clarify / spawn_task); if spawn_task, create ChatRun and return in `ConversationResult.TaskIDs`; append turn and response to history.
- Configuration: Tier 1 model (e.g. env or settings); optionally smaller/cheaper model than Tier 2.
- Portal flow: use LLM engine for portal channel instead of pass-through (Phase 2). Optional short-circuit: if request is explicitly “run task” or similar, allow skipping Tier 1 LLM and spawning run directly to reduce latency (per design §7).
- Tests: at least one test that Tier 1 can respond without spawning a run, and one that it spawns a run.

**Out of scope:** Telegram/IM adapter (same engine, different adapter); cron/webhook (Phase 4); task decomposition (Phase 5).
