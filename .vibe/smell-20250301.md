## Proposals

### 1. Unify path validation in artifact content handler with `blob.CleanRelPath`

**Location**: `internal/server/artifacts.go` (lines 138–141)

**Current state**

- The handler implements its own path check: `strings.Contains(pathParam, "..") || filepath.Clean(pathParam) != pathParam || strings.HasPrefix(pathParam, "/")`.
- `internal/storage/blob/relpath.go` already provides `CleanRelPath(p)` which normalizes and validates relative paths (no `..`, no leading `/`, backslash normalization) and returns a clear `ErrInvalidPath`.
- Two different validation styles for the same idea (no traversal, no absolute) increase maintenance and risk of drift.

**Proposed change**

- In the artifact content handler, replace the inline condition with: call `blob.CleanRelPath(pathParam)`; if it returns an error, respond with `http.StatusBadRequest, "invalid path"`.
- Dependency stays server → blob (already present). No new package.

**Benefit**: Single source of truth for “safe relative path”; consistent behavior and errors; less duplicated logic.

**Priority**: High

### 2. Reuse rel-path normalization in S3 list (blob package)

**Location**: `internal/storage/blob/s3_persist.go` (line 55)

**Current state**

- After `TrimPrefix`, the code does `rel = path.Clean(strings.ReplaceAll(rel, "\\", "/"))` and then skips `""` or `"."`.
- `relpath.go`’s `CleanRelPath` does the same normalize (Clean + ReplaceAll backslash) and validation. Here we only need normalization (the key segment is already under a prefix, so `..` is less of a concern but normalization is duplicated).

**Proposed change**

- Option A: Add an internal helper in blob, e.g. `normalizeRelSegment(s string) string` that does `path.Clean(strings.ReplaceAll(s, "\\", "/"))`, and use it in both `CleanRelPath` (internally) and in `s3_persist.go` when building the list. Option B: After TrimPrefix, call `CleanRelPath(rel)` and ignore the error by skipping invalid entries (treat invalid as skip). Prefer Option A to keep “normalize only” separate from “validate and return error.”
- Keep everything inside `internal/storage/blob`; no new package.

**Benefit**: One place for “normalize path segment”; fewer copy-paste bugs if logic changes.

**Priority**: Medium

### 3. Extract worker API HTTP helper in executor

**Location**: `internal/executor/worker_api.go` — `GetWorkerChatRun` (lines 35–56), `WorkerHTTPUpdater.UpdateRunStatus` (lines 95–118), `WorkerHTTPStreamSender.SendDelta` (similar pattern)

**Current state**

- Each place builds URL from BaseURL + path, sets `Authorization: Bearer <token>`, uses `cfg.Client` or `http.DefaultClient`, calls `Do`, then checks status. Same pattern repeated three times.

**Proposed change**

- Add a package-level helper in executor, e.g. `workerDo(ctx context.Context, cfg WorkerAPIClientConfig, method, pathSuffix string, body []byte) (*http.Response, error)` that: builds full URL, creates request, sets Bearer if token non-empty, uses cfg.Client or DefaultClient, runs Do, returns response (caller handles status and body).
- Use this helper in `GetWorkerChatRun`, `WorkerHTTPUpdater.UpdateRunStatus`, and `WorkerHTTPStreamSender.SendDelta`.
- No new package; keep in `internal/executor` to preserve clear dependency (executor → workerapi, entity).

**Benefit**: Single place for URL building, auth, and client default; easier to add timeouts or retries later.

**Priority**: High

### 4. Standardize argument parsing on `internal/util`; remove duplication in tools

**Location**: `internal/util/argparse.go` (ParseRequiredString, ParseOptionalString, ParseOptionalInt, …) and `internal/tools/args.go` (RequiredString, OptionalString, OptionalInt)

**Current state**

- Two parallel sets: util has `ParseRequiredString`, `ParseOptionalString`, `ParseOptionalInt`, `ParseOptionalBool`, `ToFloat64`; tools has `RequiredString`, `OptionalString`, `OptionalInt`. read_file and write_file use tools’ RequiredString/OptionalInt; bash, glob, grep use util’s Parse*.
- Same contract (trim, type coercion, required/optional, defaults). Duplication increases maintenance and the chance of behavioral divergence.

**Proposed change**

- Standardize on `internal/util`: keep and use `ParseRequiredString`, `ParseOptionalString`, `ParseOptionalInt`, `ParseOptionalBool`, `ToFloat64` as the single source.
- Migrate `read_file.go` and `write_file.go` to use `util.ParseRequiredString` and `util.ParseOptionalInt` (and `util.ParseOptionalString` where needed) instead of `RequiredString` and `OptionalInt`.
- Remove from `internal/tools/args.go`: `RequiredString`, `OptionalString`, `OptionalInt` (or leave a thin wrapper that delegates to util if you want to keep the tools API surface; prefer direct util use for clarity).
- Dependency: tools → util only; no new package.

**Benefit**: One place for argument parsing; clear dependency; consistent behavior and errors across all tools.

**Priority**: High

### 5. Add server helper for limit/offset query parsing

**Location**: `internal/server/chats.go` (lines 107–116) and `internal/server/conversation_handlers.go` (lines 84–94)

**Current state**

- Both parse `limit` (default 50, with max 200 vs 100) and `offset` (default 0, ≥ 0) from query with the same pattern: strconv.Atoi, bounds check, default.

**Proposed change**

- Add an internal helper in server, e.g. `parseLimitOffset(q url.Values, limitKey, offsetKey string, defaultLimit, maxLimit int) (limit, offset int)`, and use it in both handlers with the appropriate max (200 for chats, 100 for conversations).
- Keep in `internal/server`; no new package.

**Benefit**: One place for pagination query parsing; consistent defaults and bounds; less duplication.

**Priority**: Medium

### 7. Consider shared path/validation package only if more callers appear

**Location**: `internal/util/workspace.go` (ResolvePath — root-scoped resolution + “path outside allowed root”) vs `internal/storage/blob/relpath.go` (CleanRelPath — relative-path normalization and validation)

**Current state**

- ResolvePath is for tool use (resolve under a workspace root). CleanRelPath is for storage keys and server path params. Different semantics; not wrong to have both.
- If more handlers or packages need “safe path from user input,” they could all use `blob.CleanRelPath` (server and blob already do). No need to merge ResolvePath and CleanRelPath into one package unless a third “path” abstraction emerges.

**Proposed change**

- No change now. If you later add more path-validation call sites outside blob, consider a small `internal/pathutil` that wraps or re-exports a single “safe relative path” API and is used by server and blob to avoid server → blob only for path logic. For current scope, reusing `blob.CleanRelPath` in the artifact handler (Proposal 1) is enough.

**Benefit**: Clear dependency; avoid over-abstracting until needed.

**Priority**: Low
