# Smell Proposal - 2026-02-24 (Long Args/Returns in internal/)

## Scope

**Analyzed**

- Paths / packages: `internal/` (backend)
- Criteria: Long function argument lists and return values; opportunities to introduce data structures/types to simplify signatures and improve maintainability.

## Summary

- **Proposals**: 8
- **High priority**: 2
- **Overview**: Several functions in `internal/execution`, `internal/infra/objectstore`, `internal/execution/worker_api`, and `internal/interface/tui` take 5+ parameters or return multiple values. Introducing small, focused structs (run scope, client config, viewport opts, blob key scope) would reduce mistakes, make call sites clearer, and make future changes easier.

---

## Proposals

### 1. Introduce RunTaskInput (or RunContext) for executor.RunTask

**Location**: `internal/execution/runtime/runtime.go` — `RunTask` (line 36)

**Current state**

- `RunTask` has 10 parameters: `ctx`, `chat`, `run`, `sessionID`, `paths`, `persist`, `artifactStorage`, `updater`, `streamSender`.
- Call site in `workercmd/run.go` passes 9 arguments in one long line; adding or reordering parameters is error-prone.
- The same logical groups (identity: chat+run+sessionID; storage: persist+artifactStorage; paths; updater; streamSender) are not named at the call site.

**Proposed change**

- Define a struct, e.g. `RunTaskInput`, with fields: `Chat`, `Run`, `SessionID`, `Paths`, `Persist`, `ArtifactStorage`, `Updater`, `StreamSender` (ctx stays as first arg).
- Change signature to `RunTask(ctx context.Context, input RunTaskInput) error`.
- Update the single call site in `workercmd/run.go` to build and pass the struct.
- Optionally, introduce a smaller `RunIdentity` or use `chat`+`run`+`sessionID` as a group if you want to pass that through to helpers; the main win is the single input struct for `RunTask`.

**Benefit**: Single place to extend run inputs; call site is self-documenting; fewer positional mistakes.

**Priority**: High

### 2. Use PatchChatRunRequest (or status struct) in ChatRunUpdater interface

**Location**: `internal/execution/runtime/runtime.go` — `ChatRunUpdater.UpdateRunStatus` (line 31); `internal/execution/worker_api.go` — `WorkerHTTPUpdater.UpdateRunStatus` (line 80)

**Current state**

- `UpdateRunStatus` takes 9 parameters: `ctx`, `chatRunID`, `status`, `startedAt`, `endedAt`, `output`, `errMsg`, `sessionID`, `artifact`.
- Call sites in `executor.go` (reportRunFailure, reportRunSuccess) and `workercmd/run.go` build these arguments individually; the worker API already uses `workerapi.PatchChatRunRequest` for the HTTP body.
- The interface mirrors the HTTP shape with many optional pointers, which is hard to read and easy to misorder.

**Proposed change**

- Change the interface to accept a single payload: e.g. `UpdateRunStatus(ctx context.Context, chatRunID string, req *workerapi.PatchChatRunRequest) error`.
- `PatchChatRunRequest` already has Status, SessionID, StartedAt, EndedAt, Output, ErrorMessage, Artifact. Callers build one struct and pass it; `WorkerHTTPUpdater.UpdateRunStatus` can marshal it as today.
- Update all call sites to build `PatchChatRunRequest` and pass it.

**Benefit**: One clear contract; no argument order mistakes; adding a new PATCH field only touches the type and the builder, not every call site.

**Priority**: High

### 3. Introduce WorkerAPIClientConfig for GetWorkerChatRun

**Location**: `internal/execution/worker_api.go` — `GetWorkerChatRun` (line 29)

**Current state**

- `GetWorkerChatRun(ctx, baseURL, token, chatRunID string, client *http.Client)` has five parameters; baseURL, token, and client are always used together and are already grouped in `WorkerHTTPUpdater` and `WorkerHTTPStreamSender` as struct fields.
- Call site in `workercmd/run.go` passes config values that come from the same env/config source.

**Proposed change**

- Define a small struct, e.g. `WorkerAPIClientConfig`, with `BaseURL`, `Token`, `Client *http.Client`.
- Change to `GetWorkerChatRun(ctx context.Context, cfg WorkerAPIClientConfig, chatRunID string) (*entity.ChatRun, *entity.Chat, error)`.
- Worker and tests construct the config once and pass it; future options (timeouts, retries) go on the config.

**Benefit**: Clearer call sites; single place for client configuration; consistent with existing updater/sender structs.

**Priority**: Medium

### 4. Introduce RunScope (or ChatRunScope) for executor and blob keys

**Location**: `internal/execution/runtime/runtime.go` — `reportRunSuccess`, `uploadChatRunArtifacts`, `uploadRunArtifactsToStorage`, `uploadChatGlobal`; `internal/execution/runtime/paths.go` — `WorkspacePaths` methods; `internal/infra/objectstore/keys.go` — key helpers

**Current state**

- Many functions take `workspaceID`, `chatID`, `chatRunID` (and sometimes `prefix`) as three or four separate string arguments, repeated in every signature.
- In executor: `reportRunSuccess`, `uploadChatRunArtifacts`, `uploadRunArtifactsToStorage`, `uploadChatGlobal` all take these three IDs; paths interface methods take (workspaceID, chatID, chatRunID).
- In blob/keys: `ArtifactFileKey`, `ChatRunGlobalObjectKey`, `ChatRunArtifactsObjectKey` take (prefix, workspaceID, chatID, chatRunID, relPath). Same tuple appears in multiple blob APIs.

**Proposed change**

- Introduce a small value type, e.g. `RunScope` in executor (or a shared type in model if used across packages) with `WorkspaceID`, `ChatID`, `ChatRunID string`.
- For blob keys, either the same three IDs or a `BlobKeyScope` with optional `Prefix` and the three IDs.
- Refactor executor helpers to accept `RunScope` (and paths) instead of three strings; refactor blob key functions to accept scope + relPath (and prefix where needed).
- WorkspacePaths can keep current signatures to avoid a large change, or add methods that take `RunScope` and delegate to the existing (workspaceID, chatID, chatRunID) methods.

**Benefit**: Fewer parameters per function; one place to add validation or logging for “run scope”; consistent naming at call sites.

**Priority**: Medium

### 5. Introduce ViewportContentOpts for buildViewportContent

**Location**: `internal/interface/tui/format.go` — `buildViewportContent` (line 127)

**Current state**

- `buildViewportContent(sess *session.Session, version string, width int, busy bool, carouselDots int, streamingTail string)` has six parameters; display/UI options (version, width, busy, carouselDots, streamingTail) are a loose list.
- Call sites (e.g. from model) have to remember order; adding a new display option would add another parameter.

**Proposed change**

- Define a struct, e.g. `ViewportContentOpts`, with `Version`, `Width`, `Busy`, `CarouselDots`, `StreamingTail` (and keep `Session` as a separate first arg if it’s the primary data).
- Signature becomes `buildViewportContent(sess *session.Session, opts ViewportContentOpts) string`.
- Callers build the opts struct; future options (e.g. theme, max lines) go in the struct.

**Benefit**: Readable call sites; easy to add or reorder display options without changing the function signature.

**Priority**: Low

### 6. Introduce LogConfig for log.Init

**Location**: `internal/infra/log/log.go` — `Init` (line 38)

**Current state**

- `Init(logsDir, level string, filename string, alsoStdout bool)` has four parameters; the last three are configuration that could be grouped.
- Call sites (CLI, server, worker) pass values from config; adding a new option (e.g. max size) would add another parameter.

**Proposed change**

- Define a struct, e.g. `LogConfig`, with `LogsDir`, `Level`, `Filename`, `AlsoStdout` (and optional future fields).
- Change to `Init(cfg LogConfig)` or `Init(logsDir string, cfg LogConfig)` if you want to keep logsDir separate for backward compatibility.
- Update all call sites to pass the config struct.

**Benefit**: Single place for log configuration; clearer and easier to extend.

**Priority**: Low

### 7. Group blob key prefix + run identifiers in storage/blob

**Location**: `internal/infra/objectstore/keys.go` — `ArtifactFileKey`, `ChatBuildmaxObjectKey`, `ChatRunGlobalObjectKey`, `ChatRunArtifactsObjectKey` (lines 21–58)

**Current state**

- Each function takes `(prefix, workspaceID, chatID, chatRunID, relPath string)` (five string args). The first four are always the “scope” for the key; only relPath varies.
- Duplication across four similar functions; adding a new key type repeats the same signature.

**Proposed change**

- Introduce a type, e.g. `ObjectKeyScope`, with `Prefix`, `WorkspaceID`, `ChatID`, `ChatRunID string` (or without Prefix if it’s always the same and passed at storage init).
- Signatures become `ArtifactFileKey(scope ObjectKeyScope, relPath string) (string, error)` and similarly for the others.
- Callers that have (prefix, workspaceID, chatID, chatRunID) build one scope value; internal key helpers use scope fields.
- If PersistObjectKey and ArtifactResultKey don’t use chatRunID, they can keep current args or take a smaller scope type.

**Benefit**: Shorter, clearer signatures; one place to change if key layout changes; fewer mistakes when adding new key helpers.

**Priority**: Medium

---

### 8. Group reportRunSuccess / upload parameters with a result or run-output struct

**Location**: `internal/execution/runtime/runtime.go` — `reportRunSuccess` (line 197), and related upload helpers

**Current state**

- `reportRunSuccess(ctx, chat, run, endTime, outputStr, runArtifactsDir, output []byte, artifactStorage, updater)` has nine parameters; it combines “run identity,” “run result” (endTime, outputStr, output, runArtifactsDir), and “dependencies” (artifactStorage, updater).
- Similar grouping issues in the upload helpers that take (dir, workspaceID, chatID, chatRunID, storage).

**Proposed change**

- After introducing RunScope (proposal 4), consider a `RunResult` (or similar) with `EndTime`, `OutputStr`, `Output []byte`, `RunArtifactsDir` (and optionally RunScope if not passed separately).
- `reportRunSuccess` could become `reportRunSuccess(ctx context.Context, scope RunScope, result RunResult, artifactStorage blob.ArtifactStorage, updater ChatRunUpdater) error`.
- This refactor is most useful after RunScope and the UpdateRunStatus payload (proposal 2) are in place, so that the “status update” data is built in one place.

**Benefit**: Clear separation of “what happened in the run” vs “where to persist” and “how to notify”; easier to test and to add new result fields.

**Priority**: Medium (after 2 and 4)

## Suggested order

1. **ChatRunUpdater with PatchChatRunRequest (proposal 2)** — Reduces interface and call-site complexity first; no new domain types.
2. **RunTaskInput for RunTask (proposal 1)** — Single big win for the main executor entry point.
3. **RunScope / ChatRunScope (proposal 4)** — Then refactor executor helpers and optionally paths/blob to use it.
4. **Blob ObjectKeyScope (proposal 7)** — Complements RunScope for blob keys; can be done in the same pass as 4 if desired.
5. **reportRunSuccess + RunResult (proposal 8)** — After 2 and 4 are done.
6. **WorkerAPIClientConfig (proposal 3)** — Small, independent improvement.
7. **ViewportContentOpts (proposal 5)** and **LogConfig (proposal 6)** — Lower impact; do when touching TUI or log init.

## Out of scope

- Changing `WorkspacePaths` interface to take a struct (e.g. RunScope) in all methods — would touch many implementors and call sites; can be done incrementally after RunScope exists.
- Agent `Process` / `ProcessAfterUserAppended` return `(reply string, stats RunStats, err error)` — three return values are acceptable and common in Go; no change proposed unless you want a single result struct for future fields.
- Server `Config` struct — already uses a large config struct; no change.
