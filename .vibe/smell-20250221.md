# Smell Proposal — Portal

## Scope

**Analyzed**

- Paths / packages: `portal/` (React + Vite + TypeScript frontend)
- Criteria: All `src/` components, pages, hooks, lib, contexts, and layout

## Summary

- **Proposals**: 10
- **High priority**: 2
- **Overview**: Main findings are duplicated logic (upload handlers, error normalization, API fetch pattern), a few oversized or prop-heavy components, and silent error handling in one hook. The codebase is generally well-structured (e.g. CreateEntityModal reuse); refactors are tactical and local.

---

## Proposals

### 1. Extract shared upload logic in FilesPanel

**Location**: `portal/src/components/FilesPanel.tsx` — `handleUpload`, `handleFolderUpload` (lines ~65–122)

**Current state**

- `handleUpload` (file input) and `handleFolderUpload` (folder input) are almost identical: validate token, set uploading/msg, call `uploadFiles`, set success/error msg, `fetchTree()`, clear input ref in finally.
- Only differences: file limit (10 for files, none for folder), building `paths` from `webkitRelativePath` for folder, and which ref is cleared.
- Duplication makes it easy for one path to diverge (e.g. error message or cleanup) and increases maintenance.

**Proposed change**

- Extract a single async function e.g. `doUpload(files: File[], paths?: string[], options?: { maxFiles?: number })` that performs validation (maxFiles, token), sets uploading/msg state, calls `uploadFiles(workspaceId, files, token, paths)`, then updates msg and calls `fetchTree()`; returns or throws so callers can handle ref clearing.
- `handleUpload` and `handleFolderUpload` become thin wrappers: get `files` from the event, call `doUpload` with appropriate args (and `maxFiles: 10` for files), clear the corresponding ref in finally.

**Benefit**: Single place for upload behavior; easier to fix bugs and add features (e.g. progress). Readability and maintainability.

**Priority**: Medium

### 2. Introduce API request helper to remove repetitive fetch pattern

**Location**: `portal/src/lib/api/index.ts` — all `fetch`-based functions

**Current state**

- Every exported function repeats: `getApiBase()`, `fetch(...)`, `checkUnauthorized(res)`, `await throwIfNotOk(res)`, then `res.json()` or `res.text()`. Optional handling (e.g. 404, 409) is ad hoc.
- This duplicates ~5 lines per endpoint and scatters auth/error handling; adding a new header or retry would require touching many call sites.

**Proposed change**

- Add in `client.ts` (or a small `request.ts`) helpers such as:
  - `requestJson<T>(url: string, init?: RequestInit): Promise<T>` — GET by default; runs fetch, checkUnauthorized, throwIfNotOk, returns `res.json()`.
  - `requestText(url: string, init?: RequestInit): Promise<string>` for text responses.
  - Optionally `requestWithHandlers` or overloads for 404/409 if you want to keep those in one place.
- Refactor each API function to use these helpers (pass `${getApiBase()}/api/...`, method, headers, body). Keep existing function signatures so callers are unchanged.

**Benefit**: Less duplication; central place for auth and error handling; easier to add logging or retries later. Maintainability.

**Priority**: High

### 3. Remove redundant initial-state effect in AuthContext

**Location**: `portal/src/contexts/AuthContext.tsx` — `useState(loadStored)` and `useEffect(() => { setState(loadStored()) }, [])` (lines 40, 54–57)

**Current state**

- State is initialized with `useState<AuthState>(loadStored)` so the first render already has stored token/user.
- A `useEffect` with empty deps then runs and calls `setState(loadStored())` again. That causes a second render with the same data and no observable behavior change; if `loadStored()` were ever to do something side-effectful or return a new reference, it could be confusing.

**Proposed change**

- Remove the `useEffect` that syncs from storage on mount. Rely on `useState(loadStored)` as the single source of initial state.
- If the effect was intended for cross-tab sync (e.g. login in another tab), add a comment or implement a dedicated storage-event listener instead of a one-time setState.

**Benefit**: Clearer intent, one less render on mount. Readability and consistency.

**Priority**: Low

### 4. Extract chat-run polling from TaskDetail

**Location**: `portal/src/pages/TaskDetail.tsx` — `handleFollowUpSubmit` and inline `setInterval` (lines ~49–79)

**Current state**

- After `createChatRun`, the code starts a `setInterval` that polls `getChats`, finds the current chat, and when status is SUCCEEDED/FAILED clears the interval and calls `onRefetch` and `refetchSession`. Polling logic lives inside the submit handler and is hard to unit-test or reuse.
- Mixing “start run” and “poll until terminal” in one handler also makes the component harder to follow.

**Proposed change**

- Extract a hook e.g. `useChatRunPoll(workspaceId: string, chatId: string, token: string | null, options: { onTerminal: () => void; enabled?: boolean })` that:
  - Exposes `startPolling()` and optionally `stopPolling()`.
  - When polling, uses the same interval + getChats + terminal-status check and calls `onTerminal()` when done.
- Or, at minimum, extract a pure async function `pollChatUntilTerminal(workspaceId, chatId, token, { intervalMs, onTerminal })` and call it from the submit handler. TaskDetail would then only set loading/error and call `onRefetch`/`refetchSession` in `onTerminal`.

**Benefit**: Testability of polling logic; clearer separation between “submit” and “wait for result”. Maintainability.

**Priority**: Medium

### 5. Reduce tab repetition in NewChat with a small Tab component or config

**Location**: `portal/src/pages/NewChat.tsx` — tab list and three tab panels (lines ~68–198)

**Current state**

- Three tabs (Chats, Artifacts, Files) repeat the same structure: a button with `role="tab"`, `aria-selected`, `aria-controls`, `id`, and conditional class; then a tabpanel with `role="tabpanel"`, `hidden={activeTab !== "…"}`, and conditional content render.
- Copy-paste makes it easy to miss accessibility or class updates when adding a fourth tab.

**Proposed change**

- Option A: Introduce a minimal `Tabs` component (or use a shared pattern) that takes `tabs: { id: NewChatTab; label: string }[]` and `children` or `renderPanel(tabId)`, and renders the tablist + tabpanels with consistent ids and aria attributes.
- Option B: Keep the current structure but drive it from a config array (e.g. `const TABS = [{ id: "chats", label: "Chats" }, ...]`) and map over it for both the tab buttons and the panels, so adding a tab is one config entry and one panel branch.

**Benefit**: Consistency, fewer mistakes when changing tabs, easier to add new tabs. Readability and maintainability.

**Priority**: Low

### 6. Surface error (and optionally loading) in useAsyncList

**Location**: `portal/src/hooks/useAsyncList.ts` — catch block (line 25) and return type

**Current state**

- On fetch failure, the hook does `setData([])` and never sets an error. Callers (e.g. `useWorkspaceChats`) cannot show “Failed to load chats” or retry; they only see an empty list.
- The hook also does not expose loading state, so UIs that use it cannot show a loading indicator without adding their own.

**Proposed change**

- Add `error: string | null` (and optionally `loading: boolean`) to the return type. In the catch block, set error (e.g. via a small `getErrorMessage(err, "Request failed")`) instead of or in addition to clearing data.
- Optionally accept `errorMessage?: (err: unknown) => string` in options so callers can customize. Document that when `enabled` is false, error is cleared.
- If loading is added, set it true at start of runFetch and false in finally (and when disabled).

**Benefit**: Callers can show errors and loading; behavior aligns with useFetch. Consistency and UX.

**Priority**: High

### 7. Reduce Sidebar prop surface with a config object or sub-components

**Location**: `portal/src/layout/Sidebar.tsx` — `SidebarProps` and single large JSX return

**Current state**

- Sidebar accepts nine props: workspaceId, route, currentWorkspace, workspaces, onWorkspaceChange, onNewWorkspace, workspaceChats, user, onLogout. The component is one large return with header, nav, workspace block, footer, and modal.
- Many props are only used in one section; the list is long and refactoring (e.g. adding a new section) requires touching the same interface.

**Proposed change**

- Option A: Group related props into a single object, e.g. `workspace: { current, list, onChange, onNew? }`, `user: { ...user, onLogout }`, `nav: { route, workspaceId, chats }`, and pass those. Call sites (Layout) can build the objects once.
- Option B: Extract presentational sub-components (e.g. SidebarHeader, SidebarNav, SidebarWorkspaceSwitcher, SidebarUserMenu) that receive only the props they need; Sidebar composes them and passes down only what each needs. This reduces the “flat” prop list and clarifies structure.

**Benefit**: Clearer API and structure; easier to test or reuse sections. Maintainability.

**Priority**: Medium

### 8. Add a small classNames / cn helper for conditional CSS classes

**Location**: Multiple — `Sidebar.tsx`, `NewChat.tsx`, `ArtifactContentModal.tsx`, `FilesPanel.tsx`

**Current state**

- Conditional classes are built with string concatenation, e.g. `"sidebar__nav-item" + (route.name === "newChat" ? " sidebar__nav-item--active" : "")` or `"page-explore__upload-msg" + (uploadMsg.isError ? " page-explore__upload-msg--error" : "")`. This pattern is repeated in many components and is a bit noisy.

**Proposed change**

- Add a tiny helper in `lib/` or `utils/`, e.g. `function cn(...classes: (string | boolean | undefined)[]): string` that filters falsy values and joins with space. Use it like `cn("sidebar__nav-item", route.name === "newChat" && "sidebar__nav-item--active")`.
- Replace existing concatenation patterns with `cn(...)` where it improves readability. No need to change every single class; focus on conditional or multi-part class names.

**Benefit**: Readability; one place to extend later (e.g. for Tailwind-style merging). Consistency.

**Priority**: Low

### 9. Centralize error-message normalization

**Location**: `portal/src/components/FilesPanel.tsx`, `portal/src/pages/AgentList.tsx`, `NewChat.tsx`, `App.tsx`, `TaskDetail.tsx`, `WorkspaceHome.tsx`, `SignUp.tsx`, `Login.tsx` — multiple catch blocks

**Current state**

- The pattern `err instanceof Error ? err.message : "Fallback message"` appears in many catch blocks across the app. useFetch already has a default `errorMessage` that does the same. Repeating it in every handler duplicates logic and can lead to inconsistent fallbacks.

**Proposed change**

- Add a small helper in `lib/` (e.g. `lib/errorMessage.ts`): `export function getErrorMessage(err: unknown, fallback: string): string` returning `err instanceof Error ? err.message : fallback`.
- Use it in catch blocks: `setRunError(getErrorMessage(err, "Failed to start chat"))`. Keep useFetch’s default using the same helper so behavior is consistent.

**Benefit**: Single place for “how we turn unknown errors into user-facing strings”; consistent fallbacks. Maintainability and consistency.

**Priority**: Medium

### 10. Align Agent type with optional instructions

**Location**: `portal/src/lib/types.ts` — `Agent.instructions`; `portal/src/lib/api/mappers.ts` — `apiAgentToAgent`; `CreateAgentModal` — `onCreate` payload

**Current state**

- `Agent` in lib/types has `instructions: string`. The API DTO and CreateAgentModal use optional `instructions`; the mapper assigns `api.instructions` which could be undefined if the API omits it. This can cause type/runtime mismatches (e.g. undefined passed where string is expected).

**Proposed change**

- Make `Agent.instructions` optional in lib/types: `instructions?: string`. Ensure mapper uses `instructions: api.instructions ?? ""` only if you want to keep a string for display, or `instructions: api.instructions` and type as `string | undefined`. Update any consumer that assumes `instructions` is always a string to handle undefined.

**Benefit**: Type safety and consistency with API and create flow. Prevents subtle bugs when API returns partial agent.

**Priority**: Low

## Suggested order

1. **Centralize error-message normalization** (Proposal 9) — small change, unblocks consistent use in useAsyncList and elsewhere.
2. **API request helper** (Proposal 2) — reduces duplication and clarifies client layer.
3. **useAsyncList error/loading** (Proposal 6) — improves UX and consistency with useFetch.
4. **Extract upload logic in FilesPanel** (Proposal 1) — local to one component, clear win.
5. **AuthContext effect** (Proposal 3) — trivial removal.
6. **Agent type** (Proposal 10) — quick type fix.
7. **cn() helper** (Proposal 8) — adopt incrementally.
8. **TaskDetail polling** (Proposal 4) — improves testability.
9. **NewChat tabs** (Proposal 5) — refactor when touching that page.
10. **Sidebar props** (Proposal 7) — optional structural improvement.

## Out of scope

- **Full migration to Tailwind or CSS-in-JS**: Treated as a separate project; this proposal stays within current CSS approach.
- **E2E or component tests**: Not a refactor of logic; add tests when implementing the above if desired.
- **Portal backend (Go)**: Scope limited to `portal/` frontend only.
