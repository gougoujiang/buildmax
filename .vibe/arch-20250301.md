# Architecture Refactor Proposal — 2025-03-01

## Scope

**Analyzed**

- Paths: `internal/agent`, `internal/conversation`, and their use of LLM caller abstractions
- Focus: Consolidate duplicated `LLMCaller` / `StreamLLMCaller` and `StreamSink` definitions so both agent and conversation use a single shared contract from a common place.

## Summary

- **Opportunities**: 1 (consolidate LLM caller and stream sink interfaces)
- **High impact**: 1
- **Overview**: Both `internal/agent` and `internal/conversation` define their own LLM-caller abstractions and stream sinks. The method signatures are identical; only the interface boundaries differ (agent has one interface with both methods, conversation splits into `LLMCaller` and `StreamLLMCaller`). `*llm.Client` already implements both. Consolidating into a single interface (and optional shared `StreamSink`) in a common package reduces duplication, keeps server wiring simple (one caller for both stream and non-stream), and makes reuse by tools and future callers straightforward.

---

## Opportunities

### 1. Consolidate LLMCaller and StreamSink into a common package

**Scope**: `internal/agent`, `internal/conversation`, `internal/llm`, `internal/server`, `internal/tools`, `cmd/buildmax`, `cmd/buildmax-server`

**Current state**

- **internal/agent** defines:
  - `LLMCaller`: `ChatWithTools` + `ChatWithToolsStream` (one interface).
  - `StreamSink`: `OnDelta(delta string)`.
  - Used by `Agent`, `defaultSubAgentRunner`, and (indirectly) by tools that take `agent.LLMCaller` (e.g. WebFetch, Task/SubAgentRunner).
- **internal/conversation** defines:
  - `LLMCaller`: only `ChatWithTools`.
  - `StreamLLMCaller`: only `ChatWithToolsStream`.
  - `StreamSink`: `OnDelta(delta string)` (same as agent’s).
  - `RunLoop` takes `LLMCaller`; `RunLoopStream` takes `StreamLLMCaller` and `StreamSink`.
- **internal/server** holds two config fields: `ConversationLLMCaller conversation.LLMCaller` and `ConversationStreamLLMCaller conversation.StreamLLMCaller`, both set to the same `*llm.Client` in `servercmd`.
- **internal/llm**: `*Client` implements `ChatWithTools` and `ChatWithToolsStream` with the same signatures as both agent and conversation. It does not reference agent or conversation.
- **internal/tools**: WebFetch uses `agent.LLMCaller`; Task uses `agent.NewDefaultSubAgentRunner(caller)`, which takes `agent.LLMCaller`.

So today we have:
- Two interface “families” (agent’s single LLMCaller vs conversation’s LLMCaller + StreamLLMCaller) with identical method shapes.
- Two identical `StreamSink` definitions (agent, conversation).
- Server and conversation explicitly split “stream” vs “non-stream” callers even though the same concrete type implements both.

**Proposed change**

1. **Introduce a single LLM-caller contract in one place**

   - **Option A (preferred): put interfaces in `internal/llm`**
     - In `internal/llm` (e.g. in a new file `caller.go` or in `client.go`), define:
       - `LLMCaller` interface with `ChatWithTools` and `ChatWithToolsStream` (same signatures as current `agent.LLMCaller`).
       - `StreamSink` interface with `OnDelta(delta string)`.
     - `*Client` already implements `LLMCaller`; no change to `internal/llm` implementation code beyond adding the interface type and possibly a doc comment that `*Client` implements it.
     - No new package; `internal/llm` already holds message/tool types used by these methods, so the interface naturally lives next to the types it uses.
   - **Option B: new package `internal/llmcaller`**
     - Create `internal/llmcaller` that imports only `internal/llm` and defines `LLMCaller` and `StreamSink` using `llm.Message`, `llm.ToolDef`, etc.
     - Agent, conversation, server, and tools would depend on `internal/llmcaller` for the interface; `*llm.Client` would satisfy `llmcaller.LLMCaller` implicitly (no change in llm).
     - Keeps “concrete client” and “caller contract” in separate packages if you prefer that separation.

2. **Migrate consumers to the shared contract**

   - **internal/agent**: Remove `agent.LLMCaller` and `agent.StreamSink`. Use `llm.LLMCaller` and `llm.StreamSink` (or `llmcaller.*` if Option B). Update `Agent`, `processConfig`, `WithStreamSink`, and `defaultSubAgentRunner` to use the shared types. Tests: update mocks to implement the shared interface (or keep test-only mocks in agent_test that implement the same methods).
   - **internal/conversation**: Remove `conversation.LLMCaller`, `conversation.StreamLLMCaller`, and `conversation.StreamSink`. Use the shared `LLMCaller` and `StreamSink` from the chosen package. Change API to:
     - `RunLoop(..., caller llm.LLMCaller, ...)` — call `caller.ChatWithTools` as today.
     - `RunLoopStream(..., caller llm.LLMCaller, ..., sink llm.StreamSink)` — call `caller.ChatWithToolsStream` with a wrapper that forwards to `sink.OnDelta`. So a single caller type is used for both entry points.
   - **internal/server**: Replace `ConversationLLMCaller` and `ConversationStreamLLMCaller` with a single field, e.g. `ConversationLLMCaller llm.LLMCaller`. In handlers, when stream is requested call `ChatWithToolsStream`; otherwise call `ChatWithTools`. Wiring in `servercmd/run.go`: set `cfg.ConversationLLMCaller = llmClient` once (no second field).
   - **internal/tools**: WebFetch and Task (and any constructor taking “an LLM caller”) use the shared `llm.LLMCaller` (or `llmcaller.LLMCaller`) instead of `agent.LLMCaller`. No behavioral change.
   - **cmd/buildmax** and **cmd/buildmax-server**: Pass the same `*llm.Client` as the single conversation LLM caller; no second assignment.

3. **StreamSink**

   - All current `StreamSink` implementors (agent’s process, TUI, CLI print, conversation’s RunLoopStream) already share the same `OnDelta(string)` contract. After moving the interface to the chosen package, agent and conversation both reference the same type; no duplicate interface.

**Benefit**

- Single definition of “something that can do chat-with-tools (and optionally stream)” and “something that receives content deltas.” Easier to add new callers (e.g. other servers or CLI modes) without redefining interfaces.
- Server config and conversation API simplify to one caller type; no split between “stream” and “non-stream” caller fields.
- Clear reuse story for tools and future Tier-1/Tier-2 code: depend on the shared package for the caller contract.
- Aligns with existing note in `.vibe/archive/arch-20260217.md`: “Moving Tool/LLMCaller to a shared package — deferred as a possible follow-up”; this implements the LLMCaller (and StreamSink) part.

**Impact**: High

## Changes for review

| Package / area      | Change |
|---------------------|--------|
| **internal/llm** (Option A) or **internal/llmcaller** (Option B) | Add `LLMCaller` and `StreamSink` interface types. Option A: new file or block in `internal/llm`. Option B: new package with only interface definitions importing `llm`. |
| **internal/agent**  | Remove `LLMCaller` and `StreamSink`; use shared types. Update `Agent`, `processConfig`, `WithStreamSink`, `defaultSubAgentRunner`, and tests (mocks implement shared interface). |
| **internal/conversation** | Remove `LLMCaller`, `StreamLLMCaller`, `StreamSink`. `RunLoop` and `RunLoopStream` take shared `LLMCaller`; `RunLoopStream` also takes shared `StreamSink`. |
| **internal/server** | Single `ConversationLLMCaller` (shared type). Handlers branch on stream flag and call `ChatWithToolsStream` vs `ChatWithTools`. |
| **internal/tools**  | WebFetch, Task (and any other tool taking a caller) use shared `LLMCaller`. |
| **cmd/buildmax**, **cmd/buildmax-server** | Wire one `ConversationLLMCaller` from `*llm.Client`; no separate stream caller. |

No new runtime dependencies. Existing tests (agent, conversation, tools, server) should be updated to use the shared interface; mocks can remain in test files as long as they implement the same methods.
