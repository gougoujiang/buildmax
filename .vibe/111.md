# Task 111: MCP Protocol Integration

## Goal

Connect the **`buildmax` CLI** (`cmd/buildmax/main.go` — interactive TUI and `-p` prompt mode) to **MCP servers** configured in `mcp.json`, using a **lazy gateway** so the LLM only sees **two** MCP tools — not one flattened tool per MCP tool. That keeps **tool-definition tokens** small when many servers and tools are configured.

**Product scope (this task):** MCP is **CLI-only**. Desktop, worker, portal/server, and any other entry point **must not** enable MCP yet.

## Context

- **Tool contract**: Tools implement `core.Tool` (`internal/core/tool.go`) — `Name`, `Description`, `Parameters`, `Execute`. The agent builds OpenAI-style tool definitions via `agent.ToolDefs` and dispatches with `ToolsByName` in `agent.RunLoop` (`internal/core/agent/agent.go`).
- **Where tools are assembled**: `internal/execution/agentrun/runtime.go` — `Open()` calls `buildBaseTools()` (ReadFile, WriteFile, WebFetch, TodoWrite, Bash, Glob, EditFile, Grep, Skill), then appends the composite `Task` tool and constructs `agent.NewAgent(...)`. Other binaries also use `agentrun.Open` (desktop, worker); for this task they keep **MCP disabled** (see `OpenInput` flag below).
- **Tier 1 (portal)**: `internal/core/conversation` uses a **narrow** tool set (`GetCurrentDate`, task orchestration tools). It does **not** use `buildBaseTools`. Any MCP story for the web Tier 1 loop is a separate product/security discussion.
- **MCP ecosystem**: JSON-RPC over **stdio** (subprocess), **SSE** (HTTP with server-sent events), or **streamable HTTP**. In config, streamable HTTP is exposed as **`type`: `http`** (not a separate keyword). The **official** Go SDK is [`github.com/modelcontextprotocol/go-sdk`](https://github.com/modelcontextprotocol/go-sdk) (client + transports). Prefer this dependency in implementation unless a blocker appears (license, API fit); do not hand-roll the full protocol without documenting why.
- **Today**: No MCP wiring exists in the repo; `WebFetch` description mentions MCP only as LLM guidance text (`internal/execution/agenttool/web_fetch.go`).

## Lazy gateway (token-saving)

- Register **exactly two** MCP-facing tools with fixed names **`LoadMcpTools`** and **`CallMcpTool`** (must not collide with builtins):
  1. **`LoadMcpTools`** — Parameters include **`server`** (configured server id) and **`tool_name`**. Returns the **full detail** for that tool (especially **input JSON Schema** and optional description) so the model can build arguments. Its **`Description()`** embeds a **catalog**: each configured MCP server and, per server, **tool name + short description only** (from `tools/list`), not full schemas.
  2. **`CallMcpTool`** — Parameters: **`server`**, **`tool_name`**, **`arguments`** (object). Resolves the server session and MCP tool, then **`tools/call`** with those arguments; result formatting matches other tools (LLM-meaningful text; failures as `error: ...`).

- **No flattening**: Individual MCP tools are **not** separate entries in `ToolsByName` / `ToolDefs`.

## In scope

1. **Configuration** — One JSON file per run; **no merging** of multiple files.
   - **Path resolution** (first path that exists wins): (1) `BUILDMAX_MCP_CONFIG` if set; (2) `<workspace>/.buildmax/mcp.json`; (3) `<DataDir>/mcp.json` (`DataDir()` = `BUILDMAX_HOME` or `~/.buildmax`). If none exist, MCP is disabled.
   - **Format**: JSON with top-level object **`mcpServers`**: a map from **server id** (string) to server config. Each entry has **`type`**, one of:
     - **`stdio`** — local process: **`command`**, **`args`** (array), optional **`env`** (object).
     - **`sse`** — remote SSE transport: **`url`** (string, MCP endpoint).
     - **`http`** — remote **streamable HTTP** transport (simple config surface): **`url`** (string, MCP endpoint). Same `url` shape as typical streamable-HTTP clients in the Go SDK; no separate `streamable-http` keyword in JSON.

   Example (one entry per type):

```json
{
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path"],
      "env": { "MY_VAR": "value" }
    },
    "remote_sse": {
      "type": "sse",
      "url": "https://example.com/mcp/sse"
    },
    "remote_http": {
      "type": "http",
      "url": "https://example.com/mcp"
    }
  }
}
```

   - Implementation must support **all three** `type` values via the Go SDK’s matching transports.
   - Prefer **snake_case** for any additional BuildMax-specific keys we add later; the **`mcpServers`** key stays camelCase for clarity.

2. **Client integration** — Use the official Go SDK to:
   - connect per configured server (timing: see design — catalog requires `tools/list` per server; sessions kept for `LoadMcpTools` / `CallMcpTool`),
   - run MCP initialize / negotiate capabilities,
   - build **`LoadMcpTools` description** from **`tools/list`** summaries (name + description per tool per server),
   - **`LoadMcpTools` Execute**: return full schema / metadata for one `(server, tool_name)` from cached list or SDK types,
   - **`CallMcpTool` Execute**: forward to MCP **`tools/call`**.

3. **Naming** — Gateway tool names are fixed and must **not** collide with builtins (`ReadFile`, `Task`, etc.). No per-MCP-tool names in the flattened list.

4. **Lifecycle and errors** — If a server fails when building the registry / catalog at `Open()` (or at the single “connect for MCP” phase), **fail fast** (clear logs). Gateway `Execute` paths return LLM-meaningful errors for unknown server/tool or transport failures.

5. **Wiring** — **`OpenInput`** gains an explicit opt-in, e.g. **`enable_mcp`** / `EnableMCP` (default **false**). Only the CLI code path that serves **`cmd/buildmax`** sets **`true`** when opening the runtime. If **`false`**, behave as today (no MCP tools, no connections) even if `mcp.json` exists. When **`true`** and config is non-empty, append the two gateway tools and use **`Runtime.Close`** to release MCP sessions.

6. **Tests** — Unit tests without real network or external binaries: mocks / in-memory transport where possible; config parsing for `type` stdio/sse/http; **`LoadMcpTools`** returns expected schema snippet; **`CallMcpTool`** sends expected `CallTool` params (verified via mock).

## Out of scope

- **Desktop** (`cmd/buildmax-desktop`, `internal/interface/desktop`): do **not** set `EnableMCP`; no MCP gateway tools.
- **Worker / Tier 2** (`internal/execution`, `agentrun.Open` from worker): same — MCP off.
- **Portal / server** and **Tier 1** conversation loop: unchanged; no MCP in this task.
- **MCP resources and prompts** as first-class surfaces to the model (tools-only focus).
- **OAuth / authenticated remote MCP** beyond what the chosen SDK version supports with minimal wiring; can be a follow-up.
- **Per-user MCP config on the server** for multi-tenant use (future).
- **Hot-reload** of MCP servers mid-session (refresh at `Open()` is sufficient for MVP).

## Deliverables

1. **Config loading** — `internal/config`: load **one** `mcp.json` from the resolution order above; parse `mcpServers`; missing file or empty map → **no** MCP gateway tools (unchanged behavior).

2. **`internal/infra/mcp` (or similar)** — Registry (sessions + cached `ListTools` summaries), gateway tools implementing `core.Tool`, transport helpers per `type`.

3. **`agentrun` + CLI** — When **`OpenInput.EnableMCP`** is true and MCP config is non-empty, append gateway tools and set **`Runtime`** MCP cleanup; **`internal/interface/cli`** (only) passes **`EnableMCP: true`** for TUI and print mode. **`Runtime.Close`** in CLI paths releases MCP sessions.

4. **Documentation for operators** — `.env.example` + `env_spec.go` if new env keys.

5. **Tests** — As in scope #6.

## Acceptance criteria

- [ ] With valid MCP config, **`EnableMCP: true`**, and a trivial MCP server (mock or in-proc), `agentrun.Open` yields an `Agent` whose tool list includes **`LoadMcpTools`** and **`CallMcpTool`**, not a separate tool per MCP tool.
- [ ] With **`EnableMCP: false`** (default), **`LoadMcpTools` / `CallMcpTool`** are absent even if `mcp.json` exists (desktop/worker compatibility).
- [ ] `LoadMcpTools` description contains a **catalog** (servers + tool names + short descriptions); invoking it for a pair returns **full schema** (or equivalent) for that tool.
- [ ] `CallMcpTool` results in the expected MCP **`tools/call`** (verified via mock).
- [ ] With **no** MCP config, behavior matches today: **no** `LoadMcpTools` / `CallMcpTool`, no extra subprocesses or connections.
- [ ] `go test ./...` passes with `BUILDMAX_HOME` set to a test sandbox per project practice.
- [ ] New configuration keys (if any) are documented in `env_spec.go` and `.env.example`.
