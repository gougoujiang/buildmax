# Task 012: TUI scrollable banner and chat history

## Goal

The user can scroll the banner-and-chat area (viewport) to see old messages when content exceeds the visible area, using both mouse wheel and keyboard.

## Context

- TUI is implemented in `internal/tui` with Bubble Tea: `Model` has a `viewport.Model` (bubbles) for banner + chat, plus `textarea.Model` for input and a footer (`internal/tui/model.go`).
- Content is built in `format.go` via `buildViewportContent` (banner + all session messages + optional “assistant: ...” carousel). The viewport is given this full string and `GotoBottom()` is called after each content update.
- Viewport already has `MouseWheelEnabled = true` and `tea.MouseMsg` is forwarded to it in `Update`; keyboard messages are **not** forwarded—they all go to the input. So mouse wheel can scroll, but arrow keys / PgUp / PgDown do not.
- Bubble Tea’s bubbles viewport supports `ViewUp`, `ViewDown`, half-page, `GotoTop`/`GotoBottom`, and typically uses a `KeyMap` for Up/Down/PgUp/PgDown/Home/End when it receives key events.
- Project: single Go binary, Bubble Tea TUI, conventions in AGENTS.md (e.g. no stdout logging in TUI path).

## Scrollable viewport (this task)

**Layout constraint:** Only the viewport (banner + chat history) scrolls. The input box and footer must stay fixed at the bottom of the screen and must not move when the user scrolls—they are not part of the scrollable content.

For this task, “scrollable” means:

1. When the rendered content (banner + messages) is taller than the viewport height, the user can move the view up/down to see older or newer content *within the viewport area only*.
2. **Mouse**: scrolling works via mouse wheel (already wired; keep it working).
3. **Keyboard**: the user can scroll with keys (e.g. Up/Down, PgUp/PgDown, Home/End) without needing a mouse.

To avoid stealing arrow keys from the input (typing/cursor), use **focus**: when “scroll focus” is on the viewport, scroll keys are handled by the viewport; when focus is on the input, typing and cursor work as today. A simple convention is: **Tab** (or another chosen key) toggles focus between input and viewport; when viewport has focus, scroll keys scroll it.

We are **not** implementing in this task:

- Horizontal scrolling.
- Search or jump-to-message in chat.
- Changing layout (banner vs chat) or adding new UI panels.

## Deliverables

1. **`internal/tui/model.go`**
   - **Layout**: Keep the current three-region layout: viewport (top, scrollable), input (fixed below viewport), footer (fixed at bottom). Do not put input or footer inside the viewport—they must remain fixed while only the viewport content scrolls.
   - **Focus state**: Add a field (e.g. `scrollFocus bool` or `focusInput bool`) so the model knows whether the viewport has “scroll focus” or the input has focus. Default: input focused (current behaviour).
   - **Tab (or chosen key)**: In `Update`, when the user presses the chosen toggle key (e.g. Tab), switch focus between input and viewport (do not send the key to input/viewport for editing). When switching to viewport, viewport should receive subsequent scroll keys; when switching back to input, input receives keys as today.
   - **Keyboard scroll when viewport focused**: When viewport has scroll focus, forward `tea.KeyMsg` to the viewport’s `Update` (so bubbles viewport can use its KeyMap: Up/Down, PgUp/PgDown, Home/End). Do not forward that key to the input. Optionally handle only “scroll” keys and forward the rest to input; either way, when viewport has focus, scroll keys must move the viewport.
   - **Other keys when viewport focused**: Define behaviour for non-scroll keys when viewport has focus (e.g. Tab returns focus to input; Enter or Esc could also return focus to input). Ensure Quit (e.g. Ctrl+C) and any global shortcuts still work.
   - **Resize**: Keep existing `tea.WindowSizeMsg` behaviour (viewport height = total − input − footer). Ensure after resize the viewport still shows correct content and scroll position where possible (e.g. stay at bottom if already at bottom; no new requirement to “remember” scroll position across resizes beyond what viewport already does).
   - **Mouse**: Keep forwarding `tea.MouseMsg` to the viewport so mouse wheel scrolling continues to work regardless of focus.

2. **`internal/tui` behaviour**
   - When viewport has scroll focus, the user can scroll up/down with keyboard to see old messages and return to the bottom (e.g. End or Down until bottom). When input has focus, typing and input behaviour are unchanged.
   - No new packages required; use existing `viewport.Model` and its `Update`/key handling.

3. **Tests**
   - Prefer at least one unit test that verifies focus toggle (e.g. send Tab, assert focus state; send Tab again, assert focus back on input). If easier, manual acceptance is acceptable for “scroll keys move viewport when viewport focused” as long as the behaviour is clearly specified above.

## Out of scope (for later)

- Horizontal scrolling or line-wrapping changes.
- Search / filter / jump in chat history.
- Styling or layout changes beyond enabling scroll.
- Persisting scroll position across sessions or restarts.

## Acceptance

- [ ] When content (banner + messages) is taller than the viewport, the user can scroll up to see older messages (e.g. earlier in the session).
- [ ] Mouse wheel scrolls the viewport up/down when content overflows (existing behaviour preserved).
- [ ] A defined key (e.g. Tab) toggles focus between input and viewport; focus state is clear (e.g. footer or input border hint optional but not required for “done”).
- [ ] When viewport has scroll focus, Up/Down (and preferably PgUp/PgDown, Home/End) scroll the viewport; the input does not consume these keys in this state.
- [ ] When input has focus, typing and cursor behaviour are unchanged; Tab (or toggle key) does not insert a tab character when used to switch focus.
- [ ] Ctrl+C (and any other global quit) still quits regardless of focus.
- [ ] After new messages arrive, viewport content updates and stays at bottom (existing `GotoBottom()` behaviour preserved when content is set).
- [ ] Resize still correctly sizes the viewport (height = total − input − footer); scrolling still works after resize.
- [ ] During scrolling, the input box and footer stay fixed at the bottom; only the viewport (banner + chat) content scrolls.
