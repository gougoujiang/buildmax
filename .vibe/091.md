# Task 091: Two-tier agent — Phase 1 — Tier 1 interfaces and channel abstraction

## Goal

Define the Tier 1 conversation layer as Go interfaces and types in a dedicated package so that all channels (portal, telegram, cron, webhook) can be implemented against a single contract, with no new LLM or HTTP behavior in this task.

## Context

- **Design:** [design/007-two-tier-agent.md](../design/007-two-tier-agent.md) §5 (Key interfaces), §8 Phase 1.
- **Existing code:** `internal/agent` has the Tier 2 agent loop; `internal/server` has chat/run handlers; `internal/model` and `internal/storage/entity` define Chat, ChatRun; `internal/workerapi` is a types-only package for worker API (good reference for a small, interface-focused package).
- **Where it fits:** New package `internal/conversation` — used by server (and later cron/webhook/IM) to normalize input and call the conversation engine; no dependency from `conversation` on `server` or `agent`.
- **Conventions:** AGENTS.md §6.1 — persisted JSON uses snake_case; these types are in-memory only for Phase 1. Go identifiers remain PascalCase; add `json:"snake_case"` only if we expose them over HTTP in this task (we do not). Follow existing style: interfaces in one file or split by concern, types with clear doc comments.

## Tier 1 (this task)

For this task, **Tier 1** is the conversation/gateway layer: it receives normalized "turns" (user or trigger input) and decides whether to reply only or spawn Tier 2 task(s). We are defining only the **contract** (types and interfaces), not any implementation.

- **ConversationTurn:** Normalized input from any channel (workspace, channel name, channel-specific conversation id, user id, message text, optional raw payload).
- **ConversationResult:** Output of processing one turn — optional direct reply and optional list of chat_run_ids spawned.
- **ChannelAdapter:** Implemented per channel; converts channel-specific input to `ConversationTurn` and sends output back (e.g. HTTP response, Telegram message).
- **ConversationEngine:** Implemented per strategy (e.g. pass-through, LLM); takes a turn and returns `ConversationResult` (may create ChatRuns via stores, not in this task).

We are **not** implementing any adapter or engine, or wiring Tier 1 into the server.

## Deliverables

1. **Package `internal/conversation`**
   - **Types (e.g. `types.go`):**
     - `ConversationTurn` struct: `WorkspaceID`, `Channel`, `ConversationID`, `UserID`, `Message` (string), `Raw` (map[string]any, optional). Doc comment describing each field (Channel = which channel; ConversationID = channel-specific conversation/thread id, e.g. chat_id for portal).
     - `ConversationResult` struct: `Reply` (string), `TaskIDs` ([]string, chat_run_ids). Doc comment.
   - **Channel constants:** Define the four channel names as constants (e.g. `ChannelPortal`, `ChannelTelegram`, `ChannelCron`, `ChannelWebhook`) so adapters and engines can refer to them without magic strings. Optionally a slice or set of valid channels for validation.
   - **Interface `ChannelAdapter`:** `Receive(ctx context.Context, raw any) (ConversationTurn, error)`; `Send(ctx context.Context, conversationID string, output string) error`. Doc comments: Receive normalizes raw input; Send delivers output to the channel (conversationID is channel-specific, e.g. chat_id for portal).
   - **Interface `ConversationEngine`:** `Process(ctx context.Context, workspaceID, chatID string, turn ConversationTurn) (ConversationResult, error)`. Doc: processes one turn; may return reply and/or task_ids (chat_run_ids).
   - No dependency on `internal/server`, `internal/agent`, or `internal/storage` in this package (interfaces only; callers will inject stores/engines later).
   - No adapter or engine implementations in this task.

2. **Tests**
   - Unit test(s) that construct `ConversationTurn` and `ConversationResult` with all fields and that channel constants are non-empty and distinct.
   - If a small helper is added (e.g. `ValidChannel(ch string) bool`), unit test it.
   - No tests that implement `ChannelAdapter` or `ConversationEngine` (those come in Phase 2+).

3. **Build and lint**
   - `go build ./...` and `go test ./...` pass; no new linter issues in the new package.

## Out of scope (for later)

- Implementing the portal adapter or any other `ChannelAdapter` (Phase 2).
- Implementing the pass-through or LLM `ConversationEngine` (Phase 2, 3).
- Wiring Tier 1 into HTTP handlers or scheduler (Phase 2, 4).
- Adding `channel` to the Chat entity or persisting conversation history (Phase 3).
- Any change to `internal/server`, `internal/executor`, or `internal/storage`.
