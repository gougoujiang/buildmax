# Task 109 - User only communicate with Tier 1

## Goal

Make Tier 1 the **sole interface** between the user and the system: when a Tier 2 task finishes (or fails), Tier 1 automatically picks up the result and sends a summarized response to the user through the existing conversation WebSocket — so the user never navigates to a TaskDetail page or subscribes to a task stream directly.

## Context

- **Tier 1** = `internal/core/conversation.Service` + `internal/core/conversation` (low-level LLM loop). The user communicates with Tier 1 via WebSocket (`conversation.create`, `conversation.message` → `conversation.message.delta`, `conversation.message.completed`).
- **Tier 2** = Task + TaskRun, executed by the worker (`internal/execution`). Worker reports status back via `PATCH /api/worker/task-runs/{id}`. Worker also streams deltas via `POST /api/worker/task-runs/{id}/stream` → `StreamHub` → frontends that subscribe.
- **Current problem**: When Tier 1 creates a background task (via `StartTask` tool), it tells the user the task ID and says "check progress at TaskDetail." The user then navigates to a separate TaskDetail page and subscribes directly to the task stream (`subscribe.task` → `task.stream.delta` / `task.stream.done`). This means the user interacts with Tier 2 directly — viewing raw Tier 2 streaming, following up on tasks, and reading artifacts from task pages.
- **Portal frontend** currently has: ConversationDetail page (Tier 1 chat) and TaskDetail page (Tier 2 direct interaction). The frontend also has APIs: `GET /api/tasks/{id}`, `POST /api/tasks/{id}/runs`, `GET /api/tasks/{id}/stream`, `GET /api/tasks/{id}/conversation`, `GET /api/tasks/{id}/artifacts`, `GET /api/task-runs/{id}/artifacts/*`.
- **WebSocket handler** (`internal/server/portal/ws_handler.go`) currently supports both conversation events AND task stream subscription (`subscribe.task`/`unsubscribe.task` → `task.stream.delta`/`task.stream.done`).

## "User only communicate with Tier 1" (this task)

For this task, "user only communicate with Tier 1" means:

1. **Tier 1 is the only voice to the user.** All messages the user sees in the portal come from Tier 1 conversation messages (streamed via `conversation.message.delta` / `conversation.message.completed`).
2. **When Tier 2 finishes, Tier 1 picks up the result.** The server detects that a task run completed (SUCCEEDED or FAILED) and triggers a new Tier 1 conversation turn — Tier 1 runs an LLM call with the Tier 2 result injected, producing a summarized response that is streamed to the user on the conversation WebSocket.
3. **No direct user↔Tier 2 interaction from the portal.** The portal does not show TaskDetail pages, does not subscribe to task streams, and does not call task APIs directly. Everything the user sees about task progress comes through Tier 1 conversation messages.

We are **not** yet implementing:

- Displaying live Tier 2 streaming in the conversation (typewriter effect of Tier 2 output) — this task focuses on the result summary after completion.
- Removing the task REST API routes from the server entirely (they may still be used internally or by other clients) — this task only removes the portal's direct use of them.
- Task artifacts displayed inline in the conversation — Tier 1 will summarize the result text; artifact file browsing is out of scope.
- Progress updates during long-running tasks (e.g., "task is 50% done") — Tier 1 will only respond when the task reaches a terminal state (SUCCEEDED/FAILED).

## Deliverables

1. **Server-side: task completion → Tier 1 callback** (`internal/server/worker/handlers.go` or new callback mechanism)
   - When a task run reaches terminal status (SUCCEEDED or FAILED), the server triggers a Tier 1 conversation turn for the conversation that owns this task.
   - The Tier 1 turn is invoked with a **system-generated input** (not a user message) that includes: task ID, status, and the task output (or error message). For example: `[system: task c_xxx completed successfully. Output: <truncated output>]`
   - Tier 1 LLM processes this and produces a summarized assistant message for the user.
   - The assistant response is streamed to the user via the conversation WebSocket (`conversation.message.delta` / `conversation.message.completed`).
   - **Mechanism**: The `handlePatchTerminalStatus` in the worker handler (or the `Hub.Done` callback) triggers the Tier 1 turn. This could be: (a) a callback/hook on the worker handler config, or (b) a post-completion listener in the server that watches for terminal status changes.

2. **Tier 1 conversation service: support system-triggered turns** (`internal/core/conversation/service.go`)
   - Add a method or extend `HandleTurn` to accept a "system" turn that is triggered by task completion — not by a user message.
   - The system turn appends a system/internal message with task result context, runs the LLM loop, and streams the response.
   - The LLM's system prompt should instruct it to summarize the task result for the user (e.g., "A background task has completed. Summarize the result for the user.").

3. **WebSocket handler: deliver system-triggered conversation turns** (`internal/server/portal/ws_handler.go`)
   - When a system-triggered Tier 1 turn produces output, it must be streamed to the correct WebSocket connection (the user who owns the conversation).
   - This requires the WebSocket layer to support **server-initiated pushes** to a specific user's connection (currently it only sends responses to the same connection that initiated a turn).
   - **Approach**: Maintain a registry of connected users → their `wsConn`. When a system turn needs to stream to user X, look up their connection and use it (or queue if offline — out of scope for now; drop the message if the user is not connected).

4. **Portal frontend: remove direct Tier 2 interaction**
   - Remove the TaskDetail page (or redirect task routes to the conversation).
   - Remove `subscribe.task` / `unsubscribe.task` WebSocket events from the frontend.
   - Remove task-specific API calls from the frontend (`getTask`, `createTaskRun`, `getTaskConversation`, `getTaskStream`, `getTaskArtifacts`, `getArtifactItems`, `getArtifactContent`).
   - When Tier 1 tells the user "I've started a background task," the user stays on the ConversationDetail page and waits for the follow-up message.
   - The conversation view should indicate that a task is in progress (e.g., a "thinking" or "working on task..." indicator) and then show the summarized result when it arrives.

5. **Tier 1 system prompt update** (`internal/core/conversation/agent.go`)
   - Update the system prompt so that Tier 1 no longer tells the user to "check progress at task detail" or provides task IDs for direct access.
   - Instead: "I've started a background task. I'll get back to you with the results when it's done."
   - When receiving a task completion event, the prompt should instruct: "Summarize the result clearly and concisely for the user."

## Out of scope (for later)

- Live Tier 2 streaming relayed through Tier 1 (typewriter of Tier 2 output in conversation)
- Offline delivery / queuing of task results when user is disconnected
- Inline artifact rendering in conversation
- Progress updates during task execution
- Removing task REST API routes from the server (keep for internal/CLI use)
- Task rerun/follow-up initiated by the user (currently done via TaskDetail; future: Tier 1 tool `ContinueTask` handles this naturally through conversation)

## Acceptance

- [ ] When Tier 2 task completes (SUCCEEDED), Tier 1 automatically sends a summarized result to the user on the conversation WebSocket — no user action required.
- [ ] When Tier 2 task fails, Tier 1 sends an error summary to the user on the conversation WebSocket.
- [ ] The portal frontend has no TaskDetail page; task routes redirect to conversation.

- [ ] The Tier 1 system prompt no longer directs users to check task detail pages.
