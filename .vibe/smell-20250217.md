# Smell Proposal - internal/store/store.go

## Scope

**Analyzed**

- Path: `internal/store/store.go` (505 lines)
- Criteria: Single large file mixing models, interfaces, and all store method implementations; user requested refactor to split into smaller files.

## Summary

- **Proposals**: 3
- **High priority**: 1
- **Overview**: The main smell is a single 505-line file that holds six entity domains (user, workspace, project, task, artifact, artifact_item), five interfaces, one concrete `Store`, and ~25 methods. Splitting by entity into multiple files within the same package will improve navigability and maintainability without changing the public API.

---

## Proposals

### 1. Split store.go by entity into multiple files (same package)

**Location**: `internal/store/store.go` — entire file

**Current state**

- One file contains: all models (User, Workspace, Project, Task, Artifact, ArtifactItem, ArtifactWithTask), all interfaces (UserStore, WorkspaceStore, ProjectStore, TaskStore, ArtifactStore), the `Store` struct, `New`, and every method (~25) for user, workspace, project, task, artifact, plus `BackfillTaskWorkspaceID` and `Close`.
- Navigating and reviewing the store layer requires scrolling through 500+ lines. Adding a new entity or method increases the file further.
- Go allows multiple files in one package; callers already use `store.Store` and `store.User` etc. — they do not depend on a single file.

**Proposed change**

- Keep package `store` and the single `Store` struct implementing all interfaces. Split **definitions and methods** across files as follows:

| File | Contents |
|------|----------|
| `store.go` | Package doc, imports, `Store` struct, `New`, `Close`, `BackfillTaskWorkspaceID`. Optionally keep all interfaces here so the “contract” is in one place. |
| `models.go` | All GORM models: `User`, `Workspace`, `Project`, `Task`, `Artifact`, `ArtifactItem`, `ArtifactWithTask`; sentinel `ErrEmailExists`; each model’s `TableName()`. |
| `interfaces.go` | All store interfaces: `UserStore`, `WorkspaceStore`, `ProjectStore`, `TaskStore`, `ArtifactStore`. |
| `user.go` | `(*Store).UserByEmail`, `(*Store).CreateUser`. |
| `workspace.go` | `(*Store).EnsureDefaultWorkspaceForUser`, `ListWorkspacesByOwner`, `WorkspaceBelongsToUser`, `CreateWorkspace`. |
| `project.go` | `(*Store).GetProject`, `ListProjectsByWorkspace`, `CreateProject`. |
| `task.go` | All task methods: `ListTasksByWorkspace`, `GetTask`, `GetTaskBySessionID`, `CreateTask`, `GetNextPendingTask`, `UpdateTaskStatus`, `IncrementTaskSeq`; constant `taskInputSnippetMaxLen` if kept, or move it next to the only use in artifact. |
| `artifact.go` | `CreateArtifactWithItem`, `ListArtifactsByWorkspace`, `GetArtifactByID`, `ListArtifactItems`; and `taskInputSnippetMaxLen` if used only here. |

- Each of the new files (except `store.go`) needs the same minimal imports it uses (e.g. `context`, `errors`, `time`, `buildmax/internal/id`, `gorm.io/...`). Duplicate imports across files are fine in Go.
- Tests stay in `store_test.go`; they continue to use `Store`, `New`, and types from the package. Any test that touches `s.db` remains valid because tests live in package `store` and can reference unexported fields.

**Benefit**: Smaller, focused files; easier to find and change one entity’s logic; same public API and no caller changes.

**Priority**: High

### 2. Optionally colocate interfaces with implementations

**Location**: `internal/store/` — after Proposal 1

**Current state**

- After the split above, all interfaces would live in `interfaces.go`. That’s a clear “contract” file but separates the interface from the file that implements it (e.g. `UserStore` vs `user.go`).

**Proposed change**

- **Either** keep one `interfaces.go` (simpler, one place to see all store contracts), **or** move each interface into the file that implements it (e.g. `UserStore` and `User` in `user.go`). The latter improves cohesion when editing one domain but scatters the full set of store interfaces.
- Recommendation: keep `interfaces.go` so that server wiring (e.g. `store.UserStore`) and mocks stay consistent and discoverable in one place.

**Benefit**: If you move interfaces next to impls: stronger cohesion per entity. If you keep `interfaces.go`: single place for all store contracts and easier mocking.

**Priority**: Low (optional refinement after Proposal 1)

### 3. Repeated “First by ID, return (nil, nil) on not found” pattern

**Location**: `internal/store/store.go` — `UserByEmail`, `GetProject`, `GetTask`, `GetTaskBySessionID`, `GetNextPendingTask`, `GetArtifactByID`

**Current state**

- Six methods share the same pattern: run a GORM `First` with a condition, if `gorm.ErrRecordNotFound` return `(nil, nil)`, otherwise return `(nil, err)` or the result. The logic is repeated with small variations (model type, where clause).

**Proposed change**

- **Option A**: Leave as-is. The duplication is small (~5 lines per method), and each method is clear. No new abstractions.
- **Option B**: Introduce an unexported helper, e.g. `firstOrNotFound(ctx, db, model, where, args) (found bool, err error)` that fills the model and returns whether it was found. Callers then allocate the model, call the helper, and return either `&model` or `(nil, nil)`. This reduces duplication but adds indirection and may not fit all cases (e.g. `UserByEmail` uses `email`, others use id columns).
- Recommendation: **Option A** unless you add many more “get by unique key” methods; then consider a small generic or reflection-based helper in a single place (e.g. `store.go` or `helpers.go`).

**Benefit**: Option A keeps code obvious; Option B reduces duplication if the pattern grows.

**Priority**: Low

---

## Suggested order

1. **Proposal 1 (split by entity)** — do first. This directly addresses the “file is getting big” concern and does not change behavior or API. Move code in dependency order: create `models.go` and `interfaces.go`, then `store.go` (struct + New + Close + Backfill), then `user.go`, `workspace.go`, `project.go`, `task.go`, `artifact.go` with their methods. Run `go build ./...` and `go test ./...` after the split.
2. **Proposal 2** — optional; decide whether to keep `interfaces.go` or colocate interfaces with impl files.
3. **Proposal 3** — optional; only consider a helper if you add more “get by unique key” methods later.

## Out of scope

- Changing the public API (e.g. introducing separate `UserStore`/`WorkspaceStore` instances instead of a single `Store`). That would require updating server wiring and tests.
- Moving the store package into subpackages (e.g. `store/user`, `store/workspace`). That would change imports and potentially create circular dependencies; the current ask is “split to smaller files” within the same package.
- Database or GORM refactors (e.g. repositories, query builders). This proposal is file layout only.
