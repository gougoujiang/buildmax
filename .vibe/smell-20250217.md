# Smell Proposal — internal/

## Scope

**Analyzed**

- Path: `internal/` — Go packages (cmd, server, session, agent, store, config, executor, tools, tui, llm, log, app, id, util).
- Criteria: package boundaries, coupling, duplication, naming, error handling, testability, dead code, alignment with AGENTS.md.

## Summary

- **Proposals**: 8
- **High priority**: 2 (workspace-scoped handler boilerplate, internal errors not logged)
- **Overview**: Main issues are (1) repeated auth + workspace path + ownership check in every workspace-scoped handler, (2) many handlers return "internal error" without logging the underlying err, (3) duplicated project-validation block in tasks.go, (4) MySQL DSN built in cmd instead of config, (5) minor naming and structure improvements.

---

## Proposals

### 1. Extract workspace-scoped handler middleware / helper

**Location**: `internal/server/` — workspaces.go, projects.go, tasks.go, files.go, upload.go, session.go (getSessionHandler)

**Current state**

- Every handler that operates on a workspace repeats the same sequence: `requireAuth(w, r, s.cfg.JWTSecret)` → `r.PathValue("workspace_id")` → `userOwnsWorkspace(r, userID, workspaceID)` with the same error responses (400 for missing workspace_id, 500 for store error, 403 for !owned). This appears in at least 10 handler bodies (list/create workspaces, list/create projects, list/create tasks, files tree, file content, upload, and getSessionHandler after resolving task). The pattern is 10–20 lines per handler and is duplicated across files.

**Proposed change**

- Introduce a helper that performs auth + workspace path extraction + ownership check and returns (userID, workspaceID, true) on success, or writes the appropriate JSON error and returns (_, _, false). For example: `func (s *Server) withWorkspaceAuth(w http.ResponseWriter, r *http.Request, pathKey string) (userID, workspaceID string, ok bool)`. Handlers that need a workspace call this first and return if !ok. getSessionHandler is a special case (it resolves workspace via task); it can keep its current flow or use a smaller helper that only does auth + task-based workspace ownership. Optionally, a middleware that injects (userID, workspaceID) into context could be used for routes that always have workspace_id in the path.

**Benefit**: Single place for auth and workspace validation; less duplication; easier to add logging or metrics in one spot.

**Priority**: High

### 2. Log underlying errors before returning "internal error"

**Location**: `internal/server/workspaces.go`, `internal/server/projects.go`, `internal/server/tasks.go`, `internal/server/login.go`, `internal/server/session.go`, `internal/server/upload.go` (selected branches)

**Current state**

- Many handlers call `writeJSONError(w, http.StatusInternalServerError, "internal error")` without logging the underlying `err`. Examples: workspaces.go (EnsureDefaultWorkspaceForUser, ListWorkspacesByOwner, CreateWorkspace, MkdirAll), projects.go (userOwnsWorkspace, ListProjectsByWorkspace, CreateProject, Decode), tasks.go (userOwnsWorkspace, GetProject, ListTasksByWorkspace, CreateTask, Decode), login.go (UserByEmail), session.go (GetTaskBySessionID, userOwnsWorkspace, ReadFile, Unmarshal), upload.go (userOwnsWorkspace and several file ops that do log). The client correctly sees a generic message, but server-side debugging is hard because the real error is not logged.

**Proposed change**

- Before every `writeJSONError(w, http.StatusInternalServerError, "internal error")` that is taken on a non-nil `err`, add `slog.Error("handler context", "err", err, "optional_key", value)` (or use a small helper that logs then writes the generic response). Ensure handler context (e.g. workspace_id, project_id, task_id) is included where useful. Align with existing patterns in files.go and upload.go where errors are already logged.

**Benefit**: Easier debugging and operational visibility without changing the client-facing message.

**Priority**: High

### 3. Extract project-in-workspace validation into a shared helper (tasks)

**Location**: `internal/server/tasks.go` — listWorkspaceTasksHandler (lines ~75–95), createWorkspaceTaskHandler (lines ~146–166)

**Current state**

- The logic to resolve an optional project_id (query param vs body), ensure ProjectStore is set, fetch project, check non-nil, and verify project.WorkspaceID == workspaceID is duplicated in two handlers. Same error responses (503, 500, 404, 400) and same structure.

**Proposed change**

- Add a helper, e.g. `func (s *Server) resolveProjectForWorkspace(r *http.Request, workspaceID string, projectID string) (*store.Project, bool)` that returns (project, true) or writes the appropriate error and returns (nil, false). When projectID is empty, return (nil, true) so callers can pass nil to ListTasksByWorkspace. Both list and create handlers then call this helper and return if !ok.

**Benefit**: One place for project-in-workspace validation; fewer lines and consistent behavior.

**Priority**: Medium

### 4. Move MySQL DSN construction to config

**Location**: `internal/cmd/server.go` — `mysqlDSN()`, `runServer()`

**Current state**

- `mysqlDSN()` builds the DSN from MYSQL_HOST, MYSQL_PORT, MYSQL_USER, MYSQL_PASSWORD, MYSQL_DATABASE with defaults (localhost, 3306, buildmax, buildmax, buildmax). This is server/bootstrap concern and lives in the cmd package next to flag parsing and runner setup. Config package already centralizes DataDir, WorkspacesDir, LoadLLM, EffectiveLLM, etc.

**Proposed change**

- Add `config.MySQLDSN() string` (or `config.LoadMySQL() (dsn string)`) that reads the same env vars and returns the same DSN string. Keep defaults in one place (config). In `runServer`, call `dsn := config.MySQLDSN()` (or equivalent). This keeps DSN logic and env contract in config and leaves cmd to orchestration only.

**Benefit**: Single place for DB connection config; consistent with other config (paths, LLM); easier to test or override in tests.

**Priority**: Medium

### 5. Consider interface for session title ChatFunc

**Location**: `internal/session/title.go` — `ChatFunc` type, `GenerateTitle`

**Current state**

- `GenerateTitle(ctx, chatFn, messages)` accepts `ChatFunc func(ctx, messages) (string, error)`. Callers in cmd (print.go) pass a closure that calls `res.LLMClient.ChatWithTools(ctx, msgs, nil)`. The function type is minimal and testable by passing a stub, but there is no named interface (e.g. `TitleChatClient`) in the session package. This is a very small type; the smell is optional consistency with “interfaces over concrete types” where the component is injected.

**Proposed change**

- Optionally define an interface in the session package, e.g. `type TitleChatClient interface { Chat(ctx context.Context, messages []llm.Message) (string, error) }`, and have `GenerateTitle` accept that interface instead of `ChatFunc`. The closure in cmd would satisfy it. Alternatively, keep `ChatFunc` as is and document that it is the injection point for tests. No change required if the team prefers minimal types.

**Benefit**: Clearer contract and alignment with “interfaces for injection”; test code can pass a mock that implements the interface.

**Priority**: Low

### 6. Fix setupResult not appending taskTool in one path (if intended)

**Location**: `internal/cmd/setup.go` — `setupAgentAndSession`, `buildBaseTools` comment

**Current state**

- `buildBaseTools` comment says “Task is excluded — sub-agents must not recurse.” The agent is built with `append(baseTools, taskTool)`. So the main agent does get taskTool; only base tools used for sub-agents omit it. No bug identified; this note is for clarity only. If there were a code path where the main agent was built without taskTool, that would be a smell; from the current code, the main agent correctly gets baseTools + taskTool.

**Proposed change**

- None required unless a separate code path is introduced that builds an agent without taskTool. Optionally add a one-line comment next to `agent.NewAgent(client, append(baseTools, taskTool))` that the main agent includes the task tool for delegation.

**Benefit**: Avoids future confusion when adding more agent-construction paths.

**Priority**: Low

### 7. Reduce repeated store-nil checks in workspace handlers

**Location**: `internal/server/workspaces.go`, `internal/server/projects.go`, `internal/server/tasks.go`

**Current state**

- After auth and (where applicable) workspace ownership, handlers often do `if s.cfg.WorkspaceStore == nil { writeJSONError(..., 503, "… not configured"); return }`. Similar for ProjectStore and TaskStore. This is repeated in multiple handlers. If proposal 1 (withWorkspaceAuth) is implemented, the store checks could still be per-handler unless folded into a richer “handler context” that also validates required stores for the route.

**Proposed change**

- If a shared middleware or helper is introduced (proposal 1), consider a variant or option that also checks required stores for the route (e.g. “this route needs WorkspaceStore”) and returns 503 from one place. Otherwise, keep the explicit nil checks in each handler for clarity. Optional: add a small helper `func (s *Server) requireWorkspaceStore(w http.ResponseWriter) bool` that writes 503 and returns false if nil, so the repeated if-block becomes one line.

**Benefit**: Slightly less duplication and consistent 503 messaging for missing store config.

**Priority**: Low

### 8. Optional: extract static file serving into a testable helper

**Location**: `internal/server/server.go` — `openAPIHandler`, `swaggerUIHandler`

**Current state**

- Both handlers do: read file from embedded FS, set Content-Type, write 200, write body. Errors from `staticFS.ReadFile` are ignored (no write, no status), so the client may get an empty body or wrong state. The pattern is small and only used twice.

**Proposed change**

- Add a helper, e.g. `func serveStaticJSON(w http.ResponseWriter, path string)` and `serveStaticHTML(w http.ResponseWriter, path string)` that read from the package-level embed, set the appropriate Content-Type, and on read error log and write 500. Use them in openAPIHandler and swaggerUIHandler. This centralizes static serving and improves error handling.

**Benefit**: Consistent error handling for static assets; single place to add caching or validation later.

**Priority**: Low
