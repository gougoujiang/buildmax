# Task 108 - Portal WebSocket Communication

## Goal

Replace SSE-based Portal↔server communication with a persistent WebSocket connection, enabling bidirectional message flow so the server (Tier 1 agent) can proactively push events to the Portal—not just respond to requests.

## Context

- **Current Tier 1 conversation streaming**: Portal sends `POST /api/conversations?stream=1` or `POST /api/conversations/{id}/messages?stream=1`. The server runs the LLM loop in-process and writes SSE events (`text/event-stream`) on the same HTTP response via an `sseSink`. The portal reads the response body with `readSSEStream`. This is a request–response pattern: user sends → waits for full streamed reply → sends next. (`internal/server/portal/conversation_handlers.go`, `portal/src/features/conversations/api.ts`, `portal/src/lib/api/sse.ts`)
- **Current Tier 2 task streaming**: Portal subscribes to `GET /api/tasks/{task_id}/stream` (SSE). The worker pushes deltas via internal `POST /api/worker/task-runs/{run_id}/stream` → `StreamHub` broadcasts to SSE subscribers. (`internal/server/portal/stream_handlers.go`, `internal/streamhub/hub.go`, `portal/src/features/tasks/api.ts`)
- **`StreamHub`**: In-memory pub/sub keyed by `chatID` (task_id). Interface: `Append`, `Buffer`, `Done`, `Subscribe`. (`internal/streamhub/hub.go`)
- **`llm.StreamSink`**: `OnDelta(delta string)` interface used by the agent loop for streaming. `sseSink` in `conversation_handlers.go` adapts this to SSE writes. (`internal/infra/llm/caller.go`)
- **Design reference**: `design/005-portal-streaming.md` documents the original SSE implementation; `design/notebook/2026-03-21.md` outlines the vision for WebSocket and event-driven architecture.

## WebSocket communication (this task)

For this task, "WebSocket communication" means:

1. **A unified event protocol** — Define a typed JSON envelope for all events flowing over the WebSocket (client→server and server→client). Each event has a `type` and typed `payload`.
2. **A persistent WebSocket connection per Portal session** — One WebSocket connection replaces all current SSE endpoints for that user's Portal session. The connection is opened on login/page-load and maintained for the session lifetime.
3. **Client→server: send messages** — The Portal sends user messages (new conversation, follow-up) as WebSocket events instead of POST requests that return SSE.
4. **Server→client: push events** — The server pushes conversation deltas, conversation completion, task status changes, and errors over the same WebSocket. Critically, the Tier 1 agent can now push multiple messages without the user asking (e.g., "task started" → "task finished, here's the summary").
5. **Auto-reconnect** — The Portal client reconnects automatically on connection loss with backoff, and re-subscribes to active conversations/tasks.

We are **not** yet implementing:

- Desktop WebSocket (desktop uses local agent runtime, not server)
- Multi-instance scaling (Redis-backed hub); in-memory hub is sufficient for now
- Cron or Telegram event types
- Worker→server transport change (worker still uses HTTP POST for deltas)

## Event protocol

All WebSocket messages are JSON with a standard envelope:

```json
{ "type": "<event_type>", "payload": { ... } }
```

### Client→server event types

| Type | Payload | Description |
|------|---------|-------------|
| `conversation.create` | `{ channel?, message }` | Create a new conversation (optionally with first message) |
| `conversation.message` | `{ conversation_id, content }` | Send a follow-up message to an existing conversation |
| `subscribe.conversation` | `{ conversation_id }` | Subscribe to events for a conversation (auto-done on create) |
| `subscribe.task` | `{ task_id }` | Subscribe to streaming output for a background task |
| `unsubscribe.task` | `{ task_id }` | Stop receiving task stream events |

### Server→client event types

| Type | Payload | Description |
|------|---------|-------------|
| `conversation.created` | `{ conversation_id }` | Conversation was created |
| `conversation.message.delta` | `{ conversation_id, delta }` | Streamed text chunk from Tier 1 agent |
| `conversation.message.completed` | `{ conversation_id, message_id? }` | Tier 1 turn finished; client should refetch messages |
| `conversation.error` | `{ conversation_id?, error }` | Error during conversation processing |
| `task.status.changed` | `{ task_id, status, title? }` | Background task status changed (PENDING → RUNNING → SUCCEEDED/FAILED) |
| `task.stream.delta` | `{ task_id, delta }` | Streamed output from a background task (Tier 2 via StreamHub) |
| `task.stream.done` | `{ task_id }` | Task stream completed |
| `system.error` | `{ error }` | Connection-level or system error |

## Deliverables

1. **Event protocol types** (`internal/wsconn/` — new package)
   - **`protocol.go`**: Go structs for the event envelope and all typed payloads (client→server and server→client). Shared by server handler and tests.
   - Keep the types minimal and extensible (new event types = new const + payload struct).

2. **WebSocket handler** (`internal/server/portal/ws_handler.go`)
   - **`wsHandler`**: HTTP upgrade handler. Auth: JWT from query param (`?token=...`) or first message. One goroutine reads client events, one goroutine writes server events.
   - **Read loop**: Dispatches client events to appropriate handlers:
     - `conversation.create` → calls `conversationService().HandleTurn` with a `wsSink` (WebSocket-backed StreamSink).
     - `conversation.message` → calls `conversationService().HandleTurn` for follow-up.
     - `subscribe.task` → subscribes to `StreamHub` for that task; forwards deltas/done as `task.stream.delta`/`task.stream.done`.
     - `unsubscribe.task` → unsubscribes from `StreamHub`.
   - **Write loop**: Receives events from an internal channel and writes them as JSON to the WebSocket. Handles backpressure (slow client → drop or buffer).
   - **`wsSink`**: Implements `llm.StreamSink` — `OnDelta` sends `conversation.message.delta` events to the write channel.
   - **Lifecycle**: On disconnect, clean up all subscriptions. On conversation turn complete, send `conversation.message.completed`.
   - Register route: `GET /api/ws` in `register.go`.

3. **Portal WebSocket client** (`portal/src/lib/api/ws.ts` — new)
   - **`WebSocketClient` class**: Manages the persistent connection.
     - `connect(token)`: Opens `ws(s)://host/api/ws?token=...`.
     - `send(event)`: Sends a typed client event.
     - `on(type, callback)`: Registers event handlers for server events.
     - `off(type, callback)`: Unregisters.
     - Auto-reconnect with exponential backoff (1s, 2s, 4s, … max 30s). On reconnect, re-subscribes to active conversations/tasks.
     - `close()`: Clean shutdown.
   - **`WebSocketProvider` React context** (`portal/src/contexts/WebSocketContext.tsx`): Provides the client instance to the component tree. Opens on auth, closes on logout.

4. **Portal conversation hooks update** (`portal/src/features/conversations/`)
   - **`useConversationDetail`**: Replace `addConversationMessageStream` (fetch+SSE) with WebSocket `send({ type: "conversation.message", ... })` + listen for `conversation.message.delta` / `conversation.message.completed` events.
   - **New conversation flow** (`ConversationDetail` page): Replace `createConversationStream` (POST+SSE) with WebSocket `send({ type: "conversation.create", ... })` + listen for `conversation.created` then deltas.
   - Remove or deprecate `readSSEStream` usage from conversation flows. Keep `sse.ts` for now (task streaming fallback or future removal).

5. **Portal task streaming update** (`portal/src/features/tasks/`)
   - **`useTaskDetail`**: Replace `subscribeTaskStream` (fetch+SSE to `GET /api/tasks/{id}/stream`) with WebSocket `send({ type: "subscribe.task", ... })` + listen for `task.stream.delta` / `task.stream.done`.
   - On unmount or navigation away, send `unsubscribe.task`.

6. **Keep SSE endpoints temporarily**
   - Do **not** remove the existing SSE endpoints (`GET /api/tasks/{task_id}/stream`, POST `?stream=1`). They remain as fallback and for non-Portal clients. Mark them as deprecated in code comments.
   - The conversation POST endpoints (without `?stream=1`) remain unchanged for non-streaming clients.

7. **Go dependency**
   - Add `github.com/gorilla/websocket` (or `nhooyr.io/websocket`) to `go.mod`. Gorilla is widely used and well-tested; nhooyr is more idiomatic but either is fine.

8. **Tests**
   - **`internal/wsconn/`**: Unit tests for event serialization/deserialization.
   - **`internal/server/portal/ws_handler_test.go`**: Integration test using `httptest` + WebSocket client: connect, send `conversation.create`, receive `conversation.created` + deltas + completed. Mock `conversationService`.
   - **Portal**: Manual testing (WebSocket connection, conversation flow, task streaming, reconnect).

## Out of scope (for later)

- Desktop WebSocket support (desktop uses local agent runtime)
- Redis-backed StreamHub for multi-instance scaling (current in-memory hub remains)
- Cron trigger events, Telegram events (future event types)
- Worker→server transport change (HTTP POST stays)
- Server-initiated proactive messages from Tier 2 results (this task establishes the transport; proactive push logic is a follow-up)
- Binary WebSocket frames or protocol buffers (JSON is sufficient)
- WebSocket compression (can add later if needed)
- Removing SSE endpoints (deprecate only in this task)
