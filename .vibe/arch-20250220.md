# Architecture Refactor Opportunities — internal/

**Scope:** `internal/` (all packages under internal).  
**Focus:** Package boundaries, dependency direction, layering, and structural clarity.  
**Date:** 2025-02-20.

---

## Summary

Analysis of `internal/` found **five** architecture-level opportunities: (1) unify workspace path layout across executor, servercmd, and server; (2) invert or relocate config → blob dependency; (3) introduce an agent-runner interface at the tools boundary; (4) centralize the worker API contract (DTOs) between server and executor; (5) reduce log package’s dependency on config. The rest of the layout (model/entity, server/executor boundaries, worker updater interface) is in good shape.

---

## 1. Unify workspace path layout (single source of truth)

| Field | Content |
|-------|--------|
| **Title** | Unify workspace path layout (single source of truth) |
| **Scope** | `internal/executor`, `internal/servercmd`, `internal/server` |
| **Current state** | Path layout is implemented in three places. **executor**: `WorkspacePaths` interface and `workspacePathsRoot` in `executor/paths.go` (e.g. `PersistentWorkspaceDir`, `RuntimeTaskRunBuildmaxDir`, `ArtifactDir(workspaceID, taskID, runID, artifactID)`). **servercmd**: `serverWorkspacePaths` in `servercmd/paths.go` implements the same interface with identical `filepath.Join` logic. **server**: `server/paths.go` has `workspacesDir()`, `persistentWorkspaceDir(workspaceID)`, `artifactDir(workspaceID, taskID, artifactID)` with a different signature (no `runID` in artifact dir). So the same conceptual layout is duplicated and can drift (e.g. server’s artifact path vs executor’s). |
| **Proposed change** | Define the workspace/task/run/artifact path layout in one place. Prefer keeping `executor.WorkspacePaths` as the contract and the single implementation (e.g. `executor.NewWorkspacePathsFromRoot(root)`). In **servercmd**, remove `serverWorkspacePaths` and use `executor.NewWorkspacePathsFromRoot(workspacesDir)` when constructing the scheduler or any component that needs paths. In **server**, either (a) inject a `WorkspacePaths`-like helper from config (built from the same root) and use it for `persistentWorkspaceDir` and artifact paths, or (b) add a thin adapter in server that delegates to an injected path provider so server does not reimplement path logic. Ensure server’s artifact path convention (if it differs) is aligned with executor’s so API and worker use the same layout. |
| **Benefit** | Single source of truth for layout; no drift between API file/artifact paths and executor materialize/artifact paths; easier to change layout in one place. |
| **Impact** | Medium |

## 2. Invert or relocate config → storage/blob dependency

| Field | Content |
|-------|--------|
| **Title** | Invert or relocate config → storage/blob dependency |
| **Scope** | `internal/config`, `internal/storage/blob` |
| **Current state** | `config` imports `storage/blob` in `workspace_storage.go` to build `PersistStorage` and `ArtifactStorage` (e.g. `BuildPersistStorage`, `BuildArtifactStorage`). Config also uses blob interfaces (e.g. `blob.PersistStorage`) as return types. So the “env and app config” package depends on the “blob storage implementation” package. Ideally config would only read env and return structs; concrete construction of storage would live in a composition root. |
| **Proposed change** | **Option A:** Move `BuildPersistStorage`, `BuildArtifactStorage`, and `BuildS3Client` (and any blob-specific env reading) into a separate package that both config and blob can depend on, or that is used only by composition roots (e.g. `internal/storage/setup` or `internal/config/storage`). Config then only exposes `LoadWorkspaceStorageConfig()` and perhaps generic helpers; the new package turns that config into blob implementations. **Option B:** Keep env reading in config but define storage factory interfaces in config (or a small subpackage); implement those factories in `servercmd` and `workercmd` by importing blob and config, so config itself does not import blob. Prefer the option that keeps `config` free of `storage/blob` so dependency direction is env → config → (no storage). |
| **Benefit** | Cleaner dependency direction; config becomes env-only and does not pull in storage implementations; blob remains a leaf; composition roots own wiring. |
| **Impact** | Medium |

## 3. Introduce agent-runner interface at tools boundary

| Field | Content |
|-------|--------|
| **Title** | Introduce agent-runner interface at tools boundary |
| **Scope** | `internal/tools`, `internal/agent`, `internal/cmd` (setup) |
| **Current state** | `tools` package imports `agent` (and `llm`) in `task.go` and `webfetch.go` to run subagent or LLM-backed behavior. So the “tools” layer depends directly on the “agent” package. This is a deliberate subagent pattern but couples tools to a concrete agent implementation and makes tools tests that need “run agent” harder (they currently pull in agent and llm). |
| **Proposed change** | Define an interface used by tools for “run agent / subagent” (e.g. `AgentRunner` or `SubagentRunner`: single method such as `Run(ctx, messages, opts) (reply, err)`). Place this interface in `tools` (or in a small shared package used by both tools and agent). Implement the interface in `agent` (e.g. a wrapper that calls `Process`). In `cmd/setup.go` (or wherever the tool set is built), inject this implementation when constructing tools that need it (e.g. task tool, webfetch). Tools then depend only on the interface, not on `agent` or `llm` directly. |
| **Benefit** | Clearer boundary; tools tests can mock the runner; agent and tools can evolve independently; possibility to swap implementations or move to separate modules later. |
| **Impact** | Medium |

## 4. Centralize worker API contract (DTOs)

| Field | Content |
|-------|--------|
| **Title** | Centralize worker API contract (DTOs) |
| **Scope** | `internal/server` (worker_handlers), `internal/executor` (worker_api) |
| **Current state** | The worker talks to the server via GET/PATCH `/api/worker/task-runs/{run_id}`. Request and response shapes are defined in **server**: `worker_handlers.go` has `getWorkerTaskRunResponse`, `getWorkerTaskRunRun`, `getWorkerTaskRunTask`, `patchWorkerTaskRunRequest`. The **executor** package has `WorkerHTTPUpdater` and the client that calls this API (in `worker_api.go`); it builds HTTP bodies and parses responses with equivalent or duplicated logic. So the “contract” (field names, status values, artifact payload) lives in two places and can drift. |
| **Proposed change** | Introduce a single place for the worker API contract: shared DTOs and (optionally) status constants. Options: (a) a small package `internal/workerapi` (or `internal/executor/contract`) that defines the request/response structs and JSON tags; both server and executor import it; (b) keep structs in executor and have server import executor for the contract (server would then depend on executor for types only). Prefer (a) so neither server nor executor “owns” the contract alone. Document the API (e.g. in the package doc or a short design note) so future changes are intentional. |
| **Benefit** | Single definition of the worker API contract; no drift between server and client; easier to version or evolve the API. |
| **Impact** | Low–Medium |

## 5. Reduce log package dependency on config

| Field | Content |
|-------|--------|
| **Title** | Reduce log package dependency on config |
| **Scope** | `internal/log`, `internal/config` |
| **Current state** | `log` package imports `config` (e.g. for `DataDir()` or similar to resolve log file path and possibly level). So any use of the log package pulls in config. In tests or in contexts where config is not used, this can be unnecessary or cause env/setup coupling. |
| **Proposed change** | Make log initialization accept explicit parameters (e.g. log directory path, level) instead of reading from config inside the log package. Callers (e.g. `cmd` entry points, `servercmd`, `workercmd`) load config and then call `log.Init(config.LogDir(), config.LogLevel())` (or equivalent). Log package then has no import of `config`. |
| **Benefit** | Log becomes a leaf package; easier to test and reuse in contexts that don’t use the full config; clearer dependency direction. |
| **Impact** | Low |

## What is already in good shape

- **model vs entity:** Domain types live in `model`; `entity` aliases them and implements stores. Single source of truth; server uses model for DTOs and entity for stores.
- **Server as HTTP boundary:** Server depends on entity/blob interfaces; composition root (servercmd) wires concrete stores and storage. Clear.
- **Executor ↔ server worker API:** Executor defines `TaskRunUpdater`; worker uses `WorkerHTTPUpdater`; server implements the HTTP handlers that perform the store updates. Boundary is clear; only the DTOs are duplicated (addressed in opportunity 4).
- **Executor paths interface:** `WorkspacePaths` is injected for testability and avoids executor depending on config; the duplication is in the implementations (addressed in opportunity 1).
