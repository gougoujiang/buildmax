# Smell Proposal — Portal

## Scope

**Analyzed**

- Path: `portal/` — React + Vite + TypeScript app under `portal/src/` (lib, data, components, pages, contexts).
- Criteria: package boundaries, coupling, duplication, naming, error handling, dead code, alignment with project conventions.

## Addressed since last run

- **Artifact removal** (no backend API yet): Removed all artifact-related code: `ArtifactViewer` page deleted; artifact route and `Artifact` type removed from router and `lib/types`; artifact case removed from App `renderPage()`; Project page no longer shows an Artifacts section or accepts `artifacts` prop; Breadcrumbs and LeftSidebar no longer handle artifact routes; `MOCK_ARTIFACTS`, `listArtifactsForProject`, `listArtifactsForWorkspace`, `getArtifactById` removed from `data/mockData` and `data/index`. Artifacts can be reintroduced when the backend API exists.

## Summary

- **Proposals**: 9 (unchanged; proposal 1 simplified to projects/tasks only)
- **High priority**: 3 (mixed data sources for projects/tasks, API error handling duplication, App.tsx bloat)
- **Overview**: Main issues are (1) mixed API vs mock data causing Breadcrumbs/Activity to be wrong or inconsistent for projects and tasks, (2) repeated error-parsing and fetch patterns in `api.ts` and in App, (3) oversized AppContent with many responsibilities, (4) duplicated modal and status-icon logic, (5) dead or misleading UI (Login password, Quick Actions). handleRun on Projects should be implemented to submit a workspace-level (unbound) task.

## Proposals

### 1. Unify data source: stop mixing API and mock data

**Location**: `portal/src/App.tsx`, `portal/src/data/`, `portal/src/components/Breadcrumbs.tsx`, `portal/src/pages/Activity.tsx`

**Current state**

- App fetches workspaces, projects, and tasks from the API (`lib/api.ts`) but still uses `getTaskById` from `data/mockData.ts` for task-detail resolution. Breadcrumbs imports `getProjectById` from mockData — so project names in breadcrumbs come from mock only and will show "Project" for API-created projects. Activity uses `listTasksForWorkspace` and `getProjectById` from mockData, so it never shows API-created tasks. Task detail can be wrong when the task exists in API but not in mock.
- Two parallel data worlds make behavior inconsistent and hard to reason about.

**Proposed change**

- Introduce a single data layer for the UI: pass projects and tasks (or resolvers) from App so Breadcrumbs and Activity use API-sourced data. E.g. pass `projects` into Breadcrumbs and use `projects.find(p => p.id === projectId)`; have Activity receive tasks from a prop or a hook that uses API tasks for the current workspace. Ensure task-detail resolution in App uses the in-memory `tasks` list (or API) instead of `getTaskById` from mockData.

**Benefit**: Predictable behavior; breadcrumbs and activity reflect real workspace data; no silent mismatches.

**Priority**: High

### 2. Extract API error handling to remove duplication in api.ts

**Location**: `portal/src/lib/api.ts`

**Current state**

- Every function that checks `!res.ok` repeats the same block: `const text = await res.text()`, try/catch `JSON.parse(text)`, `msg = j.error ?? text`, then `throw new Error(msg)`. This appears many times (login, getWorkspaces, createWorkspace, getProjects, createProject, getTasks, createTask, uploadFiles, getFileTree, getFileContent).

**Proposed change**

- Add a helper, e.g. `async function throwIfNotOk(res: Response): Promise<void>` (or `parseErrorResponse(res): Promise<never>`) that reads response body, parses JSON for `error` when possible, and throws. Each API function calls `checkUnauthorized(res)`, then `if (!res.ok) await throwIfNotOk(res)` (or equivalent) before `return res.json()` / `return res.text()`.

**Benefit**: Single place for error parsing; easier to add logging or mapping; less copy-paste.

**Priority**: High

---

### 3. Split AppContent: extract data and routing

**Location**: `portal/src/App.tsx` — `AppContent` and `renderPage()`

**Current state**

- AppContent is ~220 lines and holds: auth gate, workspace list fetch, project fetch (effect + refetch), task fetch (effect + refetch), redirect effect, workspace create state/handlers, and a large `renderPage()` switch with repeated fallback logic (fallbackHome, fallbackProject, getProjectById). Multiple responsibilities in one component make it hard to test and change.

**Proposed change**

- Extract a custom hook, e.g. `useWorkspaceData(token, route)`, that returns `{ workspaces, projects, tasks, loadingWorkspaces, refetchProjects, refetchTasks }` and encapsulates the three useEffects and refetch callbacks. Optionally extract route→page resolution into a small function or component that takes `route`, `projects`, `tasks`, and token and returns the page element (so the big switch lives in one place). Keep AppContent as orchestration: use the hook, handle redirect, call render helper, render AppShell + modal.

**Benefit**: Smaller App; fetch and refetch logic testable in isolation; clearer separation of data vs layout.

**Priority**: High

---

### 4. Extract shared modal component from CreateWorkspaceModal and CreateProjectModal

**Location**: `portal/src/components/CreateWorkspaceModal.tsx`, `portal/src/components/CreateProjectModal.tsx`

**Current state**

- Both modals share the same structure: overlay (onClick close), modal container (role="dialog", stopPropagation), header (title + close button), body (form with label/input, error, actions Cancel/Submit). Same effects: reset form and focus when `open` becomes true; Escape to close. Only differences are title, form fields (one vs two), and submit payload (name vs name+description). This is duplicated layout and behavior.

**Proposed change**

- Introduce a reusable component, e.g. `BaseModal` or `FormModal`, with props: `open`, `title`, `onClose`, `children` (or `fields` + `onSubmit` with a render-prop for the form body). CreateWorkspaceModal and CreateProjectModal become thin wrappers that pass title and form content. Alternatively, a single `CreateEntityModal` with a type discriminator and optional description field. Ensure Escape and overlay click behavior live in one place.

**Benefit**: One place for modal UX and a11y; less duplication when adding another create flow.

**Priority**: Medium

---

### 5. Extract statusIcon to a shared helper or component

**Location**: `portal/src/pages/Project.tsx` (lines 16–29), `portal/src/pages/Activity.tsx` (lines 9–22)

**Current state**

- `statusIcon(status: Task["status"]): string` is duplicated in Project and Activity with identical switch/cases (success → ✅, running → ⏳, failed → ❌, etc.). Same logic in two files.

**Proposed change**

- Move to a shared module, e.g. `portal/src/lib/taskStatus.ts` or inside `lib/types.ts` as a helper, and export `taskStatusIcon(status: Task["status"]): string`. Use it in both Project and Activity.

**Benefit**: Single source of truth for status display; easier to add tooltips or labels later.

**Priority**: Low

---

### 6. Remove or use Login password field

**Location**: `portal/src/pages/Login.tsx`

**Current state**

- The form includes a "Password" input and `password` state, but `login(email)` only sends `email` to the API. The password is never used. This is misleading for users and adds dead code.

**Proposed change**

- Either remove the password field and state (if the API is email-only magic link or similar), or wire password into the API call when the backend supports it. If removing, keep the form accessible (single email field, submit).

**Benefit**: No dead state; form matches actual auth contract.

**Priority**: Medium

---

### 7. Implement handleRun on Projects page; clarify Quick Actions

**Location**: `portal/src/pages/Projects.tsx`

**Current state**

- `handleRun()` only does `console.log("Run (no-op):", prompt.trim())`. QUICK_ACTIONS buttons have an empty `onClick` (`/* no-op */`). These are placeholders that look like real actions and add noise.

**Proposed change**

- **handleRun**: Implement it to submit a task that is **not** bound to any project. Call the existing task API (e.g. `createTask(workspaceId, { input: prompt.trim() }, token)` with no `project_id`) so the user can run an intent from the workspace home. After success, refresh or show the new task (e.g. refetch a workspace-level task list if available, or navigate to Activity). This matches the workspace-level prompt: "What would you like to accomplish?"
- **Quick Actions**: Either wire each button to set the prompt and optionally trigger the same submit flow, or remove Quick Actions until they have defined behavior. Prefer one clear path: Run creates a workspace-level (unbound) task.

**Benefit**: Honest, working Run from Projects; no misleading no-op.

**Priority**: Medium

---

### 8. Pass project lookup into Breadcrumbs instead of importing mockData

**Location**: `portal/src/components/Breadcrumbs.tsx`

**Current state**

- Breadcrumbs imports `getProjectById` from `../data/mockData`. So breadcrumb labels for "Project" come only from mock data. When projects are from the API (as in current App), names won’t match and the second crumb will often show "Project".

**Proposed change**

- Have App (or a parent that has `projects`) pass a resolver, e.g. `getProjectById: (id: string) => Project | undefined`, or pass `projects` and let Breadcrumbs do `projects.find(p => p.id === projectId)`. Breadcrumbs no longer imports mockData; it receives data from the same source as the rest of the app.

**Benefit**: Breadcrumbs reflect actual workspace/project data; aligns with proposal 1.

**Priority**: High (if done as part of data unification); otherwise Medium

---

### 9. Reduce repeated fallback JSX in App renderPage()

**Location**: `portal/src/App.tsx` — `renderPage()` switch

**Current state**

- For routes "project" and "task", the same fallback pattern repeats: if entity missing or workspace mismatch, return `fallbackHome` or `fallbackProject(project)`. The JSX for fallbackHome and fallbackProject is defined inside renderPage and reused in multiple branches, but the branching logic is verbose and repeated (get entity → if !entity || workspace mismatch → return fallback).

**Proposed change**

- Extract a small helper, e.g. `function resolveProjectPage(route, projects, ...): ReactNode` that returns either the project/task view or the fallback. Or compute "effective view" (entity + fallback type) in one place and then map to a single switch that renders either entity detail or fallback. Reduces duplication in the switch body.

**Benefit**: Shorter, clearer routing logic; one place to change fallback behavior.

**Priority**: Medium

---

### 10. Optional: use a single loading flag for projects and tasks

**Location**: `portal/src/App.tsx`

**Current state**

- App uses `loadingProjects` and `loadingTasks` only via their setters (to trigger refetch); the values are never read for UI (e.g. showing a spinner). So `const [, setLoadingProjects] = useState(false)` and same for tasks are effectively unused for display. If loading states are not shown, consider removing them or replacing with a single "content loading" state that the shell can use.

**Proposed change**

- If loading indicators are not required for this slice, remove the unused state variables or use a single `loading` derived from refetch in progress. If loading indicators are desired, expose loading state to the shell or page and show a lightweight spinner/skeleton when projects or tasks are loading.

**Benefit**: Less unused state; clearer intent (either use loading in UI or drop it).

**Priority**: Low
