# Task 094: Two-tier agent — Phase 4 — Webhook adapter

## Goal

Add a Tier 1 webhook channel adapter and rule-based conversation path so that incoming webhook HTTP requests (no LLM at Tier 1) map to a single Tier 2 ChatRun, with optional callback on run complete.

## Context

- **Design:** [design/007-two-tier-agent.md](../../design/007-two-tier-agent.md) §2.2 (Tier 1 not always LLM), §5 (ChannelAdapter, ConversationEngine), §8 Phase 4.
- **Current code:** `internal/conversation` has `ConversationTurn`, `ConversationResult`, and channel constants (`ChannelPortal`, `ChannelCron`, `ChannelWebhook`). It does **not** currently define `ChannelAdapter` or `ConversationEngine` interfaces (they were in the design but never added). The Tier 1 entry point is `internal/app/conversation.Service.HandleTurn(HandleTurnCmd)`, which branches on ChatID (create run only) vs ConversationID (LLM RunLoop); there is no path for channel=webhook.
- **Chat/run creation:** `internal/app/chat.Service` provides `StartBackgroundChat` (new chat + first run) and `CreateRun` (new run on existing chat). Both go through quota and stores.
- **Where this fits:** New interfaces and webhook adapter live in `internal/conversation`; rule-based engine in `internal/app/conversation` or `internal/server`. Server registers the webhook route and optional config.

## Definitions (this task)

- **ChannelAdapter:** Interface: `Receive(ctx, raw) (ConversationTurn, error)` and `Send(ctx, conversationID, output) error`. The webhook adapter implements this; it normalizes the HTTP request into a `ConversationTurn` (channel=webhook). `Send` is used optionally to deliver run result (e.g. POST to callback URL or log).
- **Rule-based engine:** For turns with channel=webhook, no LLM; resolve workspace (required) and optional chat_id from turn; create one ChatRun (create new chat via StartBackgroundChat if no chat_id, else CreateRun on existing chat); return `ConversationResult` with exactly one TaskID. No conversation history.
- **Webhook trigger:** Input is HTTP request body (JSON). Workspace from header or path; message from configurable JSON path (e.g. `body.message`) or template. Optional: callback URL in payload or config; on run complete, POST result to that URL.

We are **not** implementing:

- Cron adapter or cron endpoint (deferred to a future task; without in-process cron scheduler, cron is a separate concern).
- Telegram/IM (Phase 3 LLM engine with different adapter).
- Task decomposition (Phase 5).
- Full retry or custom headers for callbacks.

## Deliverables

1. **`internal/conversation`**
   - **interfaces.go (new):** Define `ChannelAdapter` (Receive, Send) and `ConversationEngine` (Process(ctx, workspaceID, chatID string, turn ConversationTurn) (ConversationResult, error)) with doc comments. Match design §5.

2. **Webhook adapter**
   - **Type** implementing `ChannelAdapter`. Receive: raw = HTTP request (or a struct with body, headers, path). Workspace from header (e.g. `X-Workspace-ID`) or path (e.g. `/api/webhook/workspaces/{id}/...`). Message from body via configurable JSON path (e.g. `message`, `body.text`) or env default path; if path missing, return error. Produce `ConversationTurn` with Channel=ChannelWebhook. Optional: store callback URL in turn.Raw for later Send. Send: if callback URL present, POST run result (e.g. JSON with run_id, status, summary) to that URL. Location: e.g. `internal/conversation/webhook_adapter.go` or `internal/server/webhook/`.

3. **Rule-based engine**
   - **Type** implementing `ConversationEngine`. Process(ctx, workspaceID, chatID, turn): only accept turn.Channel == ChannelWebhook; else error. If chatID empty: call ChatService.StartBackgroundChat(workspaceID, userID from turn, turn.Message, nil, nil) and return ConversationResult{ TaskIDs: [runID] }. If chatID non-empty: call ChatService.CreateRun(ctx, chatID, turn.Message, turn.UserID) and return ConversationResult{ TaskIDs: [runID] }. Requires ChatService. Location: `internal/app/conversation` (e.g. RuleBasedEngine); constructor takes *chat.Service.

4. **Server HTTP endpoint**
   - **Webhook:** Register `POST /api/workspaces/{id}/webhook`. Body: JSON. Auth: **per-workspace API keys** — caller sends key (e.g. `Authorization: Bearer <key>`); server resolves key to workspace via WorkspaceWebhookKeyStore and requires path workspace_id to match; 401 if key invalid, 403 if path mismatch. Handler: parse body, call webhook adapter Receive, validate workspace exists, call rule-based engine Process, return 202 with `{ "task_id": "<chat_run_id>" }` or 400/401/403/404/500. Optional: accept callback_url in body and store for run-complete notification. Key management: API to create/list/revoke webhook keys per workspace (e.g. POST/GET/DELETE /api/workspaces/{id}/webhook-keys); keys stored hashed; plaintext returned once on create.

5. **Run-complete callback (optional minimal)**
   - When a run created from webhook completes, optionally POST to a callback URL. Document the intended callback payload shape; implement at least one of: log on complete, or POST to URL stored in request (e.g. webhook body). If implementing POST, use a small helper that sends JSON `{ "chat_run_id", "status", "reply_summary" }` to the URL.

6. **Webhook API keys (per workspace)**
   - Entity and store: WorkspaceWebhookKey (workspace_id, key_hash, name, created_at); WorkspaceWebhookKeyStore (CreateKey, GetWorkspaceIDByKey, ListKeys, RevokeKey). Keys created via API return plaintext once; only hash stored. Backend: portal endpoints to create/list/revoke keys (POST/GET/DELETE /api/workspaces/{id}/webhook-keys); only workspace owner can manage.
   - **Portal UI — workspace settings (webhook keys):** A workspace settings page (or a "Webhook" / "API keys" section in existing workspace settings) where the user can: (1) **Create** a webhook key — button opens flow that calls POST webhook-keys, then shows the new key **once** (with copy button and warning that it won’t be shown again); (2) **List** existing keys — table/cards with name (or label), created date, last used (optional); no plaintext; (3) **Revoke** a key — delete control per row, calls DELETE webhook-keys/{id}. Access: only for workspace owner (or same auth as other workspace management). If the project has no workspace settings page yet, add one with at least the webhook keys section; otherwise add the section to the existing page.

7. **Config / env**
   - Document (and add to `internal/config` if needed): webhook message JSON path (e.g. env or default `message`), optional BUILDMAX_WEBHOOK_USER_ID. Add to `.env.example` and `config/env_spec.go`. No global webhook secret (auth is per-workspace API keys).

8. **Documentation**
   - Short doc (in design folder or README): how to configure webhook (per-workspace API keys, payload shape, callback format).

9. **Tests**
   - Unit tests: webhook adapter Receive (given body/headers → correct ConversationTurn; invalid path → error). Rule-based engine Process (webhook turn → one run created, correct TaskIDs; wrong channel → error).
   - Optional: integration test for webhook: POST to webhook endpoint → 202 and one PENDING run in store.

## Out of scope (for later)

- **Cron adapter and cron endpoint** (future task; without in-process cron scheduler, cron is a separate concern).
- Telegram/IM adapter (use Phase 3 LLM engine).
- Task decomposition (Phase 5).
- Retry logic or custom headers for callback POST.
- Quota for webhook (can be same as portal or disabled for system user; clarify in design if needed).

## Acceptance

- [ ] `internal/conversation` defines `ChannelAdapter` and `ConversationEngine` interfaces.
- [ ] Webhook adapter type implements `ChannelAdapter`; Receive produces ConversationTurn from HTTP request (workspace from header/path, message from configurable JSON path).
- [ ] Rule-based engine implements `ConversationEngine`; Process creates exactly one ChatRun (new chat or existing) for webhook turns and returns one TaskID; rejects other channels.
- [ ] Server exposes POST webhook endpoint (workspace in path or header); returns 202 with task_id when successful.
- [ ] Optional callback: run complete triggers log or POST to URL; callback payload shape documented.
- [ ] Per-workspace webhook API keys: WorkspaceWebhookKey entity and store; webhook handler validates key and path workspace_id; key management API (create/list/revoke) for workspace owners.
- [ ] Workspace settings UI: page or section where user can create (see key once), list, and revoke webhook API keys for the current workspace; same access control as workspace owner.
- [ ] New env keys (if any) added to config and .env.example; documentation for webhook configuration (no global secret).
- [ ] Unit tests for webhook adapter and rule-based engine; optional integration test for webhook → one run.
