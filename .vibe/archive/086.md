# Task 086: Allow user to see usage at settings page

Let the user view their usage (quota/limits) on the Portal settings page.

---

## Goal

Expose the current user’s quota usage and tier limits via a read-only API and show them in the existing Portal Settings modal so the user can see how much of their run and token quota they have used in the current period.

## Context

- **Task 085** introduced per-user quota: tier on `User`, `quota_tier` table with limits (max_runs_per_period, max_tokens_per_period, period_days), and `UserUsageInWindow` for run count and token sum in a rolling window. Create-chat and create-run return 429 when over limit. Portal UI for showing usage was explicitly out of scope and is this task.
- **Portal**: `SettingsModal` in `portal/src/components/SettingsModal.tsx` exists and is opened from the Sidebar; the modal body is currently a placeholder. API calls use `portal/src/lib/api` with `authHeaders(token)` and `getApiBase()`.
- **Server**: JWT auth via `requireAuth(w, r, s.cfg.JWTSecret)` returns userID. Server already has `UserStore`, `UsageInWindowReader`, `QuotaTierStore` (and optionally `QuotaChecker`); no existing “current user usage” endpoint.
- **Conventions**: API JSON snake_case; entity IDs and table names per AGENTS.md; no new runtime dependencies.

## In scope

1. **Backend: GET endpoint for current user usage**
   - New route: `GET /api/usage` (or `GET /api/me/usage`). Authenticated only (JWT); 401 when not logged in.
   - Response (snake_case): current usage in the user’s tier window, plus tier and limits:
     - `run_count`, `total_tokens` — usage in the current period (same semantics as `UserUsageInWindow`: runs where chat.created_by = user, run created_at in window; tokens = run tokens + chat title tokens in window).
     - `tier` — resolved tier name (user’s QuotaTier or default from config).
     - `period_days` — from tier (e.g. 30).
     - `max_runs_per_period`, `max_tokens_per_period` — from tier; when user has no tier or tier not found, omit limits or return nulls so the UI can show “No limit” or hide limits.
   - Window: rolling window as in quota checker (end = now, start = now - period_days * 86400). Use the same logic as `internal/quota` (or call a small shared helper) so the numbers match what enforcement uses.
   - No new store interfaces required: use existing `UserStore.GetUser`, `UsageInWindowReader.UserUsageInWindow`, `QuotaTierStore.GetQuotaTier`, and default tier from config.

2. **Portal: Settings modal usage section**
   - In `SettingsModal`, add a “Usage” (or “Quota”) section that:
     - Calls the new GET usage API with the current auth token (from AuthContext or equivalent).
     - Displays: tier name; “Runs: X / Y” (and optionally “Tokens: A / B”); period description (e.g. “Rolling 30 days”). If the API does not return limits (no tier or unknown tier), show usage only (e.g. “Runs: X”, “Tokens: A”) or “No limit” as appropriate.
   - Handle loading and error states (e.g. show a message or placeholder if the request fails or 401).

3. **OpenAPI**
   - Document `GET /api/usage` (or chosen path) and the response schema in `static/openapi.json`.

## Out of scope

- Changing quota enforcement or tier configuration (085).
- Per-workspace usage; only current user’s usage.
- Historical usage over multiple periods or charts.
- Self-service tier change or billing/upgrade UI.

## Deliverables

- **Server**: New handler for `GET /api/usage` (or `GET /api/me/usage`) that returns usage + tier + limits for the JWT user; uses existing entity/store and config; OpenAPI updated.
- **Portal**: `SettingsModal` updated with a usage section that fetches and displays run/token usage and tier limits (with clear handling when limits are absent).
- **Tests**: Handler test for the new endpoint (auth required; mock store returning user, tier, usage); optional unit test for usage response shape.

## Acceptance criteria

- [ ] `GET /api/usage` (or chosen path) requires JWT; returns 401 without valid token.
- [ ] With valid JWT, response includes `run_count`, `total_tokens`, `tier`, `period_days`, and when tier exists: `max_runs_per_period`, `max_tokens_per_period`; window matches quota enforcement (rolling period_days).
- [ ] Portal Settings modal shows the current user’s usage (runs and tokens) and tier limits when available; handles missing/unknown tier without breaking the UI.
- [ ] OpenAPI documents the new endpoint and response.
- [ ] New handler is covered by tests (auth and response shape).
