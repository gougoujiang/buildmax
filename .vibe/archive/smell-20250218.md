# Smell Proposal — internal/server middlewares

## Scope

**Analyzed**

- Path: `internal/server` (all middlewares in the package)
- Focus: Should the package’s HTTP middlewares be consolidated into one file?

**Current middleware layout**

| Location        | Symbol                     | Signature / role |
|----------------|----------------------------|-------------------|
| `cors.go`      | `corsMiddleware`           | `(h http.Handler, allowedOrigin string) http.Handler` — CORS headers + OPTIONS handling |
| `worker_auth.go` | `(*Server).workerAuthMiddleware` | `(next http.HandlerFunc) http.HandlerFunc` — worker token (Bearer or X-Worker-Token) |
| `server.go`    | `requestLoggingMiddleware` | `(h http.Handler) http.Handler` — request logging (method, path, remote) |

Note: `auth.go` provides `requireAuth` and `withWorkspaceAuth` — these are per-handler helpers called inside handlers, not chain middlewares; they are out of scope for this consolidation.

## Summary

- **Proposals**: 2
- **High priority**: 1
- **Overview**: The three chain middlewares live in three places (two dedicated files and one inline in `server.go`). Consolidating them into a single `middleware.go` improves discoverability and keeps all “wrap the request/response” logic in one place. The combined file remains small (~65–70 lines).

---

## Proposals

### 1. Consolidate all middlewares into one file (middleware.go)

**Location**: `internal/server/cors.go`, `internal/server/worker_auth.go`, `internal/server/server.go` (lines 111–127)

**Current state**

- **cors.go** (20 lines): only `corsMiddleware`. Single-responsibility file but finding “all middlewares” requires opening multiple files.
- **worker_auth.go** (28 lines): only `workerAuthMiddleware`. Same as above.
- **server.go**: contains `requestLoggingMiddleware` (~17 lines) alongside `Server`, `New`, routing, and static handlers. Middleware is mixed with bootstrap and routing.

So “where are the middlewares?” is answered by three different files. There is no single place that defines the middleware layer.

**Proposed change**

- Add **`internal/server/middleware.go`** and move into it:
  - `corsMiddleware` (from `cors.go`)
  - `requestLoggingMiddleware` (from `server.go`)
  - `(*Server).workerAuthMiddleware` (from `worker_auth.go`)
- Delete **`cors.go`** and **`worker_auth.go`** after the move.
- In **`server.go`**, remove the `requestLoggingMiddleware` function body; keep the `New` logic that composes the chain (CORS → logging) unchanged; no change to how `workerAuthMiddleware` is used on worker routes.

Imports in `middleware.go`: `net/http` and `strings` (for worker auth). No new dependencies.

**Benefit**: One file answers “what middlewares do we have?” Easier to add or change cross-cutting behavior (e.g. tracing, panic recovery) in the future. `server.go` becomes focused on wiring and bootstrap.

**Priority**: High

### 2. Optional: standardize middleware signature to http.Handler

**Location**: `internal/server` — after Proposal 1, within `middleware.go`

**Current state**

- `corsMiddleware` and `requestLoggingMiddleware` take and return `http.Handler`.
- `workerAuthMiddleware` takes and returns `http.HandlerFunc`. Call sites use it with `s.workerAuthMiddleware(s.getWorkerTaskHandler)` where handlers are already `HandlerFunc`; the middleware could equally wrap `http.Handler` and call `next.ServeHTTP(w, r)`.

Having one middleware use `HandlerFunc` and the others use `Handler` is a minor inconsistency and can confuse when adding new middlewares (which type to use).

**Proposed change**

- Change `workerAuthMiddleware` to accept `http.Handler` and return `http.Handler`:
  - Signature: `func (s *Server) workerAuthMiddleware(next http.Handler) http.Handler`
  - Body: call `next.ServeHTTP(w, r)` instead of `next(w, r)`.
- Update the two call sites in `server.go` to pass `http.HandlerFunc(s.getWorkerTaskHandler)` and `http.HandlerFunc(s.patchWorkerTaskHandler)` (or keep the same call if the type converts automatically; in Go, `HandlerFunc` implements `Handler`, so wrapping a `HandlerFunc` in a middleware that takes `Handler` only requires the middleware to accept `Handler` — the existing `s.getWorkerTaskHandler` is already a `HandlerFunc`, which is an `Handler`, so `s.workerAuthMiddleware(s.getWorkerTaskHandler)` would still type-check if the middleware is `func(next http.Handler) http.Handler` because `HandlerFunc` implements `Handler`).
- No change to CORS or request-logging signatures.

**Benefit**: All three middlewares use the same contract (`Handler → Handler`), making the stack easier to reason about and document.

**Priority**: Low (optional refinement; current code works and is clear enough)
