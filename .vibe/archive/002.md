# Task 002 - Basic Agent Loop (with Tool Calling)

## Goal

Implement the core AI agent loop in `internal/agent`: **receive input → call LLM → on tool_calls, execute tools and re-call LLM → produce final reply**. The loop supports tool/function calling so the agent can use tools within a single user turn.

## Context

- We have `internal/llm.Client` with `Chat(ctx, userMessage) (string, error)` (single-turn, no tools). It will need to be extended (or a new method) to support requests with tools and to return tool_calls when the model requests them.
- `internal/agent/agent.go` is currently a stub.
- OpenAI-compatible APIs (and go-openai) support tool/function calling; we use that for the typical agent pattern.

## Agent Loop (this task)

For Task 002, the **agent loop** is one user turn with optional tool use:

1. **Input**: one user message (string). (Conversation history across turns is out of scope.)
2. **Loop**:
   - Call the LLM with the current message list (initially just the user message) and the list of available tools (name, description, parameters schema).
   - If the response has **tool_calls**: for each call, invoke the corresponding tool with the given arguments, append tool results to the message list, and call the LLM again with the updated messages.
   - If the response is **final content** (no tool_calls): exit the loop and return that content.
3. **Output**: the final assistant reply (string) or an error.
4. **Safeguards**: cap the number of loop iterations (e.g. max 10) to avoid infinite loops; return an error if exceeded.

We are **not** implementing in this task:

- Multi-turn conversation history (previous user/assistant turns across invocations).
- Streaming responses.
- Hooking the agent into the TUI (separate task).

## Deliverables

1. **`internal/agent`**
   - **Tool interface**: a single tool is something the agent can invoke by name. Required: name (string), description (string), parameters schema (e.g. JSON Schema for the arguments), and `Execute(ctx, args map[string]any) (result string, err error)`. The agent receives a list of tools (e.g. `[]Tool` or a registry) at construction or before `Process`.
   - **Agent struct**: holds an LLM client (or interface that can send chat-with-tools and return content/tool_calls), a list of tools, and config (e.g. max iterations).
   - **Constructor**: e.g. `NewAgent(llmClient, tools []Tool, opts ...Option)` so the app can build the agent from config.
   - **Process**: one method that takes context + user message, runs the loop (LLM → execute tool_calls if any → LLM again until final reply), and returns the final assistant reply and error. Signature idea: `Process(ctx context.Context, userMessage string) (reply string, err error)`.
   - No TUI or Bubble Tea imports in this package.

2. **`internal/llm`**
   - **Chat with tools**: extend the client (or add a method) so the agent can send a list of messages and a list of tool definitions, and receive either assistant content or tool_calls (and optionally content). The agent will use this to drive the loop. Exact signature is left to implementation (e.g. `ChatWithTools(ctx, messages, tools) (content string, toolCalls []ToolCall, err error)` or a struct for the response).

3. **Minimal integration**
   - A way to exercise the loop: e.g. from `cmd/buildmax` or a test that composes config → LLM client → agent with at least one tool → one `Process` call. Can be a test-only path or a temporary CLI flag.

4. **Tests**
   - Unit test: mock LLM that returns one tool_call; mock tool that returns a fixed string; mock LLM then returns final text. Assert `Process` returns that final text and that the tool was executed (e.g. via mock assertion).
   - Unit test: mock LLM that returns final text with no tool_calls; assert `Process` returns that text and no tool is executed.
   - No real API calls in tests.

## Out of scope (for later)

- Conversation history (multi-turn context across user messages).
- Streaming responses.
- TUI integration.
- Concrete built-in tools (e.g. search, run command, read file); this task is about the **mechanism** (interface + loop). Adding specific tools can be a follow-up task.

## Acceptance

- [ ] Tool interface is defined (name, description, parameters, `Execute`) and Agent accepts a list of tools.
- [ ] LLM client supports chat-with-tools (messages + tool definitions in, content and/or tool_calls out).
- [ ] Agent loop: when the LLM returns tool_calls, the agent executes them, appends results, and calls the LLM again; when the LLM returns final content, the agent returns it.
- [ ] Max-iterations (or similar) safeguard is in place to avoid unbounded loops.
- [ ] Unit tests pass: (1) tool_call path with mock LLM and mock tool, (2) no-tool path with mock LLM. No live API.
