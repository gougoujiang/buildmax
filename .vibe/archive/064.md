# Task 064: Upload session file and log file to MinIO after task finish

## Goal

After a task run finishes, persist the worker’s buildmax directory (session files, log file, settings) to object storage when MinIO is configured, so humans can inspect what happened in a task without relying on local worker disk.

## Context

- **Current layout**: For a workspace we have persist (uploads), tasks (runtime), and artifacts (result files). Persist and artifacts already support both local FS and MinIO (`BUILDMAX_PERSIST_STORAGE`, `BUILDMAX_ARTIFACT_STORAGE`). Task runtime stays on local disk because the agent process runs there.
- **Worker flow**: `executor.RunTask` creates the task’s buildmax dir, sets `BUILDMAX_HOME` to it, runs `buildmax -p`, then writes `result-<taskID>.md` and uploads it via `ArtifactStorage`. Session and log files are written by the CLI under that same buildmax dir.
- **Buildmax dir contents** (under `paths.RuntimeTaskBuildmaxDir(workspaceID, taskID)` = `.../workspaces/<id>/tasks/<id>/buildmax`):
  - `logs/buildmax.log` — rotated log from `internal/log`
  - `sessions/sessions.json` — session list index
  - `sessions/<session_id>.json` — one or more session files (one per run)
  - `settings.json` — settings under that DataDir
- **Storage**: `internal/storage/blob` has `PersistStorage` (Put/Get/List/MaterializeToDir) with keys `prefix/workspaceID/persist/<relPath>`. Task buildmax files should live under `prefix/workspaceID/tasks/<taskID>/buildmax/...` (same logical layout as local path) so they are traceable and not mixed with persist uploads.

## In scope

1. **Two-mode behavior**
   - When persist storage is **local_fs**: no upload (files remain only on worker disk).
   - When persist storage is **minio**: after the agent run (success or failure), upload the buildmax files listed above to MinIO at `prefix/workspaceID/tasks/<taskID>/buildmax/...`, mirroring the local structure.

2. **Placement**
   - Upload is **post–agent run** (after `buildmax -p` exits), inside worker logic (`internal/executor` or called from it). It runs on both success and failure so logs/sessions are available for failed runs too.

3. **Key layout in MinIO**
   - Object keys: `<prefix>/<workspaceID>/tasks/<taskID>/buildmax/<relPath>`, e.g. `workspaces/ws1/tasks/task1/buildmax/logs/buildmax.log`, `.../buildmax/sessions/sessions.json`, `.../buildmax/settings.json`. No change to existing `persist/` keys.

4. **Files to upload**
   - `logs/buildmax.log` (if present)
   - `sessions/sessions.json` (if present)
   - All `sessions/*.json` (session list + individual session files)
   - `settings.json` (if present)
   - Skip or tolerate missing files (e.g. no log if logging failed); do not fail the task when a single file is missing.

## Out of scope

- API or UI to download/view these files from the Portal (only storage and key layout).
- Changing where the CLI writes session/log/settings (still under BUILDMAX_HOME).
- Uploading task files when persist is local_fs (no-op).
- Retries or background upload; upload is best-effort after run (log and continue if upload fails, do not mark task as failed solely due to upload failure unless product decision says otherwise — for this task, best-effort is acceptable).

## Deliverables

1. **Key helper** (in `internal/storage/blob`)
   - Function or key builder for task-buildmax object keys: `prefix/workspaceID/tasks/taskID/buildmax/<relPath>`, with safe relPath validation (no path escape).

2. **Upload path**
   - Extend `PersistStorage` with a method to write task buildmax files (e.g. `PutTaskBuildmax(ctx, workspaceID, taskID, relPath string, r io.Reader) error`), or add a small helper that uses existing `Put` with a different key convention. If the interface gains a new method, **local_fs** implementation is no-op (return nil); **S3/MinIO** implementation performs PutObject with the task-buildmax key.

3. **Executor**
   - After `buildmax -p` exits (both success and failure paths), call the upload step: walk the buildmax dir for the four file sets above and upload each existing file. Use `WorkspacePaths.RuntimeTaskBuildmaxDir` for the local path and the same workspaceID/taskID for the remote key. Use the same `PersistStorage` (or new interface) passed into `RunTask`; behavior is driven by persist provider (local_fs vs minio).

4. **Config**
   - No new env vars: reuse `BUILDMAX_PERSIST_STORAGE` (and existing MinIO env). When it is `minio`, task buildmax upload is enabled; when `local_fs`, no-op.

## Acceptance criteria

- [ ] With `BUILDMAX_PERSIST_STORAGE=local_fs`, running a task leaves buildmax files only on worker disk; no upload attempted.
- [ ] With `BUILDMAX_PERSIST_STORAGE=minio` and MinIO configured, after a task run (success or failure), objects exist under `prefix/<workspaceID>/tasks/<taskID>/buildmax/` for each of: `logs/buildmax.log`, `sessions/sessions.json`, `sessions/<id>.json`, `settings.json` (when present on disk).
- [ ] Missing files (e.g. no log file) do not fail the task; upload is best-effort per file.
- [ ] Key layout does not use `persist/` for task buildmax (so ListFiles for persist and task buildmax stay separate).
- [ ] Existing tests (e.g. executor tests) still pass; add or adjust tests as needed for the new upload path (e.g. fake storage that records PutTaskBuildmax or equivalent calls).
