# Task 036: User login

## Goal

Add user login and logout so the BuildMax server can identify users and the portal is protected: unauthenticated users see a login page; after login they see the app and can logout to return to the login page.

## Context

- **Server**: `internal/server` provides HTTP server with `/healthz`, `/openapi.json`, `/swagger/`. No database or auth yet.
- **Portal**: React (Vite + TypeScript) under `portal/`; hash routing, `AppShell` + `TopBar` (currently "Profile" placeholder). No API client or auth.
- **Database**: Docker Compose runs MySQL 8 on `localhost:3306`; database name, user, and password for the app are all `buildmax` for local dev. Env overrides: `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` (and `MYSQL_HOST`, `MYSQL_PORT` if needed).
- **Conventions**: AGENTS.md — persisted data uses snake_case in JSON; backend in Go; portal is a separate frontend that will call the Go API.

## User login (this task)

For this MVP:

1. **User table**: Single table with `id`, `email`, `name`, `created_at`. Stored in MySQL; schema created via auto-migration in dev.
2. **Login**: One login API. Request: email (and optionally password in body for future use). Server checks that a user with that email exists; if so, issues a JWT and returns it with minimal user info (e.g. id, email, name). No password verification in this task.
3. **Logout**: Client-side only: discard token and redirect to login page. No server logout endpoint required.
4. **Portal**: First screen is a login page (email + password fields). On successful login, store token (e.g. in memory or localStorage), show the main app, and show user name in the top-right (profile area). Logout clears token and shows login again.

We are **not** yet implementing:

- Password hashing or verification.
- User registration or admin-created users (assume users are pre-seeded or inserted out-of-band for MVP).
- Refresh tokens or token revocation.
- Protected API routes that require JWT (can be a follow-up; this task focuses on login endpoint and portal UX).

## Deliverables

1. **Backend (Go)**
   - **User storage**: Add a user table (id, email, name, created_at) and a DB layer (e.g. `internal/store` or `internal/db`) with MySQL. Use a single, small migration or auto-migrate in dev (e.g. GORM AutoMigrate or manual DDL). DB connection config: read from env (defaults: host localhost, port 3306, database/user/password `buildmax`).
   - **Login API**: `POST /api/login` (or `POST /login`) — body: `{ "email": "..." }`. Look up user by email; if found, issue a JWT (e.g. with user id and optional expiry), return JSON `{ "token": "...", "user": { "id", "email", "name" } }`. If not found, return 401. Use a small JWT library (e.g. golang-jwt/jwt); signing key from env (e.g. `BUILDMAX_JWT_SECRET`).
   - **OpenAPI**: Document the login endpoint in the server’s OpenAPI spec.
   - **Server wiring**: Pass DB and JWT config into server; register the login handler. No auth middleware on other routes in this task.

2. **Portal (React)**
   - **Login page**: New page/view when not authenticated: form with email and password (password can be ignored by backend for MVP; still collect for future use). Submit calls the login API; on success, store token and user info (e.g. React state + localStorage or context), then show the main app.
   - **Route guard**: If no valid token, show login page instead of workspace/project UI. If token present, show existing App shell and routes.
   - **Profile + logout**: In TopBar (top-right), show the logged-in user’s name and a Logout action. On logout, clear token and user state and show login page again.

3. **Integration**
   - **API base URL**: Portal must call the backend (e.g. `VITE_API_BASE` or default `http://localhost:5678`). Login request: `POST <base>/api/login` (or agreed path) with JSON body.
   - **Tests**: Backend: unit or integration test for login (e.g. with test DB or mock: user exists → 200 + token; user missing → 401). No real external API calls in tests.

## Out of scope (for later)

- Password verification and hashing.
- User registration or admin UI for users.
- Refresh tokens, token blacklist, or server-side logout.
- Protecting other API routes with JWT middleware.
- Session list or chat in the portal.

## Acceptance

- [ ] Server has a user table (id, email, name, created_at) and DB connection config from env; auto-migration runs in dev so tables exist without manual DDL.
- [ ] `POST /api/login` (or agreed path) accepts `{ "email": "..." }`, returns 200 with `{ "token": "...", "user": { "id", "email", "name" } }` when user exists, and 401 when not.
- [ ] JWT is signed with a secret from env; token is usable for future auth (e.g. can be decoded and contains user id).
- [ ] OpenAPI spec documents the login endpoint.
- [ ] Portal shows a login page when not authenticated; after successful login, main app (workspace/projects) is shown.
- [ ] TopBar shows logged-in user name and a Logout control; logout clears auth state and shows the login page again.
- [ ] At least one backend test covers login (success and/or not-found).
