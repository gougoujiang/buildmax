# Task 077: Task detail page redesign

## Goal

Redesign the Portal chat detail page to be **conversation-centric**: a single chat-style view with history and input, aligned with the workspace/chat model and current backend (chats, conversation API, runs). Remove legacy sections that are placeholders or duplicate intent.

## Context

- **Current page**: `portal/src/pages/ChatDetail.tsx` — shows header (title + disabled Restore), Follow-up, Result (chat.summary), Agent session (conversation messages), What changed, Evidence/Data used, Details (status + time).
- **Backend**: `getChatConversation(workspaceId, chatId)` returns `ApiSession` with `messages[]` (`role`, `content`, `tool_calls`). `createChatRun(workspaceId, chatId, { input })` starts a run; frontend polls `getChats` until terminal status then refetches conversation. No API changes required for this task.
- **Concepts**: One chat = one conversation thread; runs extend it. User sees “chat” in the UI; “task” in the spec title refers to the same detail view (chat run / conversation).

## In scope

1. **Layout**
  - Exactly two main sections: **(1) Chat history** (conversation), **(2) Chat input** (follow-up).
  - Optional minimal header: chat title only (no Restore button, or keep disabled if product wants it; no separate “Details” block).
2. **Chat history**
  - Render `session.messages` in **chat style**:
    - **User** messages: aligned right (e.g. bubble on the right).
    - **Assistant** and **tool** messages: aligned left (bubbles on the left).
  - Keep existing behavior: markdown for `content`, tool calls shown (name + arguments) for assistant messages that have `tool_calls`.
  - Empty state: when there are no messages, show a short message (e.g. “No messages yet” or “Start the conversation below”).
  - Loading and error states for `getChatConversation` unchanged (loading copy, error message).
3. **Chat input**
  - Single input area at the bottom (textarea + submit button), same behavior as current “Follow-up”: submit calls `createChatRun`, then poll until terminal status and refetch conversation. No UX change to flow; only placement and labeling (e.g. “Send” or “Ask follow-up”).
  - Disable input while a run is in progress; show loading state on submit.
4. **Removals**
  - Remove the **Result** section (no longer show `chat.summary` as a separate block).
  - Remove the **What changed** section (placeholder only).
  - Remove the **Evidence / Data used** section (placeholder only).
  - Remove the **Details** section as a separate block. Status and time can appear in the header (e.g. subtitle or small text under title) so the user still sees run state.
5. **Styles**
  - Update `portal/src/css/pages/chat-detail.css` (or equivalent) so that:
    - User messages are right-aligned with a distinct bubble style.
    - Assistant and tool messages are left-aligned with a distinct bubble style.
  - Remove or repurpose styles for the removed sections. Keep markdown and tool-call styles for message content.

## Out of scope

- Backend or API changes (conversation and runs APIs stay as-is).
- Restore button behavior (can remain disabled; implementing restore is a separate task).
- Showing multiple “runs” or run history in the same view (current model: one conversation per chat; runs append to it).
- Artifact/content modal or artifact list changes.
- Changes to other pages (WorkspaceHome, Chats, Sidebar, router).

## Deliverables

- `**portal/src/pages/ChatDetail.tsx`**: Restructure to two sections (chat history + chat input); remove Result, What changed, Evidence/Data used, Details; render messages in chat layout (user right, assistant/tool left); optional header with title and status/time.
- `**portal/src/css/pages/chat-detail.css**`: Chat-bubble layout and alignment (user right, assistant/tool left); remove or simplify styles for deleted sections; keep message content (markdown, tool calls) readable.

## Acceptance criteria

- Chat detail page shows only: (1) chat history in chat style, (2) chat input at bottom. No Result, What changed, Evidence/Data used, or Details sections.
- User messages appear right-aligned; assistant and tool messages appear left-aligned, with clear visual distinction (e.g. bubbles or background).
- Conversation content is unchanged: markdown rendered for message content; tool calls (name + arguments) shown where present.
- Follow-up flow works as before: user can type and submit; new run is created; UI polls until terminal status and refetches conversation; new messages appear in the chat history.
- Loading and error states for conversation are still shown (no regression).
- Chat title is still visible; status and/or time are visible (e.g. in header) so the user knows run state.
- No new backend or API calls; no changes to other Portal pages beyond ChatDetail and its CSS.
