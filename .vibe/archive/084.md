# Task 084: Metering

## Goal

Record LLM token usage (prompt and completion tokens) per agent run and persist it on chat runs so usage can be reported and aggregated later (e.g. for billing or observability).

## Context

- **LLM today**: `internal/llm` uses go-openai; we do not read or expose usage. **Usage shape**: Both non-stream and stream responses use the same `usage` object: `prompt_tokens`, `completion_tokens`, `total_tokens`, and optionally `cost`, `prompt_tokens_details`, `cost_details`, `completion_tokens_details` (e.g. OpenRouter). Non-stream: top-level `usage` on the completion response. Stream: `usage` appears in a chunk (often the one before the final DONE). We can use a single `Usage` type and only persist the token counts for metering; optional fields like `cost` are out of scope for this task.
- **Agent**: `internal/agent` has `RunStats` with only `ToolCalls`; the loop calls `ChatWithTools` or `ChatWithToolsStream` and does not receive or accumulate token counts.
- **Chat runs**: `internal/model` `ChatRun` has no token fields. Worker reports success via `workerapi.PatchChatRunRequest` (status, ended_at, output, artifact); server persists via `UpdateChatRunStatus` and `OnRunComplete`. The worker runs `buildmax -p` in a run directory; the CLI has no direct channel to the server except by writing files in the run dir (e.g. `global/`) which the worker can read and send in PATCH.
- **Conventions**: AGENTS.md (snake_case for JSON/DB); singular table names; entity IDs in `internal/util`.

## Scope

**In scope**

- Capture token usage from the LLM API in both modes: non-streaming from the completion response; streaming by checking each stream chunk for a `usage` field and using/accumulating it when present (e.g. chunk before final DONE).
- Expose usage from the agent (e.g. add to `RunStats`) and persist it for **chat runs**: store on `ChatRun` and send from worker via PATCH when a run succeeds.
- Worker path: when the CLI runs in a worker context (run directory with `global/`), write usage to a well-known file under run `global/` after the agent completes; worker reads it and includes usage in the success PATCH.
- **Session persistence**: Save accumulated usage in the persisted session JSON file (`<session_id>.json`). For multi-turn conversations, usage should accumulate across turns: after each agent reply, add that turn’s token counts to the session’s running totals and persist (so the file always has the cumulative prompt_tokens and completion_tokens for the whole session).

**Out of scope**

- Dashboard or Portal UI for usage.
- Per-user or per-workspace aggregation API or reporting.
- Billing integration or pricing.
- Relying on request-only options for streaming usage; we use whatever chunks already carry a `usage` field.

## Deliverables

1. **LLM layer**
  - **Types**: In `internal/llm`, add a small `Usage` type (e.g. `PromptTokens`, `CompletionTokens`, `TotalTokens` int) and have the client return it where the API provides it.
  - **Non-streaming**: `ChatWithTools` should return usage (or zero value) from the completion response. Signature change: add a way to return usage (e.g. extra return value or struct that includes content, toolCalls, usage).
   - **Streaming**: In `ChatWithToolsStream`, inspect each stream chunk (e.g. `stream.Recv()` response). If a chunk contains a `usage` field (prompt_tokens, completion_tokens, total_tokens), capture it. Typically the provider sends usage in the chunk before the final DONE; we may accumulate across chunks or take the last non-zero usage so that the function returns the same shape as non-streaming (content, toolCalls, usage). If no chunk has usage, return zero usage.
2. **Agent layer**
  - **RunStats**: Extend `RunStats` with token counts (e.g. `PromptTokens`, `CompletionTokens` int) and accumulate them across loop iterations in `processLoop`.
  - **Contract**: When the LLM returns usage, add it to the accumulated RunStats; when it does not (e.g. streaming without usage), leave counts at zero.
3. **Chat run persistence**
  - **Storage choice — columns on `chat_run` (recommended)**: Add optional columns to the existing `chat_run` table (e.g. `prompt_tokens`, `completion_tokens`). Usage is 1:1 with a run (one run = one aggregate usage); the worker already PATCHes the run on success, so sending usage in the same request and writing the same row is simple. No new table or join. Aggregation (e.g. "total tokens for workspace") is a SUM over `chat_run` joined with `chat`. A **separate usage/tracing table** would make sense later if we need multiple usage records per run (e.g. per LLM call) or usage not tied to a chat run; for this task we persist one aggregate per run, so columns on `chat_run` are sufficient.
  - **Model**: Add optional `PromptTokens` and `CompletionTokens` (or equivalent snake_case JSON/DB columns) to `ChatRun` in `internal/model`. Keep them nullable (pointer or 0 = not set).
  - **Store**: Extend `UpdateChatRunStatus` (and any `UpdateChatRunStatusIf` usages that need to set usage) to accept optional usage fields and persist them. Extend `OnRunComplete` or the PATCH path so that when a run completes with artifact, usage is stored if provided.
  - **Worker API**: Extend `workerapi.PatchChatRunRequest` with optional `prompt_tokens` and `completion_tokens`. Server worker handler applies them when updating the run (e.g. on status SUCCEEDED).
4. **Worker path (CLI → run dir → worker → PATCH)**
  - **CLI**: When running in a worker context, the CLI can detect the run directory (e.g. presence of a well-known path or env from the worker). After `Process` returns, if usage is available and we are in a run dir, write a small JSON file (e.g. `global/usage.json` or similar under BUILDMAX_HOME) with `prompt_tokens` and `completion_tokens`.
  - **Worker**: Before calling PATCH for success, read that usage file from the run `global` dir (if present) and include the values in `PatchChatRunRequest`. Do not fail the run if the file is missing or invalid.
5. **Session file (accumulated usage)**
  - **Session format**: Add optional `prompt_tokens` and `completion_tokens` (snake_case) to the persisted session JSON; they represent the **cumulative** token counts for the whole session across all turns.
  - **Session type**: Session holds accumulated usage (two ints); after each agent reply, the caller adds that turn’s `RunStats` token counts to the session (e.g. `AddUsage(prompt, completion int)`) and then persists. On load, session file may omit the fields (old files) → treat as 0; when present, restore into session so the next turn adds on top.
  - **Call sites**: Wherever we persist the session after an assistant reply (CLI print mode and TUI), call `session.AddUsage(stats.PromptTokens, stats.CompletionTokens)` before `PersistAfterReply` so the saved file has the updated totals.

6. **Tests**
  - Unit or integration tests: LLM client returns usage when the API provides it (mock response); agent RunStats accumulates usage across multiple loop iterations; store and worker API round-trip usage (optional: handler test that PATCH with usage persists to DB). Session: save/load round-trip with usage; AddUsage then persist increases stored totals; load of old file (no usage fields) yields 0,0.
  - No new frontend tests.

## Out of scope (for later)

- Dashboard/UI for usage; per-user or per-workspace aggregation API; billing integration.
- Forcing streaming to include usage if the provider does not support it.

## Acceptance

- LLM client exposes usage from the completion response; `ChatWithTools` (and `ChatWithToolsStream` if supported) return token counts; agent `RunStats` includes prompt and completion token counts and accumulates them across iterations.
- `ChatRun` has optional prompt_tokens and completion_tokens; PATCH worker API accepts and persists them; worker reads usage from run global when present and sends it on success PATCH.
- CLI in worker context writes usage to run global after Process; worker includes it in success PATCH so that completed chat runs have token counts stored.
- Session JSON includes optional `prompt_tokens` and `completion_tokens`; Session has AddUsage and accumulates across turns; after each reply, callers add stats to session then persist; multi-turn sessions show cumulative usage in the file.
- Tests cover: client usage extraction (mocked), agent accumulation, session save/load with usage and accumulation, and optionally store/PATCH persistence of usage.
