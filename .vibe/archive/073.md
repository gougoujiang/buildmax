# Task 073: Align concepts frontend and backend

## Goal

Rename backend terminology from **task** / **task_run** to **chat** / **chat_run** so that API, storage, and code match the frontend’s existing concepts (workspace, agent, chat, artifact). The frontend will then use **chat** / **chat_run** in types and API calls consistently. No backward compatibility is required.

## Context

- **Current state**
  - **Frontend**: Routes and UI already use “chat” / “chats” (e.g. `chat`, `chats`, `newChat`). Domain types in `portal/src/lib/types.ts` still use `Task` and `taskId`; API layer uses `ApiTask`, `task_id`, `/tasks`, `createTask`, `getTasks`, etc.
  - **Backend**: Model has `Task` and `TaskRun`; DB tables `task` and `task_run`; API paths `/api/workspaces/{workspace_id}/tasks`, `.../tasks/{task_id}/runs`, `.../tasks/{task_id}/conversation`; JSON fields `task_id`, `task_run_id`, `run_id`. Worker API: `/api/worker/task-runs/{run_id}`. Storage (entity + blob), executor, config paths (e.g. `RuntimeTaskBuildmaxDir`), and worker binary flag `--task-run-id` all use “task” / “task_run”.
- **Where this fits**: Backend: `internal/model`, `internal/storage/entity`, `internal/storage/blob`, `internal/server`, `internal/workerapi`, `internal/executor`, `internal/config`, `internal/servercmd`, `cmd/buildmax-worker`. Frontend: `portal/src/lib/types.ts`, `portal/src/lib/api/types.ts`, `portal/src/lib/api/index.ts`, `portal/src/lib/api/mappers.ts`, and all components/hooks that reference tasks (e.g. `taskId`, `getTasks`, `createTask`).
- **Conventions**: AGENTS.md (singular table names, snake_case for JSON and persisted keys). After 072, project is removed; tasks (chats) and artifacts are workspace-scoped only.

## Scope

**In scope**

- **Backend renames (concepts only; behavior unchanged)**  
  - **Model & DB**: `Task` → `Chat`, `TaskRun` → `ChatRun`; table names `task` → `chat`, `task_run` → `chat_run`; column/JSON names `task_id` → `chat_id`, `task_run_id` → `chat_run_id` (and `run_id` where it denotes the run’s id can stay or become `chat_run_id` per design).  
  - **HTTP API**: Paths `/tasks` → `/chats`, path param `task_id` → `chat_id`; POST `.../chats/{chat_id}/runs`; GET `.../chats/{chat_id}/conversation`. Request/response JSON: `task_id` → `chat_id`, `task_run_id` → `chat_run_id` where applicable.  
  - **Worker API**: Path `/api/worker/task-runs/{run_id}` → `/api/worker/chat-runs/{run_id}`; response types and JSON fields use `chat_id` / `chat_run_id` as decided in design.  
  - **Storage**: Entity layer (TaskStore → ChatStore, TaskRunStore → ChatRunStore, method params and return types); blob interfaces and keys (e.g. `tasks/<id>/<runId>` → `chats/<id>/<runId>` or keep param names chatID/runID).  
  - **Executor, runner, worker binary**: Types and flags (e.g. `--task-run-id` → `--chat-run-id`), log/slog keys, and config path helpers (e.g. `RuntimeTaskBuildmaxDir` → `RuntimeChatBuildmaxDir` or equivalent).  
  - **OpenAPI**: Paths and schema names/fields updated to chat/chat_run.  
- **Frontend alignment**  
  - **Types**: `Task` → `Chat`, `taskId` → `chatId` in `portal/src/lib/types.ts`; remove any remaining `projectId` from Task/Artifact if not done in 072.  
  - **API types**: `ApiTask` → `ApiChat`, `ApiTasksListResponse` → `ApiChatsListResponse`, `CreateTaskRunResponse` → `CreateChatRunResponse`; request/response fields `task_id` → `chat_id`, `task_run_id` → `chat_run_id`.  
  - **API layer**: `getTasks` → `getChats`, `getTasksPaginated` → `getChatsPaginated`, `createTask` → `createChat`, `createTaskRun` → `createChatRun`, `getTaskConversation` → `getChatConversation`; URLs use `/chats` and `chat_id` path/query params; `getArtifacts` options `taskId` → `chatId`.  
  - **Mappers**: `apiTaskToTask` → `apiChatToChat`; map `chat_id` etc. to `chatId`.  
  - **Components and hooks**: All usages of `task`, `taskId`, `getTasks`, `createTask`, `createTaskRun`, `getTaskConversation`, and artifact `taskId` updated to chat naming (e.g. `chatId`, `getChats`, `createChat`, `createChatRun`, `getChatConversation`). Routes already use “chat”/“chats”; ensure route params and API calls use the new chat IDs and endpoints.

**Out of scope**

- Changing behavior of chats or runs (scheduling, execution, artifacts, conversation).  
- Backward compatibility: no support for old `task`/`task_run` API or DB schema.  
- New features (e.g. new endpoints or UI).
