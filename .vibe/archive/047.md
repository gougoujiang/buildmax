# Task 047: Task Executor

## Goal

Add a background task executor to `buildmax server` that picks up PENDING tasks from the database, runs the `buildmax` CLI agent on each one, and writes the result back — so that tasks submitted from the portal actually get executed by the AI agent.

## Context

- Portal creates tasks via `POST /api/workspaces/{workspace_id}/tasks` → DB row with status `PENDING`
- No execution exists yet — tasks just sit in the database
- The `buildmax -p "<prompt>"` CLI already works: runs the agent loop, prints output to stdout
- Workspace directories live at `config.WorkspacesDir()/<workspace_id>/`

## In Scope

### 1. Task executor (backend — new package `internal/executor`)

- A `Runner` that starts as a **goroutine inside `buildmax server`** on startup and stops on shutdown
- **Polls the DB every 5 seconds** for the oldest PENDING task (FIFO by `created_at`)
- **Processes one task at a time** (no concurrency for MVP)
- For each PENDING task:
  1. Update status to `RUNNING`, set `started_at`
  2. Resolve workspace directory: `config.WorkspacesDir()/<workspace_id>/`
  3. Spawn `buildmax -p "<task.input>"` with CWD set to the workspace directory
     - `buildmax` is assumed available in PATH
     - Child process inherits the server's environment (API keys, model config, etc.)
  4. Wait for the process to complete, capture stdout as the result
  5. Write the result to `<workspace_dir>/result-<task_id>.md`
  6. Update the task row: set `output`, `status` (SUCCEEDED or FAILED), `ended_at`, and `error_message` if failed
- Graceful shutdown: when the server receives SIGINT/SIGTERM, stop picking new tasks; if a task is running, wait for it to finish (or kill after a timeout)

### 2. TaskStore additions (backend — `internal/store`)

- `GetNextPendingTask(ctx) (*Task, error)` — returns the oldest PENDING task (by `created_at`), or `(nil, nil)` if none
- `UpdateTaskStatus(ctx, taskID, status string, startedAt, endedAt *int64, output, errorMessage *string) error` — updates task fields

### 3. Server wiring (backend — `internal/cmd/server.go` + `internal/server`)

- Start the executor when `buildmax server` starts, pass it the TaskStore
- Stop the executor on server shutdown

### 4. Portal — Activity section improvements

- **Project page** (`ProjectDashboard.tsx`): the Activity section already exists and lists tasks; ensure tasks are shown in **descending order** (newest first) — reverse the array in the frontend
- For each task, show a clickable icon/link to view the output
- Navigating to `TaskDetail` page is sufficient for viewing output (it already shows `task.summary` which maps from `output`)
- Add a "pending" status icon for PENDING tasks (currently mapped to "running" — add a distinct icon)

## Out of Scope

- Concurrent task execution (worker pool) — future improvement
- Per-task model selection — future improvement
- Configurable polling interval — future improvement
- Task cancellation from portal — future improvement
- Streaming output / live progress — future improvement
- Task timeout / max runtime — future improvement (for MVP, let it run until done)

## Acceptance Criteria

- [ ] When a task is created from the portal, the executor picks it up within ~5 seconds and starts running it
- [ ] The task status transitions: PENDING → RUNNING → SUCCEEDED (or FAILED)
- [ ] The agent output is saved to `result-<task_id>.md` in the workspace directory
- [ ] The task's `output` column in DB contains the agent's response
- [ ] On failure (non-zero exit, binary not found), status is FAILED with `error_message` set
- [ ] The executor stops cleanly on server shutdown
- [ ] The portal's project page shows tasks in newest-first order
- [ ] PENDING tasks show a distinct status icon in the portal
- [ ] Clicking a task navigates to TaskDetail where the output is visible
- [ ] `go build ./...` and `go test ./...` pass
