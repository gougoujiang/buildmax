# Task 060: Cmd binary split part 2 — executor (worker)

## Goal

Separate “run one task” (worker) from “schedule and poll” (scheduler) by introducing a dedicated worker binary (`buildmax-worker`). The worker talks to the server via HTTP API for task metadata and status; it accesses MinIO (or local storage) directly for workspace materialize and artifact blobs. The scheduler remains in the server process and spawns the worker as a local subprocess; future k8s job mode is out of scope.

## Context

- **Current state (after 059)**: `buildmax-server` runs the HTTP API and the task executor. The executor (`internal/executor.Runner`) does both: (1) poll for PENDING tasks and (2) execute each task in-process (materialize workspace, run `buildmax -p`, update DB and artifacts).
- **Desired split**: (1) **Scheduler** — poll loop in the server process; for each pending task, spawn worker with **task id only** (`--task-id`), wait. (2) **Worker** — separate binary that receives only task id; uses **HTTP API** to get task details (by task_id only, since task_id is unique) and to update task status/results; generates **session_id** internally (for RUNNING and for buildmax); uses **direct MinIO (or local) storage** for materialize and artifact blobs; runs **buildmax** (agent CLI) to finish the task. This enables later running the worker as a k8s job.
- **Existing pieces**: `entity.TaskStore` has `GetTask`, `GetNextPendingTask`, `UpdateTaskStatus`; server has list/create tasks and artifact list/content; executor uses `WorkspacePaths`, persist/artifact storage, and runs `exec.Command("buildmax", "-p", ...)`.

## In scope

- New **worker binary** `buildmax-worker`: entry point with **`--task-id` only** (no `--session-id`; session_id is generated inside the worker and used when marking RUNNING and when running buildmax). Communicates with the server via **HTTP API** for getting task details and updating task status/results. Accesses **MinIO (or local_fs) storage directly** for materialize and artifact blobs. Inside the worker, still runs **buildmax** (agent CLI) to execute the task — unchanged. Exit 0 on success, non-zero on failure.
- **Server API for worker**: **Task-id-only endpoints** so the worker does not need workspace_id (task_id is unique across workspaces): (1) **Get task**: e.g. `GET /api/worker/tasks/{task_id}` returning task details (workspace_id, task_id, input, status, etc.); (2) **Update task status/result**: e.g. `PATCH /api/worker/tasks/{task_id}` (status, session_id, ended_at, output, error_message, artifact registration). Worker auth (e.g. shared token) for these endpoints.
- **Executor package refactor**: Runner (scheduler) keeps only poll loop, TaskStore, and spawning the worker; run-one-task logic moves into the worker binary and uses API + direct storage.
- **Build and docs**: `make build` builds all three binaries (buildmax, buildmax-server, buildmax-worker). AGENTS.md updated. Config/env for worker: server base URL, worker auth token, worker binary path (for scheduler), storage env for direct MinIO/local access.

## Out of scope

- **K8s job mode**: Running the worker as a k8s job instead of a local process is a later task.
- **Configurable CLI path**: No change to how the worker invokes `buildmax -p`; making the CLI path configurable remains out of scope unless needed.
- **Distribution / install**: No new packaging or install targets.

## Deliverables

1. **Worker–server HTTP API (task-id-only)**
   - **Get task**: `GET /api/worker/tasks/{task_id}` — returns task details (workspace_id, task_id, input, status, etc.). Task ID is unique globally, so the worker does not need workspace_id. Protected by worker auth.
   - **Update task status / result**: `PATCH /api/worker/tasks/{task_id}` (or equivalent) — body: status, session_id (when setting RUNNING), ended_at, output, error_message; optionally artifact registration (artifact_id, seq, relative_path) when task succeeds (worker uploads blob to MinIO directly; server records artifact metadata).
   - **Worker auth**: Validate worker token (e.g. `Authorization: Bearer <token>` or `X-Worker-Token`) for `/api/worker/` routes. Token from env `BUILDMAX_WORKER_TOKEN`. Document in env_spec and .env.example.

2. **New worker entry**
   - **`cmd/buildmax-worker/main.go`**: Parse **`--task-id`** only (required). Load config from env: server URL (`BUILDMAX_SERVER_URL`), worker token (`BUILDMAX_WORKER_TOKEN`), storage (MinIO or local_fs). Worker: (1) calls `GET /api/worker/tasks/{task_id}` to get task (including workspace_id); (2) if task is not PENDING, exit (e.g. already claimed); (3) generates **session_id** internally; (4) PATCH task to RUNNING with session_id; (5) builds workspace paths and persist/artifact storage from config; (6) materializes workspace to local dir; (7) runs **buildmax -p** with session_id in that dir; (8) updates task to SUCCEEDED/FAILED via API and writes artifact to storage + registers via API if needed. Exit 0 on success, non-zero on failure.

3. **internal/executor**
   - **RunTask** (or equivalent): Function used by the worker binary: takes task (from API), sessionID (generated in worker), WorkspacePaths, PersistStorage, ArtifactStorage, and an API client for updating task status and registering artifacts. Contains: materialize → run buildmax -p → write result file → update status via API → upload result to storage and register artifact via API.
   - **Runner (scheduler)**:
     - Struct: `tasks` (TaskStore), `pollInterval`, `stopCh`, `doneCh`, `workerPath` (string). No paths, persist, artifactStorage.
     - Constructor: `NewRunner(taskStore entity.TaskStore, workerPath string)`. Worker path from env `BUILDMAX_WORKER_BINARY` (default `"buildmax-worker"`).
     - **loop**: GetNextPendingTask; `exec.Command(workerPath, "--task-id", task.TaskID)` with inherited env; wait. No session_id passed; worker claims the task (PATCH RUNNING with its own session_id) and performs all execution and status/result updates via API and direct storage.

4. **internal/servercmd**
   - **RunServer**: Build executor.Runner with `NewRunner(st, workerPath)` where workerPath from config (e.g. `BUILDMAX_WORKER_BINARY` or `"buildmax-worker"`). Server still builds persist/artifact storage and workspaces dir for the HTTP server and API; only the Runner is slimmed (no storage passed into Runner).

5. **Config / env**
   - **Worker binary path**: `BUILDMAX_WORKER_BINARY` default `"buildmax-worker"` (scheduler uses this to spawn the worker).
   - **Worker → server**: `BUILDMAX_SERVER_URL` (e.g. `http://localhost:5678`), `BUILDMAX_WORKER_TOKEN` (required for worker auth).
   - **Storage**: Worker uses same storage env as server (`BUILDMAX_PERSIST_STORAGE`, `BUILDMAX_ARTIFACT_STORAGE`, MinIO vars, workspaces dir) so it can access MinIO (or local_fs) directly. Document in env_spec and .env.example.

6. **Make and AGENTS.md**
   - **make**: `build` builds all three binaries: buildmax, buildmax-server, buildmax-worker. Clean removes buildmax-worker. `run server` builds and runs buildmax-server (spawns buildmax-worker when a task runs); document that buildmax-worker must be on PATH or same dir, and that worker needs BUILDMAX_SERVER_URL and BUILDMAX_WORKER_TOKEN (and storage env) when run.
   - **AGENTS.md**: Describe third binary (cmd/buildmax-worker, buildmax-worker), worker–server API and direct MinIO access, and three-binaries layout.

7. **Tests**
   - Executor: Unit test that Runner (scheduler) invokes worker command with expected args (`--task-id` only).
   - Worker: Test missing `--task-id` exits non-zero; optional test that worker calls API and storage with mocks.
   - Server: Tests for worker API (`GET/PATCH /api/worker/tasks/{task_id}`) and worker auth.
   - `go build ./cmd/buildmax`, `go build ./cmd/buildmax-server`, `go build ./cmd/buildmax-worker` and `go test ./...` pass.
