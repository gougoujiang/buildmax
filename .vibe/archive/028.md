# Task 028: Multiple model support

## Goal

Add a centralized settings file (`settings.json`) under the application data directory that defines a list of LLM models; at startup the app loads this file and uses the first configured model by default, falling back to the existing env-based single model when the file is missing or has no models.

## Context

- **Current behaviour**: `internal/config` provides `LoadLLM()` which reads a single LLM config from env (`OPENROUTER_API_KEY`/`BUILDMAX_API_KEY`, `BUILDMAX_BASE_URL`, `BUILDMAX_MODEL`). `internal/cmd/setup.go` calls `config.LoadLLM()`, builds the LLM client and agent, and passes `cfg.Model` as `ModelName` in `setupResult` (used by TUI footer and prompt mode).
- **Where it fits**: Config lives in `internal/config`; `llm.NewClient(config.LLM)` and `setupAgentAndSession` are the consumers. Settings file is the **primary** source for the model list when present; env remains the **fallback** when no file or no models.
- **Conventions**: AGENTS.md §6.1 — persisted JSON uses **snake_case** keys. Data dir is `config.DataDir()` (default `~/.buildmax`, override via `BUILDMAX_HOME`). Do not create the settings file in this task; only read it.

## In scope

- **Settings file path**: `DataDir()/settings.json` (e.g. `~/.buildmax/settings.json`). Expose via a helper (e.g. `SettingsPath()`) or inline where used; no creation of file or directory in this task.
- **Settings JSON shape**: A single root object with a `models` array. Each entry has: `model` (required, string, model ID), `name` (optional, string, for display), `api_url` (required), `api_key` (required). Other top-level keys are allowed for future use and must be ignored when parsing.
- **Load at startup**: Load settings when building the effective LLM config (e.g. from `setupAgentAndSession` or a new config loader). If the file does not exist, is invalid JSON, or `models` is missing/empty, use the existing env-based default: same behaviour as current `LoadLLM()`.
- **Effective model**: Use the **first** model in the list. No UI or CLI to choose a different model in this task.
- **Integration**: `setupAgentAndSession` (or equivalent) obtains `config.LLM` from “first model from settings or LoadLLM()”, so the rest of the stack (LLM client, agent, TUI model name) is unchanged except for the source of that config.
- **Display name**: When present, use the model entry’s `name` for display (e.g. TUI footer); otherwise use `model` (ID).

## Out of scope

- **Model selection UI/CLI**: Choosing a model other than the first (e.g. dropdown, flag) is a later task.
- **Creating or editing settings.json from the app**: No “first run” write of a default file; no config subcommand or TUI to edit settings in this task.
- **Env overriding file**: When settings exist and have at least one model, do not merge with env for that model’s api_key/base_url/model; use the file only. Env is only used when falling back (no file or empty models).
- **Validation beyond “has required fields”**: No URL format or key format checks; invalid values will surface at LLM call time.

## Deliverables

1. **`internal/config`**
   - **Types**: A struct for the settings file root (e.g. `Settings`) with a `Models` field (slice of model entries). A model entry struct with `Model`, `Name`, `APIURL`, `APIKey`, with `json:"model"`, `json:"name"`, `json:"api_url"`, `json:"api_key"` (snake_case on disk).
   - **Loader**: A function that reads `DataDir()/settings.json` and returns the parsed struct (or an error). Missing file or invalid JSON: return a sentinel/empty result so callers can fall back. Empty or missing `models`: treat as “no models”.
   - **Effective LLM**: A function that returns the “effective” `config.LLM` and display name: if settings exist and `models` has at least one entry, use the first entry (map to `config.LLM`, display name = entry’s `name` or `model`); otherwise use `LoadLLM()` and use `cfg.Model` as display name.
   - **Path helper** (optional but useful): e.g. `SettingsPath() string` returning `filepath.Join(DataDir(), "settings.json")`.
   - Keep `LoadLLM()` for fallback and for tests that rely on env-only config.

2. **`internal/cmd/setup.go`**
   - Replace the use of `config.LoadLLM()` in `setupAgentAndSession` with the new “effective LLM” loader. Use the returned display name for `setupResult.ModelName` (so TUI and prompt mode show the chosen label).

3. **Tests**
   - Unit tests for the config package: load from a temp file (valid JSON with one or more models); missing file → fallback; empty `models` → fallback; invalid JSON → fallback. No real API calls.

4. **Build and test**
   - `go build ./...` and `go test ./...` pass. Existing tests that depend on env-only behaviour should still pass (e.g. with no settings file or with empty models).

## Acceptance

- [ ] `settings.json` is read from `DataDir()/settings.json`; JSON uses snake_case keys (`model`, `name`, `api_url`, `api_key`).
- [ ] If the file is missing, unreadable, or `models` is empty, effective config equals current `LoadLLM()` and display name is `cfg.Model`.
- [ ] If the file exists and `models` has at least one entry, effective config is built from the first entry; display name is entry’s `name` if set, else `model`.
- [ ] `setupAgentAndSession` uses this effective config and display name; TUI footer and prompt mode show the same behaviour as today but can show the configured display name.
- [ ] `config.LoadLLM()` remains available and is used internally when falling back.
- [ ] Config package has unit tests for: valid settings with models, missing file, empty models, invalid JSON.
- [ ] `go build ./...` and `go test ./...` succeed.
