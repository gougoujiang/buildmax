# Task 061: Prevent scheduled multiple times

## Goal

Introduce a clear phased status flow so each task is executed by at most one worker: **PENDING → SCHEDULED → RUNNING → SUCCEEDED | FAILED**. The scheduler claims a task by moving it to SCHEDULED, then spawns the worker; if spawning fails, the task is reverted to PENDING. The worker only runs when the task is SCHEDULED and atomically moves it to RUNNING before execution.

## Context

- **Current flow**: Scheduler polls `GetNextPendingTask`, spawns worker with `--task-id`. Worker GETs task, checks PENDING, PATCHes RUNNING, runs. No atomicity: multiple schedulers or workers can double-assign or double-run the same task.
- **New flow**: Add status **SCHEDULED** between PENDING and RUNNING. Scheduler fetches a PENDING task, atomically sets it to SCHEDULED (claim), then spawns the worker; if spawn fails, set back to PENDING. Worker GETs task, requires status **SCHEDULED**, atomically sets SCHEDULED → RUNNING (only one worker can win), then runs and sets final status (SUCCEEDED/FAILED). This gives clear phases (pending → scheduled → running) and explicit spawn-failure recovery.

## In scope

- **New status SCHEDULED**: Task status lifecycle is PENDING → SCHEDULED → RUNNING → SUCCEEDED | FAILED. Any UI or API that lists or filters by status should treat SCHEDULED (e.g. show as "scheduled" or "queued").
- **TaskStore**: Add `UpdateTaskStatusIf(ctx, taskID, expectedStatus, newStatus string, ...) (updated bool, err error)` so both scheduler (PENDING→SCHEDULED) and worker path (SCHEDULED→RUNNING) can claim atomically.
- **Scheduler**: After `GetNextPendingTask`, call `UpdateTaskStatusIf(taskID, "PENDING", "SCHEDULED", ...)`. If `!updated`, skip spawn (another scheduler claimed it). If updated, spawn worker; **if spawn fails** (e.g. exec error, binary not found), call `UpdateTaskStatus(taskID, "PENDING", ...)` so the next poll retries.
- **Server worker PATCH**: When request status is RUNNING, use `UpdateTaskStatusIf(taskID, "SCHEDULED", "RUNNING", ...)`. If `!updated`, respond **409 Conflict**. Other transitions (SUCCEEDED, FAILED) remain unconditional.
- **Worker**: GET task; if status != **SCHEDULED**, exit (e.g. "task not scheduled" or "task already running"). Call PATCH RUNNING; if 409, exit without running (e.g. exit code 2). Then run task and set final status as today.

## Out of scope

- Recovery of stuck SCHEDULED or RUNNING tasks (e.g. timeout or cleanup job). Out of scope for this task.
- Changing poll interval or backpressure.

## Deliverables

1. **entity.TaskStore**
   - Add `UpdateTaskStatusIf(ctx, taskID, expectedStatus, newStatus string, startedAt, endedAt *int64, output, errorMessage, sessionID *string) (updated bool, err error)`. Update only when current status equals `expectedStatus`; return whether exactly one row was updated.
   - **Status flow**: Tasks may be PENDING, SCHEDULED, RUNNING, SUCCEEDED, FAILED. `GetNextPendingTask` continues to return only PENDING tasks. No schema change if status is already a string column.

2. **Scheduler (internal/executor)**
   - In the poll loop: get task via `GetNextPendingTask`. If task != nil, call `UpdateTaskStatusIf(ctx, task.TaskID, "PENDING", "SCHEDULED", nil, nil, nil, nil, nil)`. If `!updated`, continue (next tick or another scheduler got it). If updated, spawn worker; **on spawn failure** (e.g. `cmd.Run()` returns error), call `UpdateTaskStatus(ctx, task.TaskID, "PENDING", ...)` to revert so the task is picked again.

3. **Server worker PATCH**
   - When `req.Status == "RUNNING"`: call `UpdateTaskStatusIf(ctx, taskID, "SCHEDULED", "RUNNING", req.StartedAt, nil, nil, nil, req.SessionID)`. If `!updated`, respond **409 Conflict** (e.g. `{"error": "task not scheduled or already running"}`). Otherwise respond 200 and handle artifact as today. For SUCCEEDED/FAILED, keep unconditional `UpdateTaskStatus`.

4. **Worker (workercmd)**
   - After GET task: require **status == "SCHEDULED"**; if not, return error and exit (e.g. "task not scheduled (status=...)").
   - Call PATCH RUNNING. If server returns 409, log "task already claimed" and exit with distinct code (e.g. 2) without calling `RunTask`. Otherwise continue to `RunTask` and final status PATCH as today.
   - Executor: define sentinel error for 409 (e.g. `ErrTaskAlreadyClaimed`); worker checks with `errors.Is` and returns workercmd sentinel for exit code 2.

5. **APIs / UI**
   - Any listing or display of task status should recognise SCHEDULED (e.g. activity list, task detail). No new API contract beyond status string; clients that show status can map SCHEDULED to a label like "Scheduled" or "Queued".

6. **Tests**
   - Entity: `UpdateTaskStatusIf` — match → updated true; no match → updated false, row unchanged.
   - Scheduler: (optional) with mock store, verify that on spawn failure we call UpdateTaskStatus back to PENDING.
   - Server: PATCH RUNNING when task is SCHEDULED → 200; when task is PENDING or RUNNING → 409.
   - Worker: (optional) when status != SCHEDULED or 409, exit without RunTask.
   - `go build ./...` and `go test ./...` pass.

## Acceptance

- [ ] Status flow is PENDING → SCHEDULED → RUNNING → SUCCEEDED | FAILED; TaskStore has `UpdateTaskStatusIf`.
- [ ] Scheduler atomically sets PENDING → SCHEDULED before spawn; on spawn failure, reverts SCHEDULED → PENDING.
- [ ] Worker runs only when task is SCHEDULED; atomically sets SCHEDULED → RUNNING via PATCH; on 409 or wrong status, exits without running (distinct exit code for 409).
- [ ] Only one scheduler can claim a given PENDING task (conditional update); only one worker can move a given SCHEDULED task to RUNNING (conditional update + 409).
- [ ] SUCCEEDED/FAILED updates remain unconditional. List/display of tasks supports SCHEDULED where status is shown.
- [ ] `go build ./...` and `go test ./...` pass.
