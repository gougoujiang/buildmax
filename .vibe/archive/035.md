# Task 035: Buildmax server mode

Add a **server mode** so buildmax runs as a long-lived HTTP process, providing a backend for the portal. This task introduces the `buildmax server` subcommand, a minimal HTTP server with a health endpoint and Swagger for development.

---

## Goal

**One sentence:** Add a `buildmax server` subcommand that starts an HTTP server on a configurable port (default 5678), exposes a `/healthz` endpoint, and serves Swagger (OpenAPI spec + UI) for local development and testing; other APIs are left for later tasks.

---

## Context

- **CLI today:** Cobra in `internal/cmd` — root command runs TUI or print mode; `version` is the only subcommand. Entry is `cmd/buildmax/main.go`.
- **Portal:** React app under `portal/`; no backend yet. AGENTS.md plans "Portal: chat UI, session list, API integration with the Go backend."
- **This task:** Introduces the backend entry point (HTTP server) and a single endpoint plus Swagger so the stack is in place for future API work.

---

## In scope

- **Subcommand `buildmax server`**
  - Registered on the root Cobra command (same pattern as `version`).
  - Starts an HTTP server; process runs until interrupt (e.g. Ctrl+C). No TUI or prompt mode when server is running.

- **HTTP server**
  - Listen address: configurable port, **default 5678** (e.g. `:5678` or `localhost:5678`). Allow override via flag (e.g. `--port`) and/or env (e.g. `BUILDMAX_SERVER_PORT`); exact mechanism is design choice.
  - **`GET /healthz`** — returns 200 with a simple body (e.g. `{"status":"ok"}` or `ok`) so callers can check liveness. No auth.

- **Swagger (OpenAPI) for development and local test**
  - Expose an **OpenAPI spec** (e.g. JSON at `/openapi.json` or `/swagger.json`) describing the server’s endpoints (at least `GET /healthz`).
  - Expose **Swagger UI** (e.g. at `/swagger/` or `/docs`) that loads that spec so developers can browse and test locally.
  - Implementation: design may choose swaggo/swag (code-generated spec), a hand-written spec file, or embed Swagger UI assets; no preference mandated here.

- **Logging**
  - Use existing `internal/log` (slog, file-only). Log server start (address, port) and shutdown; no stdout/stderr so the binary stays clean when run as a service.

---

## Out of scope

- **Other API endpoints** (sessions, chat, workspaces, etc.) — future tasks.
- **Portal calling the backend** — portal stays on mock/local data for now; backend is ready for later integration.
- **Authentication, TLS, or production hardening** — not required for this task.
- **Config file** — port/address can be flag and/or env only.

---

## Technical notes

- **Port:** Default `5678`. Override via `--port` and/or `BUILDMAX_SERVER_PORT` (design decides one or both).
- **Shutdown:** Graceful shutdown on SIGINT/SIGTERM (optional in this task; at least document intended behavior).
- **Persistence:** Server mode does not need to change session or config paths; reuse `config.DataDir()` and existing dirs if any server state is persisted later.

---

## Acceptance criteria

- [ ] Running `buildmax server` starts an HTTP server and blocks until interrupt; no TUI.
- [ ] Default listen port is 5678; port is overridable (flag and/or env as designed).
- [ ] `GET /healthz` returns HTTP 200 and a simple success response (JSON or plain text).
- [ ] OpenAPI spec is served at a documented path (e.g. `/openapi.json`) and includes `GET /healthz`.
- [ ] Swagger UI is available at a documented path (e.g. `/swagger/`) and loads the OpenAPI spec.
- [ ] Server logs start and stop via existing `internal/log` (no stdout/stderr).
- [ ] `go build ./...` and `go test ./...` pass.
