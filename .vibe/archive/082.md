# Task 082: API tidy up

## Goal

Identify server HTTP API endpoints that are not used by the Portal or the Worker, analyze why they are unused, and safely remove or explicitly retain them so the API surface stays minimal and intentional.

## Context

- **Server** (`internal/server`): HTTP API for the Portal (user-facing) and the Worker (executor). Routes are registered in `server.go`; handlers live in `agents.go`, `artifacts.go`, `chats.go`, `files.go`, `login.go`, `otp.go`, `stream_handlers.go`, `worker_handlers.go`, `workspaces.go`.
- **Portal** (`portal/src/lib/api/index.ts`): Single API client; all server calls go through this module (e.g. `getWorkspaces`, `getChats`, `createChatRun`, `subscribeChatStream`, `getArtifacts`, `uploadFiles`, `getFileTree`).
- **Worker** (`internal/executor/worker_api.go`): Uses only worker API: `GET /api/worker/chat-runs/{chat_run_id}`, `PATCH /api/worker/chat-runs/{chat_run_id}`, `POST /api/worker/chat-runs/{chat_run_id}/stream`.
- **Conventions**: AGENTS.md documents routes and storage; OpenAPI lives in `internal/server/static/openapi.json`. Response keys use snake_case (6.1 Persistence naming style).

## “Unused” for this task

An endpoint is **unused** if:

1. No code path in the Portal (e.g. pages, hooks) calls an API function that hits that endpoint, and  
2. No code path in the Worker (or server-triggered worker flow) calls that endpoint.

Infrastructure endpoints (`/healthz`, `/openapi.json`, `/swagger/`) are **in scope for the audit** (document whether anything besides ops/tooling uses them) but **not candidates for removal** unless explicitly decided.

We are **not** changing request/response shapes, adding new endpoints, or refactoring handler internals beyond removing a handler and its route.

## Deliverables

1. **Audit document (in task or design)**
   - List every server route (method + path) and for each state: used by Portal (and where), used by Worker, or unused.
   - For each unused route: short reason (e.g. “single-agent detail never implemented”, “run-scoped stream not used by UI”).
   - For each unused route: recommendation — **remove** or **keep** (with one-line justification, e.g. “keep for future agent detail page” or “remove; chat stream is sufficient”).

2. **Safe removals only**
   - Remove only endpoints that the audit recommends for removal and that have no remaining callers (Portal and Worker). Remove the route registration, handler, and any handler-specific helpers if unused elsewhere.
   - Update `internal/server/static/openapi.json` so it no longer describes removed endpoints.

3. **Tests and build**
   - `go build ./...` and `go test ./...` pass. No remaining references to removed endpoints in the codebase (except optional comment in audit).

## Out of scope (for later)

- Changing API contracts (request/response fields or status codes) for endpoints we keep.
- Adding new endpoints or “replacing” removed ones with different designs.
- Refactoring handler code structure (e.g. extracting shared logic) unless required to remove a handler cleanly.
- Removing or changing `/healthz`, `/openapi.json`, or `/swagger/` unless explicitly agreed.

## Acceptance

- [ ] Audit lists every server route with used-by (Portal/Worker) and unused recommendation (remove/keep).
- [ ] All endpoints recommended for removal are removed (route, handler, OpenAPI); no dead code left.
- [ ] Endpoints recommended to be kept remain; no behavior change for them.
- [ ] `go build ./...` and `go test ./...` pass.
- [ ] Portal and Worker behavior unchanged for the flows that use the remaining APIs.
