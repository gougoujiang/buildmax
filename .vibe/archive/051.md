# Task 051: Add user registration

## Goal

Allow new users to register an account via the portal (sign up with email); unify login and signup behind an MVP OTP-style flow where the backend accepts a hardcoded OTP and does not send real emails.

## Context

- **Existing**: `internal/store` has `User` (user_id, email, name, created_at) and `UserStore.UserByEmail`. No `CreateUser`. `internal/server` has `POST /api/login` with body `{ "email" }`; returns 401 if user not found, else JWT + user. Portal has a Login page (email only) and `api.login(email)`.
- **Conventions**: AGENTS.md — snake_case for persisted/API JSON; singular table names; tools output for LLM (N/A here). Server uses `store.UserStore`, JWT in config.
- **Fit**: Registration extends the same auth surface (server + portal); store gains a way to create users.

## In scope

1. **Backend — request OTP (signup + login)**  
   New endpoint `POST /api/otp/request` with body `{ "email" }`:
   - If email already registered: return 409 (or 400) with a clear message (e.g. "email already registered"; for login flow, caller can treat as "proceed to enter OTP").
   - If email not registered (signup): create user (generate user_id, store email, name from email or empty), then return 200 with a message like "otp_sent" (no real email send).
   - Response body: e.g. `{ "message": "otp_sent" }` or `{ "sent": true }`. No JWT in this step.

2. **Backend — login with OTP**  
   Change `POST /api/login` to accept body `{ "email", "otp" }`:
   - If user not found: 401 "user not found".
   - If OTP is not the hardcoded value `123456`: 401 "invalid otp".
   - If valid: issue JWT and return `{ "token", "user" }` as today.

3. **Store**  
   - Add `CreateUser(ctx, email string) (*User, error)` to `UserStore` and implement in `Store` (generate `user_id` via `id.New()`, set name to empty or derived from email). Return error if email already exists (e.g. duplicate key).

4. **Portal — sign up**  
   - Sign-up page: user enters email, clicks "Get OTP". Call `POST /api/otp/request`. If 409/400 "email already registered", show that message and optionally link to login. On success, show "OTP sent" and a second step: enter OTP (prefill or hint `123456` for MVP) then submit to login (email + OTP).

5. **Portal — login**  
   - Login flow: user enters email, clicks "Get OTP" (or "Login"). Call `POST /api/otp/request`; if user not found (e.g. 404 or 400 from backend), show "user not found" / "please sign up first". On success, show "OTP sent" and OTP input; submit `POST /api/login` with `{ email, otp }`.

6. **API contract**  
   - OpenAPI (and any server docs) updated for `POST /api/otp/request` and `POST /api/login` with `otp` in body.

## Out of scope

- Real OTP sending (email/SMS). MVP uses hardcoded OTP `123456` only.
- Password-based auth, magic links, or other auth methods.
- Rate limiting, CAPTCHA, or abuse protection.
- Email verification (e.g. verifying that the email is reachable).
- Changing JWT expiry or refresh tokens.

## Deliverables

- **internal/store**: `UserStore` extended with `CreateUser(ctx, email string) (*User, error)`; `Store` implementation; tests for CreateUser (success, duplicate email).
- **internal/server**: `POST /api/otp/request` handler; `POST /api/login` updated to require and validate `otp` (hardcoded `123456`); OpenAPI spec updated; tests for both handlers.
- **portal**: Sign-up page and route; "Get OTP" + OTP step for both signup and login; `api.requestOtp(email)` and `api.login(email, otp)`; link between login and sign up.

## Acceptance criteria

- [ ] New user can open sign up, enter email, get "OTP sent", then complete login with email + `123456` and reach the app.
- [ ] Existing user can open login, enter email, get "OTP sent", then complete login with email + `123456`.
- [ ] If sign up is used with an already registered email, backend returns a clear "email already registered" (or similar) and portal shows it; user can go to login.
- [ ] If login is used with an unregistered email, backend returns an error and portal shows "user not found" or "please sign up".
- [ ] Login with wrong OTP returns 401 and portal shows error.
- [ ] OpenAPI and server docs describe `POST /api/otp/request` and `POST /api/login` (email + otp).
- [ ] Store and server have tests covering new and changed behavior; no real email sending.
