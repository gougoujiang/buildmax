# Task 100: Implement basic chat in desktop app

Add basic chat functionality to the Wails desktop app so users can send messages and receive assistant replies in the app, similar to the CLI/TUI experience.

## Goal

Wire the existing desktop app UI to the shared agent runtime so that the sidebar shows real sessions from disk, the main panel shows conversation history for the selected session, and the user can type a message and get an assistant reply (one turn per send, with session persistence).

## Context

- **Desktop app (task 099)**: Wails app in `cmd/buildmax-desktop/`, `internal/cmd/desktop` (App with Startup/Shutdown), React frontend in `desktop/frontend/`. App is bound to the frontend; uses `config.DataDir()` and `config.SessionsDir()` like the CLI. No backend server; local-only.
- **Agent runtime**: `internal/app/agentrun` — `Open(OpenInput)` creates a `Runtime` (session, LLM, tools); `RunPrompt(ctx, RunInput)` runs one user prompt, persists session, returns `RunOutput{Reply, ...}`. Uses `internal/session` (LoadFromDir, SaveToDir, PersistAfterReply, LoadList, UpsertListEntry, ListEntry).
- **CLI flow**: `internal/cmd/cli/setup.go` calls `agentrun.Open` with optional SessionID and model; `print.go` / TUI call `RunPrompt` with user input. Workspace defaults to CWD; session list from `session.LoadList(sessionsDir)`.
- **Current desktop UI**: `desktop/frontend/src/App.jsx` has a sidebar (thread list) and main panel (message history) driven by **mock** data (`MOCK_THREADS`, `MOCK_MESSAGES`). No message input or send action yet.

## In scope

1. **Backend (Go)**
   - Use `config.SessionsDir()` and existing session/agentrun packages (no new persistence layer).
   - Expose to the frontend (Wails bindings on `App` or a dedicated struct):
     - **ListSessions()** → list of sessions (id, title, workspace, created_at) from `session.LoadList(sessionsDir)`.
     - **GetSession(sessionID)** → load one session from disk (`session.LoadFromDir`) and return data the frontend can display: id, title, created_at, and messages (role + content only for display; tool messages can be included or simplified).
     - **SendMessage(sessionID, prompt)** → if sessionID is empty, create a new session (same semantics as `agentrun.Open` with empty SessionID); open runtime with `agentrun.Open(OpenInput{SessionID, ModelSelector: ""})` (workspace = CWD), call `RunPrompt` with the prompt, persist (already done inside RunPrompt), return reply and session ID (so frontend can update list and selection for new chats). On error return a clear error message. Run synchronously so the frontend can await and show loading state.
   - Workspace for agent: use current working directory (same as CLI when not specified). No workspace picker in this task.
   - Model: use default model (empty model selector).

2. **Frontend (React)**
   - Replace mock threads and messages with data from **ListSessions** and **GetSession**.
   - Support **New chat**: create a new conversation (e.g. clear selection or use a “new” placeholder); on first send, call SendMessage with empty sessionID and use returned sessionID to refresh list and select the new session.
   - Add **message input** (text area or input) and **Send** button (or submit on Enter). While a request is in flight, show loading state and disable send (or show “Sending…”).
   - On send: call **SendMessage(sessionID, prompt)**; on success append user message and assistant reply to the current view and refresh session list (title may have been generated). On error show an error message in the UI.
   - Display conversation history: user and assistant messages with role and content; optional: show tool calls/results in a simplified way (e.g. “Tool: …” or collapse). Minimum: user and assistant content only.

3. **Consistency**
   - Session list and session files must stay compatible with the CLI (same `sessions.json` and per-session JSON under `config.SessionsDir()`). Persistence uses existing `session.PersistAfterReply` / `UpsertListEntry` from agentrun.

## Out of scope

- **Streaming**: No streaming of assistant reply; one full reply after RunPrompt completes.
- **Workspace picker**: No UI or API to change workspace; CWD only.
- **Model selector**: No UI to change model; default model only.
- **Tool call display**: Fancy display of tool calls/results is optional; minimal is “user + assistant” content only.
- **Resume by session ID from CLI**: No requirement to support resuming a session created by CLI via a deep link; same data on disk is enough.
- **Backend server / Portal**: No sign-in, workspaces, or API; desktop remains local-only.

## Deliverables

| # | Deliverable | Notes |
|---|-------------|--------|
| 1 | Backend: session list and load | `ListSessions()` and `GetSession(sessionID)` using `session.LoadList` and `session.LoadFromDir`; return types suitable for frontend (e.g. structs with json tags for Wails). |
| 2 | Backend: send message | `SendMessage(sessionID, prompt)` that opens runtime (new session if sessionID empty), runs `RunPrompt`, returns reply and session ID (and error if any). |
| 3 | Frontend: real session list and messages | Sidebar and main panel driven by ListSessions / GetSession; “New chat” creates new conversation and uses SendMessage("", prompt) on first send. |
| 4 | Frontend: input and send | Text input + Send; loading state; append user + assistant messages on success; show error on failure. |
| 5 | Compatibility | Sessions created/updated by the desktop app are readable by the CLI and vice versa (same paths and formats). |

## Acceptance criteria

- [ ] **ListSessions** returns the same sessions that appear in the CLI session list (same `sessions.json` and DataDir).
- [ ] **GetSession(sessionID)** returns the session’s id, title, created_at, and messages (at least role and content for user/assistant).
- [ ] **SendMessage("", prompt)** creates a new session, runs the agent, persists it, and returns the reply and new session ID; frontend can refresh the list and show the new chat.
- [ ] **SendMessage(sessionID, prompt)** for an existing session runs the agent in that session, persists, and returns the reply.
- [ ] Desktop UI shows real sessions in the sidebar and real messages in the main panel (no mock data).
- [ ] User can type a message and send; loading state is shown while waiting; user and assistant messages appear in the thread after success; errors are shown in the UI.
- [ ] New chat flow works: user starts a new conversation, sends a message, and sees the new session in the list with the reply.
- [ ] No regression: existing CLI and desktop build/run still work; `go build ./...` and `go test ./...` pass (excluding any Wails-specific tests that require a display).
