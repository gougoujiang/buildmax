# Task 085: Quota and limit

Introduce quota and limit controls so we can support different user tiers (e.g. free-trial, pro) with extensible per-tier limits on runs and LLM usage.

---

## Goal

Design and implement a quota system for users: define what is limited, how tiers and tier settings are represented, and enforce limits at the API so that create-chat and create-run can reject requests when the user has exceeded their tier quota.

## Context

- **Existing metering** (design/006): Usage is attributed and stored per ChatRun (`prompt_tokens`, `completion_tokens`), per Chat (`title_prompt_tokens`, `title_completion_tokens`), and per CLI session (session file). Billing can sum run + chat title + session usage.
- **Creation flow**: `createWorkspaceChatHandler` → `ChatStore.CreateChat(...)`; `createChatRunHandler` → `ChatRunStore.CreateChatRun(chatID, input, userID)`. Both have `userID` (JWT) and `workspaceID`; no quota check today.
- **Models**: `User` (user_id, email, name), `Workspace` (owner_user_id), `Chat` (created_by), `ChatRun` (no created_by in model; chat has created_by). Quota is best attributed to **user** (created_by / workspace owner) for "tiers of user."
- **Conventions**: Entity IDs prefixed (e.g. u_, w_); JSON snake_case; singular table names; env-based config (see AGENTS.md).

## In scope

1. **Define what is limited**
   - **Runs**: number of chat runs (created runs, not scheduler steps) per user per time window (e.g. per calendar month or rolling 30 days).
   - **Tokens**: total prompt + completion tokens consumed by the user’s runs (and chat titles) in the same time window. Use existing ChatRun + Chat token fields for counting; no CLI session aggregation in this task.
   - Strategy: enforce at **create chat** and **create run** (reject with HTTP 429 and a clear message when over limit). Optionally check again before scheduler picks a run (defense in depth); at minimum, create-time check is required.

2. **Tier model and storage**
   - **Tier**: named plan attached to a user (e.g. `free_trial`, `pro`). Stored per user (e.g. `User` tier field or a small user_quota/tier table).
   - **Tier settings**: each tier has configurable limits, e.g. `max_runs_per_period`, `max_tokens_per_period`, and `period_days` (e.g. 30 for rolling window). Settings must be **extensible** (new tiers or new limit types can be added without schema churn where possible—e.g. config file or JSON column, or a tier_settings table keyed by tier name).
   - Default tier for new users (e.g. `free_trial`) and a way to assign tier (e.g. env/config or admin-only for now; no self-service upgrade in this task).

3. **Usage aggregation**
   - For a given user and time window: sum runs (count of ChatRuns where the chat’s created_by = user_id and run created_at in window); sum tokens (ChatRun.prompt_tokens + completion_tokens for those runs, plus Chat.title_prompt_tokens + title_completion_tokens for chats created by that user in the window). Use existing entity/store; add a small quota package or store methods that return (run count, token sum) for a user in a window.

4. **Enforcement**
   - Before `CreateChat`: resolve user’s tier, get tier limits, compute current usage for the user in the current period; if creating this chat would imply a new run (first run for that chat) and run count or token budget would be exceeded, return 429 with a JSON error message (e.g. "quota exceeded: run limit" or "quota exceeded: token limit").
   - Before `CreateChatRun`: same check (run count and token budget). If over limit, return 429.
   - Use a consistent time window (e.g. rolling 30 days from now) defined by tier settings.

5. **API and config**
   - Document quota errors in OpenAPI (429 response for create chat and create run).
   - Tier names and default tier: configurable via env or config (e.g. `BUILDMAX_DEFAULT_QUOTA_TIER=free_trial`). Tier limits (e.g. free_trial: 10 runs, 100k tokens per 30 days) in config or DB; design must allow adding pro (e.g. 1000 runs, 10M tokens) without code change for values.

## Out of scope

- CLI/session usage aggregation for quota (only server-side chat/run usage in this task).
- Per-workspace quota (only per-user in this task).
- Self-service tier change or billing integration (admin/config only).
- Portal UI for quota (e.g. “you have X runs left”); can be a follow-up.
- Rate limiting (requests per second); this task is usage quota only.

## Deliverables

- **Data**: User-tier association (field or table); tier settings (extensible: config or DB table keyed by tier name with limit key-value or columns for max_runs_per_period, max_tokens_per_period, period_days).
- **Logic**: Usage aggregation for a user in a time window (run count + token sum); quota check (would this run push the user over limit?); tier resolution for a user.
- **Integration**: Quota check in create-chat and create-run handlers; 429 and JSON body when over limit.
- **Config**: Default tier and tier limit values (env or file) so free_trial and one other tier (e.g. pro) can be configured without code change.
- **Tests**: Unit tests for usage aggregation and quota check; handler tests that assert 429 when over limit.

## Acceptance criteria

- [ ] User has an assigned tier (default from config); tier settings are stored or loaded from config for at least two tiers (e.g. free_trial, pro) with max runs and max tokens per period.
- [ ] Usage for a user in the configured period (e.g. rolling 30 days) is computed from ChatRun + Chat token and run counts (chats/runs created by that user).
- [ ] Create chat and create run return 429 with a clear message when the user would exceed their tier’s run or token limit.
- [ ] When under limit, create chat and create run behave as today (no regression).
- [ ] Adding a new tier or changing limit values does not require code changes (config or DB only).
- [ ] Tests: quota logic and handler 429 behavior covered by tests.
