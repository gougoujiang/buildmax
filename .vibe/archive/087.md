# Task 087: Scheduler optimization

Make the chat-run scheduler use a clear, one-way state machine so runs never flip back from SCHEDULED to PENDING. On worker spawn failure, mark the run as FAILED instead of reverting to PENDING.

---

## Goal

Ensure the run status flows in one direction: **PENDING → SCHEDULED → RUNNING → SUCCEEDED or FAILED**. When the scheduler fails to spawn the worker (e.g. `runner.Run()` returns an error), the run must not be reverted to PENDING so that the next poll does not repeatedly claim and fail the same run (avoid PENDING ↔ SCHEDULED flip-flop).

## Context

- **Scheduler** (`internal/executor/scheduler.go`): Polls with `GetNextPendingChatRun`, atomically claims with `UpdateChatRunStatusIf(ctx, run.ChatRunID, "PENDING", "SCHEDULED", ...)`, then calls `runner.Run(ctx, *run)`. On `Run()` error it currently reverts with `UpdateChatRunStatus(..., "PENDING", ...)` so the run is picked again next poll, causing status to oscillate and logs to be noisy.
- **Worker API** (`internal/server/worker_handlers.go`): Worker PATCHes SCHEDULED→RUNNING via `UpdateChatRunStatusIf(..., StatusScheduled, StatusRunning, ...)`, then later PATCHes SUCCEEDED or FAILED via `UpdateChatRunStatus`. On FAILED, handler calls `SyncChatFromRun` so chat denormalized fields reflect the failed run.
- **Status flow today**: PENDING (created) → SCHEDULED (scheduler claim) → [if spawn fails: revert to PENDING] → [if spawn ok: worker reports RUNNING → SUCCEEDED/FAILED]. The only problematic path is revert-to-PENDING on spawn failure.
- **Stores**: `entity.ChatRunStore` already includes `SyncChatFromRun` (see `internal/storage/entity/interfaces.go`). The scheduler receives `ChatRunStore`; after setting the run to FAILED it calls `SyncChatFromRun(ctx, run.ChatRunID)` so the chat denormalized fields match the failed run.


## In scope

1. **Stop reverting to PENDING on spawn failure**
   - In `internal/executor/scheduler.go` `loop()`: when `runner.Run()` returns an error, do **not** call `UpdateChatRunStatus(..., "PENDING", ...)`.
   - Instead: set the run to **FAILED** with an `error_message` that indicates schedule/spawn failure (e.g. include `err.Error()` or a short prefix), and set `ended_at` to now so the run has a clear end time.
   - Ensure the chat’s denormalized fields are updated: after updating the run to FAILED, call the same sync used when the worker reports FAILED (e.g. `SyncChatFromRun`). That requires the scheduler to have access to `SyncChatFromRun`; see “Chat sync on scheduler-set FAILED” below.

2. **Chat sync on scheduler-set FAILED**
   - When the scheduler sets a run to FAILED (spawn failure), the chat row for that run’s `chat_id` must be updated so `last_run_id`, `status`, `output`, `started_at`, `ended_at`, `error_message` (and optionally `session_id`) match the run — same semantics as when the worker PATCHes FAILED and the server calls `SyncChatFromRun`.
   - `ChatRunStore` already defines `SyncChatFromRun`. After `UpdateChatRunStatus(..., "FAILED", ...)` the scheduler calls `s.chatRuns.SyncChatFromRun(ctx, run.ChatRunID)`.

3. **Logging and observability**
   - Keep a clear log line when spawn fails and the run is set to FAILED (e.g. “scheduler: worker spawn failed, marking run as FAILED” with `chat_run_id` and error). Remove or adjust the log that said “reverting run to PENDING”.

4. **Tests**
   - Unit test(s) for the scheduler: when `WorkerRunner.Run` returns an error, the run is updated to FAILED (with non-empty `error_message` and `ended_at`), chat is synced (if mock supports it), and the run is **not** set back to PENDING. Optional: test that a subsequent poll does **not** return this run (because it’s no longer PENDING).

## Out of scope

- Introducing a new status value (e.g. `SCHEDULE_FAILED`); use existing `FAILED` with `error_message` to distinguish spawn failure from worker-reported failure.
- Changing poll interval, concurrency, or number of schedulers.
- Automatic retry of spawn failures (e.g. moving FAILED back to PENDING); “rerun” or “retry” remains a separate feature (e.g. user-triggered new run or existing rerun flow).
- K8s Job backoff/retry behavior; only the in-process scheduler’s transition on `Run()` error is in scope.

## Deliverables

- **internal/executor/scheduler.go**: On `runner.Run()` error, set run to FAILED (with `error_message`, `ended_at`), call chat sync, and do not revert to PENDING.
- **internal/storage/entity**: No interface change; `ChatRunStore` already has `SyncChatFromRun`. Executor already depends on entity for `ChatRunStore`.
- **Tests**: Scheduler test that verifies on Run() error the run becomes FAILED and is not reverted to PENDING; chat sync is called (via mock or store test).
- **Docs**: Optional one-line comment in scheduler or design doc noting the intended state machine (PENDING → SCHEDULED → RUNNING → SUCCEEDED/FAILED; spawn failure → FAILED).

## Acceptance

- [ ] When `runner.Run()` returns an error, the run’s status is set to **FAILED** with a non-empty `error_message` and `ended_at` set; it is **never** set back to PENDING.
- [ ] After the scheduler sets a run to FAILED (spawn failure), the corresponding chat’s denormalized fields (`last_run_id`, `status`, `ended_at`, `error_message`, etc.) are updated (same as when the worker reports FAILED).
- [ ] Scheduler unit test(s) cover the “Run() fails → run is FAILED, no PENDING revert” behavior.
- [ ] Existing happy path unchanged: PENDING → SCHEDULED (claim) → worker reports RUNNING → SUCCEEDED/FAILED; and worker-reported FAILED still syncs chat via existing handler.
