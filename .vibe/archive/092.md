# Task 092: Two-tier agent — Phase 2 — Portal as ChannelAdapter and pass-through engine

## Goal

Wire the portal **create-run** flow through Tier 1 so that the first channel uses the conversation contract: a portal adapter turns the request into a `ConversationTurn`, and a pass-through engine creates one Tier 2 run and returns its id. The external API (POST create run, response shape) stays unchanged; only the internal path uses Tier 1. No Tier 1 LLM or conversation history.

## Context

- **Design:** [design/007-two-tier-agent.md](../design/007-two-tier-agent.md) §8 Phase 2. Depends on Phase 1 (091).
- **Existing code:** `internal/conversation` (091) provides `ConversationTurn`, `ConversationResult`, `ChannelAdapter`, `ConversationEngine`, and `conversation.ChannelPortal`. `internal/server` has `createChatRunHandler` (POST .../chats/{chat_id}/runs): auth, path chat_id, body `{ "input" }`, quota, then `ChatRunStore.CreateChatRun(ctx, chatID, req.Input, userID)` and 201 with `{ "chat_run_id", "chat_id" }`. Chat and run stores are in `internal/storage/entity`; server Config is built in `internal/cmd/server/run.go`.
- **Where it fits:** New types and wiring live in `internal/server` (portal adapter, pass-through engine impl) and optional `Config.ConversationEngine`; handler calls engine when set. No new top-level package.
- **Conventions:** AGENTS.md; JSON snake_case for API; keep existing handler behavior and status codes (400, 409, 201).

## Tier 1 pass-through (this task)

For this task, **Tier 1** for the portal is pass-through only:

1. **Portal adapter:** Builds a `ConversationTurn` from the HTTP create-run request (workspace_id, chat_id, user_id, message = input). `Receive` accepts a request-shaped struct (or equivalent); `Send` is implemented but the create-run path does not call it in Phase 2 (no direct reply; client gets run id in JSON).
2. **Pass-through engine:** Implements `ConversationEngine`. `Process` always creates exactly one chat run with `turn.Message` as input (and workspace/chat from args), returns `ConversationResult{ TaskIDs: []string{ run.ChatRunID } }`. No LLM, no conversation history.
3. **Wiring:** When `Config.ConversationEngine` is set, `createChatRunHandler` builds the turn (from request), calls `Process`, and returns 201 using `Result.TaskIDs[0]` and chat_id. When nil, current direct `CreateChatRun` behavior is kept so existing setups are unchanged.

We are **not** changing create-chat (POST .../chats), stream endpoint, or any other route; **not** adding Tier 1 LLM or history (Phase 3).

## Deliverables

1. **Portal adapter (internal/server)**
   - A type that implements `conversation.ChannelAdapter`.
   - `Receive(ctx, raw)`: `raw` is a struct with workspace_id, chat_id, user_id, message (e.g. `PortalTurnInput`). Populate and return a `conversation.ConversationTurn` with Channel=conversation.ChannelPortal, ConversationID=chat_id, and the rest from the struct.
   - `Send(ctx, conversationID, output)`: for portal, may no-op or write to a provided response/stream in a later phase; for Phase 2, implementation may be a no-op or store output for the existing stream path. No change to the create-run response body (still 201 with chat_run_id).
   - Adapter is used so that the handler (or a small helper) builds the input struct from the HTTP request and calls `Receive` to obtain the turn. No HTTP dependency inside `internal/conversation`.

2. **Pass-through engine (internal/server)**
   - A type that implements `conversation.ConversationEngine`, taking `entity.ChatRunStore` (and optionally `entity.ChatStore` for existence check if desired).
   - `Process(ctx, workspaceID, chatID, turn)`: ensure chat exists in workspace (optional, or rely on handler already having validated); call `ChatRunStore.CreateChatRun(ctx, chatID, turn.Message, turn.UserID)`; on success return `ConversationResult{ TaskIDs: []string{ run.ChatRunID } }`; on error (e.g. ErrRunInProgress) return the error so the handler can map to 409/500.

3. **Server config and handler**
   - Add optional `ConversationEngine` to `server.Config` (type `conversation.ConversationEngine`). When non-nil, `createChatRunHandler` builds the turn (via portal adapter Receive or by constructing `ConversationTurn` directly from request), calls `engine.Process`, and returns 201 with `result.TaskIDs[0]` and chat_id; when nil, keep current direct `CreateChatRun` logic.
   - Quota and auth: unchanged; still applied in the handler before calling the engine.
   - In `internal/cmd/server/run.go`: instantiate the pass-through engine with the existing store(s) and set `cfg.ConversationEngine` so the server uses Tier 1 by default when running from this binary.

4. **Tests**
   - Unit test for pass-through engine: mock `ChatRunStore`; call `Process` with a turn; assert one `CreateChatRun` with correct chatID and message, and result contains one TaskID matching the returned run’s ChatRunID.
   - Unit test for portal adapter: call `Receive` with a request-shaped input; assert `ConversationTurn` has ChannelPortal, correct ConversationID, UserID, Message.
   - Handler test (existing or new): one test that a create-run request results in 201 and one Tier 2 run with the given input (can go through the real or mocked engine).

## Out of scope (for later)

- Tier 1 LLM conversation or multi-turn history (Phase 3).
- Changing POST .../chats (create chat) to go through Tier 1; only create-run is wired.
- Using `Send` to stream or push reply in this task; adapter implements `Send` but create-run path need not call it.
- Cron or webhook adapters (Phase 4).

## Acceptance

- [ ] Portal adapter type in `internal/server` implements `conversation.ChannelAdapter`; `Receive` builds `ConversationTurn` from request-shaped input with Channel=portal and correct ConversationID/UserID/Message.
- [ ] Pass-through engine type in `internal/server` implements `conversation.ConversationEngine`; `Process` creates one run via `ChatRunStore` and returns its `chat_run_id` in `ConversationResult.TaskIDs`.
- [ ] `server.Config` has optional `ConversationEngine`; `createChatRunHandler` uses it when set and preserves existing API (201, body `{ chat_run_id, chat_id }`, 409 when run in progress, 400 for bad input).
- [ ] `internal/cmd/server/run.go` sets `ConversationEngine` to the pass-through implementation so default server run uses Tier 1.
- [ ] Unit tests for adapter Receive and engine Process; at least one handler or integration test that create-run produces one run with correct input.
- [ ] `go build ./...` and `go test ./...` pass.
