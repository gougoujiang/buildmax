# Task 065: Deployment configs for buildmax server on kind cluster

## Goal

Provide plain Kubernetes YAML (no Helm) to deploy the buildmax server (and its worker, spawned in-pod) into an existing kind cluster, using in-cluster MinIO and MySQL and a single `make deploy` command that builds, loads images, and applies the manifests.

## Context

- **Cluster services** (after `./make setup`): MySQL in namespace `db` (service `mysql`, port 3306); MinIO in namespace `storage` (service `minio`, ports 9000/9001); ingress-nginx in `ingress-nginx`. We deploy the buildmax application in a **dedicated namespace `buildmax`** (new namespace, not `default`). **Ingress hosts**: API server at **`buildmax-api.kind.local`**; **`buildmax.kind.local`** is reserved for the portal (React) application.
- **Existing setup**: `setup/setup.sh` creates a kind cluster (`BUILDMAX_KIND_CLUSTER`, default `buildmaxdev`), deploys MinIO in namespace `storage`, MySQL in namespace `db`, ingress-nginx, and creates bucket `bmstore`. `./make pub_images` builds `buildmax:local` from `Dockerfile.buildmax` (all three binaries: buildmax, buildmax-server, buildmax-worker) and loads it into kind.
- **Server and worker**: The server process runs `buildmax-server`; the scheduler inside it spawns the `buildmax-worker` binary with `--task-id`. Worker runs in the same pod (same container), inheriting env; it needs `BUILDMAX_WORKSPACES_DIR` for runtime workspace roots and must be able to reach the server and MinIO/MySQL.
- **Config**: All env keys are in `internal/config/env_spec.go`. Server requires JWT secret, DB, and (for in-cluster) MinIO for both persist and artifact storage. Worker requires `BUILDMAX_SERVER_URL`, `BUILDMAX_WORKER_TOKEN`, and storage env (MinIO); workspace dir is used for task runtime (e.g. materialize and buildmax run).

## In scope

1. **Plain deployment YAML** (under `setup/` or a dedicated `deploy/` directory)
   - One or more YAML files (namespace, deployment, service, ingress).
   - No Helm chart; only static manifests.

2. **Deployment configuration**
   - **Image**: `buildmax:local` (same as `./make pub_images`).
   - **Single Deployment** for buildmax server: one container running `buildmax-server`. The scheduler in that process spawns `buildmax-worker` as a child; worker binary is in the same image.
   - **Env for in-cluster dependencies**:
     - **MySQL**: `BUILDMAX_DB_HOST=mysql.db.svc.cluster.local`, `BUILDMAX_DB_PORT=3306`, `BUILDMAX_DB_USER=buildmax`, `BUILDMAX_DB_PASSWORD=buildmax`, `BUILDMAX_DB_DATABASE=buildmax` (match `setup/mysql.yaml`).
     - **MinIO**: `BUILDMAX_MINIO_ENDPOINT=http://minio.storage.svc.cluster.local:9000`, plus `BUILDMAX_MINIO_ACCESS_KEY=minio`, `BUILDMAX_MINIO_SECRET_KEY=minio123`, `BUILDMAX_MINIO_BUCKET=bmstore`, `BUILDMAX_MINIO_REGION=us-east-1`, `BUILDMAX_MINIO_PREFIX=workspaces` (match setup bucket).
     - **Storage**: `BUILDMAX_PERSIST_STORAGE=minio`, `BUILDMAX_ARTIFACT_STORAGE=minio` (no local FS in cluster).
     - **Server**: `BUILDMAX_JWT_SECRET` (from Secret or fixed dev value), `BUILDMAX_SERVER_PORT=5678`, `BUILDMAX_WORKSPACES_DIR` — see below; **`BUILDMAX_CORS_ORIGIN=http://buildmax.kind.local`** so the API allows requests from the portal when it is served at buildmax.kind.local.
     - **Worker (used when server spawns worker)**: `BUILDMAX_WORKSPACES_DIR=/buildmax/worker/workspaces`; `BUILDMAX_SERVER_URL` = in-cluster URL for the buildmax service in namespace `buildmax` (e.g. `http://buildmax.buildmax.svc.cluster.local:5678`); `BUILDMAX_WORKER_TOKEN` (same as server expects); same MinIO env as above.
   - **Worker workspace volume**: Mount an `emptyDir` at `/buildmax/worker/workspaces` and set `BUILDMAX_WORKSPACES_DIR=/buildmax/worker/workspaces` in the pod so the spawned worker uses this path for task runtime.

3. **Service**
   - ClusterIP (or equivalent) so that the worker (same pod) can call the server via in-cluster DNS for `BUILDMAX_SERVER_URL`.

4. **Ingress**
   - Ingress rule with host **`buildmax-api.kind.local`** for the API server so it is reachable from the local machine. Traffic goes to ingress-nginx (from `./make setup`) then to the buildmax Service. Reserve **`buildmax.kind.local`** for the portal application (not used in this task). Document that the user must add `127.0.0.1 buildmax-api.kind.local` (and optionally `127.0.0.1 buildmax.kind.local` for future portal) to `/etc/hosts`.

5. **Secrets**
   - JWT secret and worker token: from a Kubernetes Secret (e.g. generated or placeholder for dev). Document required keys (`BUILDMAX_JWT_SECRET`, `BUILDMAX_WORKER_TOKEN`).

6. **`make deploy`**
   - New subcommand in the root `make` script that: (1) builds binaries (`./make build` or equivalent), (2) builds and loads the image into kind (`./make pub_images` or equivalent), (3) applies the deployment YAML to the kind cluster (e.g. `kubectl apply -f ...`).
   - Assumes the kind cluster and dependencies (MinIO, MySQL) already exist (e.g. after `./make setup`); does not create the cluster.

7. **Dockerfile for portal**
   - New Dockerfile for the portal application (React + Vite + TypeScript in `portal/`). Multi-stage: build the static assets with Node/npm, then serve them with a minimal runtime (e.g. nginx or similar). Enables building a portal image for future deployment (e.g. at `buildmax.kind.local`). Naming: e.g. `Dockerfile.portal` at repo root or in `portal/`.

## Out of scope

- Helm chart or Kustomize (plain YAML only).
- Using local_fs for persist/artifact storage inside the cluster (MinIO only).
- Deploying or managing MySQL/MinIO (they remain from `./make setup`).
- Production hardening (RBAC, network policies, resource limits beyond basics, TLS).
- Deploying the portal to the kind cluster in this task (Dockerfile only; `buildmax.kind.local` is reserved for future portal deployment).
- CI/CD or automated testing of the deploy path.

## Deliverables

1. **Kubernetes manifests**
   - Namespace **`buildmax`** for the application (new namespace; cluster has `db`, `storage`, `ingress-nginx`, `test`, etc.).
   - Secret for `BUILDMAX_JWT_SECRET` and `BUILDMAX_WORKER_TOKEN` (or document how to create it).
   - Deployment: buildmax-server container, env as above, emptyDir at `/buildmax/worker/workspaces`, `BUILDMAX_WORKSPACES_DIR=/buildmax/worker/workspaces`.
   - Service for the server.
   - Ingress with host **`buildmax-api.kind.local`** routing to the buildmax API Service (so the API is reachable at `http://buildmax-api.kind.local` after adding the host to `/etc/hosts`). Host **`buildmax.kind.local`** is reserved for the portal.

2. **Dockerfile for portal**
   - New Dockerfile (e.g. `Dockerfile.portal`) for the React/Vite portal: build stage (Node, npm install, npm run build), then serve `portal/dist` with a static server (e.g. nginx). No deployment to kind in this task; image can be used later for portal at `buildmax.kind.local`.

3. **`make deploy`**
   - Implement in repo root `make` script: build → pub_images → kubectl apply -f <manifests>.
   - Use `BUILDMAX_KIND_CLUSTER` for context/name if applicable.
   - Document in `make` usage and/or `setup/README.md` that cluster must exist (e.g. `./make setup` first) and that JWT/worker token must be set (Secret or env).

4. **Docs**
   - Brief note in `setup/README.md` (or adjacent) on how to deploy buildmax to kind (prereqs, `make deploy`, how to set secrets). Document ingress hosts: add `127.0.0.1 buildmax-api.kind.local` to `/etc/hosts` to use the API; `buildmax.kind.local` reserved for the portal.

## Acceptance criteria

- [ ] Plain YAML manifests exist; no Helm.
- [ ] Deployment uses `buildmax:local`, one container running buildmax-server, with env for MySQL (`mysql.db.svc.cluster.local`) and MinIO (`minio.storage.svc.cluster.local`), `BUILDMAX_PERSIST_STORAGE=minio`, `BUILDMAX_ARTIFACT_STORAGE=minio`, and **`BUILDMAX_CORS_ORIGIN=http://buildmax.kind.local`** so the portal can call the API.
- [ ] Pod has emptyDir mounted at `/buildmax/worker/workspaces` and `BUILDMAX_WORKSPACES_DIR=/buildmax/worker/workspaces` set so the in-pod worker uses it.
- [ ] Server is reachable inside the cluster (Service in namespace `buildmax`); worker env `BUILDMAX_SERVER_URL` points at that service (e.g. `http://buildmax.buildmax.svc.cluster.local:5678`); `BUILDMAX_WORKER_TOKEN` is set and matches server expectation.
- [ ] JWT secret and worker token are provided via Secret (or clearly documented).
- [ ] `./make deploy` runs build, pub_images, and applies the manifests; succeeds when kind cluster and setup (MinIO, MySQL) are already present.
- [ ] Ingress exists with host `buildmax-api.kind.local`, routing to the buildmax API Service; docs state that adding `127.0.0.1 buildmax-api.kind.local` to `/etc/hosts` allows visiting the API from the local machine; `buildmax.kind.local` is documented as reserved for the portal.
- [ ] After `make deploy`, server pod runs and (with valid DB and bucket) the API is usable at `http://buildmax-api.kind.local` (after `/etc/hosts` is updated).
- [ ] Dockerfile for the portal (React/Vite) exists; multi-stage build produces a runnable image that serves the built static assets (e.g. nginx serving `portal/dist`).
