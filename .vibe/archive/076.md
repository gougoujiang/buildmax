# Task 076: Remove artifact table

## Goal

Remove the `artifact` table and use **chat_run** as the single identity for run output (one artifact per run). File metadata stays in a table keyed by `chat_run_id`; blob storage and API continue to expose "artifacts" but identified by `chat_run_id` instead of a separate `artifact_id`.

## Context

- **Current model**: `artifact` (artifact_id, chat_id, chat_run_id, created_at, seq) is 1–1 with a successful chat run. `artifact_item` (artifact_item_id, artifact_id, relative_path) lists files per artifact. Blob keys use `workspace/artifacts/chatID/chatRunID/artifactID/...`.
- **Observation**: With artifact 1–1 to chat_run, the artifact table is redundant; we can treat the successful run as the artifact and key everything by `chat_run_id`.

## In scope

1. **Database**
  - Drop the `artifact` table.
  - Keep file-level metadata: either rename/repurpose `artifact_item` to be keyed by `chat_run_id` (e.g. `chat_run_id`, `relative_path`), or introduce a small table like `chat_run_output_file(chat_run_id, relative_path)`. Migration: move existing artifact_item rows to the new shape using artifact → chat_run_id from the artifact row before dropping artifact.
  - Remove `chat.last_artifact_id` and `chat.artifact_seq`; "last artifact" is implied by `last_run_id` when that run has status SUCCEEDED (and has output files).
2. **Entity & storage**
  - Remove `model.Artifact` and `entity.Artifact`; remove or refactor `ArtifactWithChat` to a DTO that carries chat_run_id, chat_id, workspace_id, created_at, chat_input_snippet (from run/chat).
  - Replace `ArtifactStore` with a smaller interface (or extend ChatRunStore): e.g. "list runs with output by workspace (optional chat_id)", "get run by id", "list output files for run", "record output files for run on completion".
  - Implement the new store methods in `internal/storage/entity` and keep the single Store implementing the new interface.
3. **Blob storage**
  - Change artifact blob layout from `.../artifacts/chatID/chatRunID/artifactID/...` to `.../artifacts/chatID/chatRunID/...` (drop artifactID segment). One namespace per chat run.
  - Update `ArtifactStorage` interface and implementations (local FS, S3) to use (workspaceID, chatID, chatRunID) only; no artifactID parameter. Adjust `PutResult`/`GetResult` and `PutArtifactFile`/`GetArtifactFile` signatures and keys accordingly.
  - Update `internal/storage/blob` keys (e.g. `ArtifactResultKey`, `ArtifactFileKey`) and any config that passes `ArtifactDir(..., artifactID)`.
4. **Executor & worker API**
  - Executor: on run success, stop generating a separate artifact_id; use `chat_run_id` as the output identifier. Upload result and files to blob using (workspaceID, chatID, chatRunID) only. Call server to "complete run with output" passing `chat_run_id` and `relative_paths`.
  - Worker PATCH payload: replace `artifact_id` with identifying the run (already have chat_run_id); send `relative_paths` only (or keep a single optional `artifact_id` for backward compat as chat_run_id if needed during migration; this task can assume clean break).
  - Server: `OnRunComplete(ctx, chatRunID, relativePaths)` — create output-file rows for chat_run_id, update chat denormalized fields (no last_artifact_id / artifact_seq).
5. **HTTP API**
  - Keep routes: `GET /api/workspaces/{id}/artifacts`, `GET .../artifacts/{id}/items`, `GET .../artifacts/{id}/content`. The `id` in these routes becomes **chat_run_id** (interpret as "run output" / "artifact").
  - List artifacts: return successful runs (with output) in the workspace (optional chat_id filter), each with chat_run_id, chat_id, workspace_id, created_at, chat_input_snippet.
  - Items: list output files for that chat_run_id.
  - Content: serve file by path for that chat_run_id from blob (no artifact_id in blob path).
6. **Portal (frontend)**
  - No URL or UX change: "artifact" id in the API is now chat_run_id. Frontend continues to call same endpoints with the same shape; only the meaning of the id changes (artifact_id → chat_run_id). Ensure types and mappers use the same field name for the identifier (e.g. keep `artifact_id` in JSON as the run output identifier, or rename to `chat_run_id` in API and update frontend accordingly). Prefer keeping `artifact_id` in API response as the chat_run_id value to minimize frontend changes.
7. **Config & wiring**
  - Remove or repurpose `ArtifactStore` from server config; wire the new "run output" listing/read from Store. Keep `ArtifactStorage` (blob) but with the updated interface (no artifactID). Update `servercmd`, tests, and any setup that builds ArtifactStore/ArtifactStorage.
8. **Tests**
  - Update entity tests (store), executor tests, server handler tests, and any test that mocks ArtifactStore or uses artifact_id. Table-driven tests where applicable.

## Out of scope

- **Migration of existing blob data**: Do not migrate existing S3/FS keys from `.../artifactID/...` to `.../` in this task; either document that new layout applies to new runs only and old artifact URLs may break, or add a one-time migration script in a follow-up. For this task, define the new layout and use it for all new writes; migration of old data can be a separate task.
- **Removing the concept of "artifact" from the product**: The user-facing concept (view run output, list outputs) stays; only the backend table and id semantics change.
- **Changing Portal routes or UX** beyond adapting to API id semantics if needed.

## Deliverables

- DB: artifact table dropped; artifact_item replaced or renamed to chat_run–scoped output file table; chat columns last_artifact_id and artifact_seq removed; migration(s) to apply and back out safely.
- Entity/model: Artifact removed; new or refactored DTO and store interface for "run output" by chat_run_id; Store implementation.
- Blob: ArtifactStorage and key helpers use (workspaceID, chatID, chatRunID) only; no artifactID.
- Executor + worker API: report success with chat_run_id + relativePaths; no artifact_id generation.
- Server: OnRunComplete(chatRunID, relativePaths); artifact handlers use chat_run_id as id; list returns run-based "artifacts".
- Portal: works with API (id = chat_run_id); minimal changes if API keeps same response shape.
- Tests updated and passing; build and `./make test` pass.

## Acceptance criteria

- `artifact` table no longer exists; output files are associated with `chat_run_id`.
- `chat` has no `last_artifact_id` or `artifact_seq`; last run output is inferred from `last_run_id` and run status.
- GET /api/workspaces/{id}/artifacts returns run-based list (id in response can be chat_run_id); optional chat_id filter works.
- GET .../artifacts/{id}/items and .../content work with id = chat_run_id; blob paths use only workspace/chat/run.
- Worker PATCH on success sends chat_run_id and relative_paths; server creates output file rows and updates chat without artifact table.
- Executor and blob layer do not generate or use artifact_id.
- Portal list and artifact view/modals work; no regressions.
- `go build ./...` and `./make test` pass.
