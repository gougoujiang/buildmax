# Task 110: New task from agent should also use conversation based

## Goal

Make "starting a task from an agent" indistinguishable from starting a conversation: the portal creates a conversation, the initial message tells Tier 1 to start a background task with the selected agent, and Tier 1 knows which agents exist so it can pass the correct `agent_id` to the `StartTask` tool.

## Context

- **Current "New Task from Agent" flow**: In `AgentList.tsx`, clicking "New task" opens `NewConversationFromAgent`. The modal prefills a textarea with agent name/description/instructions. On submit, it calls `createConversation()`, sets `pendingConversation` with the prefilled text as `initialMessage`, and navigates to the new `ConversationDetail`. The first message is sent via WebSocket and Tier 1 processes it. This already goes through the conversation flow.
- **Problem 1 — Naming**: The button says "New task" and the modal is called `NewConversationFromAgent`, but the action is really "start a new conversation (with this agent's context)". This is confusing given that we now want users to only interact with conversations, not tasks directly.
- **Problem 2 — No agent_id in context**: The initial message contains agent name, description, and instructions as plain text, but does **not** include the `agent_id`. Tier 1 cannot reliably pass the correct `agent_id` to `StartTask` because it doesn't know the mapping between agent names and IDs.
- **Problem 3 — Tier 1 doesn't know available agents**: The `StartTask` tool has an `agent_id` parameter, but the tool description and system prompt provide no information about which agents exist. The LLM has to guess or the user must type agent IDs manually.

## In scope

1. **Inject available agents into the StartTask tool description** — When building conversation tools, fetch the user's agents from `AgentStore` and append them to the `StartTask` tool description so the LLM knows which agents exist (name, ID, description).
2. **Include agent_id in the initial message from agent** — When the portal starts a conversation from an agent card, the initial message should include the `agent_id` so Tier 1 can reference it when calling `StartTask`.
3. **Rename UI elements** — Change "New task" to "New Conversation" on agent cards. Adjust the modal title/button text accordingly.

## Out of scope

- Storing `agent_id` on the conversation entity (the agent context is in the message, not the conversation).
- Changing the `conversation.create` WebSocket event schema (the `agent_id` is embedded in the message text).
- Changing how `StartTask` tool executes — it already accepts `agent_id`, that part works.
- Agent selection UI within the conversation (user picks agent after conversation starts) — Tier 1 already has `agent_id` as a tool parameter.

## Deliverables

### 1. Dynamic StartTask tool description with available agents

**Where**: `internal/execution/agenttool/start_chat.go` (tool definition) and `internal/core/conversation/service.go` (tool wiring)

Currently `startTaskTool.Description()` returns a static string. Change so available agents are injected:
- Add an `agents` field to `startTaskTool` (list of agent summaries: id, name, description).
- `Description()` appends the agent list when non-empty:
  ```
  ...Use this when the user asks for a long-running job, analysis, or work that should run in the background.
  
  Available agents:
  - agent_name (id: a_xxxx) - agent description
  - another_agent (id: a_yyyy) - another description
  ```
- In `conversation.Service`, when building tool runners, fetch the user's agents from `AgentStore` and pass them to `NewStartTaskTool`.

**Requires**: `conversation.Service` needs access to `AgentStore`. Add `AgentStore entity.AgentStore` field to `conversation.Service`.

### 2. Include agent_id in the initial message from agent card

**Where**: `portal/src/pages/AgentList.tsx`, `portal/src/components/NewConversationFromAgent.tsx`

Currently `buildAgentPreview(agent)` produces:
```
Agent: {name}
Description: {description}
Instructions:
{instructions}
```

Change to include the agent ID:
```
Agent: {name} (id: {id})
Description: {description}
Instructions:
{instructions}

Please start a background task with this agent.
```

This gives Tier 1 all the information it needs to call `StartTask(input=..., agent_id=<the id>)`.

### 3. Rename portal UI elements

**Where**: `portal/src/pages/AgentList.tsx`, `portal/src/components/NewConversationFromAgent.tsx`

- Agent card button: "New task" → "New Conversation"
- Modal title: adjust if it says "New Task" → "New Conversation"
- Modal submit button: "Start task" → "Start Conversation" (or similar)

### 4. Wire AgentStore into conversation.Service

**Where**: `internal/core/conversation/service.go`, `internal/server/portal/ws_handler.go` (conversationService builder), `internal/server/portal/conversation_handlers.go` (conversationService builder)

The conversation service is built on-demand in the portal handler. Add `AgentStore` to the `Service` struct and pass it when constructing the service. The service uses it to fetch agents for the dynamic tool description.

## Acceptance

- [ ] The `StartTask` tool description dynamically lists the user's available agents (name, id, description) when agents exist.
- [ ] When a user starts a conversation from an agent card, the initial message includes the `agent_id`.
- [ ] The agent card button says "New Conversation" instead of "New task".
- [ ] The modal title and submit button text reflect "conversation" instead of "task".
- [ ] Tier 1, when receiving a message that says "start a background task with agent X (id: a_xxx)", can call `StartTask` with the correct `agent_id` because the tool description lists available agents.
