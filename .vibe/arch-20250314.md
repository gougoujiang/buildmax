# Architecture Refactor: internal/server

**Scope:** `internal/server` package (33 Go files: handlers, middleware, auth, stream hub, conversation adapters, tests).

**Date:** 2025-03-14.

## Summary

The `internal/server` package has grown into a single flat namespace with many responsibilities: HTTP routing, auth, workspace/chat/agent/artifact/conversation/worker handlers, stream buffering, and Tier 1 conversation adapters. This makes the package hard to navigate, test in isolation, and extend. The proposals below focus on **package boundaries**, **dependency grouping**, and **moving domain adapters out of the HTTP layer** without changing external API behavior.

---

## 1. Split Config into grouped options

**Scope:** `internal/server` — `Config` struct and `New()` in `server.go`.

**Current state:** `Config` has 20+ fields in one flat struct: stores (User, Workspace, Agent, Chat, ChatRun, RunOutputLister, ConversationStore, ConversationMessageStore), blob (PersistStorage, ArtifactStorage), paths (WorkspacesDir), auth (JWTSecret, CORSOrigin, WorkerToken), optional behavior (ChatTitleGenerator, QuotaChecker, DefaultQuotaTier, ConversationEngine, PortalAdapter, ConversationLLMCaller). Every new feature adds more optional fields. Callers (e.g. `internal/bootstrap/server.go`) construct one large literal.

**Proposed change:** Introduce grouped config structs (e.g. `AuthConfig`, `ConversationConfig`, `WorkerConfig`, `StorageConfig`) and embed or reference them in `Config`. Keep `Config` as the single struct passed to `New()` but organize fields so that (a) related options live together, (b) optional feature blocks are clearly grouped, and (c) future additions (e.g. rate limiting) have a natural place. Optionally, use a functional options pattern for optional groups to reduce constructor clutter.

**Benefit:** Clearer configuration surface; easier to see what is required for auth vs. conversation vs. worker; simpler to add new optional features without inflating a single struct.

**Impact:** Medium (touch all `Config` construction sites; no change to handler logic).

---

## 2. Extract StreamHub into a separate package

**Scope:** `internal/server/stream_hub.go` (and `stream_hub_test.go`).

**Current state:** `StreamHub` interface and `memStreamHub` implementation live in `package server`. They are generic: chat-scoped stream buffers with Append/Buffer/Done/Subscribe. Handlers and worker handlers depend on `s.hub`; the concept is not HTTP-specific.

**Proposed change:** Move `StreamHub`, `StreamEventDone`, `NewStreamHub()`, and the in-memory implementation to a new package, e.g. `internal/streamhub` (or `internal/server/stream` if you prefer to keep it under server). `Server` would hold a `streamhub.StreamHub` and pass it to handlers that need it. Tests for the hub can run without importing the rest of `server`.

**Benefit:** Reusable stream buffer abstraction; can test or replace (e.g. Redis-backed) without pulling in HTTP handlers; clearer single responsibility.

**Impact:** Low (one new package; server imports it and wires it in).

---

## 3. Move Tier 1 conversation adapters out of server

**Scope:** `internal/server/conversation_tier1.go`, `internal/server/conversation_tools.go`, and the adapter types used in `conversation_handlers.go` (e.g. `convTitleGen`).

**Current state:** `PortalAdapter`, `PassThroughEngine`, `serverStartChatRunner`, and `convTitleGen` implement interfaces defined in `internal/core/conversation` (and `internal/execution/agenttool`) but live in `internal/server`. Server both depends on `conversation` and owns concrete implementations that translate HTTP/portal concerns (e.g. request body, workspace/user context) into conversation/tool calls. This mixes HTTP transport with domain adaptation.

**Proposed change:** Move these adapters into a dedicated package that sits between server and conversation/tools, e.g. `internal/core/conversation/adapter` or `internal/server/adapter` (if you want to keep them next to server). Server would then depend on this adapter package and inject adapter instances into `Config` (or receive handler dependencies that use adapters). The adapter package would depend on `conversation`, `tools`, and `entity`; server would only call adapter constructors and pass them into the conversation engine. Optionally, `convTitleGen` could live in the same adapter package as a small type that wraps `ChatTitleGenerator` for the conversation package.

**Benefit:** Clear boundary: server = HTTP routing and request/response; adapter = translation from HTTP/portal context to conversation/tool APIs. Conversation package stays free of HTTP types; server stays free of conversation domain types beyond what handlers need to return.

**Impact:** Medium (new package or new files under conversation; server and servercmd wiring changes).

---

## 4. Introduce handler groups as optional subpackages

**Scope:** `internal/server` — all `*Handler` methods and their request/response types.

**Current state:** All handlers are methods on `*Server` in one package. Files are split by domain (workspaces, chats, agents, artifacts, conversation_handlers, conversation_tier1, conversation_tools, worker_handlers, stream_handlers, files, upload, login, otp, usage, middleware, auth, response, paths, query), but there is no package boundary. Every handler has access to the full `Config` and shared helpers (`withWorkspaceAuth`, `writeJSON`, etc.).

**Proposed change:** Option A — Keep a single package but document clear “handler groups” (auth, workspace CRUD, chats & runs, artifacts, conversations, worker, stream, files) and optionally group files into subdirectories that are still `package server` (e.g. `internal/server/handlers/workspaces.go` with `package server`). This improves navigation without changing Go package boundaries. Option B — Extract one or two cohesive groups into subpackages that receive only the dependencies they need (e.g. `server/worker` with a `Handler(cfg WorkerConfig) http.Handler` that registers worker routes and uses a minimal config). Start with the worker API (small, already distinct auth and semantics); if that works, consider a `server/portal` or `server/conversation` group for user-facing conversation and chat endpoints.

**Benefit:** Option A: easier to find code and enforce logical grouping. Option B: weaker coupling (worker handlers don’t depend on conversation or portal config), smaller surface for tests, and a pattern for future splits.

**Impact:** Option A — Low (move files, maybe adjust build tags or tooling). Option B — Medium (define per-group config and handler registration; main `server.New()` composes subpackages).

---

## 5. Centralize shared HTTP helpers in a small surface

**Scope:** `internal/server`: `auth.go`, `response.go`, `query.go`, `paths.go`, `middleware.go`.

**Current state:** Helpers like `requireAuth`, `withWorkspaceAuth`, `writeJSON`, `writeJSONError`, `parseLimitOffset`, `workspacesDir()`, and middleware are used across many handler files. They are all in `package server` and tied to `*Server` or global behavior (e.g. JWT secret in config).

**Proposed change:** Keep these in `internal/server` but group them under a minimal “core” surface: (1) a single file or clearly named files (e.g. `auth.go`, `response.go`, `middleware.go`) and (2) avoid spreading auth/response logic into handler files. If you later split handler groups into subpackages (proposal 4B), introduce a thin `server/httputil` (or `internal/httputil`) that provides pure functions for JSON write and query parsing, and have auth/middleware stay in the main server package so that only one place knows about JWT and workspace ownership. Document that all workspace-scoped handlers must use `withWorkspaceAuth` and that response helpers are the single way to send JSON.

**Benefit:** Predictable place for cross-cutting HTTP behavior; when splitting packages, you avoid duplicating auth or response logic.

**Impact:** Low (reorganize or document; optional small `httputil` only if splitting packages).

---

## 6. Reduce Server’s direct store usage in favor of use-case facades (optional, longer term)

**Scope:** `internal/server` — handlers that call multiple stores (e.g. create chat + create run + optional conversation).

**Current state:** Handlers often call `s.cfg.ChatStore`, `s.cfg.ChatRunStore`, `s.cfg.ConversationStore`, etc., and orchestrate multi-step logic (e.g. create conversation, create chat, create run, maybe call conversation engine). Server is aware of entity and storage details.

**Proposed change:** Introduce small “use case” or “application” facades (e.g. in `internal/core` or a dedicated server-facing use-case package) that expose methods like `CreateChatRun(workspaceID, userID, input, …)` and internally use the appropriate stores and conversation engine. Handlers would call these facades instead of touching stores directly. This would reduce the number of store interfaces that `Config` and handlers need, and keep transaction or ordering logic in one place.

**Benefit:** Handlers become thinner (parse request, call facade, write response); easier to test use cases without mocking many stores; clearer place for cross-store workflows.

**Impact:** High (new layer and refactor of several handlers); defer until after 1–4 are done.

## Changes for review

| # | Proposal | New/edited packages or files | Main change |
|---|----------|------------------------------|-------------|
| 1 | Config grouping | `server.go` (Config struct); `internal/bootstrap/server.go` (construction) | Grouped config structs or options |
| 2 | Extract StreamHub | New `internal/streamhub` (or `internal/server/stream`); `server.go`, `stream_handlers.go`, `worker_handlers.go` | Move interface and impl to dedicated package |
| 3 | Conversation adapters | New `internal/core/conversation/adapter` or `internal/server/adapter`; move types from `conversation_tier1.go`, `conversation_tools.go`, adapters in `conversation_handlers.go` | Server wires adapters; adapter package implements conversation/tool interfaces |
| 4 | Handler groups | Option A: `internal/server/` subdirs, same package. Option B: e.g. `internal/server/worker` subpackage with own config and route registration | Clear grouping or subpackages for worker (and optionally portal/conversation) |
| 5 | Shared HTTP helpers | `auth.go`, `response.go`, `middleware.go`, `query.go`, `paths.go`; optional `server/httputil` or `internal/httputil` | Single documented surface; optional small httputil if splitting |
| 6 | Use-case facades (optional) | New `internal/core` facade or dedicated server-facing use-case package; refactor handlers to call facades | Handlers call use-case facade instead of stores directly |

Recommended order: **2** (StreamHub) and **5** (helpers) first (low risk); then **1** (Config) and **3** (adapters); then **4** (handler groups, starting with worker). Defer **6** until the package is stable.
