# Task 067: Use k8s job to run worker instead of local process

## Goal

Make how the scheduler runs a worker configurable: keep the current **local process** mode (spawn `buildmax-worker` in the same host/pod) and add **Kubernetes Job** mode so that each task is run by a Job in the same cluster (e.g. kind). This improves scalability when many tasks run concurrently. When Job mode is enabled, the server creates a k8s Job per claimed task; the Job pod runs `buildmax-worker --task-id <id>` with the same env (server URL, worker token, MinIO/storage). RBAC (ServiceAccount, ClusterRole, RoleBinding) is added so the server deployment can create Jobs in the cluster.

## Context

- **Current behavior**: `internal/executor.Scheduler` polls for PENDING tasks, claims one (PENDING→SCHEDULED), and runs `exec.CommandContext(ctx, workerPath, "--task-id", task.TaskID)` with inherited env; `cmd.Run()` blocks until the worker exits. Used by `internal/servercmd.RunServer`, which gets `workerPath` from `config.WorkerBinaryPath()` (env `BUILDMAX_WORKER_BINARY`, default `buildmax-worker`).
- **Deployment**: `setup/buildmax-deploy.yaml` deploys the server in namespace `buildmax` with image `buildmax:local` (same image contains buildmax, buildmax-server, buildmax-worker). No ServiceAccount or RBAC is defined; the server pod cannot create Jobs today.
- **Worker requirements**: The worker needs `BUILDMAX_SERVER_URL`, `BUILDMAX_WORKER_TOKEN`, `BUILDMAX_WORKSPACES_DIR`, and storage env (MinIO or local). In Job mode, each Job pod gets these via env from the Job spec (e.g. copied from server env or from a shared Secret/ConfigMap).
- **Conventions**: Config is env-only (`internal/config`, `env_spec.go`). Single table names in DB; snake_case for persisted JSON. AGENTS.md documents executor and server/worker layout.

## Scope

### In scope

- **Runner strategy configuration**: Add a configurable “worker run mode”: `local_process` (current) or `k8s_job`. Source: new env var (e.g. `BUILDMAX_WORKER_RUN_MODE`, default `local_process`). When `local_process`, scheduler behavior is unchanged (spawn local binary, block until exit, revert to PENDING on spawn failure). When `k8s_job`, scheduler creates a Kubernetes Job in a target namespace (e.g. same as server: `buildmax`) instead of exec’ing; no blocking wait on Job completion (fire-and-forget); on Job create failure, revert task to PENDING.
- **Executor changes**: Introduce an abstraction for “run worker for task” (e.g. interface or strategy type) so the scheduler loop calls it instead of directly exec’ing. Implementations: (1) local process runner (current logic), (2) k8s Job runner that builds a Job spec and submits it via cluster config (in-cluster or kubeconfig). Scheduler constructor accepts this runner/strategy (from servercmd based on config). No change to `RunTask` or worker binary.
- **Kubernetes Job spec**: Job name follows the pattern `buildmax-worker-<task-id>-<timestamp>` (timestamp for uniqueness; e.g. Unix seconds). Namespace from env or default `buildmax`. Job runs one pod, restart policy appropriate for Jobs (e.g. OnFailure with backoff limit). Container: same image as server (e.g. `buildmax:local`), command `buildmax-worker`, args `--task-id <task.TaskID>`. Env: pass through `BUILDMAX_SERVER_URL`, `BUILDMAX_WORKER_TOKEN`, `BUILDMAX_WORKSPACES_DIR`, and all storage-related env (MinIO keys, bucket, prefix, etc.) so the worker can reach server and MinIO. Server URL must be reachable from the Job pod (e.g. `http://buildmax.buildmax.svc.cluster.local:5678`). No need for server to mount a shared workspace volume for Job mode; worker uses its own filesystem and MinIO for materialize/artifacts.
- **RBAC for server**: So that the server pod can create (and optionally list/delete) Jobs in the target namespace: create a ServiceAccount for the server Deployment, a ClusterRole (or Role in that namespace) that allows create/get/list/delete of `jobs` and `pods` (and optionally `events`) in that namespace, and a RoleBinding (or ClusterRoleBinding) binding that Role/ClusterRole to the ServiceAccount. Update the server Deployment to use that ServiceAccount. All in `setup/buildmax-deploy.yaml` (or a separate manifest applied with it).
- **Config**: New env key in `env_spec.go` and a getter in `config` (e.g. `WorkerRunMode() string` returning `local_process` or `k8s_job`). Optional: env for Job namespace (e.g. `BUILDMAX_WORKER_JOB_NAMESPACE`, default `buildmax`) and worker image (e.g. `BUILDMAX_WORKER_IMAGE`, default same as server or `buildmax:local`) so deployers can override.
- **Persist worker info on task**: When the scheduler runs a worker (either mode), persist the following on the task record: `worker_type` (`local_process` or `k8s_job`); for k8s_job mode also persist `k8s_job_name` and `k8s_job_created_at` (Unix timestamp when the Job was created). Job name pattern: `buildmax-worker-<task-id>-<timestamp>` (timestamp is used for uniqueness and traceability; e.g. Unix seconds or a short format). This requires adding these fields to the task model/table and extending the task store (and any status-update path used at claim/spawn time) so the scheduler can write them when it claims and runs a task.
- **Tests**: Unit tests for the new runner/strategy (local unchanged; k8s Job runner can be tested with a fake client or skipped in unit test if not in cluster). Existing scheduler tests remain valid; NewScheduler or equivalent may take a runner dependency instead of only workerPath when in local mode. `go build ./...` and `go test ./...` must pass.

### Out of scope

- Waiting for Job completion in the server (e.g. watch Job until succeeded/failed) or updating task status from the server based on Job status; the worker continues to update task status via the existing API (PATCH). Cleanup of completed/failed Job pods (e.g. TTL or cron) can be a follow-up.
- Supporting multiple clusters or arbitrary kubeconfig path; assume in-cluster config when running inside the cluster, or a single kubeconfig from env for local dev.
- Changing the worker binary or the executor `RunTask` flow.
- Helm or other packaging; only the existing YAML deployment is extended.

## Deliverables

1. **Config**: `BUILDMAX_WORKER_RUN_MODE` (values `local_process` | `k8s_job`, default `local_process`). Optionally `BUILDMAX_WORKER_JOB_NAMESPACE` (default `buildmax`) and `BUILDMAX_WORKER_IMAGE` (default e.g. `buildmax:local`). `internal/config`: getters and `env_spec.go` updated.
2. **Executor**: Abstraction for “run worker for task” (e.g. `WorkerRunner` interface with `Run(ctx, task)` or similar). Local implementation: current exec logic. K8s implementation: build batch/v1 Job spec, submit via client-go (or equivalent), return on create success/failure; on create failure, caller reverts task to PENDING. Scheduler loop uses this abstraction; when mode is `local_process`, scheduler gets local runner (with workerPath); when `k8s_job`, scheduler gets k8s runner (with namespace, image, env map or reference to Secret). `internal/servercmd.RunServer`: read run mode from config, construct appropriate runner, pass to scheduler.
3. **K8s Job spec**: One Job per task; name pattern `buildmax-worker-<task-id>-<timestamp>`; namespace from config. Pod: one container, image from config, command `buildmax-worker`, args `["--task-id", task.TaskID]`; env from server (or from a Secret that the server also uses). Restart policy and backoff limit set so the Job is not restarted indefinitely.
4. **Task record worker info**: Add to the task model (and DB table): `worker_type` (string: `local_process` | `k8s_job`), `k8s_job_name` (*string, optional), `k8s_job_created_at` (*int64, optional, Unix timestamp). When the scheduler claims and runs a task: for local_process, set worker_type and leave k8s fields nil; for k8s_job, set worker_type, k8s_job_name (the Job name used), and k8s_job_created_at. Extend TaskStore (e.g. UpdateTaskStatusIf or a dedicated method) so the scheduler can persist these at claim/spawn time. API/Portal: expose these fields on task responses if desired (in scope for this task: persistence and scheduler writing; API response shape can be a small follow-up or included here).
6. **RBAC**: In `setup/buildmax-deploy.yaml` (or linked file): ServiceAccount `buildmax-server` in namespace `buildmax`; Role/ClusterRole with rules for `jobs` and `pods` (create, get, list, delete) in namespace `buildmax`; RoleBinding binding that Role to the ServiceAccount; server Deployment `spec.template.spec.serviceAccountName: buildmax-server`.
7. **Tests**: Scheduler (or runner) tests updated/added so that local mode still validates current behavior; k8s runner can be covered by a test that mocks the k8s client or is skipped when not in cluster. No flaky e2e in this task.

## Acceptance criteria

- [ ] With `BUILDMAX_WORKER_RUN_MODE=local_process` (or unset), server behaves as today: scheduler spawns `buildmax-worker` locally and waits for exit; on spawn failure task is reverted to PENDING.
- [ ] With `BUILDMAX_WORKER_RUN_MODE=k8s_job`, server creates a Kubernetes Job per claimed task in the configured namespace; Job pod runs `buildmax-worker --task-id <id>` with env that allows it to reach the server and MinIO; on Job create failure, task is reverted to PENDING.
- [ ] Server deployment in `setup/buildmax-deploy.yaml` uses a ServiceAccount that has permission to create (and optionally list/delete) Jobs and Pods in the buildmax namespace; deploying the YAML and running a task in k8s_job mode does not fail with RBAC errors.
- [ ] Env keys for run mode (and optional namespace/image) are documented in `env_spec.go` and `.env.example`.
- [ ] Task record stores `worker_type` (`local_process` or `k8s_job`); for k8s_job mode also `k8s_job_name` (pattern `buildmax-worker-<task-id>-<timestamp>`) and `k8s_job_created_at` (Unix timestamp). Scheduler writes these when it claims and runs a task.
- [ ] `go build ./...` and `go test ./...` succeed.
