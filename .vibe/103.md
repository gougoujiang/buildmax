# Task 103 - Login from desktop and TUI

## Goal

Add unified user authentication to the desktop app and TUI/CLI so users can log in to the BuildMax server from any client, not just the portal.

## Context

- **Portal auth already exists**: `POST /api/otp/request` (email + intent) and `POST /api/login` (email + OTP → JWT + user). OTP is currently hardcoded `123456`. JWT is HS256, 24h expiry, `sub` = user ID. Portal stores token/user in `localStorage`.
- **Desktop is fully local**: Wails app with Go bindings (`ListSessions`, `GetSession`, `SendMessage`, `SendMessageStream`). No auth, no server connection. Single-page layout (sidebar + chat).
- **TUI/CLI is fully local**: Bubble Tea TUI or `-p` print mode. Config from env + `~/.buildmax/settings.json`. No auth, no server connection. Cobra commands: root (TUI), `version`.
- **Settings file** (`~/.buildmax/settings.json`): currently stores `models[]` only. No auth token storage.
- **Three user-facing clients** (portal, desktop, TUI) should share a unified user identity model. The worker (`buildmax-worker`) uses machine credentials and is not part of this task.

## "Login" (this task)

For this task, "login" means:

1. A shared Go credential store that persists server URL, JWT token, and basic user info to disk
2. CLI subcommands (`login`, `logout`, `whoami`) that authenticate against the server using the existing OTP flow
3. Desktop Go bindings and a frontend login screen that perform the same OTP flow
4. A shared authenticated HTTP client that CLI and desktop can use for future server API calls

We are **not** yet implementing:

- Browser-based / device-code login flow (open browser → redirect back)
- Refresh tokens or token auto-renewal
- Multi-profile / multi-server support
- Auth-gated features in CLI or desktop (conversations, tasks, artifacts sync) — those are follow-up tasks that will use the auth infrastructure built here
- Any changes to the portal's existing auth flow
- Any changes to buildmax-worker authentication

## Deliverables

1. **`internal/auth/` — credential store (new package)**
   - **`credentials.go`**: `Credentials` struct (server URL, JWT token, user ID, email, name, saved timestamp). `Save(path)` and `Load(path)` — JSON file at `DataDir()/auth.json`. `Clear(path)` to delete. `IsValid()` checks token is non-empty (no expiry check for now).
   - **`client.go`**: `Client` struct wrapping `http.Client` + server base URL + token. Methods: `RequestOTP(email, intent) error`, `Login(email, otp) (*LoginResponse, error)`. `LoginResponse` = token + user (id, email, name). Reuses the same request/response shapes as the existing server endpoints.
   - No dependency on TUI, desktop, or Cobra.

2. **`internal/config/` — auth path helper**
   - **`AuthPath() string`**: returns `DataDir()/auth.json`. Single source of truth for the credentials file location.

3. **`internal/cmd/cli/` — CLI login commands**
   - **`buildmax login`**: Cobra subcommand. Prompts for server URL (default from env `BUILDMAX_SERVER_URL` or `http://localhost:5678`), email, then calls `RequestOTP`. Prompts for OTP, calls `Login`. On success, saves credentials via `auth.Save()`. Prints confirmation.
   - **`buildmax logout`**: Clears stored credentials via `auth.Clear()`. Prints confirmation.
   - **`buildmax whoami`**: Loads credentials, prints user email and server URL, or "not logged in".
   - All three work in non-TUI mode (plain stdin/stdout, no Bubble Tea).

4. **`internal/cmd/desktop/` — desktop login bindings**
   - **`Login(serverURL, email, otp string) (*auth.LoginResponse, error)`**: Go binding exposed to Wails frontend. Calls `auth.Client.Login`, saves credentials on success.
   - **`RequestOTP(serverURL, email, intent string) error`**: Go binding for OTP request step.
   - **`Logout() error`**: Clears credentials.
   - **`GetAuthStatus() (*AuthStatus, error)`**: Returns current auth state (logged in? user info? server URL?) for the frontend to check on startup.

5. **Desktop frontend — login screen**
   - **Login page**: Two-step form (email → OTP), matching portal UX. Uses shared GUI components (`FormModal` or similar from `@buildmax/gui`).
   - **App startup**: Check `GetAuthStatus()`. If not logged in, show login screen. If logged in, show the existing chat UI.
   - **Logout**: Add a logout option (e.g. in sidebar or settings).

6. **Tests**
   - Unit tests for `internal/auth/` — credential save/load/clear, client request building.
   - No real HTTP calls in tests; use `httptest.Server` for client tests.

## Out of scope (for later)

- Browser-based OAuth / device-code flow
- Refresh tokens / automatic token renewal
- Token expiry detection and re-login prompt
- Multi-server or multi-profile support
- Auth-gated API features in CLI (sync sessions, remote tasks, etc.)
- Auth-gated features in desktop (remote conversations, file sync, etc.)
- Changes to portal auth or server auth endpoints
- TUI-mode login (interactive login inside Bubble Tea) — login is a separate CLI subcommand
