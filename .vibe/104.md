# Task 104: BuildMax TUI/CLI interactive mode login check

## Goal

Add a startup login check to both TUI (interactive) mode and print (`-p`) mode so the user must be authenticated before using the agent.

## Context

- **Auth infrastructure exists** (task 103): `internal/auth` has `Credentials`, `Load`, `Save`, `Clear`, `IsValid`; `internal/config` has `AuthPath()`. CLI already has `buildmax login`, `buildmax logout`, `buildmax whoami` subcommands.
- **No login check today**: `runRoot` in `internal/cmd/cli/root.go` goes straight to `runPrintMode` or `runTUI` without verifying credentials. A user who has never run `buildmax login` proceeds to an agent session that may fail at the LLM call.
- **Two modes, two behaviours**:
  - **TUI (interactive)**: Can show a message in the terminal and prompt the user to run `buildmax login`. The TUI should not launch if the user is not logged in.
  - **Print (`-p`)**: Non-interactive; cannot prompt. Must print an error message to stderr and exit with a non-zero status.
- **Credential check is lightweight**: Just `auth.Load(config.AuthPath())` + `creds.IsValid()`. No network call, no token validation against the server. That matches the current `IsValid` contract (token is non-empty).

## In scope

1. **Login gate in `runRoot`** — After resolving flags and session ID, before dispatching to `runTUI` or `runPrintMode`, load credentials and check `IsValid()`.
2. **Print mode behaviour** — If not logged in: print a clear message to stderr (`Not logged in. Run "buildmax login" first.`) and return an error (non-zero exit). Print mode is non-interactive; it should not prompt.
3. **TUI (interactive) mode behaviour** — If not logged in: run through the interactive login flow (prompt for server URL, email, OTP — same as `buildmax login`) before starting the TUI. On successful login, proceed to TUI normally. On failure (user aborts or OTP fails), print the error and exit.
4. **Extract interactive login logic** — The login prompting logic currently lives in `runLogin` (login.go). Extract it into a reusable function (`interactiveLogin`) so both `buildmax login` and the TUI startup login gate can call it.
5. **Skip check for non-agent subcommands** — `login`, `logout`, `whoami`, `version` must work without being logged in (they already run as separate Cobra subcommands, so no change needed — the check is in `runRoot` only).

## Out of scope

- Token expiry / validity checking against the server (future task).
- Auto-launching `buildmax login` from within the TUI.
- Refresh tokens or re-auth prompts mid-session.
- Changes to desktop app auth flow.
- Changes to `internal/auth` package itself.

## Deliverables

1. **`internal/cmd/cli/root.go`** — Add a login check in `runRoot`, after flag resolution and before dispatching to TUI/print mode. TUI mode: run interactive login flow. Print mode: print error and exit.
2. **`internal/cmd/cli/login.go`** — Extract the interactive prompting logic from `runLogin` into a reusable `interactiveLogin() error` function. `runLogin` calls it; `runRoot` calls it in TUI mode when not logged in.

## Acceptance

- [ ] Running `buildmax` (TUI) without logging in prompts for server URL, email, and OTP (same as `buildmax login`); on success, proceeds to TUI
- [ ] Running `buildmax` (TUI) without logging in, if user aborts or OTP fails, prints error and exits non-zero
- [ ] Running `buildmax -p "hello"` without logging in prints the same message to stderr and exits non-zero
- [ ] Running `buildmax login` still works without being logged in (no circular dependency)
- [ ] Running `buildmax version` still works without being logged in
- [ ] Running `buildmax whoami` still works without being logged in
- [ ] After `buildmax login`, both `buildmax` (TUI) and `buildmax -p "hello"` proceed normally
- [ ] `go build ./...` passes
