# Task 068: Support rerun existing task

## Goal

Allow users to add follow-up questions to an existing task so the agent continues the same conversation and produces another result. Each execution (initial question or follow-up) is modeled as a **task run**; the task aggregates the last run’s status and one shared session for the whole conversation.

## Context (current state)

- **Task**: One record per “user request” (workspace, optional project, input, status, output, session_id, worker_type, k8s_job_name, started_at, ended_at, artifact_seq, last_artifact_id). Creating a task creates one PENDING task; scheduler polls `GetNextPendingTask`, claims it (PENDING→SCHEDULED), spawns worker with `--task-id`; worker runs `buildmax -p <input> --session-id <new UUID>` and updates task status/artifact via PATCH.
- **Session**: One session per task; worker generates a new UUID and stores it on the task when marking RUNNING. Conversation is stored under task buildmax dir (`sessions/<id>.json`) and uploaded to persist storage after run. GET `/api/workspaces/{id}/tasks/{id}/conversation` reads that session.
- **Artifact**: One or more artifacts per task (artifact table has `task_id`, `artifact_id`, `seq`); task has `artifact_seq`, `last_artifact_id`. Blob path: `workspaces/<ws>/artifacts/<taskID>/<artifactID>/result.md`.
- **Portal**: Task detail page shows result, “Agent session” (conversation), and meta. No follow-up input today. Tasks are created via POST `/api/workspaces/{id}/tasks` with `input` and optional `project_id`.

## Decisions (locked)

| Decision | Choice |
|----------|--------|
| **Artifact blob path** | Option B: `artifacts/<taskID>/<runID>/<artifactID>` |
| **Task table after TaskRun** | Option A: Keep task columns as denormalized “last run” (status, output, started_at, ended_at, etc.) for simple reads. |
| **Concurrent runs per task** | Reject: If any run for the task is PENDING/SCHEDULED/RUNNING, reject new follow-up (e.g. 409 Conflict). |
| **Migration of existing tasks** | No migration: user will truncate tables; no backfill. |
| **Worker CLI** | Single flag `--task-run-id`. Worker gets task from server via run; no `--task-id`. |
| **Follow-up UX after submit** | Poll until the new run is SUCCEEDED or FAILED, then refresh task + conversation. |
| **Persist path for task buildmax** | Add run layer. Current: `…/workspaces/<ws>/tasks/<taskID>/` (buildmax subdir here). New: `…/workspaces/<ws>/tasks/<taskID>/<runID>/…` — each run has its own buildmax content (sessions, logs, settings) under `…/tasks/<taskID>/<runID>/buildmax/`. |

## Scope

### In scope

- Introduce **TaskRun** entity: one run per execution (initial or follow-up). Each run has: run_id, task_id, input, status, output, error_message, started_at, ended_at, session_id (set when run starts), worker_type, k8s_job_name, k8s_job_created_at, created_at. Artifact belongs to task run; blob path `artifacts/<taskID>/<runID>/<artifactID>`.
- **Task**: workspace_id, project_id, created_by, created_at, session_id (one conversation for all runs). Denormalized “last run” fields on task: status, output, started_at, ended_at, error_message, worker_type, k8s_job_name, k8s_job_created_at, last_artifact_id (or equivalent) so list/get task stay simple.
- **Create task**: Creates Task + first TaskRun (input = body.input, status PENDING). Scheduler polls for next PENDING task run.
- **Follow-up**: POST `/api/workspaces/{id}/tasks/{task_id}/runs` with body `{ "input": "follow-up text" }`. Creates new TaskRun (PENDING) only if no run for that task is PENDING/SCHEDULED/RUNNING; otherwise return 409 Conflict.
- **Worker**: accepts only `--task-run-id`. GET worker API (e.g. GET `/api/worker/task-runs/{run_id}`) returns run + task (run input, task workspace_id, project_id, session_id). Worker resolves task from run; if task has session_id, fetch previous run’s buildmax session from persist into current run’s buildmax dir (`…/tasks/<taskID>/<runID>/buildmax/`), then run `buildmax -p <run.input> --session-id <task.session_id>`; else generate new session_id. After run, PATCH updates run and task (session_id, denormalized last-run fields). Persist: upload this run’s buildmax to `…/tasks/<taskID>/<runID>/buildmax/`.
- **Scheduler**: Polls GetNextPendingTaskRun(); claims run (PENDING→SCHEDULED); spawns worker with `--task-run-id <run_id>`.
- **API responses**: List/get task show denormalized last-run state. Conversation: GET `.../tasks/{id}/conversation` — server resolves “current” session (e.g. from task.session_id and latest run’s buildmax or a single merged view; see design). List artifacts: by workspace/task; path includes run_id.
- **Portal – Task detail**: Follow-up input + submit → POST runs. Then poll until the new run is SUCCEEDED or FAILED; then refresh task and conversation.
- **DB**: New table `task_run`. Artifact has task_run_id. Task keeps denormalized last-run columns. No migration of existing data; tables can be truncated.

### Out of scope

- Editing or deleting a specific run; only “last run” state is shown on the task card.
- Allowing multiple concurrent runs per task (we reject with 409 if a run is already in progress).
- Restore / “revert to previous run” in UI (mentioned as future in current Task detail).
- Config file or Viper-based config; env-only remains.
- Backward compatibility or data migration; user will truncate tables.

## Deliverables

1. **Data model**
   - `TaskRun`: run_id (PK), task_id (FK), input, status, output, error_message, started_at, ended_at, session_id (set when run starts; first run sets task.session_id, later runs reuse it), worker_type, k8s_job_name, k8s_job_created_at, created_at. Status flow: PENDING → SCHEDULED → RUNNING → SUCCEEDED | FAILED.
   - `Task`: workspace_id, project_id, created_by, created_at, session_id; plus denormalized last-run fields: status, output, started_at, ended_at, error_message, worker_type, k8s_job_name, k8s_job_created_at, last_artifact_id. Updated when a run completes.
   - `Artifact`: task_run_id (required); artifact blob path `artifacts/<taskID>/<runID>/<artifactID>`.

2. **Storage layer**
   - TaskStore: CreateTask creates Task + first TaskRun (both in one transaction or two steps). GetTask, ListTasksByWorkspace unchanged in spirit; task’s status/output etc. come from last run.
   - New TaskRunStore (or extended TaskStore): CreateTaskRun(taskID, input, createdBy), GetNextPendingTaskRun(), GetTaskRun(ctx, runID), UpdateTaskRunStatus(…), UpdateTaskRunWorkerInfo(…), and way to get “last run” for a task (e.g. GetTaskLastRun(taskID) or task.last_run_id).
   - ArtifactStore: CreateArtifactWithItem(ctx, taskID, taskRunID, artifactID, seq, relativePath); list/filter by task_id and optionally task_run_id. Artifact table: task_run_id not null (after migration).

3. **Server API**
   - POST `/api/workspaces/{id}/tasks`: body `{ "input", "project_id"? }`. Creates Task + first TaskRun (input = body.input, status PENDING). Returns task (with status from run or “PENDING”).
   - POST `/api/workspaces/{id}/tasks/{task_id}/runs`: body `{ "input" }`. Creates new TaskRun (PENDING) only if no run for that task is PENDING/SCHEDULED/RUNNING; otherwise 409 Conflict. Returns run or task with run id.
   - GET `/api/worker/task-runs/{run_id}` (or similar): returns run (input, task_id, …) and task (workspace_id, project_id, session_id). Worker invoked with `--task-run-id <run_id>` only.
   - PATCH `/api/worker/task-runs/{run_id}`: update run status, output, session_id (when run starts), artifact, worker_type, k8s_*. On run completion, update task.session_id if this run set it and task’s denormalized last-run fields.
   - GET list tasks / get task: response includes status, output, started_at, ended_at from last run (or null if no run). Conversation endpoint unchanged (task-scoped session).

4. **Executor**
   - Scheduler: poll GetNextPendingTaskRun(); claim (PENDING→SCHEDULED) by run_id; spawn worker with `--task-run-id <run_id>` only; on spawn success, persist worker info on the run.
   - Worker binary: accept `--task-run-id`; GET worker API by run_id returns run + task; runtime buildmax dir is `…/tasks/<taskID>/<runID>/buildmax/`. If task has session_id, copy session file from previous run’s persist path (`…/tasks/<taskID>/<prev_run_id>/buildmax/sessions/<id>.json`) into current run’s buildmax dir; run buildmax -p <run.input> --session-id <task.session_id or new>; PATCH run and task on completion; upload this run’s buildmax to `…/tasks/<taskID>/<runID>/buildmax/`.
   - RunTask(ctx, task, run, sessionID, paths, persist, artifactStorage, updater): paths expose run-scoped buildmax dir; materialize workspace; optionally restore session into run’s buildmax dir; run buildmax; upload run’s buildmax; write result; register artifact under `artifacts/<taskID>/<runID>/<artifactID>`.

5. **Blob / persist storage**
   - Task buildmax (per run): `…/workspaces/<ws>/tasks/<taskID>/<runID>/buildmax/` (sessions, logs, settings). Each run writes and reads only its own run dir; for continuation, worker copies session from a previous run’s buildmax into current run’s buildmax before invoking buildmax.
   - Artifact: `…/workspaces/<ws>/artifacts/<taskID>/<runID>/<artifactID>/` (e.g. result.md). Artifact table has task_run_id.

6. **Portal**
   - Task detail: “Follow-up” section with text input and “Send”. Submit → POST `.../tasks/{id}/runs` with { input }. Then poll until the new run is SUCCEEDED or FAILED; then refresh task and conversation.

7. **Migration**
   - No migration of existing data. Add task_run table and task_run_id on artifact; task keeps denormalized last-run columns. User will truncate tables.

## Implementation path (suggested order)

1. **Model and DB**: Add TaskRun type and table; add task_run_id to Artifact; add last_run_id (or equivalent) and keep task.status as “last run status” denormalized; No backfill; truncate acceptable.
2. **TaskRun store**: CreateTaskRun, GetNextPendingTaskRun, GetTaskRun, UpdateRunStatus, UpdateRunWorkerInfo, set task denormalized fields on run completion. CreateTaskRun rejects if task has a run in progress.
3. **Config/paths**: Runtime and persist paths include run_id: `…/tasks/<taskID>/<runID>/buildmax/`; artifact path `artifacts/<taskID>/<runID>/<artifactID>`.
4. **Server – user API**: POST tasks creates task + first run; POST tasks/{id}/runs creates run (409 if run in progress); GET task/list return denormalized last-run state.
5. **Server – worker API**: GET/PATCH by run_id only (e.g. `/api/worker/task-runs/{run_id}`); response includes run + task; PATCH updates run and task.
6. **Executor**: Scheduler spawns worker with `--task-run-id`; worker fetches by run_id, uses run-scoped buildmax dir, restores session from previous run's buildmax if needed, RunTask(run-scoped), uploads run's buildmax.
7. **Portal**: Follow-up input, POST runs, poll until SUCCEEDED/FAILED then refresh.
8. **Cleanup**: OpenAPI/docs; conversation endpoint may read session from latest run (design doc to specify).

## Acceptance criteria

- [ ] Creating a task creates one Task and one TaskRun (PENDING). Scheduler picks up the run; worker runs with `--task-run-id`; task shows SUCCEEDED/FAILED and conversation after run. Buildmax content is stored under `…/tasks/<taskID>/<runID>/buildmax/`.
- [ ] User can submit a follow-up in the Portal; POST runs creates a new TaskRun (409 if any run is PENDING/SCHEDULED/RUNNING). After new run completes, conversation continues in the same session.
- [ ] Portal polls until the new run is SUCCEEDED or FAILED, then refreshes task and conversation.
- [ ] Worker accepts only `--task-run-id`; GET worker API by run_id returns run + task; for follow-up, session is restored from a previous run’s buildmax into current run’s buildmax; buildmax is invoked with task.session_id so the agent continues the thread.
- [ ] Task denormalized fields reflect the last run; artifacts live under `artifacts/<taskID>/<runID>/<artifactID>` and are listed by task/run.
- [ ] No migration of existing data; tables can be truncated.
- [ ] Build and tests pass; manual smoke: create task → follow-up → see continued conversation and new result.
