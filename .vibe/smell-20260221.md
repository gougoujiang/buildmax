# Smell Proposal — Portal (2026-02-21)

## Scope

**Analyzed**

- Paths: `portal/` (React + Vite frontend)
- Focus: (1) unused files, (2) layout vs router structure (AppShell as layout), (3) component and page names vs user/design concepts

## Summary

- **Proposals**: 6
- **High priority**: 2
- **Overview**: The portal has dead code (mock data layer; unreachable Projects/Project pages). **Project concept is being removed** — delete those pages and project from context/API surface. Layout and routing are mixed in `App.tsx` and `WorkspaceRouter`; several names (pages, components, CSS) diverge from user-facing terms (e.g. "Chat" vs "Task", "project" CSS for chat cards).

### Decisions (reviewed)

| # | Decision |
|---|----------|
| 1 | **Mock data**: Option A — delete `portal/src/data/` entirely. |
| 2 | **Project backend**: Backend is not changed yet; on the portal, do **not** rely on project backend APIs (remove project from portal even though backend still has project). |
| 3 | **User-facing labels**: Use **Chat**, **Chats**, **Home**, **Files** (task detail = Chat, activity list = Chats, workspace home = Home, explore = Files). |
| 4 | **Layout**: Use **`src/layout/Layout.tsx`** as the workspace layout entry (dir name lowercased to align with others). |

## Proposals

### 1. Remove or gate unused mock data layer

**Location**: `portal/src/data/` — `index.ts`, `mockData.ts`, `mockActivity.ts`

**Current state**

- The app uses the real API (`lib/api`) for workspaces, tasks, artifacts. No file in `src` imports from `./data` or `../data`.
- `data/index.ts` re-exports mock helpers and `MOCK_ACTIVITY`; `mockData.ts` and `mockActivity.ts` implement them. This entire folder is dead code and adds maintenance and confusion.

**Proposed change**

- **Chosen: Option A** — Delete `portal/src/data/` and any references (none in app code; only internal to `data/`).

**Benefit**: Less dead code, single source of truth for data (API), clearer onboarding.

**Priority**: High

---

### 2. Remove Projects and Project pages (project concept removed)

**Location**: `portal/src/pages/Projects.tsx`, `portal/src/pages/Project.tsx`; `portal/src/hooks/useWorkspaceData.ts`, `portal/src/contexts/WorkspaceContext.tsx`; `portal/src/components/CreateProjectModal.tsx`; project-related API and types used only for projects

**Current state**

- **Project concept is being removed** from the product. `WorkspaceRouter` does not render Projects or Project; those pages are unreachable. `useWorkspaceData` and `WorkspaceContext` still expose `projects` and `refetchProjects`. CreateProjectModal, useProjects, and project API calls exist but are only used by the removed pages (or not at all in the app).

**Proposed change**

- Remove project-centric UI and surface: delete `Projects.tsx`, `Project.tsx`, `CreateProjectModal.tsx`.
- Remove project from workspace context and data hook: drop `projects` and `refetchProjects` from `useWorkspaceData` and `WorkspaceContext`. Remove `useProjects` usage (and the hook itself if nothing else uses it).
- **Do not rely on project backend APIs in the portal**: Remove or stop using `createProject`, `getProjects`, and project-specific task creation (e.g. `project_id`) in the portal. Backend may still expose project APIs; portal should not call or depend on them.
- Clean up: `lib/workspace.ts` has `getProjectById` / `getProjectName` — remove if unused after the above; same for project types in `lib/types.ts` if not used elsewhere.

**Benefit**: Aligns portal with decision to remove project concept; less dead code and no misleading project surface in UI or context.

**Priority**: High

---

### 3. Extract layout and router into a clear structure

**Location**: `portal/src/App.tsx`, `portal/src/components/AppShell.tsx`, `portal/src/components/WorkspaceRouter.tsx`, `portal/src/lib/router.ts`

**Current state**

- **Layout** is effectively `AppShell` (TopBar + LeftSidebar + main area with Breadcrumbs + children), but `App.tsx` also owns: auth gate, workspace redirect, modals (CreateWorkspace, ArtifactContent), and the decision to render `<AppShell><WorkspaceRouter /></AppShell>`. So "layout" is split between App (shell wrapper + modals) and AppShell (chrome).
- **Router** is hash-based in `lib/router.ts` (parseHash, buildHash, navigate, Route type) and **component routing** lives in `WorkspaceRouter` (big if/route.name switch). Route-to-component mapping is hard-coded inside WorkspaceRouter; there is no single "routes config" that lists route name → component.

**Proposed change**

- **Layout**: Use **`src/layout/Layout.tsx`** as the single workspace layout entry. Move all workspace chrome (TopBar, LeftSidebar, Breadcrumbs, main slot) there (from current AppShell). Have `App.tsx` only: auth, redirect, choose layout vs auth screens, and mount modals at the app root. So: "layout" = one place that wraps content; "App" = auth + layout choice + global modals.
- **Router**: Extract a **route → component map** (e.g. `src/routes.tsx` or `src/config/routes.ts`) so that adding a page is one line (route name + component). `WorkspaceRouter` becomes a thin wrapper that reads current route and renders `routeMap[route.name]` (or a small switch over that map). Optionally co-locate route constants (e.g. segment names) with this map.

**Benefit**: Clear separation of layout vs routing; easier to add/remove pages and to test or reuse layout; App.tsx stays minimal.

**Priority**: Medium

### 4. Align page and route names with user-facing concepts

**Location**: `portal/src/pages/` (names), `portal/src/lib/router.ts` and `portal/src/lib/types.ts` (Route), `portal/src/components/Breadcrumbs.tsx` and `portal/src/components/LeftSidebar.tsx` (labels)

**Current state**

- With project concept removed, model is **Workspace** → **Task** (single run / chat). User sees "Activity timeline", "restore"; sidebar uses "Chats" and "New Chat" (user concept = chat).
- Current naming: **TaskDetail** = one task/run (user: one "chat"); **Activity** = list of tasks (user: "chats" or "activity"); **WorkspaceHome** = workspace landing (user: "Home"); **NewChat** = new chat (aligned). **Explore** = files in workspace (user could read "Files"); **Agents** / **AgentList** = agents (aligned). Breadcrumbs use "Activity", "Explore", "Task", "Home" — "Task" is technical; user thinks "Chat".
- Inconsistency: Sidebar says "Chats" and "New Chat"; Breadcrumbs say "Task" for the open chat and "Activity" for the list. So user concept "Chat" is not reflected in page/route labels everywhere.

**Proposed change**

- **Chosen labels**: **Chat**, **Chats**, **Home**, **Files**. Apply consistently in breadcrumbs, sidebar, and page titles. Keep Route type and URL segment names as-is if needed for URLs; align UI labels and consider renaming page/component files for consistency:
  - **TaskDetail** → breadcrumb and user label **"Chat"**; page/component name Chat or ChatDetail.
  - **Activity** → breadcrumb and user label **"Chats"**; page/component name ChatList or keep Activity.
  - **WorkspaceHome** → user label **"Home"** (already in breadcrumbs); page/component can stay WorkspaceHome or be renamed Home.
  - **Explore** → user label **"Files"**; page/component can stay Explore or be renamed Files.
- Document in a short glossary: Route/type name (e.g. `task`) vs user label ("Chat") and when each is used (URL vs UI).

**Benefit**: Consistent mental model for users and developers; UI copy matches design doc and sidebar.

**Priority**: Medium

---

### 5. Fix WorkspaceHome CSS class names (project vs chat)

**Location**: `portal/src/pages/WorkspaceHome.tsx` (and possibly `portal/src/index.css` under "Page: Project Dashboard")

**Current state**

- WorkspaceHome shows "Recent chats" and "Recent artifacts". The list items are tasks (chats), but the CSS classes are `page-workspace__projects`, `page-workspace__project-card`, `page-workspace__project-link`, `page-workspace__project-name`, etc. With project concept removed, "project" in the DOM/CSS is misleading — it refers to chat cards only.

**Proposed change**

- Rename classes to chat-oriented names, e.g. `page-workspace__chats`, `page-workspace__chat-card`, `page-workspace__chat-link`, `page-workspace__chat-name`, and update `index.css` accordingly. If a "Project Dashboard" section in CSS is for this workspace home, rename it to "Workspace Home" or "Chat list".

**Benefit**: UI (Chat = task run) and CSS (chat for chat list) align; no leftover "project" naming now that the project concept is removed.

**Priority**: Medium

---

### 6. Clarify ExploreTree export (TreePanel vs ExploreTree)

**Location**: `portal/src/components/ExploreTree.tsx`

**Current state**

- File is named `ExploreTree.tsx` but the only exported component is `TreePanel`. Callers (e.g. `Explore.tsx`) import `TreePanel` from `ExploreTree`. So the file name suggests "ExploreTree" but the public API is "TreePanel" (generic). This is a minor naming inconsistency.

**Proposed change**

- Either: (1) Export a wrapper named `ExploreTree` that composes `TreePanel` (and use `ExploreTree` in Explore), or (2) Rename the file to `TreePanel.tsx` (or `FileTreePanel.tsx`) and update imports. Option (2) matches the current usage and keeps one component per file.

**Benefit**: File name and main export align; clearer for future "tree" components (e.g. a second tree elsewhere).

**Priority**: Low

## Suggested order

1. **Remove or gate unused mock data (1)** — no dependency; reduces noise and clarifies data source.
2. **Remove Projects/Project and project from app (2)** — do early; removes project concept from portal UI and context before layout/route refactors.
3. **Extract layout and router (3)** — improves structure; route config stays simpler without project routes.
4. **Align page/route names with user concepts (4)** and **Fix WorkspaceHome CSS (5)** — can be done together (both naming/UX); order between 4 and 5 is flexible.
5. **ExploreTree / TreePanel naming (6)** — optional cleanup after the above.

## Out of scope

- Full redesign of navigation (e.g. adding Explore/Activity to sidebar) — left as product/UX follow-up; smell doc only calls out naming and structure.
- Backend or API changes — scope limited to portal frontend; backend may still expose project until it is removed there.
- Test or storybook setup for mocks — mentioned in (1) as optional reason to keep `data/` gated.
