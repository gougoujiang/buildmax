# Task 050: Portal URL solution

## Goal

Define the portal’s URL scheme in one place, document it for users and developers, and keep the existing hash-based routing as the single source of truth with small, clear improvements where needed.

## Background

The portal already uses **hash-based routing** so the SPA works without server path fallback:

- **Router**: `portal/src/lib/router.ts` — `parseHash`, `buildHash`, `navigate`, `useHashRoute`.
- **Route type**: Discriminated union in `portal/src/lib/types.ts`: `workspace`, `project`, `task`, `artifact`, `activity`, `explore`.
- **URL shape**: `#<workspaceId>`, `#<workspaceId>/project/<id>`, `#<workspaceId>/task/<projectId>/<taskId>`, `#<workspaceId>/artifact/<projectId>/<artifactId>`, `#<workspaceId>/activity`, `#<workspaceId>/explore`.

Navigation and redirects use `navigate(route)` and `useHashRoute()`; `App.tsx` redirects when `workspaceId` is missing or invalid. The format is consistent but not documented as a single “URL scheme,” and segment names (`project`, `task`, `artifact`, `activity`, `explore`) are string literals in both `router.ts` and `LeftSidebar` (sidebar only uses workspace/activity/explore). This task clarifies the contract and improves maintainability without changing behavior for users.

## In Scope

1. **Document the URL scheme** — Add a short “URL scheme” section (e.g. in `portal/README.md` or a dedicated `portal/docs/url-scheme.md`) that describes:
   - Base: hash-only (e.g. `#` or `#<workspaceId>`).
   - All route patterns with examples: workspace home, project, task, artifact, activity, explore.
   - Rule: first segment is always `workspaceId`; then optional `/project/<id>`, `/task/<p>/<t>`, `/artifact/<p>/<a>`, `/activity`, `/explore`.
   - Note that IDs are opaque (e.g. short base62 from task 049).

2. **Keep hash-based routing** — No switch to path-based URLs; no server or Vite config changes for SPA fallback. Hash routing remains the only mechanism.

3. **Single source of truth for segment names** — Introduce a small set of constants (e.g. in `router.ts` or `types.ts`) for the path segment strings (`"project"`, `"task"`, `"artifact"`, `"activity"`, `"explore"`) and use them in `parseHash` and `buildHash` so that adding or renaming a route segment happens in one place.

4. **Behavior and tests** — Ensure existing behavior is unchanged: invalid or empty hash still yields a workspace route (with empty or invalid `workspaceId`); App continues to redirect when workspace is missing or not in list. Optionally add a few unit tests for `parseHash` / `buildHash` (round-trip and edge cases) if the project already has portal tests; otherwise document the contract in the URL-scheme doc.

## Out of Scope

- **Path-based routing** — No `/w/:workspaceId/...` or React Router path routes; would require server or Vite history fallback and is a larger change.
- **Query parameters** — No `?tab=...` or `?panel=...` for UI state in this task.
- **Server-side rendering or SEO** — Not in scope.
- **Changing the Route type or adding new route names** — Only documenting and centralizing the current scheme.

## Acceptance Criteria

- [ ] URL scheme is documented (in `portal/README.md` or `portal/docs/url-scheme.md`) with all route patterns and examples.
- [ ] Path segment names used in hash parsing and building are defined as constants and used in both `parseHash` and `buildHash`.
- [ ] No change to user-visible behavior: same hash formats, same redirect and navigation behavior.
- [ ] `go build ./...` and portal build (`cd portal && npm run build`) succeed.
- [ ] If portal has existing tests, add or extend tests for `parseHash`/`buildHash` round-trip and edge cases; otherwise acceptance is satisfied by the written URL-scheme doc and constants.
