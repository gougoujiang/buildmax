# Smell Proposal - internal/cmd/root.go

## Scope

**Analyzed**

- Paths / packages: `internal/cmd/root.go` (309 lines)
- Criteria: User-requested smell review after refactoring root command into `internal/cmd`

## Summary

- **Proposals**: 5
- **High priority**: 2
- **Overview**: `root.go` carries too many responsibilities — root command definition, tool construction, agent-type wiring, agent+session setup, and two distinct run modes (TUI and prompt). Splitting by concern will improve readability, make each piece independently testable, and keep files short as more tools and subcommands are added.

---

## Proposals

### 1. Extract tool construction into `setup.go`

**Location**: `internal/cmd/root.go` — `setupResult`, `buildBaseTools`, `buildAgentTypes`, `setupAgentAndSession` (lines 89–262)

**Current state**

- These four symbols (~170 lines) handle config loading, tool construction, agent-type wiring, sessions directory creation, and session loading.
- This is setup/infrastructure plumbing, not command definition. It dominates the file and makes `root.go` hard to scan for command-level logic.
- The heavy import list (10 internal packages) is mostly driven by these functions, not by the root command itself.

**Proposed change**

- Move `setupResult`, `buildBaseTools`, `buildAgentTypes`, and `setupAgentAndSession` into a new file `internal/cmd/setup.go` (same package, no export changes needed).
- `root.go` shrinks to ~100 lines: command definition, flag handling, and the `runRoot` dispatcher.

**Benefit**: Readability — `root.go` becomes purely about the root command; setup logic is isolated and easier to test independently.

**Priority**: High

---

### 2. Extract `runPromptMode` into `prompt.go`

**Location**: `internal/cmd/root.go` — `runPromptMode` (lines 286–308)

**Current state**

- `runPromptMode` is a self-contained run mode: it calls `setupAgentAndSession`, runs the agent, persists the session, and prints the reply.
- It sits alongside the root command definition and TUI runner, mixing three different run paths in one file.

**Proposed change**

- Move `runPromptMode` into `internal/cmd/prompt.go`.
- This mirrors the pattern already established with `version.go` — one file per distinct run path / subcommand.

**Benefit**: Consistency with the one-file-per-subcommand convention; keeps `root.go` focused on routing.

**Priority**: Medium

---

### 3. Extract `runTUI` into `tui.go`

**Location**: `internal/cmd/root.go` — `runTUI` (lines 264–284)

**Current state**

- `runTUI` builds TUI options and launches the Bubble Tea program. It imports `internal/app`, `internal/tui`, and `bubbletea`.
- Like `runPromptMode`, it's a distinct execution path that happens to live in the root file.

**Proposed change**

- Move `runTUI` into `internal/cmd/tui.go`.
- After this and proposal #2, `root.go` only contains `NewRootCommand` and `runRoot` — pure command definition and dispatch.

**Benefit**: Each run mode is in its own file; `root.go` becomes a clean dispatcher. Adding a new mode (e.g. server, REPL) won't bloat the root file.

**Priority**: Medium

---

### 4. Repetitive tool-creation pattern in `buildBaseTools`

**Location**: `internal/cmd/root.go` — `buildBaseTools` (lines 100–144)

**Current state**

- Nine tools are created one by one, each with the same `if err != nil { return nil, nil, fmt.Errorf(...) }` pattern.
- Adding a new tool means copy-pasting the same 4-line block. This is boilerplate-heavy and error-prone.

**Proposed change**

- Introduce a small helper type or closure pattern that registers tools, e.g.:

```go
type toolBuilder struct {
    tools []agent.Tool
    byName map[string]agent.Tool
    err   error
}

func (b *toolBuilder) add(t agent.Tool, err error) {
    if b.err != nil { return }
    if err != nil { b.err = err; return }
    b.tools = append(b.tools, t)
    b.byName[t.Name()] = t
}
```

- Then `buildBaseTools` becomes a series of `b.add(tools.NewReadFile(cwd))` calls — one line per tool, one error check at the end.

**Benefit**: Reduces boilerplate; adding a new tool is one line instead of four. Less visual noise.

**Priority**: Low — the current code is correct and clear, just verbose. Tackle after the file splits.

---

### 5. Inline `--continue` resolution in `runRoot`

**Location**: `internal/cmd/root.go` — `runRoot` (lines 62–87), specifically lines 66–80

**Current state**

- The `--continue` flag logic (load session list, find last by creation time, set `resumeID`) is 14 lines embedded in the root command handler.
- If more flag-driven logic is added (e.g. `--list`, `--delete`), `runRoot` will grow and mix unrelated concerns.

**Proposed change**

- Extract the continue-resolution into a small helper, e.g. `resolveResumeID(resumeID string, cont bool) (string, error)`.
- `runRoot` becomes a clean three-step function: resolve flags → dispatch to prompt or TUI.

**Benefit**: Readability; `runRoot` stays short and each flag's logic is self-contained and testable.

**Priority**: Low — current size is manageable; becomes more valuable as flags grow.

---

## Suggested order

1. **Extract setup logic into `setup.go`** (Proposal 1) — biggest single improvement; reduces `root.go` by ~170 lines.
2. **Extract `runPromptMode` into `prompt.go`** (Proposal 2) and **`runTUI` into `tui.go`** (Proposal 3) — can be done together; completes the file split.
3. **Tool builder helper** (Proposal 4) — refactor within `setup.go` after the split.
4. **Extract `resolveResumeID`** (Proposal 5) — small cleanup, do whenever convenient.

## Out of scope

- **`buildAgentTypes` built-in vs user-defined split** — Considered splitting into two functions, but the user-defined merge is tightly coupled to the built-in map. Deferring unless the function grows further.
- **`setupAgentAndSession` decomposition** — Could split config/client creation from session loading, but the function is linear and reads well as-is. Revisit if it grows past ~60 lines.
