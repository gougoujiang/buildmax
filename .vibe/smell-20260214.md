# Smell Proposal — `cmd/buildmax/root.go`

## Scope

**Analyzed**

- Paths / packages: `cmd/buildmax/root.go` (297 lines) and its direct dependencies in `internal/`
- Criteria: All code in the file, focusing on function length, duplication, mixed concerns, and API design

## Summary

- **Proposals**: 5
- **High priority**: 2
- **Overview**: The file's central function `setupAgentAndSession` (143 lines) carries too many responsibilities and contains highly repetitive tool-construction boilerplate. Several secondary smells (duplicate config load, mixed error-handling strategy, wide return tuple) stem from the same root cause.

---

## Proposals

### 1. Extract tool registry construction into a dedicated function

**Location**: `cmd/buildmax/root.go` — `setupAgentAndSession`, lines 106–153

**Current state**

- Nine tool constructors are called sequentially, each with the identical pattern: call `tools.NewXxx(...)`, check `err`, `slog.Error(...)`, return `fmt.Errorf(...)`. This accounts for ~50 lines of nearly identical boilerplate.
- Adding a new tool requires copy-pasting the same 5-line block, which is error-prone and inflates the function.

**Proposed change**

- Create a helper function (e.g. `buildTools(client llm.Client, cwd string, skillPaths []string) ([]agent.Tool, map[string]agent.Tool, error)`) that constructs all base tools and returns the tool slice plus a name-lookup map.
- Inside the helper, consider a table-driven approach: define tool constructors in a slice of structs and iterate with a single error-handling block, or at minimum group them into a single function to isolate the concern.

**Benefit**: Readability — `setupAgentAndSession` shrinks dramatically. Adding a tool becomes a one-liner. Testability improves because tool construction can be tested in isolation.

**Priority**: High

---

### 2. Extract agent-type configuration into a dedicated function

**Location**: `cmd/buildmax/root.go` — `setupAgentAndSession`, lines 161–211

**Current state**

- After building tools, 50 lines are spent defining built-in agent types, loading user-defined agent definitions, resolving tool names, and merging them. This is a separate concern from tool creation and session management.
- The agent-type wiring logic uses both `baseTools` and `toolsByName`, coupling it tightly to the tool-creation block above.

**Proposed change**

- Extract into a function such as `buildAgentTypes(baseTools []agent.Tool, toolsByName map[string]agent.Tool, cwd string) (map[string]tools.AgentTypeConfig, error)`.
- This function owns the built-in type definitions and the user-defined agent loading/merging logic.

**Benefit**: Single responsibility — each function does one job. The agent-type logic can be tested independently (e.g. verifying that a conflicting user-defined name is skipped).

**Priority**: Medium

---

### 3. Eliminate duplicate `config.LoadLLM()` call

**Location**: `cmd/buildmax/root.go` — `runTUI`, line 247

**Current state**

- `setupAgentAndSession` calls `config.LoadLLM()` on line 96 to build the LLM client.
- `runTUI` calls `config.LoadLLM()` **again** on line 247, solely to extract `cfg.Model` for display in the TUI.
- Two separate loads of the same environment-backed config is wasteful and fragile — if env vars changed between calls (unlikely but possible), the TUI would show a different model than the one actually used.

**Proposed change**

- Return the `config.LLM` (or at least the model name string) from `setupAgentAndSession` so `runTUI` can use it directly.
- Alternatively, store the resolved config on the `Agent` struct so callers can query it.

**Benefit**: Consistency — the TUI always displays the same model the agent uses. Removes one unnecessary function call.

**Priority**: High

---

### 4. Remove `os.Exit(1)` inside `runRoot` — use consistent error propagation

**Location**: `cmd/buildmax/root.go` — `runRoot`, lines 79–83

**Current state**

- `runRoot` is a Cobra `RunE` handler that returns `error`. When `runPromptMode` fails, it calls `os.Exit(1)` on line 81 *and* returns `nil` on line 83 (the return is unreachable after exit, but the intent is unclear).
- Meanwhile, `runTUI` on line 86 returns the error normally.
- `main.go` already handles a non-nil error from `root.Execute()` by printing and calling `os.Exit(1)`.

**Proposed change**

- Remove the `os.Exit(1)` from `runRoot`. Simply return the error from `runPromptMode`, letting `main.go` handle the exit.
- This makes the error flow for prompt mode identical to the TUI path.

**Benefit**: Consistency — one error-handling strategy throughout. Easier to reason about and test.

**Priority**: Medium

---

### 5. Reduce `setupAgentAndSession` return arity (5 values)

**Location**: `cmd/buildmax/root.go` — `setupAgentAndSession`, line 95

**Current state**

- The function returns 5 values: `(a *agent.Agent, sess *session.Session, sessionsDir, cwd string, err error)`.
- `cwd` is fetched internally (line 100) but is also needed by callers for TUI display and session persistence. `sessionsDir` is derived from `config.DataDir()`. Returning both as raw strings makes the call site cluttered and the function's contract wide.

**Proposed change**

- Introduce a small result struct (e.g. `type setupResult struct { Agent *agent.Agent; Session *session.Session; SessionsDir string; CWD string; ModelName string }`).
- `setupAgentAndSession` returns `(setupResult, error)`.
- This also provides a natural place to carry the LLM model name (fixing proposal 3) without adding yet another return value.

**Benefit**: Readability — callers destructure a named struct instead of a positional 5-tuple. Extensibility — adding a new field doesn't change the function signature.

**Priority**: Low

---

## Suggested order

1. **Proposal 1** (Extract tool registry) — do first; it's the largest reduction in function length and the simplest refactor.
2. **Proposal 3** (Eliminate duplicate LoadLLM) — combine with proposal 5 since both touch the return values.
3. **Proposal 5** (Result struct) — do alongside proposal 3 for a clean result type.
4. **Proposal 2** (Extract agent-type config) — second phase; depends on proposal 1's `toolsByName` being available.
5. **Proposal 4** (Remove os.Exit) — independent, can be done anytime.

## Out of scope

- **Move `setupAgentAndSession` into `internal/`** — The function orchestrates several internal packages, and `cmd/` is the intended location for wiring. Moving it would blur the `cmd/` vs `internal/` boundary. Deferred unless the file continues to grow.
- **Tool constructor pattern change** — All tool constructors return `(*ConcreteType, error)` rather than `(agent.Tool, error)`. Changing the interface would be a wider refactor across `internal/tools/`; not in scope for this file-focused review.
- **Cobra flag handling** — `runRoot` silently ignores flag-parse errors with `_ =`. This is standard Cobra practice (flags are pre-validated) and not a smell.
