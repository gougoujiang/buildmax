## Proposals

### 1. Extract shared root-path constructor for file tools

**Location**: `internal/tools/readfile.go`, `writefile.go`, `editfile.go`, `grep.go`, `glob.go`, `bash.go` — `NewReadFile`, `NewWriteFile`, `NewEditFile`, `NewGrep`, `NewGlob`, `NewBash`

**Current state**

- Six tools (`ReadFile`, `WriteFile`, `EditFile`, `Grep`, `Glob`, `Bash`) each have a `root string` field and an identical constructor pattern:

  ```go
  func NewXxx(root string) (*Xxx, error) {
      if root == "" {
          root, err = os.Getwd()
      }
      abs, err := filepath.Abs(root)
      return &Xxx{root: filepath.Clean(abs)}, nil
  }
  ```

- The same 10–12 lines are copy-pasted six times with only the struct type changed.
- Adding a new file-rooted tool requires copying the pattern again, risking drift.

**Proposed change**

- Create a shared helper in a new file `internal/tools/rootpath.go`:

  ```go
  // resolveRoot normalizes and absolutizes root; defaults to os.Getwd() if empty.
  func resolveRoot(root string) (string, error) { ... }
  ```

- Each tool constructor calls `resolveRoot(root)` instead of duplicating the logic.
- Optionally, embed a small `rootBase` struct (`root string`) that tools can embed, but this is less important than the helper function.

**Benefit**: Eliminates ~60 lines of duplication across 6 files; single place to fix root-resolution bugs; faster to add new tools.

**Priority**: High

### 2. Extract shared path-resolution and boundary-check helper

**Location**: `internal/tools/readfile.go:86-114`, `writefile.go:87-107`, `editfile.go:121-156`, `grep.go:242-280`, `glob.go:144-186`

**Current state**

- Five tools repeat the same "resolve path under root" sequence:
  1. `filepath.Join(root, userPath)`
  2. `filepath.Abs(filepath.Clean(...))`
  3. `filepath.Rel(root, resolved)` to detect traversal
  4. Check `rel == ".." || strings.HasPrefix(rel, "..")`
  5. `os.Stat` with `IsNotExist` / `IsPermission` handling

- **Inconsistency**: `WriteFile` and `EditFile` add an extra Windows-safe check (`strings.HasPrefix(resolvedClean, cleanRoot+string(filepath.Separator))`), but `ReadFile` and `Grep` do not. This means `ReadFile` and `Grep` may have a path-traversal vulnerability on Windows that the other tools fixed.

**Proposed change**

- Create `resolvePath(root, userPath string) (resolved string, err error)` in `internal/tools/rootpath.go` that:
  1. Joins, cleans, absolutizes
  2. Checks `filepath.Rel` traversal **and** the Windows prefix check (from EditFile/WriteFile)
  3. Returns a clear error on traversal or resolution failure

- Each tool calls `resolvePath(t.root, filePath)` and then does its own `os.Stat` check (file vs dir varies by tool).

**Benefit**: Fixes the inconsistent Windows security check in `ReadFile` and `Grep`; removes ~80 lines of duplication; all tools get identical boundary enforcement.

**Priority**: High

### 3. Consolidate duplicated arg-parsing helpers

**Location**: `internal/tools/grep.go:670-722` (`parseString`, `parseBool`, `parseInt`), `internal/tools/readfile.go:146-157` (`toFloat`), `internal/tools/bash.go:141-152` (`toFloat64`), `internal/tools/glob.go:128-142` (`parsePattern`)

**Current state**

- `readfile.go` defines `toFloat(v any) (float64, bool)`.
- `bash.go` defines `toFloat64(v any) (float64, bool)` — identical logic, different name.
- `grep.go` defines `parseInt(args, key, default)` which internally does the same `float64`/`int`/`int64` type switch.
- `grep.go` defines generic `parseString`, `parseBool`, `parseInt` that would be useful in other tools, but they're file-private and only used by Grep.
- `glob.go` defines `parsePattern` which is nearly identical to `parseGrepPattern` in `grep.go` (both extract a required string arg named `"pattern"`).

**Proposed change**

- Create `internal/tools/argparse.go` with:
  - `parseStringArg(args map[string]any, key, defaultVal string) string`
  - `parseBoolArg(args map[string]any, key string, defaultVal bool) bool`
  - `parseIntArg(args map[string]any, key string, defaultVal int) int`
  - `parseRequiredString(args map[string]any, key string) (string, error)`
  - `toFloat64(v any) (float64, bool)` (the canonical version)
- Remove the duplicates from `readfile.go`, `bash.go`, `grep.go`, `glob.go`.

**Benefit**: Single source of truth for arg parsing; eliminates ~70 lines of duplication; consistent handling of JSON number types across all tools.

**Priority**: High

### 4. Replace custom `itoa` with `strconv.Itoa`

**Location**: `internal/tools/webfetch.go:251-263`

**Current state**

- `webfetch.go` defines a 13-line manual `itoa(n int) string` function that converts an integer to a string by extracting digits into a byte array.
- The Go standard library provides `strconv.Itoa(n)` which does exactly the same thing and is already imported in other tools (`readfile.go`, `bash.go`).

**Proposed change**

- Replace the call sites (`truncateContent`) to use `strconv.Itoa(n)`.
- Delete the custom `itoa` function.

**Benefit**: Removes dead-weight code; uses well-tested stdlib; `strconv` is already a dependency in other tool files in the same package.

**Priority**: Low

### 5. Split `grep.go` into tool + formatting + search

**Location**: `internal/tools/grep.go` (494 lines)

**Current state**

- `grep.go` is the largest source file (494 lines) and mixes four distinct concerns:
  1. Tool interface implementation (`Name`, `Description`, `Parameters`, `Execute`) — ~70 lines
  2. File collection logic (`collectFiles`, `matchesType`, `typeExtensions`) — ~80 lines
  3. Search logic (`searchFile`, `byteOffsetToLine`, `compilePattern`, `resolvePath`) — ~100 lines
  4. Output formatting (`formatContent`, `formatFilesWithMatches`, `formatCount`, `lineRange`, `mergeRanges`) — ~180 lines
  5. Arg-parsing helpers (`parseGrepPattern`, `parseString`, `parseBool`, `parseInt`) — ~60 lines (moves to `argparse.go` per Proposal 3)

**Proposed change**

- Extract output formatting into `internal/tools/grep_format.go` (formatContent, formatFilesWithMatches, formatCount, lineRange, mergeRanges).
- After Proposal 3, the arg-parsing helpers move to `argparse.go`.
- `grep.go` keeps the tool interface + search + file collection (~250 lines).

**Benefit**: Each file has a single concern; easier to read, review, and test formatting logic independently.

**Priority**: Medium

### 6. Bound the WebFetch cache

**Location**: `internal/tools/webfetch.go:42-47` (`cache map[string]cacheEntry`)

**Current state**

- `WebFetch.cache` is a `map[string]cacheEntry` that grows without limit.
- Entries have a TTL (checked on lookup), but expired entries are only removed when the same key is looked up again. URLs that are fetched once and never revisited remain in memory forever.
- In a long-running TUI session where the LLM fetches many different URLs, the cache can grow indefinitely.

**Proposed change**

- Add a `maxEntries` constant (e.g. 100).
- On cache store, if `len(cache) >= maxEntries`, evict the oldest expired entries first; if still over limit, evict the oldest entry by `expiresAt`.
- Alternatively, periodically sweep expired entries (e.g. on every store call, delete entries where `time.Now().After(expiresAt)`).

**Benefit**: Prevents unbounded memory growth in long sessions; simple to implement (sweep-on-store is ~10 lines).

**Priority**: Medium

### 7. `config.LoadSettings` silently swallows errors

**Location**: `internal/config/config.go:97-115`

**Current state**

- `LoadSettings` returns `Settings{}` (empty, no error) for:
  - File read errors (other than missing default file)
  - Invalid JSON
  - Any other unmarshalling failure
- Callers (`EffectiveLLMWithSelector`, `EffectiveLLM`) have no way to know if settings were actually loaded or if there was a configuration problem.
- A user who has a typo in `settings.json` will silently fall back to env-based config with no warning, making misconfiguration very hard to diagnose.

**Proposed change**

- Change `LoadSettings` signature to `LoadSettings(path string) (Settings, error)`.
- Return `(Settings{}, nil)` only for the "default path + file missing" case (auto-creation).
- Return the error for invalid JSON, unreadable files, or non-default missing paths.
- Update callers to handle (or at least log) the error.

**Benefit**: Configuration errors surface to the user instead of being silently ignored; easier to debug "wrong model" issues.

**Priority**: Medium

### 8. Inconsistent `"q"` quit binding in TUI

**Location**: `internal/tui/model.go:132-140` (`handleKeyMsg`)

**Current state**

- The TUI quits when the user presses bare `q` (a single rune), regardless of focus state or whether the input textarea is active:

  ```go
  case tea.KeyRunes:
      if len(msg.Runes) == 1 && msg.Runes[0] == 'q' {
          return m, tea.Quit
      }
  ```

- This check runs **before** the focus/scroll logic, so typing `q` in any context quits the app.
- However, looking more carefully, this is inside `handleKeyMsg` which has a `KeyCtrlC` check first, then this `KeyRunes` check. If the user is typing in the input box, the input captures the `q` before it reaches `handleKeyMsg`... unless focus is on the viewport. In viewport-focused mode, pressing `q` would quit instead of being a normal key. This is actually reasonable vim-like behavior, but it should be guarded to only fire when `!m.focusInput`.

**Proposed change**

- Move the `q`-to-quit binding inside the `!m.focusInput` block so it only fires when the viewport has focus (scroll mode), not when the input textarea has focus.

**Benefit**: Prevents accidental quit when typing in input; consistent with vim-like "q to quit in navigation mode" convention.

**Priority**: Low
