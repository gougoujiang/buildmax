# Smell Proposal — Portal (Re-run after folder reorg)

## Scope

**Analyzed**

- Paths: `portal/src/` — current layout with `lib/`, `data/`, `components/`, `pages/`
- Criteria: structure, duplication, dead code, naming, consistency

## Addressed since last run

- **Folder structure**: Types and router live in `lib/`; mock data in `data/`; Header, PromptArea, RecentActivity moved into `components/`. Root of `src/` now only has App, main, index.css, vite-env.d.ts.

## Summary

- **Proposals**: 9
- **High priority**: 2 (dead components, duplicated prompt UI)
- **Overview**: Same main findings as before: unused components (Header, PromptArea, RecentActivity), duplicated prompt UI in two pages, repetitive fallback logic in App, redundant Breadcrumbs ternary, repeated LeftSidebar buttons, misleading TaskDetail placeholders. One new low-priority item: optional barrel exports for cleaner imports.

---

## Proposals

### 1. Remove or adopt dead components (Header, PromptArea, RecentActivity)

**Location**: `portal/src/components/Header.tsx`, `portal/src/components/PromptArea.tsx`, `portal/src/components/RecentActivity.tsx`

**Current state**

- These three components are never imported anywhere. App uses AppShell/TopBar; WorkspaceHome and ProjectDashboard implement their own prompt UI. RecentActivity is unused.
- Dead code adds confusion and maintenance cost.

**Proposed change**

- **Option A**: Delete the three files if there is no near-term plan to use them.
- **Option B**: Adopt PromptArea in WorkspaceHome and ProjectDashboard (proposal 2), then remove Header and RecentActivity or document their intended use.

**Benefit**: Clearer codebase, no orphan files.

**Priority**: High

---

### 2. Use shared PromptArea to remove duplicated prompt UI

**Location**: `portal/src/pages/WorkspaceHome.tsx`, `portal/src/pages/ProjectDashboard.tsx`, `portal/src/components/PromptArea.tsx`

**Current state**

- WorkspaceHome and ProjectDashboard each render their own prompt section (heading, input, Run button) with the same CSS classes and the same handleRun no-op. PromptArea exists but is unused.

**Proposed change**

- Import and use PromptArea in both pages; pass value, onChange, onRun from local state. Add an optional `placeholder` prop to PromptArea so ProjectDashboard can use "Prepare February sales analysis" and WorkspaceHome "Help me prepare this month's sales analysis". Remove the duplicated inline prompt markup from both pages.

**Benefit**: Single place for prompt UI; easier to wire to real API later.

**Priority**: High

---

### 3. Extract fallback routing and reduce switch duplication in App

**Location**: `portal/src/App.tsx` — `renderPage()` and surrounding logic

**Current state**

- renderPage() is a large switch. For project, task, and artifact, the same fallback pattern repeats: if entity missing or workspace mismatch, render WorkspaceHome or ProjectDashboard with the same props — three nearly identical JSX blocks.

**Proposed change**

- Extract helpers or small components: e.g. getFallbackProject(route), and render helpers for WorkspaceHome and ProjectDashboard. In each case branch, compute entity + fallback once, then branch on "show entity page vs fallback" instead of repeating fallback JSX.

**Benefit**: Shorter, clearer App; single place for fallback behavior.

**Priority**: Medium

---

### 4. Simplify redundant ternary in Breadcrumbs

**Location**: `portal/src/components/Breadcrumbs.tsx` — lines 19–21

**Current state**

- `const projectId = route.name === "project" ? route.projectId : route.projectId` — both branches return `route.projectId`. Redundant.

**Proposed change**

- Use `const projectId = route.projectId` (in the branch where route is project/task/artifact, projectId exists).

**Benefit**: Readability; no behavior change.

**Priority**: Low

---

### 5. Reduce repetition in LeftSidebar nav items

**Location**: `portal/src/components/LeftSidebar.tsx`

**Current state**

- Three nearly identical button blocks (Projects, Activity, Explore), differing only in label, active flag, and target route.

**Proposed change**

- Define an array of nav config (label, route name, isActive derived from route.name) and map over it to render one button per item.

**Benefit**: Easier to add/change nav items; less duplication.

**Priority**: Low

---

### 6. Clarify or remove hardcoded placeholder content in TaskDetail

**Location**: `portal/src/pages/TaskDetail.tsx` — "What changed" and "Evidence / Data used" sections

**Current state**

- These sections show fixed bullet lists not derived from `task`. Users may think it is task-specific data.

**Proposed change**

- Remove these two sections until backend provides data, or show explicit placeholder text (e.g. "Not yet available") so the UI does not imply real content.

**Benefit**: Honest UI; no false expectations.

**Priority**: Medium

---

### 7. Consolidate activity-related types

**Location**: `portal/src/lib/types.ts`, `portal/src/data/mockActivity.ts`

**Current state**

- ActivityItem is defined in mockActivity.ts and used only by the unused RecentActivity. Other entity types live in lib/types.ts.

**Proposed change**

- Move ActivityItem to lib/types.ts so all domain types are in one place. Keep MOCK_ACTIVITY in data/mockActivity.ts. If RecentActivity is removed (proposal 1), do the type move when adding real activity support.

**Benefit**: Consistent type location; clearer boundary between types and mocks.

**Priority**: Low

---

### 8. Document data access before adding API layer

**Location**: `portal/src/App.tsx` and pages — use of listWorkspaces(), getProjectById, etc. from `./data/mockData`

**Current state**

- Mock data is called directly from App and Breadcrumbs during render. No abstraction layer; switching to async API will require refactor.

**Proposed change**

- Add a short note in portal/README.md or a comment in App: "Data is currently synchronous mock; when adding API, introduce a data layer (e.g. React Query + hooks) and have App/pages consume that instead of calling data/mockData directly." Optionally a thin re-export module (e.g. data/index.ts) so a future swap touches one place.

**Benefit**: Clear path for backend integration.

**Priority**: Low

---

### 9. (Optional) Add barrel exports for lib and data

**Location**: `portal/src/lib/`, `portal/src/data/`

**Current state**

- Consumers import from `./lib/router`, `./lib/types`, `./data/mockData`, `./data/mockActivity`. Multiple import lines when a file needs both router and types, or both mock modules.

**Proposed change**

- Add `lib/index.ts` re-exporting from router and types; add `data/index.ts` re-exporting from mockData and mockActivity. Then App can use `from "./lib"` and `from "./data"` if desired. Optional; current explicit paths are clear and acceptable.

**Benefit**: Slightly shorter imports; single entry for each layer. Risk: barrel files can encourage broad imports and slower tree-shaking if not careful.

**Priority**: Low
