# Task 088: New chat from an agent

Support starting or creating a new chat from an agent so that the conversation uses that agent’s persona (instructions) from the first run. This enables “select an agent and start a new chat” in the Portal and prepares for future use cases (e.g. scheduled runs with an agent).

## Goal

One sentence: **Allow users to create a new chat from a workspace agent so that the chat’s `input` is filled with the agent’s name, description, and instructions (so the LLM knows what task to do), and expose this flow in the Portal (e.g. from the agent list or agent detail page).**

## Context

- **Chats today**: Created via `POST /api/workspaces/{workspace_id}/chats` with body `{ "input": "…" }`. No agent association. First run is created in the same transaction; worker prepares run `AGENTS.md` from the materialized workspace only (run directory layout + optional workspace `AGENTS.md` from run home).
- **Agents**: Workspace-scoped entities (`internal/model` Agent, `AgentStore`). Fields: `agent_id`, `workspace_id`, `name`, `description`, `instructions`. Portal: `AgentList`, agent detail page (083); `getAgents`, `createAgent`, `getAgent`, etc. No current link between chat and agent.
- **Executor**: `WriteRunAgentsMd(runDir, runHome)` builds run `AGENTS.md` from `runHome` only; no change needed for this task.

## In scope

1. **Backend — Chat associated with an agent; input composed from agent**
  - Add optional `agent_id` to the Chat model (nullable; same workspace as chat). Migration or schema update as per project conventions.
  - `POST /api/workspaces/{workspace_id}/chats`: accept optional `agent_id` in the request body. If present, validate it exists and belongs to the same workspace; **when `agent_id` is present, the stored chat `input` is set to a combined string built from that agent’s attributes** so the LLM receives the task context via the first message. Format is agreed (e.g. `<name>: {agent name}\n<description>: {description}\n<instructions>: {instructions}` with optional user-provided text appended). If the client also sends `input`, it may be appended after this block. If only `agent_id` is sent (no `input`), the composed block alone is the chat input. No injection of agent content into run `AGENTS.md`; worker/executor unchanged.
  - Chat response (and list) includes `agent_id` when set (snake_case).
2. **Portal — Start new chat from an agent**
  - From the agent list or agent detail page: a clear action (e.g. “New chat” / “Start chat”) that creates a new chat with that agent. Call create chat with `agent_id` (and optionally user-supplied input to append); the backend fills the chat `input` from the agent’s name, description, and instructions so the LLM knows what task to do. Navigate to the new chat view.
  - New chat creation from the existing “New chat” entry point may optionally allow choosing an agent (e.g. dropdown or agent picker). At least one path must support “from agent list/detail” as above.
3. **API and types**
  - OpenAPI spec updated for `POST .../chats` (optional `agent_id`) and for chat response (optional `agent_id`). Portal API client and types updated to send and display `agent_id` where relevant.

## Out of scope

- **Cron / scheduled runs**: Running an agent on a schedule (e.g. “email-checker every day at 8:00”) is out of scope. This task only covers user-initiated “new chat from agent”; scheduling can be a follow-up.
- **General “input required” rule**: When `agent_id` is present, `input` may be optional (server composes from agent); when `agent_id` is absent, `input` remains required as today.
- **Editing agent on an existing chat**: Changing the agent for an existing chat is out of scope (chat’s `agent_id` is set at create time only for this task).
- **Follow-up runs and agent**: If chat has `agent_id`, follow-up runs (e.g. `POST .../chats/{id}/runs`) use the same agent; no separate “agent per run” in this task.

## Deliverables

- Chat model and storage: optional `agent_id` on Chat; migration if needed.
- `POST /api/workspaces/{workspace_id}/chats`: optional `agent_id`; when present, validate and persist, and set chat `input` to the composed string (agent name, description, instructions; optional user input appended). No worker/executor or AGENTS.md changes.
- Chat responses (create + list) include `agent_id` when set.
- Portal: “New chat” from agent list or agent detail; optional agent selection in general “New chat” flow.
- OpenAPI and Portal types/API client updated.

## Acceptance criteria

- [ ] Chat has optional `agent_id`; DB migration/schema applied; create and list APIs return it when set.
- [ ] Creating a chat with valid `agent_id` (same workspace) stores it and sets chat `input` to the composed string (agent name, description, instructions; optional user input appended); creating with invalid or missing `agent_id` behaves correctly (400 or success without agent).
- [ ] A run for a chat created from an agent receives the agent context via the chat’s `input` (first user message), not via AGENTS.md; no worker/executor changes.
- [ ] From the Portal, user can start a new chat from an agent (agent list or detail) and is taken to the new chat; the created chat has `agent_id` set and `input` contains the agent’s name, description, and instructions.
- [ ] OpenAPI and Portal types reflect optional `agent_id` on create and on chat response.
