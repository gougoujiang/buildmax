# Task 033: Workspace switch in portal

## Goal

Enable **workspace switching** in the portal so users can select one of multiple workspaces; the UI (sidebar, pages, top bar) reflects the selected workspace’s projects, tasks, and artifacts. All data remains **mock-only** (POC, no backend).

## Context

- **Portal today**: Task 032 added an app shell (TopBar, ProjectsSidebar, Breadcrumbs) and 4 pages. A single `MOCK_WORKSPACE` ("Sales Team") and flat mock arrays for projects/tasks/artifacts live in `portal/src/mockData.ts`. `App.tsx` uses `listProjectsForWorkspace(MOCK_WORKSPACE.id)` and passes `workspaceName` and `projects` into `AppShell`. The hash router has no workspace notion (`#workspace`, `#project/<id>`, etc.).
- **Design reference**: `design/001-about-portal.md` defines Workspace as the persistent context container; users see "Workspace: …" in the wireframe. Task 032 left the TopBar workspace area as a static label.
- **Constraint**: Frontend-only; no Go backend or API. Mock data must be structured so it can later be replaced by API calls from a single abstraction point.
- **User note**: Support multiple workspaces and switching; provide 3 workspaces for demo; each workspace has its own projects, activities, artifacts; centralize mock data for future API replacement.

## Workspace switch (this task)

For this task, "workspace switch" means:

1. **Multiple workspaces**: The app has 3 mock workspaces with distinct **UUID** ids and names. Each workspace has its own set of projects; tasks and artifacts belong to projects (and thus to a workspace).
2. **Current workspace**: One workspace is "current". The top bar shows its name; the sidebar lists its projects; all pages show data for that workspace. The current workspace is encoded in the URL (hash) so that switching is deep-linkable and back/forward work.
3. **Switcher UI**: The TopBar includes a workspace switcher (e.g. dropdown or select) that lists all workspaces. Choosing another workspace navigates to that workspace’s home and updates the view.
4. **Centralized mock**: All workspace-scoped mock data lives in one place (e.g. `mockData.ts`) with a clear surface: list workspaces, get workspace by id, and existing per-workspace lookups (projects/tasks/artifacts). No scattered single-workspace constants so that later we can swap this module for API calls.

We are **not** yet implementing:

- Backend/API integration, auth, or real persistence.
- Creating, editing, or deleting workspaces.
- Workspace-level settings or permissions.

## Deliverables

1. **Mock data (centralized)**
   - **Three workspaces**: Use **UUIDs** for workspace ids (e.g. `crypto.randomUUID()` or fixed UUID strings in mock data). Distinct names per workspace. Each has its own projects; projects have `workspaceId`. Tasks and artifacts stay keyed by `projectId`; no change to entity types beyond what’s needed for multiple workspaces.
   - **API surface**: `listWorkspaces(): Workspace[]`, `getWorkspaceById(id: string): Workspace | undefined`. Keep `listProjectsForWorkspace(workspaceId)`, `getProjectById`, and other existing helpers. All mock arrays and these functions live in one module (e.g. `mockData.ts`) so that a future "data layer" can replace this module with API calls.
   - **Content**: At least 2 projects per workspace with distinct names; tasks and artifacts spread across those projects so that switching workspaces visibly changes sidebar and page content.

2. **Route and router**
   - **Route type**: Extend `Route` so every variant includes `workspaceId: string`. Examples: `{ name: "workspace", workspaceId }`, `{ name: "project", workspaceId, projectId }`, etc.
   - **Hash format**: Include workspace (UUID) in the hash (e.g. `#<uuid>`, `#<uuid>/project/p1`, `#<uuid>/task/p1/t1`, `#<uuid>/artifact/p1/a1`) so that the current workspace is recoverable from the URL. Default when hash is empty or invalid: use the first workspace id from `listWorkspaces()`.
   - **Router**: Update `parseHash`, `buildHash`, and `navigate` to read/write `workspaceId`. Ensure `useHashRoute()` returns the extended `Route`.

3. **App and shell**
   - **App**: Resolve current workspace from `route.workspaceId` (validate against `getWorkspaceById`; if invalid, redirect to first workspace home). Pass current workspace, list of workspaces, and projects for current workspace into the shell. All page resolution and data loading use the current workspace from the route.
   - **AppShell**: Accept current workspace (or id + name), list of workspaces, and a way to navigate when workspace changes (e.g. callback or navigate with new workspaceId). Pass these to TopBar.
   - **TopBar**: Replace the static "Workspace: {name}" with a **workspace switcher** (dropdown or select) that shows the current workspace name and lists all workspaces; on select, navigate to `{ name: "workspace", workspaceId }` for the chosen workspace.
   - **Breadcrumbs / ProjectsSidebar**: When building routes for navigation (e.g. Home, project link), include the current `workspaceId` so that links stay within the same workspace.

4. **Styling**
   - Style the workspace switcher so it is clearly a control (e.g. dropdown or select) and fits the existing TopBar layout. No new dependencies; use existing CSS patterns.

## Out of scope (for later)

- Backend/API integration for workspaces or any entity.
- Workspace create/edit/delete UI or forms.
- Persisting selected workspace (e.g. localStorage); URL is the source of truth for this task.
- Unit tests or E2E tests (unless already present); manual verification is sufficient.

## Acceptance

- [ ] **Three mock workspaces** exist with **UUID** ids and distinct names; each has at least 2 projects; tasks and artifacts are spread across projects so that switching changes visible content.
- [ ] **Centralized mock**: `listWorkspaces()` and `getWorkspaceById(id)` are the entry points; all workspace-scoped data is in one module.
- [ ] **Route includes workspaceId**: Hash format supports `#<workspaceId>`, `#<workspaceId>/project/<id>`, etc.; invalid or missing workspace id redirects to first workspace home.
- [ ] **TopBar** shows a workspace switcher (dropdown or select) listing all workspaces; selecting one navigates to that workspace’s home and the whole UI (sidebar + main) shows that workspace’s data.
- [ ] **Deep link**: Opening a URL with a specific workspace id in the hash shows that workspace; breadcrumbs and sidebar project links preserve the current workspaceId in the hash.
- [ ] `npm run dev` and `npm run build` succeed in `portal/`; no new dependencies.
- [ ] Go build/tests remain unaffected (`go build ./...`, `go test ./...`).
