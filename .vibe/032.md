# Task 032: Portal layout

## Goal

Add a **multi-page Portal layout shell** (workspace switcher + projects sidebar + main content) and implement 4 scaffold pages (**Workspace Home**, **Project Dashboard**, **Task Detail**, **Artifact Viewer**) using **static/mock data only** (no backend).

## Context

- **Portal today**: `portal/` is a React + Vite + TypeScript app. It currently renders a single landing view composed from `Header`, `PromptArea`, and `RecentActivity` in `portal/src/`.
- **Design reference**: `design/001-about-portal.md` describes the product direction (agent-mediated, versioned workspace, Git/containers hidden from users).
- **Constraint**: This task must remain **frontend-only** (no Go backend, no API integration).
- **Dependencies**: Prefer **no new dependencies**. Keep navigation simple (e.g. local state or hash-based routing) instead of introducing React Router.

## Portal layout (this task)

For this task, "portal layout" means:

1. **App shell**: a stable frame with:
   - **Top bar**: app brand + workspace switcher (static) + settings/profile entry (visible, no functionality required).
   - **Left sidebar**: project list and basic project actions (mocked).
   - **Main area**: page content that changes based on the current view.
2. **4 pages with mock data**:
   - Workspace Home
   - Project Dashboard
   - Task Detail
   - Artifact Viewer
3. **Navigation between pages**:
   - Clicking a project in the sidebar opens its Project Dashboard.
   - Clicking a task/activity item opens Task Detail.
   - Clicking an artifact opens Artifact Viewer.
   - Provide a way to go "back" (e.g. breadcrumb or back button).

We are **not** yet implementing:

- Real workspace/project/task persistence, auth, permissions, or settings.
- Any backend/API calls, websockets, or agent execution.
- Real "Restore" behavior (only a disabled button / placeholder UI).
- File diffs, git concepts, containers, or technical implementation details in UI.

## Deliverables

1. **Portal page scaffolding (`portal/src/`)**
   - **Pages** (names are flexible, but keep responsibilities separated):
     - `WorkspaceHome` (or `pages/WorkspaceHome.tsx`): list projects + quick actions (mocked).
     - `ProjectDashboard` (or `pages/ProjectDashboard.tsx`): project overview + "Ask in this project" prompt + latest result placeholder + artifacts list + activity/task list.
     - `TaskDetail` (or `pages/TaskDetail.tsx`): result section + what changed + evidence + restore placeholder.
     - `ArtifactViewer` (or `pages/ArtifactViewer.tsx`): show one artifact (mock content).
   - **Keep all content mocked** (simple strings/arrays are fine).

2. **Reusable layout components**
   - **App shell** component that composes:
     - top bar
     - projects sidebar
     - main content slot
   - Sidebar supports:
     - list projects (mock)
     - highlight selected project
     - “+ New Project” button as no-op/placeholder

3. **Minimal navigation (no new deps)**
   - Implement a minimal router using one of:
     - hash routes (`#workspace`, `#project/<id>`, `#task/<id>`, `#artifact/<id>`), or
     - internal React state for the current view + selected ids.
   - Navigation must be deep-linkable if using hash routes (preferred), but full browser routing is not required.

4. **Mock data + types**
   - Add small TypeScript types and mock data for:
     - Workspace, Project, Task (activity), Artifact
   - Keep the "user language" surface: no Git/container terms in UI strings.

5. **Styling**
   - Extend `portal/src/index.css` to support:
     - app shell grid/flex layout (top + sidebar + main)
     - responsive behavior (e.g. sidebar collapses or stacks on narrow screens; can be minimal)
     - consistent typography and spacing with the existing landing styles

## Out of scope (for later)

- Backend/API integration (projects/tasks/artifacts from real sources).
- Real run flow, chat UI, session list, timeline restore implementation.
- Workspace/project creation forms and editing.
- Search, filters, tagging, sorting, pagination.
- Advanced responsive design and full accessibility audit (basic semantics only in this task).
- Tests/tooling additions (e.g. unit tests, Playwright) unless already present.

## Acceptance

- [ ] Portal renders an **app shell layout** with top bar + left projects sidebar + main content.
- [ ] Portal includes 4 pages: **Workspace Home**, **Project Dashboard**, **Task Detail**, **Artifact Viewer**, all using **mock data**.
- [ ] User can navigate between pages via clicks (project → dashboard, task → detail, artifact → viewer) and can return via a simple back/breadcrumb UI.
- [ ] UI copy does **not** expose Git/containers; restore is a placeholder only.

- [ ] `npm run dev` and `npm run build` succeed in `portal/`.

## Appendix: Reference IA + Wireframes (from initial notes)

These are reference-only for implementation (keep them as guidance; do not over-scope this task).

### Workspace / Project / Task model (user mental model)

- **Workspace**: long-lived context container (team/personal space).
- **Project**: an executable work unit under a workspace.
- **Task**: one intent → execution → output loop; shown as an activity card/timeline entry.

### MVP page list (layout focus)

1. Workspace Home (project list + quick actions)
2. Project Dashboard (prompt + latest result + artifacts + tasks)
3. Task Detail (result + what changed + evidence + restore placeholder)
4. Artifact Viewer (view one artifact)
