# Task 059: Entry cmd binary split (part 1)

## Goal

Ship a dedicated server binary so that the HTTP API server is a separate executable from the CLI, giving a clear responsibility boundary between “agent CLI/TUI” and “backend server.”

## Context

- **Current layout**: One binary from `cmd/buildmax/main.go`. Cobra root in `internal/cmd` registers subcommands `version` and `server`; default run is TUI or `-p` print mode. Build: `go build -o buildmax ./cmd/buildmax`.
- **Executor**: In `internal/executor`, task execution runs `exec.CommandContext(ctx, "buildmax", "-p", task.Input, ...)`. The executor expects the **CLI** binary named `buildmax` on PATH; it does not run the server.
- **Server**: `internal/cmd/server.go` defines `newServerCommand()` and `runServer()` (port, DB, workspace paths, blob storage, executor, `server.New(cfg)`). `./make run server` builds the single binary and runs `./buildmax server`.
- **Conventions**: AGENTS.md documents `cmd/buildmax` as the single entry point; config and env are in `internal/config`; logging in `internal/log`.

## “Binary split” (this task)

For this task:

1. **CLI binary** (`buildmax`): Built from `cmd/buildmax`. Provides TUI, `-p` print mode, and `version`. Does **not** include the server subcommand or link server/executor/entity/blob in the default build.
2. **Server binary** (`buildmax-server`): New entry point that runs the HTTP server and task executor. Built from a new `cmd/buildmax-server` (or equivalent). No Cobra; just flags/env for port and startup.
3. **Shared logic**: Server startup (DB, workspace paths, blob storage, executor, `server.New` + `Run`) lives in one place so the server binary calls it; the CLI root no longer registers or compiles server code.

We are **not** in this task:

- Changing how the executor invokes the agent (it continues to call `buildmax -p`).
- Adding a configurable path for the CLI binary in the executor.
- Splitting `version` into its own binary or changing CLI version behavior.
- Packaging or distribution (e.g. install scripts, multi-binary releases).

## Deliverables

1. **New server entry and package**
   - **`cmd/buildmax-server/main.go`**: New main that initializes log, parses port (flag and/or env via existing config), then runs the server startup logic. Binary name when built: `buildmax-server` (e.g. `go build -o buildmax-server ./cmd/buildmax-server`).
   - **Server startup moved out of `internal/cmd`**: Move the current server startup logic (workspace paths, DB, blob storage, executor, `server.New` + `Run`) into a callable unit that the new main uses. Prefer a new package (e.g. `internal/servercmd`) with a single entry such as `RunServer(ctx, port int) error`, so that `internal/cmd` no longer depends on server/executor/entity/blob for the default CLI. Remove the Cobra server subcommand from `internal/cmd` (delete or relocate `internal/cmd/server.go` so the CLI does not import it).

2. **CLI root**
   - **`internal/cmd/root.go`**: Remove `root.AddCommand(newServerCommand())`. Root continues to expose only TUI, `-p`, and `version` (and any existing flags). No imports that pull in `internal/server`, `internal/executor`, or storage in the CLI code path.

3. **Build and scripts**
   - **Makefile (`make`)**: Update so that `./make build` still builds the CLI binary `buildmax` from `cmd/buildmax`. Add a target (or extend `run server`) so that the server is built from `cmd/buildmax-server` and the server is started by running the `buildmax-server` binary (e.g. `./make run server` builds and runs `buildmax-server`). Document in the script or comments that two binaries exist.
   - **AGENTS.md**: Update the “Build & Test” and “Project Directory Structure” sections to describe both `cmd/buildmax` (CLI) and `cmd/buildmax-server` (server), and that `buildmax server` is replaced by running the `buildmax-server` binary.

4. **Tests**
   - **Server startup**: Add or adjust tests so that the new server entry (or `RunServer` / `internal/servercmd`) can be tested without building the CLI (e.g. unit test that startup logic runs or that port/config are applied). Existing `internal/cmd/server_test.go` should be moved or reimplemented as appropriate for the new package.
   - **CLI**: Ensure `go build ./cmd/buildmax` and `go test ./...` pass; no server code is required for the CLI build.

## Out of scope (for later)

- Making the executor’s path to the CLI binary configurable (e.g. env or config for “buildmax” path).
- Adding more binaries (e.g. separate “version” or other subcommands).
- Distribution or install targets that ship both binaries.

## Acceptance

- [ ] Two entry points exist: `cmd/buildmax` (CLI → `buildmax`) and `cmd/buildmax-server` (server → `buildmax-server`).
- [ ] The CLI binary has no server subcommand and does not import server/executor/entity/blob on the main code path.
- [ ] `./make build` produces the CLI binary; a documented make/script target builds and runs the server binary (e.g. `./make run server` runs `buildmax-server`).
- [ ] Executor still runs `buildmax -p ...` unchanged; no change to executor invocation or binary name.
- [ ] `go build ./cmd/buildmax` and `go build ./cmd/buildmax-server` both succeed; `go test ./...` passes.
- [ ] AGENTS.md describes the two-binaries layout and how to build/run each.
