# Task 003 - Application Data Folder Configuration

## Goal

Add configuration for the BuildMax **application data folder**: default location under the user's home directory (platform-aware), an optional environment override, and a local **testing-sandbox** directory used when running `make test` so tests do not touch the real user data dir.

## Context

- `internal/config` currently provides only LLM config (`LoadLLM()` from env). No data-dir or paths config exists yet.
- Application data will be used later for config files, cache, conversation history, etc.; this task establishes **where** that root lives.
- Project uses Go only; use `os.UserHomeDir()` for cross-platform home (Windows: `USERPROFILE`, macOS/Linux: `HOME`).
- There is no Makefile yet; tests are run via `go test`. This task introduces a Makefile with a `test` target that uses the testing-sandbox.

## Application data folder (this task)

For this task:

1. **Default**: The application data folder is `{UserHome}/.buildmax`, where `UserHome` is from `os.UserHomeDir()` (Windows and macOS/Linux are handled by the Go standard library).
2. **Override**: If the environment variable **`HOME_DIR`** is set (non-empty), it is used as the **full path** to the application data folder, replacing the default. No `.buildmax` suffix is appended when `HOME_DIR` is set.
3. **Testing**: A directory **`testing-sandbox`** in the **workspace root** (repository root) is the data dir used when running `make test`. The Makefile’s `test` target sets `HOME_DIR` to the absolute path of `./testing-sandbox` so all tests see that directory and do not touch `~/.buildmax`.

We are **not** in this task:

- Creating subdirectories inside the data folder (e.g. `config/`, `cache/`) or storing any files there.
- Adding TUI or agent logic that reads/writes the data dir; only the **resolution** of the path is in scope.

## Deliverables

1. **`internal/config`**
   - **DataDir resolution**: Add a function that returns the application data folder path (string). Logic:
     - If `os.Getenv("HOME_DIR")` is non-empty, return that value (after cleaning the path, e.g. `filepath.Clean`).
     - Otherwise return `filepath.Join(os.UserHomeDir(), ".buildmax")`.
   - **API**: Expose a single function is enough for now, e.g. `DataDir() (string, error)` if cleanup/creation is needed later, or `DataDir() string` that only resolves the path. Prefer `DataDir() string` for this task (no creation; callers will create dirs when needed).
   - **Tests**: Unit test that (1) with `HOME_DIR` unset, `DataDir()` returns a path ending in `.buildmax` and containing `UserHomeDir()`; (2) with `HOME_DIR` set (in test, use `t.Setenv`), `DataDir()` returns the set value (cleaned). Use a temporary dir for the set case to avoid affecting the host.

2. **Workspace: testing-sandbox**
   - **Directory**: Ensure a **`testing-sandbox`** directory exists at the repository root. It can be created by the Makefile when running `make test` (e.g. `mkdir -p testing-sandbox`) so it is not required to exist before the first run.
   - **Ignore**: Add **`testing-sandbox/`** to `.gitignore` so its contents are not committed.

3. **Makefile**
   - **New file**: Create a **`Makefile`** at the repository root.
   - **Target `test`**: Run `go test ./...` with `HOME_DIR` set to the **absolute path** of `./testing-sandbox` (e.g. on Unix `$(CURDIR)/testing-sandbox`, on Windows use a path that `go test` and the shell understand). Ensure the `testing-sandbox` directory exists before running tests (e.g. `mkdir -p testing-sandbox`).
   - **Portability**: Prefer a single Makefile that works on both Windows (e.g. where `make` is available) and Unix; if needed, document that `make test` is the canonical way to run tests with the sandbox. Optionally add a `test` target in `scripts/` for Windows-only users (out of scope unless trivial).

## Out of scope (for later)

- Creating subdirs or files inside the data folder; persistence; config file loading from the data dir.
- TUI or agent code that uses the data dir (they will call `config.DataDir()` in a follow-up).
- Changing LLM or other existing config to read from the data dir.
- Supporting a second env var (e.g. `BUILDMAX_DATA_DIR`) alongside `HOME_DIR`; one override is enough for this task.

## Acceptance

- [ ] `internal/config` has a function that returns the application data folder path: default `UserHomeDir()/.buildmax`, or `HOME_DIR` when set (path cleaned).
- [ ] Unit tests for `DataDir()`: (1) no `HOME_DIR` → path ends with `.buildmax` and contains `UserHomeDir()`; (2) `HOME_DIR` set (e.g. via `t.Setenv`) → returned path equals the set value (cleaned). No leftover env in other tests.
- [ ] Repository root has a `Makefile` with a `test` target that creates `testing-sandbox` if missing, sets `HOME_DIR` to its absolute path, and runs `go test ./...`.
- [ ] `testing-sandbox/` is listed in `.gitignore`.
- [ ] Running `make test` uses `testing-sandbox` as the data dir (e.g. verified by a test that checks `config.DataDir()` when `HOME_DIR` is set).
- [ ] Code follows project layout and AGENTS.md (Go only, no new runtime deps).
