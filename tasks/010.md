# Task 010: TUI wiring

## Goal

Wire the Bubble Tea TUI to the agent and session so users can run `buildmax` (or `buildmax --resume <id>`), see a chat layout with history and input, send messages, get assistant replies and tool-call lines in the UI, and have the session persisted.

## Context

- **Existing TUI**: `internal/tui/model.go` — minimal Bubble Tea model: Init, Update (quit on `q`/`ctrl+c`, WindowSizeMsg sets `ready`), View returns "BuildMax – AI Agent TUI" and quit hint. No session, agent, or input.
- **Entry**: `internal/app/app.go` — `NewModel()` returns `tui.NewModel()`. Root in `cmd/buildmax/root.go` runs TUI when no `-p`; `tea.NewProgram(app.NewModel(), tea.WithAltScreen())`. Today `--resume` is only used with `-p`; TUI does not accept `--resume` yet.
- **Session**: `internal/session` — `NewSession(title)`, `LoadFromDir(dir, sessionID)`, `SaveToDir(sess, dir)`, `sess.Append(msg)`, `sess.Messages()` (returns `[]llm.Message`). Session holds user/assistant/tool messages; ID, title, created_at.
- **Agent**: `internal/agent` — `NewAgent(caller, tools, opts)`, `Process(ctx, sess, userMessage) (reply string, err error)`. Process appends the user message, runs the loop (LLM → tool_calls → tools → LLM until done), appends assistant and tool messages to session, returns final text reply.
- **Config**: `internal/config` — `LoadLLM()` (APIKey, BaseURL, Model), `DataDir()`. Workspace = process cwd (for read_file root and footer).
- **Prompt mode** (reference): In `runPromptMode`, root creates LLM config, cwd, read_file tool, client, agent; creates or loads session by resumeID; calls `a.Process(ctx, sess, prompt)`; saves session to `DataDir()/sessions`; prints reply. Session is saved after each run.
- **Version**: `cmd/buildmax/main.go` — `var Version = "0.0.1"`; needed in TUI banner and can be passed from root to app/tui.
- **Conventions**: All-Go, Bubble Tea for TUI; persistence under `DataDir()/sessions`; snake_case for JSON; `make.bat test` with `HOME_DIR=./testing-sandbox`.

## TUI layout (this task)

For this task, "TUI wiring" means:

1. **Layout** (top to bottom): One scrollable content area (banner + chat history) → User input box (fixed above footer) → Footer (fixed at bottom). Only the input and footer are fixed; the banner and chat scroll together. When the user scrolls, the banner moves up with the chat messages. The banner is basic info for when a new session starts; it does not need to stay visible at all times.
2. **Banner**: Single line: `BUILDMAX` followed by version tag (e.g. `BUILDMAX 0.0.1`). Rendered at the top of the scrollable content (first thing the user sees), but when they scroll down it scrolls away with the chat.
3. **Chat history**: Rendered from current session messages. Format: `you: <content>` for user; `assistant: <content>` for assistant; for assistant messages that have tool_calls, next line(s) like ` * read_file (/path/args)` (tool name + a short args summary). Tool-only messages (role "tool") may be shown as a brief line (e.g. ` * result: ...`) or omitted for simplicity; at least assistant content and tool call lines must be visible.
4. **User input**: A text input or textarea at the bottom; submit (e.g. Enter) sends the text to the agent and clears the input. While the agent is running, show a loading/thinking state and do not send another message until the current one completes.
5. **Footer**: One line: `model: <model name> | <workspace path> | ctrl+c: quit` (and optionally other shortcuts). Model and workspace come from config and cwd passed into the TUI.
6. **Session**: If no `--resume`, create a new session when TUI starts; if `--resume <id>`, load session from `DataDir()/sessions/<id>.json` (exit or show error if not found). Persist session after each successful assistant reply (and optionally on quit if there are unsaved changes).

We are **not** yet implementing:

- Session list or session picker inside the TUI (e.g. "choose which session to open").
- Changing model or workspace from within the TUI.
- Rich formatting (e.g. markdown rendering) in the chat area; plain text is enough.

## Deliverables

1. **`cmd/buildmax/root.go`**
   - When starting TUI (no `-p`), allow `--resume <id>` for TUI mode: if `--resume` is set without `-p`, use it to load the session for the TUI; if not set, create a new session. (Remove or relax the current "resume requires -p" rule so that `buildmax --resume <id>` starts TUI with that session.)
   - Before starting the TUI: load LLM config (`config.LoadLLM()`), get cwd, create read_file tool (`tools.NewReadFile(cwd)`), create LLM client and agent (`llm.NewClient(cfg)`, `agent.NewAgent(client, tools)`), create or load session (new or `session.LoadFromDir(sessionsDir, resumeID)`). Pass into the TUI: agent, session, model name (`cfg.Model`), workspace path (cwd), version (`Version`), and sessions dir for saving.
   - Ensure sessions dir exists when loading/saving (e.g. `os.MkdirAll(sessionsDir, 0755)`).

2. **`internal/app`**
   - Extend `NewModel` (or add a constructor) to accept the dependencies the TUI needs: agent (e.g. `*agent.Agent`), session (e.g. `*session.Session`), model name, workspace path, version string, sessions directory path. Signature is for the implementer to choose (e.g. a struct or separate args). Return a `tea.Model` that uses these for display and for sending user messages to the agent.

3. **`internal/tui`**
   - **Model**: Hold references to agent, session, model name, workspace, version, sessions dir; state for viewport (scroll), input buffer, focus, and "busy" (agent running). Optionally use Bubble Tea components (e.g. viewport, textarea) from the Bubble Tea ecosystem where they fit.
   - **Init**: No async load required for session (already created/loaded by root). Return nil or a simple command.
   - **Update**: Handle `tea.KeyMsg`: e.g. `ctrl+c` (and optionally `q`) → quit; Enter in input → submit current line/buffer, trigger agent run (e.g. send a custom message that triggers `agent.Process` in an async command). Handle `tea.WindowSizeMsg` to resize viewport and keep input/footer at bottom. Handle a custom "user submitted text" message by calling `agent.Process(ctx, sess, text)` (in a tea.Cmd to avoid blocking), then on success append is already done by Process; add a "reply received" or "agent done" message to update UI and persist: `session.SaveToDir(sess, sessionsDir)`. On quit, optionally save session if there are new messages.
   - **View**: Render in order: (1) Scrollable area (viewport): first line is the banner `BUILDMAX <version>`, then for each message in `session.Messages()` render "you: ..." / "assistant: ..." and "* tool_name (args)" for tool calls; the whole viewport content (banner + chat) scrolls together so the banner is not fixed at top. (2) User input area (single line or multi-line). (3) Footer: `model: <model> | <workspace> | ctrl+c: quit`. Input and footer must stay fixed at the bottom.
   - **Formatting**: Add a small helper (e.g. `formatMessage` or `linesForMessage`) that, given a `llm.Message`, returns the display lines (e.g. "you: content" or "assistant: content" plus "* name (args)" for each tool call). Tool call args can be summarized (e.g. first argument or truncated JSON) for display; keep it short so the UI stays readable.
   - **Async agent run**: Use `tea.Cmd(func() tea.Msg { ... })` or similar to run `agent.Process` in the background and send a result message (reply + error) back to Update; in Update, on success update the model (session already updated by Process), save session, clear busy state; on error, show error in the chat or a status line and clear busy state.

4. **Tests**
   - Add at least one unit test for the chat display logic: e.g. given a list of `llm.Message` (user, assistant with tool_calls, tool), the formatted output contains expected "you:", "assistant:", and "* read_file (...)" lines. Prefer testing a pure function in `internal/tui` (e.g. in `model_test.go` or a small helper in a separate file) so tests do not require a real agent or session.
   - Optionally: a test that the TUI model initializes and renders the banner without crashing (e.g. `View()` returns a string containing "BUILDMAX").

5. **Documentation**
   - Update `AGENTS.md` (or README) to state that running `buildmax` starts the TUI; `buildmax --resume <id>` starts the TUI with that session loaded. Mention the layout (banner, chat, input, footer) and that the session is persisted after each reply.

## Out of scope (for later)

- Session list or session picker in the TUI (e.g. choose session from a menu).
- Config subcommand, Viper, or config-file binding.
- Additional tools (e.g. search, run commands).
- Shell completion.
- Markdown or rich formatting in the chat bubble content.

## Acceptance

- [ ] Running `buildmax` with no flags starts the TUI; the scrollable area shows a banner ("BUILDMAX" + version) followed by chat history (banner and chat scroll together); input and footer are fixed at the bottom; footer shows model name, workspace path, and "ctrl+c: quit".
- [ ] Running `buildmax --resume <id>` starts the TUI with the session loaded from `DataDir()/sessions/<id>.json`; if the file is missing, the program exits with a clear error (or shows it in the UI and exits).
- [ ] Without `--resume`, a new session is created when the TUI starts.
- [ ] Submitting a message (e.g. Enter) sends it to the agent; the assistant reply appears in the chat history; tool calls are shown as lines like ` * read_file (/path/to/file)`; the session is saved to disk after each successful reply.
- [ ] While the agent is processing, the UI shows a busy/loading state and does not accept another submit until the current one completes.
- [ ] Banner and chat history scroll together (user can scroll so the banner moves up and out of view); the input and footer remain fixed at the bottom; new messages appear at the bottom (newer messages flow down).
- [ ] Pressing ctrl+c (and optionally q) quits the TUI; the session is saved on exit if there are new messages since last save.
- [ ] At least one unit test exists for the message-formatting (chat line) logic and passes with `make.bat test`.
