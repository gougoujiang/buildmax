# Task 007 - Chat session (in-memory)

## Goal

Introduce an in-memory **chat session** that holds conversation history (user, assistant, tool messages) and integrate it with the agent run loop so that multi-turn chats use and update the same session, with messages appended during each turn and LLM calls made over the full history.

## Context

- **`internal/agent`**: `Process(ctx, userMessage)` builds a fresh `[]llm.Message` (system + user) each call, runs the agent loop (LLM → tool calls → append assistant/tool messages locally), and returns the final reply. There is no notion of a persistent conversation across turns.
- **`internal/llm`**: `Message` already supports roles `"user"`, `"assistant"`, `"system"`, and `"tool"`, with `Content`, `ToolCallID`, and `ToolCalls` (see `types.go`). The agent uses these for `ChatWithTools`.
- **AGENTS.md**: Core capabilities include "Conversation and history: multi-turn dialogue, context management, optional persistence." This task covers in-memory context only.
- Task docs live in **`tasks/`**; build/test: `./make build`, `./make test`. All-Go stack; no new external runtime dependencies.

## Chat session (this task)

For this task:

1. **Session** = an in-memory container with: **id** (a UUID generated at creation), **title**, **created_at** (timestamp when the session was created), and **chat history** (a sequence of `llm.Message` values: user, assistant, tool only—no system message stored in the session).
2. **Multi-turn chat** = the caller invokes the agent once per user turn, passing the same session; the agent appends the new user message and all resulting assistant/tool messages to the session and uses the full session history (plus a prepended system message) for each LLM call.
3. **In-memory** = session state lives only in process memory; no file or DB persistence in this task.

We are **not** yet implementing:

- Persistence (save/load sessions to disk or DB).
- A session manager or store (e.g. list sessions, get by id from a registry); a single session created and used by the caller is sufficient.
- TUI wiring (e.g. session list, session selector); that can consume this API in a follow-up.
- Auto-generating session title from the first user message.

## Deliverables

1. **`internal/session` (new package)**
   - **`Session` struct**: Holds `id` (UUID string), `title`, `created_at` (creation timestamp), and a slice of `llm.Message` (conversation history). Export fields or provide getters as needed; internal storage is not exposed for direct mutation.
   - **`NewSession(title string) *Session`**: Constructs a new session with a **new UUID** for id (e.g. via `github.com/google/uuid`), the given title, **created_at** set to the current time (e.g. `time.Now()`), and empty history. Title may be empty; no validation required beyond storing it.
   - **`Append(msg llm.Message)`**: Appends one message to the session’s history. Caller must ensure roles are user/assistant/tool (system is not stored in session).
   - **`Messages() []llm.Message`**: Returns a **copy** of the current conversation history (so callers cannot mutate session state, and the agent can safely append during the loop and call `Messages()` again for the next LLM call).
   - **`ID() string`**, **`Title() string`**, **`CreatedAt() time.Time`**: Return the session’s id (UUID), title, and creation timestamp. Optionally **`SetTitle(title string)`** to update the title (e.g. for future use).
   - No dependency on `internal/agent`; `internal/session` may depend on `internal/llm` for `llm.Message` and a UUID library (e.g. `github.com/google/uuid`) for id generation.

2. **`internal/agent`**
   - **`ProcessWithSession(ctx context.Context, session *session.Session, userMessage string) (reply string, err error)`**:  
     - Appends a user message `{Role: "user", Content: userMessage}` to `session`.  
     - Builds `messages` as: system message (using `DefaultSystemPrompt`) + `session.Messages()`.  
     - Runs the same agent loop as `Process`: for each iteration, call `ChatWithTools(ctx, messages, a.toolDefs)`; if no tool calls, return the content; otherwise append the assistant message (with optional tool calls) and each tool result message to `session`, then set `messages = system + session.Messages()` and repeat.  
     - Returns the final assistant text reply.  
   - **`Process`** remains unchanged and continues to work as today (stateless, no session).
   - Agent package must depend on `internal/session` only for `ProcessWithSession`; no need to expose session types from agent.

3. **`cmd/buildmax` (prompt mode)**
   - **Wire prompt mode**: When the user runs `buildmax -p PROMPT`, create one session with `session.NewSession("")` and call `ProcessWithSession(ctx, session, PROMPT)` instead of `Process(ctx, PROMPT)`. Each run of the process gets a new session (no persistence in this task). Output and error handling stay the same (print reply, exit on error).

4. **Tests**
   - **`internal/session`**: Unit tests that (1) `NewSession(title)` produces a session with `ID()` a valid UUID (non-empty, parseable as UUID), `Title()` equal to the given value, `CreatedAt()` set to a time close to the test run (e.g. within a few seconds of `time.Now()`), and `Messages()` empty; (2) after `Append` of one or more user/assistant/tool messages, `Messages()` returns a copy with the same length and order, and a second call to `Messages()` still matches (copy is independent); (3) appending and then calling `Messages()` returns the new messages (session state is updated).
   - **`internal/agent`**: Unit test for `ProcessWithSession`: use a mock LLM that returns a final reply on the first call; call `ProcessWithSession` twice with the same session and two different user messages; assert that (1) the session’s `Messages()` contains both user messages and the assistant reply(ies) in order, and (2) the second call’s LLM invocation receives the full history (system + first user + first assistant + second user). This can be done with a recording mock that stores the `messages` passed to `ChatWithTools` on the last call and asserts on length and roles/content.

5. **Dependencies**
   - One new external Go module for UUID: **`github.com/google/uuid`** (or equivalent) for generating session ids. All other code uses `internal/llm` and existing agent/llm types.

## Out of scope (for later)

- Persistence: saving/loading sessions to/from file or database.
- Session manager or registry (create/list/get/delete multiple sessions).
- TUI integration: session list, session picker, or wiring TUI to `ProcessWithSession`.
- Auto-setting session title from the first user message.
- Truncation or summarization of long histories (e.g. token limits).

## Acceptance

- [ ] **Session type**: `internal/session` defines `Session` with id (UUID), title, created_at (timestamp), and conversation history; `NewSession(title)` generates a new UUID and sets created_at; `Append(msg)`, `Messages()` (returns copy), `ID()`, `Title()`, `CreatedAt()` (and optionally `SetTitle`) are implemented and exported.
- [ ] **ProcessWithSession**: `Agent.ProcessWithSession(ctx, session, userMessage)` appends the user message to the session, runs the agent loop using system + session history for each LLM call, appends all assistant and tool messages to the session, and returns the final reply. `Process` behavior is unchanged.
- [ ] **Session tests**: Unit tests in `internal/session` cover NewSession (UUID format, CreatedAt), Append, Messages (copy semantics and order), ID, Title.
- [ ] **ProcessWithSession test**: Unit test in `internal/agent` verifies that two turns with the same session result in session history containing both user messages and assistant reply(ies), and that the LLM sees the full history on the second turn.
- [ ] **Prompt mode**: `buildmax -p PROMPT` creates one session with `session.NewSession("")` and calls `ProcessWithSession(ctx, session, PROMPT)`; each run gets a new session.
- [ ] **Build and test**: `./make build` and `./make test` pass.
