第一阶段，统一身份基础。

目标不是“能登录”，而是把三个用户端真正纳入同一身份体系。这里建议先把 Portal、Desktop、buildmax TUI 统一看成 user client，把 buildmax-worker 明确看成 runtime component。

这一阶段的交付应包括：
Portal / Desktop / buildmax 都具备 login/logout。
统一 token/session 模型。
统一 client auth abstraction。
本地 credential storage 方案定下来。
worker 不持有用户长期凭证，只使用 task-scoped 或 runtime-scoped credential。

这一阶段最关键的设计决策是：
Desktop 和 TUI 是否都采用 browser-based login。
token 是 access token + refresh token，还是 session + short-lived access token。
logout 是仅本端失效，还是服务端也撤销 refresh/session。

我会建议这里先做最小闭环：
先让 buildmax 和 Desktop 都支持 `login / logout / whoami` 语义，
先不做太复杂的多账号切换。

第二阶段，实时事件骨架。

目标不是“把 SSE 换成 WebSocket”，而是把 portal 会话机制改造成真正的事件驱动。

这里建议先定义统一事件模型，再落 WebSocket。否则后面很容易只是把 SSE 语法机械改写一遍。

这一阶段建议的核心事件类型可以先收敛成几类：
conversation.message.delta
conversation.message.completed
task.status.changed
task.run.started
task.run.completed
artifact.created
system.error

先少，不要一开始定义太多。

这一阶段的交付应包括：
Portal conversation transport 改为 WebSocket。
前端具备自动重连能力。
服务端支持主动推送消息和状态。
Tier 1 agent 可以在异步场景下主动回推内容。
Portal 页面能同时显示消息流和任务状态变化。

如果你要压缩范围，我会建议先只服务于 portal conversation，不急着马上把所有后台事件都并进去。

第三阶段，cron trigger。

目标是让系统第一次具备“无用户实时输入也能启动执行”的能力。

这一阶段其实是在验证你的执行模型是否真的脱离单一聊天入口。建议从非常克制的范围开始，不要一开始就做复杂 scheduler UI。

最小可行范围可以是：
用户为 agent 或 task 创建 cron trigger。
系统按计划创建一次新的 task_run。
执行结果能回到原 conversation，或生成新的系统消息。
失败状态可见。

这里需要尽早定的规则有两个：
cron trigger 是绑定 agent，还是绑定 conversation，还是绑定 task template。
触发执行后，结果进入原会话，还是产生新会话。

我倾向于：
先绑定 agent 或 task definition，
每次触发生成新的 run，
结果写入一个固定 conversation thread 或 activity stream。
这样模型更稳。

第四阶段，Telegram integration。

Telegram 不应该被实现成“另一个专用逻辑分支”，而应该只是新的 chat channel adapter。

这一阶段建议的目标是：
Telegram 用户发消息
→ 映射到平台内某个 user identity
→ 进入同一套 Tier 1 conversation pipeline
→ 结果通过 Telegram 返回
→ 如有需要，也能同步到 portal

一开始先做单用户绑定和单 bot 模式就够了。不要一开始就碰复杂多 bot、多 workspace、多团队映射。

Telegram 最小闭环建议是：
用户在 Portal 中绑定 Telegram 账号。
Telegram 发来的消息可以创建或续接 conversation。
Tier 1 agent 正常回复。
运行状态和最终答复可返回 Telegram。
Portal 至少能看到这条会话记录。

按执行顺序，我会建议这样排：

1. 统一 auth abstraction
2. buildmax TUI login/logout/whoami
3. Desktop login/logout
4. Portal auth 对齐与清理
5. 定义 conversation event protocol
6. Portal WebSocket conversation
7. 服务端主动推送 Tier 1 消息
8. cron trigger 最小闭环
9. Telegram account binding
10. Telegram message channel 接入

如果你想把它变成更明确的里程碑，我会这样定义。

M1：用户端身份打通
验收标准：用户能从 Portal、Desktop、buildmax 任一端登录，并被系统识别为同一身份。

M2：Portal 实时事件化
验收标准：Tier 1 agent 可以主动向 portal 推送消息和状态，不依赖单次请求响应。

M3：系统可定时执行
验收标准：用户可创建 cron trigger，到点后系统自动发起 run，并可见结果。

M4：系统具备首个外部 IM 入口
验收标准：用户可通过 Telegram 与系统对话，消息进入统一会话模型。

如果你问我哪一块最值得你现在立刻开始，我会说不是 Telegram，而是这两件事：
先定 auth model，
再定 conversation event model。

因为这两个一旦定了，后面做得会顺很多；如果这两个没定，Telegram 和 cron 都会把系统内部边界搅乱。

你们现在已经完成了“核心执行能力 + 多入口雏形 + 基本产品壳”，但距离“可以对外试用”的版本，还差三类东西：

我会这样重新审视当前进度。

目前已经基本具备的能力

从代码现状看，你们已经有这些非常关键的基础：

一，执行主链路已成型。
server / scheduler / worker / shared agent runtime 这条链已经不是 stub，而是完整可运行的形态。Tier 1 会话入口和 Tier 2 task/task_run 后台执行边界也已经落到了代码里。

二，Portal 已经不是空壳。
它已经有登录注册、会话页、task 详情页、artifact 视图、文件上传、settings 等核心页面，说明“Web 端试用入口”基本具备产品轮廓。

三，Desktop 已经不是 demo。
桌面端已经能列 session、看历史、发消息、收流式输出，这说明它已经是一个可工作的本地聊天入口。

四，共享 GUI 和 shared runtime 已经打底。
这意味着后续 buildmax TUI、Desktop、Portal 之间不是三套完全割裂的产品，而是有机会统一成一个系统。

所以，问题不是“能不能跑”，而是“用户第一次进来，能不能顺畅完成一个完整体验，并且第二天还愿意继续用”。

从试用版视角看，当前主要差距

我把差距分成 8 个维度。

1. 多客户端身份体系还不完整

这是当前最明显的差距之一。

Portal 虽然已有登录注册，但 Desktop 和 buildmax TUI 还没有纳入统一登录体系。对试用用户来说，这会直接导致两个问题：
第一，他无法把 Web、Desktop、TUI 当成同一个产品使用；
第二，你无法稳定地把 conversation、artifact、resource、quota、trigger 绑定到同一个身份之下。

这意味着现在的 Desktop 更像“本地聊天工具”，而不是 BuildMax 的正式客户端。

试用版至少需要做到：
Portal / Desktop / buildmax 都能 login/logout；
同一个用户在三个端被识别为同一身份；
buildmax-worker 不参与用户登录，只使用运行时凭证。

2. Portal 的实时通信模型还不够“平台化”

现在 Portal conversation 是 SSE，这对于“单次发问 -> 单次流式返回”还够用，但对你要做的系统不够。

因为一旦进入下面这些场景，SSE 模型就开始显得别扭：
Tier 1 agent 主动回推消息；
后台 task_run 状态变更；
cron 自动触发执行后结果推回页面；
Telegram 发来的消息同步到 Portal；
多端同时看到同一 conversation 更新。

所以，试用版若想让用户感觉它是“活的系统”，不是一次性聊天页，Portal 必须进入 WebSocket 模式，并建立统一事件模型。

试用版至少需要做到：
Portal conversation 改为 WebSocket；
支持服务端主动推送；
前端支持连接恢复；
至少能推送 message delta、message completed、task status changed 这几类事件。

3. 触发器能力还未形成闭环

cron trigger 是对外试用非常重要的一项，因为它代表系统不只是“我问一句，你答一句”，而是具备主动执行能力。

如果没有 trigger，试用用户看到的更像“另一个 chat agent”；
如果有 trigger，用户才会开始把它理解为“帮我做事的系统”。

当前这块显然还没闭环。试用版至少要有一个最小模型：
用户创建 cron trigger；
系统到点自动创建 task_run；
结果能回写到某个 conversation 或 activity stream；
用户能看见成功/失败。

不需要一开始就做复杂 UI，但能力闭环必须有。

4. 外部聊天入口还没接上

Telegram integration 的价值不只是“多一个渠道”，而是验证你整个系统是否真的脱离 Portal 独立存在。

如果试用版只支持 Portal，那用户会把它理解为一个网站。
如果试用版支持 Telegram，那用户会开始理解它是“一个可以通过不同渠道触达的 agent system”。

但 Telegram 要落地，不是只做收发消息接口，还要解决这些问题：
Telegram 用户如何绑定平台账号；
一条 Telegram 消息映射到哪个 conversation；
回复如何返回 Telegram；
是否同步到 Portal；
权限和配额按谁计算。

也就是说，Telegram 本身是建立在 auth + event model 之上的。

5. 用户试用的“第一次成功体验”还不够完整

这是很多技术团队最容易忽略的点。

即使底层能力已经很多，试用用户最关心的不是架构，而是：
我注册后能立刻干什么；
系统能帮我完成什么；
结果在哪里看；
失败了我怎么知道原因；
我下次回来还能继续吗。

现在从你描述的现状看，功能很多，但试用用户的“首日体验路径”还不够清晰。比如：

进入后默认该做什么；
如何开始一次 conversation；
什么时候会进入后台 task；
task 和 conversation 的关系是否对用户足够清楚；
artifact 什么时候出现、在哪里看；
Desktop 和 Portal 是否形成一致认知。

试用版通常需要一个非常明确的 first-run path，而不只是“页面已经很多”。

6. 连接器能力还不够，真实使用场景会受限

你前面已经识别出 connectors 是下一阶段重点，这判断是对的。

没有连接器，用户能做的事情会被限制在：
手动输入 prompt；
手动上传少量文件；
看系统返回结果。

这对试用来说可以启动，但很快会碰到上限。尤其是你后面想把它做成真正的工作系统，而不是单纯聊天产品。

不过这里有个现实判断：试用版不一定要一口气做很多 connector。
但至少需要一个能代表真实价值的接入点，哪怕只是：
GitHub；
本地文件；
Telegram；
Webhook。
否则用户很难产生“这个系统能进入我的工作流”的感觉。

7. 运营护栏还不够完整

从试用版角度，这一块非常关键，但常被低估。

你们已经有 quota checker 的雏形，这很好，但试用期至少还要补齐这些能力：

用户级 usage 统计；
基本配额限制；
失败时明确错误提示；
任务状态可靠展示；
最基本的 webhook / bot key / token 安全处理；
基础审计日志。

因为一旦给真实用户试用，没有这些护栏，很容易出现：
有人刷爆资源；
任务失败但用户无感知；
凭证问题难排查；
你自己也看不清谁在用、怎么用、哪里坏了。

8. 产品语义虽然在收敛，但仍需再打磨

你们现在从 workspace-centric 向 user / conversation / task / task_run 转，这个方向是对的。但对试用版来说，还要多问一步：

这些概念是否已经足够让普通用户看懂？

因为工程上合理，不等于产品上自然。比如：
conversation 和 task 的区别是否显而易见；
task detail 为什么单独存在；
artifact 对用户来说是不是结果文件；
Desktop 的 session 是否就是 conversation；
Portal 里的命名是否已经统一。

如果这些不统一，试用用户会觉得系统“能力很多，但理解成本偏高”。

我会把“推出试用版前需要完成的功能”分成三档。

第一档：必须完成，否则不建议开放试用

这一档是“试用版底线”。

1. 三端统一身份闭环
   Portal / Desktop / buildmax 支持 login/logout；
   同一用户身份贯通三端；
   buildmax-worker 使用 runtime credential，不持有用户长期 token。

2. Portal WebSocket 化
   至少支持 conversation 消息主动推送；

3. 明确的试用主路径
   用户注册后能快速开始一次 conversation；
   后台 task 的进入逻辑清楚；
   结果和 artifact 可见；
   失败时有明确信息。

4. 基本配额与运行护栏
   用户级 usage 统计；
   基本 quota；
   任务失败状态可见；
   超限或错误有用户可理解的反馈。

5. 基本的运行可观测性
   至少你们自己能看见：
   谁发起了什么；
   哪次 run 卡住；
   为什么失败；
   资源消耗大致情况。

第二档：强烈建议在试用前完成

这一档不是绝对底线，但会显著影响试用效果。

6. cron trigger 最小闭环
   用户可以创建一个简单定时任务；
   系统会自动跑；
   结果可回写到 conversation 或 activity。

7. Telegram integration 最小闭环
   账号绑定；

8. 更清晰的 conversation/task/artifact 关系呈现
